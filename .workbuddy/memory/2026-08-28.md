## 评估：日版 AXVJ 接入美版 text.c / pokeRS 式少量 hook（仅评估，未改码）

### 一手静态发现（capstone 级手工反汇编 + ROM 字节比对）
- **JP 原生 PrintNextChar @0x080032F8 只有 144 字节**（0x080032F8–0x08003387）。
  结构：取字符 & index++ → `c-0xFA` 跳转表（6 项 @0x08003324）→ 否则
  `FontFuncTable[win+0x0A](win, c)` 经 `CALL_VIA_R2 @0x081B12DC`，返回 1。
- **JP 已有与美版同构的两级分发表，且在 ROM（纯数据）**：
  - `FontFuncTable[4]` @**0x081BB3AC** = tm0 0x08003569 / tm1 0x0800360D / tm2 0x0800338D / tm3 0x08003495
  - `FontSubTable[7]` @**0x081BB3BC** = font0,3→0x08003585 / font1,4→0x080035A1 / font2,5→0x080035C9 / font6→0x080035E5
    （第 8 个 word 是 0x00010408，非指针 → 表长就是 7，勿越界）
  - 引用点全为 literal pool 取址：0x081BB3AC 被 0x080032B0、0x08003388 引用；
    0x081BB3BC 被 0x0800362C（PrintGlyph_TextMode1 内）、0x08003F38（未标定）引用。
    无 memcpy → **ROM 直改有效**。
- 原生步进是内联常量（非宽度函数）：
  - tm0 @0x0800356E–0x0800357A：`tileDataOffset(+0x18) += 2` 然后 `cursorTileX(0x1B) += 1`
  - tm1 @0x0800360C：`FontSubTable[fontNum](win,c)` 然后 `cursorTileX(0x1B) += 1`
  - tm0 内层调用 `sub_8002D50(win,glyph)`；FC 处理在原生 `0x08003110`；FA/FB 调 `0x0800304C`。
- **ABI 不同构（决定性否决点）**：pokeruby `struct Window`（即 TextPrinter）与 AXVJ 字段全错位
  - US: textMode 0x00 / fontNum 0x01 / cursorX 0x10 / state 0x16 / tileDataStart 0x1A / textIndex 0x1E / text 0x20 / template 0x2C（0x30 字节）
  - JP: template 0x00 / state 0x04 / textMode 0x0A / fontNum 0x0B / textIndex 0x14 / text 0x10 / tileBase 0x16 / cursorX 0x1A / cursorTileX 0x1B
  → 4393 行 US text.c 里每个 `win->x` 都会读写错字段。
- `WindowTemplate` 也不同：US 0x1C 字节（tileData 0x10 / tilemap 0x14，含 spacing/tilemapLeft/tilemapTop）；
  JP 0x14 字节（tileData 0x0C / tilemap 0x10）。模板同时被 bg/window 绘制代码读取 → 改布局会级联。
- `link/game.ld` 只有 `ROM : ORIGIN=0x08800000, LENGTH=0x10000`，**无 .data/.bss**；
  US text.c 需要 sGlyphBuffer(132B)、gStringVar1..4、gBGTilemapBuffers(8KB) 等可写静态量。
  game.bin 现 15032 B / 65536 B。ROM 空间本身不是瓶颈（已扩到 ≥0x09EA0000）。
- `TranslateHandleChar` 拦截**每一个**字节（`c != 0xF9` 时走 slot_lookup），不只是 F9 →
  薄前端方案必须保留 slot 查表，且未命中时要 index-1 再回跳原生体。

### 结论（已向用户交付，未实施）
- **方案 A（接入美版 text.c 完全桥接）**：否决。ABI 错位 + 数据资产不对 + 无 RAM 段 + 零语义增量。
  绘制数学已 vendored 在 `reference/pokeruby/draw_glyph_tile.c`（~700 行）+ `reference/pokeemerald/copy_glyph_to_tiles.c`，
  不需要拖进整个引擎。
- **方案 B（pokeRS 式少量 hook）**：精神采纳，点位替换。JP 无 GetGlyphWidth/GetStringWidth/DrawGlyphTiles
  （前人已证伪），但**改两张 ROM 分发表 = 11 个 word 的纯数据补丁**，比 pokeRS 在函数体中间插桩更干净。
  可删掉 PrintNextChar_hook.c 中重建的 HandleExtCtrlCode(95 行)+FA~FF 状态机(~60 行)+箭头(~38 行) ≈ 190 行。
  12px 步进与半列相位**无论走哪条路都省不掉**。
- 现有 hook 数已是 pokeRS 量级：PrintNextChar + MapNamePopup + UnusedPrintMonName +
  DrawOptionMenuChoice + UpdateNickInHealthbox(3 池 4 处) ≈ 10 处；pokeRS = 3 引擎 + 5 场景 = 8 处。
  **问题不在 hook 数量，在被 hook 函数内部手写了太多引擎该干的事。**
- 建议优先级：① 改分发表（需先 RE tm2 0x0800338D / tm3 0x08003495 / 0x08003F38 调用者）
  ② 相位从全局 8 槽 LRU(0x0203FF80) 迁入 printer 结构体空闲字段（需先标定 0x1E/0x1F 是否被用）
  ③ 测量侧（居中/换行）另立一案，与打印侧正交，一个钩子都少不了。

### 顺带记
- `sPcsTm1FontFuncs[8]` 按 8 项建，但原生 FontSubTable 只有 7 项 → `fontNum & 7` 有读越界风险。

## 设计稿：text 汉化重构 —— 接管分发 + 薄桥接层（docs/PLAN_TEXT_BRIDGE_REDESIGN.md）

### 核心结论（重要，后续勿重复论证）
- **美版 text.c 不能整体搬到 AXVJ**：依赖 ① US `struct Window` 布局（与日版全错位）
  ② `gCurGlyph` 全局 RAM（我们无 RAM 段） ③ `sFonts` 指向 US ROM 地址。三样全不满足。
- **真正的杠杆是日版官方原语**，不是美版源码。尤其 `sub_8003630(glyph, dst, font, fg, bg, shadow)`
  **dst 是参数** → 比美版 `DrawGlyphTile_*` 写死 `gCurGlyph` 更好桥接。
- **日版唯一真正缺的是「像素级游标」**（美版 `cursorX` 像素级 `AddToCursorX`；
  AXVJ 只有 +0x1B `cursorTileX` tile 级）。连带必须自己补：分配器 + 像素步进 + 半列相位。
- 美版只借**语义**不借代码：像素游标语义 + 宽度表（压成 switch 8/12/16，比表更省）。

### 三层架构
- L0 唯一 hook：拦截 glyph 绘制公共入口，不再按 textMode 分 4 套分支。
- L1 `bridge.c`（~250 行，我们写）：`chs_alloc` 唯一分配器 / `chs_add_px` 唯一像素步进 /
  `chs_paint` 分派（汉字 4bpp 直搬，其余交 `sub_8003630`）/ `chs_emit` UpdateTilemap 封装。
- L2 ROM 原语零维护：0x08003630 sub_8003630、0x080036DC UpdateTilemap、
  0x08003110 HandleExtCtrlCode、0x08003F4C DrawInitialDownArrow。

### 修 P1 bug 的原理（关键铁律）
P1 翻车根因 = 中文走我们的 pitch 分配、日文交还原生落址（`win[0x16]+win[0x18]`）
→ **同一窗口两套 tile 空间** → 混排时数字错位、箭头落点错。
**新设计铁律：所有字符（含日文/ASCII/数字）一律走 `chs_alloc`，只是像素交给官方画。**

### 行数预估（现状 1730 → ~1530，−12%）
- `PrintNextChar_hook.c` 415 → ~120（塌缩成一个 `Chs_DrawGlyph` 调用）
- 新增 `bridge.c` ~250
- `text_render.c` 575 → ~420（删与 hook 重复分支）
- `text_scene.c` 233 / `text_translter.c` 507 **原样保留**（场景门控+码位查表，日版不提供，借不来）
→ 省不掉的大头 = tile 分配 + 场景门控 + 相位，这三样桥接层借不来。

### sub_8003520 @0x08003520（tm0 内核，纯函数、零状态推进）—— 已完整解出
```c
void sub_8003520(win, glyph) {
    u16  tileIdx = win[0x16] + win[0x18];              // 唯一分配器（线性追加）
    u8  *dst     = win->template->tileData + (tileIdx<<5);
    sub_8003630(glyph, dst, win[0xB], win[0xC], win[0xD], win[0xE]);
    UpdateTilemap(win, tileIdx, tileIdx+1);
}
```
FontFunc_tm0 @0x08003569 = sub_8003520 后 `win[0x18] += 2; win[0x1B] += 1;`

### 三个决定性结论（后续勿再重复论证）
- **A. 日版不缺分配器**（推翻前稿判断）。`win[0x16]+win[0x18]` 就是线性追加分配器，
  与 windowId/场景/charblock 无关；`dst` 由 tileIdx 派生 → 控 `win[0x18]` 即控落址。
  **sub_8003630 的 5 参 fontNum/fg/bg/shadow 全部取自 win[0xB]/0xC/0xD/0xE**
  → 前稿"未决风险 2（参数来源待实证）"已解决。
- **B. scene 门控根因**：`scene_gctn_linear` = `win[0x16]+win[0x18]+2*xOff+yOff`，
  原生裸值里没有后两项；而 text_render.c:346/396/468/560/568 **确实在推进** `win[0x18]+=2`。
  → 同一游标被两套公式解释。mode2 更极端，另起 `y*GRID_W+x+band+base+origin` grid。
  **门控存在的唯一理由 = 猜这个窗口该用哪套坐标系。回归原生协议 → 门控整体可删。**
- **C. 替换 BUG 机制**：不是"两套 tile 空间并存"，而是**两套公式解释同一个游标**。
  中文落址用 xOff/yOff 或 grid 公式，日文交还原生用裸 `win[0x16]+win[0x18]`
  → 中文落后则被日文覆盖（替换）；超前则占日文位并留空洞（数字错）。
  "让日文也走我们通道"只是统一公式的 workaround，正解是**废弃我们的公式、回归原生**。

### 新设计：接管绘制，其余交还原生（约 12 行）
```c

u8 *dst = tpl->tileData + (tileIdx<<5);
is_chs(glyph) ? chs_blit(glyph,dst) : sub_8003630(glyph,dst,win[0xB],win[0xC],win[0xD],win[0xE]);

```
可删：pitch 分配器、行相位表(8 slot @0x0203FF90)、scene 门控(233 行)、
mode2 grid、CHS_LAST_OFF_ADDR 回滚。

## 【BUG 修复】中文字模漏调色板烘焙 → 蓝底白条 / 透明透背景

### 症状（用户实测第二轮）
1. 开始游戏界面彻底乱：文字变成**蓝底 + 白条**
2. 对话框文字**透明透出背景**

### 根因
中文字模是 **2bpp 索引**，必须经 `CopyGlyph2bppTo4bpp_Origin(src, dst, fg, shadow, bg)`
烘焙成 4bpp 才能落 VRAM。我在 `FontFunc_hook.c` 的 `chs_blit()` 里直接
`copy_tile32(dst, &g.gfxBufferTop[0])` 搬原始数据 → **2bpp 索引值被当成 4bpp 调色板号**。
旧路径 `DrawGlyphTile_refpr`(text_render.c:221) 正是用 CopyGlyph2bppTo4bpp 烘焙的，
重写时漏了这一步。

### 修复（chs_blit）
```c
uint8_t fg_ov  = *(volatile uint8_t *)ADDR_OPT_FG_COLOR;
uint8_t color_c = (fg_ov != 0u) ? fg_ov : win_u8(win, WIN_COLOR_C);
uint8_t color_d = win_u8(win, WIN_COLOR_D);
uint8_t color_e = win_u8(win, WIN_COLOR_E);
DecompressGlyph_Chinese(&g, glyph, font);
CopyGlyph2bppTo4bpp_Origin(&g.gfxBufferTop[0],    dst,      color_c, color_e, color_d);
CopyGlyph2bppTo4bpp_Origin(&g.gfxBufferBottom[0], dst + 32, color_c, color_e, color_d);
```
注意参数顺序 = (src, dst, **fg=c, shadow=e, bg=d**)。

### 为什么第一轮 tm0 原型"对话正常"却没暴露
第一轮只有 textMode==0 走新路径；**对话大概率不是 tm0**（可能是 tm3 grid），
仍走旧路径（有烘焙）→ 正常。第二轮所有 tm 都走新路径后，中文的无烘焙才全面暴露。
→ 教训：判断"某场景走哪个 tm"不能靠猜，gdb 脚本已加 tm 列。

### 教训（通用）
**重写渲染路径时，必须把旧路径的"像素后处理"全链路搬过来**，
不能只搬落址。旧路径 DrawGlyphTile_refpr 的完整链路是：
`CopyGlyph2bppTo4bpp(烘焙) → 按 startPixel 移位 → need_spill 溢出 tile 处理 → map_at`。
新 chs_blit 目前只做了烘焙一步（8px 字模 startPixel 恒为 0，暂不需要移位/spill）。

## 【BUG 修复 7】栈溢出崩溃 PC=0xF81FFF1E

### 现象
mGBA 报 F81FFF1E（非法地址，典型"栈被冲、返回地址变垃圾"）。
gdb_patcher_log 显示崩溃前最后 InitTextPrinter 的文本是 `a6 a6 f9 00 10 8c ff`
= '５５只'（全角数字×2 + 汉字），**textMode=3**、fontNum=3、TILE_BASE=0x0001。

### 根因
上一轮为了让非中文也走相位，新增了栈上缓冲，在 tm3 这条深调用链上压爆栈：
- `native_via_phase()` 里 `uint8_t tmp[64]`
- `chs_refpr_nobake()` 里 `dest_words[8] + spill_words[8]`（64B）
两层叠加 ~130B，超出 GBA 剩余栈（IWRAM 栈顶 0x03007F00，游戏已占大半）。

### 修复（零栈占用）
1. 临时缓冲改**固定 RAM**：`#define CHS_TMP_ADDR 0x0203FF8Cu`（64B）
   安全区 0x0203FF80-0x0203FFCF 内分配：
   0x0203FF84=px相位 / 0x0203FF88=base_tx / 0x0203FF8C-0xCB=字形缓冲
2. `chs_refpr_nobake()` 改 **in-place** 直接读写 dest/spillTile，不开局部数组。

chs_blit 224B / chs_core_ex 112B / chs_refpr_nobake 56B / chs_tile_num 16B
→ 非中文路径栈占用大幅下降；chs_blit 的 224B 主要来自 struct TextGlyph(128B)，
  属既有占用（中文路径一直这么跑，未溢出）。

### 教训
**GBA hook 里禁用栈上数组**：game.bin 无 RAM 段，全局落 ROM 不可写，

## 【BUG 修复 8】sub_80033B4 写 dst+960 → 冲掉游戏数据（31-39.PNG）

### 现象
31/32/33/34/35/36/37 基本正常（110号道路、119号道路、真伤脑筋、图鉴 No03-07 全对）。
**38.PNG 图鉴详情页**：`No花番`、`たかさ 约．花`、`おもさ 花花．花`
→ **所有数字位被汉字"花"替代**。39.PNG 队伍名也异常。

### 根因（反汇编铁证 0x08003424-0x08003430）
tm3 用的 `sub_80033B4` 把 lower 写到 **dst + 960**：
```asm
0800341A: mov  r1, r8             ; upper → dst
08003420: bl   CopyGlyph1bppTo4bpp
08003424: ldr  r0, [sp,#8]        ; lower 源
08003426: movs r1, #0xf0
08003428: lsls r1, r1, #2         ; = 960
0800342A: add  r1, r8             ; ★ dst + 960
08003430: bl   CopyGlyph1bppTo4bpp
```
因为 tm3 的 upper/lower 在 VRAM 里相隔 30 个 tile（idx 与 idx+30，30*32=960）。
而 native_via_phase 的临时缓冲只有 64B → 每画一个非中文字符就往 tmp+960 写 32B。
- 缓冲在**栈**上时 → 写穿栈 → 崩溃 PC=0xF81FFF1E（上一轮）
- 缓冲改**固定 RAM** 0x0203FF8C 后 → 冲 0x0204034C 一带的游戏数据 → 数字位变汉字

### 修复
`draw_native()` 统一用 **sub_8003630**（写 dst 与 dst+32，upper/lower 相邻），
不再按 textMode 切到 sub_80033B4。DrawGlyph_Tm3_Origin 保留备用（加 unused 属性）。
game.bin 14284 → 14260 B

### 已排除的嫌疑（不要再查）
- slot 表格式：正确（magic='SLT2'、n_buckets=256、max_jp=51、数据区 0x40C~0x6C1A）
- slot 查表逻辑：用 Python 复现 FNV-1a 哈希匹配，'ユウキ'(75 53 57) → match_len=3、
  中文流 2 字，**正确**
- 全角数字 0xA1-0xAA 走 slot：**无匹配**（走 fallback DrawGlyph，符合预期）

### 教训（通用）
**给 ROM 原语传"临时缓冲"前，必须先反汇编确认它的写入跨度和布局假设。**
sub_8003630 / sub_80033B4 虽然签名相同（glyph,dst,font,fg,bg,shadow），
但 lower 的落点完全不同（+32 vs +960），不能互换。

## 【BUG 修复 10】缺「连续性校验」→ px 跨绘制会话累加，文字横向铺满屏幕

### 症状（用户 4 张截图）
- 来回移动后，**路名弹窗 + 对话两批字同时横向铺满整屏、互相穿插**（"118号道路""119号道路"交错）
- 图鉴数字/说明内容不对（"这不是简单的替换 BUG"）
用户比喻："私有变量的值直接追加到公有变量" —— 方向完全正确。

### 根因（查 bak 才确认，旧实现有、我漏了）
旧 `DrawGlyphTiles_common`(bak/text_render.c:436-453) 命中槽时有一层连续性校验：
```c
if (st->chs_px != 0 && cur_tx <= st->base_tx)          → px=0, 重捕 base_tx
else if (st->chs_px != 0) {
    expect = base_tx + ((chs_px + last_adv - 1) >> 3);
    if (cur_tx != expect)                               → px=0, 重捕 base_tx
} else  st->base_tx = pitch_capture_base_tx(win);       /* = win[0x1B] */
```
我只管累加 px。同一窗口重开一次绘制（路名弹窗重复触发、图鉴滚动重绘行）时，
引擎把 win[0x1B] 拨回行首，槽里的 px 却接着涨 → 一路往右铺、多串互相穿插。

### 修复（FontFunc_hook.c）
- `phase_bind()` 命中槽时加入同样两条校验（+ char_base=tpl[1] 参与 key 匹配，同旧）
- 槽结构加 `last_adv`（8B：key u16 / px u16 / btx / last_adv / gen / char_base）
  → PHASE_GEN_ADDR 由 0x0203FFB4 移到 **0x0203FFC4**（槽区 8×8B=64B 占 0xFF84-0xFFC3）
- `chs_sync_tilex(win, slot, px, adv)` 改为**旧式**：`curTX = btx + ((px + adv - 1) >> 3)`
  （我原来写 `((px-1)>>3)` 与旧的 expect 式不配对，会误判换会话）
  ★ 教训：**写入式与校验式必须严格配对**，旧式对 12px 会多进 1 列，但自洽且已跑通。

### 已核对：我的两趟 spill 与旧实现逐行同构
旧 `DrawGlyphTiles_core`(297-419) 确认：
- tile 号 = `base + off + 2*xOff + yOff`（**线性分配，与屏幕列无关**）
- 屏幕列由 `map_at(win, map_tx, abs_u, abs_l)` 单独写入 tilemap
  → 12px 靠"tilemap 显式映射"解耦，不需要 tile 号对齐屏幕列。我的实现与之等价。
- pass2 的 `startPixel` 复用 pass1 的值是正确的：(px0+8)&7 == px0&7。
