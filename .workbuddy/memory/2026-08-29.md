### 2. 文本引擎架构（hook/src/text/，2026-08-28 定型的 textMode 分派制）

**主控 `PrintNextChar_hook.c`**（全局唯一 ROM hook：P01@0x032F8 → entry.s EngineEntry）
- 特例：tm1+font4+tilemap0 → `PrintNextChar_Origin` 整窗交官方（血条/队伍窗）
- 控制码 0xFA/0xFB(翻页箭头,含 `arrow_inplace12` 相位对齐)、0xFC(→HandleExtCtrlCode
  FC 子类型 1..16)、0xFD/0xFE/0xFF；0xEF 菜单光标
- `TranslateHandleChar` 翻译链路（F9 协议/slot）→ `DrawGlyph`
- `DrawGlyph`：SYM 标点带自绘；≥0xF7 直接消费（缺字=排查信号）；
  否则 `sPcsPrintFuncs[textMode & 7]` 两级分发

**落址桥接 `FontFunc_hook.c`** — `Chs_FontFunc_hook(win, glyph, is_chs)` 按
`win[0x0A]` 分派四套**原生**协议（反汇编实证，见 docs/调研_20260828_原生tm0协议与替换BUG根）：

| tm | 入口 | 落址公式 | 推进 |
|---|---|---|---|
| tm0 | 0x08003569 | `win[0x16]+win[0x18]` | `win[0x18]+=2; win[0x1B]+=1` |
| tm1 | 0x0800360D | ROM 预渲染查表，零 VRAM 写；中文借用线性+地板 `TM1_LINEAR_FLOOR=0x100` | `win[0x1B]+=1` |
| tm2 | 0x0800338C | `win[0x20]` 缓冲直绘 | `win[0x20]+=0x40` |
| tm3 | 0x08003494 | grid：`base+col+2+row*30` | `win[0x1B]+=1` |

- 12px 字模两趟 spill：pass1 宽 8（溢出 spill 到 N+1）、pass2 宽 4；
  相邻字共享 tile，必须经 `DrawGlyphTile_refpr` 移位，不能直接 copy_tile32
- 行相位存 8 槽 LRU `@0x0203FF84`（每槽 8B：key/px/btx/last_adv/gen/char_base），
  `phase_bind` 命中时**必须做连续性校验** `curTX == btx + ((px+last-1)>>3)`，
  否则残留 px 会累加 → 文字一路向右铺满整屏

**两个致命约束（写 C 时务必遵守）**
1. `game.bin` 是 freestanding 平坦镜像（link/game.ld 无 RAM 段）→ **全局变量落 ROM
   写入被硬件丢弃**。字形缓冲一律用栈上局部（`struct TextGlyph g`），
   跨调用状态只能放已验证安全区 `0x0203FF80-0x0203FFCF`
2. tm3 专用原语 `sub_80033B4` 会写 `dst+960`（upper/lower 在 VRAM 相隔 30 tile），
   对 64B 缓冲会写穿 → 非中文一律用 `sub_8003630`（写 dst 与 dst+32）

## 设置菜单乱码 BUG 修复（用户实测待验收）

### 现象
设置菜单所有选项行显示同样的碎片字形（"快 匦底 弋"），移动光标原生重绘后
依旧错误（"不看底 弋"）。gdb 日志：`src/util/work/POKEMON_RUBY_AXVJ00/gdb_patcher_log.log`

### 根因（新旧引擎对比 + gdb 实证）
设置菜单选项 = `DrawOptionMenuChoice_hook` 构造 dst（栈上，日志中 `文本=0x03007DD0`
即 IWRAM 栈）→ `MenuPrint_Text` → 每行一次独立 `InitTextPrinter` 会话，
win=0x0202E658、**textMode=1**、fontNum=3、TILE_BASE=1（882 条全部如此）。

- **gdb 实证**：每会话 `TILE_OFF(win[0x18])` 被原生重置回固定值——
  分布仅 5 个取值：0x102×538、0x106×324、0x108×11、0x10C×5、0x0×4。
- **新版**（8-28 分派制）tm1 中文 = 借用线性，游标就是 `win[0x18]`，且只有
  「off<0x100 才提升」的地板逻辑（0x102>0x100 根本不触发）→ **每行都从同一
  tile 起写**：行间互相覆盖 + 踩预渲染字库区 → 全屏同样的碎片。
- **旧版**（bak/text_original）`screen_menu_mode2` 命中走 **mode2 grid 位置式
  寻址**，tile 位置只由 cursor 字段决定，与 win[0x18] 无关 → 会话重置无害。
  8-28 重构删掉 grid 路线时，tm1 中文改线性借用，此坑随之而来。

### 修复（`FontFunc_hook.c`，最小侵入，保留分派制）
tm1 原生实证零读写 win[0x18]（调研_20260828 §6.1），借用安全 → 加**持久分配游标**：
- `TM1_ALLOC_CUR 0x0203FFC6`(u16) / `TM1_ALLOC_PAGE 0x0203FFC8`(u16)
  （PHASE 槽占 0x84..0xC3、gen@0xC4，此两字节空余）
- `chs_blit` tm1 分支：页指纹（template 指针^TILE_BASE）变化 → 游标重置
  0x100；否则恢复持久游标进 win[0x18]（替换原先只提地板的逻辑）
- blit 完成后把推进过的 win[0x18] 存回持久游标 → 同窗跨会话顺序推进，
  行间不再共用 tile
- 已知残余风险：同 charBase 的**同时可见**多窗（设置菜单顶部回显窗+主窗）
  页指纹不同、各自从 0x100 起写，理论上互踩；比修复前全屏乱码轻，待实测

### 修复 v3（确定性分区，替换 v2 行槽——v2 残余问题被第二轮 gdb 否决）
**v2 残余问题实证**（第二轮日志，同路径 01:09 采集）：
- **标签和值是同 curY 的不同会话**（值列 curX=15/18/19/20/22/23 vs 标签 curX=4，
  同 curY=5/7/9/11/13/15）→ 并发 key ≈ 8 标签+8 值+顶窗 ≈ 17 个，8 槽必轮转
  → 行内容串换（用户"移动光标会使得文本替换"）；顶窗槽被抢 → 顶窗残留
- **会话重置值有公式**：off = 0x100 + (curTX-1)*2，全部样本吻合
  （curTX=2/4/5/7 → 0x102/0x106/0x108/0x10C）。它可能恰好落在子区区间内，
  区间判定漏判 → 行首残留。另见 off=0x0 的特殊会话（IWRAM 短文本）。
- v2 行槽方案的"每行 12 tile"假设也错：标签+值分属两会话，各需独立区。

**v3 = 无状态确定性分区**（`tm1_row_base`，零分配器零槽零 RAM）：
- base = 0x100 + (curY>>1)*0x10 + (curX>=8)*0x8 —— 行 9 档 × 标签/值两子区，
  每子区 8 tile=4 字（"文字速度"恰好 4 字；值最长"立体声"3 字）
- 总占 0x90 ⊂ [0x100,0x1C8)；同会话重绘恒映射同子区 → 幂等、不漂移、不外溢
- 会话开始判定：off == 0x100+(curTX-1)*2（显式公式比对，防区间内漏判）
  或 off 出子区区间 → 恢复 base
- 已知边界：值文本变短时尾部字形残留（表项未清）；>4 字标签会溢出子区
  （当前菜单最长恰好 4 字）；curY>17 的 tm1 场景 row 全挤到 8

### 5. 重构合理性评估（应用户要求，反汇编复核）
产出：`docs/评估_20260829_text重构合理性反汇编复核.md`（完整版）

**反汇编新发现（修正既有认知）**：
- **N1** FontSub[0] 实际 `lower = upper + 0x100`（`movs r3,#0x80; lsls #9`），
  调研_20260828 §6.1 写 +1 是笔误；tm0 表项同样 +0x100（N2）。
  tm0/tm1 字库 = 上/下半行分离布局；仅 tm3 连续 grid。

验证就删）** / 非中文走相位✅。

实测章位应沉淀为声明式表。

**遗留风险排序**：R1 字库下半区重叠 > R2 UI 章 > R3 值变短残留 > R4 charBase
未实证（待 gdb 采 BGCNT）> R5 重置值公式单窗。

- **反汇编给布局不变量**（字库只引奇数槽、lower=upper+0x100、表项差 0x100

### v7（03:12 出 ROM，待实测）——修 off 推进 bug + 三种字宽分账

## ⛔ v9 前置：gdb 反算推翻「安全块 [121,322]」（重要，勿复用 v5-v8 布局依据）

用 `src/util/work/POKEMON_RUBY_AXVJ00/gdb_patcher_log.log`（02:04 采，v3 回退版）
重跑解析，得到三条**推翻性事实**：

### 事实 1：预渲染字库**写满整个 charblock**，不是"只引用 22 字模"
```
[IWTD] r0=0x081BB874 startOffset(r1)=0x0001 r2=glyph
   → glyph 0..255 连续 256 次，返回 r1 = 0x06008060/0A0/0E0/...（每 glyph +0x40 = 2 tile）
   → 落址 tile = 1 + glyph*2 ，实占 **[1, 513) = 512 tile**
```
**"22 字模"只是 tilemap 实际引用的稀疏集合，不等于 VRAM 占用。**
引用稀疏 ≠ 占用稀疏 —— v5~v8 整段「安全块 [121,322]」的地基**不成立**，
那 202 个 tile 上压着的是 128 个真实字形，这就是 R1（数字/问号被踩）的真身。
唯一真正干净的区域是 **[513, 1024) = 511 tile**（BG tile 索引 10 bit，上限 1023）。

### 事实 2：ITP 行的 curX/curY 是**上一会话的残留值**，不是本次的行列
- `[InitTextPrinter] ... curX/curY` = 打印**前**的 win 字段（上一会话结尾）
- `[CFF] ... curX/curTX/curY/curTY` = 打印**时**的真值
→ 之前按 ITP 的 cx/cy 推的「顶窗 curY=0 / 标签 curY=1,5,7..」全是偏移一位的。
**真值（以 CFF 为准）**：标题在 row=1，标签在 row=5,7,9,11,13,15,17（共 8 行）。

### 事实 3：设置菜单真实几何（tpl 0x081BB874, tm=1, fontNum=3, TILE_BASE=1）
- `win[0x1A]` = **本次会话的起始列**（不是窗口左边距）；`win[0x1B]` = 行内推进
  （旧 bak `x = win[0x1A] + tile_x` 正是这个语义，与 tm3 原生 `win[0x1A]+win[0x1B]+2` 同构）
- 列：标签恒 col=4；候选值 col ∈ {15,18,19,20,22,23}（**不是一个候选一个值，
  是该行所有候选并列**，每行 2~3 个独立 ITP 会话）
- 行（跨模板合计）：1 ~ 20，列 2 ~ 27
- ~~12px 连续 n 字 = 2n+2 tile~~ ⛔ **该式已作废**，见下方「tile 账目修正」；
  正解 12px = **4n**、8px = **2n**（v8 修掉 pass2 的 off 推进 bug 后重算）

### 矛盾（也是"为什么有 tile 限制"的准确答案）
| 方案 | 容量需求 | 能否装进 [513,1024) | 真问题 |
|---|---|---|---|
| 分配制（v5-v8） | ~140 | ✅ 余量 4 倍 | **不是容量问题**：需要预知"每行几个候选/每候选几字"，猜错就互覆 |
| 位置式 grid | ~627 | ❌ 溢出 116 | 无需预知文本结构，但 (行跨度 20 × 列跨 30) 撑爆 |

**所以"tile 限制"有两层，别混为一谈**：
1. **硬限制**：BG tile 索引 10 bit → 单 BG 最多 1024 tile；4bpp 下 1 tile=32B，
   一个 charblock(16KB) = 512 tile。tm1 的**设计前提**就是"字库独占 charblock、
   文本零 VRAM 分配"，所以它天生没给动态字形留位置 —— 这是 tm1 的**语义限制**。
2. **自限制**：我们把中文区挤进 [121,322]，是因为误以为那里是空的。

### v8 的具体死因（模拟确认，与"没啥变化"吻合）
`tm1_value_slot` 的 `if (cx < 23u) return slot3; return 0u;`
→ **curX=23 落进兜底槽 0，与 col15 完全同址**（第 5/7/13 行都是 col15+col23 组合）

## v9.2：用户反馈两个现象 → 定位到两个真 BUG（04:4x）

用户反馈：① 左侧 12px 字**奇数字后出现背景透明格子**（"经典 BUG，文档有提"）；
② 右边值列的**默认字库字透明**（ＬＲ、７），"属于默认字库的空了"。

### BUG A（我上一版引入，致命）：P24 跳板把实参寄存器当暂存
原生 `InitWindowTileData` 入口：
```
0x08002A50 push{r4-r6,lr}  0x08002A52 sub sp,#8
0x08002A54 adds r4,r0,#0   0x08002A56 lsls r1,r1,#0x10
0x08002A58 lsrs r3,r1,#0x10
0x08002A5A lsls r2,r2,#0x18   ← r2 就是 glyph！
```
而 P24 覆盖指令用 `ldr r1, =...`、Origin 桩用 `ldr r2, =0x08002A59` 做跳转
→ **r1(startOffset) 和 r2(glyph) 全被冲掉**：256 次预渲染画成同一个字形、
落点也错，整本字库等于全空 → 值列的 ＬＲ / ７ 全透明。
**修：暂存一律改用 r3**（caller-saved，且 0x08002A58 第一句就重写 r3）。
校验：`4B00 4718` = `ldr r3,[pc,#0]; bx r3`（原来是 `4900 4708`）。

> **通用纪律（写进骨头里）**：写 ROM 入口跳板前，先把被覆盖指令之后
> **前 8 条**用到的寄存器列出来；`ldr rX, =addr` 的 rX 只能取这之外的
> caller-saved 寄存器。P01 那条 `ldr r1` 之所以没事，是因为
> `PrintNextChar` 只有 r0 一个实参。

### BUG B（v7 引入）：12px pass2 的 off 推进被改成恒定 +2，破坏了相邻字共享
文档 `FONT_12PX_DRAW.md` 第 27 行「右缘填 D，**不碰左缘**」= 相邻字共享 tile
（字 N 的右 4px 与字 N+1 的左 4px 同处一格）。正确关系统式：
```
off 恒等于  sub_start + 2*(px >> 3)
  pass1 off = sub + 2*(px>>3)
  pass2 off = sub + 2*((px+8)>>3) = pass1 + 2        （sp=0/4 都成立）
  下一字 pass1 = sub + 2*((px+12)>>3)
     sp==0 → +2（相对 pass2 即 **+0**） ； sp==4 → +4（即 **+2**）
→ pass2 之后应推进  (startPixel == 0) ? 0 : 2
```
恒定 +2 的后果：off 比正确值大 2 并累积 → 字 N+1 的 pass1 落到一格**新** tile，
其左 4px 从没被写过（本该放上一字的右 4px）→ **背景透明格子**，且 4 字标签多耗 4 tile。
**修：改回 `chs_off_add(win, (startPixel == 0u) ? 0u : 2u);`**
（v7 当年为治"白条"改的，那个白条另有原因——v6 是分区撞车，不是这里。）

自检（修正后）：占用 3..318 共 **120 tile**（修正前 146），无重叠、
不踩引用字形；各子区 off 序列全部落在 span 内：
```
标签4字 [0,2,6,8] / 标签2字 [0,2] / 值1字 [16] / 值2字 [18,20] / 值3字 [16,18,20]
```
game.bin 14508 → **14516** 字节。

## tile 账目（修正版）— 回答「16px 能不能省 tile」

### 先回答：占用的 tile 就是实际渲染所需，一分不多
当前设置菜单 **120 tile** 的构成（与脚本实测完全对上）：
```
标题 4 字 @12px = 12
标签 4,4,4,2,4,2,2 字 @12px = 12+12+12+6+12+6+6 = 66
候选 1,2,1 / 1,2 / 2,3 / 3,3 / 2 / 1 字 @8px = 42
--------------------------------------------------
合计                                        120 ✓
```

### n 字占 tile（v9.2 恢复相邻字共享后）
```
n        1    2    3    4    5    6
8px      2    4    6    8   10   12      = 2n
12px     4    6   10   12   16   18      = 2*(floor(1.5*(n-1))+2) ≈ 3n+1
16px     4    8   12   16   20   24      = 4n
```

### ⛔ 「16px 省 tile」是错的 —— 16px 是三者里**最贵**的
- **16px**：advance=16=正好 2 个 tile 列，相邻字**不重叠 ⇒ 无共享**，
  每字 2 列 × 2 行 = **4 tile 恒定**。
- **12px**：advance=12 < 宽度 16 ⇒ 相邻字**共享 1 列**，摊薄到 ≈3 tile/字。
- **8px**：advance=8=1 列，无 spill，**2 tile/字**。

16px 唯一的好处是**实现简单**（无 spill、无半列相位），不是容量。
**"更宽 ⇒ 更多 tile" 才是对的；12px 便宜恰恰因为它压得比字宽更密。**

### 具体代价：标签改 16px 就装不下
```
标签 66 tile(12px) → 88 tile(16px)
行跨度 16+6+4+6=32 → 7 行需 224 tile
而可用空档只有 [141,255)=114 + [257,323)=66 = 180  →  ✗ 装不下
```

### slot（SLT2）能不能改善？**不能**
slot 与 F9 00 / F9 80 的区别只在**中文流从哪来**：
- `F9 00` = 旁载单字（内联 4B）
- `F9 80` = PhraseTable 切流（解决字段定长限制）
- `slot`  = PrintNextChar 运行时按原串查表，整体换成中文流

三者**下游完全相同**：同一个 win、同一套 chs_blit、同样的字宽与几何。
决定 tile 的是「多少字 × 多宽 × 几何」，slot 一个都不碰 → **tile 用量一模一样**。

slot 真正改善的是：ROM 空间压力（中文不必塞进定长字段）、指针重定位风险。
反过来说，slot 解除长度限制后译文可能**更长** → tile 反而更吃紧。

### 真正能省 tile 的手段（按性价比）
1. **候选列保持 8px**（已做）——最省，2 tile/字
2. **译文更短**——12px 下 4 字→3 字省 2 tile
3. **按需字形镜像（根治稀缺）**：字库 512 tile 里本菜单只用 ~24 个。
   给"自然落址正好落在中文区"的字形做**运行时镜像**（首次用到时
   `GetGlyphTilePointers` + `CopyGlyph*` 画到 [19,33)/[51,111) 这类空档，
   再改写 tilemap 表项），不必预知完整引用集 → 可用空间可从 ~200 涨到 ~470。
   ⚠ 这是设计提案，尚未实现。

## bak 为什么能全 12px —— 它用的是**位置式 grid**，不是分配式

### 机制（`bak/text_original/text_scene.c`）
```c
x = win[0x1A] + tile_x;            /* 屏幕列 */
y = win[0x1C] + win[0x1D];         /* 屏幕行 */
idx = y*30 + x + band;
idx += win_u16(win, WIN_TILE_BASE);   /* 1 */
idx += origin;                        /* 2 (tpl[1]==2 时) */
upper = remap(idx);
lower = remap(idx + 30);              /* 下一行同一列 */
```
⇒ **tile = 3 + 30·行 + 列**。每个屏幕格子固定拥有一格 tile，**不分配、不记账**。

### 为什么这样就能全 12px
- 不需要知道"一行几个候选 / 每候选几个字" —— 位置直接决定 tile。
- 相邻字共享天然成立：字 N 的 pass2 与字 N+1 的 pass1 算出的**是同一个 x**。
- 完全无状态、幂等，重绘不会漂移。
→ 代价是把容量需求从"实际字数"换成了"屏幕格数"。

### 代价（实测算出来的）
| | bak grid | 现行分区 |
|---|---|---|
| 实际写入 tile | 148（全12px） | 120（值列8px） |
| 写入范围 | 37..549 | 3..318 |
| 越出 charblock2(>512) | **6 个**（517-519,547-549） | 无 |
| 名义跨度（格位全覆盖） | **600 tile**（30列×20行） | — |
| 踩设置菜单引用字形 | **5 个**（325/327/369/397=Ｌ/447） | 无 |

### ⚠ 但 bak 也并非干净
按上表它会踩到 **397 = Ｌ**（PCS 0xC6）。也就是说 bak 的按键模式行可能本来
就有「Ｌ 显示成标签字左半」这类瑕疵，只是没被当成问题。
另注：bak 的 `screen_menu_mode2` 门控要求 `tpl[1] ∈ {0,2}`，而
`0x081BB874` 的 `tpl[1]` 未实测 —— 若不是 0/2，bak 对该窗口走的是
**Linear**（`CHS_MENU_LINEAR_FLOOR=0x100`），不是 grid。**跑 bak 实测才能定论。**

### 结论 / 可选动作
grid 与分区不是对错之争，是**容量 vs 结构无关性**的取舍：
- 分区：省、不越界、可静态证明安全；但要预知文本结构，且为了塞下必须给值列降 8px。
- grid：全 12px、结构无关；但要 ~600 格位，越界且会覆盖大半个字库。
→ 可在配置表加 `mode` 字段（PARTITION / GRID）让**每个窗口自己选**，
  checker 对两种模式分别校验。这是下一步可做的增强。

## v12：字形镜像（Glyph Mirror）—— GRID 从"无解"变"有解"

### 💡 核心洞察：tm1 原生字符**零 VRAM 写入**
`br_tm1` 非中文走 `FontSub_Origin` = ROM 预渲染查表，**只写 tilemap 表项**
（值 = 字库 tile = startOffset + glyph*2），一个字节都不写 VRAM。
→ 所以"腾出字库"**根本不用动字库**，只要把表项改指到别处即可。
→ 之前 v9 想"跳过预渲染给中文让地盘"是走错方向（且证明有害，见上）。

### 镜像机制（两条铁律）
**① 拷贝时机必须在 `InitWindowTileData_Hook` 内、Origin 之后**
```
预渲染循环  日志行 698–4013
首个文本打印 日志行 4026
```
中文一写入就把原 tile 覆盖了，**之后再拷只会拷到中文碎片**。
而预渲染时期字形刚渲染完、内容干净，且整体早于任何中文写入 → 唯一正确时机。
逐 glyph 调用（256 次）⇒ 每个字形只命中一次 ⇒ **完全无状态**，
不需要 RAM 映射表，更不需要失效逻辑。（0x0203FF80-FFCF 安全区本已占满，
若走"运行时查表"路线根本没地方放表。）

**② 表项地址必须复刻 ROM `sub_08003708`，且在 FontSub_Origin【之前】算**
反汇编 0x080036DC 得到：
```
col  = (win[0x1A] + win[0x1B]) & 0xFF
row  = (win[0x1C] + win[0x1D]) & 0xFF
addr = tpl->tilemap + ((row*32 + col) << 1)
lower 表项在 addr + 0x40
```
⚠ `lsls r1,#0x18` + `lsrs r1,#0x13` = `row << 5` = row*32（不是右移 19 丢光）。
⚠ FontSub_Origin 会推进 win[0x1B]，所以 tx 必须先取。

### 配置化
`struct Tm1Mirror { uint16_t src, dst; }`，src/dst 都填**字形起点**（必为奇数），
各占 2 格（src/src+1 → dst/dst+1），lower 一律 = upper+1。
两个查询：
- `scene_tm1_mirror_of()` 宽松（命中 src 或 src+1）→ 运行时表项改写用
- `scene_tm1_mirror_src()` 严格（只认精确 == src）→ 预渲染拷贝用，杜绝错位

镜像表用 `#if OPTION_MODE == TM1_MODE_GRID` 门控：
镜像槽 3..10 与 PARTITION 的 title_base [3,19) 重叠，
PARTITION 下 `mirror_n = 0` ⇒ 钩子整个跳过，**零副作用零回归**。

### 📊 结果：GRID 从 0 个可行 base → 118 个
最优 `base=40`：全 12px、写入 **148 tile**、范围 40..433（≤511 不越界），
冲突 7 格全部被 **4 条镜像**覆盖（335/337/339/409 → 3/5/7/9）。
候选列也随之从 8px 升到 **12px**（`OPT_CAND_FONT` 随模式切换）—— 这才是
GRID 相对 PARTITION 的真正收益：标签与候选视觉统一。

### 自检脚本三项升级
1. **`preprocess_conditionals()`**：脚本此前无脑收集所有 `#define`，
   把 `#else` 分支的值也收了 → mode=GRID 却按 PARTITION 参数校验。
   现在能求值 `#if/#elif/#else/#endif/#ifdef/#ifndef`。
2. **`check_mirrors()`**：镜像槽不得越界 / 压引用字形 / 落中文足迹 / 互相重叠；
   src/dst 必须奇数；**反向检查**"是否有冲突未被镜像覆盖"。
   `report()` 会把被镜像兜住的冲突从"踩踏"里扣除。
3. **`--search-base` 自带镜像分配**：纯 GRID 已证无解，搜索现在会算冲突集并
   自动分配镜像槽，直接打印可粘贴的 `kOptMirrors[]`。

### 🐛 脚本自身的两个 bug（已修）
- 模拟传参：`sim_grid(c, sess, all_12)` 应为 `cand_wide`。
  `all_12` 只是命令行开关（默认 False），导致 148 tile 被算成 120 tile、
  冲突集算错（漏了 337）。**显示用 cand_wide、模拟也必须用 cand_wide。**
- 宏递归展开：`OPTION_MODE` → `TM1_MODE_GRID` 是二级宏，需循环求值；
  且 `defs` 的值可能是 int（`.strip()` 会炸），要先判类型。

## v13：镜像冲突集改按**保护区矩形**算（修 Ｌ/Ｒ 乱码）

### 🐛 现象
v12 出包后：其余行全部正常（含"7"），**只有按键模式行的 Ｌ/Ｒ 变乱码**。

### 根因：冲突集依赖了一份手抄的字数表
`check_tm1_scene.py` 的 `SESSIONS` 是手抄的会话几何，**漏了 `(15,13,2,"普通")`**
（按键模式行第一个候选），还把「类型」错挂在 curY=13（实际在 15）。
→ 模拟出的中文足迹偏小 → 327/329/331 等 tile **没被判为冲突** → 没有镜像
→ 中文"普通"压上去 → 用到这些字形的 Ｌ/Ｒ 显示成中文碎片。

**这是结构性缺陷**：按"每个会话精确字数"算冲突，改一次翻译就失效一次，
而且漏一条就漏镜像。SESSIONS 只能当参考，不能当判据。

### ✅ 改法：中文**保护区矩形**（prot_row0/row1/col0/col1）
配置新增矩形字段，冲突集 = **矩形 ∩ 引用字形**，与文本字数无关：
```c
row 0..17  ← curY 1..17；⚠ row1 必须 +1，因为 lower 表项在下一行(+stride)
col 0..22  ← stride-1（spill 的 col+1 已被 clamp）
```
矩形 tile 40..453（414 格）→ 其中引用字形 22 个 → **镜像从 4 条涨到 22 条**。
镜像槽放矩形之上 454..503。自检新增一条：**实际足迹不得越出矩形**。

### ⚠️ 期间差点引入新 BUG：镜像槽压住菜单光标
`▶` 字形 tile = 479,480（PCS 0xEF），`CHS_MENU_CURSOR_TILE` = 480,481 ——
**正好落在 454..497 的镜像槽区**。镜像拷贝会把光标字形覆盖掉。
→ 把 479/481 加进 `kOptGlyphAvoid`（该表现在含两类：实测引用 + 特殊用途保留区），
  槽位自动跳到 484 继续。最大 tile 503。
→ **分配镜像槽时必须把"已知特殊用途 tile"一并排除**，不能只看实测引用。

### 两个已纠正的错误认知
1. **dst 的奇偶无关紧要**。表项改写是 upper→dst、lower→dst+1，与源 tile 奇偶
   无关；只要 (dst, dst+1) 连续空闲即可。（自检里那条奇偶检查已删。）
2. **矩形要含 lower 行**。GRID 的 lower = upper + stride，最末行的 lower 会
   落在 row1+1 —— 第一版取 row1=16 就被自检抓出 3 格越界。

### 残留风险（已写进代码注释）
`kOptGlyphAvoid` **清单不完整**是这类方案的主要风险：漏一个就表现为某个非中文
字符变乱码（已漏过两次：139/255、327/329/331）。
处置流程：发现乱码字符 → 反推 tile（= 1 + PCS*2）→ 加进 avoid → 重跑自检
→ `--search-base` 重算镜像表。
根治需要"运行时按需镜像"（不预知引用集），但那要一张 RAM 映射表，而
0x0203FF80-FFCF 安全区已被 pitch 表占满 —— 除非把表藏进无 tilemap 引用的
VRAM 空白 tile（如 504..511），尚未实施。

### 产物
game.bin 15496 → **15576** 字节；自检全绿；打包全通。

3. `chs_blit` 查表拿到槽位 → 画到那里 → 写表项（表项仍由我们写）

- 实际占用 **141..308（164 tile）**，与引用/保留字形 **零冲突**
- 每汉字 4 个连续 tile：`+0 左上 / +1 左下 / +2 右上 / +3 右下`

### 代码改动（只加不改，旧的 PARTITION/GRID 路径完整保留）
1. `chs_tile_num` / `chs_tile_ptr` / `chs_core_ex` 各加 `uint16_t ptr_base` 参数；
   `ptr_base != 0` 时 `chs_tile_num` 直接返回 `ptr_base + col_delta*2 + row_delta`，
   **pass1/pass2/spill/表项写入全部复用现有逻辑**（没重写绘制）
2. 指针模式下**跳过 `chs_off_add`**（槽位固定，不需要 off 推进）
3. `chs_blit` 开头算 `pb = chs_ptr_base(win, glyph)`；`pb==0` 时行为与旧版**完全一致**
   （未登记汉字自动回退，不会崩）
4. `chs_ptr_base` 放在 `chs_blit` 之前（`tm1_cfg` 定义在 354 行，不能放文件前部）
5. `cand_font` 条件改为 `#if OPTION_MODE == TM1_MODE_PARTITION` → 8px，否则 12px
   ⇒ **指针模式是全 12px**

### 落址公式推导（关键，省得下次重推）
`chs_sync_tilex(win, slot, px, adv)` 里 `cursorTileX = btx + ((px+adv-1)>>3)`。
照抄 `chs_core_ex` 的 `px += 12; chs_sync_tilex(..., 12)` 即可让每字占 2 列、
互不重叠（实测推导：字1 写列 0,1；字2 从列 2 起）。**不要自作聪明改步进。**
