## 调研定案：美版 PokeRS 工具架构 vs 本项目路线（重构方向再简化）

读完 `tools/Pokemon_GBA_Font_Patch/pokeRS` 全部 hook 源码 + pokeruby 美版 text.c：

1. **美版工具核心 hook 只有一处**：`DrawGlyphTiles+2 → bl DrawGlyphTilesChinese`，加 GetGlyphWidth/GetStringWidth 两个宽度 hook。对战血条（UpdateNickInHealthbox 等 3 处）、寄放系统（PrintDisplayMonInfo）是"不走标准打印器的窗口"逐个专用 hook。
2. **三代引擎字体根本不进 VRAM**：DrawGlyphTiles = ROM 字体 → 窗口 tileData 缓冲（EWRAM）的像素拷贝。官方窗口系统（GetCursorTileNum/window tilemap）本身就是图集分配器+落址系统。16px 全角字符每字独占 2×2 tile，永不共享/踩踏。
3. **字库整体替换 ROM 数据**：PokeRSFontChsNormal/Small 各 0xE0000 字节（~900KB/份），ROM 扩容 32MB。索引→地址是纯函数（(码-修正)<<8|第二字节 <<7），零可写状态。
4. **编码借三代全角双字节区**（首字节 0x01-0x1E + 第二字节），中文槽位 7168+。
5. **结论**："美版可以日版不可以"是伪命题——卡住本项目的不是日版，是自选的 12px 半格 + VRAM 动态分配。16px 满格 + ROM 常驻字库 + 三 hook 路线连自研图集分配器都不需要（官方窗口系统即分配器）。
6. 重构方案随之再简化：渲染层 = DrawGlyphTiles hook + 宽度函数 + 特殊窗口专用 hook；字库 ROM 化；保留 F9/PhraseTable/SLT2 文本编码层与打包链路；tm1 预渲染窗口按美版"专用 hook"思路逐个收敛，废弃通用 zones 机制。
7. D 商历史做法（网络检索佐证）：本质是"套字库"——只动数据不动引擎（字库 tile 替换 + 码表映射 + 文本导出导入 + 图形文本重绘），代表作如 Tom_C《宝可梦金·银》韩版汉化（2021-2024）。

## 用户纠偏（重要）：D 商不是 16px，是 8px 瘦小字体

- D 商经典做法：汉字塞进**半角 Latin 字库槽**（8px 宽、单字节编码），走官方可变宽度通道。字号不是关键。
- **关键验证（pokeruby text.c:3877 DrawGlyphTile_UnshadowedFont）**：官方 blit 是**逐像素 RMW 混合写入**——`sGlyphMasks[width][startPixel]` 支持任意宽度+任意亚 tile 起点，`startPixel+width>8` 时原生写下一列（buffer+=8），mask 外保留已有像素。可变宽度/跨列共享 tile 是引擎原生语义，tile 从不"属于"任何字形。
- **修正后的分界线**：不是 16px vs 12px vs 8px，而是「混合写入（官方语义）」vs「tile 独占分配（本项目发明的槽位机制）」。字号是自由参数（8/12/16 都能走官方通道）。
- 本项目 BUG 根源收敛为一句话：用"槽位分配+tilemap 引用改写"替代了官方的混合写入，引入了数据本身没有的"独占"语义 ⇒ 踩踏/相位/pass2 全是给这个错误语义擦屁股。
- 修正后架构不变量：**运行时零 tile 分配**。动态文本 = DrawGlyphTiles 层 hook + blend 原语 + 官方游标 + ROM 字库；静态预渲染文本 = 构建期烘焙 tile 数据（D 商重绘图片思路），不走运行时槽位。
