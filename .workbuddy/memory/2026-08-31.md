## 调研定案：美版 PokeRS 工具架构 vs 本项目路线（重构方向再简化）

读完 `tools/Pokemon_GBA_Font_Patch/pokeRS` 全部 hook 源码 + pokeruby 美版 text.c：

1. **美版工具核心 hook 只有一处**：`DrawGlyphTiles+2 → bl DrawGlyphTilesChinese`，加 GetGlyphWidth/GetStringWidth 两个宽度 hook。对战血条（UpdateNickInHealthbox 等 3 处）、寄放系统（PrintDisplayMonInfo）是"不走标准打印器的窗口"逐个专用 hook。
2. **三代引擎字体根本不进 VRAM**：DrawGlyphTiles = ROM 字体 → 窗口 tileData 缓冲（EWRAM）的像素拷贝。官方窗口系统（GetCursorTileNum/window tilemap）本身就是图集分配器+落址系统。16px 全角字符每字独占 2×2 tile，永不共享/踩踏。
3. **字库整体替换 ROM 数据**：PokeRSFontChsNormal/Small 各 0xE0000 字节（~900KB/份），ROM 扩容 32MB。索引→地址是纯函数（(码-修正)<<8|第二字节 <<7），零可写状态。
4. **编码借三代全角双字节区**（首字节 0x01-0x1E + 第二字节），中文槽位 7168+。
5. **结论**："美版可以日版不可以"是伪命题——卡住本项目的不是日版，是自选的 12px 半格 + VRAM 动态分配。16px 满格 + ROM 常驻字库 + 三 hook 路线连自研图集分配器都不需要（官方窗口系统即分配器）。
6. 重构方案随之再简化：渲染层 = DrawGlyphTiles hook + 宽度函数 + 特殊窗口专用 hook；字库 ROM 化；保留 F9/PhraseTable/SLT2 文本编码层与打包链路；tm1 预渲染窗口按美版"专用 hook"思路逐个收敛，废弃通用 zones 机制。
7. D 商历史做法（网络检索佐证）：本质是"套字库"——只动数据不动引擎（字库 tile 替换 + 码表映射 + 文本导出导入 + 图形文本重绘），代表作如 Tom_C《宝可梦金·银》韩版汉化（2021-2024）。

## 用户纠偏（重要）：D 商不是 16px，是 8px 瘦小字体

- D 商经典做法：汉字塞进**半角 Latin 字库槽**（8px 宽、单字节编码），走官方可变宽度通道。字号不是关键。
- **关键验证（pokeruby text.c:3877 DrawGlyphTile_UnshadowedFont）**：官方 blit 是**逐像素 RMW 混合写入**——`sGlyphMasks[width][startPixel]` 支持任意宽度+任意亚 tile 起点，`startPixel+width>8` 时原生写下一列（buffer+=8），mask 外保留已有像素。可变宽度/跨列共享 tile 是引擎原生语义，tile 从不"属于"任何字形。
- **修正后的分界线**：不是 16px vs 12px vs 8px，而是「混合写入（官方语义）」vs「tile 独占分配（本项目发明的槽位机制）」。字号是自由参数（8/12/16 都能走官方通道）。
- 本项目 BUG 根源收敛为一句话：用"槽位分配+tilemap 引用改写"替代了官方的混合写入，引入了数据本身没有的"独占"语义 ⇒ 踩踏/相位/pass2 全是给这个错误语义擦屁股。
- 修正后架构不变量：**运行时零 tile 分配**。动态文本 = DrawGlyphTiles 层 hook + blend 原语 + 官方游标 + ROM 字库；静态预渲染文本 = 构建期烘焙 tile 数据（D 商重绘图片思路），不走运行时槽位。

## tm0/tm3 中文「上下两层都是上半+错位」根因（2026-08-31 实证，已修复验证）

用户症状：文本「真伤脑筋」分成上下两层，上层=上半部分，下层=「伤脑筋」的上一半
（少第1字且右移错位）。tm0 与 tm3 都有。

### 排除项（逐条实证，均非根因）
- nibble 序：字库=GBA 标准（低 nibble=最左），blend_row_4bpp 正确。
  构建脚本 build_chinese_font.py 头部注释「left=high nibble」是错的/过时。
  注意：tests/test_blend_glyph.py 的 Python 参考 expand_row_4bpp 与 C 同假设，
  对拍全绿属自证一致，不能当正确性证据。
- 字库布局 [TL@0][BL@32][TR@64][BR@96] 正确（v5 读取对）。
  证据：「真」TL(行0-7)+BL(行8-15) 竖拼=完整「真」左半（十+目+底横）。
- 字库墨迹只有 0 和 15 两个 nibble（无 14 阴影，是 unshadow 版）。
- 墨迹 12x12 左对齐放进 16x16 槽（右侧 4 列常空）=> 右半 tile 墨量远小于左半，
  实测 中[15,11,5,2] 真[15,13,1,3]，属正常。
- VRAM 落点/tilemap/推进/取色/FontFuncTable 重定向/打包：官方反汇编逐条核对一致
  （tm0_core@0x08003520、tm0@0x08003568、UpdateTilemap@0x080036DC）。
- 纠正旧误记：tm0 的 lower tile = upper +1 不是 +0x100。
  movs r0,#0x80; lsls r0,r0,#9 -> 0x10000，再 adds r2,r2,r0; lsrs r2,r2,#0x10 => +1。

### 根因：tm3 下半 tile 偏移误用 tm0 的 +1，官方是 +30
blit_column_at_tile 被 tm0/tm3 共用，硬编码下半=tile+1 且 UpdateTilemap(tile, tile+1)。
这是 tm0 的官方布局；但 tm3 官方下半 = tile+30（反汇编 0x080034A8 实证）：
  080034C2 adds r1, r2, r1   ; upper = X_part + Y*30
  080034C8 adds r4, #1       ; Y+1
  080034D0 adds r2, r2, r3   ; lower = X_part + (Y+1)*30   <- 差 30
  080034D6 bl   UpdateTilemap
tm3 的 VRAM 网格行宽 30（省空间），tilemap 行宽仍 32（硬件），两者本就不同。

连锁后果：tm3_tile_no 按 cursorTileX 每列+1，故 col=1 的 tile = col=0 的 tile+1
=> col=1 把 col=0 刚写的下半 BL 覆盖成 TR；tilemap 下一行引用 tile+1
=> 行 r+1 显示被覆盖后的内容 => 下层=从第2字开始错位的上半（正是用户所见）。

### 修复（已实施）
blit_column_at_tile 增加 lower_delta 形参（下半 tile 相对上半偏移）：
  tm0 / draw_sym_mode0 -> lower_delta = 1
  tm3                  -> lower_delta = 30
VRAM 写 tile_data + ((tile+lower_delta)<<5)，
UpdateTilemap_Origin(win, tile, tile+lower_delta)。tm3_tile_no 公式不变（*30 正确）。

### 12px（可行，设计稿步骤 5）
- 字库墨迹本就是 ~12px（实测「中」TR/BR 有墨列 [0,1] => 总宽约 10px；
  复杂字接近 12px）；当前按 16px advance 推进，每字右侧白浪费 4-6px。

    phase=4: 本 tile 写 4px + 下 tile 写 8px      -> 推进 2 列, phase<-0
  推进列数 = (phase + 12) / 8，正是设计稿 L56 的 1,2,1,2。
- 技术前提已具备：blend_glyph_4bpp 支持 startPixel + spillTile。
- 代价/风险：需 1 个 phase 状态位。
  * 必须显式落 EWRAM（game.ld 无 .bss/.data，static 会静默进 ROM 恒 0）；
  * 换行/窗口重置必须归零，否则相位漂移越界写 VRAM 花屏（v4 血泪教训）。

### 8px（卡在字库，不是渲染层）
- 渲染侧已支持：cols = (fn==4) ? 1 : 2（8px 单列）。
- 但 Small 字库实测异常：「中」Small TL 几乎全空、BL 才像字形，
  非零仅 21 字节 => 字库布局/内容存疑，印证旧结论「8px 小字库字形有误，

## 12px 两个实测 BUG 修复（2026-08-31 下午，已打包待实测）

### 症状
1. 奇数字后有一个透明小格子
2. 标点符号显示成了奇怪的日文

### 根因（**两个 BUG 同源**：半角字节绕过 12px 相位 / 绕过中文标点字库）
- fontfunc_hook.c 的 4 个 thunk 链路 = `TranslateHandleChar(win,c) || FontFunc_NativeDispatch(tm,win,c)`。
  `TranslateHandleChar` 对非 F9 字节**只查 SLT2 slot 表**（按 JP 原文串 FNV 哈希匹配），
  标点单字节（0x37。/0x3A、/0x3B，/0x3C！/0x3D？/0x3E：）几乎不可能命中
  ⇒ **直接落原生处理器 ⇒ 画出 JP 字体同码字形**（= BUG 2）。
  ⇒ `DrawGlyph` 的 SYM 自绘分支**只有 slot/phrase 替换流内部走得到**，主文本流到不了。
- 原生 tm0/tm3 处理器只从 **startPixel=0** 写整列 8px，**不知道像素相位**：
  奇数个汉字后 phase=4（12·n mod 8 = 4），半角被画到 [8c,8c+8) 压掉前字尾 4px，
  自己应占的 [8c+4,8c+12) 里落在下一列 tile px0-3 的 4px 无人写，
  而下一个汉字 phase 仍是 4 只写 px4-7 ⇒ **该 4px 永久空洞**（= BUG 1）。
  偶数字 phase=0 恰好对齐 ⇒ 不出现。
- 纯中文无半角时布局**无空洞**（已逐字推演证明：不变量 px = 8*col + phase 恒成立）。

### 修复（一次改完，用户拍板「一次修完 + 标点 8px」）
- **A** thunk 在原生分发**之前**拦截：`if (c < 0xF7 && DrawHalfWidth(win,c)) return;`
  （0xF7+ 是控制码/终止符，行为照旧）
- **B** 新增 `DrawHalfWidth`（text_render.c，text.h 导出）：
  - SYM 带 0x36-0x3E 且 tm∈{0,3} → `draw_sym_px` 用中文标点字库（0x091E0000，64B/枚
    [U@0][L@32]）**相位感知自绘**（填进 128B 暂存槽 TL/BL，TR/BR 留 0 复用 extract_cols）；
  - 其余半角且 tm∈{0,3} → 先 `chs_flush_to_col` 再交原生；
  - tm1/tm2 无像素路径 → 返回 0。
- **C** `print_glyph_12px` 泛化为 `print_glyph_px(..., ink, phase)`：
  w0=min(8-phase,ink)、w1=ink-w0、adv=(phase+ink)/8，12px 汉字与 8px 半角共用。
- **D** `chs_flush_to_col`：把当前 tile 剩余 [phase,8) 用底色填掉（blend 全 0 源），
  游标推到列首（cursorTileX+=1；tm0 额外 TILE_OFFSET+=col_stride），px 补到 8 的倍数。
  代价：半角前多 4px 空白（标点留白，可接受）；收益：前字不被覆盖、无空洞、相位不变量保持。
- **E** `DrawGlyph` 简化为：`c>=0xF7 → return 1；(void)DrawHalfWidth(...); return 1;`
  （必须恒返回 1，否则 inline_phrase_no_controls 会中途放弃整条短语）

### 验证（静态，禁模拟器）
- 编译 6652 → 7356 字节，零 warning；`.bss`/`.data` 大小均为 0（无 static 被塞 ROM）。
- 反汇编核对：`FontFuncTm0_Hook` 顺序 = TranslateHandleChar → `cmp r4,#0xF6; bls` →
  `bl DrawHalfWidth` → 判决 → 原生。`DrawHalfWidth` 用 **位掩码 9>>tm** 判定 tm∈{0,3}
  （GCC 把 {0,3} 编成 0b1001）；tm0 分支 lower_delta=1/col_stride=2，
  tm3 分支 lower_delta=30/col_stride=1；TILE_OFFSET 仅 tm==0 时推进（`lsls r3,r3,#29` 判 tm&7）。
- `check_rom_hook.py`：ROM @0x800000 与 game.bin 逐字节一致 = True。
- ⚠ 该脚本在 GBK 控制台会 UnicodeEncodeError（⚠ 字符），须 `PYTHONIOENCODING=utf-8` 跑。

### 方法论沉淀
- 遇到「某字符类显示异常」先查**分发链是否真的到达目标分支**——
  本例 SYM 自绘代码写得完全正确，但它根本不在主文本流的调用路径上。
