## 方案 A 前置核查：InitWindowTileData 反汇编（完成）

背景：用户选方案 A（窗口独占 charBase + 每帧全量重绘）后，需先摸清官方
InitWindowTileData 如何分配 charBase、blit 写的是 VRAM 还是 WRAM。

反汇编结论（ROM=origin/POKEMON_RUBY_AXVJ00.gba，capstone）：

### InitWindowTileData @0x08002A50
- 签名 `(win=r0, r1, r2)`；r1<<16>>16 存 r3，r2<<24>>24 存 r6。
- 读 `win[0x08]` 做 switch：`cmp r0,#5; bhi` → 只收 0~5（6 case）。
- 跳转表基址 **0x08002A74**（非 0x08002A70；ldr r1,[pc,#8] 在 0x08002A66
  解析出的 lit 值就是 0x08002A74，表项是函数指针，mov pc,r0 跳转）。
- 6 case 归 3 块：
  - case 0/3 → 0x08002A8C → bl 0x08003630（等宽 1bpp blit）
  - case 1/2 → 0x08002AAC → bl 0x08003830（查表 0x081B49AC）
  - case 4/5 → 0x08002ACC → bl 0x080038A0（查表 0x081B51AC）

### 关键发现（方案 A 突破口）
- **blit 0x080038A0 内部 `[lit]=0x03000330` 是 WRAM 地址**（非 VRAM 0x0600xxxx），
  说明官方"字模预渲染"写的是 **WRAM 缓冲**，不是直接写 VRAM charblock。
- blit 0x08003630 内部还有第二个 switch（表 @0x08003678，7 项，font 0/1/2/6→0x08003694，
  3/4/5→0x080036B0），尾段 0x080036B0 调 0x080038A0 两次（lower 偏移 +0x20），
  与 skill 里"两个 blit 副本 lower 差 +0x20/+0x3C0"一致。
- 0x080036DC 起是 UpdateTilemap（`bl 0x08003708` GetCursorTilemapPointer + palette
  win[0x0F]<<12 orr），与 memory 里"位置这条腿"记载一致。

### 搬运链追查（完成，关键结论）
1. **blit 0x080038A0 尾段 `ldr r2,=0x04000008` + `bl 0x081B1294`**：0x081B1294 =
   `svc #0xb; bx lr` = **BIOS CpuFastSet**（SVC 0x0B）。所以官方把渲染好的字形用
   CpuFastSet 高速拷贝到目的地址。`r0=0x03000330(源缓冲) r1=sb(目的) r2=控制`。
2. **0x03000330 是 blit 内部的源中转缓冲**（字形解压中转），不是最终目的。
3. **InitWindowTileData 唯一调用点 = 0x08002A14**，父函数 = `Text_LoadWindowTemplate
   @0x08002A34`（符号表）。父函数更外层是 0x08002950，设置全局状态区
   **0x03000324~0x03000330**（文本引擎专用局部全局）：0x03000328=窗口指针、
   0x0300032C=字号、0x0300032E=glyph 计数。
4. **符号表确证**（pokeruby.sym）：`InitWindowTileData=0x08002a50 size 0x86`、
   `InitVariableWidthFontTileData=0x08002ad8 size 0x54`、
   `MultistepInitWindowTileData=0x08002bfc`、`Text_LoadWindowTemplate=0x08002a34`、
   `Text_InitWindowWithTemplate=0x08002d54`。
5. **struct WindowTemplate（28B）**：`[0x00]bgNum [0x01]charBaseBlock [0x02]screenBaseBlock
   [0x03]priority [0x04]paletteNum [0x05]fgColor [0x06]bgColor [0x07]shadowColor
   [0x08]fontNum [0x09]textMode [0x0A]spacing [0x0B]tilemapLeft [0x0C]tilemapTop
   [0x0D]width [0x0E]height [0x0F]pad [0x10]tileData* [0x14]tilemap* [0x18]maybeUnused`。
   ⚠ InitWindowTileData 的 r4 参数 = `struct Window *`（TextPrinter），switch 键读
   `[0x08]`，blit 目的地址读 `[0x0C]`（32位 ldr，跨 win_field_C/delayCounter/spacing/
   win_field_F 四字节）——这个字段的精确语义（是 tileData 指针还是别的）仍需 gdb
   实测确认，静态推演到此为止（反过度分析护栏）。

### 方案 A 落点判断（待最后一步）
- 官方字模预渲染确实是「WRAM 中转 → CpuFastSet 搬 VRAM」两段式，不是直接写死 VRAM。
- 但搬运链的「目的地址 = r4[0x0C]」究竟指向 VRAM charblock 还是 WRAM 缓冲，静态
  反汇编已到临界点（字段跨字节 32 位读），需 gdb 实测一个窗口的 r4[0x0C] 值定论。
- 若 = VRAM（0x0600xxxx）⇒ 方案 A 要改 charBaseBlock 分配 + 接管 CpuFastSet 目的；
  若 = WRAM ⇒ 方案 A 可落在 WRAM 缓冲层，干净得多。

## 美版 vs 日版差异实证（用户纠偏：不能拿美版源码当权威）

用户指出「美版和日版估计不太一样，要按特征最终确定」。实证确认：**完全正确**。

### 关键修正（推翻之前误判）
- 日版 `Text_InitWindow@0x08002C68`（VERIFIED，= InitTextPrinter）反汇编实证：
  **日版 win[0x0C] = foregroundColor（1 字节 strb，=template[5]）**，不是 tileData 指针！
  之前记的「InitWindowTileData 读 win[0x0C] 32位 ldr = tileData 指针」有误——
  那是读**窗口控制块**（template[0x00] 指向的 EWRAM 运行时实例）的 [0x0C]，不是 struct Window。
- 日版 struct Window 布局 vs 美版（pokeruby/include/text.h）不同：美版 tileData@0x24，
  日版 win[0x0C]=fgColor。**两版 struct Window 布局已分叉**。

### 三处结构性分叉（详见 tools/pokeruby-jp/docs/美版日版文本引擎差异.md）
1. struct Window 布局不同（win[0x0C] 语义不同）
2. InitWindowTileData 分派键不同：日版 switch win[0x08]（6 case），美版 switch
   template->textMode（2 分支）
3. 底层拷贝原语不同：日版 `svc #0xb`(CpuFastSet)，美版 CpuFastCopy/CpuFastFill

### 跨版本一致（方案 A 锚点）
WindowTemplate 结构字段偏移**跨版本一致**（bgNum@0x00 / charBaseBlock@0x01 /
fontNum@0x08 / textMode@0x09 / tileData*@0x10）。charBaseBlock 是方案 A 要动的字节。

### 日版 Text_InitWindow 字段映射（实证，重要）
参数 (win=r0, text=r1, startOffset=r2, left=r3, top=[sp+0x18])，映射：
win[0x04]=1, [0x08]=0(switch键), [0x0A]=template[9](textMode), [0x0B]=template[8](fontNum),
[0x0C]=template[5](fg), [0x0D]=template[6](bg), [0x0E]=template[7](shadow),
[0x0F]=template[4](palette), [0x10]=text指针(u32), [0x16]=startOffset(u16),
[0x1A]=left, [0x1C]=top。

## gdb_patcher 加 handler 实测方案 A 落点（2026-09-03 晚）

用户建议「基于 gdb_patcher 加 handler」实测。已做两处改动（src/util/gdb_patcher.py）：

1. **修正 region_of 的 VRAM 判定 bug**（关键）：原代码把 `0x05000000`（PAL RAM）
   误判成 "VRAM"，把 `0x06000000`（真 BG/OBJ VRAM）判成 "其它"。已改为：
   VRAM=`0x06000000..0x06018000`、PAL=`0x05000000`、OAM=`0x07000000`。
   否则 tileData 值域判断会全错（VRAM 被当"其它"→ 误判成"不在 VRAM"）。
   已验证：无其他调用依赖旧的 "VRAM"（=PAL）/"其它" 语义，安全。

2. **增强 InitWindowTileData handler（_on_iwtd）**：现在直接输出方案 A 需要的结论——
   - r0 身份（region_of(r0) + 读 0x03000328 全局交叉验证 r0==template[0x00] 控制块）
   - ★tileData = r0[0x0C] 的值域（VRAM/WRAM/PAL/ROM）+ blit 落点值域
   - 自动判读：tileData 在 VRAM ⇒ 方案 A 须动 charBaseBlock；不在 ⇒ 落缓冲层每帧重绘
   - r0[0x00]→template 再解一层看 charBaseBlock/font/textMode/tileData/tilemap

### 反汇编补证（确定 handler 该读哪些字段）
- InitWindowTileData r4(=r0) 读：`[0x08]`(fontNum, switch 键) / `[0x0C]`(32位 tileData
  指针) / `[0x05][0x06][0x07]`(fg/bg/shadow 色)。blit 目的 = `r0[0x0C]+(startOffset<<5)+(glyph<<6)`。
- 父函数 0x08002950 实证：r3=r0(参数=template)，`0x03000328=[r3]`=template[0x00]，
  读 `[r1, #9]`(textMode) 判断。⇒ InitWindowTileData 的 r0 = template[0x00] 指向的
  **窗口控制块**（非 struct Window、非 template 本体）。
- 关键点：handler 里颜色字段读 `r0[5/6/7]`（不是 [0x0C]），旧 handler 把 [0x0C]
  当颜色是错的。

## 反汇编吃透四个 FontFunc 的 tile 号算法（2026-09-03 深夜，重要认知）

用户追问「既然都 hook 了，为什么中/日不能共用同个 tile 区」。为彻底回答，反汇编
吃透四个 textMode 的 tile 号来源（capstone，ROM=origin 日版）：

| mode | 函数 | tile 号算法 | 每字占宽 | upper/lower |
|---|---|---|---|---|
| tm0 | 0x08003568→sub_8003520→CopyGlyphToVRAM(0x8003630) | base+TILE_OFFSET(每行清零) | 2 tile | 相邻 +1 |
| tm1 | 0x0800360C | 查表 base+2*glyph(不写动态tile) | 1 tile | — |
| tm2 | 0x0800338C | 缓冲指针(win[0x20]) | — | — |
| tm3 | 0x08003494→sub_8003464→sub_80034e0/sub_8003500/sub_80033b4/sub_80034a8 | base+cx+tx+2+(cy+ty)*30 网格 | 1 tile | 分离 +30 |

关键结论：
- **tm3 tile 号 = 网格位置确定**：`base+(cursorX+cursorTileX+2)+(cursorY+cursorTileY)*30`，
  每行 30 tile 行距（`cy*15*2`），lower 半在 `+30`（下一行同列，`0x3C0=30*32`）。天然唯一不撞。
- **tm0 tile 号 = 顺序领号**（base+TILE_OFFSET，InitTextPrinter 每行清零）→ 中文必须独立高水位。
- **tm1 不写动态 tile**（查预渲染表）→ 天然与中文不撞，无需同源。
- **tm2 缓冲指针**→ 无 tile 分配。
- 四个 FontFunc 各不同源、语义不同，**无法用单一「同源公式」统一**。
