# 2026-09-07 工作日志

## 调研：能否「接管」UI 的 tile 分配（静态分析阶段，未实机验证）

起因：用户实机测试发现部分页面 UI 是**操作后才出现**的（例：商店买卖按钮），
静态避让带穷举不完，问能否反过来接管游戏的 tile 分配。

### 结论（代码证据，非实机）
- **BG 侧不能接管**：R/S（含 AXVJ00）**没有集中式 BG tile 分配器**。
  硬证据：`pokeruby.sym` / `pokeruby_jp.sym` 中 `BgTileAllocOp`、
  `gpu_tile_allocation_map_bg`、`gWindowTileAutoAllocEnabled` **均为 0 处**；
  `pokefirered.sym` 有 3 处（该机制是 FRLG 特性）；
  `tools/pokeemerald/src/bg.c:294` 的 `BgTileAllocOp` 是 `return 0;` stub。
  → 窗口 tile 区由调用方硬编码 `startOffset` 链式传递
    （`menu.c:113` InitWindowTileData → TextWindow_SetBaseTileNum(+9)
     → TextWindow_SetDlgFrameBaseTileNum(+14)，见 `text_window.c:101/200`）。
  → 大量 UI 图形直接 `LZDecompressVram(gBuyMenuFrame_Gfx, VRAM+0x7C00)`
    （`shop.c:270`）= 绝对 tile **0x3E0**，编译期常量，不过任何分配器。
- **OBJ 侧有真分配器但用不上**：`SpriteTileAllocBitmapOp` 0x080014B8 +
  `sSpriteTileAllocBitmap` 0x03002450(128B) + `AllocSpriteTiles` 0x0800139C。
  OBJ 在 cb4/5，BG 在 cb0~3，物理隔离，接管它解决不了 BG 冲突。

### 漏网根因（三条）
1. UI 图形硬编码 VRAM 地址（0x3E0 类），无分配器可感知。
2. tilemap 快照时序不可靠：`shop.c:281` `Menu_EraseWindowRect(0,0,0x20,0x20)`
   清 tilemap；视口走 `gBGTilemapBuffers[]` RAM 缓冲 + VBlank DMA
   （`shop.c:251-253`），与 VRAM tilemap 不同步。
3. 分配区间过宽：`lo=0x100`、`hi=(4-cb)*512`，必然吃到高段 UI 区。
   附带：`tpl[TPL_TILEMAP]==NULL` 的「缓冲直绘」窗直接跳过扫描（`tile_alloc.c:132`）。

### 提出的替代方案（待用户拍板，尚未实现）
- **A（推荐）VRAM 非空探测**：避让依据从 tilemap 换成「VRAM tile 是否非零」，
  另开 `ours` 位图防自画污染，避让带 = VRAM非零 − ours，
  `ours` 在 `Text_LoadWindowTemplate`(0x08002D4C) 场景边界清零。
- **B（止血）收紧分配区间**：`lo/hi` 改按场景配置，高段（>0x2FF，含 0x3E0）永久排除。
- **C（治本）咽喉点登记**：hook 7 个 BG 函数（地址见文档 §3）记账到 EWRAM 256B 全局账本。
  **覆盖不到硬编码 LZDecompressVram**，仍需 A/B 兜底。
- 建议组合：先 B 止血，再上 A。

- `docs/调研_20260907_接管UItile分配可行性.md`（含咽喉点日版地址表）

## 追加：美版汉化对照 —— 它们**根本不分配 tile**

本地就有现成实现：`tools/Pokemon_GBA_Font_Patch/pokeRS/`（PMRUS_CHPLUS，R/S 汉化）、
`pokeE/`、`pokeFRLG/`（美版汉化）。**三者都没有任何 tile 分配器。**

### 它们怎么做
1. **落址复用官方 `GetCursorTileNum`**（`pokeRS/src/HackFunction/DrawGlyphTilesChinese.s:90-94`）：
   `dest = win->tileData + 32 * GetCursorTileNum(win, xOff, yOff)`，一个汉字画 4 次
   （左上/右上/左下/右下），中间 `win->left += 8`、`tileDataOffset += 2` 推进。零"找空闲"。
2. **写表项复用官方 `UpdateTilemap(win, 2)`**（`tools/pokeruby/src/text.c:4357-4377）：
   官方**原生支持 2×2 tile 宽字符**，自动写 tilemap[0]/[32]/[1]/[33] 四个号。
   ⇒ 日/美版引擎本来就是为 16px 宽字符设计的，汉化只需换字模来源+宽度。
3. **不冲突来自 `GetCursorTileNum` 可变宽度分支**（text.c:4380）：
   `index = tileDataStartOffset + ((top+cursorY)>>3 + yOff)*width + ((left+cursorX)>>3 + xOff)`
   → tile 号**由光标位置唯一决定**，行间天然不同号 ⇒ 不需要知道"哪块空着"。

### 美版（Emerald/FRLG）额外两件武器
- **A1 窗口独占 VRAM 区**：`AddWindow` 用 `BgTileAllocOp` 给每窗口分 `width*height` tile（baseBlock）。
- **A2 EWRAM 缓冲 + `CopyWindowToVram` 整块 blit**：每帧全量重绘，不需要回收。

### 我们为什么不行（ROM 字节实证）
读 origin ROM 的窗口模板，主力窗 textMode 全是 **1 或 3**：
`0x081BB5BC`=1 / `0x081BB874`=1 / `0x081BB544`=1 / `0x081BB46C`=3 / `0x081BB43C`=1。
⇒ 全走 `GetCursorTileNum` 的 **else 分支** `index = tileDataStartOffset + tileDataOffset + 2*x + y`，
tile 号只跟 `tileDataOffset` 走，该游标**每文本块（InitTextPrinter）清零一次** ⇒ 块间复用 ⇒ 替换 BUG。
⇒ v6/v7/v8 三代分配器 + 今天"撞 UI"的问题，**全部长自这一条分支差异**。

### 由此产生的新方向（未验证）
不改进分配器，改**把落址换回「位置决定」**（套用可变宽度分支的网格公式）。
若成立：v8 可整个删掉、不会撞 UI 固定图形区、改动只集中在落址一处。
需先验证：① tileDataStartOffset 后是否有 width*height 连续 tile（不跨 cb、不撞 UI）
② 2×2 tile 时 tileDataOffset 推进量 ③ 同屏多文本块是否各有独立窗口。

### 产出
- `docs/调研_20260907_接管UItile分配可行性.md` §0.5（美版汉化对照 + ROM 实证表）

## 追加：网格落址静态验证 + 12px 绘制方式定论

### 🔴 12px：官方**不支持**原生 12px，但拆分机制与官方同源（用户直觉部分对）
- **铁证字宽上限 = 8**：`tools/pokeruby/src/text.c:251`
  `static const u32 sGlyphMasks[9][8][3]`（第一维 9 = width 0~8）；
  `sShiftGlyphTileUnshadowedFuncs[]` / `...ShadowedFuncs[]`（line 468/484）**各只有
  Width0~Width8 九项**；`line 3882` 直接按 width 索引无边界检查。
  ⇒ width ≥ 9 必越界。**「官方原生 12px 绘制」不存在。**
- **但官方原生支持亚 tile 拆分**（`DrawGlyphTile_UnshadowedFont` text.c:3877）：
  `startPixel = (win->left + win->cursorX) & 7`（0~7 任意相位）；
  跨 tile 时溢出写相邻：textMode≠2 → `buffer += 8`（**+64B = +2 tile**）、
  textMode==2 → **+32B = +1 tile**（与 blend_glyph.c 注释「mode0 右邻+64B / mode2 +32B」吻合）；
  返回 `tilesWidth = (startPixel + width) / 8`，`UpdateTilemap(win,2)` 原生写 2×2。
  ⇒ 我们的 8+4 / 4+8 **就是官方 width≤8 拆分机制的延伸，拆分本身没错**。
- **当前实际布局**（`PrintNextChar_hook.c: print_glyph_px`）：相位 0/4 循环，
  **2 字占 3 tile 列**（每列含上下两半 ⇒ 2 字 6 tile），相邻字靠
  `v8_phase_last_tile()` 共享。紧凑 12px 下共享是数学必然。
  ⇒ 「壤切半/冒号鬼影」根因**不是共享**，是**共享的 tile 号由顺序分配器给出**（不可预测、
  可能撞 UI、跨块不复位）。**修 12px 不要改拆分，要改 tile 号来源。**

### 网格落址方案（位置决定）
- 官方公式 `GetCursorTileNum` text.c:4371，网格分支条件 `textMode == TEXT_MODE_UNKNOWN2(=2)`：
  `idx = tileDataStartOffset + ((top+cursorY)>>3 + yOff)*width + ((left+cursorX)>>3 + xOff)`
- **主力窗全是 textMode 1**（MONOSPACE），走 else 分支。textMode 1 下
  `PrintGlyph_TextMode1` → Font3: `val = tileDataStartOffset + 2*glyph` ⇒
  **「字库常驻 VRAM」模式**：tile 号 = 字符索引。中文 6000 字需 12000 tile ≫ 1024，
  装不下才被迫动态绘制 —— **这是 v6/v7/v8 三代分配器存在的唯一根因**。
- **绕开 stride 未知的方案**（hook 的 WIN_* 宏里**没有 width/height**，模板 24B 的
  0x14-0x17 恒 0；日版 Window 结构与 pokeemerald 反编译不同）：改用 **BG 固定 stride=32**
  （由 screenBase 间隔 0x800 = 32×32×2B 实证），
  `idx = GRID_BASE + row*32 + col`，row/col 取**屏幕绝对 tile 坐标**。
- **空间测算（相对号，charBase 决定可访问 2 个 charBlock，0~1023）**：
  | charBase | charBlock | UI 固定图形 | 可用网格区 |
  |---|---|---|---|
  | 0 | cb0/cb1 | 0x3E0 起（在 cb1） | [0x209, 0x3E0) ≈ 471 tile ≈ 14 行 |
  | 2 | cb2/cb3 | 无 | [0x209, 1024) ≈ 795 tile ≈ 24 行 |
  商店 UI `LZDecompressVram(..., VRAM+0x7C00)` = 绝对 tile 0x3E0 = **charBlock 1**
  ⇒ charBase=2 窗口**物理够不到**。文本一般 4~6 tile 行 ⇒ 空间充足。
- 网格方案同时解决：撞 UI（限本 cb 安全段，UI 不同段物理隔离）、避让带漏网
  （**避让带整个不需要**）、12px 奇偶残留（同位置同 tile，天然幂等）、跨块残留。

### 模板结构实证（重要，修正此前认知）
日版模板 **24 字节**：`bgNum@0 charBaseBlock@1 screenBaseBlock@2 priority@3 paletteNum@4
fgColor@5 bgColor@6 shadowColor@7 fontNum@8 textMode@9 spacing@0x0A ?@0x0B
tileData@0x0C(u32) tilemap@0x10(u32) 0x14-0x17=0`。
校验：`tileData == BG_CHAR_ADDR(charBaseBlock)` 且 `tilemap == BG_SCREEN_ADDR(screenBaseBlock)`
（如 0x081BB5BC: cb2 → 0x06008000 ✓，sb30 → 0x0600F000 ✓）。
与 hook 宏 `TPL_TILE_DATA=0x0C` / `TPL_TILEMAP=0x10` 一致。
⚠ 与 pokeemerald 的 `gWindowTemplate_81E6C3C` 布局（width@0x0D/height@0x0E、tileData@0x10）
**不同**，别拿它套日版。
⚠ 待查：`0x081BB46C` 的 textMode==3，但 `sPrintGlyphFuncs[]` 只有 3 项
（text.c:359-363）。该模板 tileData/tilemap 自洽、确为合法模板。**不深究。**

### 下一步（②③未做）
先 B 止血（收紧 lo/hi，>0x2FF 永久排除，一行改动解商店撞 UI）；
再上网格（可删 `tile_alloc.c` 整套 + 避让带）；**12px 拆分保持不变**。
需 gdb 实测：`win->width/height` 真实偏移、各窗 `tileDataStartOffset` 与 atlas 上界

UI 0x3E0 占用长度。

## 更正：❌「>0x2FF 永久排除」是错的（用户质疑 → 实测推翻）

我提的 B 止血方案「高段 >0x2FF 永久排除」**不成立**，已作废。用 `scene_cfg.c`
实测 bands 现算（`lo=0x100`、`hi=min((4-cb)*512,1024)`）：

| 场景 tpl | cb | 最大连续空闲 | 位置 |
|---|---|---|---|
| 0x081BB40C 战斗血条 | 0 | 768 | [0x100,0x3FF] |
| 0x081BB49C 地图名 | 0 | **62** | [0x3C2,0x3FF] |
| 0x081BB43C 队伍窗 | 1 | 658 | [0x16E,0x3FF] |
| 0x081BB874 设置菜单 | 2 | 503 | [0x209,0x3FF] |
| 0x081BB544 背包 | 2 | 443 | [0x209,0x3C3] |
| 0x081BB46C 继续菜单 | 2 | 348 | [0x264,0x3BF] |
| 0x081BB5BC 宝可梦详情 | 2 | 238 | [0x212,0x2FF] |
| **0x081BB514 战斗UI** | 3 | **0** | **★ 无可用** |

**三条实证**：
1. **atlas 上界因场景而异，不是 0x209**：0x081BB5BC→0x211、0x081BB544/874→0x208、
   **0x081BB49C→0x2D1**（远超 0x209，旧记忆值 0x209 只在部分场景成立）。
2. **0x2FF 以上恰恰是主力可用区**：背包 [0x209,0x3C3]、设置菜单 [0x209,0x3FF]
   **都跨过 0x2FF**，砍到 0x2FF 各只剩 247（腰斩）；地图名最大块 [0x3C2,0x3FF]
   在 0x2FF **之上**，砍掉直接归零。
3. 0x2D7/0x300 附近确实有 UI 撞边界（0x081BB49C [0x2D7,0x301]、0x081BB5BC
   [0x300,0x327]）—— 但那是"要避让的点"，**不是全局分界线**。

⇒ **`hi` / `GRID_BASE` 一律按场景从实测 bands 现算，禁止写全局常量。**

**顺带暴露两个隐患**：
- `0x081BB514` 战斗UI（cb3）**已无可用 tile**：band `{cb3,0x003,0x208}` 覆盖整个
  搜索区 [0x100,0x200)（`hi=(4-3)*512=512`）⇒ 该场景当前分不到号。
- **避让带"并集"策略过宽**：0x081BB49C 注释「地图名弹窗 + 淡出后场地（并集取更密占用）」，
  `{cb0,0x001,0x2D1}` 很可能是把**整个场地背景**算成避让 ⇒ 只剩 15 段 4~9 tile 碎片。
  这是"避让带越加越不够用"的根源之一。建议改按**单一状态**采集，不要跨状态并集。

⇒ 结论加强：顺序分配器 + 避让带这条路**越补越碎**，应直接上网格方案。

## ⚠️ 再更正：网格方案也被质疑 —— **它不是银弹，且比顺序分配器更费空间**

用户质疑「GRID_BASE 也是拍脑袋的常量，改善不了哪里去」→ **量化后证实用户基本正确。**

### 量化：网格 vs 顺序分配器的空间需求
网格需要 **maxRow × stride 个「连续」tile**；顺序分配器只需 **glyph_len=2**。
按 stride=32 算（4/6/8 文本行的需求 = 128 / 192 / 256）：

| 场景 | 可用连续 | 4行(128) | 6行(192) | 8行(256) |
|---|---|---|---|---|
| 战斗血条 cb0 | 768 | OK | OK | OK |
| **地图名 cb0** | **62** | **✗差66** | ✗差130 | ✗差194 |
| 队伍窗 cb1 | 658 | OK | OK | OK |
| 设置菜单 cb2 | 503 | OK | OK | OK |
| 背包 cb2 | 443 | OK | OK | OK |
| 继续菜单 cb2 | 348 | OK | OK | OK |
| 宝可梦详情 cb2 | 238 | OK | OK | **✗差18** |
| **战斗UI cb3** | **0** | ✗差128 | ✗差192 | ✗差256 |

**结论**：
- 网格把「N 次小赌博（每字找 2 连续）」换成「1 次大赌博（一次要 128+ 连续）」。
- **8 个场景里 2 个根本选不出 GRID_BASE**（地图名 62、战斗UI 0）。
- 一旦 GRID_BASE 选错 ⇒ **100% 稳定撞**，比顺序分配器偶发撞**更糟**。
- 网格唯一真实收益在**时序**（定好 BASE 后不再判断，不受"操作后才出现的 UI"影响），
  **不在空间**。它比顺序分配器**更费空间**（64~96 倍）。

- **① 扩 cb 上限 = 硬件死路【实证-外部】**：tonc（gbadev.net/tonc/objbg.html）——
  BG charBase 仅 2 bit（BGxCNT bits[2-3]）、tile 号 10 bit ⇒ 一个 BG 最多见 charBase 起
  32KB；BG tile VRAM 恒 64KB。**借 OBJ 区（cb4/5）真机不可行**：tonc 原文
  "On the emulators I've tested, this does indeed work. On a real GBA, however, it does not."
  —— 与本项目战斗UI cb3 高段花屏实测吻合。仅剩等效扩充：8px 中文（容量×2）、
  【推论】回收 atlas（tm1 字库常驻死区，前提=该 BG 全部文本走 hook，待 gdb 验证）。
- **② 最强候选 = 照抄 pokeRS「位置决定」路径**：tilemap entry 硬件无基址字段，
  逐 entry 自定义 cb ❌；改 BGxCNT 整 BG 搬字库风险大 ❌。但「直接加载字库瓦片」有实战先例：
  pokeRS（本仓库 tools/）零分配器，`GetCursorTileNum` 位置落址 + `UpdateTilemap(win,2)`，
  tile 永在官方文本区 = **结构上不可能撞 UI**；其「显示不完全」清单 = 窗口区预算溢出按场景修，
  而我们 12px 3tile/字 比它 16px 4tile/字 更省。agb VRamManager（动态改 tile 数据、
  tilemap 不动）为同构工程先例。**块间复用是唯一待实测风险**（日版哪些场景前块须存活）。
- **③ OBJ 文字层 = 补盲区**：tonc TTE obj_puts / agb ObjectTextRenderer 硬件原生支持；
  OBJ 独立 1024 tile + 16 调色板 + 游戏自带分配器。定位：BG 无空间场景
  （战斗UI cb3=0、地图名 cb0=62）走 OBJ，其余走②，混合架构。
  原地画进显示中 tile ❌（空白 tile 全屏共享）；HBlank ❌。
