## 美版 VRAM 分配器研读结论（pokeruby 源码：menu.c/text.c/text_window.c/text.h）

**核心真相：美版是「链式分配游标」，不是测占用、不是顶基址。**

- `struct WindowTemplate` 28B：含 `charBaseBlock`（tile data charblock，写 BGCNT bits2-3）、`screenBaseBlock`（tilemap charblock）、`width/height`@0x0D/0x0E、`tileData`=`BG_CHAR_ADDR(cb)` 指针、`tilemap`=`BG_SCREEN_ADDR(sb)` 指针、`maybeUnused` 4B 填充。
- 全局游标（EWRAM，menu.c:42-45）：`gMenuTextTileOffset` 等 4 个。
- `InitMenuWindowInternal` 链式分配（menu.c:115）：`gMenuTextTileOffset=tileOffset(=1)` → `InitWindowTileData` 返 `start+2+w*h`(603) → `TextWindow_SetBaseTileNum` 返 `base+9`(612) → `SetDlgFrameBaseTileNum` 返 `base+14`(626)。**返回值即下一段起点**。
- `InitVariableWidthFontTileData` 返 `startOffset+2+width*height`（text.c:1809）。
- 生命周期：每次 `InitMenuWindow` 传 tileOffset=1 复位游标；窗口 tileData 指针=模板写死 charblock；整块 charblock 当窗口独占 scratch，开窗从头线性分配、关窗整体作废复用。**从不问「哪里空」**。
- 三种对比：测避让带=扫描空位塞 tile；抬水位=固定顶基址占段；美版=链式游标+所有权+生命周期。

**产出**：`docs/调研_20260909_美版VRAM分配器机制.md`。

**下一步（移植方向）**：日版 AXVJ 缺模板的 charBlock/tileData 指针+width/height，以及分配游标生命周期。需研读日版开窗链（InitMenuWindowInternal 日版对应物）+ charblock 固定布局，确定腾哪块 charblock 给「美版式窗口分配器」，让 UI 文本窗都走它。

### 日版模板 24B 精确结构（真实地址 0x081BB 区 dump，非符号表 0x081B7 假映射）

### 日版 charblock 固定布局（模板写死 tileData 绝对地址，无分配池）
- **cb0** 0x06000000：招式(tm0)/地图名/血条/粉框(tm1,BG3)
- **cb1** 0x06004000：队伍(font4 大字体)
- **cb2** 0x06008000：对话框/设置/请选择-开始菜单（tm1/tm3 文本主力）
- **cb3** 0x0600C000：战斗UI

### 美版 charblock 池（对比）
charBaseBlock 分布 {0:29,1:4,2:22,3:3}，4 个 BG 都有文本窗（bg0:35/bg1:9/bg2:8/bg3:6）。
**每 BG 经模板 charBaseBlock 独占一个 charblock，池内线性分配 + 开窗复位/关窗作废**，
不问「哪里空」。tileData 指针在 ROM 里是重定位编码（tilemap 大端存 0x0600F800→0x00F80006）。

**正确路线（待用户确认）**：让每个 BG 的窗口系统「接管」它的 charblock 全 512 tile 作线性分配池，

## 🔴 无 glyph 缓存 + 字符缓存有「拼接」硬障碍（2026-09-09 14:13 用户拍板先做缓存）

**确认：当前领 tile 无任何缓存**。链路 `PrintNextChar_Hook → chs_emit → print_glyph_px → chs_claim_tile`，tm1 分支直调 `v8_alloc_tile`（逐字领号，无「字符码→tile」查表）。日志 1171 次 alloc / glyph_len 恒 2 ≈ 585 字全是一次性新领。**同一字在一页里出现 N 遍就领 N 遍**。

**用户三约束**：①绑定 palette ②窗口内共享 ③跟随会话（InitTextPrinter 边界清空）。

**🔴 硬障碍（相位两段式 → tile 跨字符拼接，字符缓存做不了）**：
- 中文 11px 墨宽、12px 步进，tile 一格 8px → 一字横跨 2 列，相邻字**共享列边界**。
- phase 交替 0/4（12 mod 8 = 4）：phase=0 字领 t0（字[0:8]，纯）+ t1（字[8:11]，后会被拼接）；phase=4 字 t0=复用 `v8_phase_last_tile()`（上一字 t1），往其 [4,8) 列再写本字头 [0:4]。
- ⇒ phase=0 的尾段 tile 最终 = 前字尾[0:3)+背景[3:4)+后字头[4:8)，**依赖两个字符**，无法按字符码缓存；且「往已缓存 tile 追加写」会污染缓存。
- **结论**：tile 级字符缓存的唯一前提 = 消除拼接 = 每字独占整数 tile 列（取消相位压缩）。代价：12px→16px 步进（宽 33%），每字 3 tile→4 tile，靠缓存命中抵消。
- 纯字符可缓存的部分：phase=0 头段 tile（字[0:8]）、phase=4 尾段 tile（字[4:11]+清底）；phase=0 尾段 tile 不可缓存（被拼接）。平均每字 3 tile 中 2 可缓存 1 不可。
- 「跟随会话」→ 领航员多页短文本每页重复字少，缓存收益有限；大段对话收益大。
- 待用户定：①改渲染模型做缓存（接受 +33% 宽）或 ②回到「回收」路线（无拼接障碍，可直接落地）。

⚠️ 5 秒的具体拆解（VRAM 读 vs 返 0 重试各占多少）**无实测数据，属推论**。

### 当前「扫描避让」原理（动态，非静态表，2026-09-07 起已废静态带）

每次会话 **运行时**算一张 1024-bit 占用位图，三层判定：

1. **活引用层**（`v8_alloc_begin`，权威）：清零位图 → 扫 win 自身 tilemap
   (1024 项) + 所有启用 BG 中 charBase 相同的 screenblock（1024/2048/4096 依
   size 位），非零 tile 号标 1；再把各 BG tilemap **内存区整段**标占
   （防零槽位被当空闲数据写入）。
2. **VRAM 非空层**（`v8_tile_usable`，分配时实时）：候选读 32B，全空→可用；
   非空→查 ours 表，不在表内 → 负缓存标 1（本会话永久放弃）。
3. **ours 段表**（19 段 EWRAM）：我们领过的 tile 可自我覆盖回收；
   **超 19 段淘汰最旧 → 变"非 ours" → 被负缓存永久锁死**（泄漏根因）。

分配：`v8_alloc_tile` 顺序扫 [0x100, hi)，逐候选过 `v8_tile_usable`，
找连续 glyph_len 个 → 领号+标位图+推进游标；两遍无果返 0。**没有字符缓存**
（同字重复出现 N 次就领 N 次，2026-09-09 确认）。

**教训**：第 2 次栽在「跳过活引用重建」。以后任何"省掉预扫"的提议，
