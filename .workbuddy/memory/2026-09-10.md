### 硬结论（实证）
- **`0-2560` 不成立**：GBA BG VRAM 只有 64KB = 2048 tile（cb0..cb3），cb4/cb5 = OBJ（0x06010000 起）。
  ROM 自身证据：血条模板 `0x081BB40C` 的 `tileData = 0x06010000`。
  ⇒ 分配域 `[0,2048)`，逐窗再受 `[cb*512, cb*512 + min(1024,(4-cb)*512))`。
- 用户示例勘误：`cb1, 5 => **517**`（不是 516）；`cb0, 0 => 0` 正确。
- **跨块别名是全局下标的硬理由**：PSS B 图标物理 `g=522..525`，对 cb0 窗是 `t=0x20A`，对 cb1 窗是 `t=0x0A`。
  因此避让带只能按全局下标登记 —— 按「相对号+cb」必漏判。
- **静态避让带（读模板算得，非扫描）** 4 条共 448 tile：
  `[0,64) [896,1024) [1472,1600) [1920,2048)`；剩余 1600 tile。

## 17:10 修「回卷撞活字」（用户：设置页整屏乱 / 缓存疑似没命中）

**根因（两条，第二条是主因）**
1. 缓存「迟到一步」：内容只有 blend 之后才知道，而 blend 必须写进一个已分配的格

   ⇒ 回卷重扫认为它们是空地 ⇒ 直接写进去 ⇒ **屏幕上那些字被改内容**。

- **相位拼接格跟着换号**：12px 步进 12 ⇒ 相位只有 0/4，相邻两字**共用同一格**

### 18:05 回滚版为什么反而安全（读 b0dbcd3 的 `tile_alloc.c` 486 行的结论）
分配算法只有三个判定，**全部是当帧事实，零预测**：
① `v8_bit_get` 位图 —— `v8_alloc_begin` 从 win 自身 tilemap + DISPCNT 启用 BG 的
   screenblock 重建**活引用**：屏幕正在引用的格 ⇒ 永不可用；
② **现场读 VRAM 32B 是否全空**（`v8_tile_usable`）：非空即跳过，并做负缓存（本会话只读一次）；
③ ours 段表：非空格只有「确实是我们写过的」才允许回收。
🔴 `lo = 0x100 (256)` —— 起点**就落在官方图集区里**（fn3 图集 [1,535)），
   它敢这么放，是因为**不靠算准图集边界**，靠 ②「此刻空不空」兜底。
安全前提：引擎在打印文字**之前**已把该窗图集/框铺进 VRAM ⇒「此刻为空」= 本轮没人用。
⇒ 它不预测未来，所以不会被"预测错"反噬。这就是"理论上更容易撞却不撞"的全部原因。

我三轮的错（与三闸门一一对应）：
- 把 ②「实时读事实」换成「按 DISPCNT/BGxCNT/固有公式**推算**谁占用」，还把推算结果
  固化成避让带（带不能像读 VRAM 那样逐格实时重判）⇒ 推算**多标**时游标被推到我算不到的
  区域（别人的窗尚未使能/尚未装载，无从推算）⇒ 覆盖；少标则直接覆盖。
- 加 `v8_unmark_ours` 无条件清 ours 段的位图标占 ⇒ **削弱了唯一的权威层 ①**：
  屏幕正引用的格被放回池子 ⇒ 直接覆盖（叠字 / 整屏花的成因）。
- 改 `lo`（1 / 535）替代 256：丢掉了"靠 VRAM 兜底"的容错，变成必须算准边界才能活。

**结论修正**：不是「缺权威占用来源」，而是**本来有的权威来源（现场读 VRAM + 活引用重建）
被我用推算替换掉了**。以后若再做，只在旧三闸门上做最小增量，不叠检查。

## 18:15 修复「奇数个字的一行，换行后行尾只剩半个字」（渲染层，非分配器）

**症状**：野外对话框，一行**奇数个**汉字，换行后**行尾那个字只剩半个**（用户实机截图）。

**机制（`PrintNextChar_hook.c:print_glyph_px` 相位两段式）**：
- `phase != 0` 时 **`t0 = v8_phase_last_tile()`** —— 复用**上一个字的尾列 tile**（相邻字共享一列，设计如此）。
- 12px 步进 ⇒ 行末累计相位 `= 12n mod 8` ⇒ **n 为奇数时 = 4**（偶数时 = 0）。
- 换行后若相位没归零 ⇒ 下一行首字带 4 起步 ⇒ 走复用分支 ⇒ t0 = **上一行行尾字的尾列**
  ⇒ 整列（[0,8)）覆写它 ⇒ 行尾字右半没了 ⇒ **「半个字」**。
- n 为偶数时相位 0 ⇒ 走新领分支 ⇒ 不受影响 —— 这就是用户说「**奇数**文本」的来由。
  （推演 `_newline_half_sim.py` §1/§4 实证）

**为什么漏检**：行标识 `tpl^curY^curTileY` 是**间接**检测；官方 FE 是「先推一个、
另一个稍后才变」（`v8_phase_get` 自己的注释），存在窗口 ⇒ 偶发漏检。

**修复两处（都在渲染层，不碰分配算法）**：
1. **`PrintNextChar_Hook` 在 FA/FB/FE 上显式复位相位**：新增 `v8_phase_reset()`
   （tile_alloc.c：只清 `PHASE / PHASE_ROW / LAST_TILE`，**不动分配游标** —— 游标跨行
   继续推进才能让下一行的 tile 不与上一行重叠）。不依赖时序，是那条链的兜底。
2. **`t1 == 0` 保护**（同症状的第二条路径）：`w1 != 0` 时 `t1 = chs_claim_tile(...)`
   可能返回 0（v8 队列耗尽），原代码**无保护** ⇒ `tile_data + (0 << 5)` 写 **tile 0**
   （charBase 首格 = 图集/空白槽）+ `UpdateTilemap` 把 tile 0 写进表项 ⇒ 该字只剩左半。
   改为 `t1 == 0 ⇒ w1 = 0`（放弃右半，宁缺不砸）；另给 `phase != 0 且 last_tile == 0`
   加同样保护（退回领新对，绝不写 tile 0）。

**推演**：`src/util/work/POKEMON_RUBY_AXVJ00/_newline_half_sim.py` **ALL PASS**
（n 奇 ⇒ 相位 4 / 不复位 ⇒ 复用行尾尾列 = 覆写 / 复位 ⇒ 新对零重叠 / n 偶 ⇒ 安全）。

**产物**：`hook/out/game.bin` **8584 B 零告警**（回滚后基线）；ROM 打包 `PACK_OK`，
`0x800000` 段逐字节一致（`HOOK_MATCH`），sha1 `9258335818324d6eb767e0decde7bc5b3326aaf1`。
⚠ **打包时 mGBA 占着 `POKEMON_RUBY_AXVJ00_translated.gba`** ⇒ 产物落在
`POKEMON_RUBY_AXVJ00_translated_new.gba`，需关模拟器后重命名回原名。

**顺带**：`build_sh_equiv.sh` 已同步回滚后的 `build.bat` 清单（删掉不参与编译的
`scene_cfg.c` 编译/链接行与 `ChsAtlasWin_Entry` 导出）。
