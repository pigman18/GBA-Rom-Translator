## 一、派了 4 个 agent 并行搜索（3 成功入账 + 1 被误当"重跑"）

### Agent A：绕过 cb 区的渲染路线
- **1024 tile 是硬天花板**：tilemap entry 16 bit 里 tile 号占 10 bit（bit0-9）⇒ 0..1023。无法扩大。
- ❌ 位图模式 Mode3/4/5：系统级切换，宝可梦引擎全程 Mode0/1 ⇒ 全废。
- ❌ Affine BG：tile 号**只有 8 bit**，更差。
- ⚠️ OBJ 层：VRAM 分区独立（`0x06010000`，另有 1024 tile），但 **OAM 只有 128 个** ⇒ 只能当"溢出通道"。
  先例：Tonc ch.19 自带 `obj_puts()`。
- ✅ **每屏字模滚动装载（tile 号不变、内容动态换）** —— 这才是正路。
  先例：GBAtemp Klonoa 逆向教程（顺着游戏自己的 DMA 装载生命周期走，而非对抗）。
- `BGxCNT` charBase（bit2-3）/ screenBase（bit8-12）运行时可改，硬件支持，**但无成熟项目先例**。

### Agent B：Wokann 手法 + 同类项目
- **Wokann 关键源码已本地实测**（`tools/Pokemon_GBA_Font_Patch/pokeRS/src/`）：
  `HookInOrigin/DrawGlyphTiles.s` = `.org DrawGlyphTiles+2` + `bl DrawGlyphTilesChinese`（**改动只有一个 bl**）
  `HackFunction/DrawGlyphTilesChinese.s`：自己填 `GlyphTileInfo` + 调官方 `GetCursorTileNum` 拿落点
  + 调官方 blit **4 次**（16×16 = 左8px/右12px × 上下两半），字模 **128 字节/字**（`lsl r1,r1,#7`）。
- **`rh-hideout-chinese/pokeemerald-expansion` 是纯翻译数据仓库（31 个文件，无 src/）**。
  真引擎在 **`sayseong/pokeemerald-expansion`**：`src/chinese_text.c` —— 直接改 `RenderText` 主干，
  `width=12`(大字)/`10`(小字)、`height=15/13`，字模 **32 字节/字**（压缩字模 `DecompressGlyphTile`）。
  ⇒ **非 8 倍数宽度在 pokeemerald 系是原生支持的**（`widthMask=(1<<(width*4))-1`），**日版不行**。
- **Wokann 本人同时用三种字模规格**（`PokemonPinballRubySapphire_CHN` 有 charmap_16x16/8x16/8x8）⇒ 字模尺寸是自由参数。
- **美版有 `sGlyphMasks[9][8][3]`（RMW 混合 + 相位），日版没有** ⇒ 这是日美最大分歧点。

### Agent C：CJK 在 1024 tile 下怎么显示
- ★ **GBC 韩文版是教科书先例**：Bulbapedia 原文「loaded dynamically into VRAM…
  **a maximum of 128 different two-byte characters can be displayed at once**」。
  几千音节字靠"每屏最多 128 个不同字 + 动态换"。
- **Tonc TTE 作者亲自承认**：全量预载字体（Verdana 9 占 480 tile ≈ OBJ VRAM 一半），
  动态加载是"更安全但未实现"的替代方案。
- ★★ **日版红宝石官方字符集 0x00–0xFF 全是平假名/片假名/全角数字拉丁，零汉字**
  （`Bulbapedia Character_encoding_(Generation_III)`）。⇒ **日版引擎压根没有「双字节字符 → 字模索引」概念**。
  对照 NDS 珍珠钻石日版**有**汉字（选项里可切 かな/かんじ）⇒ GBA 时代 Game Freak 主动选了全假名。
- ⇒ **「几千汉字怎么进 1024 槽」是伪命题**：官方窗口 tile 槽本来就是**逐字复用**的，
  一屏可见字符 ≤128 ⇒ 只需 ~128 个 tile 号。
- 建议排序：① 移植 Wokann glyph streaming（首选）② 扩 `GetStringWidth` 支持汉字宽度（**必须**，否则换行错位）
  ③ 汉字双字节编码 + 避开日版控制码 0xFA–0xFF ④ **别再投入** charBase/screenBase 分页（无先例）。

## 二、🔴🔴 我亲自逐指令反汇编 —— 推翻旧地址表

**旧记忆里的日版地址表整体错位，最致命的是钩点。**

| 项 | 旧记忆 | **实测真身** |
|---|---|---|
| `DrawGlyphTiles` | `0x08003630` | ✅ **正确** |
| `GetGlyphTilePointers` | `0x08003730` | ❌ **`0x08003708`**（`0x08003730` 是函数体内 `mov pc,r0`，差 0x28）|
| `GetCursorTileNum` | `0x08003708` | ❌ 该地址就是 `GetGlyphTilePointers` 入口 |
| `UpdateTilemap` | `0x080036DC` | ✅ 正确（`bl 0x8003708`）|
| blit 非阴影/阴影 | `0x08003830`/`0x080038A0` | ✅ 正确 |

- 证据：`0x08003630` 内 `bl 0x8003730` @`0x08003660` —— **它调的正是 `0x08003730`**，
  但 `0x08003730` 是 `GetGlyphTilePointers` 的**分派指令地址**，不是入口。
  同理 `0x080036F0`(另一函数) 内 `bl 0x80037f0`。
- **`GetGlyphTilePointers` 跳转表池 @`0x0800374C`** → `0x08003750`(池外) / `376C` / `377C` / `3794` / `37AC` / `37D0` / `37F0`
  （与旧记忆的表内容一致，但基址记错）。
- 字模源实测吻合旧记忆：font0 → `0x081B3AAC+idx*16`；font3 → `(idx&0xFFF0)*64+(idx&0xF)*32+0x081B6D2C`。
- **教训（并入铁律 8）**：地址必须**逐指令反汇编核**，**禁止按「附近锚点 + 偏移」推算**。
  旧表就是"推算"的产物，错了整轮。

## 三、🔴🔴 官方 blit 是「8 像素定宽 + 整字覆盖写」—— 用户痛点的真机理

反汇编 `0x08003830`（非阴影）：
```
800383a: mov sl, r0        ; r0 = 1bpp 源指针
800383c: mov r9, r1        ; r1 = VRAM 目标
800383e/44: r2→ip(fg色), r3→r7(bg色)  (均为 u8)
800384a: r8 = 0x80         ; 位掩码
8003850: 循环 8 行 (cmp r1,#7)
8003854: r3 = *src++
800385c: 内层循环 8 次 (cmp r2,#7)
          位为 1 → r0 = fg色 ; 否则 → r0 = bg色
          r0 <<= r2*4 ; r4 |= r0
8003886: str r4, [r9+r5]   ; ★ 整 4 字节覆盖写（不做 RMW）
```
`0x080038A0`（阴影）：`cmp r4,#31` 固定 **32 字节 = 1 个 8×8 tile**，走 IWRAM 缓冲，
尾部 `bl 0x081B1294`（= `svc 0x0B`，蹦床区）。

⇒ **日版官方 blit：宽度/高度硬编码 8，整字覆盖，无相位掩码表**
（美版是 `sGlyphMasks[9][8][3]` RMW + `startPixel` 相位 = 支持任意宽度与跨 tile）。

**⇒ 用户「非 8px 在日版不好绘制」的真机理 = 官方 blit 的物理限制，不是我们代码的 BUG。**
**⇒ 中文字模应做成 8 的整数倍宽（8 或 16）；非 8 宽必须自写 blit 函数。**

## 🔴 一、地址表最终定案（含一次自我纠错）

**上一条里我改错了 —— `GetGlyphTilePointers = 0x08003730` 本来就是对的**，现已纠正回来。

| 函数 | 地址 | 判据 |
|---|---|---|
| `DrawGlyphTiles` | `0x08003630` | `bl 0x8003730` @`0x08003660`；表 @`0x08003674` |
| **`GetGlyphTilePointers`** | **`0x08003730`** | `push {r4,lr}` 叶函数；表 @`0x0800374C`；**2 个调用点** |
| `GetCursorTilemapPointer` | `0x08003708` | 5 行小函数；**1 个调用点** `0x080036EC` |
| `UpdateTilemap` | `0x080036DC` | **3 参数**；6 个调用点 |
| `CopyGlyph1bppTo4bpp` | `0x08003830` | 10 个调用点；`game_addrs.asm:21` |
| `CopyGlyph2bppTo4bpp` | `0x080038A0` | 6 个调用点；`game_addrs.asm:22` |

🔴 **教训（新）**：美版有**两个**易混函数 —— `GetGlyphTilePointers`（6 参，出两个字模指针）与
`GetCursorTilemapPointer`（1 参，出 tilemap 指针）。日版各有一份且**地址相邻**（`0x08003730` / `0x08003708`，
中间只隔 0x28）。**不要因为相邻或名字像就混为一谈。**

## 🔴 二、BL 扫描器新坑（已修，自证通过）

Thumb BL(T1) 的 `I1`/`I2` 必须由 `J1`/`J2` 与 `S` **取反还原**，不能只拼 `imm10<<12 | imm11<<1`：
```python
imm10 = hw1 & 0x3FF ; imm11 = hw2 & 0x7FF
S=(hw1>>10)&1 ; J1=(hw2>>13)&1 ; J2=(hw2>>11)&1
I1 = ~(J1^S)&1 ; I2 = ~(J2^S)&1     # ★ 取反，此前漏了 ⇒ 扫出 0 命中
imm = (S<<24)|(I1<<23)|(I2<<22)|(imm10<<12)|(imm11<<1)
```
自证：`0x08002AA6` 处 `hw1=f000 hw2=fdc3` → `imm=0xb86` → `tgt=0x08003630` ✅（扫出 572644 条 BL）

## 🔴🔴 三、核心发现 —— 痛点的完整机理链

### 3.1 步进源头：`FontFunc` 处理器硬编码
```
FontFunc[0] @0x08003568 (tm0):
   bl 0x08003520              ; 画字
   win[+0x18] += 2            ; ★★★ 恒定 +2 砖，硬编码
   win[+0x1B] += 1
0x080033A2 (tm2 尾):
   bl 0x08003630
   win[+0x20] += 0x40         ; ★ 恒定 +64 字节 = 2 tile
```
✅ 印证 `game_addrs.asm:65-70` 既有注释「日版无 `GetGlyphWidth`，步进由 FontFunc 硬编码」。

### 3.2 `DrawGlyphTiles` 真实 ABI（修正后）
```c
DrawGlyphTiles(u16 idx,       // r0
               u8 *tileBase,  // r1 ← VRAM 目标（**不是字形！**）
               u8 fontNum,    // r2 低8位
               u8 a3, u8 a4, u8 a5)
// 分支体 0x08003694 (font 0/1/2/6):
//   bl CopyGlyph1bpp(out0, tileBase,      a3, a4)
//   bl CopyGlyph1bpp(out1, tileBase+0x20, a3, a4)   ← ★ 下半恒 +0x20
```

### 3.3 `UpdateTilemap` 是 3 参数（≠ 美版）
```asm
08036dc: UpdateTilemap(win, upperTileNum, lowerTileNum):
   r0 = GetCursorTilemapPointer(win)       ; bl 0x0803708
   *(u16*)r0        = upper | (win[0x0F]<<12)   ; tilemap[0]
   *(u16*)(r0+0x40) = lower | (win[0x0F]<<12)   ; tilemap[32]
   ; ★ 没有美版那个 if (tilesWidth == 2) 写右列的分支！
```

### 3.4 🔴 三条硬结论
1. **宽度硬编码 8**（`cmp r2,#7` / `cmp r4,#31`）⇒ 9/11/12px 字模官方 blit **读不出来**
2. **日版无相位机制**（无 `sGlyphMasks` / `sGlyphShiftAmounts`）⇒ 必须 8 对齐
3. **日版结构上不支持「一字占 2 列」** ⇒ **Wokann 的 16×16 在日版会右半丢失**

### 3.5 ✅ 正解 = **8 宽 × 16 高**（零改动）
**实证依据**：日版原生假名字模（font0 `0x081B3AAC` idx=1「あ」）实测就是
**1bpp、8 宽 × 16 高、16 字节/字**（上 8 行 + 下 8 行）⇒ 这正是 `win[+0x18] += 2` 的来历。
**中文沿用此尺寸 = 日版原生设计，官方逻辑一行不改。**
