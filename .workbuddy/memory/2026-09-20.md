### 核心发现：`DrawGlyphTiles` 有双胞胎 —— **钩它不够**

全 ROM 特征扫描（`f0b5 4f46 4646 c0b4 83b0 041c 8846`）**只有 2 个成员**，前 32 字节逐字节相同：

|---|---|
| `0x08003630` | 4 处：`0x08002AA6` / `0x08002B16` / `0x080033A2` / `0x08003542` |

**⇒ 总覆盖点 5 处。只钩 `0x08003630` 会漏 tm2 家族那条。**

**⇒ 最终方案：钩 `GetGlyphTilePointers (0x08003730)`** —— 两个双胞胎的**唯一公共前置**
（`0x08003660` / `0x080033E4`，各一份）。**钩一处 = 覆盖全部 5 条路径。**

`GetGlyphTilePointers` ABI（已反汇编）：
```

 8003730: b510  push {r4,lr}      ← 叶函数
 8003732: 1c14  adds r4,r2,#0      ; r4=out0
 8003734: 0600/0e00  u8(fontNum)
```

后跳回 `0x0800373A`。**栈净额：桩 −8 == 原体 `push {r4,lr}` −8 ✅（铁律 4 满足）**。

### `idx` 语义（重大，B2 设计输入）

font3 字模公式（`0x080037AC`，重解）：
```c
*out0 = (idx & 0xFFF0)*64 + (idx & 0xF)*32 + 0x081B6D2C;
*out1 = *out0 + 0x200;
```
⇒ **`idx` 是 u16，语义 = 「字符号 << 4 | 字内子砖号」**：
**`idx >> 4` = 字符号（0..0xFFF）**，**`idx & 0xF` = 字内子砖（0..15）**。

实测（`ggtp_b1_5.log`，39 次，游戏内对话+菜单）：
- font3：idx `0x000`..`0x0F0`，如 `0A2 0A3 0EF 0F0`
- font4：idx `0x000`..`0x0B6`
- `idx >= 0x1000` 出现 **0 次**

**建议中文字区 = `idx >= 0x8000`（字符号 ≥ 0x800）**，让出 32768 字符号给官方（实际仅数百）。
⚠️ 样本仅 39 次偏小 —— **样本只能证明「上界 ≥ 观测值」，判死须查每张字体表实际长度。**

## `DrawGlyphTile_*` 的真实语义（B2 关键）

```c
/* 0x08003830 4 参：src = 8×8 1bpp（每行 1 字节，bit7 最左），dst 逐行 RMW 写 u32 */
void DrawGlyphTile_Unshadowed(const uint8_t *src, uint32_t dst, uint8_t w, uint8_t ink)
{
    for (y = 0; y < 8; y++) {
        b = src[y]; r4 = 0;
        for (x = 0; x < 8; x++) { r4 |= ((b & 0x80) ? ink : 0) << (x*4); b <<= 1; }
        *(uint32_t*)(dst + y*4) = r4;
    }
}

/* 0x080038A0 5 参：src = 32 字节 4bpp 索引 tile，值 0=底 / 15=墨 / 14=阴影 */
void DrawGlyphTile_Shadowed(const uint8_t *src, uint32_t dst,
                            uint8_t ink, uint8_t shadow, uint8_t bg)
{
    for (i = 0; i < 32; i++) {
        b = src[i];
        hi = b & 0xF0;  lo = b & 0x0F;
        v  = map(hi) | map(lo);        /* 0→bg, 0xF→ink, 0xE→shadow, 其他原样 */
        lut[i] = v;                    /* 先写 IWRAM 0x03000330 暂存，再转存 dst */
    }
}
```
**⇒ `chs_cell_from_1bpp` 产出的 128B 单元（TL@0/BL@0x20/TR@0x40/BR@0x60，
墨 15 / 阴影 14 / 空 0）与 `DrawGlyphTile_Shadowed` 的期望格式 100% 一致。**
**但官方一次只给 2 tile（TL+BL），中文要 4 tile ⇒ 差在「谁来展开第 3、4 个 tile」。**

### 6.2 🔴🔴 外部查证（本轮唯一真收获）

**权威证据**（`pret/pokeemerald` wiki · How Menus Work Part 2）：
> 「窗口系统会为该矩形区域**预留**所需数量的 tiles」
> 「A window will use **width × height** many tiles in the tileset」
> 「5×2 tile 的文本区 ⇒ 需要 5×2 = **10** 个 tile」
> 「VRAM 分 4 个 tileset 各 512 tile ID；**ID 2048 及以上是精灵数据，不能安全作 BG**」

⇒ **官方是「按屏幕格子定号」（tile 号 = 位置的函数），与「画了多少个字」无关。**
同一窗口里重画一万遍，tile 消耗恒等于 `width × height`。

**🔴 关键推论（推翻我们长期的隐含假设）**：
中文 12px 步进在一行里占的**格子列数**与日文 8px **相同**（都受窗口宽度约束）
—— 因为 tile 按「格子」算，不按「字」算。
⇒ **中文不比日文多花一个 tile**；代价只是「一行汉字数 = 日文的 2/3」。
⇒ **「空间不够」不是汉字的固有代价，是我们绕开官方窗口模型、自建「按字领号」全局池造成的。**

**外部其他汉化怎么做**：清一色「静态字库替换 / 图片替换 / 混合」（CSDN TextForm、
FE8-Compact-CN 12×12 等）——因为宿主游戏本来就走「格子定号」，**从不缺 VRAM**；
它们说的「汉字数量有限」是 **ROM 容量**问题（我们已解决，8192 槽）。
⇒ 没有公开案例解决过「全局动态池」这个我们自造的坑，**也没有「绕过 cb」的先例**。

**❌「绕过 cb 区」被硬件否掉（记下，别再重复找）**：
- 位图模式 Mode3/4/5：可全屏任意汉字，但宝可梦引擎全程 Mode0/1 ⇒ 等于重做整个渲染。
- OBJ（精灵）：OBJ VRAM 独立 1024 tile（`0x06010000`），但硬件 OAM 上限 **128 精灵/帧**、
  单行 ≤32；一屏 80~180 个汉字放不下，且 16×16 汉字占 4 个 OBJ tile。只适合少量大字。
- ⇒ **GBA 的 BG 文字物理上必须走 VRAM tile，没有例外。**

### 11.2 🔴 决定性参照一：官方美版引擎 = 「窗口私有网格 + 格→号算术」
`pret/pokeemerald src/window.c` 原文：
```c
allocatedBaseBlock = BgTileAllocOp(bgLayer, 0, templates[i].width * templates[i].height, 0);
gWindows[i].window.baseBlock = allocatedBaseBlock;
BgTileAllocOp(bgLayer, allocatedBaseBlock, templates[i].width * templates[i].height, 1);
// 写 tilemap：
u16 currentRow = windowLocal.window.baseBlock + (y * windowLocal.window.width) + x
               + GetBgAttribute(windowLocal.window.bg, BG_ATTR_BASETILE);
// RemoveWindow: BgTileAllocOp(..., 2) 归还
```
⇒ **tile 号 = `baseBlock + y*width + x`，纯算术、零分配决策、零扫描、零账本。**
关键推论：**行 tile 消耗 ∝ 行像素÷8，与字数无关。**

### 11.3 🔴 决定性参照二：同引擎家族的中文实现 —— 零 tile 号分配
`rh-hideout-chinese/pokeemerald-expansion src/chinese_text.c`（已跑通）全文只有三件事：
`IsChineseChar`（双字节判定）/ `GetChineseFontWidthFunc`（大 12 小 10）/
`DecompressGlyph_Chinese`（`DecompressGlyphTile` ×4 把 2×2 共 4 个 tile 塞进 `gCurGlyph`）。
**没有任何一次申请 tile 号**，交回原生 `CopyGlyphToWindow` 写进窗口自己的块。跨 8px 边界由
`OffsetCurrGlyph` 处理（注释自嘲 `Do cursed u64 handling of double wide glyphs`）。

### 11.4 硬件上限（GBATEK/tonc 原文核实，别再找捷径）
- 单 BG 层 **1024 tile 是硬顶**；8bpp 不涨（"a bit less in 256 color mode"）；affine 只 256；
  charBase 4 档只是**移动窗口**；拿 OBJ charblock 当 BG **真机不行**（tonc 原话）。
- **OBJ 画字不可行**：OAM 硬顶 128/帧；16×16 汉字 1 字 1 精灵 + 4 tile ⇒ 最多 128 字。
  另纠正：**"每扫描线 ≤32 个精灵"是错的**（那是 NES/SNES/DMG 的数），GBA 每行可达 128。
- **位图模式是"取代"不是共存**：Mode 4 直接占 `0x06000000–0x06009FFF`，BG tile 层不存在。
- **多 BG 只是"分片"不是扩容**：BG VRAM 共 64KB=2048 tile，还要扣每层 tilemap 2KB。
- ✅ **HBlank DMA 是唯一硬件扩容手段**：扫描线 1232 周期（HBlank **272**），每 HBlank 实用
  **100–200B ≈ 6 个 4bpp tile**；须按 8 行条带换（tile 是 8×8，中途换会撕裂）。
- GBA 上唯一现成的字形缓存实现：`agb`（Rust）`DynamicTile16`；`tonc` TTE / Butano / libgba 都没有。

## 13. 路线调研 v14「跳出三条前提」（用户：「挖掘一下其他方案」）

**用户给出的三个前提**（自认的无奈之举）：

### 13.1 核心结论：**「完全不够」是算术必然，不是实现缺陷**

把痛点折算成一个可验收的数字 **L = 同屏可驻留文本行数 = 可用号 ÷ 60**：

| 口径 | 号 | L |
|---|---|---|
| 一层 BG 硬上限 | 1024 | — |
| 官方日文图集（font0/3 cap=512） | **512** | 占号空间的一半 |
| 窗框 `[cap, cap+23)` | 23 | |
| 领航员静态美术（`VRAM+0x5000` = 号 640） | 64 | **落在"池"内部，`v8_official_end` 看不见** |
| ⇒ 名义池 `[535,1024)` = 489，扣碎片后最大连续 ≈ **425** | | |
| 一行中文（20 字 / 240px）= 30 tile 列 × 2 tile 行 | **60** | |
| 领航员需要 9～12 行 ⇒ 需 **540 ~ 720 号** | | **L 需 ≥ 12** |
| **现状 L ≈ 5~7 ⇒ 缺口约 2 倍** | | |

⇒ **三条前提是同一个病**：在一个「官方已预定一半、且被碎片化」的号空间里做增量分配。

### 13.2 本轮新增实测（可复核）

| # | 事实 | 方法 |
|---|---|---|
| 1 | 全 ROM **52 个窗口模板**，`charBase ∈ {0,1,2,3}` 全在用；模板区 0x081BB3DC..0x081BB8C4，步长 0x18 | 扫描 0x081BB300..0x081BBC00 |

6. 🔴 **GBA 汉化通行档位是 8×8 / 8×16，不是 12×12**：
   `suhli/gba-narutorpg-chs`（8×8 小字 + MuzaiPixel 8×12 pad 到 8×16）；
   传统法「汉字写进 16×16 等分 4 个 8×8 tile、tilemap 写 4 项」；
   FE 链（`laqieer/FEHRR` + FEBuilderGBA）「**Draw utf-8 patch + Anti-Huffman + 字模按需生成入 ROM**」+
   **字宽表（Width Table）** 决定 ASCII 半宽/汉字全宽。
   ⇒ ①**每字 4 tile 是常态**，我们不特殊；②我们走 **11×11 比通行档更宽更豪华**（所以空间更紧）；
   ③**B3（ASCII/数字回官方 8px 图集）是传统做法，我们没试过**。

### 14.3 结论没变（诚实交代）

- **"全网"做不到**：贴吧/B站/QQ群/Discord/日文改造圈**不入索引** = 永久盲区；
  日文检索我没做；Discord（RHH/pret/gbadev）最可能有答案但需登录（**标记为高价值未挖**）。
- **但结论不依赖"有没有别的做法"**：一切方案都在解
  `同屏需驻留 tile 数 ≤ 1024 − 512(官方图集) − 23(窗框) − 64(领航员静态美术) ≈ 425`，
  而需求 ≈ 60/行 × 9~12 行 = **540~720** ⇒ **缺口 ≈1.7×**。
  **换渲染器/换定号/换分配器都不改这个不等式。**

### 14.4 下一步（比再找 10 篇调研值钱）

**实测 A**：领航员**到底需要多少个不同的字形 tile**（逐页逐行统计真实不重复汉字数）→
得出真实需求 N，与真实可用 M 比：
- N ≤ M ⇒ **根本不用扩容，只修排版（零 ROM 风险）**
- N ≈ 1.2M ⇒ 可能 **B3（ASCII 回官方 8px 图集）就够**
- N ≥ 1.7M ⇒ 才必须动 A1/A2/A3

⇒ 验证「**领航员 BG1 关闭 ⇒ 那段 VRAM 是否真空闲**」（A3 可行性）。

**顺序建议**：实测 A（零风险，定生死）→ 若够则 B1 排版 → 否则 **A1（回收 512 图集，

## 15. 方案再整理：领号单位从「字」改成「窗口」（v15，用户当场否掉 14.4）

### 15.1 用户的否决（成立）

### 1. 判据级修正：号必须按 charBase 归位
`scripts/verify_pool_safety.py` 第一版把 `tile_index` 当全局号 ⇒ 得出「处处冲突」的假象，
两版结论（含我一度采纳的 `[252,512)`）**全部作废**。
正解：`gnum = charBase*512 + tile_index`（charBase = `BGxCNT` bits2-3）。
- 文本层 **BG0**，charBase 常 **2** ⇒ 号 **[1024,2048)**
- 美术层 BG1/2/3，charBase 常 **0** ⇒ 号 [0,1024)

### 2. 数据裁决：**不存在安全静态池**
6 个 savestate 并集（号 [0,1024) 被引用 312 个）：

| 池 | 结果 |
|---|---|
| `[0,384)`（v21 现役） | ❌ 正压在美术 tileset 上 |
| `[252,512)` | ❌ 归位后 **149 号冲突** |
| `[585,767)` | ❌ 72 号冲突 |
| `[854,1023)` | ❌ 13 号冲突 |

号 [1024,2048) 内六场景并集空闲段只有 `[1824,2024)` 200 号 / `[1683,1809)` 126 号 / 其余 ≤17。
⇒ 静态避让带**在数据上判死**，不可能靠「换个区间」修好。

### 3. 规则闸门：本路线本身违规 ⇒ 依规停下问用户
`axvj-no-avoidance-band.mdc` 字符串级判定命中三行：`POOL_LO` 起点常量（0x1..0x3FF）/
扫 VRAM 找空档（`verify_pool_safety.py`）/ 注释里「交集最大的一段」措辞。
该规则明文：**「若修法是 cap span / 抬 lo / 全局顶基址 → 违规，先停问用户」**。
