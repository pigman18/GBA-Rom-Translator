### 发现（逐指令反汇编，零推测）
| | 官方 | 我们（v21 之后） |
|---|---|---|
| 定号依据 | **字形索引 `c`** | **窗口内位置 `TILE_OFFSET`** |
| 公式 | `tile = TILE_BASE + 2c` | `tile = TILE_BASE + win[0x18]` |
| 同屏多块 | 同字同号 ⇒ 共享，**绝不覆盖** | 每块从 0 ⇒ **全部互相覆盖** |
| 号用量 | `2×不同字形数 ≤ 200`（有上界） | `2×总字数`（**无上界**） |

- `PrintNextChar 0x080032F8`：`0x0800330A ldrb r3,[r1]` 取字符 `c` → `0x0800337A adds r1,r3,#0`
  把 **`c`（不是列号）** 传给 `FontFuncTable[tm](win,c)`。**这是全新认知**（此前误以为传列号）。
- 落砖 `0x08003585`：`lsls r2,r1,#1` → `ldrh r1,[r0,#22]`(TILE_BASE) → `r2 = TILE_BASE+2c`
  → `bl UpdateTilemap(win,t,t+1)`（`+1` = 同号下半 tile）。
- 字形加载 `0x08002A8C`：`dst = tileData + startOffset*32 + glyphIdx*64` ⇒ 字形按**同一索引**落位；循环上界 **256 字形**。

  （`1 3 5 7…`）=「位置定号」指纹 ⇒ 22 块只剩最后写的 7 个字 ⇒ 整屏塌成几种字形反复。

### 结论
- **「领航员正常 vs 设置页崩坏」的分界 = 同一基址上的独立文本块数**（长串串内推进不覆盖 / 22 个独立块块块复位）。
  ⇒ 不是页面问题，是**块数**问题。
- **容量账**：官方 `2G ≤ 200`（`G ≤ (30×20)/(2×2) = 100`）**有上界**；
  我们按位置定号 ⇒ `∑(每块字数)` **无上界**。
  ⇒ 「领航员撑不住」「战斗久了文本乱飞」是**坐标系选错**，不是容量不够。

- 🔴 **P 的 4977 px + 「73 字只用 18 号」= 设置页塌陷的量化复现**，与 VRAM 实证（7 个字）方向/量级一致。
- 🔴 **「严格按字形索引定号」(A) 在 11×11 字形上不成立**，原因是三条硬约束：
  ① 官方 `TILE_BASE+2c` 成立的前提是**字形宽 8 px = 1 tile**；我们墨宽 11 > 8 必须跨 2 列。
  ② 同一 code 在相位 0/4 需要**两份不同偏移的字模** ⇒ 一 code 两槽。
  ③ 按 code 定号 ⇒ **相邻字不可能同号 ⇒ 尾列无法共享 ⇒ 每字被迫独占 2 列 = 16px 步进**。
  ⇒ **「按字形索引定号」与「12px 紧凑步进」结构上互斥**。A 满屏要 791 号，溢出即崩。
- ✅ **S = 第三条路**：不按 code、不按块内线性偏移，而按**字形最终落在屏幕哪一格**定号
  ⇒ 同格天然共享（重画零消耗）、异格天然不同号（不覆盖），**且 12px 步进不变**。

### 选定方案 S（公式）
```
cell(ty, tx) = ty*30 + tx        (ty∈[0,20), tx∈[0,30))
n = cell(ty, tx);  if (n >= 0xFE) n += 2;    /* 跳过引擎箭头保留号 254/255 */
tile = TILE_BASE + n
下半 = claim(ty+1, tx)   ← 🔴 必须重算，不是 t0+30
```
- 纯函数：不查表/不记账/不扫描/不设水位 ⇒ **不触「禁抬水位」，不触「禁避让带」**。
- 容量：号需求 = 屏幕格数（≤600），**与字数解耦**；最坏 188+602 = **790/1024**，溢出不可能。
  ⇒ 这就是「涨到 1000 怎么办」的答案：**不用怎么办，号用量根本不由字数决定。**
- **S 严格优于 P**：P 下任何两个同 TILE_BASE 的块都从 0 起画、必然互撞；
  S 下只有「占同一格」才冲突（那本来画面就是同一位置）。

### ✅ 核实① `ty` 取哪个字段 / 换行改什么 —— 闭，结论比预期强
- `GetCursorTilemapPointer 0x08003708` 逐指令：`格 = (win[0x1C]+win[0x1D])*32 + (win[0x1A]+win[0x1B])`
  ⇒ **stride 32（不是 30）**；行 = `0x1C+0x1D`，列 = `0x1A+0x1B`。
  `UpdateTilemap 0x080036DC` 只写 2 项，第二项 `adds r0,#64` = 下一行，与 stride 32 自洽。
- **换行**：`PrintNextChar` 跳转表**基址 = `0x08003324`**（`ldr r1,[pc,#8]` 载入的是**指针**）。
  `FE → win[4]==6` 分支（`0x08002DF4`/`0x08002E60`）⇒ **`win[0x1B]=0; win[0x1D]+=2`**（一文本行 = 2 tile 行），**不改 `0x1C`**。
- 🔴 **`InitTextPrinter 0x08002C68` 每次复位游标**（`win[0x1B]=0`、`win[0x1D]=0`、`win[0x18]=0`、`win[0x04]=1`），
  并把 **`win[0x1A]=a4`、`win[0x1C]=a5`**（`strb r3,[r0,#26]` / `strb r9,[r0,#28]`）。
  ⇒ 游标和 `TILE_OFFSET` 一样是「每块复位」量 ⇒ **块基准只能取 a4/a5**。
- 🔴🔴 运行时实证（设置页，120 次采样）：22 块同 `win=0x0202E658`、同 `tb=1`、同 `tpl/tmap`，

### 🔴🔴 核实③（计划外）`TILE_BASE + 号 < 1024` 是硬约束 —— 选型文档容量账作废
- **函数拓扑补全**：`InitTextPrinter` 本体有 **4 个**调用者：
  `0x08002CDE`（函数 `0x08002CC0`）、**`0x08002D10`（纯转发器 `0x08002CFC`）**、
  `0x08002D52`（主包装 `0x08002D1C`）、`0x080030FA`。
  🔴 原文只扫了主包装 60 点，**漏掉转发器 39 点** —— 这就是取值集合被低估的根因。
- 两个转发器都只做 `lsls/lsrs #16`（r2 截 u16）、`#24`（r3/a5 截 u8），**都不改 tileBase 的值**。
- `TILE_BASE` 实测集合 = `{1, 32, 64, 96, 128, 160, 168, 256, 400, 440, 656, 704, 752}` + 运行期取值。
  🔴 **`0xBC` 那族真值 = 752**（`movs r2,#0xBC` 紧跟 `lsls r2,r2,#2`）；
  `scan_inittp_sites.py` 的回溯正则不含 `lsls` ⇒ 它会停在 `movs` 上报 188。**该脚本已修**。
- 层 tile 空间 = `tileData 0x06008000` 起 **32 KB = 1024 tile**，tilemap 项 10 位
  ⇒ **预算 = `1024 - TILE_BASE`**：752→**272**、704→320、656→368、440→584、400→624。
- `TILE_BASE=752` 的窗口实测 `a4=1, a5=15` ⇒ 绝对格号起点 `15×32+1 = 481 > 272` ⇒ **第一个字就溢出**。

**池子 100% 落在「某块的字模写入区」内**（不是 53%，也不是 21%）。

**⇒ 可持续方案只剩两类（都不是调地址）：**
1. **独占**：在 `0x08002950` 桩里把引擎的字模写入钉死到一个块（`*0x03000328` 换成 RAM 副本 +
   改其 `tileData`），其余块归我们。代价：`UpdateTilemap` 的号是 `TB+2*glyph`，10 位号域
   从 charBase C 只能到达块 C 与 C+1 ⇒ 需约束所有文本层的 charBase。
2. **不做第二份缓存**：喂字给引擎自己的缓存（引擎 index 域只 256 ⇒ 需 bank 切换）。


## v37 判据级定论：引擎字模缓存 = 整块，我方砖无立足点（2026-09-21 下午）

用户质疑「池子就是静态避让带 2.0」，核实后**成立**，且目标本身不可满足。

- 全 42 页实测：`tpl[+8]=3`（⇒ `InitWindowTileData` 走 `index*64` 分支，512 槽）、
  `tpl[+9]=1`（⇒ 预取器 `0x080029E0` 只在 font==1 时执行，而它恒为 1）、`TB` 恒 1。
  预取器逐指令：`r2 = counter & 0xFF` 作**槽号**传给 `InitWindowTileData`，`counter += 16`，
  `counter == 0x100` 返回 1 ⇒ 每次窗口激活**重写 `tileData` 块槽 `[1,513)`**。
- 约束链（显示侧）：引擎 map 号 = `win[+0x16](TB) + 2*glyph`，写砖槽 = `TB + 2*glyph`
  ⇒ 两者相等 ⇒ **`tileData` 必须 == 该层 charBase**。实测两例吻合：
  人口 0 `tileData=0x06004000`(cb1)/`mapBase=0x0600F000`(sb30)；人口 1 `0x06008000`(cb2)/`0x0600F800`(sb31)。
- 我方砖的 map 号经同层 charBase 寻址 ⇒ **必须落在同一 charBlock**。
- ⇒ **块内只剩槽 0 一块砖（32 B）没被覆盖**。所以「找空档」是可满足性问题（解集为空），
  不是采样密度问题 —— 避让带族（含 v35/v36 池子）在数学上无解，正式判死，不要再出 3.0。
- 模板表静态核对：`0x081BB000..0x081BC000` 共 105 条候选模板，`tileData` 指向
  cb0=24 / cb1=13 / cb2=29 / cb3=38 / OBJ=1 ⇒ 四个块都至少有一条模板指过来。
- 12px 步进的必然结果：11px 墨 + 12px 步进 ⇒ 字形跨 8px 网格
  ⇒ 借引擎自己的网格渲染只能退到 16px 步进（用户已否决）⇒ **自写渲染器不能省**。
- 唯一还成立的方向：**不再与引擎共享 charBlock** —— 让引擎缓存落到邻块（`TB` 抬到 512 或
  `TB=0`），并在我们已有的 `UpdateTilemap` 钩子里给引擎那套号加偏移（`TB+2g` → `+512`），
  层 `charBase` 不动。风险点 = 4 个 charBlock 的预算（tilemap / 静态美术 / 我方砖 / 引擎缓存）。
- 纪律：**先出 4 块完整预算表（屏 × 层），表闭合才写代码**；不闭合就报「哪一屏没位置」，
  不许先改码再撞。


## v38：预算表出炉，「挪缓存到邻块」全页闭不住；空档族再判死一层（2026-09-21 下午）

用户质疑「你只是把风险推给 UI 分配」。核实后**成立**。

**1. 4 块预算表**（`.tmp/budget.py`，逐页 × 逐块：tilemap / 非零砖 / 自由砖）
—— 依据全是结构量：tile 数据寻址 `charBase*0x4000 + n*32, n∈[0,1024)`；
引擎缓存 `tileData + TB*32 + index*64`（font3）、TB=1、512 号；tilemap = `screenBase*0x800` 独立于 charBase。

| 页 | BG0 cb | cb0 | cb1 | cb2 | cb3 | 「缓存挪邻块」 |
|---|---|---|---|---|---|---|
| o_title | 2 | 0 | 0 | 143 | 41 | cb2→cb3 差 41 ❌ |
| o_start | 2 | 458 | 195 | 76 | 206 | cb0→cb1 差 195；cb2→cb3 差 206 ❌ |
| o_bag | 2 | 0 | 164 | 500 | 44 | cb1→cb2 差 500；cb2→cb3 差 44 ❌ |
| o_party | 1 | 134 | 369 | 511 | 28 | cb2→cb3 差 28；cb1→cb2 差 511 ❌ |
| o_info | 2 | 190 | 124 | 500 | 128 | cb0→cb1 差 124；cb2→cb3 差 128 ❌ |
| o_moves | 2 | 190 | 124 | 500 | 134 | 同上 ❌ |

⇒ **每一页的邻块自由砖都 < 512**，提案在数学上闭不住，**正式放弃**。

**2. 引擎缓存的号区间 = `[1, 1+2G)`，G = 当前装载字库的字形数（数据相关）**
判据：`0x08002A50` 的 font3 公式 `tileData + TB*32 + index*64`，TB 实测恒 1。
实测各页 cb2 非零 = 143 / 500 / 500 / 511（o_title / bag / info / moves / party）
⇒ G = 71…256 **逐屏不同**。cb1 同样 124…369。**没有固定占用图。**

**3. 更致命：VRAM 跨屏不清零 ⇒ 采样法「双重失效」**
失活屏的残留数据在 dump 里照样非零（o_party 的 BG2 disp=0，cb2 却有 511 非零 = 上一屏残留）。
⇒ 采样法不只是「漏掉尚未写入的空档」，还会把**已死的残留当成已占用**。
「采样求补集」族（静态避让带 / freemap 池 / v35~v36 段表）**两头都错**，不是密度问题。

**4. 唯一闭合的几何（charBase=2 的文本页）—— 固定三段，零采样**
```
[1,   513)   引擎字模缓存   512 号 = 256 字形 × 2 砖（TB=1）
[514, 768)   我方字形       254 号 = 127 槽
[768, 1024)  tilemap        256 号 = 4 层 × 2KB
合计 1022 / 1024
```
菜单页实测吻合：tilemap 恰在 [768,1024)（sb28/29/30/31 → 号 768/832/896/960）。
我方 v36 的 p1 = 号 514..768 **正是这一段** ⇒ cb2 页的布局本来就是对的。

**5. 队伍/概况页的问题在 charBase=1**
文本层 cb1 ⇒ 窗口 = cb1+cb2，**两半都被引擎缓存占用**（cb1 是 G=184 的缓存，cb2 是另一屏残留/缓存）
⇒ 窗口内没有 [514,768) 可站。**修复方向 = 把该页文本层 charBase 1→2**（BG0CNT 2 位字段），
让所有文本页共用同一套几何；cb1 还给 BG1/BG2/BG3 的美术（它们 charBase=0）。
待核：队伍页 BG2 charBase 也是 2 但 disp=0，开概况子页时会不会同时亮。

**6. 下一步（改动小、可回退、能定论）**
`0x08002950` 全 ROM 仅 2 个调用点，是 `*0x03000328` 唯一写入者；桩 `SetWindowTileCache_Hook`
已装好。在其内记录 `(win, tileData, TB, tpl[+8])` 到 RAM 环，跑一遍得到**完备三元组集合**
（候选 tileData 有限：模板表里落 VRAM 的 105 条）——这是**有限枚举**，不是「采了几页」。

## 【外部调研】坐标系选错了（用户要求「从头调研，别在当前工程思维里打转」）

产出：`docs/调研_20260921_外部视角_引擎坐标系与硬件边界.md`

**结论一句话：我们一直在打一场不存在的仗。**
引擎模型 = **「每窗口一块私有画布，tile = TILE_BASE + TILE_OFFSET」**（15-0b 已逐指令证），
而 v8~v36 全部假设「有全局官方占位区，要在里面找空档」——后者是对 `cap=512` 的误读。

**外部一手（本次实际读原）**：
- 硬件：一层 1024 tile 是硬墙；BG/OBJ 物理隔离不可互换；`DISPCNT bit5` 是 H-Blank Interval Free
  非 VRAM 重映射；**不存在「扩展 cb 区」技术**；HBlank 换字模粒度 8 行、无商业先例；
  OBJ 独立 1024 tile 但 OAM 硬顶 128 项/帧。
- **美版 pokeruby `src/text.c`**（本工程 `tools/` 内）：`GetCursorTileNum` 有**两分支**——
  VWF 网格 = `startOffset + 2 + (cursorY>>3)*width + (cursorX>>3)`（**号=位置**）；
  等宽 = `startOffset + tileDataOffset + 2x + y`。`InitWindowTileData` 也两分支，
  网格分支**不加载字库**、返回 `startOffset + 2 + width*height`（**串联分配，窗口天然不重叠**）。
  ⇒ **美版有「窗口私有 tile 缓冲」，号由位置决定。**
- **Wokann pokeRS 补丁**（同代引擎，源码在 `tools/Pokemon_GBA_Font_Patch/pokeRS/`）：
  `dest = win->tileData + 32*GetCursorTileNum(win,0,0)`，汉字逐半写入窗口自己的缓冲；
  字模留 ROM（`0x09000000/0x09100000`）；README 明写**「不动 charBase、不扩容 VRAM 字库」**
  且「**海外版非美版也可用，只需改函数地址定义**」。
- **MOTHER 3 英化/法化**（GitHub `JumpmanFR/Mother3VF` 有完整 ASM）：
  字库**从不常驻 VRAM**（`lsl r0,r0,#5` 按字符号从 ROM 取 0x20 字节）；自写 VWF 焊接
  （`text_weld`：右移 curr_x 后 OR 进当前 tile，溢出位左移进下一 tile）；
  精灵文本写 **OBJ 区**（`new_pos_base $6011800`）。代价：Tomato 原话
  「**没有任何一个文本显示例程没被动过，至少 10~20 套**」+ RAM 行缓冲 21→250。
- **pokeemerald 中文 fork**：`chinese_text.c` 全文件**零 tile 号分配**，字形塞进官方
  `gCurGlyph.gfxBufferTop/Bottom` ⇒ 前提同样是「站在窗口私有网格上」。
- 其他中文汉化：火纹用「原地覆盖日文字模 + tbl 重映射」（受字库容量限）；
  「字库扩容」类只解决 ROM 侧，**对 VRAM 无效**——问题从来不在字库，在落点坐标系。

**关键内部印证**：日版 tm3 就是网格模式（`sub_80034A8`：`tile = cursorTileX + cursorX + 2
+ TILE_BASE + row*30`，与美版 VWF 同构，只是 stride 写死 30）。
**`chs_claim_tile` 的 tm==3 分支从来没出过撞 UI 问题**（09-21 实测 START 主菜单 8 项全完整）；

### 外部硬事实（每条有出处）
- **官方自己就复用码位**：Gen II 在战斗/概要/图鉴界面「**覆盖**在不用于显示文本的 code point 上」（Bulbapedia）。

- **SNES 动态法**：按需取字 → 生成 tile → 上传 VRAM → **改 tilemap 去引用新 tile**。
- **NDS NFTR**：`CMAP` 段 = 字符 → 字形索引；字形索引与 tile 号无关。
- **Wokann（同代同源）**：号来自引擎 `GetCursorTileNum`，只用官方字段。
- 🔴 **撞 UI 的根因是「扩容」**：「原地覆盖」不改字形**数量**、不改**装载长度**、不改 charblock 布局
  ⇒ **完全不触碰 VRAM 分配 ⇒ 不抢 UI**；**扩容/加字才会抢**（装载长度一变就压到后面的 UI tile）。—PGCG 教程·图形篇
- **官方中文（iQue 神游，2005《密特罗德：零点任务》等一批）也是改引擎/覆盖字库**，从不做运行时避让。

### 项目已四次得出同一结论、四次未执行
09-08 全网检索 / 09-11 路线纠偏（删 v8/v9 分配器改用官方 `GetCursorTileNum`）/ 09-20 15-0b（不存在全局官方占位区）/ 09-21 真问题定位（官方=字形索引定号）。

### 🔴🔴 本轮唯一新判据：`20260921_真问题定位` §9.3 把「字形缓存」误判成「账本」
§9.3 原文：「取字形码要先建 `code → slot` 表 = **账本**（用户明令禁止）⇒ 只复刻性质、不复刻形式」。
**这是误判**：
- 账本 = **读回 tilemap/VRAM 推断**「这格是不是我们写的」⇒ 依赖对外部行为的观测，不可靠。
- `code → slot` = **我方私有数组**，自己分配 ⇒ 不依赖任何外部观测。
- **全世界都这么做**（= 字形缓存 glyph cache）；**官方自己就是 `tile = TB + 2*glyphIdx`，`glyphIdx` 就是 slot**。
⇒ 用户禁的是「探测外部占用」，不是「管理自己拥有的槽位」。两者被混为一谈了。

### 结论：唯一「加字不涨号」的结构
```
tile = TILE_BASE + 2 * slot(code)
号需求 = 2S（有上界，与字库总量无关）
```
| 方案 | 号需求 | 加字/加场景 |
|---|---|---|
| 避让带/水位 | ∑(每块字数) 无上界 | 线性增长 ⇒ 迟早不够 |
| 位置定号（方案H，现状） | ∑(每块字数) 无上界 | 线性增长，靠版式不变式侥幸 |
| **字形槽定号** | **2S 有上界** | **槽位轮换，号不变** |

⇒ **这才是「可持续」**：加场景、加文字、加字库，号需求恒定；同字同号自动共享 ⇒ 多块不覆盖。

### 待决（实施阶段）
1. 槽数 S 与 TB 越界（TB 最大 752 ⇒ `752+2S ≤ 1024` ⇒ S ≤ 136；或按 15-0b 第 2 步归一 TB）。
2. 槽位回收时机（`InitTextPrinter` 粒度太细：设置页 22 块会被误判为 22 屏）。
3. 与静态 UI 图块区间的关系：须**构建期**确定分区，不得**运行时探测**（后者即避让带）。

## 2026-09-21（续四）用户追问「16×16 也撞」⇒ 撞的判据归因到「地契」

用户原话：「撞 UI 是我们自造落址方式的特有产物，那有没有什么办法不撞，实际我记得以前哪怕用 16×16 也是撞的，
所以才搞了日文同链路，自定义分配器」。

**更正**：我上一轮「复用引擎的槽 ⇒ 构造性不撞」说得太满。16×16 也撞 = 形状不是原因。

### 撞的两种成因（都不是字形尺寸造成的）
1. **被覆盖**：我们的号落在引擎预取缓存区 `[1,513)` 内 ⇒ 被引擎整块重写（P32 实证）。
2. **撞 UI**：我们的号落在 UI 美术 / tilemap 的号上。

### 16×16 为什么救不了（三条硬账）
- **4 tile/字**（2 列 × 2 行）= 最贵形状 ⇒ 整块 1024 号只容 256 字，还要分给 tilemap/引擎。
- 日版 `UpdateTilemap` **一次只写 2 项**（8 宽字）⇒ 16 宽字右半的 map 项写不进去
  （`方案2/Wokann 16×16` 判死原话「右半必丢」）；当年为补右半要多占号。
- 当年是**内容定号 + 全局池**（V7 的 256 槽表 → v8+ 的分配器族），池子**没有地契** ⇒ 必撞。

### 归因（判据级）
引擎里「不撞」的形态**已经存在**：**tm3 = 位置定号 + 窗口专属网格（stride 30）**，实测从不撞；
**tm1 = 内容定号 + 全窗口共享 `TB=1` 的 512 槽预取图集** = 撞的源头。
⇒ **不撞的充分必要条件 = 「这块号是这个窗口专属的，且活到本次重画结束」**。我们现在不满足：
池子全局共享、跨窗口、且一半落在引擎预取区里。

### 拿到专属的两条路（都不靠 gdb）
- **(a) 位置定号 + 每窗口画布**：把 tm3 形态推广到 tm0/tm1。容量最优（12px 步进跨字共享
  ≈1.5~2 tile/字；V7 §4.5 也确认 8px 步进 2 tile/字为容量旋钮）。代价 = 改一处重画该行/整窗。
- **(b) 关掉引擎预取**（`tpl[+9] 1→0` = 15-2 三步的步 1），整块按窗口切分给自己。
  代价已实证：引擎自己画的那部分文字（Lv/HP 数字）会空白（P32 证据），须一并接管。

**数字账**：16px 步进下独占区需 ≥ 4×N；N=128 字 ⇒ 512 槽 = 整整一块，已无位置留给引擎自己的
256 日文字形与 tilemap ⇒ **「独占」与「省 tile（12px 跨字共享）」必须同时成立** —— 这就是
16×16 那条路在数学上走不通的原因，也是 v36 的 `[514,768)`=127 槽（仅容 63 字）不够用的原因。
