## v14：找到「按行复位」的真源头 = **InitTextPrinter 钩子对所有 tm 都改归属键**

### 修正 v13 日志里的一条错判
v13 日志把「设置页撞自己」归因于 `v8_alloc_begin` 按 `(win, 模板)` 双键复位。
**这条不成立**：实测设置页只有一个 tm1 窗口（EWRAM `+2E658` / tpl#49），
win 与 tpl 在整屏 7 行之间都没变，双键根本不会复位。
真正让 v12 塌掉的是**引擎自己**：`InitTextPrinter 0x08002C68` 每个字符串都把
`win[0x1B]`（CURSOR_TILE_X）清 0 —— v12「借道引擎槽号」直接继承了这个复位，
所以每行都从槽 0 起，全屏塌成同一批砖。v13 起不再读它，问题源头即消除。

### 本轮新发现（真·残留源头）
`InitTextPrinter_hook_C` → `v8_alloc_begin(win)` 是**无条件**调用的（不分 tm），
而复位条件里 `prev_tpl != cur_tpl`。⇒ 任何 **tm0/tm3 窗口在两行 tm1 之间打印一次**，
归属键就被改成它自己的模板，下一行 tm1 立刻被误判成「换屏」→ 游标复位到 521
→ 全屏每行都从池首领号 → 塌成同一批砖。这是「按行复位」类故障的第二条通路。

### 改动（v14，只动 tile_alloc.c 一个函数）
- `v8_alloc_begin`：**相位复位仍对所有 tm 生效**（tm0 战斗文本起点的 12px 相位
  复位不能丢）；随后 `if (win_u8(win, WIN_TEXTMODE) != 1u) return;` —— 非 tm1
  窗口不参与池会话，游标不受扰动。
- 复位规则统一为**只看模板**（= 换屏信号），不看 win 指针（实测「一行一个字符串、
  win 可能每行不同」，按 win 判会误复位）。`v8_alloc_n` 那处 v13 已是只看模板，未动。

### 池位置的运行时核查（新脚本，比静态分组硬）
- `.tmp/poolcb.py`：静态版，按「同函数一起建窗」分组，按 4bpp=1 块 / 8bpp=2 块
  精确算。三条建窗通路（`0x080027DC` / `0x0806F158` / `0x08002C28`）全扫：
  **只有 `k9/k10 cb3` 命中**（那两个模板从未被调用，且 cb3 时池落 OBJ 区 ⇒ 该层不画）。
  旧 `pool_page3.py` 报的 5 处「B 撞他层字模区」是**假阳性**（它把一层 char 区当
  `0x8000`=两块，对 4bpp/512 砖的层是过近似）。
- `.tmp/poolrt.py`：**运行时**版（模板 charBase × 实机 BGxCNT），40 个有 io 的 dump
  逐个核「我方池所在物理块有没有被别的 BG 层占」：**0 命中**。全部 tm1 层是
  cb2 → 池块 3；领航员 v_nav 是 cb0 → 池块 1，均无人占。8bpp（占两块）也已覆盖。
- 遗留（不擅自加，只记账）：v11 删掉的 `charBase>=3` 守卫未恢复。cb3 层的池会落
  OBJ VRAM。三条通路都证明该情形不存在（k9/k10 从未被调用），故不动。

## ✅ v15：真根因 = **发号不幂等**（用户拍板方向 A：改成幂等发号）

### 决定性证据（我留的诊断环，读出来就是铁证）
```
chs_print 调用总数 = 4247      设置页整屏汉字约 25 个
⇒ 每个字被重画约 170 次        环内最近 14 条全是同一个串 ptr=03007DD0
```
用户补充的关键事实：**「设置页面是自动刷新的，所以现在是疯狂跳文字」**。

### 机理（一句话）
设置页**连续自动重画**；而 v13/v14 的发号是「单调游标 + **只在换模板时**复位」。
自动刷新屏上模板永远不变 ⇒ 游标永不复位 ⇒ 每次重画都去池里领新砖
⇒ `4247×2 ≈ 8500` 次领号穿过 **503 砖**的池 ⇒ **回卷约 17 圈**，
把 map 还指着的砖一圈圈盖掉 ⇒ 文字每帧都变 = **疯狂跳字**。
（旁证：池 `t521..t790` 出现周期 14 的自复制，正是被同一批字形反复回卷写满。）

### 用户的三条判词（记住，别再犯）
- 「**之前 v8 的时候好歹还能显示正常**」——v8 是**按块复位**游标的 ⇒ 重画=原地覆写 ⇒ 幂等。
  我 v13/v14 把复位去掉，等于**把幂等性丢了**。这是最致命的一步。
- 「**来来回回都是测占用带**」——v8~v38 那族是已判死的路；池 `[521,1024)` 的位置**早就定了**，
  不该再测任何占用带。
- v8 代码**已从工作区删除**（`_recover/hook_snap_20260921_1740.tgz` 其实是 **v21**，不是 v8）。

### 设计：行段登记表（幂等发号）
- **行身份 = `InitTextPrinter` 的 (cur_x, cur_y) 入参 + 模板**。
  ⚠ 不能用 `win[0x1C]`：本钩子在 InitTextPrinter **入口**，此刻引擎还没写它。
  entry.s 跳板已把参数重排好：`ldr r4,[sp,#0x28]`（= 0x18+16，cur_y 在后来的 sp 上），
  `r1=tile_base, r2=cur_x, r3=cur_y` ⇒ C 签名 `(win, tile_base, cur_x, cur_y)` 已验证。
- 每个「行」在池内登记一个**段基址**，一经登记**永不变**（sticky）；行首把游标拉回段基址。
  ⇒ 重画序列相同 ⇒ 砖号逐字相同 ⇒ 原地覆写 ⇒ 画面恒定。
  ⇒ **不需要检测"重画的趟边界"**，不需要窗口/字符串模型，不需要任何扫描/账本。
- 段按需增长，**结算点 = 切到下一行时**（把上一行实际用量并进 `pool_top`）。
- 🔴 **永不回卷**：到顶就返回 0（宁缺不砸）。回卷必然盖掉别行的砖，与幂等互斥。
  这也是相对旧版的**行为变更**：旧版到顶会绕回池首复用。

### 改动文件
- `hook/game_addrs.asm`：退役 `ChsPitchCtrl/ChsPitchSlots/V8OursSegs`（自 v5/v8 起零引用），

### 切入点的变化（这是本轮真正的突破）
不再问「哪块砖没人用」（= 已判死的可满足性问题），而是问：
**引擎自己是怎么算出「这一格该显示什么」的？** —— 答案是 `GetCursorTilemapPointer 0x08003708`，
逐指令核对为**纯叶函数**（只读，无副作用）：
```
tpl->tilemap + ((win[0x1C] + win[0x1D]) * 32 + (win[0x1A] + win[0x1B])) * 2
               CURSOR_Y  CURSOR_TILE_Y       CURSOR_X  CURSOR_TILE_X
```
⇒ 把**这个算式的结果**（格序 10bit）当作段键，就等于站进引擎的坐标系：
同一屏幕位置 ⇒ 同一段基址 ⇒ 重画时逐字拿到同一批砖 ⇒ **原地覆写 ⇒ 幂等**。

### 为什么必须在「首字」读键
`InitTextPrinter 0x08002C68` 会清 `win[0x18]/[0x1B]/[0x1D] = 0`，并把 `win[0x1A] = x`。
⇒ 本串**首个字形**到来时 `win[0x1A..0x1D]` 恰好就是本串起始格（还没被任何 UpdateTilemap 推进）。
我们只在那一刻解析一次，随后把「段游标」落地（非 0）⇒ 本串后续字形不再解析。


⇒ 干净解只有两条：**8px 步进**（8px 宽汉字不可读）/ **16px 步进**（一字符独占砖对 `(2k,2k+1)`，

## 16:2x~16:5x 「字体发虚」（领航员 PokéNav）· 取证与定性

### 结论先行（仍待用户拍板，未改任何代码）
**「发虚」最可能 = 我方字形砖落在引擎自己的字形缓存里，被引擎的「预取 worker」周期性覆写。**

### 来源：反编译源码（`_research/pokeruby_text.c` + `tools/pokeruby/src/text.c`、`text_window.c`）
这是本轮最大收获 —— **不用再猜，官方 tile 账本有权威出处**。

1. 🔴 **`win[0x16]` 的真名 = `tileDataStartOffset`**（不是「TILE_BASE」这种全局基址）。
   `InitWindowTileData(win, startOffset)`（JP `0x08002950`）里只有一句 `strh r2,[r3,#0x16]`。
   它是**相对该 BG 的 charBase 的砖号**（与 tilemap 项同一个坐标系）。
2. 🔴 **font 0/3 的字符缓存 = 砖 `[tileDataStartOffset, tileDataStartOffset + 512)`**
   = 256 字形 × 2 砖。逐指令实证（JP `0x08002A50`，字体分派后落到 `0x08002A8C`）：
   ```
   08002A8C: lsls r1, r3, #5     ; startOffset*32
   08002A8E: ldr  r0, [r4, #0xC] ; tpl[0xC] = tileData
   08002A90: adds r0, r0, r1
   08002A92: lsls r1, r6, #6     ; glyph*64
   08002A94: adds r5, r0, r1     ; dest = tileData + 32*so + 64*glyph
   ```
3. 🔴 **`GlyphPrefetchWorker 0x080029E0` 每帧写 16 个字形、连写 16 帧**（计数器
   `*(0x0300032E)` 从 0 加到 `0x100<<8`），全局量 `*(0x03000328)`=模板、`*(0x0300032C)`=startOffset。
   **⇒ 任何窗只被 `0x08002950` 初始化一次之后，引擎在随后 16 帧里把 512 块砖按该 startOffset 灌满日文字形。**
   仅 `textMode == 1` 才预取（tm0/tm2/tm3 直接 return）。
4. **`0x08002950` 的返回值**（跳转表在 `0x080029B4`）：**font 0/3 → 512；font 1/2/4/5 → 256**。
   与 `text_window.c` 的 `InitWindowTileData` 返回值语义一致（= 缓存之后的第一个砖号）。
5. **官方标准窗框**：`TextWindow_SetBaseTileNum(512)`（`text_window.c:101`）⇒
   九宫格 = 砖 **512..520**，并 **返回 521** 当「文本内容偏移」。⇒ 记忆里那句
   「边框 = 512..520」✓ 对；但**推论「我方从 521 起就安全」是错的**（见下）。
6. 🔴 **三色槽在模板、不在窗**（JP `0x08002AAC` / `0x08002ACC` 逐指令）：
   `CopyGlyph1bppTo4bpp(src, dst, fg = tpl[0x05], bg = tpl[0x06])`；
   font4/5 → `ApplyColors_ShadowedFont(src, dst, fg = tpl[0x05], shadow = tpl[0x07], bg = tpl[0x06])`。
   ⇒ **tpl[5]=前景 / tpl[6]=背景 / tpl[7]=阴影**。默认 fg=15 / shadow=14 / bg=0。
   我方 engine.c 用的 `win[0x0C]/[0x0D]` 是**另一套（窗口自带的 tm0/tm2 变量宽路径用）**，
