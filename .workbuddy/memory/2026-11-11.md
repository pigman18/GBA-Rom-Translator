## 结构：小补丁的归属（用户定的原则）

「能进主流程作为算法的进 plan，没办法的进 patches」。已落地：

- `plan["tables"][].insns` / `.literals`：由 plan 函数**算**出来（改 stride 立即数、
  改读点指令、改基址字面量）
- `plan["patches"]`：配置里声明的字节补丁（`texts["patches"]` 或
  `modules[X]["patches"]`），rows_writer 与 insns 走同一条 `.org/.byte` 通道
- 结果：`struct_trampoline.py` 里硬编码的 `0xF22CA` / `0xF22CE` 已撤掉

## 修复的 bug（都有实测证据）

1. **insns 字节序反了**：旧实现写 `bytes="68 61"`，writer 是 `.byte 0x68,0x61`
   → 半字 0x6168 = `str r0,[r5,#0x14]`，不是 `ldr`。上一版「657 条全部写入」
   的读点其实被改坏，只是场景没覆盖。现在由编码函数生成（`61 68`）。
2. **`_find_name_copy_sites`**：literal → 函数 → 精确解码 BL 找 StringCopyN
   → 回溯 `adds rX,rY,#name_off`。**不能拿 `_name_cap` 当长度判据**（它推的是
   名字+填充宽度 16，代码硬编码 5）。
3. **池头保护误伤**：`_packed_scan_pool_heads` 无条件把 range 起点当池头，
   地点名 0x3BECB7 / 道具说明 0x3984DC 自己就是要翻的文本却被拒。
   改为用 `find_ldrs` 验证「真被代码当基址加载」才保护。
4. **扫描器把串切在中间**：`FD xx xx 00 FD xx xx` 里那个 `00`（空格）被当
   串结尾，于是战斗模板 address 偏 6~10 字节 → 永无指针。手工修了 7 条。

## 写入模型归一（结论）
- `rows_writer` 消费 plan 时**不看 `tables[].mode`**，只做三件事：blob→new_base、
  insns 打补丁、literals 改字面量。mode 只是 planner 算补丁的策略名（5 种）。
- 归一一句话：搬（写新区）→ 指（改站点）→ 读（0 补丁 / N 补丁）。
  站点只有 3 形：u32 字面量、表内 u32 指针槽、`base+i*stride` 索引算术。
- **「改步长」只是「patch 一个立即数」的特例**，不必与 patch 并列。
  补丁 4 落点：索引立即数、栈缓冲窗口、字段布局(field_map)、读点改解引用（2B 原地或 8B `ldr+bx` 跳板）。
- 逃逸项 3 个且都非新协议：inplace 4 条（退化为新区=旧区）、
  对战塔 28 条（站点窗口 4<5，连跳板塞不进）、树果名 no_reader（无读端）。
- 待收敛：站点空间不足的两级出口、`read.kind` 显式化、`plan.patches` 与 `tables[].insns` 合流。
- **纠正「放不下」这一伪约束**：ROM 已 32MB，表区 0x1EB0000-0x1F00000=320KB 只用 127KB。
  用户定调：等长（不足补00）/等距（固定N个分隔）/混合（夹代码块，剥离后塌成前两者）
  + 固定写入规则 + 读端补丁。已落 docs/TEXT_WRITE_MODEL.md（提交 9d7c7d1）。
  任何「不行」必须给出「读端常量地址+原值」或「RAM 结构基址+引用处数」两条实数之一。
- 对战塔真因：不是空间，是一直走「ROM 侧扩 stride」，而该表被 memcpy 整条拷进
  RAM 0x0203826C（实测 66 处字面量引用），必然撞 RAM 守恒。正确路线=名槽改 u32 指针。
- **对战塔 28 条解决（name_ptr_fold，提交 c95ae3e）**：名槽 +2 置 FF、+4 存 u32 指针；
  读点 `adds rS,rBase,#2`→`#4`，紧邻 `adds rA,rIdx,rS`→`ldr rA,[rS,rIdx]`，
  两条 2B 原地换、无跳板无窗口问题（地址和 idx*64+base+4 天然 4 对齐，寄存器偏移无 imm5 限制）。
  三处读点 0x080A9B78 / 0x080AE4AE / 0x080AE530，**读的都是 RAM 0x0203826C 不是 ROM 表基址**
  ——按 ROM 基址找函数才会「一个都找不到」。结果 translated 32→60、keep_jp 28→0。
- 打包通过：13 tables / insns=356 / literals=174，全部走 `gen/patch_table.asm` 单通道。
- verify_output_rom.py 的 ROOT 少一层（scripts/misc），已修 parents[2]；仍有 3 项 stale 失败
  （P25 InitWindowTileData、PhraseTable 期望 F9 实际 F7、Small ink 8x8），与本次无关。
- **剩余日文 338→195，unresolved 261→4**（提交 9e0bf16 / a7d190c）：
  ① `no_ref` 分类：整块文本里无任何 u32 指向 → 死文本（サンプル メッセージ等），-114；
  ② `_plan_pool_relocate` 池搬迁（等距布局）：无 00 的 FF 分隔文本池整块重编码，
     按内部偏移映射重写池内所有 u32（sites[].add），22 个池 143 条；
     0x3B2804 池 4351B→4784B、FF 数 977 不变、头指针 0x83B3E68→0x094D6964；
  ③ `allow_latin_heavy`：有指针的全角数字串（わざマシン３２）不再误杀，+14。
- 教训：池搬迁必须排除含 00 的块（定长字段靠 base+固定偏移读，变长会错位）；
  对话 bank 的 0x00 是空格，不能整池搬，只能逐条指针。

    的像素游标语义，再用同一探针验 index 是否变 25。

## 12:40 #9 关键结构：一行是两次 print

用 RAM 串日志（`ix==0` 时记录 tptr + cx/ctx/cy/tm）抓到的真凭实据：

```
07 03007DA4 cx=19 ctx=0 cy=16 tm=1 first=A1   ← 编号串 "003"（IWRAM 缓冲）
08 03007D94 cx=22 ctx=0 cy=16 tm=1 first=AE   ← 名字串（另一缓冲）
```
- 编号与名字是**两个独立 print**，字符串都在 IWRAM（06007D94 / 03007DA4 一带）；
- 名字那次的 `cx`：我们 22、origin 实际落在 23（像素实测 176 vs 184）；
- 编号两侧**逐像素相同**（ink 161/169 两段一模一样）⇒ 编号本身的排版没差；
- 所以差异产生在「编号 print 结束时的游标」，游戏随后拿它当名字的 x。
- 下一枪（还没打）：在编号 print 收到 0xFF 时记 `WIN_CURSOR_TILE_X`（0x1B），
  对比原生是否 4、我们是否 3。若同等，则 x 是游戏常量，得用 GDB 断在名字 print 前抓调用点。

## 12:45 #9 否掉两个假设（都不成立）

- 假设 A「空格不推进」：`GetGlyph(code=0)` 明确 `width=8` 并会推进 ⇒ 不是它；
  且编号串 `a1 a1 a4 ff` = "003" 根本没有空格。
- 假设 B「原生 currentX 是 1 基，EOS 补 +1」：在 0xFF 分支给 0x1B 加 1 后重跑，
  名字仍在 x=176（没动）⇒ 游戏**不读** 0x1B，假设作废，已回退。
- 现在的事实：两次 print（编号 cx=19 / 名字 cx=22，我们）；origin 名字落在 23。
  游戏代码相同 ⇒ x 的来源还有第三个变量，静态推不出来了。
- 下一步只剩动态：GDB 断在名字 print 之前（`AddTextPrinter` 调用点），
  读它算出来的 x 与调用者，看那 1 格是从哪来的。

## 13:45 #9：四个假设全否（记录，别重试）

| 假设 | 结果 |
|---|---|
| 空格不推进 | ✗ `GetGlyph(0)` 明确 width=8；编号串无空格 |
| EOS 给 0x1B +1 | ✗ 画面完全不动 → 游戏不读 cursorX |
| EOS 给 0x1A +1 | ✗ 同上 → 也不读 x |
| 0x1B 改 1 基 + 绘制 -1 | ✗ 名字仍 176，dex fail 19→82（已回退） |

- 本轮仍稳定拿到：编号/名字两次 print（IWRAM 0x03007DA4 / 0x03007D94，cx=19 / 22）；
- 探针直读：游戏给名字 print 的 `0x1A` 就是 22；origin 落在 23；
- 结论：静态到顶，下一步必须 GDB 断在名字 print 前读调用栈。
- 现状：树干净，只有 #8 的 `bg=0` 修复；dex fail=19。

## 14:15 GDB 并入 bot + #9 错位定案（根因是我们自己的常量）

### GDB 并入 bot（用户要求：仓库里主动发起 GDB 的东西一般要并入 bot）

- 新增 `bot/gdbprobe.py`（`ProbeSession`）：复用 `src/util/gdb_patcher.py` 的
  yaml 监听点 / handler / `Ctx`，加上「连 stub → 下断点 → cont 循环 → 落盘」。
- `bot/run.py` 新增 `--gdb <点名[,点名]>` / `--gdb-port` / `--gdb-side`：
  起 mGBA 时自动加 `-g`，探针线程随即连上；命中数与截图同目录
  （`{side}/gdb_probe.log`）。attach 失败会明确报错（否则一侧等于没跑）。
- **坑**：mGBA 的 `-g` 是**无参数开关**，写成 `-g 2345` 会把 `2345` 当 ROM 路径，
  mGBA 直接退出、stub 根本没起来。端口要用 `-C gdb.port=N`。
- **关键增强**：每次命中额外打一行 `栈@0x… 代码地址: +08=… +14=…`（扫栈 128B，
  只挑像 ROM 地址的字）。`InitTextPrinter` 只有一层 LR，而上层
  `AddTextPrinterParameterized` 被 5+ 处调用、LR 恒为 0x08002D14 ——
  区别全在栈上。这一行直接把调用链摊开。
- 探针默认**不去重**（`Ctx(dedup=False)`）：bug 常藏在「连着 N 次相同 print」的第 k 次。

### #9 编号/名字错位 —— 根因

GDB 一次跑出完整链：
`0x080030C5(parameterized 返回) → 0x0806F18F(Menu_PrintText) →
0x0808ADDF(图鉴列表行 0x0808AD44) → 0x0808AA2D → 0x0808AF11`

- 上层 `0x0808AA24` = `movs r1,#0x17` → **x 是硬编码常量 23，不是算出来的**；
- 两侧 ROM 对比：`0808AA00/AA24/AB34/ABDA/ABFE` 全是 `17 21 → 16 21`；
- 来源 `hook/game_addrs.asm: DEX_NAME_COLUMN equ 0x16`（原版 0x17），
  `patches/pokedex.asm` 5 处统一引用。改成 0x16 后名字列与「19+3=22」挤在一起，
  中间那格空隙没了；破折号按右边界补，起点左移一格就多画一个。
- 修：`DEX_NAME_COLUMN equ 0x17`。实测名字墨迹 px176→**184**（=origin），
  破折号 6→5 个（=origin）；options fail 0、bag 246（均与基线一致）。
- 遗留：`dex` fail 19→28，全是 `g_garble` 的「1px 竖条残片」——
  12px 汉字竖直笔画落在 8px tile 边界，被 verify 的 sliver 判据判掉（目视无残影）。
  属验收判据对 12px 字体误报，单独跟进。

### 教训
- 「游戏代码相同却给出不同结果」这类矛盾，先怀疑**我们改过的东西**（常量/补丁/表），
  不要一路怀疑静态分析不成立。这次一个 `equ` 值就是全部答案。
- 之前四轮静态假设全否，是因为一直在猜「宽度/游标/空格」，从没看过
  `DEX_NAME_COLUMN` 这个我们自己定义的符号。

## 15:00 破折号乱码 + 底色错：两个真因（都推翻了 bg=0）

用户反馈「仅解决红块，但滚动时 ---- 变日文乱码，其他页面背景色不对」。

### 真因 1：破折号填充循环被 stride 补丁一起放大（红块 + 乱码都源于此）

- 图鉴列表「无名字」行填 5 个 `0xAE` 占位（0x0808ADC0，`cmp r4,#4` 循环 5 次）。
- 名字表 stride 6→24 时，`write_plan._name_window_patches` 按「cmp+bls=循环上限」
  一刀切，把这条也改成 23 → 占位串撑满整行溢出（「乱码」），
  且越界读到后面 `FC 02` 控制码 → `WIN_COLOR_D` 被改成 2 → **红块真因**。
- 证据：origin 侧 GDB 记录 `C/D/E=1/2/8` **0 次**，我们 32 次；修后降到 2 次。
- 修：识别 `movs rX,#0xAE` + 其后循环体含 `strb rX,[rB,rI]` → 不收进 caps；
  同函数有破折号占位时 `buf[old-1]=FF` 也不放大（那是破折号串终止符）。
- 字节验收：`0808ADD0 04→17`、`0808AD72 41→C1` 不再出现；破折号回到 5 个。

### 真因 2：底色必须取**模板**的 D，不是运行时 `win[0x0D]`

`InitTextPrinter` 把模板 tpl[5]/[6]/[7] 抄进 win[0xC]/[0xD]/[0xE]，之后运行时
会被 `FC 0C` / 红字效果改写。模板是 ROM 常量：
- 图鉴列表 `0x081BB784` 的 D=**0**（透明，露出橙底）
- navigator 提示条 `0x081BB46C` 的 D=**15**（米色）
⇒ `chs_colors()` 改成 `*bg = tpl[6]`。

四个被否掉的方案（都试过、都有截图）：
1. `bg=0` 全局 → navigator 透出点阵（用户说的「背景颜色不对」）
2. `bg=win[0x0D]` → 图鉴列表整片白（D=15）
3. 按 tile 池缓存首值 → 白（池被多窗口复用）
4. tilemap 采样（众数/起点左一格）→ 蓝 / 红（采到高亮行，时序不可靠）

### 验收
dex `pass=20 suspect=104 fail=37`，名字 px184、破折号 5、橙底；
navigator 米色底正常；start_menu 1（基线同）；bag 246（基线同）；
options 53 —— 都是 `g_garble` 竖条/碎片（12px 汉字压 8px tile 边界的判据误报，
目视无残影），要单独收敛 verify 判据。

### 教训
- 「红块」和「乱码」看着是两个问题，其实是**一个**：字符串太长越界读到控制码。
  先修数据（串长），再谈渲染（颜色）。
- 底色这类「窗口属性」，要从**模板**取（不可变），不要从运行时结构体取（会被改）。

## 16:25 火红 12px 实测 + 文本块归属（决定性数据）

### 火红是怎么做的（实测，不是文档转述）

- 取字形 `0x081DB3EE`：4 段 × 32B → 16×16，返回 `width=12 height=13`；
- 挂载方式：**函数指针表** `0x08742148 = 0x081DB3EF`（thumb），没有任何 `bl` 指向它；
- 截图实测（`work/_probe/snap3`）：单字墨宽 **12px**、步进 **13px**、4 字占 x=26..76 = 51px；
- tile 编排（BG0 screenblock 0xF000）：`ty1: tx3=001 ... tx26=018`，**按屏幕列连续编号**，
  `ty2` 紧接 `019..`。与 Ruby 原版 `GetCursorTileNum = TILE_BASE + TILE_OFFSET + 2*xOff + yOff` 同构。

### 关键澄清（推翻我之前的错误前提）

| | 字宽 | 步进 | 每字占列 | 每字 tile |
|---|---|---|---|---|
| 火红 | 12 | 13 | 2 | 4 |
| 我们 | 12 | 12 | 2 | 4 |

**tile 用量完全一样。** 所以「12px 装不下」不成立，「8+4 两趟」也不是 12px 的必然代价。
火红不撞 UI 的原因是**独占 char block**——因为它的字形永远只有屏幕上那几十个，写在自留地。

### 我们的真实情况（GDB 实测 4145 次 InitTextPrinter）

三场景 **所有中文文本窗口的 tileData 全是 `0x06008000`（block2）**：
dex 111 次 / bag 478 次 / options 3556 次，tm=1 fn=3 与 tm=3 fn=3 两种。

- 数据链路：`win[0x00]` = 模板指针 → 模板 `[+0x0C]` = tileData（VRAM 绝对地址）→ block = (addr-0x06000000)>>14
- 模板 `[1]` = charBase 号、`[+0x10]` = tilemap。全 ROM 共 **52 个窗口模板**：
  block0×24 / block2×20 / block1×4 / block3×4

⇒ 结构性障碍不是「空间不够」，是**所有文本窗口共用 block2**，与 BG2 的 UI 图形冲突。
⇒ 换块的正解入口是**改模板的 tileData**（ROM 常量，每个模板只被引用 1 次），
   而不是改 `BG2CNT`（已证否：游戏按绝对地址 0x06008000 解压图形）。

### 工具
- `bot/run.py --gdb InitTextPrinter` 现在会额外输出「文本块归属」汇总
  （tileData / charBlock / tm / fn → 次数），实现在 `gdbprobe._log_textblock()`。
