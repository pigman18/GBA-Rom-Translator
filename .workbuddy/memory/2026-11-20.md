   ⇒ 名字**不从 EWRAM 读**，渲染时直接读 ROM 指针表
   - 汉化 EWRAM F7=98 / 原版=92（差 6 = 那条详情串），结构几乎无差异

3. **原版日文名表 0x203CB8（412×6B）差异 0 字节** ⇒ 存档永远存原版编码

4. **新增 412 项指针表 0x0871BFB0**（原版全 FF）

5. **只换一个 bl**：`0x08053376  bl StringCopy` → `bl 0x0810935E`
   → `bx 0x087C04DD` → 扫描器 `0x087C04F6`（返回 3/10/17 裁剪档）

6. **9 处 0x203CB8 引用换成新代码**（0x08FFD535×7, D539×1, CF01×1）
   - 新代码用 `0xAAAB` 魔数反解 idx = species/6，查指针表

## 09:50 遇敌崩溃事故 + 回滚（重要教训）

**事故**：照火红思路改 `0x08042430` 为「取 species 再查新表」，遇敌崩溃
`mGBA: Jumped to invalid address: E3A02004`（= ARM 指令编码 mov r2,#4，跑进数据区）。

**根因**：`0x08039F24` 不是轻量取字段函数，而是 **substruct 全解密器**
（`0x08039FB4 → bl 0x8039FC0`，`0x08039FC0` 会把 field 0..11+ 全解一遍）。
我在 hook 里 `sub sp,#16` 给的局部缓冲太小 → 解密越界写坏栈帧 → 返回地址被毁。

**关键教训**
1. `0x08039F24` 是重函数，不能在栈上随便给 16B 缓冲
2. 崩溃地址形如 `E3A02004` 是 ARM 指令编码 → 说明执行流跑进数据区
3. 改 hook 前必须确认原调用点的**完整寄存器约定**，不能只看 `r1=11` 就照抄

**正确方向**：不要自己调 `GetMonData(mon,11)`。`0x08042408` 在 `0x08042460`
**已经**调过一次并拿到 species，hook 点应在 `0x08042464` 之后复用那个值。

## 10:10 火红方案移植：数据层打通，但撞 UI 布局墙

**上一轮崩溃的真根因（不是栈太小）**：`ldr r3, =0x08039F24` 少写 `|1`，
`bx` 到偶数地址让 CPU 切 ARM 模式 → 把 Thumb 字节当 ARM 指令 → 跳飞。
**铁律：所有 `ldr r3, =0x08xxxxxx` 必须 `|1`。**

**第二个坑**：`0x0803B11C` 硬编码 `cmp r1,#10`（最多 11 字节），
第 12 字节被强写 FF → 3 汉字名的第 3 字丢失。
3 个调用者共享（0x08037D06 队伍 / 0x0803FC68 / 0x0811CA60），
不能直接放宽（队伍路径 dst 后紧跟 nickname[10]）。
**解法：hook 里自实现拷贝**（表基址 + species*24，逐字节到 FF）。

**数据层已完全打通（GDB 实证）**
- `NickHookMid` @0x08800066：species 282 → `f7 00 05 7d f7 00 0e cf f7 00 05 91 ff`（火焰鸡 3 字完整）
- `NickAfterCopy` @0x08042444：目标 `0x0202362C` = `fc 02 02 | 火焰鸡(完整) | ff`

**但画面坏了**：血条里只剩一个「级」字，`Lv:24` 被推走。
原因：`0x08042452` 之后的排版（血条/Lv/HP 定位）依赖固定布局，
名字从 5B 变 13B 后基准没跟着变 → 全错位。

**结论**：火红能这么做是因为它整个 UI 按字符格排版（11×11、步进 13）。
红宝石血条按固定 5 字节槽设计，塞 13 字节必然撞坏后续元素。

**三条路**：A 缩短译文(2字仅12%，不可行) / B 改排版基准(工作量大) /
C 只扩名字区(中等) / D 维持现状2字(零风险)。

**已回滚**：game.bin 9568B、0x08042430/0x08042436 均原版、127 帧正常。

**保留资产**：两级跳模板、0x081B504C 空洞、NickFullName_entry.s（数据层已验证正确）、
SpeciesDump / NickHookMid / NickAfterCopy 三个探针。

## 11:00 遭遇对话框名字修复完成（P12）★ 正解

**最终方案**：只替换 **`0x0811C776`** 一条 bl（对战文本渲染器的名字汇合点）。

**正确架构（静态反汇编定案）**
- `0x0811BE94` = 对战文本框渲染器主函数
- `0x0811BEB6` `cmp r1,#0xFD` → `0x0811BEC4` 读 FD 参数 → `0x0811BED6 mov pc,r0`
- **FD 参数跳表基址 `0x0811BEDC`**；`FD 03` → `0x0811BFE4`
- `0x0811BFE4` 用 **`0x030044F0`（敌方槽基址）** 算 mon
- **所有 param 分支汇合到 `0x0811C772`**：`movs r1,#2` / `mov r2,sp` / `bl 0x08039F24`
- 之后 `0x0811C7B0` StringCopyN → `0x0811C84A` 无上限拷贝

**之前三次尝试全错**
| 挂载点 | 错因 |
|---|---|
| `0x08042430` | 血条路径，不是遭遇 |
| `0x0803A1AC` | 这是 GetMonData 的 **field 2 处理器**，不是占位符展开 |
| `0x0811C7AA` | 只是某个 param 分支，只覆盖我方（所以只看到 species 282） |

**实现**：`NickSlot_entry.s`，species→新表 0x1EB0AF4(+idx*24)→逐字节到 FF→写 dst。
范围检查 1..411，越界退回 `GetMonData(mon,2,dst)`。
挂载 `0x0811C776` → `bl 0x081B504C`（1.5MB）→ `ldr/bx 0x0880003C`。

**实测**：「啊！野生的**长翅鸥**跳出来了！」3 字完整 ✅
battle_dialog 314 帧、battle_full 127 帧均正常，无崩溃。

**保留**：`0x4294`=0d24（5→13）；血条 `0x08042430` 原版；`0x0811C77A` 原版 e018。

**铁律补充**
- `GetMonData(mon,11)` 局部缓冲必须 ≥32B（8B 会返回异常值）
- r9 是高寄存器，要先 `mov r4,r9` 再 `ldrb`
- 所有 `ldr r3,=0x08xxxxxx` 必须 `|1`
- 判断敌我：`0x03004290` 我方 / `0x030044F0` 敌方（差 0x260）
