## 火红汉化调研：名字「显示汉化 + 串档不乱」的唯一正解

样本 `roms/translated/宝可梦火红日版汉化2.2.gba`，对照日版 BPRJ 逐字节 diff。

**核心手法：改指针，不改原表。**
日版 `0x16F744` 的值 `0x0816F9FB`（原有日文表）被汉化改成 `0x086D0000`
（`0x6D0000` 起新增的中文文本区，日版该处全是 FF）。原表一个字节没动。
中文编码同样是 `F7 00 hi lo`。

配套：
- 变长字符串长度函数换掉了（`0x1DB554/55C/564` 三个跳板 → `0x7C0001` 等），
  遇 `F7` 走 12B、日文走 10B。火红原版只认日文，所以必须换。
- 字体走函数指针表挂载：`0x742148` 处 `FFFFFFFF` → `0x081DB3EF`。

⇒ **显示与存档彻底解耦，存档字段永远是原版编码**，所以串档不乱。

SLT2 已确认不可取（`f33208f` 提交记录）：短语表 + 运行时递归查表 + 5B 退路，
复杂度高，已统一到 `F7 00 hi lo`。用户的「不太优化」判断成立。

**根因（不是栈/寄存器/地址问题）**
只要中文 F7 串真正进入 0x0806B288 这条渲染路径就必停摆（fr=9240，复现 4 次）。
源码 text.c:2040 `while (win->state != WIN_STATE_END)`，state 只在读到 EOS(0xFF)
才置 END；而这条路径按**固定 0x200 字节** CpuFastCopy 到 OBJ_VRAM1，
中文（4B/字）与日文（1B/字）的布局差异让 state 到不了 END。

**决定性反证**：把 `bl PartyName_LookupJp` 换成 `movs r0,#0`（永不命中）
→ 帧 3/14/19 全部 38316 完全正常；加回真实查表 → 必停摆。
这一条排除了所有其他因素，是这轮最有价值的结论。

**四个工具陷阱（都踩过，代价很大）**
- A `bl C函数符号名` 会跳到函数中间：PartyName_LookupJp 跳到 0x088014D4，
  真实起点 0x088014D0（跳过 push 和 cmp）→ 必须用 ldr r3,=<显式地址|1>+bx
- B 在 0x0806B2E4 下 GDB 断点会误报 LR=0x0806B376、r2=长度值（断点没设上）；
  必须断在 0x0806B288 才看到真实参数 r2=0x03007DC8
- C **mGBA 开着时产物写不进去，meowth 静默输出到 *_new.gba**，
  后续验证全跑旧文件 —— 浪费了好几轮。打包前必须 taskkill mGBA
- D build.bat 失败只打印 `Error:`（含空格），grep "error" 会漏掉
  → 用 grep -iE "error|Build OK" 并核对 Size 变化
