## 美版汉化的 `:` 与数字：确认是原生字库，未挂载其他字库

### 基线确认（关键，避免再认错）

`work/_us_cn.gba` 虽卡带代号写成 `AXVJ`，但**实际基于美版 Ruby 1.1 (AXVE)**：
- 与日版 AXVJ00 前 8MB 相似度仅 **4.31%**
- 与美版 1.1 相似度 **95.16%**
- 定版依据（1.1 vs 1.2 仅差 4 字节）：`0xBC=02`、`0x919B=DB`、`0x91BF=DA` 全与 1.1 一致

### 美版字体表（实测，权威）

`GetGlyphTilePointers` 美版 = `0x08003A1C`（签名 `r0=fontNum, r1=language, r2=glyph, r3=&upper`）
字体表基址 = **`0x081E6B48`**，条目 12B：`{u32 type, u32 dataPtr, u16 bytesPerGlyph, u16 maxGlyph}`

| 槽 | type | dataPtr | B/glyph | maxGlyph |
|---|---|---|---|---|
| 0 | 0 | `0x081E4208` | 16 | 8 |
| 1 | 1 | `0x081E5108` | 8 | 0 |
| 2 | 2 | `0x081E5108` | 8 | 0 |
| 3 | 4 | `0x08EA8744` | 64 | 512 |
| 4 | 1 | `0x08EAC6C4` | 32 | 0 |
| 5 | 2 | `0x08EAC6C4` | 32 | 0 |
| 6 | 3 | `0x081E5908` | 8 | 0 |
| 7 | 0 | `0x081E2A08` | 16 | 8 |

**汉化版这张表与美版逐字节完全相同。**

### 字形数据对比结果

| 槽 | 数据区大小 | 与美版差异 |
|---|---|---|
| 0 | 144 B | **0** |
| 1 | 16 KB | 6 B（`0x81E79C8/0x81E79F8`，函数指针补丁，非字形） |
| 2 | 16 KB | 同上 6 B |
| 3 | 32 KB | **0** |
| 4 | 16 KB | **0** |

| 7 | 144 B | **0** |

**结论：汉化版完全没有改动任何字形数据。数字 `:` 用的就是美版原生字库。**

### 汉化版真正做了什么

1. 换文本：英文文本表替换成中文编码（例 `0x08170000` 处 `ad ff` 后英文变中文）
2. 新增 16MB（ROM 16MB → 32MB），其中约 580KB 有内容，落在 `0x09000000` 区
   （55 段、每段约 31KB、间隔 `0x8000`）
3. 打函数指针补丁（`0x081E79xx` 6 字节）

### 美版原版字库区（零改动，可直接参考）

- `0xC00000..0xD00001`（1MB）：差异 0
- `0xEAE241..0x1000000`（1.35MB）：差异 0

### 教训

**判断"某功能是不是原生字库"→ 先定位字体表 → 逐槽对比字形数据区差异。
不要靠搜索字形图案（效率极低）或看渲染截图（采样易失真）。**

## 美版数字字形 → 日版血条（已完成，一比一替换 + 按日版规则重排）

### 两版字形结构差异（反汇编 + GDB 出口探针实测）

| | 日版 AXVJ | 美版 AXVE |
|---|---|---|
| 结构 | **8x8 单 tile** | **8x16 双 tile**（up + lo） |
| 字形尺寸 | row1-7（7 行高）、x0-x7（8px 满宽） | row2-10（9 行高）、x1-x3（3px 窄）+ 右侧阴影 |
| 取址 | `0x081B51AC + FontType1Map[glyph*4+1]*32` | `up`/`lo` 各 32B，`lo = up + 0x20` |

**关键：直接搬会变成贴着格子左边的细窄字（像 "k"）—— 必须按日版规则重排。**

### 日版取址路径（GDB 环形记录实测，win=0x020231CC）

- `win[0x0B]`（`WIN_FONTNUM_REAL`）= **4**，走 fn=4 分支 `0x080037D0`
  - 之前误取 `win[+8]=0`，导致白改 `0x081B3AAC`，务必记牢
- `FontType1Map = 0x081B34A8`，`idx_lo = byte[MAP + glyph*4 + 1]`
- `*lower = 0x081B51AC + idx_lo*32`；`up` 恒为 `0x081B6C2C`（全 0）
- 数字槽：`0xA1→0x081B606C`，步长 `0x20`，至 `0xAA→0x081B618C`；冒号 `0xF0→0x081B6C4C`

### 美版取址路径（GDB 出口探针 0x08003AC4 实测）

- 美版函数 `GetGlyphTilePointers @0x08003A1C`（日版是 `0x08003730`）
- 签名：`r0=fontNum, r1=language, r2=glyph, r3=&upper, [sp+16]=&lower`
- **按 type 分派**（不是 fontNum），表 `0x081E6B48`，条目 12B `{type,dataPtr,bpg,maxGlyph}`
- 血条走 idx11（fn4/lang2，type=1，data=`0x08EA6BC4`，bpg=32）
- 但**实际字形地址是运行时算的**，实测：`0xA1→up=0x08EA5484`，步长 `0x40`，`lo=up+0x20`

### 转换规则（scripts/font/gen_font_origin.py）

1. 取美版 up+lo 拼成 8x16 nibble 网格
2. 求墨迹包围盒（含阴影 nibble=14）
3. **垂直压到 7 行 + 水平居中铺满 8px**（最近邻采样）
4. 落到日版 row1-7，打包成 32B

### 验证结果

- 产物 10 个数字槽（0xA1-0xAA）全部替换，冒号 0xF0 按设计保留日版
- bot 回放：`Lv:30` 完整可读，数字已是美版细笔画风格

### 坑（已踩，勿重走）

- hook 里 `win[+8]` ≠ `WIN_FONTNUM_REAL`，后者是 **`win[0x0B]`**
- 改 C 代码后**必须手动跑 `hook/build.bat`**，`meowth full` 不会重编 C
- 探针在函数**入口**读 `*upper` 拿到的是调用方栈垃圾，要断**出口** `0x08003AC4`
- `patch` 的 `.asm` 里**不能写 `.open/.gba/.close`**（ROM 由 main.asm 统一打开）

## 美版汉化版 small 字库导出（已完成导出，卡在字符映射）

### 字库位置（反汇编 + GDB + 实测）

汉化版 `work/_us_cn.gba` 中文字库注入在扩展区：
- **基址 `0x090AF220`**，每字 **128B**（4 个 8x8 tile），共 8411 槽
- 非空范围到 `0x091B5F9C`
- 取字模代码 `0x090000CC`：`lsls r0,r0,#5` → `*upper = base + glyph*32`，
  `+32` 取 `*lower`

### 两套字库连续存放（按字形墨迹高度分段，二分确认）

| idx 区间 | 墨迹行 | 高度 | 类型 |
|---|---|---|---|
| 0..1404 | row2..row12 | 11 行 | **Normal 大字** |
| 1405.. | row6..row14 | 9 行 | **Small 小字** |

### 128B 槽内排布（实测墨量）

```
tile0 = 11 ink  ← 字形上半 8x8
tile1 = 34 ink  ← 字形下半 8x8
tile2 =  1 ink  ← 几乎空
tile3 =  0 ink  ← 空
```
⇒ 有效字形 = **tile0 + tile1 纵向拼成 8x16**，tile2/3 是填充。
nibble：0=背景 14=阴影 15=主墨，lo nibble 是左像素。

### 脚本（按用户要求放 scripts 下按功能分目录）

- `scripts/font/export/export_us_cn_small_bdf.py` → 导 BDF
- `scripts/font/export/map_us_cn_to_unicode.py` → 映射反推（未成功）

### BDF 格式坑（用户用 BdfEditor 打不开，已修）

三处都必须对：
1. **XLFD 必须严格 15 字段**，字段名内部不能再有 `-`
   （写成 `US-CN-Small-8x16` 会撑成 18 字段 → 直接打不开）
2. **ENCODING 必须 ≤ 0xFFFF**。原来 `0xE000+idx`，idx 到 8410 会算出 0x10xxx，
   210 个越界。改为从 `0xE100` 起顺序编号，真实 idx 记 COMMENT
3. **STARTPROPERTIES 区不能放 COMMENT**（BdfEditor/bdflib 判错）

验证：`bdflib` 严格解析通过 `OK: 6763 glyphs`。
BDF 与 ROM 逐字节一致（idx 1405 已校验）。

### 卡点：idx → Unicode 映射

- **指纹匹配走不通**：我们 `small.bdf` 是 Unifont 降采样（9x9 宽），
  汉化版是原生精细字模（8px 宽），两边字形设计完全不同，匹配数 0。
- **ROM 里找不到 `F7 00 ll tt` 文本**：GDB 抓到的名字串
  `fc 02 02 f7 00 05 7d ...`（多=1405 刺=3791 菊=1425）在 ROM 和 RAM
  里都搜不到原始字节；全 ROM 扫到的 234 处 `F7 00+合理idx` 上下文都是
  指令/指针表，不是文本。
- 汉化版没有随 ROM 提供码表文件。

**结论：映射需要人工标注或从别处获取。当前 BDF 只能保证「字形与 ROM 一致」，
无法自动知道每个 idx 是哪个汉字。**

## ★★★ 真正的根因链（2026-11-25 深夜定位）★★★

### 一、字库基址定死：0x090DB0A0（不是 0x090AF220）

**权威依据**：Wokann 补丁的 `pokeRS/graphic/fonts/PokeRSFontChsSmall(0xE0000).bin`
（917504B = 7168 字 x 128B），在汉化版 ROM 里 find 其前 64B → 命中 `0x090DB0A0`。

**之前 0x090AF220 是「用 index 反推」猜的，偏 0xBE80 = 200 个字。**
「火焰鸡」在那个错误基址下能对上纯属巧合，导致后续一路错。

### 二、nibble 顺序：左像素在**高** 4 位

```
正确: v = (x%2==0) ? (b>>4) : (b&0xF)
错误: v = (x%2==0) ? (b&0xF) : (b>>4)   ← 我一开始写反了
```
写反 = 每个字节左右像素对调 = 8px 汉字整体镜像错位
（实测现象："巨" 画成 "发"、"多刺菊石兽" 画成 "帽粒盗贼袋"）。
与管线 `pack_slot16_4bpp(lo_first=False)`（默认 hi-first）一致。

### 三、**不需要 TBL 码表**（之前绕了大弯路）

官方 bin 本身就是**按本项目同一套槽位号**排的：
charmap `078E=巨` 经 glyph_index → 槽 1422，bin 第 1422 块解出来正是「巨」。
**所以直接用槽位号取字即可**。之前拿 TBL 的 key（字符编码）当槽位地址，
纯属多余且有害。`load_tbl()` 已从主路径移除。

### 四、字形尺寸：row6..row15，**10 行高**

实测 6630/6763 字墨迹落在 row6..15（10 行），宽 8px 满宽。
原配置 `ink=9x9` 会把最后一行裁掉 → 缺底横。
**已改 `ink=8x10` / `pad_top=6`，advance 保持 10 不动（已验收规格）。**

### 五、生成链路已验证到字节级

- BDF 里「巨/火/宝/多/刺/菊/石/兽」字形全部正确

## ★★★ 最终定案：nibble 顺序 lo-first（这是字形错的真正根因）★★★

### 一句话结论

**官方 bin 用 lo-first（左像素在低 4 位），hook 也按 lo-first 读。
`us_cn_glyph` 提取时必须用 lo-first，不能改成 hi-first。**

### 三方证据（全部实测/源码级）

1. **汉化版官方源码** `DrawGlyphTilesChinese.s`：
```
loadfontglyph:
    lsl r1, r1, 7        ; slot * 128  ← 每字 128B
    add r0, r0, r1       ; 地址 = 字库基址 + slot*128
    mov r0, 8            ; 宽度 8px
    add r0, 0x20         ; 下半格 +32B
    add r0, 8            ; cursorX += 8  步进 8px
```
2. **hook 的 `grid_glyph_px`**：`(x & 1) ? (b >> 4) : (b & 0xF)` = lo-first
3. **管线 `pack_slot16_4bpp(lo_first=True)`**：`left | (right << 4)`

### 反证（关键判别法）

官方 bin 的「巨」BL 首字节 = `f0`：
- 按 **lo-first** 解 → `[背景, 墨, 墨, ...]` 墨从第 2 列起、阴影紧贴其右 → **正确的「巨」**
- 按 **hi-first** 解 → `[墨, 背景, ...]` 阴影与墨隔一格 → **错**

我曾误改成 hi-first，写出的字节变成 `0f`（两半字节对调），
ROM 里字形整体左移 1px，屏幕「巨沼怪」看着就成了「巨作馆」。

### 验证结果：逐像素对比通过

「沼」「怪」两字 **10/10 行与官方 bin 完全一致**（OK）。
「巨」仅差 1px 左移 —— 原因是 `bdf_to_ink` 会把墨迹 bbox 左对齐，
而「巨」的笔形天然带 1px 左边距（实测 14 个抽样字里只有「巨」最左墨列=1，
其余全是 0）。属单字笔形特性，非系统性问题。

**美版 sFonts 表位置：0x081E6B48（日文）/ 0x081E6B9C（拉丁）。汉化版未改此表。**

### 二、汉化版真正的绘制入口（反汇编实证）

`0x08006874`（美版 DrawGlyphTiles 入口，原本是 `f0 b5`）
在汉化版被替换成跳板 → `bx 0x0900004D` → `0x0900004C`

反汇编要点：
```
9000060: cmp r1,#1       ; glyph >= 1
9000064: cmp r1,#30      ; glyph <= 30
9000068: cmp r1,#6       ; 排除 6
900006c: cmp r1,#27      ; 排除 27
9000070: ldrb r6,[r0,#2] ; language
9000072: cmp r6,#2       ; == LANGUAGE_CHINESE
9000094: lsls r1,r1,#8   ; lead_adjust << 8
9000096: adds r1,r1,r0   ; + trail = slot
900009a: cmp r3,#4       ; fontNum==4 → small
900009e: ldr r0,[pc,#240]; 否则 normal
90000a4: lsls r1,r1,#7   ; slot << 7 = slot*128  ★每字128B
90000bc: movs r0,#8 / strb r0,[r1,#2]   ; width 硬编码 8
9000126: adds r0,#8 / strb r0,[r6,#16]  ; cursorX += 8  ★步进8
```

字库基址常量（0x09000190/0x09000194）：
- `0x09000194 -> 0x090DB0A0` = **Small 库**（我用的基址，正确）
- `0x09000190 -> 0x090001A0` = Normal 库

### 三、GDB 实测（新增探针 GlyphPtrCN @0x0900004C）

```

```
汉字（glyph 小值 0x03~0x10）width=4；日文字符（0xA2/0xA4）width=5~6。

### 四、★ 真正的观感差异根因：14/15 双色被压成单色 ★

| | 官方 bin | 我们的 BDF 管线 |
|---|---|---|
| 像素值 | 15 主墨 + **14 阴影** | 只有 15（`shadow:false`） |
| 阴影来源 | 字库自带，精确 1:1 | hook 程序化补右下 1px |
| 主墨:阴影 | 115:114 ≈ **1:1** | 全靠运行时补 |

**BDF 是 1bpp，物理上无法同时表达 15 和 14 两种颜色**，所以走 BDF 必然丢一层。
实测：官方「巨」是 `.#++++++`（主墨+浅阴影，层次分明），
我们的是 `.#......`（只有主墨），
而合并 15+14 会变成 `.#######`（全糊）。

### 五、把官方 bin 直嵌进 ROM 的实测（失败，但暴露了最后一个 bug）

直接把 `FontChsSmall.bin` 覆盖到 `0x09100000` 后跑，**字形糊成白块**。

原因（hook 代码，`PrintNextChar_hook.c` L1383/L1392）：
```c
if (grid_glyph_px(g, sx, ty))            // ← 非 0 就算墨
    grid_pair_set(p, dx & 7u, ty, fg);   // ← 14(阴影) 也被画成 fg 主墨色
```
**hook 不区分 14 和 15，任何非 0 值都当主墨画** ⇒ 官方 bin 的阴影层被当主墨，
主墨与阴影叠成一片。

### 六、待决定（需用户确认，属渲染层改动）

要让官方 bin 生效，必须改 hook 两处 L1383/L1392：
```c
uint8_t v = grid_glyph_px(g, sx, ty);
if (!v) continue;
grid_pair_set(p, dx & 7u, ty, (v == 15) ? fg : sh);   // 15→主墨, 14→阴影
```

**0x22 = 血条框装饰底色；0x23/0x21 = 低半字节 3/1（窗口背景色索引）。**
**没有一个是 0x2F / 0xF2 这类「装饰色 + 主墨15」的组合。**

⇒ **p1 里完全没有字形数据。主墨循环根本没往 p1 写。**

### 已排除
- `ncols=2`：`ink_w=9`、`adv=10` 的宏值已用 gcc -E 验证，公式 `(0+9+7)>>3=2`
- `p1[28]` 计算：离线按 grid_draw_chs 真实逻辑模拟，`p1[28]=0x0F` 正确
- 合并循环起点：反汇编 `880099a: adds r3,#88`，88=64+24，覆盖 offset 24..63
- 合并覆盖逻辑：`if (lo != 0u)` 会写入；但源数据本身就是 0

## A 路线（像素连续落址）进展 — 2026-11-26 10:30

### 已实现
`width_px` / `width_tokens` / `adv_px` 沿调用链传入 `grid_emit`。
buffered 分支的指针推进量从死写 `+64` 改成跟随实际像素宽：
```c
step = ((width_px + adv_px) >> 3) - (width_px >> 3)
win[0x20] = addr + 64 * step
```
adv=10 时：width 0→10 推 1 单元；20→30 推 1；**30→40 推 2**（跳过单元 4）。

### 效果（负电拍拍 species=314 双侧固定）
**前 3 字与 origin 逐像素完全一致**（x20..x48 全等）。
小火龙 3 字名 270/270 100%，无回归。

### ⚠ 关键教训：修正只能做一处
试过「addr 修正 + 推进量修正」同时做 → 双重补偿，第 5 字跳到单元 6、
单元 4 全空、第 3 字之后全乱（只有 2 个字）。
**只修推进量**才对：addr 自然等于「上字 addr + 上字实际占的单元数」。
