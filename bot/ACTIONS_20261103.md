## 1. `burst` — 多帧连续采集

**问题**：旧场景基本只截 1-2 帧。单帧只能证明「某个定型帧长这样」，
证明不了**过程连续**：转场有没有错位、逐字打印有没有覆盖、菜单高亮过渡有没有残影，
这些都必须看连续帧。

**用法**：

```lua
api.burst("bt_menu", 20, 8)   -- 前缀、张数、每张间隔帧数
```

落盘名 `bt_menu_01.png … bt_menu_20.png`，进 index.csv 时按序号递增。

**为什么只出 PNG（不出 vram/ram 五件套）**：
全量 dump 每帧约 385KB（vram 96K + ram 288K + pal/io/oam），
连续 20 帧就是 7.7MB。burst 的用途是看画面演进，不是逐帧做 tile 级分析。
需要 dump 的关键帧仍旧单用 `shot`。

**实测收益**：

| 场景 | 改前 | 改后 |
|---|---|---|
| `pokemon_menu` | 17 帧 | **95 帧** |
| `bag` | 24 帧 | **144 帧** |
| `dialogue` | ~8 帧 | **87 帧** |
| `battle_full`（新增） | — | **127 帧** |

## 2. `poke` — 金手指（写实时内存）

**问题**：有些场景在现有 4 份存档里到不了（战斗/大赛/道馆），
而**换地图靠改存档是不成立的**（见 §4 实测）。

**用法**：

```lua
api.poke{ { addr = 0x03004818, width = 4, value = 0x0000AAAA, note = "钉 RNG" } }
api.poke{ { sb1 = 0x00, width = 2, value = 68, note = "pos.x" } }   -- SaveBlock1 内偏移
```

- `addr`：绝对地址；`sb1`：SaveBlock1 内偏移（推荐，跟着存档走，由 prove 定位）
- `width`：1 / 2 / 4，写后**自动复核读回值**，不一致立刻失败

### ⚠⚠ 顺序铁律（用户口径）

> 「最好是先加载 .sav 后再用金手指，否则我怕类似跟即时缓存一样
> 不会加载实时 ROM 导致汉化看不出效果。」

这条约束做成了**三道门槛**：

| # | 位置 | 条件 | 后果 |
|---|---|---|---|
| 1 | `_lib.poke()`（准备期） | 此前必须有 `prove` 步骤 | 顺序写错，**开跑前**就 assert 失败 |
| 2 | `bot.lua do_poke()`（运行时） | `SB2_RUNTIME ~= nil` | 即「存档身份字节已在 EWRAM 命中」 |
| 3 | `bot.lua do_poke()`（运行时） | `DISPCNT ∉ {0x1741, 0x3140}` | 还在标题/继续游戏菜单就拒绝 |

**为什么门槛 3 必须存在**：Gen3 在**标题画面**就已经把存档读进内存
（用于画「继续游戏」摘要），所以只看 `SB2_RUNTIME` 拦不住「还在标题就写内存」。
写早了改的是尚未被存档初始化的 EWRAM，读档时会被整个覆盖 ——
表现成「按了没反应」，更糟会写坏别的结构，让人误判成汉化有问题。

## 3. `hunt` — 遇敌搜捕

**问题**：野外遇敌是 RNG，而两侧文本打印耗时不同 ⇒ 按键落在不同帧
⇒ 遇敌判定分岔。历史上这直接把对照废掉过。

**做法**：逐格走，每帧看 `DISPCNT` 是否离开野外值 `0x7F60`；
一离开立刻停手并 `advance`，后面的采集**从战斗画面开始**。

```lua
api.hunt{ dir = "DOWN", x = 68, y = 7, steps = 40, timeout = 120 }
```

- 撞墙/走出草丛会自动**掉头**（实测只朝一个方向走 30 格全程不遇敌）
- 走满还没遇到会记 `[HUNT] gave-up`，由后续 `await` 判定是否真的进战斗

**确定性遇敌的最终配方**（实测 6 轮定下来，勿再改）：

```
prove → poke 钉 gRngValue(0x03004818) → hunt → await{any_of={0x0000,0xBF40}}
```

| 试过 | 结果 |
|---|---|
| 只钉 RNG（逐格递增） | 两侧遇敌格差 1（origin 第7格 / translated 第6格） |
| 只 hunt | translated 侧 30 格没遇到，纯随机 |
| **钉一次 RNG + hunt** | **两侧都在第 5 格（另一次第 7 格）遇敌，完全一致** ✅ |

> 为什么「差 1 格」治不掉：实测两侧写入的 RNG 值序列**逐值相同**、
> 走位坐标**逐格相同**，说明还有与帧号相关的判定参与遇敌。
> `hunt` 把这 1 格差异吸收在内部，保证后面从同一画面对齐。

## 4. 这些路试过但**不成立**（省下一轮）

| 尝试 | 结果 |
|---|---|
| 改 .sav 的 `location` 换地图 | **无效**。改完 prove 读到 `loc=10:7` 与真商店存档一模一样，画面仍是 Route118 且主角消失。原因：SaveBlock1 `+0x34` 起还有 226+ 字节「当前地图运行时数据」，地图是读档流程加载的，不是 `location` 一个字段驱动 |
| 把 `continueGameWarp` 一起改 | **更糟**：读档直接失效（那是读档落点） |
| `gWildEncountersDisabled` / `sWildEncounterImmunitySteps` | **无效**，游戏每帧重算，poke 进去立刻被覆盖 |
| 调 ROM 函数（如 `SweetScentWildEncounter`） | **做不到**。mGBA 的 Lua 绑定只有 `read8/16/32`、`readRange`、`write8/16/32`，**没有函数调用接口**；跳板改 PC 无法安全接管 |
| 改 `gWildMonHeaders` 遇敌率表 | **放弃**。实测它不是简单 (mapGroup,mapNum) 索引表：28 字节表项混着地形行为表（`0xA1A8..0xA6A2`）和指向别处的指针，结构未定死，改 ROM 有污染产物风险 |
| 网传瞬移码 `02031F84` / `020322E4` | **无效**。两个地址在 AXVJ 里都落在 **`gPokemonStorage` 内部**（`0x020300A0..0x02038470`）= PC 箱子数据，不是 warp 变量。实测能写入且值保住，穿门后地图不变。那套码是美版/绿宝石的 |

## 4.45 ★★★ 精确跳图：已跑通的方案（本轮最重要成果）

### 实测结果

```
[WARP] start f=4698 from=(23,17) map=0:2 → target map=0:33 (68,7) mon=1
[WARP] set lastHealLocation f=4699 -> 0:33 (68,7)
[WARP] hit f=5475 map=0:33 grid=(68,7) target=0:33 (68,7) OK 完全命中
```

从 Mauville City `(23,17)` 一步传到 Route118 `(68,7)`，**坐标一字不差**，
画面是 Route118 的草丛与岩壁，与原始存档起点完全相同。

### 原理（源码依据 `pret/pokeruby` `src/overworld.c`）

```c
static void ApplyCurrentWarp(void) {
    gLastUsedWarp = gSaveBlock1.location;
    gSaveBlock1.location = gWarpDestination;   // location 被覆盖
}
void WarpIntoMap(void) { ApplyCurrentWarp(); LoadCurrentMapData(); SetPlayerCoordsFromWarp(); }
```

- `WarpIntoMap()` 全文件**只有三处**调用：`DoWhiteOut()`、传送术、秘密基地。
- 白屏与传送术都会先 `Overworld_SetWarpDestToLastHealLoc()`
  ⇒ `gWarpDestination = gSaveBlock1.lastHealLocation`。
- **`lastHealLocation` 在 `SaveBlock1+0x1C`，可以直接写，且实测能保住。**

⇒ 写 `lastHealLocation` → 让游戏自己走传送流程 → 精确落点。

### 权威结构（`include/global.h`）—— 别再猜偏移

```c
struct WarpData {
    s8  mapGroup;   // +0
    s8  mapNum;     // +1
    s8  warpId;     // +2
    s16 x, y;       // +4(x)  +6(y)      ← s16 对齐，不是 +5！
};
struct SaveBlock1 {
    /*0x00*/ struct Coords16 pos;
    /*0x04*/ struct WarpData location;
    /*0x0C*/ struct WarpData warp1;
    /*0x14*/ struct WarpData dynamicWarp;
    /*0x1C*/ struct WarpData lastHealLocation;   ← 用这个
    /*0x24*/ struct WarpData warp4;
    /*0x234*/ u8 playerPartyCount;
    /*0x238*/ struct Pokemon playerParty[6];
};
```

⚠ **踩坑**：我曾把 y 写到 `+0x05`，结果 y 覆盖 x 的高字节，
x 变成 `0x0744 = 1860`，角色落进水里。正确是 `x@+0x04(s16)`、`y@+0x06(s16)`。

### 队伍加密三层（改技能必须全对，缺一个游戏判数据损坏）

| 层 | 日版实测结论 |
|---|---|
| XOR | `key = pid ^ otid`，每 4 字节异或。往返 6/6 通过（`verify_mon_crypto.py`） |
| 子结构顺序 | 由 `pid%24` 决定，但**日版与 pokeruby `gSubstructOrder` 有 3/5 错位**。用「PP 不超过上限」打分反推（`derive_substruct_order.py`） |
| 校验子 | **日版 = `(四个 slot 的 u16 和 的累加) & 0xFFFF`**，写在 `+0x1C`（单个 u16），`+0x1E` 固定 0。⚠ pokeruby 说是「异或 + 4 个同值 u16」，照抄会写坏。6/6 命中（`verify_checkword_algo.py`） |

### 用法

**Step 1（一次性）** 植入传送术：

```powershell
python scripts/warp_tool.py                 # 体检：打印 6 只技能 + 校验子
python scripts/warp_tool.py --apply --out work/teleport.sav
```

**Step 2（每个场景）**：

```lua
api.warp{ map = "0:33", x = 68, y = 7, mon = 1 }
```

内部自动：写 `lastHealLocation` → 走菜单（START→ポケモン→选第 mon 只→A→A）
→ 等 map 变化 → 打 `[WARP] hit ... 完全命中`。

### 已知限制

**同一场景里连续调用第二次会 TIMEOUT**。第一次传送后菜单/光标状态与起点不同，
固定按键序列对不上。实测「加 B 清场 + 额外 UP」的改法更差（两次全 TIMEOUT），
已回退到「单次可靠」版本。
⇒ 一个场景只做**一次** warp；要多次跳图请拆成多个场景。

## 4.5 ★ 金手指能做到什么、不能做到什么（2026-11-03 实测边界）

这条边界一开始没分清，导致我一度以为「图内也能瞬移」，白试了三轮。

| 操作 | 是否有效 | 实测证据 |
|---|---|---|
| 改数量/旗标/等级/道具这类**普通字段** | ✅ 有效 | 队伍、金钱、gRngValue 都写入成功且被游戏采用 |
| 写 `SaveBlock1.pos`（`sb1+0x00/0x02`） | ⚠️ **值生效，但画面不跟随** | 见下 |
| **跨图改 `mapGroup/mapNum`** | ❌ 无效 | 值改对了、`[POS]` 读对了，画面仍是旧地图、主角消失。地图要读档流程加载 |
| 调 ROM 函数 | ❌ 无接口 | mGBA Lua 只有 `read8/16/32`、`readRange`、`write8/16/32` |

### 「图内瞬移」为什么不行（这轮最重要的负面结论）

实测四轮，每轮都有据可查，**根因最终在源码里定死**：

**根因（pret/pokeruby `src/overworld.c`，权威源码）**

```c
static void ApplyCurrentWarp(void)
{
    gLastUsedWarp = gSaveBlock1.location;
    gSaveBlock1.location = gWarpDestination;   /* ← location 被 gWarpDestination 覆盖 */
    ...
}
void WarpIntoMap(void) { ApplyCurrentWarp(); LoadCurrentMapData(); SetPlayerCoordsFromWarp(); }
```

- `gSaveBlock1.location` 在 warp 时**必然**被 `gWarpDestination` 覆盖
  ⇒ 只改 `location` 一定无效（第 1 轮实测：`wc_poked` 读到 `map=0:33`，
  一穿门仍是 `0:2`）。
- `WarpIntoMap()` 在整份 `overworld.c` 里**只有三处**被调用：
  `DoWhiteOut()`（全员濒死白屏）、传送术/秘密基地 `sub_8053778()`、秘密基地2。
- **普通走门走的是 `CB2_LoadMap` 路径，根本不读 `gWarpDestination`**
  ⇒ 提前改 `gWarpDestination` 也无效（第 2、4 轮）。
  第 4 轮实测：`003` 帧里我写的 `g=0 n=33 x=68 y=7` **保留住了**，
  但 `map` 仍是 `0:2` —— 值在、没人读。

**`struct WarpData` 是 s8 不是 s16**

```c
struct WarpData { s8 mapGroup; s8 mapNum; s8 warpId; s8 x; s8 y; };
```

前几轮我按 `s16` 写 x/y（`width=2`），结构是错的。第 4 轮改成 1 字节才对。

**另外实测**：改 `SaveBlock1.pos` 后 `[POS]` 值会变且保持
（`(23,17)→(5,12)→(30,12)`），但**画面/角色 sprite 不跟随**；
`scripts/find_real_pos.py` 在 288KB RAM 里搜两帧坐标，唯一命中
`0x02025494` = `SaveBlock1+0x00`，说明坐标系只有一份、我改的没错，
渲染读的是另一套每帧由走位逻辑重算的缓存。

**⇒ 结论**

`poke` 能改**游戏逻辑会主动读**的字段（数量/旗标/RNG/level），
但**不能瞬移**：位置移动只有两条真实路径 ——
① 走位；② 触发 `WarpIntoMap`（白屏/传送术/秘密基地），
而后者需要游戏自己发起，纯写内存触发不了。

### 那「跳场景」到底怎么做

```
换图：走位（出门/进城/进建筑）—— 实测 DOWN 穿门就能 map 10:7 → 0:2
图内定位：也只能走位
```

图内走位用 `roam`（见 §4.6），它只按方向推进、撞墙自动换向，
不依赖绝对坐标 —— 这是本轮唯一走通的方式。

## 4.6 `roam` 动作（跨图与图内走位）

```lua
api.roam{ seq = { "DOWN", "DOWN" }, steps = 8 }
```

- 只按**方向**推进，不依赖绝对格坐标 —— 因为换图会把坐标重置
  （实测 `10:7 → 0:2` 时坐标从 `(3,7)` 变成 `(23,14)`）。
- 每格读 `SaveBlock1` 坐标判断是否真的挪动；40 帧没挪 = 撞墙，自动换下一方向。
- 换图时会在日志里打 `[ROAM] map 10:7 -> 0:2 (坐标重置为 23,14)`。

> 局限：只会「撞墙换向」，不会规划绕路。遇到花坛这类障碍需要
> 手工把 `seq` 写成「先退、再侧移、再前进」的形状。

## 4.7 ⚠ 一个很贵的坑：Lua 结构错会**静默卡死**

改 `bot.lua` 时我曾误删了 `else` 分支和两个 `end`，
结果是**语法合法、模拟器不报错**，但 `stop()` 与后面几个顶层
`if` 被卷进了 `for` 循环体里 —— 表现是「mGBA 跑满超时、输出目录空空如也、
连 scene.log 都没有」，看起来像场景逻辑卡住，实际是引擎坏了。

对策：`scripts/lint_lua.py`。它除了查括号/`function-end`，还点名检查
`bot.lua` 必须存在的顶层语句（`if shots == 0 then stop(...)`、
`callbacks:add("keysRead"` 等）。改完 bot.lua 先跑它。

```powershell
python scripts/lint_lua.py bot\bot.lua bot\scenes\POKEMON_RUBY_AXVJ00\_lib.lua
```
