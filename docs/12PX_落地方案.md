# 12px 主字体落地方案（v5 混合写入架构）

> 状态：**待拍板，未实施**。
> 依据：`docs/REWRITE_DESIGN_混合写入架构.md`（§5 步骤 5「可选 12px 主字体」）
> 前置：tm0/tm3 16px 整格已落地并实机验证（2026-08-31，开始菜单/对话中文正常）。

## 1. 为什么要做

字库墨迹本就是 **12×12**（`scripts/build_chinese_font.py`：INK_W=INK_H=12，
PAD_TOP=2 放进 16×16 槽）。实测「中」TR/BR 有墨列 `[0,1]` ⇒ 墨迹实宽约 10px，
复杂字接近 12px。

当前按 **16px advance** 推进 ⇒ **每字右侧白白浪费 4–6px**。改 12px 后：

| 指标 | 16px（现状） | 12px（目标） |
|---|---|---|
| 字间距 | 4–6px（偏散） | 0–2px（紧凑） |
| 单行字数（30 列窗口） | 15 字 | 20 字（+33%） |

## 2. 设计稿依据

| 位置 | 原文 |
|---|---|
| L8 | `字号（8/12/16px）退化为自由参数` |
| L56 | `12px 字距的推进序列（列数 1,2,1,2…平均 1.5）在混合写入下完全自洽` |
| L92 | `字号：12px(相位机制根源) → 8/12/16 自由参数，默认待定` |
| L170 | `（可选）12px 主字体：字号此时只是参数，若需要再开` |

`blend_glyph_4bpp` 的 `startPixel` + `spillTile` 就是为此准备的，**原语本身不用改**。

## 3. 核心技术推导

### 3.1 相位只有两态

advance = 12，12 mod 8 = 4 ⇒ `px` 每次 +12，相位 `phase = px & 7` 只在 **0 ↔ 4** 间交替。

```
字序:   1     2     3     4     5     6
phase:  0     4     0     4     0     4
推进列: 1     2     1     2     1     2      ← 正是设计稿 L56 的 1,2,1,2
```

推进列数 = `(phase + 12) / 8` = `phase==0 ? 1 : 2`。

### 3.2 每个字拆两段（关键）

`blend_glyph_4bpp` 一次调用最多写 8 像素宽（`sGlyphMasks[9]` 的 width 索引上限 8），
12px 必须拆两次。以 `phase` 分段，**第一段填满本 tile 剩余空间**：

| | 第一段（本 tile） | 第二段（下 tile） |
|---|---|---|
| dest 起点 | `startPixel = phase` | `startPixel = 0` |
| 宽度 | `w0 = 8 - phase` | `w1 = 4 + phase` |
| 源列范围 | 字列 `[0, w0)` | 字列 `[w0, 12)` |

验算：
- `phase=0`：w0=8（字列 0–8）、w1=4（字列 8–12）✓
- `phase=4`：w0=4（字列 0–4）、w1=8（字列 4–12）✓

### 3.3 ⚠ 源列可能跨字库 tile，必须先拼接

字库槽是 `[TL@0][BL@32][TR@64][BR@96]`（列 0–7 在 TL/BL，列 8–11 在 TR/BR）。

`phase=4` 时第二段的源列是 **字列 4–11**，横跨 TL（列 4–7）与 TR（列 0–3）。
而 `blend_row_4bpp` 从 src 的第 0 像素开始取，**不支持 src 偏移**。

⇒ 需要一个 `extract_cols()` 先把任意列范围拼成连续块，再交给 blend：

```c
/* 从 128B 槽取字列 [xs, xs+w) → 8x16 块（up[32] 上半 / lo[32] 下半，右补 0） */
static void extract_cols(const uint8_t *g128, unsigned xs, unsigned w,
                         uint8_t up[32], uint8_t lo[32]);
```

**这是对 `blend_glyph.c` 唯一的增量**（新增一个纯函数，不动原语、不重跑对拍主体）。

### 3.4 列步进与 lower_delta 必须分 mode

本列/下行的 tile 关系已由上一轮修正，12px 还要再区分**列步进**：

| mode | lower_delta（上下半间距） | col_stride（列步进） | 说明 |
|---|---|---|---|
| tm0 | 1 | 2 | 上下 tile 相邻，每列占 2 个 tile 号 |
| tm3 | 30 | 1 | 上下 tile 隔 30，每列占 1 个 tile 号 |

第一段写 `tile` / `tile+lower_delta`；第二段写 `tile+col_stride` / `tile+col_stride+lower_delta`。

## 4. 相位存储（前人已定案，直接复用）

`include/game.h` L163 已有 **2026-08-25 反汇编定案**结论：

```
12px 步进的半列相位必须自存。表落 0x0203FF80-FFCF（多轮验证安全区；
0x0203FFD2 起为游戏数据区，严禁占用——旧页表死机根因）。
key = 行指纹（TILE_BASE^CURSOR_Y^CURSOR_TILE_Y^template^stream），
换行/换流自动换 key = 相位自动归零；失配检测（cursor 回退/跳列）防重印错位。
```

**v5 下该区已完全空闲**：`ADDR_CHS_PITCH_CTRL` / `ADDR_CHS_PITCH_SLOTS` /
`ADDR_GLYPH_ALLOC_NEXT` 在 `src/` 中已无任何引用（v4 槽位机制已删）。

### 4.1 结构精简

v4 的 `struct ChsPhase` 带 `scr_org/scr_next`（槽位分配残留），v5 不需要，精简为：

```c
#define CHS_PHASE_COUNT  8u
struct ChsPhase {
    uint16_t key;   /* +0 行指纹 */
    uint16_t px;    /* +2 行内已绘像素；phase = px & 7 */
};                  /* 4B × 8 = 32B @ 0x0203FF90 */
```

### 4.2 行指纹

```c
static uint16_t chs_phase_key(TextPrinter *win)
{
    uint8_t *tpl = win_template(win);
    uint16_t w = tpl ? (uint16_t)(((uintptr_t)tpl >> 2) & 0xFFFFu) : 0;
    return (uint16_t)(win_u16(win, WIN_TILE_BASE)
                    ^ ((uint16_t)win_u8(win, WIN_CURSOR_Y) << 8)
                    ^ ((uint16_t)win_u8(win, WIN_CURSOR_TILE_Y) << 4)
                    ^ w);
}
```

**归零靠 key 失配，不靠显式换行事件** —— 换行 ⇒ `CURSOR_Y/CURSOR_TILE_Y` 变 ⇒ key 变 ⇒
`px` 归零；换窗口 ⇒ `template/TILE_BASE` 变 ⇒ 同样归零。

⚠ **强制约束**：新变量必须显式落 EWRAM 绝对地址。
`game.ld` 无 `.bss/.data` 段，文件级可写 static 会被**静默塞进 ROM 恒为 0 且不报错**。

## 5. 混排处理（易漏点）

日文半角字符走 `FontFunc_NativeDispatch` 原生路径，**也必须推进 px**，否则中文相位全错。

```c
/* DrawGlyph：原生分发一个半角字符后 */
phase_advance(win, 8u);      /* 半角 8px */
```

控制码（换行/换色等）与 ≥0xF7 消费位：按 PCS 语义处理，换行交由 key 失配兜底。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| phase 落 ROM 恒 0（静默失效） | 显式落 0x0203FF90 绝对地址；编译后用 `nm` 确认未进 `.rodata` |
| 相位漂移越界写 VRAM 花屏 | key 失配归零 + `tx0` 行首列锚点做失配检测（cursor 回退/跳列重置） |
| 混排相位错乱 | `DrawGlyph` 同步推进 px（见 §5） |
| 与 16px 模式冲突 | `CHS_ADVANCE_PX` 宏开关（12/16），默认先 16，实测再切 |
| 跨 tile 拼列出错 | `extract_cols` 纯函数 + Python 参考实现单测对拍 |

## 7. 实施步骤

1. `game.h`：新增精简 `struct ChsPhase` 与 `ADDR_CHS_PHASE`(=0x0203FF90)、`CHS_ADVANCE_PX`。
2. 新增 `chs_phase.c`（或并入 `text_render.c`）：`phase_get()` / `phase_advance()`，
   含 key 匹配与失配检测。
3. `blend_glyph.c`：新增纯函数 `extract_cols()`（**不改动 blend 原语本体**）。
4. `text_render.c`：
   - `blit_column_at_tile` 增加 `col_stride`、`phase` 参数；
   - 新增 `print_glyph_12px()`（按 §3.2 两段式）；
   - `DrawGlyph` 同步推进 px（§5）。
5. 单测：`extract_cols` 与 Python 参考实现对拍（列边界、phase=0/4 全覆盖）。
6. 编译 → `check_rom_hook.py` → 打包 → **实机实测**。
7. 实测通过后再考虑把默认 `CHS_ADVANCE_PX` 从 16 切到 12。

## 8. 回退

`CHS_ADVANCE_PX` 改回 16 即回到当前已验证的 16px 整格路径；
phase 相关代码在 16px 模式下不参与推进，可保留不动。

## 9. 未决问题（需拍板）

1. **advance 取 12 还是 13/14**：12 时复杂字（墨迹满 12px）会**零间距紧贴**；
   若觉得挤，可取 13（相位 0→5→2→7→4→1→6→3 循环，仍自洽，但不再两态）。
   建议先按 **12** 实测，看实际观感再定。
2. **tm1（队伍/图鉴）是否同步**：tm1 目前**未实现像素路径**（只消费+推进），
   本轮不覆盖；12px 先在 tm0/tm3 验证。
