# 15-0 窗口级画布账本 · 结论

> 对应 `docs/方案总纲_v15_领号单位改为窗口_20260920.md` §六 步骤 15-0。
> 脚本：`scripts/ledger_15_0_window_canvas.py`（**5 道自证闸门全过**，零 ROM 风险）。
> 本文件只记**实测结论**与它推翻/修正了什么。

---

## 一、先修正 v15 里三处不准的数字

| v15 原文 | 实测（本轮） | 证据 |
|---|---|---|
| 「52 个窗口模板」 | **53 条**（`0x081BB3DC .. 0x081BB8D4`，步长 0x18） | 53×0x18 = 0x4F8，起点+0x4F8 恰好 == ID 表起点 |
| 「tm0 ×14 / tm1 ×36 / tm3 ×2」 | **tm0 ×14 / tm1 ×36 / tm2 ×1 / tm3 ×2** | 漏掉的那条就是下面 §二 的 OBJ 槽 |
| 「font3 ×49 / font0 ×2 / font4 ×1」 | font3 ×49 / font0 ×2 / **font4 ×2** | 同上 |
| 「cb0 ×24」 | **cb0 ×25** | 同上 |

**教训**：v14/v15 的模板枚举用了「tilemap 必须落在 `0x06000000..0x06017FFF`」的过滤判据，
而漏掉的那条 `tilemap == 0` ⇒ 被静默剔除。**「过滤条件」会把不符合假设的真数据当成噪声丢掉** ——
这正是本项目铁律「自研扫描器必须先自证」要防的事。本轮改为**按 stride 硬取 53 槽**（不过滤），
再用「末槽 +0x18 == ID 表起点」自证条数。

## 二、🔴 新发现：引擎自带一条 **OBJ VRAM** 模板

`0x081BB40C`（53 槽中的第 3 条）：

```
bg=0  charBase=0  screenBase=0  palette=0  混合 1/0/3
font=4  textMode=2   tileData=0x06010000   tilemap=0x00000000
```

`0x06010000` 是 **OBJ VRAM 起点**（GBA：BG 占 `0x06000000..0x0600FFFF`，OBJ 占 `0x06010000..0x06017FFF`）。
⇒ **这条窗口的字形根本不占 BG tile 号**，且它是 **53 条里唯一的 textMode==2**。

意义三条：

1. 这是 **引擎内已有的「OBJ 画字」先例** —— v14 里被列为备选的路线 A2（中文走 OBJ）不是外来的，
   游戏自己就这么干（对应 font4 = 队伍/血条那族，与 MEMORY 记的「队伍 font4 被覆盖」同源）。
2. 它解释了 `v8_official_end` 为什么对 font4 算 279：那条窗口压根不在 BG 号空间里。
3. **`TPL_TILE_DATA ≡ 0x06000000 + charBase×0x4000` 有且仅有 1 个例外**，就是这个 OBJ 槽。
   本轮把它写成**可预测的例外**（G2 断言「例外数恰为 1」），而不是放宽判据。

## 三、🔴 新发现：`0x081BB8D4` 是 **{模板指针, 窗口ID} 配对表**

紧随 53 槽之后，53 项，id 覆盖 0..52：

```
+0x000  0x081bb3dc  id=0      +0x040  0x081bb49c  id=8
+0x008  0x081bb3f4  id=1      +0x048  0x081bb4b4  id=24
+0x010  0x081bb424  id=2      ...
+0x028  0x081bb40c  id=5      ← OBJ 槽
```

⇒ **引擎按「窗口 ID」建窗，ID → 模板**。这是 15-0b「哪个场景开几个窗、用哪条模板」的入口：
在 `AddWindow` 调用点枚举常量 ID 即可。本轮的 G4 断言「表内每个指针都必须是 53 槽之一」已经用来自证这张表的解释是对的。

---

## 四、🔴 模板里**没有** width / height ⇒ 版式宽度是**数据**不是引擎字段

字段语义（实证，`tools/scan_axvj_templates.py` + 本轮交叉核对）：

```
0x00 bg        0x01 charBase    0x02 screenBase   0x03 ?(<4)   0x04 palette
0x05/0x06/0x07 混合系数(fg/bg/mode)     0x08 font     0x09 textMode
0x0A/0x0B 恒 0（53/53）                 0x0C tileData(u32)   0x10 tilemap(u32)
0x14..0x17 未用
```

⚠ v15 与旧账本里把 `[5]` 当「起始偏移」是**错的** —— `[5]/[6]/[7]` 是混合系数（分布
`[5]∈{1,15,13}`、`[6]/[7]∈{0..15}`，与 `scan_axvj_templates.py` 早先的判据一致）。
已修脚本，改为不解释 `[5]`，`official_end` 只用 font 决定（535 / 279）。

**推论（重要）**：日版引擎的换行完全靠文本里的显式控制码（`\n` `\l` `\p`），
所以「一个窗口几列几行」这件事，**只存在于文本数据里，不存在于窗口元数据里**。
⇒ 画布尺寸只能：**(a) 从译文量算**（§五，已做）或 **(b) 运行时按行带懒分配**。
⇒ 任何「从模板读 W/H」的设计都不可能成立，不要再试。

## 五、✅ 需求侧实测（7489 条真实译文，两道自证闸门剔除 5195 条二进制/乱码）

模型：**画布 tile = ceil(最宽行 px / 8) × 2 × 行数**
（11px 墨迹 + 12px 步进 ⇒ 每字横跨 2 个 tile 列；11px 落在 16px 高格 ⇒ 每行 2 个 tile 行）

| # | module | 最坏画布 tile | = 列×2×行 | 最大行宽 |
|---|---|---|---|---|
| 1 | 剧情 | **160** | 20×2×4 | 160px |
| 2 | 招式说明 | 120 | 15×2×4 | 120px |
| 3 | UI界面 | 120 | 20×2×3 | 160px |
| 4 | 道具说明 | 90 | 15×2×3 | 120px |
| 5 | 招式说明-华丽大赛 | 80 | 20×2×2 | 160px |
| 6 | 补漏剧情 | 52 | 13×2×2 | 104px |
| 7..21 | 其余 15 个模块 | ≤30 | 全部 **1 行** | ≤224px |

**全语料分布（7489 块）**：`min=4  p50=12  p90=60  p99=120  max=160`
**全语料最大行宽 = 224px**（= 28 个 tile 列，比屏幕 240px 只小 16px）

## 六、✅ 结论：**容量不是瓶颈**（本轮最重要的一条）

```
单窗最坏需求（实测）           = 160 tile
同 charBlock 可用（保留官方图集）= 1024 − 535 − 23 = 466 tile
```

⇒ **3 倍余量。不需要回收官方图集（A1），不需要专属 charBlock（15-4）。**

领航员专项（§5 可行域表，直接回答「9~12 行撑不撑得住」）：

| 场景 | 画布 | 判定 |
|---|---|---|
| 12 行 × 13 列（104px） | 312 | ✅ 保留官方图集即可 |
| 12 行 × 15 列（120px） | 360 | ✅ 保留官方图集即可 |
| 12 行 × 20 列（160px） | 480 | △ 要回收官方图集 |
| 满屏天花板 30 列 × 10 行 | 600 | △ 要回收官方图集 |

⇒ **只要领航员最宽行 ≤ 18 个 tile 列（144px），保留官方图集就装得下。**
「领航员完全不够」在实测面前不成立 —— 之前的「差一倍」是拿 **489 号 ÷ 60/行** 算的，
而 60/行 那个数**假设了满 30 列宽**，实际译文最宽只有 20 列。

**⇒ v15 的方向（位置定号）依然正确，但它的收益不再是「把需求从无上界压到 600」，
而是「让号变成位置的纯函数，从而消掉 4 份跨窗缓存状态」。容量账这一侧，本来就平。**

## 七、领航员落在哪（本轮校正的一处误判）

领航员的两条模板（`scene_cfg.c` 实证）：

```
0x081BB7B4  注册人数/对战人数   bg0 cb0 sb31 pal15 font3 tm1 tileData=0x06000000 tilemap=0x0600F800
0x081BB7E4  训练家名           bg3 cb0 sb30 pal2  font3 tm1 tileData=0x06000000 tilemap=0x0600F000
```

🔴 **两条都是 tm1、font3、charBase 0、`TILE_BASE = 0x06000000`（号 0）。**

- ⇒ 它们和 **cb0 里另外 23 条模板**（cb0 共 25 条，是全 4 个 charBlock 中最挤的）**抢同一块地**。
- ⇒ 它们的可用池是 `[v8_official_end=535, 1024)` = 489 号 —— v12 抬水位的由来。
- ⚠ 我一度猜「cb1 那两条 tm0 模板是领航员」，**读 `scene_cfg.c` 后否掉了** —— 领航员是 cb0/tm1。
  （教训：`charBase` 空 ≠ 场景用得到；必须按 **tpl 地址**去场景配置里查，不能按「哪个 cb 空」猜。）

## 八、下一步（15-0 已完成的判定 + 剩余缺口）

**已完成**：供给侧、模板属性、需求侧全部钉成实测值；5 道自证闸门。

**剩余缺口（一）**：**「哪个场景开几个窗口」** —— 需要枚举 `AddWindow` 调用点的常量 ID
（入口已找到：§三 的 ID 配对表 + `0x08004228` 那个 id→模板函数）。这决定同屏**多窗求和**，
也决定画布分配器的槽数与尺寸。

**剩余缺口（二）**：**画布宽度 W 从哪来**。三条候选（按推荐序）：

| 方案 | 做法 | 代价 |
|---|---|---|
| **W1 运行时分行带懒分配** | 每个 `(窗口, 行号)` 领一条带，带宽 = `2×COLS`；`tile = 行带基址 + 2×列号` | 无需知道 W；账本 = 同屏行数（≤20），符合「单位 = 窗口」 |
| **W2 场景表给 W** | 扩 `scene_cfg.c`：每场景带一个 `canvas_cols`（默认 20） | 需逐场景填；但领航员一条就能从 480 降到 384 |
| **W3 固定 W=24** | 全窗口统一 `W=24`（192px > 实测最大 160px） | 最省事；领航员 12 行 ⇒ 576 tile，**必须回收图集** |

**建议**：**W1**。它与 v15「领号单位 = 窗口」同构（带 = 窗口的某一行），零 W 知识，
且天然满足 `tile = f(窗口, 行, 列)` 的 J1/J2 判据；W2 作为「给某场景再省一点」的调节旋钮后加。
