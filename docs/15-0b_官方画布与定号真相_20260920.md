# 15-0b 官方画布与定号真相 · 结论

> 承接 `docs/15-0_窗口画布账本_结论_20260920.md` §八「剩余缺口（一）」。
> 脚本：`scripts/scan_inittp_sites.py`（含自证闸门，零 ROM 风险，只读）。

## 〇、一句话结论

**日版引擎的文本画布本来就是「位置定号 + 每窗口一块私有基址」，而且
`TILE_BASE` 只有 3 个常量值 `{0x28, 0x90, 0xBC}`。
v12 的 `v8_official_end(win) ∈ {535, 279}` 是错的 —— 它把「要加载多少个字形」
误读成了「占用号区间的上界」，于是凭空造出一个不存在的「官方占位区」。**

## 一、证据链（全部逐指令反汇编，`arm-none-eabi-objdump -M force-thumb`）

### 1. `InitTextPrinter 0x08002C68` —— TILE_BASE 的唯一来源

```
0x08002C84  ldr  r5,[r0,#0]        r5 = win->tpl
0x08002C86  ldrb r4,[r5,#9]        tpl[9] = textMode
0x08002C88  strb r4,[r0,#10]       🔴 win[0x0A] = textMode   ← 直接抄模板
0x08002C8A  ldrb r4,[r5,#8]        tpl[8] = font
0x08002C8C  strb r4,[r0,#11]       win[0x0B] = font
...
0x08002C9E  str  r1,[r0,#16]       win[0x10] = text
0x08002CA0  strh r6,[r0,#20]       win[0x14] = 0        (textIndex)
0x08002CA2  strh r2,[r0,#22]       🔴 win[0x16] = r2    ← TILE_BASE = 第 3 参数
0x08002CA4  strh r6,[r0,#24]       win[0x18] = 0        (TILE_OFFSET 复位)
0x08002CA6  strb r3,[r0,#26]       win[0x1A] = cur_x
0x08002CAC  strb r9,[r0,#28]       win[0x1C] = cur_y
```

⇒ **`textMode` 与 `TILE_BASE` 都在这里一次性定死**：前者来自模板，后者来自调用者。
全 ROM 只有 **4 个** `InitTextPrinter` 直接调用点。

### 2. 主路径 `0x08002D1C` —— 60 个调用点，透传 `tile_base`

```
0x08002D28  lsls r2,r2,#16 / lsrs r2,r2,#16     r2 归一化成 u16（保留入参！）
...
0x08002D50  adds r0,r7,#0                        r0 = win
0x08002D52  bl   0x08002C68                      InitTextPrinter(win, r1, r2, r3, r5)
0x08002D56  ldrb r0,[r7,#10]                     r0 = win[0x0A] = textMode
0x08002D58  cmp  r0,#0
0x08002D5A  bne  0x08002D92                      🔴 非 tm0 ⇒ 跳过下面整段
--- tm0 专用：初始化时往画布写 2 个 tile ---
0x08002D5C  ldr  r0,[pc,#76]                     → 0x081B3A84（font0 某字形源）
0x08002D5E  ldr  r3,[r7,#0]                      tpl
0x08002D60  ldrh r2,[r7,#22]                     TILE_BASE
0x08002D62  ldrh r1,[r7,#24]                     TILE_OFFSET
0x08002D64  adds r2,r2,r1                        🔴 tile = TILE_BASE + TILE_OFFSET
0x08002D66  lsls r2,r2,#5                        ×32 字节
0x08002D68  ldr  r1,[r3,#12]                     tpl->tileData
0x08002D6A  adds r1,r1,r2                        dst 上半
0x08002D70  bl   0x08003830                      CopyGlyph1bppTo4bpp
0x08002D84  adds r1,#32                          🔴 +32 字节 = 下半 tile
0x08002D8E  movs r0,#4
0x08002D90  strh r0,[r7,#24]                     TILE_OFFSET = 4
```

⇒ **官方 tm0 的 `tile = TILE_BASE + TILE_OFFSET`，且 `+0`/`+32` 是同一号的上/下半。**

### 3. tm0 处理器 `0x08003568` —— 步进

```
0x08003568  push {r4,lr}
0x0800356A  adds r4,r0,#0                  win
0x0800356C  bl   0x08003520                画字形
0x08003570  ldrh r0,[r4,#24]               TILE_OFFSET
0x08003572  adds r0,#2
0x08003574  strh r0,[r4,#24]               🔴 TILE_OFFSET += 2
0x08003576  ldrb r0,[r4,#27]               CURSOR_TILE_X
0x08003578  adds r0,#1
0x0800357A  strb r0,[r4,#27]               CURSOR_TILE_X += 1
```

⇒ **官方每字「1 列 = 2 号」的线性推进。我们的 `TILE_OFFSET += adv*2`
（`adv = (phase+advance)>>3`）与它完全同构，本来就对。**

### 4. 🔴🔴🔴 `InitWindowTileData 0x08002A50` —— 官方字形加载到哪

```
0x08002A5E  ldrb r0,[r4,#8]        r4 = tpl（不是 win！）  r0 = tpl[8] = font
0x08002A60  cmp  r0,#5 / bhi      font > 5 ⇒ 返回
0x08002A66  ldr  r1,[pc,#8]  → 0x08002A74  font 分派跳转表
0x08002A6A  ldr  r0,[r0,r1] ; mov pc,r0
表 @0x08002A74 = [0x08002A8C, 0x08002AAC, 0x08002AAC, 0x08002A8C, 0x08002ACC, 0x08002ACC]
   font 0,3 → 0x08002A8C ｜ font 1,2 → 0x08002AAC ｜ font 4,5 → 0x08002ACC

--- font 0/3 分支 0x08002A8C ---
0x08002A8C  lsls r1,r3,#5          r1 = startOffset * 32
0x08002A8E  ldr  r0,[r4,#12]       r0 = tpl->tileData
0x08002A90  adds r0,r0,r1          + startOffset*32
0x08002A92  lsls r1,r6,#6          r1 = glyphIdx * 64
0x08002A94  adds r5,r0,r1          🔴 dst = tileData + startOffset*32 + glyphIdx*64
```

⇒ **官方字形落在 tile 号 `startOffset + 2×glyphIdx`，其中 `startOffset` 就是窗口的
`TILE_BASE`。** 配合 `tpl->tileData ≡ 0x06000000 + charBase×0x4000`（15-0 §二 G2 已证），
**官方资产区间 = `[TILE_BASE, TILE_BASE + 2×已加载字形数)` —— 它是「跟着窗口走」的，
不是一块全局的 `[0, 512)`。**

### 5. 🔴🔴🔴 多帧加载 worker `0x080029E0` —— 哪些 textMode 会加载

```
0x080029E2  ldr r0,[pc] → 0x03000328     sMultistepLoadFont 状态块
0x080029E4  ldr r0,[r0]                  状态块[0] = tpl 指针
0x080029E6  ldrb r0,[r0,#9]              r0 = tpl[9] = textMode
0x080029E8  cmp r0,#0 ;  beq 0x08002A48  🔴 textMode == 0 → 直接 return 1（什么都不做）
0x080029EC  cmp r0,#0 ;  blt (不可能)
0x080029F0  cmp r0,#3 ;  bgt 0x080029F8  > 3 → 去加载
0x080029F4  cmp r0,#2 ;  bge 0x08002A48  🔴 textMode 2 或 3 → 直接 return 1
                                            ⇒ 只有 textMode == 1 落到加载分支
0x08002A08  ldr r0,[0x03000328] ; ldrh r1,[0x0300032C]  (tpl, startOffset)
0x08002A14  bl  0x08002A50                InitWindowTileData(tpl, startOffset, glyphIdx)
0x08002A18  adds r4,#1                    glyphIdx++
0x08002A1E  adds r0,#16 ; cmp r4,r0 ; blt 每次 worker 处理 16 个字形
0x08002A2C  lsls r1,r1,#16 ; ... cmp 0x1000000   progress 到 256 停
```

状态块 `{tpl*, u16 startOffset, u16 progress}` @`0x03000328 / 0x32C / 0x32E`（8 字节）。

⇒ **🔴 只有 `textMode == 1` 的窗口才把日文字形灌进 VRAM。tm0 / tm2 / tm3 一律不灌。**

## 二、🔴 于是 v12 的 `v8_official_end` 是错的

v12 的模型（`tile_alloc.c`）：

```
上界 = max(startOffset + cap, cap + 23)      cap: font0/3 ⇒ 512, 其余 ⇒ 256
     ⇒ font0/3 = 535, 其余 = 279
```
它把 `[1, 上界)` 当成「官方资产占位区」，一律不复用。

**错在两处：**

| # | 错在哪 | 实证 |
|---|---|---|
| 1 | `cap` 是**待加载字形的个数**，不是「号区间长度」 | 它只用来当 `progress` 的循环上界（`0x08002A1C`），字形实际落在 `TILE_BASE + 2×glyphIdx`（§一.4） |
| 2 | 起点不是 0，而是**每个窗口各自的 `TILE_BASE`** | `0x08002D60` 读 `win[0x16]`；3 个常量 `{0x28,0x90,0xBC}`（§三） |

⇒ **「官方占了一半号空间」是假象。** 真实的官方占位是
**`[TILE_BASE_该窗口, TILE_BASE_该窗口 + 2×该窗口用到的字形数)`**。
而**只要窗口是 tm0，这个区间是空的**。

## 三、TILE_BASE 的真实取值分布（60 个调用点全扫）

`scripts/scan_inittp_sites.py 0x08002D1C`：

| TILE_BASE | 调用点数 | 代表地址 |
|---|---|---|
| **0x90 (144)** | **21** | `0x802B8FE`、`0x802D76A`、`0x80327D2`、`0x80370FE`、`0x810D45A`…`0x810DEC8`（16 连发）、`0x811AFD6`、`0x81268EA`、`0x8133ED6` |
| **0xBC (188)** | **13** | `0x80A7634`…`0x80ACE9A`（同族连发） |
| **0x28 (40)** | **13** | `0x810E388`…`0x810EA0E`（同族连发） |
| 0x2C (44) | 1 | `0x8040908`（`adds r2,#44`） |
| 0x2 | 1 | `0x80F321A` |

⇒ **引擎给「窗口组」预留 3 块画布，每块由一族同场景调用点共用。**
相邻基址间距只有 **44 ~ 104** 号 ⇒ **官方隐含假设「一个窗口组的画布 ≲ 44 号」**
（≈ 官方 8px 步进下 22 个字形位，或 11 行文本）。

**这解释了实机所有症状**：我们从 535 起发号（一个不存在的水位），
正好撞进 `0x90` / `0xBC` 两族的画布 ⇒ 领航员（0x90/0xBC 族）、队伍 font4 全中招。
「抬水位」修不掉它，因为**水位本身就定错了坐标系**。

## 三补、🔴 缺口①已答：共用基址的多个调用点**不同屏**

`scripts/group_inittp_by_host.py`（自证：`0x0802B8FE` 的 r2 必须是 `0x90`，通过）：

```
宿主函数        #bl    TILE_BASE
0x0802B8D8      1     0x90
0x080A7D50     11     0xBC ×11     ← 同函数内 11 次！
0x0810D304     15     0x90 ×15     ← 同函数内 15 次！
0x0810DF24     13     0x28 ×13     ← 同函数内 13 次！
（其余 21 个宿主各 1 次）
```

**这三个"同基址多次"的宿主，全部是跳转表分派器**（`0x080A7D50` 实证）：

```
0x080A7D50  push {r4,r5,r6,r7,lr} … push {r5,r6,r7}
0x080A7D5C  lsls/`lsrs` r0,#0x18/#0x18    r0 = 入参 (u8) = case 索引
0x080A7D64  ldrb r7,[r2,#0x11]
0x080A7D68  lsls r0,r0,#2 ; add r0,r8 ; lsls r0,r0,#3 ; adds r0,r0,r1
0x080A7D72  ldrsh r0,[r0,#8]               r0 = 表[idx].field8
0x080A7D78  cmp r0,#0x3b ; bls            越界检查（60 个 case）
0x080A7D7C  bl 0x080A9346                 （越界处理，尾随不返回）
0x080A7D80  lsls r0,r0,#2 ; ldr r1,[pc] ; adds r0,r0,r1 ; ldr r0,[r0]
0x080A7D88  mov pc, r0                    🔴 跳转表分派，一次只走一个 case
```

且**三个函数都有 0 个直接调用者** ⇒ 只能经函数指针被调用。

⇒ **不是「同屏 11 个窗口抢一块画布」，而是「11 种情况轮流用同一块画布」。**
⇒ **缺口① 结论：`TILE_BASE` 标识「画布」，同一画布上的窗口是顺序使用，天然不撞。**
⇒ **15-3「窗口级画布分配器」不必为"同屏多窗"而做。**

### ⚠ 但由此暴露一条新硬约束

```
TILE_BASE 由调用点用 Thumb `movs r2, #imm8` 传 ⇒ 🔴 立即数上限 255
```

3 块画布只剩 `[0, 255]` ⇒ 任一块画布**最大 255 号**，且必须互不重叠。
而 15-0 §五 实测：**领航员 12 行 × 15 列 = 360 号**。
⇒ **官方给领航员的画布装不下它自己，这与"TILE_BASE ≤ 255"无关，是「画布本来就这么小」。**

领航员的模板 id（ID 表实证）：**slot41 `0x081BB7B4` → id=37**（注册/对战人数）、
**slot43 `0x081BB7E4` → id=47**（训练家名）。

⇒ 结论不变，但**实现不能再靠改调用点的立即数**（255 封顶）。
⇒ 必须**在 `InitTextPrinter` 钩子里直接写 `win[0x16]`** —— 它是 `u16`，上限 1023。

## 四、⇒ 15-2 的方案骨架（**待用户确认后才动手**）

### 4.1 必须做的三步

| 步 | 做法 | 为什么必须这样 |
|---|---|---|
| **1** | **ROM 模板 `tpl[9]`：`1 → 0`**（36 处，每处 1 字节） | 字形加载 worker 读的是 **`tpl[9]`（不是 `win[0x0A]`）** ⇒ 只在钩子里改 `win[0x0A]` **挡不住字形灌入**。必须改数据 |
| **2** | **钩 `InitTextPrinter 0x08002C68` 尾部，直接写 `win[0x16]`** | `win[0x16]` 是 **u16（上限 1023）**；而调用点用 `movs r2,#imm8` 传值，**上限 255** ⇒ 想给大画布就只能自己写字段 |
| **3** | **删掉** `v8_alloc_tile` / `v8_ours_*` 账本 / `chs_cell_slot` / `v8_official_end` / 相位 tile 复用 | 位置定号下 `tile` 是算出来的，那套「读回 tilemap 猜这格是不是我们写的」失去存在理由 |

**第 1 步是安全的全局改动**：本工程是整体汉化，不存在要保留日文渲染的窗口；
且它**顺带关掉官方字形加载**（§一.5）⇒ 反而把 VRAM 让出来。
⚠ 唯一改不到的是 **tm2 血条**：`0x08002CC0` 会把 `win[0x0A]` 强制设成 2
（`strb r0,[r4,#10]`，r0=2），这条路**不受模板影响**，也**正确** —— 血条必须留 tm2。

### 4.2 画布基址怎么给（**这是唯一未决点**）

`tile = TILE_BASE + TILE_OFFSET`，`TILE_OFFSET += adv*2`（adv∈{1,2}）。
所以「画布大小」= `TILE_BASE` 到「下一块画布起点」的距离，**必须由我们保证**。

| 候选 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **C1 窗口实例顺序分配** | 一张 ≤8 项的 `(win → base)` 表；`InitTextPrinter` 时查表，没有就从游标领一块（块大小 ≈480 号） | 简单、有界、可回退 | 同屏 >2 个大窗口会溢出，需溢出降级策略 |
| **C2 屏幕位置定号** | `tile = f(屏幕格)`，靠 `win[0x1A]/[0x1C]` 或 `tpl->tilemap` 推 | 零分配器 | ⚠️ **2026-09-21 更正：判死不成立（部分）**。原文理由是「`cur_x/cur_y` 是窗口内偏移」—— 但 `InitTextPrinter 0x08002C68` 的 `strb r3,[r0,#26]`（`win[0x1A]=a4`）/ `strb r9,[r0,#28]`（`win[0x1C]=a5`）把**调用点给的屏幕格坐标**直接写进去；实测**同一窗口的 22 个块 a4/a5 逐块不同** ⇒ 能区分。仅「两个不同窗口可给同一 `(a4,a5)`」那一半仍成立。见文末 §十一 |
| **C3 行带懒分配（W1）** | 每个 `(窗口, 行)` 领一条带，带宽 `2×W` | 需求 = 实际行数，最省 | 需在换行处改 `win[0x16]`，且要知道 W |

**推荐 C1**，理由：`TILE_BASE ≤ 255` 的官方约束不再需要遵守（第 2 步直接写字段），
所以可以给每块画布 480 号；扣掉窗框 23 号后 `[23, 503) ∪ [503, 983)` 恰好放 **2 块**。
而 15-0 §五 实测**单窗最坏 160 号**、**领航员 360 号** ⇒ 480 有 1.3~3 倍余量。

### 4.3 必须遵守的判据（施工时逐条自证）

- **J1** `tile = TILE_BASE + TILE_OFFSET` 是**纯函数**，不含任何账本/扫描查询。
- **J2** 同一次文本块内 `TILE_OFFSET` 单调不减；换行**不复位**（官方 tm0 也不复位）。
- **J3** `win[0x16]` 的两个不同值对应的区间**不相交**（分配器唯一不变量）。
- **J4** tm2 血条路径**完全不受影响**（`win[0x20]` 缓冲 + `0x40` 步进）。
- **J5** 关掉 `v8_official_end` 后，**font4 半角字符仍正确**（因为 `GetGlyphTilePointers_Origin`
  是从 **ROM** 取字形，不经 VRAM）。

## 五、残留风险与缺口（诚实交代）

1. 🔴 **同屏到底几个中文窗口？** 缺口① 只证明了「同一 `TILE_BASE` 的多个调用点
   分布在同一**分派器**函数里 ⇒ 不同屏」。但**不同 `TILE_BASE` 的窗口同时活着**
   （对话 + 菜单 + 战斗四格）**没有证实也没有证伪**。
   ⇒ C1 的块数（2 块够不够）取决于这条。**建议在改造第一步前用 gdb 采一次实测**
   （在 `InitTextPrinter` 断点记 `(win, tpl, tile_base, lr)` 的组合），否则只能按 2 块下手。
2. ⚠ **`v20`（LZ/UI 门控）不在代码树里**（全仓搜不到 `0x081B1298`/`LZ77UnCompVram`/`lz_ui_sites`）
   ⇒ 静态 BG 层美术仍可能与我们的画布物理重叠。**这是「撞 UI」的另一半，本文件未覆盖。**
3. ⬜ **未枚举** `0x03000328` 状态块（`sMultistepLoadFont`）的写入点 ——
   确认除 `InitTextPrinter` 外还有谁会启动字形加载（影响第 1 步是否足够）。
4. ⬜ **未定位**领航员场景代码（只知道模板 id = **37 / 47**）⇒ 它当前拿到的
   `TILE_BASE` 是 `{0x28,0x90,0xBC}` 中的哪一个，尚未实测。若它是 `0x28`（画布仅 104 号）
   则「完全不够」的算术解释就闭合了。

## 六、本轮的方法论收获（已进铁律）

1. **BL 解码必须符号扩展**：`imm32 = S:I1:I2:imm10:imm11:'0'` 是 25 位有符号数。
   漏掉 `if d & 0x1000000: d -= 0x2000000` 会算出天文数字，表现为
   **「一个调用点都找不到」**。本脚本的自证闸门（段内 3 个已知点）当场抓住。
2. **找路径要看「参数怎么传」**，不要只看「函数在哪」：
   `InitTextPrinter` 只有 4 个直接调用点，看起来像冷门函数；
   但经过 `0x08002D1C` 这层透传包装后有 **60 个**调用点。
   ⇒ **包装函数的调用点才是真实使用面。**
3. **一个「上界」数字，必须问清它数的是什么**：
   `cap=512` 数的是**加载字形个数**，被 v12 当成**号区间长度**，
   于是一整条路线（回收图集 / 抬水位 / 专属 charBlock）都建在错坐标上。

## 十一、更正（2026-09-21 全量复核）

本节**推翻**本文前面三处结论。全部证据来自 `scripts/itp_site_table.py`（只读 ROM，自带自证闸门）。

### 11.0 函数拓扑（本文原文漏了一半）

```
InitTextPrinter            0x08002C68   ← 本体：strh r2,[r0,#22] → win[0x16]=TILE_BASE
  ├─ 0x08002CDE  ← 函数 0x08002CC0（入口，传 TB=0/a4=0/a5=0，随后自己 0x6226 存 text）
  ├─ 0x08002D10  ← 转发器 0x08002CFC   ★ 设置页 22 块走这里（运行时 lr=0x08002D15 实证）
  ├─ 0x08002D52  ← 主包装 0x08002D1C（60 个调用点，多出「tm0 清 2 个 tile + win[0x18]=4」）
  └─ 0x080030FA  ← 另一处
```

- `0x08002CFC` 与 `0x08002D1C` 都只做 `lsls/lsrs #16`（r2 截 u16）、`#24`（r3、a5 截 u8），
  **都不改 tileBase 的值** ⇒ 调用点的 `r2` 就是最终 `win[0x16]`。
- 🔴 本文原文只扫了 `0x08002D1C`，**漏掉 39 个调用点的 `0x08002CFC`**，这才是取值集合被低估的根因。

### 11.1 TILE_BASE 真实取值集合（推翻 §三 的「3 个常量」）

| 目标 | 调用点数 | TILE_BASE 取值 |
|---|---|---|
| `0x08002D1C`（主包装） | 60 | `2`, `144`, **`752`**(×14，同为 0x80A76xx 族)，其余 22 点为运行期取值 |
| `0x08002CFC`（纯转发器） | 39 | `1`, `32`, `64`, `96`, `128`, `160`, `168`, `256`, `400`, `440`, `656`, `704` + 7 点运行期 |
| `0x08002C68`（本体） | 4 | `0` 与运行期 |

- 🔴 **`0xBC` 的真值是 752**：现场是 `movs r2,#188` + `lsls r2,r2,#2`。
  `scripts/scan_inittp_sites.py` 的回溯正则是 `^(movs|mov|adds|subs|ldr|adr)\s+r2\b`，
  **不含 `lsls`** ⇒ 它会停在 `movs` 上报 188。**该脚本的 TILE_BASE 列一律不可信，以 `itp_site_table.py` 为准。**
- 「Thumb `movs r2,#imm8` ⇒ TILE_BASE ≤ 255」（§三 末尾）**已废**：`lsls` 链最高到 704，
  且 39 点里的 tile base 有从结构体 `ldrb` 读来的（运行期 0..255），不限于立即数。

### 11.2 🔴🔴 硬约束：`TILE_BASE + 号 < 1024`（**选型文档的容量账因此失效**）

`win[0x16]` 是**该 BG 层 tile 空间内的索引**：主包装 `0x08002D64` 算
`addr = tpl->tileData + (TILE_BASE + TILE_OFFSET)*32`，落点 `tileData = 0x06008000`
（= char block 2 起，覆盖 char block 2+3 = **32 KB = 1024 个 4bpp tile**）。
tilemap 项是 **10 位** ⇒ 值域硬上限 1023。

⇒ **每个窗口能用的号数 = `1024 - TILE_BASE`：**

| TILE_BASE | 预算（格） | | TILE_BASE | 预算（格） |
|---|---|---|---|---|
| 1 | 1023 | | 400 | 624 |
| 32 | 992 | | 440 | 584 |
| 96 | 928 | | 656 | 368 |
| 168 | 856 | | **704** | **320** |
| 256 | 768 | | **752** | **272** |

🔴 **对「屏幕格定号（方案 S）」的直接后果**：S 的号 = `(a5+ty)*32 + (a4+tx)` 是**绝对**屏幕格，
最大 639。要装进窗口预算，必须 `TILE_BASE ≤ 384`。
而实测存在 `TILE_BASE = 752` 的窗口（`0x80A7634` 族，`a4=1, a5=15`）——
`(15+0)*32+1 = 481 > 272` ⇒ **第一个字就溢出**，会绕回低号，与同层其它窗口互撞。
⇒ **S 必须带「装得下才用」的判据**（见 `docs/20260921_定号重构_三方案离线判据与选型.md` §十一）。

### 11.3 a4/a5 的语义（本文原文没写）

`InitTextPrinter` 里：`strb r3,[r0,#26]` ⇒ `win[0x1A] = a4`（**X，列**）；
`strb r9,[r0,#28]` ⇒ `win[0x1C] = a5`（**Y，行**）；`win[0x1B] = win[0x1D] = 0`（游标复位）。

- **设置页实测**（同一 `win=0x0202E658`、`tb=1`，走 `0x08002CFC`）：
  `a4 ∈ {4,15,18,19,20,22,23}`、`a5 ∈ {1,5,7,9,11,13,15,17}` —— 8 行 × 7 列，**逐块不同** ⇒ 格定号能区分。
- ⚠ 但**并非所有调用点**都给有意义的屏幕格：`0x8029C84` 给 `(a4=19, a5=55)`、
  `0x802B6C8` 给 `(25, 57)`、`0x802D81E` 给 `(19, 35)` —— `Y > 20` 超出 20 行屏幕。
  这类调用点的游标是**事后**另设的，`InitTextPrinter` 时的 a4/a5 只是初值。
  ⇒ 定号方案**不能假设 a4/a5 一定是有意义的屏幕格**（S 的溢出回退正好覆盖这一类）。
