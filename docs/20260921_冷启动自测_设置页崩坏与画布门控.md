## 0. 方法论纠正（用户指令，已采纳）

| | 错误做法（本轮之前） | 正确做法（本轮起） |
|---|---|---|
| 加载方式 | `mGBA.exe -g -t <rom>.ss1 <rom>` | `mGBA.exe -g <rom>`（`-t` 一律不加） |
| 状态来源 | **savestate 内存快照** | **电池存档 `.sav`**（游戏自己写的那种） |
| 问题 | `.ss1` 是 **7月18日**、`.ss6` 是 **8月18日** 的 RAM 快照 ⇒ 里面是 v8~v12 时代的 EWRAM/VRAM/IO。新 ROM 的初始化根本没跑过 ⇒ 从快照读到的 RAM 值（分配器状态、窗口表…）**与当前构建无关** | 冷启动让**当前 ROM 自己**跑完全部初始化；`继续游戏` 从 `.sav` 恢复的只是游戏进度（队伍/地图/道具），不是机器状态 |

**结论**：凡是要判断「当前构建的运行时行为」，**必须冷启动**。savestate 只允许用于「确认某段代码在某个画面下会被调用」这类与 RAM 初值无关的观察。

## 2. 画布门控真值（单步跟踪，寄存器级）

`InitTextPrinter_hook_C` 的机器码（`hook/out/game.bin`，force-thumb，--adjust-vma=0x08800000）：

```
8800080 push {r4,lr}
8800082 movs r4,r0              ; r4 = win
8800084 movs r0,r1              ; r0 = tile_base（默认返回值）   ← 断点唯一的可靠落点
8800086 cmp  r4,#0
8800088 beq  0x88000bc          ; win==0 -> return
880008a..9c r3 = *(u32*)win     ; tpl = win_template(win)
880009e beq  0x88000bc          ; tpl==0  -> return
88000a0..b2 r2 = *(u32*)(tpl+0x0C)   ; ← tileData
88000b4 movs r1,#192 / lsls r1,#19   ; 0x06000000
88000b8 cmp  r2,r1
88000ba beq  0x88000c2          ; tileData == 0x06000000 -> 门控 A 过
88000bc pop {r4}; pop {r1}; bx r1    ; 统一出口 = 返回官方 tile_base
88000c2 ldrb r3,[r3,#9]         ; tm = tpl->textMode
88000c6 bhi  0x88000bc          ; tm > 1 -> return（门控 B）
88000ce bl   0x88000c58         ; chs_canvas_base_for(win)
```

🔴 **mGBA 的断点只在「翻译块起点」命中**：`0x088000A0` / `0x0880009E` 此类块内地址
**装了也永不触发**（曾据此误判「没走到」）。→ 改用**单步跟踪**（`s`）从 `0x08800084` 起步。

单步实测（`.tmp/hp2d.out`，44 步）：

```
step 12  PC=0x0880009E   r3 = 0x081BB874   ← tpl（非 0，在 ROM 里）
step 13  PC=0x088000A0                        ← 走了 fallthrough，tpl ≠ 0
step 23  PC=0x088000B4   r2 = 0x06008000   ← ★ tileData 真值
step 26  PC=0x088000BA                        ← cmp r2,r1；r1 = 0x06000000
step 27  PC=0x088000BC                        ← ★ beq 未跳 ⇒ 直接 return tile_base
```

其余寄存器（174 次命中全部一致）：
```
r0 = win = 0x0202E658（同一实例）
r1 = tile_base = 1        ← 官方请求的基址
r2 = cur_x（0x0f/0x13/0x16/0x17/0x18…）
r3 = cur_y（5/7/8/9）
```

### 静态核验（零内存依赖，铁证）
`tpl = 0x081BB874` 是 **ROM 里的静态模板**，`roms/origin` 与 `roms/outputs` 在该处**逐字节相同**：
```
@0x1bb874: 0002 0f00 0f01 0f08 0301 0000 0080 0006 0078 0006
           tileData = 0x06008000  (charBase = 2)
           tilemap  = 0x06007800
           tpl[9]   = 0x01        (textMode 1 → 门控 B 本来会过)
```
⇒ **门控 A 对这条主体路径恒不成立**：`0x06008000 != 0x06000000` ⇒ 在 `0x088000BA` 跳走。
⇒ `chs_canvas_base_for` **一次都没被调用** ⇒ **v21「窗口私有画布」对主文本窗口是死代码**。

### ⚠️ 但「恒假」说过头了 —— 需要修正
扫模板表区 `0x081BB000..0x081BC000`（u32 对齐滑动）：
```
tileData=0x06000000 (charBase=0)  ×6   ← 这些模板【能】过门控 A
tileData=0x06008000 (charBase=2)  ×5   ← 实测命中的 0x081BB874 属于这类
tileData=0x06004000 (charBase=1)  ×1
```
所以准确说法是：
**门控不是恒假，而是「只对 6 个 charBase=0 的模板成立」；实测 174 次调用全部走 charBase=2 模板 ⇒ 0 次通过。**
而那 6 个能过的模板，其 charBase=0 区间正是**压在美术资产上**的区间（见 `verify_pool_safety.py` 的结论）
⇒ 就算门控过了，也是往回踩「撞 UI」。

### 结论
`v21 窗口私有画布` 目前是**未激活的架构**：主路径进不去，能进的那条路会撞美术。
这解释了为什么「设置页」这种**一屏上百个中文字**的界面必然崩 ——
中文仍然全部写进官方共享画布（`tileData=0x06008000`，号从 `win[0x16]=1` 起），
字模互相覆盖，最终塌成几种字形的重复。
