## 〇、结论（一句话）

**选「屏幕格定号」`tile = TILE_BASE + cell(ty, tx)`（cell = `(a5+ty)×32 + (a4+tx)`，跳过箭头保留号）。**

> 🔴 **2026-09-21 复核修订（3 处）**：`cell` 的 stride 是 **32 不是 30**（`GetCursorTilemapPointer 0x08003708` 逐指令）；
> 行/列的真正来源是 **`a4/a5`（调用点给的屏幕格坐标，被 `InitTextPrinter` 写进 `win[0x1A]/[0x1C]`）**，
> 而不是 `win[0x1B]/[0x1D]`（那两个每次 `InitTextPrinter` 都复位成 0）；
> 且 `TILE_BASE` 存在 **752** 这种大值 ⇒ **本文 §五.3 的容量账（790/1024）无效**，必须加「装得下才用」的判据。
> 详见 **§十 / §十一**。

- 22 块设置页场景：**0 像素差异**（现状方案 4977 像素差异）
- 满屏 200 字全不同：**0 像素差异**，最大号 **602**（`charBase` 区共 1024 号）
- **保持 12px 步进**（不动版式）、**零分配器 / 零账本 / 零水位 / 零避让带**
- 而「严格复刻官方按字形索引定号」（下面方案 A）**在 11×11 字形上实测不成立**：
  必须退化成 16px 步进，且满屏要 800 号、溢出容限极窄。

## 三、实测结果（零推测）

### 场景 ①：设置页形态（22 块共享一个 TILE_BASE）

| 方案 | 差异像素 | 用号数 | 最大号 | 溢出 |
|---|---|---|---|---|
| **P 现状(位置定号)** | **4977** | **18** | 18 | 0 |
| **A 字形槽定号** | 0 | 200 | 200 | 0 |
| **S 屏幕格定号** | **0** | 230 | 621 | 0 |

🔴 **P 的 4977 像素差异 +「73 个字只用了 18 个号」正是设置页塌陷的量化复现**：
22 个块各自从号 0 起画，后写覆盖先写，屏幕上只剩最后写进去的少数几个字形。
与 `docs/20260921_真问题定位_位置定号vs字形索引定号.md` §1.5 的 VRAM 实证（14 个非零 tile / 7 个字）**方向一致、量级一致**。

### 场景 ②：满屏 200 字全不同

| 方案 | 差异像素 | 用号数 | 最大号 | 溢出 |
|---|---|---|---|---|
| **S 屏幕格定号** | **0** | 600 | 602 | 0 |
| A 字形槽 cap=128 | 3951 | 503 | 512 | **288** |
| A 字形槽 cap=256 | 0 | 791 | 800 | 0 |

🔴 **A 的溢出是致命的**：cap=128 时溢出 288 次，画面立刻崩（3951 px）。
A 要么把容量开到 256 槽 / 800 号（只剩 224 号余量），要么崩。

## 四、为什么「严格按字形索引定号」在 11×11 字形上不成立

官方的 `tile = TILE_BASE + 2c` 能成立，前提是**官方字形宽 8 像素**——正好等于一个 tile。
所以「一个字形 = 2 个号（竖向一对）」，且**图像在 tile 网格上是天然对齐的**。

我们的中文字形**墨宽 11 像素 > 8**，必须跨 2 个 tile 列。于是：

1. **相位问题**：12px 步进下，串内第 n 个字落在像素 `12n`，相位在 0/4 之间交替。
   同一个 code 出现在相位 0 与相位 4 时，**需要两份不同偏移的字模** ⇒ 一个 code 要 2 个槽。
2. **共享问题**：现状靠「相邻字共享尾列」（第 n 字的尾列 = 第 n+1 字的头列，
   同一个 tile 号）把每字压到 2~4 号。而**按 code 定号时，相邻两个字是不同 code ⇒ 不可能同号**
   ⇒ 尾列无法共享 ⇒ **每字被迫独占 2 个 tile 列 = 16px 步进**。
3. **容量问题**：于是号需求 = `4 号 × code 数 × 相位变体数`，最坏 8 号/字。
   满屏 200 字实测 791 号（cap=256 时），1024 号空间只剩 233 号余量。

⇒ **「按字形索引定号」与「12px 紧凑步进」在结构上互斥。**
取前者就要接受 16px 步进 + 800 号占用；取后者就必须放弃 code 级共享。

**S 是第三条路**：不按 code、也不按「块内线性偏移」，而是按**字形最终落在屏幕哪一格**定号。
同一格天然共享（重画零消耗）；不同格天然不同号（不覆盖）。**既保留了 12px 步进，又拿到了不覆盖。**

## 五、S 的机制与容量账

### 5.1 公式

```
cell(ty, tx) = ty × 30 + tx          /* ty ∈ [0,20)，tx ∈ [0,30) */
tile         = TILE_BASE + cell(ty, tx)
下半 tile    = TILE_BASE + cell(ty + 1, tx)     /* 同一函数再算一次，不是简单 +1 */
尾列 tile    = TILE_BASE + cell(ty, tx + 1)
```

- `ty`/`tx` = 窗口内 tile 行/列（`win[0x1C]`/`win[0x1B]` 一族的当前值）
- **纯函数**：不查表、不记账、不扫描、不设水位
- **同格重画零消耗**：同一格永远同一个号 ⇒ 重画只是覆盖同样的像素
- **多块不覆盖**：22 个块在屏幕上位置不同 ⇒ 格不同 ⇒ 号不同

### 5.2 保留号

引擎换行箭头固定写在 `TILE_BASE + 0xFE`（243 与 244 号之间）。
S 的号集是**稠密**的，必须跳过 254/255：

```
n = cell(ty, tx);
if (n >= 0xFE) n += 2;      /* 单射且单调，跳过 254/255 */
tile = TILE_BASE + n;
```

⚠️ **上下半必须走同一个函数**（不是 `t0 + 30`）。首版判据正是因为这个出现过 68 像素差异：
`t0` 在阈值下方不位移、`t0+30` 在阈值上方要位移 ⇒ 上下半对不上。已修正，现为 0 差异。

### 5.3 容量账

| 项 | 值 |
|---|---|
| 号空间 | `charBase` 起 32 KB = **1024 号**（0..1023） |
| 屏幕格数 | 30 列 × 20 行 = 600 |
| S 最大号 | 601（跳过 254/255 后）+ `TILE_BASE` |
| `TILE_BASE` 实测/官方取值 | 官方常量 `{0x28, 0x90, 0xBC}`；本轮采样为个位小值 |
| 最坏占用 | 188 + 602 = **790 / 1024** ✅ |
| 溢出 | **不可能**（号需求 = 屏幕格数，与文本长度无关） |

> 🔴 **上表最后三行已于 2026-09-21 推翻**：`TILE_BASE` 实测最高到 **752**（`0x80A76xx` 族，14 个调用点），
> 另有 704 / 656 / 440 / 400。硬的约束是 **`TILE_BASE + 号 < 1024`**（tilemap 项 10 位，层内只有 1024 个 tile），
> 所以**每个窗口的号预算是 `1024 - TILE_BASE`**，`TILE_BASE=752` 时只有 **272 格**，
> 而 `a5=15` 的窗口第一个字的格号就是 `15×32+1 = 481` ⇒ **溢出**。
> ⇒ S 必须配「**装得下才用 S，装不下退回 `TILE_OFFSET`**」的判据。见 §十一。

🔴 **关键：号需求有上界 = 屏幕能容纳的格数，与「同屏多少字」解耦。**
这正是用户关心的「涨到 1000 怎么办」的答案：**不用怎么办，号用量根本不由字数决定。**

### 5.4 S 严格优于 P（跨窗口情形）

现状 P 下，**任何两个同 `TILE_BASE` 的块都从号 0 起画**，所以只要两块同屏就必然互相覆盖。
S 下只有「两个块占据同一格」才冲突，而那本来在画面上就是同一个位置。

⇒ **S 在每一种情形下都不比 P 差，且覆盖了 P 覆盖不到的绝大部分情形。**

## 七、实施前必须核实的 2 件事 —— ✅ 已闭合（2026-09-21）

### 核实① `ty` 取哪个字段、换行时谁变 —— ✅ 已闭，且结论比预期强

`GetCursorTilemapPointer 0x08003708`（逐指令）：

```
tilemap 格 = (win[0x1C] + win[0x1D]) * 32 + (win[0x1A] + win[0x1B])
                └─ 行 ────────┘            └─ 列 ────────┘
```

- **stride = 32**（不是 30）；`UpdateTilemap 0x080036DC` 只写 2 项，第二项 `adds r0,#64`
  （= 32 个 u16 = **下一行**），与 stride 32 自洽。
- `0x1A/0x1C` = 窗口起点（**由 `InitTextPrinter` 从 a4/a5 赋值**，见下），`0x1B/0x1D` = 游标。
- 🔴 **换行不改行起点，只推游标**：`PrintNextChar` 跳转表（基址 `0x08003324`，注意 `ldr r1,[pc,#8]`
  载入的是**指针**）里 `FE → win[4] == 6`，该分支（`0x08002DF4` / `0x08002E60`）执行
  **`win[0x1B] = 0`；`win[0x1D] += 2`** ⇒ 一文本行 = **2 个 tile 行**（8×16 字形），`0x1C` 不动。
- 🔴 **`InitTextPrinter 0x08002C68` 每次都复位游标**：`win[0x1B]=0`、`win[0x1D]=0`、`win[0x18]=0`、`win[0x04]=1`，
  同时 `win[0x1A] = a4`、`win[0x1C] = a5`。
  ⇒ **引擎游标与 `TILE_OFFSET` 一样是「每块复位」量**，单靠 `0x1B/0x1D` 定号救不了多块；
  **块基准必须取 a4/a5**。

### 核实② 箭头保留号 0xFE 的真值 —— ✅ 已闭

- `0x08003E64`：`movs r2,#254; adds r0,r2,#0; ldrh r1,[r5,#22]; adds r0,r0,r1`
  ⇒ 箭头号 = **`TILE_BASE + 0xFE`**；font 0/3 分支 `0x08003E70` 同为 `+0xFE`。
  表基址 **`0x08003E48`**（同样是 `ldr` 载入指针），8 项映射：
  `{0x3E48, 0x3E64, 0x3E70, 0x3E70, 0x3E64, 0x3E70, 0x3E70, 0x3E70}`。
- **全 ROM `UpdateTilemap` 只有 7 个调用点**：
  `0x080034D6 / 0x0800355A / 0x08003598 / 0x080035BC / 0x080035DC / 0x08003600`（六个文字处理器，全走字段）
  + `0x08003EAE`（箭头）⇒ **固定号只有箭头一处**；另有 `game.h` 记录的
  **`0x1E8..0x1FF`（Dex 编号球 / Summary A·B 固定 UI 图标区）**。
  ⇒ S 的稠密号集**只需跳过 254/255**（图标区 0x1E8..0x1FF 在 11×11 屏幕上只可能被 TB≥488 的窗口触及）。

### 核实③（新发现，原计划外）🔴🔴 `TILE_BASE + 号 < 1024` 是硬约束

扫描全部 **99 个调用点**（`0x08002D1C` 60 个 + `0x08002CFC` 39 个）后发现：

- `TILE_BASE` 实测集合 = `{1, 32, 64, 96, 128, 160, 168, 256, 400, 440, 656, 704, 752}` + 运行期取值。
  （本文原以为只有 `{0x28, 0x90, 0xBC}`；`0xBC` 那族的**真值是 752**，
  `movs r2,#0xBC` 紧跟 `lsls r2,r2,#2`，`scripts/scan_inittp_sites.py` 的回溯正则漏了 `lsls`。）
- 层的 tile 空间 = `tileData 0x06008000` 起 **32 KB = 1024 个 tile**，tilemap 项 **10 位**
  ⇒ **`TILE_BASE + 号 ≤ 1023`，窗口预算 = `1024 - TILE_BASE`**（752 → **272 格**）。
- `TILE_BASE=752` 的窗口实测 `a4=1, a5=15` ⇒ 绝对格号起点 `15×32+1 = 481 > 272` ⇒ **第一个字就溢出**。
- ⚠ 另有调用点给 `a5 = 55 / 57 / 35`（超出 20 行屏幕）⇒ **不能假设 a4/a5 一定是有意义的屏幕格**。

## 十、实施补充判据（由核实③ 导出）

```
S 的号：n = (a5 + ty) * 32 + (a4 + tx)          /* 绝对屏幕格 */
装得下  ⇔  TILE_BASE + n <= 1023                /* ← 硬约束 */
装不下  ⇒  退回现状的 TILE_BASE + TILE_OFFSET   /* 该窗口行为与今天完全一致，不会变差 */
```

- **不退步保证**：退回分支的行为 = 现状 P。所以 S **在任何窗口上都不会比今天差**。
- 用户痛点（设置页，`tb=1`、22 块同 `win`）的预算 1023，绝对格号 ≤ 601 ⇒ **一定走 S**。
  ⇒ 修复目标场景 100% 命中。
- 若将来发现「大 `TILE_BASE` + 同窗多块」的窗口，可把退回分支升级为
  `n = ((a4+tx) + (a5+ty)*32) % (1024 - TILE_BASE)`（对预算取模，纯函数、零账本）。
  **当前不需要**（尚无实证场景），留作记录。

## 十一、残余风险（2026-09-21 更新）

| 风险 | 现状 P | S（带 §十 判据） |
|---|---|---|
| 同窗多块互相覆盖 | **必然发生**（设置页 22 块全撞） | **消除**（预算足够） |
| 大 `TILE_BASE` 窗口（752/704/656…） | 无问题（单块） | **退回 P ⇒ 仍旧无问题** |
| 同屏多窗、但恰好给同一 `(a4,a5)` | 必然发生 | 仍会撞（残余，未见实例） |
| a4/a5 非屏幕格（a5=55/57/35）的调用点 | 无问题 | 溢出判据触发 ⇒ **退回 P，无问题** |
| 版式 | 12px 步进 | **12px 步进不变** |
| 分配器 / 水位 / 避让带 | — | **零** |

## 十二、附：为什么另两条不选

- **P 维持不动**：设置页崩坏就是它造成的，已量化（4977 px）。
- **A 严格按字形索引**：0 差异但代价是 **16px 步进**（版式变松）+ 满屏 791 号 + 溢出即崩。
  与用户「尽量走 11×11、不要撞 UI」的目标相比，S 在保持版式的前提下达到同样效果。
