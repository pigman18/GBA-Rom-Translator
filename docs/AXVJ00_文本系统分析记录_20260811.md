### 1.2 mGBA GDB 能力（实测）

- mGBA.exe（Qt 版）`-g` 参数开 GDB stub，监听 `127.0.0.1:2345`（源码：`src/debugger/debugger.c` 固定 2345）。
- **单连接**：断开后 stub 不重新 accept，需重启 mGBA。
- **断点命中后连接保持**：`Z0,addr,2` 设软断点 → `c` → 命中收到 `S05`/`S02`，之后可继续 `g`/`m` 交互（`0x080000D0` 命中验证成功）。
- **单步 `s` 保持连接**（验证成功，PC 前进）。
- **`c` 长跑会断连**（`ConnectionResetError 10054`），无法"继续→等断点"式长跑。
- **写内存 `M` 对 ROM 镜像有效**：改 `0x081CBB0C` 写入 `69 6B 6F 79 FF` 并读回成功。
- **读 VRAM 不可靠**：`m 0x060xxxxx` 返回全 0（文本/图形验证受阻）。

### 1.3 游戏运行状态（实测）

## 二、重大教训（本会话最关键的失败）

### 2.1 误判"ROM 加密"，浪费约 2-3 小时

- **错误**：一开始用 **ARM 模式**反汇编 `0x08002000+`，看到乱码 + 高熵，误判为"R/S 1.0 防拷种子加密 ROM"。
- **真相**：GBA 主代码是 **THUMB 模式**。用 `CS_MODE_THUMB` 反汇编 `0x08004000` 得到正常的 `push {r4-r7,lr}` 等序言，全代码区 THUMB 密度 50-98%，**ROM 完全未加密、可静态分析**。
- **连锁浪费**：为"绕过加密"尝试了 mGBA GDB、Lua dump、离线解密资料搜索，全部白费。

### 2.2 反复误判候选函数为"文本引擎"

以下地址曾被认为与文本相关，**后证实不是**（或无法证实），不应继续采信：

- `0x0809CD6C` 族（`0x0809C9BC/CF10/CFA0/D03C`）：写 VRAM `0x06006800`、处理 FF/FD/FE → 判为**精灵/战斗 UI 渲染**，主菜单/标题不调用；引用的 `0x083A4A44`/`0x083A555C` 是精灵属性表，非 charmap。
- `0x080F31B8`：`mov pc,r0` 跳转表 + FC/FE/FF 分派 → 判为精灵对象处理器。
- `0x080AE0D0`：处理 0xD8/0xDA/0x90 → 判为战斗个体值相关。
- `0x0813DCF4` 族（`0x0813C55C/3DCxx`）：`div 100/div 10` → 判为数字→字符串格式化。
- `0x08145470/08145698`：`cmp #0x19/0x3d/0x61` → 是数据表反汇编伪指令。
- `0x081B0344` 族：DMA 传输，非文本。

### 2.3 方法论失序

- 正确顺序应为：查资料 → 静态分析 → 动态分析 → 汇总 → 验证 → 总结。
- 实际：先做了大量盲扫（字体/LZ77/指针/函数特征），后在 GDB 动态上反复卡壳（断连、VRAM 读 0、按键无效），**静态核心定位（charmap 表、8×8 字库、PrintChar 主函数）始终未完成**。
- 用户在 `0x0809CD6C` 断点 60-100s 不命中后指出：标题画面不调用文本打印，验证应针对主菜单/对话。

### 2.4 另一个概念错误：日版"12px"字库

- 误把本工程中文侧载字库的 **12px advance** 当成日版原版字体，反复搜索"12×12 瓦片"。
- **日版 R/S 字形是标准 8×8 瓦片（4bpp，0x20 B/tile），全角假名/汉字占 2 tile**。
