## 2. 根因（四个，都是算法级）

### R1 句读标点全是汉字残片

`scripts/build_chinese_font.py:274-311` 按**整张 charmap 顺序**填每个槽，
Sym 槽 `slot_size=576`（9×64B）被 `buf[:576]` 截断 → 槽里是「啊/阿/埃/挨」的前半。
渲染端 `hook/src/text/text_translter.c:37-49` 按 64B/字取址，于是
`0x36–0x3E` 九个码位全画成汉字残片：`！`(0x3C) 画的是「挨」左半，形似 `]`。

> 结论：不是 charmap 映射错，是字库槽内容错位 + 读写步长不一致。

### R2 「一/二/三」不居中

`bdf_to_ink`（`scripts/build_chinese_font.py:121-204`）只算墨迹 bbox，然后从
`(min_x,min_y)` 贴到 ink `(0,0)`；`font_ascent` / `bbx_y` 两个形参**全函数未使用**。
所有字形被"顶对齐"：「一」的墨迹在 BDF 第 8 行，被贴到槽内第 3 行（应约第 10 行）。

### R3 名字旁路只改「主读点」

`plan_struct_name_ptr` 只 patch `_find_name_copy_sites` 认到的一处，
其余把 `base+idx*stride+name_off` 当字符串读的点全部漏掉：

- 训练家个人名 `0x0800CC98`（扫 FF 累加长度）→ 现在读到 u32 指针字节
- 图鉴分类名 `0x0808C1D6` / `0x0808D590`（直接读 `0x0838474C` 绘制）→ 仍读旧表
- `base+4` 字面量 `0x0811C690`、`0x083DBF4` 未被重写 → 仍读旧表（不损坏，只是漏译）

### R4 渲染层没有宽度概念

`text_render.c:328-350` 只按 `gx < advance` 推进，`col` 不设上限，从不读窗口模板宽度。
任何超长文本必然画出窗口；招式名 stride 扩到 32（可放 7 字）而屏幕只够 4 字。

## 5. 图鉴分类名两处绘制点（已反汇编确认，待实现）

`たねポケモン` 仍是日文，因为 `trampoline_name_ptrs` 只把 **getter**
`0x0808D830` 挂了钩，而真正画分类名的两处是**直接读字段**：

**A. 图鉴条目页 `0x0808C008`**
```
0808C1CE  ldrh r1,[r2,#0]        ; r1 = idx
0808C1D0  lsls r0,r1,#3
0808C1D2  subs r0,r0,r1
0808C1D4  lsls r0,r0,#2          ; r0 = idx*28
0808C1D6  ldr  r4,=0x0838474C    ; = base+6（名字字段）
0808C1D8  adds r0,r0,r4          ; ← 名字地址
0808C1DA  movs r1,#13            ; 右对齐列
0808C1DC  movs r2,#5
0808C1DE  bl   0x0808DD60        ; 画字
```

**B. 另一个图鉴页 `0x0808D4EC`**
```
0808D58A  lsls r4,r5,#3          ; r5 = idx
0808D58C  subs r4,r4,r5
0808D58E  lsls r4,r4,#2          ; r4 = idx*28
0808D590  ldr  r6,=0x0838474C
0808D592  adds r5,r4,r6          ; ← 名字地址
0808D594  adds r0,r5,#0
0808D59A  bl   0x0808DD60
```

### 修法（与对战塔「折址」同一套）

新表保持 **stride 28**，把 6 字节名字字段 `+6..+11` 换成
`u32 指针 + FF`（指针 4B + `0xFF` 截断，旧的字节扫描读者在此停下）：

| 站点 | 原字节 | 改成 | 语义 |
|---|---|---|---|
| `0x0808C1D8` | `adds r0,r0,r4` | `ldr r0,[r0,r4]` | 地址 = idx*28 + (base+6)，解引用得指针 |
| `0x0808D592` | `adds r5,r4,r6` | `ldr r5,[r4,r6]` | 同上 |

两条都是 2 字节原地替换、总长不变，不需要跳板：

```
0808C1D8  00 19  →  00 58   (ldr r0,[r0,r4]，Rn=r0 Rm=r4)
0808D592  a5 19  →  ??      (ldr r5,[r4,r6]，需按编码算出)
```

### 前置冲突已排除（2026-11-11 09:46 复核）

`0x0808D85E` 的 literal 实测 **`0x0838474C`（= base+6）**，而它后面那条是
`ldrh r0,[r1,#6]`，`r1 = (base+6) + idx*28` —— 实际读的是
**`entry+12`**（身高 u16），不是 `entry+6`。所以 `entry+6` 确实只是名字区，
折址方案不与身高/体重冲突。

仍需审计的其余 literal（同一个 `0x0838474C` 的引用点）：

```
0x0808C1D6  图鉴条目页 画分类名     ← 要挂钩（A）
0x0808C244  同函数，读 entry+16.. 数值
0x0808CF88  / 0x0808D028            数值
0x0808D590  另一图鉴页 画分类名     ← 要挂钩（B）
0x0808D5E4                          ?
0x0808D86C  身高 getter（读 entry+12，改表后仍正确）
0x0808D880                          ?
```

折址改法本身成立（`+6..+9` = u32 指针、`+10` = `FF`），但会改变**所有**读
`entry+6` 的文本点行为；因此要么把上表 7 处全部审计一遍，要么改走
「两个绘制点 `bl` 到 stub（入参 idx 已在 `r1`/`r5`）」这条不动旧表的路。
**倾向后者**：不碰 386 条旧数据，风险只在两条 4 字节指令。

## 7. #7 图鉴分类名：已修（2026-11-11 10:45）

### 结论

图鉴条目页的分类名现在出中文（`种子` + 未译后缀 `ポケモン`）；
身高/体重/说明指针等字段逐字节未变；67 帧 bot 对照无新增回归。

### 上一版「整屏乱码」的真因（不是方案错，是配置错）

`texts.json` 的 `图鉴分类名` 写的是 `start=0x384746 / name_offset=6`，
**真实几何是 `start=0x38474C / name_offset=0`**——旧配置用「表基址前移 6 字节 +
名字偏移 6」凑出同一条名字地址，读名字没错，但一旦按「表项 +0..+27」克隆镜像表，
整个 28 字节窗口就**前移了 6 字节**：镜像里 `+6` 位置放的是原 `+0` 的名字字节，
而身高读点仍按 `+6` 取 → 读到名字残渣 → 实机整屏乱码（10:08 那张截图）。

⇒ 教训改写：不是「共享 literal 不能改」，而是**改字面量之前必须确认克隆窗口的起点**。
本次把几何改正后，共享 literal 指向镜像表反而变成正确行为：
镜像除名字区外与原表逐字节一致，数值读点照旧。

### 改动

| 位置 | 改动 |
|---|---|
| `texts.json` `图鉴分类名` | `start 0x384746→0x38474C`、`end 0x38717D→0x387183`、`name_offset 6→0`、`draw_sites false→true` |
| `src/meowth/struct_trampoline.py` | 新增 `_mov_reg_after()`：站点若在 `adds rD,rLit,rIdx` 之后还有 `adds rX,rD,#0`（把名字地址搬进参数寄存器），就改那一条为 `ldr rX,[rD]`，**不动 rD**——图鉴另一页 bl 之后还要用 r5 读 `entry+6/+8` 与 `+0xC` 说明指针，改 adds 会把 r5 变成字符串指针 |

产物字节（`roms/outputs/POKEMON_RUBY_AXVJ00_translated.gba`）：

```
0808C1D8  00 19 → 20 58    adds r0,r0,r4 → ldr r0,[r0,r4]      （条目页）
0808D594  28 1C → 28 68    adds r0,r5,#0 → ldr r0,[r5]         （另一图鉴页，r5 保留）
0808C244 / 0808D5E4        literal 0x0838474C → 0x09ECE1B4（镜像表，name@0）

## 8. 二次修正（2026-11-11 11:05）：说明回日文是我的改动造成的

### 8.1 图鉴说明变日文的真因（已修）

`图鉴分类名` 的表项 `+0x0C` 是**说明正文指针**。上一版（10:45）做法是「整表克隆到新区 +
改 literal」，克隆用的是**原盘字节** → 把 rows_writer 已经改好的 `+0x0C` 覆盖回旧值

说明指针由 rows 阶段原地改，两边不再打架。

证据：`0x384790`（idx=2 的 `+0x0C`）输出 = `0x094087B0`，指向 `f7 00 0d 70 …`（中文）；

### 8.2 分类名的显示机制（已查清的部分）

```

## 9. #8 / #9：图鉴列表「滚动红块」与「编号-名字错位」（2026-11-11 11:45）

两条都是**通用问题**，不是图鉴专属。下面每个数字都是实测（bot 逐帧 + VRAM/调色板/EWRAM dump）。

### 9.1 #8 滚动时的纯红实心块 = 整格填了 `WIN_COLOR_D`

实测（`bot/dex/*/translated` 滚动过渡帧，列表窗 x=130..232 / y=36..132）：

| 项 | 实测值 |
|---|---|
| 最差一帧红色像素数 | 326 |
| 红色像素的 RGB | 只有一种：`(255,0,0)` = 15bit `0x001F` |
| 该色在调色板的位置 | `bank15[2] = 0x001F`（bank15 = `0000 2529 001F 03E0 7C00 03FF …`，红/绿/蓝/青/黄/品红 正好占 index 2..7） |
| 行文本的 printer 字段 | `tm=3 fn=3 C/D/E = 01/0F/08` |
| 行 tilemap 表项 | 带 `palette=15` 位（`0xF15D` 这类） |
| 窗口真正的底色 | 来自下层 BG（bank0 `[0x0A] = 0x2F1F` 橙），**只有写 index 0 才透出来** |

⇒ 红块 = `blit_run()` 把「非墨像素」写成 `bg = WIN_COLOR_D` 的整格填充。
官方引擎只在**自己 8×8 字形位图内**用 bg，而这批窗口的 `D` 字段被游戏当
「阴影 / 红字色」用；定型帧看着没问题，是因为那条路径把 bg 压成了 0（透明）
——正是 `PcsPrint_Custom` 里「整块无墨 → bg 压 0」那段注释的由来；
滚动重绘走的是**另一半路径**，压 0 覆盖不到，于是整格红。

**通用规则**：12px 渲染器不能把 `WIN_COLOR_D` 当「窗口背景色」整格填。

**已落地（2026-11-11 12:05）**：`text_render.c` 的 `draw_glyph_tilemap()` 里
`bg = 0`（tm2 缓冲除外），`blit_run`/`clear_cols` 因此都写透明。验收：

| 项 | 修前 | 修后 |
|---|---|---|
| dex 窗内红色像素（最差帧） | 498 | **264 = origin 同帧值**（那 264 是 UI 本身的红） |
| dex 场景 fail 帧 | 73 | **19** |
| options 场景 | — | fail 0 |
| bag 场景 | fail 246 / 相似度 0.881875 | **完全一致**（同一批既有失败，非本次引入） |

剩下 19 个失败帧全在 `dex_scrollup*`，相似度 0.96+，属 #9 那一格错位。

### 9.2 #9 名字左移一格：一行其实是两条绘制路径

同一帧（`dex_open`）两侧 BG2（screenBase `0x06007000`）逐格 dump：

```
origin      ty10  列17=1FE 18=1FC 19=F143 20=F143 21=F149 | 23=F0D9 24=F0B9 …
translated  ty10  列17=1FE 18=1FC 19=F15D 20=F15F 21=F161 | 22=F163 23=F165 …
```

- 列 17..21 = `No` + 3 位编号，两侧**同位同宽**：编号不走 `PrintNextChar`（把日志挂到
  `PrintNextChar_Hook` 最顶端也抓不到它），是游戏自己把数字 tile 直写进 tilemap；
- 名字是 `AddTextPrinter` 打的**独立串**：抓到的字节是
  `f7 00 0d 24 f7 00 05 e3 ff`（2 字）、未捕获行 `fd 01 ff`，字段 `cx=24 ctx=0 cy=2,4,6…16`；
- 于是「对齐」= 一条游标被两条路径共用：先直绘编号，再用同一窗口游标打名字。
  我们落在列 22、origin 落在列 23 ⇒ **我们记账比原生少一格**，不是串里少了空格
  （串头就是 `F7`，没有空格字节）。
- 破折号同因：填充循环按「画到固定右边界」补 `-`，起点左移一格就多画一个 ——
  origin `185,193,…,217` 五个、我们 `177,…,217` 六个，**右端都停在 217**，
  正好证明「宽度是到边框的像素填充，不是固定字符数」。

**2026-11-11 13:40 追加：四个假设已用 bot 实测逐个否掉（不要再重试）**

| 假设 | 实测 | 结论 |
|---|---|---|
| 空格不推进 | `GetGlyph(code=0)` 返回 `width=8`，会推进；编号串 `a1 a1 a4 ff` 里没有空格 | ✗ |
| EOS 时给 `0x1B`(cursorX) +1 | 重跑后名字仍在 x=176，纹丝不动 | ✗ 游戏不读 0x1B |
| EOS 时给 `0x1A`(x) +1 | 同上，一动不动 | ✗ 游戏不读 0x1A |
| `0x1B` 改 1 基 + 绘制侧 -1（`win_col0`） | 名字仍在 176，且 dex fail 19→82 | ✗ |

**已钉死的结构事实**
- 一行是两次 print：编号串（IWRAM `0x03007DA4`，`cx=19`）+ 名字串（`0x03007D94`，`cx=22`）；
- 编号两侧逐像素相同；名字我们画在列 22、origin 在列 23；
- 游戏下发给名字 print 的 `0x1A` **就是 22**（探针直接读到的），而 origin 落在 23；
- 模板 `tpl[6]`（疑似 x）在列表行是 0、在条目页是 15；`tpl[8]` 恒为 3 —— 都不是当前游标。

⇒ 静态能做的到此为止：游戏代码两边完全相同，却给出 22 这个 x，
说明决定它的是运行期第三个变量。**下一步只能 GDB**：断在名字 print 之前
（`AddTextPrinter` 调用点），读调用栈与算 x 的那几条指令。
### 9.4 终局（2026-11-11 14:15）：根因是**我们自己的常量**

GDB 并入 bot 后（`bot/run.py --gdb InitTextPrinter`），一次就抓到了完整链：

```
栈 0x0202E9B8 代码地址:
  +08=0x080030C5   ← AddTextPrinterParameterized 返回
  +14=0x0806F18F   ← Menu_PrintText(0x0806F16C) 返回
  +24=0x0808ADDF   ← 图鉴列表行绘制(0x0808AD44) 返回
  +48=0x0808AA2D   ← 列表页循环
  +68=0x0808AF11
```

上层 `0x0808AA24` 就是 `movs r1,#0x17`（x=23）——**x 是硬编码常量，不是算出来的**。
两侧 ROM 该字节对比：

```
0808AA00  origin 17 21 | out 16 21      ← 5 处全被改成 0x16(22)
0808AA24  origin 17 21 | out 16 21
0808AB34  origin 17 21 | out 16 21
0808ABDA  origin 17 21 | out 16 21
0808ABFE  origin 17 21 | out 16 21
```

来源：`hook/game_addrs.asm` 的 `DEX_NAME_COLUMN equ 0x16`（`patches/pokedex.asm` 5 处
`.org` 统一引用它）。**原版是 0x17**，被改成 0x16 之后名字列与「编号起点19+3字符=22」
挤在一起，中间那一格空隙消失；破折号行按「画到右边界」补，起点左移一格就多画一个。

**修法**：`DEX_NAME_COLUMN equ 0x17`（改回原版值），重编重打包。

**验收（bot 像素实测，同一帧）**：

| | origin | 修前 | 修后 |
|---|---|---|---|
| 第 2 行名字墨迹起点 | **px 184**（列23） | px 176（列22） | **px 184** ✅ |
| 编号→名字之间 | 有空隙 | 紧贴 | 有空隙 ✅ |
| 破折号个数 | 5 | 6 | 5 ✅ |

`dex` 场景 `pass=20 / suspect=113 / fail=28`（修前 19）。
fail 增加的是 `g_garble` 的「1px 竖条残片」——12px 汉字的竖直笔画正好落在
8px tile 边界上被 `verify` 的 sliver 判据判掉（bbox 如 `[191,123,191,130]`，
`touches_origin_ink=true`），截图目视无残影。这条属验收判据对 12px 字体的误报，
单独跟进，不影响本 BUG 的结论。


### 9.3 可复用技巧：EWRAM 文本日志（本次用完已从 hook 移除）

- `game.bin` **没有 RAM 段**（`link/game.ld`）→ 所有 `static` 变量落 ROM、写不进去
  （`PrintGlyph()` 里早有这条注释）。所以调试状态也必须放 EWRAM：
  `LOG_BASE=0x0203F000`、`LOG_STATE=0x0203F7F0`（`[0]`=环写指针、`[4..7]`=上一条串指针、
  `[8]`=命中计数），槽 32B = 20B 串 + `tm/fn/C/D/E/cx/ctx/cy`；
- 只在 `WIN_TEXT_PTR` 变化时记一条（= 一次 print 一条），`bot` 的 `shot` 会落 `ram.bin`，
  离线按 `charmap` 解码。**注意** `burst` 帧不落五件套（只有 `shot` 有），
  要抓滚动瞬间得先给 `bot.lua` 的 burst 加「单帧 dump」。

## 10. #8/#9 之后又炸出来的两条（2026-11-11 15:00）：破折号与底色

用户实机反馈：「仅解决了红块，但是移动的时候其他 `----` 变成了日文乱码，
而且其他页面的文字存在着背景颜色不对」。两条都不是新功能引入的，
是 #8 那版 `bg = 0` 和更早的 stride 补丁留下的。

### 10.1 `----` 变成乱码：破折号填充循环被 stride 补丁一起放大了

图鉴列表「没有名字」的行画 5 个 `-`（0xAE）占位，代码在 0x0808ADC0：

```
0808ADC0 movs r4,#0
0808ADC2 movs r1,#0xAE      ← 占位字符
0808ADC4 mov  r2,sp
0808ADC6 adds r0,r2,r4
0808ADC8 strb r1,[r0]
...
0808ADD0 cmp  r4,#4         ← 循环 5 次
0808ADD2 bls  0x808adc4
```

名字表 stride 从 6 扩到 24 时，`write_plan._name_window_patches` 按
「`cmp + bls` 回跳 = 循环上限」一刀切，把**这一条也改成了 `cmp r4,#0x17`（23）**，
于是占位串变成 23 个 `-`：撑满整行、溢出到相邻行列（用户看到的「日文乱码」），
而且越界读到后面的 `FC 02` 控制码 → `WIN_COLOR_D` 被改成 2（红字色）→
**这就是 #8 红块的真因**（origin 侧 GDB 记录里 `C/D/E=1/2/8` 出现 0 次，我们 32 次）。

修法（`src/meowth/write_plan.py`）：
- 识别「`movs rX,#0xAE` + 其后循环体含 `strb rX,[rB,rI]`」= 破折号填充循环 → **不收进 caps**；
- 同一函数既放名字又放破折号时，`buf[old_stride-1]=FF` 是**破折号串的终止符** → 不放大。

字节验收：`0808ADD0 04→17` 与 `0808AD72 41→C1` 不再出现在产物里；
破折号回到 5 个（= origin），`dex` 名字行 D 不再变 2。

### 10.2 底色不对：底色要取**模板**的 D，不是运行时 `win[0x0D]`

`InitTextPrinter`（0x08002C68）开头把模板三色抄进 printer：

```
ldrb r4,[r5,#5] ; strb r4,[r0,#0x0c]   ← C
ldrb r4,[r5,#6] ; strb r4,[r0,#0x0d]   ← D（底色）
ldrb r4,[r5,#7] ; strb r4,[r0,#0x0e]   ← E
```

抄完之后 `win[0x0D]` 会被运行时改写（`FC 0C` 控制码、红字/高亮效果），
**模板是 ROM 常量、永不改变**。实测对照：

| 窗口 | 模板 | 模板 D | 运行时 win D | 真正底色 |
|---|---|---|---|---|
| 图鉴列表 | `0x081BB784` | **0** | 0 → 15 / 2（被改） | 0（透明，露出橙色 BG） |
| navigator 提示条 | `0x081BB46C` | **15** | 15 | 15（米色） |

所以 `chs_colors()` 改成 `*bg = tpl[6]`。三种历史方案逐一否掉：

| 方案 | dex | navigator | 结论 |
|---|---|---|---|
| `bg = 0`（#8 那版） | 正常 | 透出点阵（「背景颜色不对」） | ✗ |
| `bg = win[0x0D]` | 整片白（D=15） | 正常 | ✗ |
| 按 tile 池缓存首值 | 白 | — | ✗（池被多窗口复用） |
| tilemap 采样（众数 / 起点左一格） | 蓝 / 红 | — | ✗（采样到高亮行，时序不可靠） |
| **`bg = tpl[6]`** | **正常** | **正常** | ✓ |

### 10.3 验收

| 场景 | 结果 |
|---|---|
| dex | `pass=20 suspect=104 fail=37`；名字 px184、破折号 5 个、橙底无白块无红条 |
| navigator | 提示条米色底与周围一致（之前是点阵） |
| start_menu | fail 1（与基线相同） |
| bag | fail 246（既有问题，与基线一致） |
| options | fail 53（`g_garble` 竖条残片/字形碎片，12px vs 8px 的判据误报，目视正常） |

options 的 53 与 dex 剩下的 fail 是同一类：12px 汉字笔画落在 8px tile 边界上，
被 `verify` 的 sliver/fragment 判据判掉。**这是验收判据对 12px 字体的误报，
需要单独收敛判据，不是渲染问题** —— 截图逐帧目视无残影。

## 11. #8/#9 之后：滚动乱码 + 精灵球图标被写坏（2026-11-11，**未修，已定位**）

用户第三轮截图：向下移动时列表里出现乱码，**编号左边的精灵球图标变成方块问号**。
这一轮试了四个方案全部失败，已全部回退；下面是查实的根因和走不通的原因，
下次动手前先看这一节，不要再重复试。

### 11.1 根因：文本 arena 的排布撞上了非文本资源

`text_render.c` 的 arena 排布是：

```c
base = win_u16(win, WIN_TILE_BASE) + seg * CHS_ROW_TILES;   /* 62 tiles/段，8 段 */
```

图鉴列表实测 `WIN_TILE_BASE = 1`（GDB），于是 8 段铺满 **0x001..0x1F0**：

| seg | tile 范围 | 撞到什么 |
|---|---|---|
| 0 | 0x001..0x03E | **BG3 边框 0x002 / 0x003** |
| 1 | 0x03F..0x07C | **BG3 边角 0x06C / 0x06D** |
| 2..6 | 0x07D..0x1B2 | 原版字形（我们已接管，安全） |
| 7 | 0x1B3..0x1F0 | **菜单光标 ▶ 0x1F0 / 0x1F1** |

列表行 `cy = 10..18` → `seg = ((cy)>>1) & 7 = 5,5,6,6,7,7,0,0,1`
⇒ **第 4/5 行（seg=0/1）画字时把 BG3 的边框、编号左边的精灵球整块覆盖掉**。
这就是「球变方块问号 + 编号出乱码」的来源。

逐 tile 统计（bot 六场景 origin 侧）确认：0x080..0x1EF 里被引用的几乎全是
**原版字形**（我们接管渲染后不再显示），真正的图形资源都在 **0x00..0x7F**
和 **0x1F0..0x1FF** 两头。

### 11.2 四个方案全部失败（数据都在，别再试）

| # | 方案 | dex | bag | options | 失败原因 |
|---|---|---|---|---|---|
| 0 | 现状 `TILE_BASE + seg*62`，8 段 | fail 37 | 246 | 53 | 撞 seg=0/1 低段（本节 11.1） |
| 1 | 基址抬到 0x80，46 tile/段（23 列），8 段 | fail **10** ✅ | — | 53 | **名字消失**：`CHS_SCREEN_COLS` 被迫降到 23，而图鉴名字从**列 23** 起画 → 一个字都不画 |
| 2 | 基址 0x80，60 tile/段（30 列），**6 段** | fail **84** | 250 | 60 | 段不够：背包 7 行可见，6 段循环 → 两行共用一段互相覆盖 |
| 3 | 基址 0x80，**相对列**（以行首为 0）+ 52 tile/段 + 7 段 | fail **104** | 100 | 88 | 相对列改动波及 `put_entry`/`clear_cols`/`hend` 记账，回归面太大 |

方案 1 的数字说明方向是对的（fail 37→10），只是被「23 列装不下从第 23 列起的名字」
卡住；方案 2 说明 **7 段是硬需求**（背包 7 行）。

### 11.3 为什么这条路走不通：算术上塞不下

可用空间 = `0x080..0x1EF` = **368 tile**（低段 0x00..0x7F 是 BG3 边框/精灵球，
高段 0x1F0..0x1FF 是光标 ▶ 与 "No" 字形）。

需求 = 7 段 × 30 列 × 2（12px 字占上/下两片）= **420 tile**。

**368 < 420，差 52 个 tile —— 不是调参能解决的。**

### 11.4 下一步的三个候选（需要选一个方向，别再微调常量）

1. **换 charBase**（最彻底）：把文本层的 `BGxCNT` charBase 改到一个我们独占的
   block。风险：实测这个画面上 4 个 char block 分别被 BG0(0)/BG1(3)/BG2(2)/BG3(2)
   占用，要先腾一个出来（把某个装饰层挪到别处），改动面大但一次性。
2. **动态 tile 分配**（最符合引擎做法）：维护一张空闲 tile 位图，按「当前需要
   绘制的字」现场分配、文本重印时回收。origin 的字形 tile 就是这么来的
   （0x0B9/0x0CB/0x0D9… 是它的字体表）。改动集中在渲染器，但要新增分配器 + 回收时机。
3. **按可见行数动态映射段**：段不再由 `row % N` 决定，而是「当前活跃的屏幕行 →
   0..K-1」的登记表（K = 可用段数）。改的是段的分配策略，不动列基准，风险居中。

建议先做 **3**（改动最小、可回归验证），不够再上 **2**。
