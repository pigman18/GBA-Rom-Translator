# FIRERED_BPRE00 · 12px 渲染与昵称机制（参照）

> 火红（美版 BPRE / 日版 BPRJ）在本工程里只作**参照样本**：验证「12px 是否必须 8+4」「中文种名如何与 6B 昵称槽解耦」。
> 结论全部来自当时的 GDB + VRAM + 截图实测（2026-11-11 / 11-15），不是移植代码阅读。

---

## 1. 火红怎么渲染 12px（实测）

| 项 | 实测值 | 怎么测的 |
|---|---|---|
| 单字墨宽 | **12 px** | `menu.png` 逐列扫非白像素 |
| 单字步进（pitch） | **13 px** | 4 字起点 x=26 / 39 / 52 / 65 |
| 4 字实际占用 | x=26..76 = **51 px** | 同上 |
| 字形缓冲 | 4 段 × 32B → 16×16 | 反汇编 `0x081DB3EE`：`+0x00/+0x10/+0x100/+0x110` → `+0x00/+0x20/+0x40/+0x60` |
| 返回宽高 | `width=12, height=13` | `0x081DB450 bl 0x81DB630; strb r0,[r1]; movs r0,#0xD; strb r0,[r1,#1]` |
| 挂载方式 | **函数指针表** `0x08742148 = 0x081DB3EF`（thumb），不在任何 `bl` 目标里 | 全 ROM 搜索 |

**tile 编排（BG0 screenblock `0xF000`）**

```
ty1: tx3=001 tx4=002 ... tx26=018   ← 24 个，等于整窗宽
ty2: tx3=019 tx4=01A ...            ← 下半片紧接上半
```

⇒ **tile 号按「屏幕列」连续递增，不按「字」分配**；同一行所有字共享一整段连续 tile。
这与红宝石原版引擎 `TILE_BASE + TILE_OFFSET + 2*xOff + yOff` 完全同构。

**关键澄清**：火红每字也占 2 列（12px + 1px 空），tile 用量与我方一样（每字 4 个，上/下各 2）。
「12px 装不下」不是字号问题；火红不撞 UI 的真正原因是**它把这 4 个 tile 放在自己独占的 char block**。

## 2. 火红怎么解决「中文名 vs 6B 昵称槽」

| 事实 | 证据 |
|---|---|
| 原版日文名表**一个字节没动** | 表基址内容对比 |
| 新增 **412 项指针表** | 新表结构 |
| 改动只在「取名字」这一层：全 ROM **40 处** `0x08203CB8` 引用，**9 处**换成新代码 | 引用点枚举 |
| EWRAM 里只有 **1 条** F7 串，但屏上 5 个中文名 | 内存 dump vs 截图 |
| 原版跑同场景，EWRAM 结构几乎一样 | 对照 |

**机制**：显示与存档彻底解耦——存档仍写 `nickname`，**显示时按 `species` 查新表取完整中文名**。
所以「串档不乱」：存档字段永远是 6B 的日文/空，不会因为中文名超长而写坏。

### 与本工程的关系

红宝石已按同一思路落地：

| 位置 | 实现 |
|---|---|
| 战斗血条名 | `NickFullName_entry.s`（species → `0x09EB0AF4 + species*24`） |
| 遭遇「野生的XXX」 | `NickSlot_entry.s`（替换 `0x0811C7AA` 的 `GetMonData(mon,2,sp)`） |

**不要照抄的部分**：

1. 火红的「独占 char block」在红宝石做不到——游戏按绝对地址 `0x06008000` 解压图形，换 charBase 会花屏（`../POKEMON_RUBY_AXVJ00/20-渲染与钩子.md` §6）。
2. 火红的「8+4 双遍渲染」不是必需；红宝石单遍像素合成已够用（用户 2026-11-19 明确「复刻落址不复刻渲染」）。
3. SLT2（master 早期曾用过的方案）与火红**不是同一思路**：SLT2 是 11-04 就被换掉的旧法，不能拿来论证「火红式解耦可行/不可行」。
