## 二、现行方案的核心缺陷

### 2.1 区间重叠（D4 收窄后依然存在）

即使把三个全 ROM 模块收窄到「实际条目范围」，它们仍然大幅重叠：

```
UI界面   ∩ 剧情     = 0x14C000..0x3F2FFF  (2.65 MB)
UI界面   ∩ 补漏剧情  = 0x14C000..0x3F2FFF  (2.65 MB)
剧情     ∩ 补漏剧情  = 0x144000..0x7F0FFF  (6.68 MB)
```

**原因不是区间没划好，而是它们本来就是同一片区域**：
ROM 的文本池把剧情、UI、战斗提示、词库全部交错存放在 `0x14xxxx`–`0x3Fxxxx`。

### 2.2 归属靠 FCFS 抢，不靠定义

`export_texts()` 的机制是：按模块声明顺序抽取，先抽到的模块「认领」字节带，
后续模块跳过已被认领的部分（`exported_bands`）。

**后果**：加一个模块、调一次顺序、改一个 filter，归属就全变，
而且不会有任何报错——沉默地改写结果。

### 2.3 `scan` 的起点语义（**前版结论已更正**）

> ⚠️ **更正**：本方案初版写「`extract_scan` 的串起点由 `start` 之前最近的 `0xFF` 决定，
> 切子区间会打断串边界」——**这是错的**。
> 实际逻辑见 `src/meowth/extract.py:1041-1055`：
> 从区间起点 `a = lo` 开始**逐字节推进**，遇 `0xFF` / `0x00` / `F7+`（`FC`/`FD` 除外）跳过，
> 遇到第一个可打印字节就作为串首。**起点偏移不影响串边界**。

实测（`texts_50`，同一区间末端、不同 lo）：

```
lo=0x3B2000 -> 首条 @0x3B2000
lo=0x3B1FF4 -> 首条 @0x3B1FF4
lo=0x3B1FF0 -> 首条 @0x3B1FF0（多一条 '►めも'）
```

起点前移，只是多收起点之前的内容，不会「打断」后面的串。

**那 129 条乱码的真实原因是「区间起点选在了数据区」**，不是串错位。
`0x3B2000..0x3B2800` 本来就不是文本（实测该段含裸 `F7`、`Ä`、700+ 字节超长串，
词表命中 0）。真正的词库从 `0x3B280C` 才开始。

**教训**：选 scan 起点前，必须先证实「起点所在位置的字节是文本」，不能按整块区段拍脑袋。

### 2.5 现有 type 的能力边界

现有 `extract_module` 支持的 type：

| type | 语义 | 边界由什么决定 |
|---|---|---|
| `stride` | 定长槽 | 表几何（start/end/stride）✅ 精确 |
| `struct` | 结构体行 | 表几何（entry_size/name_offset）✅ 精确 |
| `stride_ptr` | 指针表 | 指针表几何 ✅ 精确 |
| `scan` / `addr_bands` | 全段扫描（逐字节找串首） | 起点/终点 + filter，**可精确定区间，不能按内容筛选** |
| `needle` / `prefix` / `pointer` | 未实现（返回空） | — |

**`addr_bands` 只是 `scan` 的别名**（`texts_patcher.py:2581` 两者走同一分支），
不是「按地址白名单」。

**更正**：初版写「scan 不能精确切子集」也不准确。
scan 切子集是精确的（起点由 `lo` 决定，逐字节推进），问题只是
**起点若落在数据区，会把数据解成乱码**。选对起点即可。

## 三、目标形态

> **每个模块 = 明确区间 + 明确 type + 不靠 fallback 抢归属**

### 3.1 三条原则

1. **能定长就定长**：表结构已知的一律用 `stride` / `struct` / `stride_ptr`，
   边界由几何决定，与 FF 无关，天然精确。
2. **不能定长就按语义带切**：确实要 `scan` 的，区间必须对应 ROM 里一段**独立的、不与其他模块交错的**存储区。
3. **禁止 fallback 抢归属**：`fallback_filters` 只能作为「同模块内补漏」，
   不能作为「跨模块归属仲裁」。

### 3.2 分层

```
第 1 层：定长表（精确，15 个）—— 不动，只修边界
第 2 层：结构区段（可精确）—— 若 ROM 里确实独立成片，用 scan + 选对起点
第 3 层：剧情正文（不可精确）—— 只能靠内容判定，交给新流水线 auto_layout
第 3 层：剧情正文（不可精确，只能靠内容判定）—— 交给新流水线 auto_layout
```

**关键判断**：第 3 层不该再用「模块」表达。
剧情的归属应当由 **`auto_layout` 按译文内容自动判定**（这也是 Chief 说的新方案方向）。
用 texts.json 的模块去表达「哪句话属于哪个剧情场景」，本质上是在用错误工具。

   （起点由 `lo` 决定、逐字节推进），实测起点偏移 0xF00 字节都不影响后面。
   真正的问题是**起点可能落在数据区**，于是把数据解成乱码。

   所以问题变成：**怎么判据一个地址「是否是文本区的起点」？**
   目前我用「词表命中 + 形态干净 + 裸控制码检测」三重判据
   （`texts_53`/`texts_54` 的做法），能区分但比较笨。
   如果新流水线的 `auto_layout` 有更可靠的文本/数据判别，这件事就交给它。

2. **第 3 层（剧情正文）还要不要在 texts.json 里分模块？**
   我的看法是不需要。texts.json 只该回答「哪些字节是文本」，
   「这句话属于哪个场景」应由 `auto_layout` 按内容判定。
   **但先等 TextAuditor1/2/3 的审查结果**，看真实归属分布再定形态。

3. **`补漏剧情` 是否整个删除？**
   建议等 audit 结果：若它的 1,561 条大部分是「剧情漏掉的」，说明该并进剧情；
   若是 garbage 为主，直接删。
