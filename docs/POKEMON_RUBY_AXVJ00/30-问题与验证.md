### BUG-9 定案（2026-11-23，动态实证 + 已修）

**现象收窄**：只有信息框**第一行的 3 个数字格**坏成形似「?吗?」，标签/数值/第二行「号道路」全正常。

**取证链**（全部实测，非推演）：

1. GDB `SaveInfoDraw` + `GlyphPtr` 两侧采集：窗参数 origin/translated 完全一致
   （`tm=3 fn=3 TB=1 tilemap=0x0600F800`），数字走原版 PCS 单字节（产物字节
   `a2 a2 a9` = 「118」），字模取址正确。
2. `GRID_DIAG` 诊断构建（新增 `diag_store` 快照），EWRAM 环形日志逐条解码：
   - `row0 col1..3` 写 tile 5/7/9 = 「118」的**正确**字模；
   - `row8 col16..19`（确认句第二行「里吗？」）经 `col^16` **折回 col0..3** → tile 3/5/9；
   - 两句同 band0，确认句后画，把数字格覆盖成「里吗？」的残字。
3. `diag_store` 的 `p0` 快照证实写进 tile 5 的确实是数字「1」，说明**写的是对的，之后被改写**——
   这解释了历史文档里「诊断显示写的是纯背景，之后被另一条路径改写」的困惑：第二条路径是**同一渲染器**
   的回绕行，不是游戏代码。

**根因**：`grid_store_col(row,col)` 对 `row>=8` **无条件** `col^16`。`col^16` 只在「同 band 同列
真有两行」时才需要（图鉴 11 行），无条件执行会把存档框这类**单行窗口**的列平移到别人的槽上。

**修法**（只加判据，不动协议）：`grid_store_col` 改为「只有该 tile 真被本列别的行引用时才翻」，
判据 `grid_col_claims_tile()` 只扫同一列 32 项、排除本格自身（与 `grid_tile_taken` 同口径）。

**验收**（产物 `f514dd16…47aabd`）：

| 项 | 结果 |
|---|---|
| save 帧 `020 save_confirm` 第一行 | **`118号道路`** 逐字正确 |
| save 变化包围盒 | x=8..30 / y=11..23（正好三个数字格），其余像素零变化 |
| start_menu 56 步 | 与修复前**逐像素相同**（零回归） |
| dex 编号列与 origin 差异 | 16,289 px → **4,158 px**（超阈值帧 121 → 63，顺带改善 BUG-B 残留） |
| 静态验收 | 19 PASS / 1 FAIL（`Small ink 8x8`，已知误报） |

**判据修正**：`col^16` 是行间隔离机制，但**必须按需**，无条件折会制造新碰撞（本条 BUG 即为反例）。

### BUG-10 定案（2026-11-23）：是**场景状态分叉**，不是渲染缺陷

**现象（原始描述）**：出招时有几帧撕裂——屏幕上下半区不同步、底部出现纯黑带、
或上屏是冻结的过渡帧（UI 已上移但菜单框还是空的）。见 `battle_move_anim.lua` 头注与
`docs/research/FIX_PLAN_BATTLE_BAG_20261116.md` 的 B11（「帧 090–104 底部 y112–159 纯黑带」）。

**本次实测**（产物 `f514dd16…47aabd`，`battle_move_anim` 132 帧对）：

| 观测 | 数据 |
|---|---|
| 黑带区间 | translated **第 73–132 帧** y=112..159 恒 100% 纯黑；origin 同帧 **0%** |
| 边界精度 | 影像整宽在 y=111/112 处齐平断开（= 14 行 tile），此后 60 帧不恢复 |
| 是否为本次改动引入 | ❌ 否。用修复前 ROM（`994F0518…`）跑同一场景，黑带区间**完全相同**（73..132） |
| 寄存器侧 | 帧 72 两侧 `DISPCNT=BF40 mode=0` 全等于 BG0..3 全开；`BGxHOFS/VOFS` 无跳变；BGVOFST 差异仅个位数（P03 血条名 DMA 源的正常波动） |
| 对照场景 | `battle_full` / `battle_dialog` 的黑带只出现在转场帧（2..6），是转场黑场，正常 |

**根因**：两侧**遭遇的对手不是同一只**。
第 73 帧 origin 我方血条 = `キャモメ Lv25`，translated = 另一只 `Lv24`；
第 72 帧两侧虽同为战斗菜单，但对手精灵已经不同（origin 长翅鸥 / translated 另一只）。
野生遭遇的 RNG 在两侧分叉后，我方进入的动画状态机分支不同，于是同号帧内容不可比。

**决定性反证**：新建 `_probe_bug10.lua` 用同一套钉 RNG + 逐帧 dump 重跑，
这次两侧**遭遇同一只长翅鸥**，画面全程正常——对话框正常打出
「野生的长翅鸥的／超音波！」「但是野生的长翅鸥的／攻击没有命中！」，
底部黑带 **0%**（帧 38/47 两侧均 0%）。

**结论与判据**：
1. BUG-10 的「黑带/撕裂」**不是渲染层缺陷**，是采集侧未做到确定性遇敌导致的对照失效。
2. 判据：战斗类场景必须先验证**两侧对手一致**（我方/敌方名字与等级），再比像素；
   两侧对手不同时，任何帧差异都不可作为 ROM 缺陷证据。
3. 同类陷阱已在 `battle_dialog` 复现过：两侧帧号偏移 -78 / +171，内容完全错位。

**最终修法（同日完成，取代上方所有临时方案）**：金手指写死敌方 `species`。
`gBattleMons` 真实地址 = `0x020247E0`（符号表的 `0x02024A80` 差 `0x2A0`，不可用）；
结构 `0x58` B/battler，`species` 见 `+0x00`（u16）、`level` 见 `+0x2A`（u8）。
推导：用「我方 Lv36 / 敌方 Lv26」+ 物种 282/288 在 EWRAM 反查 → 两处命中正好差
`0x58`，六项能力值紧跟 `species` 之后 → 结构确认。

⚠ **必须写两次**：只在「转场中」写**无效**（那时 `gBattleMons` 还在被初始化覆盖）；
必须在「进菜单后」再写一次。

验收：4/4 个有战斗结构的帧敌方物种完全一致（288 Lv24）；帧 2–6 敌方名字区
逐像素 diff = **0**；对话框正确显示「野生的落雷兽跳出来了」。

### 确定性遇敌：三种写法都失败（2026-11-23 实测记录）

目标：让 origin / translated 两侧**遭遇同一只野生宝可梦**，否则战斗类场景全部不可比。
三轮实测全部失败 —— **旧注释里的「钉一次 RNG + hunt ⇒ 完全一致 ✅」不成立**：

| 写法 | 结果 | 证据 |
|---|---|---|
| ① `poke` 一次 → `hunt` 40 步（旧法，`battle_full` 注释标「勿改」） | ❌ 对手不同 | `battle_full` 帧 2：两侧是不同物种 |
| ② 每走一格 `poke` 再 `walk` 一格（`_probe_detbattle4` 写法） | ❌ 对手不同 | origin ジグザグマ Lv24 / translated 另一只 Lv26 |
| ③ `poke` → `hunt` → `await` 战斗 → **转场后重钉**（`battle_menu_audit` 写法） | ❌ 对手不同，但**黑带消失** | 帧 11：两侧同为 Lv26、我方同为 `バシャーモ Lv36 77/115`，敌方物种仍不同 |

**失败原因**：两侧 settle 时长不同（译文更长），`poke` 只决定**写入那一瞬**的 RNG；
从写入到「遇敌判定」之间还要跑几十帧，RNG 早被消耗掉。钉得再勤也追不上。

**已确认的判据与坐标**（可直接复用）：

- 屏幕坐标（240×160 口径）：敌方血条名字 `x=145..236, y=80..94`；我方 `x=8..120, y=42..52`。
- 判据：crop 敌方名字区做逐像素 XOR，差异 > 0 ⇒ 对手不同 ⇒ 本次采集不可比。
  实测 `battle_move_anim` mv_list 段 diff=42（不同），判据有效。
- 物种内存地址：`bot/analyze_battle_menu_frames.py` 的 `SPECIES_PLAYER=0x02024A80` /
  `SPECIES_ENEMY=0x02024AD8` **在 Ruby 上读出全 0，不可用**（该地址来自 Emerald）。
  官方分析脚本跑本工程返回 `"species": null`。

**下一步（用户已选：写死对手物种）**：需先在 Ruby 上定位 `gBattleMons` 真实地址。候选路径：
① 用「我方 Lv36 + 77/115」做特征反查（实测 `0x02025722` 有 `77,115` 相邻，但周边是
0xFF/小整数混杂，尚不能确认是结构字段）；② 用 `scripts/battle/scan_wild_headers.py`
把 Route118 遇敌率改 100%，让两侧必然同格触发。

### BUG-11 定案（2026-11-23，用户截图 + 动态实测）

**现象**：存档确认框第一行「要把至今为止的活跃表现」**右侧**，靠对话框右上角处多出
一小串残字（形似半截日文假名，约 3 个字号宽）。第二行「记录到宝可梦报告里吗？」右侧正常。
用户截图：`Clipboard_Screenshot`（2026-11-23 15:35）。

**实测数据**（`save` 帧 020 `save_confirm`，两侧同帧）：

| 项 | origin | translated |
|---|---|---|
| 第一行非零列范围 | col **4..25** | col **4..20** |
| 列 4..20 的 tile 号 | `1C9,1CA,1CB…1DD`（**连续，1 列/字，8px 日文**） | `1BD,1BF,1C1…1DD`（**间隔跳号，2 列/字，12px 汉字**） |
| 列 21..25 的表项 | `1DA,1DB,1DC,1DD,1DE` | **同样是** `1DA,1DB,1DC,1DD,1DE` |
| 这 5 个 tile 的墨量 | **全 0（空）** | `1DA=13 / 1DB=0 / 1DC=14 / 1DD=0 / 1DE=6` |

**根因（两层）**：

1. **行尾 5 格的表项是旧布局遗留**：原版 12 个字各占 1 列，排到 col25；汉化版 12px 汉字
   各占 2 列，只排到 col20。col21–25 这 5 格**本该没有表项**，但上一次（8px 日文）
   布局写下的 `1DA..1DE` 没被清掉，仍指着那批 tile。
2. **那批 tile 已不是空的**：「现」字（第 12 字，phase=0，col19 → 本征 `t0=475`=0x1DB，
   占 `0x1DB/0x1DC`）把字模写进了这两格，于是 col22/23 也把它显示出来 →
   屏幕上是「现」的右半 + 邻近碎片，读起来像半截假名。

**为什么 12px 推进本身没错**：诊断环实测 `drel` 严格是 phase=0 → +2、phase=4 → +1
（`rel=7,9,10,12,13,15`），`col` 与 `rel` 同步，t0 与本征公式 `TB+2+band*62+2*col`
逐格吻合。**列号与 tile 号都正确**，问题只在「旧的更宽布局留在行尾的表项没清」。

**修法方向**（未实施，三种备选）：

1. **写行尾空白格**（推荐）：每行结束时把 `[最后列+1, 原版行宽)` 的表项改成指向空白 tile。
   风险：需要知道「原版行宽」，而它随原文长度变化。
2. **整行预清**：`InitTextPrinter` 收到 `FC_CLEARWINDOW` 或每次开始打印一行时，把该行
   `GRID_COLS_PER_SEG` 全列的表项清成空白。代价是每行多 62 次表项写。
3. **共用 tile 隔离**：`grid_tile` 分配的 tile 若已被本行**其它列**引用，就迁址。
   这与 BUG-9 的 `grid_col_claims_tile` 思路同源，但判据要覆盖「同 band 同列」之外。

**注意**：这三个方向都会动 `PrintNextChar_hook.c`（整个文本引擎），按铁律必须跑完整
场景矩阵回归：开始菜单、队伍、背包、商店、图鉴、对话、存档、战斗（dialog/full）。

### BUG-13 队伍列表宝可梦名未汉化（2026-11-23，七次尝试均失败，根因已定）

**现象**：队伍界面（`pokemon_menu` 帧 `party_list`）右侧 5 只名字全是日文
（`バシャーモ` / `ラグラージ` / `ジグザグマ` / `ツチニン` / `キノココ` / `タマゴ`），
只有底部提示「请选择」是中文。摘要页顶部名字同样是日文（但底部「火焰鸡」是中文
⇒ 分类名有 hook、**物种名没有**）。

**实测定位（GDB `InitTextPrinter` 断点，win=`0x03004170`）**：

| 项 | 实测值 |
|---|---|
| fontNum | **4**（Small / 8px，与用户口径一致） |
| textMode | 1 |
| charBase / tileData | 1 / `0x06004000` |
| tilemap | `0x0600F000`（BG0） |
| 文本指针 | **栈上缓冲**（IWRAM `0x03007DC0` / `0x03007DC8`） |
| 内容 | 6 字节日文名，如 `8d 89 8c 89 6f ff` = ジグザグマ |

**已证伪的三条路线（都别重走）**：

1. **hook 取源函数 `0x0803B11C`**（`0x08037D06` 是它全 ROM 唯一调用点）
   → GDB 断点 `PartyNickSrc`/`PartyNickCall` **命中 0 次**。
   队伍名字**根本不经过它**。
   附带纠正：`0x0803B11C` 反汇编确认是「日文物种名表 `0x081CA354` + species*6 + 上限 10B」，
   旧注释写的「→ `0x1EB0AF4` 拷完整名」是**错的**。

2. **在 `PrintNextChar` 字符流里换源**（独立游标 + `grid_draw_chs`）
   → `WIN_STATE` 到不了 END → `RenderText` 无限调用 → **输入回调停摆**
   （实测 `fr=9241 last_tick=6240 idx=34/105`）。
   根因：引擎的结束判定依赖**原串字节游标**，换源后两者不自洽。

3. **在 `InitTextPrinter` 入口（`0x08002C68`）改 r1**
   → **崩溃**：`Jumped to invalid address: D3030000`。
   根因：入口指令 `0x464E` 是 **`mov r6, r9`**（不是 `mov r9,r1`，我误读了），
   重放时把 r9 覆盖 → 原函数 `mov r6,r9` 拿到垃圾值 → 跳飞。
   ⇒ 该函数**不在入口直接用 r1**，文本指针在 `push {r5,r6}` 之后从栈上取
   （`ldr r4,[sp,#0x18]`）。

4. **修好栈帧后挂 `Text_InitWindow` 入口（第 4 次，r7 跳板）**
   → **开始菜单直接卡死**。
   根因：`Text_InitWindow` 是**通用函数**，每场景被调用 **160 次**（GDB 实测），
   在这上面做查表替换等于给所有文本打印加开销/副作用。
   另：原跳板 `ldr r3,=(hook|1)` 会毁 **r3 = left 参数**，
   而 `0x08002CA6` 用 r3 写 `win->tileDataStartOffset`（`+0x1A`）——
   GDB 实测该字段从 `0x0119` 变成 `0x01A1`，字模基址错位 → 只推进不绘制。
   ⇒ 换 r7 跳板 + 换 hook 位置。

**pokeruby 源码带来的关键纠正（`tools/pokeruby`）**：

| 项 | 旧假设 | 源码权威值 |
|---|---|---|
| `MON_DATA_NICKNAME` | 2 / 58（都试过） | **2**（`include/constants/pokemon.h:6`） |
| `Text_InitWindow` 签名 | 猜 | `(win, text, tileDataStartOffset, left, top)`，`src/text.c:1962` |
| Window 布局 | `game.h` 的 `+0x0B=fontNum` | 源码 `+0x01=fontNum`、`+0x12=left`、`+0x1A=tileDataStartOffset` |
| 队伍名字出口 | 以为走 `InitTextPrinter` 就完事 | `GetMonNickname(pokemon,buf)` → `GetMonData(mon,2,buf)` + `StringGetEnd10(buf)`，`src/party_menu.c:2600` |
| 队伍名字缓冲 | 以为够大 | **`u8 nameBuffer[12]`**，中文 3 字 = 12B 已满、无 FF 空间；而中文表里 80 个 4 字名、9 个 5 字名 ⇒ **必须换指针而不是拷进这个缓冲** |
| 队伍名字渲染目标 | 以为 BG tilemap | `CpuFastCopy(gTileBufferPtr, OBJ_VRAM1 + monIndex*0x400, 0x200)` ⇒ **OAM 精灵**，不是 BG |

**符号表 `pokeruby_jp.sym` 不可直接信**：`GetMonNickname` 记 `0x0806B7D8`，
实际代码在 `0x0806B7E4`（偏 0xC，前者是数据）。用前必须逐条反汇编核对。

**当前状态**：所有尝试已回退，产物 `93ebcf7f…`（9988B），
`start_menu` 56 帧 / `pokemon_menu` 95 帧均无 ERR，游戏可正常游玩。

**七次尝试的完整账（2026-11-23 第二轮）**：

| # | 方案 | 结果 |
|---|---|---|
| 5 | 0x0806B2E4 改 r2 + 拷进 12B 缓冲 | 停摆 fr=9240 |
| 6 | 在 0x0806B288 内调 GetMonData 算 species | 队伍界面全黑（帧14 非黑=0） |
| 7 | 0x0806B288 入口换 r2 为 ROM 中文表指针 | 停摆 fr=9240 |

**根因已定（不是栈/寄存器/地址问题）**：
只要让中文 F7 串真正进入 `0x0806B288` 这条渲染路径，就必然停摆。
源码依据 `src/text.c:2040 Text_PrintWindow8002F44`：
```c
while (win->state != WIN_STATE_END) { ... PrintNextChar(win); }
```
`state` 只在读到 `EOS(0xFF)` 时置 END。而队伍名字经
`CpuFastCopy(gTileBufferPtr, OBJ_VRAM1 + idx*0x400, 0x200)` 按**固定 0x200 字节**
处理，中文（4 字节/字）与日文（1 字节/字）的布局差异使 state 到不了 END。

**决定性反证**：把 `bl PartyName_LookupJp` 换成 `movs r0,#0`（永不命中）
→ 帧 3/14/19 全部 38316，完全正常；加回真实查表 → 必停摆。
⇒ 排除栈帧、寄存器、对齐、符号地址等所有其他因素。

**工具陷阱（都踩过，务必记住）**：
- **A** `bl C函数符号名` 可能跳到函数中间：实测 `PartyName_LookupJp` 跳到
  `0x088014D4`，真实起点 `0x088014D0`（跳过 `push {r4-r7,lr}` 和 `cmp r0,#0`）。
  ⇒ 必须用 `ldr r3,=<显式地址|1>` + `bx`。
- **B** 在 `0x0806B2E4` 下 GDB 断点会**误报** `LR=0x0806B376`、`r2=长度值`
  （断点没设上，命中了别处）。必须断在 `0x0806B288` 才能看到真实参数
  `r2=0x03007DC8`。
- **C** mGBA 开着时产物写不进去，meowth 会**静默**输出到 `*_new.gba`，
  导致后续验证跑的都是旧文件（浪费了好几轮）。打包前先 `taskkill mGBA`。
- **D** build.bat 编译失败时只打印 `Error:`（含空格），`grep "error"` 会漏掉
  ⇒ 用 `grep -iE "error|Build OK"` 并检查 Size 是否变化。

**下一步方向**：不要在 `0x0806B288` 这条路径上做。它按固定长度 CpuFastCopy
到 OBJ_VRAM1，与变长中文串不兼容。应改 `0x0806B2C8` 上层，让中文名在
`PrintPartyMenuMonNickname` 之前就替换整只宝可梦的显示路径；
或查清 `0x0806B288` 里那 0x200 字节拷贝的确切用途再定方案。

**下一步（正确路线）**：
1. 用 GDB 在 `GetMonData` 入口抓 `r1==2` 的调用者，**动态确定** `GetMonNickname` 真实地址
   （符号表偏移不可信）；
2. 在该函数的 `GetMonData(mon,2,buf)` 返回点之后，把 buf 指针换成中文表条目
   （中文表在 ROM 里，长度不受 `nameBuffer[12]` 限制）；
3. 注意队伍名字最终 `CpuFastCopy` 到 OBJ_VRAM1，宽度上限 8 格（模板 `width=8`），
   中文 3 字 = 24px 够用，4~5 字需验证是否截断。

### BUG-14 名字写进存档导致串档乱码（2026-11-23，方案已调研未实施）

**现象**：汉化版把宝可梦名/训练家名的汉化编码写进存档，存档串回原日版游戏显示乱码。

**根因**：Gen3 名字字段是**定长**的——`nickname[10]`、`playerName[8]`，
而中文 1 字 = 4 字节（`F7 00 hi lo`），3 字 = 12B 塞不下 ⇒ 截断或越界写坏相邻字段。
实测队伍内存里 nickname 尾部出现 `75 53 57`（存档校验 magic 残渣），
即中文名已越界写出。

**火红汉化的做法（实测，见 `docs/通用/名字存档兼容调研.md`）**：
显示与存档彻底解耦——**改指针不改原表**（日版 `0x16F744` 的 `0x0816F9FB`
→ `0x086D0000` 指向新增中文表），存档字段永远是原版编码。
配套替换了变长字符串长度函数（遇 `F7` 走 12B、日文走 10B）。

**本工程现状**：宝可梦名已按此思路解耦（P10 血条 / P12 遭遇 / 摘要页），
**训练家名仍是「扩 stride」路线**，未解耦。
