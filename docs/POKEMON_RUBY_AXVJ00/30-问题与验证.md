### BUG-9 定案（2026-11-23，动态实证 + 已修）

**现象收窄**：只有信息框**第一行的 3 个数字格**坏成形似「?吗?」，标签/数值/第二行「号道路」全正常。

**取证链**（全部实测，非推演）：

1. GDB `SaveInfoDraw` + `GlyphPtr` 两侧采集：窗参数 origin/translated 完全一致
   （`tm=3 fn=3 TB=1 tilemap=0x0600F800`），数字走原版 PCS 单字节（产物字节
   `a2 a2 a9` = 「118」），字模取址正确。
2. `GRID_DIAG` 诊断构建（新增 `diag_store` 快照），EWRAM 环形日志逐条解码：
   - `row0 col1..3` 写 tile 5/7/9 = 「118」的**正确**字模；
   - `row8 col16..19`（确认句第二行「里吗？」）经 `col^16` **折回 col0..3** → tile 3/5/9；
   - 两句同 band0，确认句后画，把数字格覆盖成「里吗？」的残字。
3. `diag_store` 的 `p0` 快照证实写进 tile 5 的确实是数字「1」，说明**写的是对的，之后被改写**——
   这解释了历史文档里「诊断显示写的是纯背景，之后被另一条路径改写」的困惑：第二条路径是**同一渲染器**
   的回绕行，不是游戏代码。

**根因**：`grid_store_col(row,col)` 对 `row>=8` **无条件** `col^16`。`col^16` 只在「同 band 同列
真有两行」时才需要（图鉴 11 行），无条件执行会把存档框这类**单行窗口**的列平移到别人的槽上。

**修法**（只加判据，不动协议）：`grid_store_col` 改为「只有该 tile 真被本列别的行引用时才翻」，
判据 `grid_col_claims_tile()` 只扫同一列 32 项、排除本格自身（与 `grid_tile_taken` 同口径）。

**验收**（产物 `f514dd16…47aabd`）：

| 项 | 结果 |
|---|---|
| save 帧 `020 save_confirm` 第一行 | **`118号道路`** 逐字正确 |
| save 变化包围盒 | x=8..30 / y=11..23（正好三个数字格），其余像素零变化 |
| start_menu 56 步 | 与修复前**逐像素相同**（零回归） |
| dex 编号列与 origin 差异 | 16,289 px → **4,158 px**（超阈值帧 121 → 63，顺带改善 BUG-B 残留） |
| 静态验收 | 19 PASS / 1 FAIL（`Small ink 8x8`，已知误报） |

**判据修正**：`col^16` 是行间隔离机制，但**必须按需**，无条件折会制造新碰撞（本条 BUG 即为反例）。

### BUG-10 定案（2026-11-23）：是**场景状态分叉**，不是渲染缺陷

**现象（原始描述）**：出招时有几帧撕裂——屏幕上下半区不同步、底部出现纯黑带、
或上屏是冻结的过渡帧（UI 已上移但菜单框还是空的）。见 `battle_move_anim.lua` 头注与
`docs/research/FIX_PLAN_BATTLE_BAG_20261116.md` 的 B11（「帧 090–104 底部 y112–159 纯黑带」）。

**本次实测**（产物 `f514dd16…47aabd`，`battle_move_anim` 132 帧对）：

| 观测 | 数据 |
|---|---|
| 黑带区间 | translated **第 73–132 帧** y=112..159 恒 100% 纯黑；origin 同帧 **0%** |
| 边界精度 | 影像整宽在 y=111/112 处齐平断开（= 14 行 tile），此后 60 帧不恢复 |
| 是否为本次改动引入 | ❌ 否。用修复前 ROM（`994F0518…`）跑同一场景，黑带区间**完全相同**（73..132） |
| 寄存器侧 | 帧 72 两侧 `DISPCNT=BF40 mode=0` 全等于 BG0..3 全开；`BGxHOFS/VOFS` 无跳变；BGVOFST 差异仅个位数（P03 血条名 DMA 源的正常波动） |
| 对照场景 | `battle_full` / `battle_dialog` 的黑带只出现在转场帧（2..6），是转场黑场，正常 |

**根因**：两侧**遭遇的对手不是同一只**。
第 73 帧 origin 我方血条 = `キャモメ Lv25`，translated = 另一只 `Lv24`；
第 72 帧两侧虽同为战斗菜单，但对手精灵已经不同（origin 长翅鸥 / translated 另一只）。
野生遭遇的 RNG 在两侧分叉后，我方进入的动画状态机分支不同，于是同号帧内容不可比。

**决定性反证**：新建 `_probe_bug10.lua` 用同一套钉 RNG + 逐帧 dump 重跑，
这次两侧**遭遇同一只长翅鸥**，画面全程正常——对话框正常打出
「野生的长翅鸥的／超音波！」「但是野生的长翅鸥的／攻击没有命中！」，
底部黑带 **0%**（帧 38/47 两侧均 0%）。

**结论与判据**：
1. BUG-10 的「黑带/撕裂」**不是渲染层缺陷**，是采集侧未做到确定性遇敌导致的对照失效。
2. 判据：战斗类场景必须先验证**两侧对手一致**（我方/敌方名字与等级），再比像素；
   两侧对手不同时，任何帧差异都不可作为 ROM 缺陷证据。
3. 同类陷阱已在 `battle_dialog` 复现过：两侧帧号偏移 -78 / +171，内容完全错位。

**待办**：见下一节「确定性遇敌：三种写法都失败」。

### 确定性遇敌：三种写法都失败（2026-11-23 实测记录）

目标：让 origin / translated 两侧**遭遇同一只野生宝可梦**，否则战斗类场景全部不可比。
三轮实测全部失败 —— **旧注释里的「钉一次 RNG + hunt ⇒ 完全一致 ✅」不成立**：

| 写法 | 结果 | 证据 |
|---|---|---|
| ① `poke` 一次 → `hunt` 40 步（旧法，`battle_full` 注释标「勿改」） | ❌ 对手不同 | `battle_full` 帧 2：两侧是不同物种 |
| ② 每走一格 `poke` 再 `walk` 一格（`_probe_detbattle4` 写法） | ❌ 对手不同 | origin ジグザグマ Lv24 / translated 另一只 Lv26 |
| ③ `poke` → `hunt` → `await` 战斗 → **转场后重钉**（`battle_menu_audit` 写法） | ❌ 对手不同，但**黑带消失** | 帧 11：两侧同为 Lv26、我方同为 `バシャーモ Lv36 77/115`，敌方物种仍不同 |

**失败原因**：两侧 settle 时长不同（译文更长），`poke` 只决定**写入那一瞬**的 RNG；
从写入到「遇敌判定」之间还要跑几十帧，RNG 早被消耗掉。钉得再勤也追不上。

**已确认的判据与坐标**（可直接复用）：

- 屏幕坐标（240×160 口径）：敌方血条名字 `x=145..236, y=80..94`；我方 `x=8..120, y=42..52`。
- 判据：crop 敌方名字区做逐像素 XOR，差异 > 0 ⇒ 对手不同 ⇒ 本次采集不可比。
  实测 `battle_move_anim` mv_list 段 diff=42（不同），判据有效。
- 物种内存地址：`bot/analyze_battle_menu_frames.py` 的 `SPECIES_PLAYER=0x02024A80` /
  `SPECIES_ENEMY=0x02024AD8` **在 Ruby 上读出全 0，不可用**（该地址来自 Emerald）。
  官方分析脚本跑本工程返回 `"species": null`。

**下一步（用户已选：写死对手物种）**：需先在 Ruby 上定位 `gBattleMons` 真实地址。候选路径：
① 用「我方 Lv36 + 77/115」做特征反查（实测 `0x02025722` 有 `77,115` 相邻，但周边是
0xFF/小整数混杂，尚不能确认是结构字段）；② 用 `scripts/battle/scan_wild_headers.py`
把 Route118 遇敌率改 100%，让两侧必然同格触发。

### BUG-11 定案（2026-11-23，用户截图 + 动态实测）

**现象**：存档确认框第一行「要把至今为止的活跃表现」**右侧**，靠对话框右上角处多出
一小串残字（形似半截日文假名，约 3 个字号宽）。第二行「记录到宝可梦报告里吗？」右侧正常。
用户截图：`Clipboard_Screenshot`（2026-11-23 15:35）。

**实测数据**（`save` 帧 020 `save_confirm`，两侧同帧）：

| 项 | origin | translated |
|---|---|---|
| 第一行非零列范围 | col **4..25** | col **4..20** |
| 列 4..20 的 tile 号 | `1C9,1CA,1CB…1DD`（**连续，1 列/字，8px 日文**） | `1BD,1BF,1C1…1DD`（**间隔跳号，2 列/字，12px 汉字**） |
| 列 21..25 的表项 | `1DA,1DB,1DC,1DD,1DE` | **同样是** `1DA,1DB,1DC,1DD,1DE` |
| 这 5 个 tile 的墨量 | **全 0（空）** | `1DA=13 / 1DB=0 / 1DC=14 / 1DD=0 / 1DE=6` |

**根因（两层）**：

1. **行尾 5 格的表项是旧布局遗留**：原版 12 个字各占 1 列，排到 col25；汉化版 12px 汉字
   各占 2 列，只排到 col20。col21–25 这 5 格**本该没有表项**，但上一次（8px 日文）
   布局写下的 `1DA..1DE` 没被清掉，仍指着那批 tile。
2. **那批 tile 已不是空的**：「现」字（第 12 字，phase=0，col19 → 本征 `t0=475`=0x1DB，
   占 `0x1DB/0x1DC`）把字模写进了这两格，于是 col22/23 也把它显示出来 →
   屏幕上是「现」的右半 + 邻近碎片，读起来像半截假名。

**为什么 12px 推进本身没错**：诊断环实测 `drel` 严格是 phase=0 → +2、phase=4 → +1
（`rel=7,9,10,12,13,15`），`col` 与 `rel` 同步，t0 与本征公式 `TB+2+band*62+2*col`
逐格吻合。**列号与 tile 号都正确**，问题只在「旧的更宽布局留在行尾的表项没清」。

**修法方向**（未实施，三种备选）：

1. **写行尾空白格**（推荐）：每行结束时把 `[最后列+1, 原版行宽)` 的表项改成指向空白 tile。
   风险：需要知道「原版行宽」，而它随原文长度变化。
2. **整行预清**：`InitTextPrinter` 收到 `FC_CLEARWINDOW` 或每次开始打印一行时，把该行
   `GRID_COLS_PER_SEG` 全列的表项清成空白。代价是每行多 62 次表项写。
3. **共用 tile 隔离**：`grid_tile` 分配的 tile 若已被本行**其它列**引用，就迁址。
   这与 BUG-9 的 `grid_col_claims_tile` 思路同源，但判据要覆盖「同 band 同列」之外。

**注意**：这三个方向都会动 `PrintNextChar_hook.c`（整个文本引擎），按铁律必须跑完整
场景矩阵回归：开始菜单、队伍、背包、商店、图鉴、对话、存档、战斗（dialog/full）。

### BUG-11 修复实施（2026-11-23，产物 `58f96e57…`）

**最终修法**：新增 `grid_clear_row_tail()`，在收到 `0xFE`（换行）时把**光标右侧
连续指向公式区**的表项改指空白 tile（`TB+1`）。三版判据的实测收敛过程：

| 版本 | 判据 | 结果 |
|---|---|---|
| v1 | `0xFF` 时从光标列清到表宽 | ❌ **开始菜单 8 项全消失**（菜单是「一项一次独立打印」，每项以 0xFF 结束且光标已回行首） |
| v2 | `0xFE` 时从光标列清到表宽 | ❌ 存档框修好，但**背包列表滚动帧被削 822 px**（列表行内也带 0xFE，光标右侧还有同行的未打印列） |
| v3 | `0xFE` 时只清「连续指向公式区」的格子，遇非公式区即停；且从**光标格+1** 开始 | ✅ **存档框残字 0，8 场景零回归** |

v3 判据的实测依据：

- 存档框 `r15 col21..25 = 474..478`（都在公式区 `3..498`）→ 清掉；
  `col26 起 = 623/625/622`（框体装饰，原版也有）→ 停，装饰不受损。
- 背包列表 `col20 起 = 1`（空白 tile）→ 立刻停，列表不被误削。
- **必须只用上半行 `ty` 判停**：12px 字的离屏副本落在 `ty+1`，那里指向公式区之外
  （实测 `r16 col21 = 504`），拿它判停会一格都清不掉。
- **必须从光标格 +1 开始**：光标格可能正是本行最后一个 12px 字的第二列，
  碰它会把字削掉（实测 v2 把 `col20=477` 清成空白，正是「现」的右半）。
