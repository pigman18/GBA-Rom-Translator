# POKEMON_RUBY_AXVJ00 · BUG 根因台账

> 只记**根因**与**判定依据**。现象与验收数据见 `30-问题与验证.md`；构建流程见 `../通用/00-工程手册.md`。
> 每条都标注证据等级：`动态`（bot/GDB/VRAM 实测）> `静态`（反汇编/字节比对）> `文档`（推断，未实测）。
> **未标「动态」的条目不得当事实使用。**

## 一、已修 BUG 的根因

| ID | 现象 | 根因 | 证据等级 | 依据 |
|---|---|---|---|---|
| BUG-1 | 战斗对话/主菜单/招式整框空白 | 旧实现把 `textMode 0` 也套网格公式 `TB+2+band*62+2*col`；`TB=0x1B8`、`row=17` 时算出 `0x1F8 > 0x1F0` 上限，整条串被越界分支挡掉，一字不写 | 动态 | GDB 逐字采 win：tm0 的 `TILE_OFFSET` 是累加器（`0x12→0x24`），换行不清零；改成 `tile = TILE_BASE + TILE_OFFSET` 后与 origin tilemap 同构 |
| BUG-2 | 领航员详情左栏道路名空白/不跟随 | 调用了「名字像但行为不对」的函数（`0x080EB9C0` 叫 PrintLocation，`flag=2` 时直接返回不打印） | 动态 | GDB 在 `0x080EB9CC` 读 `flag=2` 命中；改用真打印函数 `0x080EC2E0` |
| BUG-3 | 图鉴名字列 `------` / 滚动顶行编号被改 | ① 名字表 stride 扩容时把「破折号填充循环」的 `cmp #4` 也一起改成 `#0x17`，占位串变 23 个 `-` 越界；② `DEX_NAME_COLUMN` 被改成 `0x16`，名字列与编号挤在一起 | 动态+静态 | 字节验收 `0808ADD0 04→17` 消失；像素实测名字起点 px176→184 = origin |
| BUG-4 | 招式 PP/属性框灰底 | 底色取错源：`WIN_COLOR_D` 在运行时会被 `FC 0C` 改写（红字/高亮），不能当窗口底色 | 动态 | 模板 `tpl[6]` 才是 ROM 常量、永不变化；tm0 保留 `win[0x0D]` 是有意例外 |
| BUG-5 | HP 显示 `377/115` | buffered 窗（tm2）的 HP 串首字符是空格 `0x00`，旧实现「空格只推进不重绘」，把上一条等级串的首位字模留在原地 | 动态 | GDB 采到两条串写同一缓冲同一段：等级 `36` 残留 `3` → `377`；`grid_fill_blank_cell` 整格刷背景后与 origin 逐像素一致 |
| BUG-8 | 「野生的雷?」种名残字 | Gen3 `nickname[10]` 定长，中文 3 字 = 12B 塞不下；第 3 字被强行写 `FF` 截断 | 动态 | `0x0803B11C` 里 `cmp r1,#10 / ble` 硬限；改显示与存档解耦（按 species 查 24B 名表） |
| BUG-9 | 存档框「118号道路」数字格乱码 | `grid_store_col()` 对 `row>=8` **无条件** `col^16`；确认句第二行（row8 col16..19）折回 col0..3 → tile 3/5/9，覆盖信息框第一行的「118」 | 动态 | `diag_store` 写前快照 + EWRAM 环形日志：`row8 col16` 与 `row0 col1` 的 t0 都是 5；改为「仅当该 tile 已被本列别的行引用才翻」 |
| BUG-11 | 存档确认句第一行右侧多出残字 | ① 原版 12 字各占 1 列排到 col25，汉化 12px 各占 2 列只排到 col20；col21–25 这 5 格**本该没有表项**，但上一轮 8px 日文布局写下的 `1DA..1DE` 没被清掉。② 那批 tile 已不再为空——「现」字的 12px 拆分占了 `0x1DB/0x1DC`，于是 col22/23 也把它显示出来 | 动态 | 新增 `grid_clear_row_tail()`：`0xFE` 时清「光标右侧连续指向公式区」的表项。三版判据收敛过程见 `30-问题与验证.md` |
| BUG-10 | 出招画面撕裂 / 底部黑带 | **两侧遭遇的不是同一只宝可梦**（origin enemy=338 / translated enemy=288，等级都是 26），战斗类场景所有同号帧不可比。画面黑带只是这个对照失效的表象 | 动态 | `gBattleMons` 实测 `0x020247E0`（符号表 `0x02024A80` 差 `0x2A0`）；`species`=+0x00、`level`=+0x2A、跨度 0x58。金手指写死 enemy species 后 4/4 帧一致 |
| BUG-12 | 敌方血条名字栏破碎残字 + 绿块（对话框里名字却正确） | 血条名走的是与对话框**不同的表**；具体的表/打印路径未定 | 动态（写死 species 前后两版采集都是碎的，与 BUG-10 无关） | 未修 |
| BUG-13 | 队伍列表宝可梦名全是日文（fontNum=4/Small） | 名字经 `InitTextPrinter`（win=`0x03004170`，fontNum=4、textMode=1、文本在 IWRAM 栈缓冲）打印，**取源函数 `0x0803B11C` 命中 0 次**（队伍不走它）。三条修法均失败：字符流换源→输入停摆；入口改 r1→崩溃（`0x464E`=`mov r6,r9` 误读） | 动态（GDB `InitTextPrinter`/`PrintNextChar`/`PartyNickSrc` 断点） | 未修 |
| BUG-14 | 名字写进存档 → 串回日版乱码 | Gen3 名字字段**定长**（`nickname[10]`/`playerName[8]`），中文 1 字 4B、3 字 12B 塞不下 ⇒ 截断或越界（实测队伍内存 nickname 尾部有 `75 53 57` 校验 magic 残渣） | 动态 + 火红 ROM 对照 | 未修（火红式解耦方案已调研） |

## 五、反复踩过的「假根因」（别再信）

| 说法 | 为什么是错的 |
|---|---|
| 「墨量 605>561，判定 PASS」 | 墨迹量证明不了字对不对（真实反例：屏幕上是「战消/背筐/羽跑」） |
| 「诊断显示写的是纯背景，之后被另一条路径改写」 | 那条「第二条路径」其实就是**同一渲染器的回绕行**（BUG-9 定案）；不是游戏代码 |
| 「`2*col` 是 bug，改成 `step=1`」 | `2*col` 是行间隔离机制；改 `step=1` 会撞行，已实测回滚 |
| 「12px 装不下，要 8+4 双遍渲染」 | 火红实测每字同样占 4 tile；单遍合成已够用 |
| 「换 charBase 给文本私有 block」 | 游戏按**绝对地址** `0x06008000` 解压图形，改 charBase 必花屏 |
| 「符号表说这里是函数」 | `0x08004290` 被标 GetExtCtrlCodeLength，实际是 `StringCopyN(上限5)`；文本域 85 个符号只有 18 个是真函数头 |
| 「图鉴分类名要追加后缀」 | 后半截是占位串 `？？？？？ポケモン` 的尾巴，不该改译文也不该 nop 原版流程 |
| 「钉一次 RNG + hunt ⇒ 两侧遇敌完全一致 ✅」（`battle_full` 注释曾标「勿改」） | **实测不成立**。三种钉 RNG 写法（一次/hunt、每格重钉+walk、转场后重钉）全部让两侧遭遇不同物种。poke 只决定写入瞬间的 RNG，到遇敌判定还要跑几十帧 |
| 「`SPECIES_ENEMY=0x02024AD8` 能读对手物种」 | 那是 **Emerald** 的地址；Ruby 上读出全 0，官方 `analyze_battle_menu_frames.py` 也返回 `species: null` |
