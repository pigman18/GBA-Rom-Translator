# 固定遇敌重构：运行时注入（不改 ROM 文件）

> 2026-11-27 实测定案。方案 A：pokecart 写 ROM 域。
> 本文所有结论都来自 bot 实跑，不是推演。

---

## 1. 结论速览

| 需求 | 能否 | 手段 |
|---|---|---|
| 指定**物种** | ✅ | 遇敌表 12 槽全改（`pokecart`） |
| 指定**等级** | ✅ | 遇敌表 `minLevel/maxLevel` |
| 指定**技能** | ⚠️ 间接 | 改等级 → 野怪按等级取招（实测 Lv13→Lv50 招式全变） |
| 指定**六维 IV/EV** | ❌ | Gen3 野怪 IV 由 `Random()` 生成，不走遇敌表 |
| 指定**性格/性别** | ❌ | 由随机 personality 决定 |
| **不修改磁盘 ROM** | ✅ | 改的是 emu.memory.cart0 域，退出即失效 |
| **两侧都用注入** | ✅ | 同一份 Lua 两侧同跑，天然保证同一只怪 |

## 2. 为什么不是「写 gEnemyParty」

两条路都实测失败，记录在此避免重犯：

### 2.1 写明文派生区（失败）

`gEnemyParty[0]`（日版实测 `0x030044F0`）的
`+0x54 level` / `+0x56 curHP` / `+0x58 maxHP` / `+0x5A atk`：

```
[POKE] f=7606 #1 @0x03004544 w1 0xD -> 0x4D ; level 12->77     ← 复核成功
[PROBE] f=7613 tag=enemy_after ...                            ← 读回仍是 0D
```

**poke 写后复核通过，但下一次读回已变回原值** —— 游戏每帧从加密区重算并回写这些派生值。
血条无任何变化（仍 `Lv13`）。

### 2.2 写加密区（失败）

`+0x20` 起 48B（species / exp / IVs / moves 都在这里），配好 personality、
重新加密、算好 checksum 后写 17 处：

```
[PROBE] tag=after ... pers 已变成 6A2234D4，species 变成 367
```

**整只结构被游戏重建了** —— `gEnemyParty` 不是战斗显示的数据源。

### 2.3 关键教训

> Gen3 战斗显示的数据源不是 `gEnemyParty` 本身；在战斗中途改它会被重建。
> 要改就改**遇敌表**（生成新怪之前），而不是改生成结果的容器。

## 3. 可行方案：pokecart 写 ROM 域

### 3.1 为什么普通 poke 不行，pokecart 行

| 方式 | 结果 | 原因 |
|---|---|---|
| `emu:write32(0x083786D0, ...)` | ❌ `复核失败: 写入 0x1621919 读回 0x1200C0C` | 走 CPU 总线，GBA ROM 是只读掩膜，写被丢弃 |
| `emu.memory.cart0:write32(off, ...)` | ✅ 12 槽全部写入成功 | MemoryDomain 用**相对域偏移**，绕过总线保护 |

mGBA scripting API 的 GBA 域（官方文档）：

```
Key   Name  Base
cart0 ROM   0x08000000
wram  EWRAM 0x02000000
iwram IWRAM 0x03000000
```

`MemoryDomain.write*(address, value)` 的 address 是**相对该域 base 的偏移**，
所以总线地址 `0x083786D0` 对应偏移 `0x3786D0`。

### 3.2 实测效果

```
[PCART] #1 @0x083786D0 (off 0x3786D0) w4 0x1200C0C -> 0x1621919 ; slot0
...（12 槽全部成功）
[PCART] step=12 共写 ROM 12 项
```

敌方血条：**`负电拍拍 Lv13` → `负电拍拍 Lv25`** ✅

### 3.3 遇敌表结构（复用 fix_encounter 的既有知识）

```
map 0:25 (Route110)  wildPokemon = 0x083786D0，12 槽 × 4B
每槽： minLevel u8 | maxLevel u8 | species u16
      例：0x01621919 = lv25-25, species 354
```

12 槽全改成同一 species 的**原因**（源码依据）：
`ChooseWildMonIndex_Land()` = `Random()%100` 分 12 档返回 0..11。
12 槽同物种 ⇒ 无论 RNG 落哪档结果都一样，随机性被消灭而非追逐。

## 4. 已知边界：六维与技能

### 4.1 技能可以「间接」控制（已实测）

Gen3 野生宝可梦的技能由 `GiveMonInitialMoveset` 按「等级可达的最近 4 招」生成。
所以改等级 = 改技能。实测同一只负电拍拍：

| 等级 | 解密出的招式（编号） | 中文名 |
|---|---|---|
| Lv13 | (45, 86, 98, 270) | 吼叫 / 打雷 / 愤怒 / 戏法 |
| Lv50 | (268, 87, 226, 97) | 挑衅 / 落石 / 再来一次 / 电光一闪 |

⇒ **测招式名文本 BUG 够用**：想要某招，就调到对应等级。

### 4.2 六维 IV/EV 无法指定

野怪的 IV 由 `CreateMon` 用 `Random()` 逐项生成（0..31），性格/性别由 personality 决定。
这些**不经过遇敌表**，运行时无法指定。

若确实需要固定六维，只有两条路：
- **改源码重编译**（pokeemerald `createmom` 路线）—— 工程量大，且要动 ROM
- **在生成后立刻改 gBattleMons** —— 需要先找到 gBattleMons 的真实地址
  （本轮搜 species 在 EWRAM 0..0x40000 命中 0 处，说明它不在这段，需继续定位）

对当前目标（修文本 BUG）而言，六维不重要，**不必强求**。

## 5. 工具用法

### 5.1 生成 pokecart 语句

```bash
# 把 map 0:25 的 12 槽改成 species 354 / lv50，输出 Lua
python scripts/encounter/fix_encounter.py apply --map 0:25 \
    --species 354 --level 50 --emit-lua work/enc_354_lv50.lua
```

产物形如：

```lua
local WILD = 0x083786D0
api.pokecart{
    { addr = WILD + 0x00, width = 4, value = 0x01623232, note = "slot0 sp=354 lv50" },
    ...（12 条）
}
```

### 5.2 在场景里使用

```lua
L.preamble(api)
api.pokecart{
    { addr = 0x083786D0, width = 4, value = 0x01623232, note = "slot0" },
    ...（12 条，或 dofile 上面的文件）
}
-- 然后正常触发遇敌（香甜气息路线）
```

### 5.3 诊断工具

```bash
# 读内存并落盘（scene.log 里 [PROBE] 行）
api.probe{ addr = 0x030044F0, len = 100, tag = "enemy" }

# 在 dump 里找队伍结构（按 level/hp/stat 特征）
python scripts/encounter/find_party.py <run目录>

# 解密 Gen3 加密子结构（验证 species/IV/技能）
python scripts/encounter/build_mon.py --species 354 --level 50 --verify
```

## 6. 两侧对照（用户要求：origin 也用注入）

原则：**同一份 Lua，两侧都跑**。

```
python bot/run.py POKEMON_RUBY_AXVJ00 <场景> \
  --save    roms/outputs/POKEMON_RUBY_AXVJ00_translated.sav \
  --origin  roms/origin/POKEMON_RUBY_AXVJ00.gba \
  --translated roms/outputs/POKEMON_RUBY_AXVJ00_translated.gba
```

场景里只写一次 `api.pokecart{...}`，bot 会对两侧各执行一次 ⇒ 两侧遇到同一只怪。

**注意**：`pokecart` 有和 `poke` 相同的前置门槛 —— 必须 `prove` 成功（存档已载入），
否则改的是尚未初始化/错误的内存态。这是既有机制，不用额外处理。

## 7. 与旧方案（改 ROM 文件）的关系

| 方式 | 适用 | 缺点 |
|---|---|---|
| **旧：改 ROM 文件** | 需要跨多次运行保持一致 | 要维护多份 ROM 副本；改错了得重打包 |
| **新：pokecart 运行时注入** | 日常调试、临时换对手 | 每次启动都要重跑一遍（正常，本来就要跑场景） |

两者保留。`fix_encounter.py` 的 `--rom`（写文件）与 `--emit-lua`（出 Lua）并存。
**日常调试优先用 `--emit-lua`**，因为它不产生 ROM 副本、不碰产物。

## 8. 本轮踩坑记录

1. **符号表的队伍地址不能直接用**
   `pokeruby_jp.sym` 里 `gPlayerParty=0x03004360` / `gEnemyParty=0x030045C0`
   标着 `KEEP-US`（沿用美版）。实测日版真实值是
   `gPlayerParty=0x03004290`、`gEnemyParty=0x030044F0`（差 0xD0）。
   判定方法：在战斗里 dump IWRAM，按「level 1..100 + curHP<=maxHP + 六维合理」
   搜 100B 结构（脚本 `find_party.py`）。

2. **写 ROM 必须走 MemoryDomain**
   `emu:write8(0x08xxxxxx)` 静默失败（写后读回是原值）。
   必须用 `emu.memory.cart0:write8(offset)`，offset = 地址 - 0x08000000。

3. **改 gEnemyParty 是死路**
   粒子级实测两次（明文区 / 加密区）都被游戏重建覆盖。
   要在「生成之前」改，即改遇敌表。

4. **加 bot 动作要三处都接**
   ① 参数校验分支 ② settle_begin 分支 ③ 执行分支。
   漏任一处会静默不执行（Lua 语法仍合法，`lint_lua.py` 也查不出来）。
   本轮加 `probe` / `pokecart` 都是三处齐改。
