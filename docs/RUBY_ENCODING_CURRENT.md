## 一、三套通道，各自的职责边界

现有方案不是「三选一」，而是**一条优先级链**，每个条目在编排期（translate 阶段）一次性定死走哪条，build 阶段只照 `type` 直写、不再改路径。

```
plan_entry() 决策顺序（src/meowth/translate_plan.py:623）

  1. relocate   指针重定向到扩展区   ← 有可用指针 + 模块允许
  2. replace    原地写槽：
                 2a. len(encoded) <= slot_cap  → F900 整串原地
                 2b. 放不下但 slot_cap >= 5   → F980 短语引用原地
  3. slot       SLT2 运行时查表拦截   ← 兜底通路
  4. keep       保留日文原文
```

**关键反直觉点**：F980 不是「更差的通路」，而是 **replace 通路内部的越槽降级方案**。F900 和 F980 在 `translate.build.json` 里都是 `type: "replace"`，区别只在于条目上有没有 `phrase_code` 字段。

## 二、F900：单字内联（4 字节/字）

### 编码格式

```
F9 00 hi lo      单汉字，hi/lo 是字库码位（pack_glyph_index）
F9 00 hi lo ...  FF
```

- 每个汉字固定 4 字节（`F9 00` + 2 字节码位）
- 流以 `FF` 结尾
- 渲染走 `CHS_GLYPH_ADVANCE_PX = 12` 像素步进
- 字库 `FontChsNormal @ 0x09000000`，每字 128 B（16 字节 × 8 行？实际 4 个 32B tile）
- `CHS_FONT_GLYPH_MAX = 7168`

### 实测分布（translate.build.json）

**F900 原地写入只有 153 条**，占 replace 通路的 2.1%。这是最容易被误解的地方——F900 现在几乎不承担「原地写长文本」的任务，它的主战场在 **relocate**（2,221 条）和 **PhraseTable 内部**（短语表里存的就是展开后的 F900 流）。

| 槽宽 | 条数 | 典型 |
|---|---|---|
| 5 | 63 | 属性名（2 汉字 + FF） |
| 56 | 55 | 招式说明（一整块固定宽度） |
| 8~40 | 35 | 各类短名 |

样本（`bl=5`，属性名）：
```
orig = 45 08 ff
tgt  = f9 00 03 63 ff
```

样本（`bl=56`，招式说明，多个 F900 串成一行）：
```
orig = 61 86 a0 9d ... ff
tgt  = f9 00 0f 71 f9 00 0c 1b ... fe f9 00 04 cc ff ff ff
```

注意 `fe` 是换行控制码，`ff` 是填充。**说明 F900 流里可以直接夹原版控制码**（`charmap` 的 00-FF 已含日版控制码，整句 encode 即可，无需按控制符拆段）。

### 为什么 relocate 条目也用 F900

`relocate` 只是把**字节写到哪**改了（扩展区），**字节长什么样**仍然是 F900 流。看实测样本：

```
mount 地点名  id=axvj_e568c7b5688c  addr=0x083BED07  bl=7
orig = 70 65 73 5c 63 80 ff
tgt  = f9 00 0c 51 f9 00 07 62 f9 00 0c 15 ff
ptr  = 1 个指针源
```

7 字节的日文槽（3 个假名 + FF），中文 3 个汉字需要 12 字节 + FF = 13 字节，放不下 → 写扩展区 + 改指针。

## 三、F980：短语表（5 字节/条，码位引用）

### 编码格式

```
F9 80 hi lo      短语引用，code = (hi<<8)|lo
F9 80 hi lo FF   完整条目流
```

- 槽里只放 5 字节（`F9 80 xx xx FF`），正文在 PhraseTable 里
- **code 空间 0x0000~0xFFFF**，实测最大用到 10594

### PhraseTable 布局（固定 VMA，C 代码直读）

```
PhraseOffsets @ 0x08810000   u32[code]，哨兵 >= 0x01000000 表示空
PhraseTable   @ 0x08820000   PCS 流（F900 展开流 + 控制码），FF 结尾
```

生成：`src/meowth/build_rom_data.py`（`ADDR_PHRASE_OFFSETS = 0x08810000` / `ADDR_PHRASE_TABLE = 0x08820000`）
钉死 VMA：`src/meowth/font_patch.py:637 pin_phrase_table_vma()`

**约束**：`font_patch._GAME_BIN_MAX = 0x10000` —— hook 的 C 代码不能超过 64KB，因为 `PhraseOffsets` 在 `0x08810000`，而 game.bin 从 `0x08800000` 起。

### 短语表内容

`translate.build.json` 的 `phrases` 是一个**数组**（不是对象），10,595 条字符串，按长度+字典序排列，**数组下标就是 code**。

```
phrases[0]   = "一般"
phrases[1]   = "上菜"
phrases[2]   = "下载"
...
```

生成时机：`src/meowth/core/engine.py:2196` 优先复用 `translate.build.json` 里的 `phrases`，保证 PhraseTable 与 build.json 的 F980 码一致。

### 触发条件

`src/meowth/core/engine.py:2228`：

```python
# Auto-switch F9 00 → F9 80: ONLY fixed-slot modules (stride/struct).
# Trusted-ptr modules (scan/剧情/…) keep full F9 00 and relocate.
if not module_is_fixed_slot(_gid, mid):
    continue          # scan/pointer 类模块不升级
bl = en.get("byte_length", 0)
if bl < 5:
    continue          # 太小放不下 F9 80
raw_len = len(_raw_enc(t))
if raw_len > bl:      # 只有越槽才升级
    code = len(_pc)
    _pc[s] = code
```

**所以 F980 的准入条件是三条同时满足**：
1. 模块 `type` ∈ {`stride`, `struct`}（定长槽）
2. `byte_length >= 5`
3. 原文编码长度 > 槽宽

但 `translate_plan.plan_entry()` 里还有第二条升级路径（`:708`）：relocate 不可用时，replace 内部 `slot_cap >= len(ph_prefix) + 5` 也会升 F980。所以实际 7,144 条远多于 `module_is_fixed_slot` 的那几个模块——剧情（scan 类型）也有大量 F980，说明它们的 relocate 指针不够用。

### runtime_ph_prefix（占位前缀）

`translate_plan._prepare_encoded():408` 有个 `_split_runtime_placeholder` 机制：某些条目译文里要保留运行时占位字节（如宝可梦名前的标记），占位字节写在槽头、短语只存**后缀**。

```
encoded = ph_prefix + encode(suffix) + FF
```

所以在 `translate_plan:709` 判空时用的是 `slot_cap >= len(ph_prefix) + 5`，而不是硬编码 5。

## 四、SLT2：实时替换表（运行时查表，不动 ROM 原文）

### 这一层解决什么问题

用户原话：
> f980 存不下的，比如选项的 是 / 否，用 slt2
> 一些旧日版汉化版，和常规日版串档时，会出现宝可梦名乱码问题，因为它们是宝可梦那块写入了汉化内容，导致存档也乱了，因此引入 slt2 不改变原本编码，从而实现汉化宝可梦名查看

**核心特性：ROM 里的原文一个字都不改。** 运行时按 `(日文字节 → 中文字节)` 的映射表实时替换。这正是「不改变原本编码」的实现方式——存档里的宝可梦名仍然是日文字节，所以串档不乱。

### 表格式（v2 分桶）

`src/meowth/translated_slot.py`：

```
Header (.align 4):
  u32 magic 'SLT2' = 0x32544C53
  u32 n_buckets(u16 LE) | max_jp_len(u16 LE)
  u32 bucket_offset[n_buckets + 1]     相对 SlotTable 标签的字节偏移

Entries（按 jp_bytes[0] 分桶）:
  key(4B FNV1a(jp)) | jp_len_le16(2B) | jp_bytes | chinese_bytes(... 0xFF)
```

- 地址 `SLOT_TABLE_ADDR = 0x09EA0000`
- 分桶数 `SLOT_TABLE_N_BUCKETS = 256`（按日文首字节）
- 哈希 `FNV-1a`，`h = 0x811C9DC5`，`prime = 0x01000193`
- legacy 平铺布局（`key|len|jp|cn … 4x00 哨兵`）仍被 runtime 支持：magic 不匹配自动回退线性查找

### 运行时匹配（`hook/src/text/text_translter.c`）

```c
TranslateHandleChar():
  if (c != CHS_ESCAPE)                     // 非 F9 开头
      return slot_lookup_and_draw(win, c); // → SLT2 查表
```

`slot_lookup_v2()` 用 `cur_char` 直接定位桶，只遍历桶内条目，流窗口以 `max_jp_len` 封顶，增量 FNV 前缀哈希与条目 key 比对。

实测注释：801 条 / ~94 个首字节 / 最大桶 ~43 条 → 查找成本比 v1（每条重哈希）降约三个数量级。

### ⚠️ 定长名称表的实测判定（2026-11-04 三轮回查后的最终结论）

> 第一版把「第一条名称字段地址」当作「表基址」去搜字面量，招式名/特性名报 0 命中，

### 槽结构（决定搬走后能否放大）

> ⚠️ **texts.json 的 stride 不能直接当事实**——它是为「全 replace+slt2」妥协出来的配置，
> 后续方案必然大改。以下几何全部从 ROM 字节独立反推（`probe_geometry_ff.py`），
> 只把 texts.json 当候选值来验证。

**关键判据修正**：ruby 定长表用 **FF 填充**（不是 00）。
```
0x1CAD04: 1a 10 08 ff ff ff ff ff   ← 3B 文本 + 5×FF = stride 8
0x1CAD0C: 06 27 13 61 86 a0 9d ff   ← 7B 文本 + 1×FF = stride 8
```
按「FF 后全 00」判会误判成 26% 不合规，改用「FF 后全 FF」后 stride=8 合规 **100%**。

| 表 | ROM 实测 stride | 合规率 | texts.json 值 | 一致 |
|---|---|---|---|---|
| 招式名 `0x1CAD04` | **8** | **100%** | 8 | ✅ |
| 属性名 `0x1CBB0C` | **5** | **100%** | 5 | ✅ |
| 宝可梦名 `0x1CA354` | **6** | 54%（前 120 项含表尾其他数据） | 6 | ✅ |
| 特性名 `0x1CBC4C` | 8（前 120 项超出 77 项范围） | 13% | 8 | 待细查 |

### ⭐ 决定性结论：遍历全部硬算 `index*stride`

反汇编每个基址字面量的使用点（`probe_index_arith.py`），**6/6 张表都是乘法展开**：

| 表 | 反汇编证据 | 等价运算 |
|---|---|---|
| 特性名 `0x09C6C4` | `lsls r0,r4,#2` / `adds r0,r0,r4` / `lsls r0,r0,#2` | `(i×4+i)×4 = i×20`（20 字节/项） |
| 道具名 `0x0A538E` | `lsls r1,r0,#2` / `adds r1,r1,r0` / `lsls r1,r1,#3` | `(i×4+i)×8 = i×40` ✅ |
| 图鉴分类名 `0x08C1D6` | `lsls r0,r1,#3` / `subs r0,r0,r1` / `lsls r0,r0,#2` | `(i×8−i)×4 = i×28` ✅ |
| 秘密基地装饰名 `0x0AF2C8` | `lsls r0,r1,#3` / `subs r0,r0,r1` / `lsls r0,r0,#2` / `adds r2,#0x14` | `i×28 + 0x14` ✅ |
| 属性名 `0x02B6B0` | `adds r1,r1,r0`（基址） + `lsls r2,r2,#2` | 固定偏移访问 |
| 招式名 `0x02B53A` | `adds r1,r1,r0`（基址） + `lsls r0,r6,#0x14` | 硬算字节偏移 |
| 宝可梦名 `0x00CD02` | `lsls r1,r0,#1` / `adds r1,r1,r0` / `lsls r1,r1,#1` | `(i×2+i)×2 = i×6` ✅（流式扫描） |

**⇒ stride 是编译进代码的常量，不可变。** 整表搬走时必须保持 stride 完全一致，只允许改基址字面量。

### 各表中文放不放得下（F900 4B/字 vs F7 3B/字）

| 表 | stride | F900 | F7 |
|---|---|---|---|
| 招式名 | 8 | 2 字=9B ✗ | 2 字=7B ✓ |
| 特性名 | 8 | 2 字=9B ✗ | 2 字=7B ✓ |
| 属性名 | 5 | 1 字=5B ✓ | 1 字=4B ✓ |
| 宝可梦名 | 6 | 1 字=5B ✓ | 1 字=4B ✓ |

**这是 F7 的实质价值**：让 stride=8 的表能放下 2 个汉字（F900 放不下 → 现在只能走 F980）。
招式名 354 + 特性名 77 = 431 条，换 F7 后 2 字以内的名字全部能原地装下，直接消灭这部分 F980。

> ⚠️ **3 字以上的名字不能靠缩写解决。**
> 用户明确：缩写是实在没办法才允许，不是方案选项。正确做法见下节——**火红是整表换成指针表**。

### ⭐⭐ 火红对定长表的核心手法：整表换成「指针数组 + 变长串」

> 本节推翻了本文档此前两版的说法。用户指出「整表换变长本来就是允许的」，实测火红坐实：
> 火红**没有**采用「缩写」，而是把定长表整张换成指针数组。

**实测证据（`probe_pointer_tables.py` / `probe_ptr_table_confirm.py` / `probe_orig_arrays.py`）**

火红汉化版里找到 70 个指向中文区的「≥8 元素连续指针数组」，特征完全一致：

| 数组 | 元素数 | 原版同位置 | 目标串长度 | 长度种类 |
|---|---|---|---|---|
| `0x726124` | **354**（= 招式数） | **全 FF** | 47~64B | 31 种 |
| `0x71BFB4` | 251 | 全 FF | 6~15B | 5 种 |
| `0x71C404` | 135 | 全 FF | 6~15B | 4 种 |
| `0x71F234` | 79 | 全 FF | 9~18B | 8 种 |
| `0x711940` | 79（≈ 特性数） | 全 FF | 51~64B | 18 种 |

数组内容长这样（`0x726124`）：
```
+00: 74 0a 72 08 → 0x08720A74   f7 00 4e f7 00 75 f7 02 ad ...  (20B)
+04: a4 0a 72 08 → 0x08720AA4   f7 00 44 f7 01 e2 f7 01 23 ...  (20B)
+08: f0 0a 72 08 → 0x08720AF0   ...
```

**结构 = 「变长中文串区」+「指针数组」两块拼在一起，放进原版全 FF 的空白区。**
代码侧靠「基址 + 固定偏移」访问，所以数组本身没有独立基址字面量（实测用任何对齐方式搜都是 0 处引用）。

**全局统计（`probe_orig_arrays.py`）**

```
汉化版 ≥16 元素指针数组:        255 个
其中原版同位置也是指针数组:      229 个 (89.8%)
```

⇒ **89.8% 是「原地把指针值改成指向中文串」**，代码完全不用动；
剩下 10.2% 是新增的指针表（对应原版靠 `index×stride` 硬算的那些表）。

**这就是「整表换变长」的火红实现方式，而且用户确认这是允许的。**

### 对 ruby 的三条可行路线（按火红经验排序）

| 路线 | 做法 | 适用 | 代价 |
|---|---|---|---|
| **A. 整表换指针表** | 原定长表 → 指针数组 + 变长串，全放新区；改代码里那段 `index×stride` 机器码 | 招式名/特性名/属性名/道具名/图鉴分类名/装饰名/树果名 **全部适用** | 需改 6~7 处代码；但一次性消除所有超槽问题，**无缩写** |
| **B. 只改编码 F7** | 保持 stride 与表结构，只把 F900 换 F7 | stride=8 的表能放 2 汉字（431 条） | 零风险；但 3 字以上仍超槽 |
| **C. 混用** | 2 字内走 B（原地 F7），3 字以上走 A（该表换指针表） | 折中 | 实现复杂 |

**A 是火红验证过的正解，也是唯一能彻底不用缩写的路线。** B 只能吃下 431 条，其余（招式名里 3 字以上的、图鉴分类名等）仍需 A。

对应的 ruby 代码改动点已定位（`probe_index_arith.py`）：
- 招式名 `0x02B53A` 附近
- 特性名 `0x09C6C2~0x09C6DC`（`lsls#2/adds/lsls#2` = ×20）
- 属性名 `0x02B6B0`
- 道具名 `0x0A5390`（×40）
- 图鉴分类名 `0x08C1E6`（×28）
- 秘密基地装饰名 `0x0AF2D2`（×28 + 0x14）

### 火红对照实测（2026-11-04，origin-vs-translated 逐字节）

用户质疑「内联会很慢」，实测火红确认：

| 项 | 实测值 |
|---|---|
| 汉化新增中文区 | `0x6D0000..0x730000`，约 **384 KB** |
| 该区在原版 | **全 FF 空白**（FF 数 65536/65536） |
| 该区在汉化版 | 填满 F7 中文串（F7 数 18,390 / 64KB） |
| 指向该区的指针 | 原版 34 个 → 汉化 **7,787 个（Δ+7,753）** |
| 原日文名表区 `0x3A0000..0x3C0000` | 差异仅 **1.1%**（1,455/131,072），**主体原样保留** |
| 原日文名表被引用 | 原版 3,505 → 汉化 3,372（Δ-133） |

**结论：火红是「整表搬到新区 + 批量改指针」，绝不是内联，也没有原地改写日文表。**
7,753 个指针改向证明这是数据级的静态改写，运行时零查找成本——这正好解释为什么火红不卡，而 ruby 的 SLT2（1,485 条运行时哈希查表）在千条以上会卡。

## 七、火红五类文本的实测结论（已定案）

> 来源：`docs/research/FIRERED_FULL_LOGIC.md` §2，基于 6,517 条中文段逐个定性（脚本 `31_finalize.py`）。
> **这一节不是待查事项，是已完成的研究**。原始需求里的 5 个问题全部有答案。

### 总账

| 容器 | 段数 | 占比 | 平均长 | 段首有指针 |
|---|---|---|---|---|
| 直指针 | 3,597 | 55.2% | 49.3 | 100% |
| 无特征（无指针、非块） | 1,757 | 27.0% | 65.9 | 0 |
| 直指针 + 超短 | 499 | 7.7% | 5.8 | 100% |
| 各种等长块成员 | 664 | 10.1% | — | 多数无 |

指针可达率 67.3%，完全无指针 32.7%。

### 第 1 类：常规文本（有指针 / 无指针）

**有指针** → 改指针指向新串，原串留成孤儿（97.9% 逐字节原样保留）。

**无指针** → **火红没有「缩短译文」这条策略**。它把整串搬走、改指针，原串留孤儿。

那 32.7% 的「无指针段」不是无处安放，而是：
- 被**结构体基址 + 偏移**访问（名字表 `0x0871F446` 用 `index × 步长` 算）
- 被**上一级容器指针**整体引用（块级指针）

⇒ **这条推翻了原始假设**。「无指针就缩短译文」是本工程的做法，不是火红的。

### 第 2 类：等长块（定宽补 00）

**不是「整块一个指针」，而是「每个元素各自一个指针」或「未对齐的结构体字段」。**

实测 68 个等长块：

| 情况 | 块数 | 特征 |
|---|---|---|
| 块首被引用 + 元素引用率 100% | 10/68 | **每个元素各自有指针** |
| 块首无引用 + 元素引用率 17~67% | 58/68 | 结构体字段，基址+偏移访问 |

典型 `0x086D5CC0`：16 段，步长 12，块首 ×1，元素 16/16 全被引用。

⇒ **「整块改一个指针」在火红上不存在。** 这是原始假设中唯一被直接否掉的一条。

### 第 3 类：等距块（00 分隔）

**就是「串后紧跟 FF」的普通串流，没有专门的容器。**

判据 `gap == 1`（串尾 FF 后直接是下一串）扫出 81 个「≥4 段紧邻」的块：

```
块首            段数   块首指针   元素被引用   段长样本
0x08702608      34      无         14        [35,35,35,35,35,35]  ← 等长
0x0871F446     356      无          0        [20,18,18,12,21,9]   ← 变长（名字表）
```

⇒ 变长内容靠串尾 FF 自然分隔，无额外机制。

### 第 4 类：超短文本（≤6 字节）

**没有特殊处理。98.8% 都有独立指针。**

508 条 ≤6 字节中文段：L3:31、L4:1、L5:3、**L6:473**（L6 = 2 汉字 + FF）。有指针 502 条。

```
0x086D27D8 L=6 汉字2 ptr×1  f7 02 1a f7 03 66 ff
0x086D2974 L=6 汉字2 ptr×4  f7 00 60 f7 00 39 ff
0x086D2B10 L=6 汉字2 ptr×4  f7 00 ec f7 00 26 ff
```

⇒ 「是 / 否」这类选项在火红里就是普通 6 字节串，有独立指针可改。**这正是火红不需要 SLT2 的原因。**

### 第 5 类：宝可梦名（串档不乱）

**火红没有在原版物种名数据上写中文，它另做了一张中文显示表，原版数据结构完全保留。**

证据：`0x0871F446` 起是「00 补齐 + 中文名 + FF」的变长项表，前 30 项：
```
[0] 00×14 | f7 02cf f7 0271 | ff                          汉字2
[1] 00×9  | f7 01aa f7 01e2 f7 0277 | ff                  汉字3
[2] 00×6  | f7 0385 f7 0332 f7 02b3 f7 02d9 | ff          汉字4
[9] 00×6  | f7 0234 | ff                                  汉字1
```
原版 `0x0871F000..0x08722000`（73,728 B）非 FF 字节 = 0，完全空白。

⇒ **与 SLT2 同思路（原数据不动、另建显示表），但实现更干净**：火红是 ROM 里的静态表 + 改读取路径，SLT2 是运行时哈希查表。

### 五类对照表

| 五类 | 火红做法 | ruby 现状 | 判定 |
|---|---|---|---|
| 常规·有指针 | 改指针，原串留孤儿 | relocate 2,221 条 | **一致** |
| 常规·无指针 | **不缩短**，整串搬走改指针 | 缩短 or keep | **反向** |
| 等长块 | **每元素各自一指针**，非整块一个 | 硬禁 relocate，全挤 F980 | **差异** |
| 等距块 | 普通串流，FF 自然分隔 | 同 | **一致** |
| 超短（≤6B） | 98.8% 有独立指针，无特例 | F980 / F900 塞槽 | **差在指针识别** |
| 宝可梦名 | 另建显示表，原数据一字节不动 | SLT2 | **同思路** |

### 对本工程的直接含义

1. **`NO_RELOCATE_TYPES` 禁掉 stride/struct 与火红做法相反** —— 火红等长块恰恰是「每个元素各自一个指针」。
   这不是「整块改指针」，而是「逐元素改指针」，也就是**把定长表按 stride 拆成 N 个独立 relocate**。
   现状代码把整张表当整体、不允许动，所以才退到 F980。

2. **「无指针就缩短译文」应当取消** —— 火红证明无指针段实际是「基址+偏移访问」，只要能定位基址，就能整块搬走。

3. **SLT2 的思路是对的，火红也是这么做的** —— 差别在于火红把显示表放进 ROM 静态区并改读取路径，我们做成了运行时哈希表。要「移除 SLT2」，等价于把运行时查找改成「ROM 静态表 + 改读取路径」，**不是取消这个机制**。

## 九、一句话总结

**现有方案是「relocate 优先、replace 降级、slot 兜底」的三级链**，F900 和 F980 是 replace 内部的两种编码粒度，SLT2 是唯一「不动 ROM」的通道。

对照火红实测，方向 1 的正确结论是：

1. **火红的定长表是「整张换成指针数组 + 变长串」** —— 实测 354 元素指针表（`0x726124`）对应 354 个招式，目标串 47~64B、31 种长度；原版该位置全 FF。全 ROM 255 个指针数组里 **229 个（89.8%）是原地改指针值**，代码不动；10.2% 是新增数组（原版靠 `index×stride` 硬算的表）。

2. **ruby 的 6/6 张定长表全是硬算 `index×stride`** —— 乘法展开已定位到具体指令（`lsls#3/subs/lsls#2` = ×28 等）。所以 ruby 属于火红那 10.2% 的情况，**必须改代码**才能换变长。

3. **缩写不是方案** —— 用户明确只有没办法才用。正确路线是整表换指针表，代价是改 6~7 处遍历代码。

4. **F7 是第一刀，不是终点** —— F7 让 stride=8 装下 2 汉字（431 条），零风险；但 3 字以上仍需整表换指针表。

5. **运行时查表才是性能痛点** —— 火红纯静态数据零开销；ruby 的 SLT2 是运行时 FNV 哈希查表，千条以上必卡。方向 1 的实质是把运行时成本转成构建期成本。

### 下一步（按火红实测修正）

| 优先 | 事项 | 涉及条数 | 依据 |
|---|---|---|---|
| 1 | **招式名/特性名换 F7** | 431 | stride=8 装不下 F900 的 2 字（9B），F7 只需 7B ✓。零风险，先吃掉这批 |
| 2 | **招式名/特性名/属性名 整表换指针表** | 449 | 火红 354 元素指针表实测（`0x726124`），彻底解决 3 字以上超槽 |
| 3 | 道具名/秘密基地装饰名 整表换指针表 | 402 | stride 40/28 硬算，需改 `0x0A5390`/`0x0AF2D2` |
| 4 | 图鉴分类名 整表换指针表 | 386 | stride 28，改 `0x08C1E6` |
| 5 | 剧情 3,550 条「指针不够」重查 | 3,550 | F980 最大头（49.7%），火红证明「无指针」多半是基址+偏移 |

### ⚠️ 三个必须记住的约束

1. **stride 不可变，除非同时改代码** —— 6/6 张表遍历硬算 `index*stride`（乘法展开已定位到具体指令）。要改成变长，必须改那段机器码（火红 10.2% 的新增指针表就是这么做的）。
2. **缩写不是方案** —— 用户明确：只有实在没办法才允许缩写，否则一律整表换变长/指针表。
3. **texts.json 不可当事实** —— 它是为「全 replace+slt2」妥协的配置，几何值需逐项对 ROM 复核（本文档 stride 已用 ROM 字节独立验证）。
