### ⚠️ 改 texts.json 必须遵守的四条（踩过坑）

**1. `end` 含末字节**

条数 = `(end − start + 1) // entry_size`，不是 `(end − start) // entry_size`。
按半开区间算会少一条，尾部结论全错。

已踩坑 3 次：

| 表 | 若写错 | 后果 |
|---|---|---|
| 树果名 | `end=0x3A14E8`（stride=28） | 42 条，丢末条 `ナゾ`；须 `0x3A1503` |
| 性格名 | `end=0x397248` | 24 条，丢末条 `きまぐれ`；须 `0x39724C` |
| （教训）| — | 改 `entry_size`/`start` 时**必须同步重算 `end`**，否则末条静默丢失 |

**2. 单模块独立重抽不代表生产行为**

`export_texts()` 按模块声明顺序做 FCFS 认领：先抽到的模块占住字节带，
后续模块跳过已被占用的部分（`exported_bands`）。

所以：
- 单模块单独 `extract_module()` 会得到**错误的结论**。
  实测把 `补漏剧情` 单独重抽 → **0 条**（它依赖前序模块的认领状态）。
- 验证 texts.json 改动必须用全流程模拟（`scripts/research/ruby/texts_37_simulate.py`：
  含 `ptr_index` 构建 + `resolve_filters` + `exported_bands` 排除 + `seen_addr` 去重）。
- **但模拟器的绝对条数也不能当验收依据**——它尚未完全复刻生产路径
  （缺 `omit_ranges` 等），与文件差 236 条。
  **验收要用备份 diff**（`work/_texts_backup_*.json` vs 现文件，逐模块比条数），
  这是不受任何工具偏差影响的硬判据。

**3. `addr_bands` 不是地址白名单；scan 的起点语义容易误解**

`addr_bands` 只是 `scan` 的别名（`texts_patcher.py:2581`），不是地址白名单。

**更正**：早前记过「`extract_scan` 的串起点由 `start` 之前最近的 `0xFF` 决定，
切子区间会打断串边界」——**这条是错的**。
实际逻辑（`src/meowth/extract.py:1041-1055`）：

```python
a = lo
while a <= hi:
    b = rom[a]
    if b == 0xFF or b == 0x00 or (b >= 0xF7 and b not in (0xFC, 0xFD)):
        a += 1; continue
    raw = read_pcs(rom, a, 512)   # 从 a 开始读
```

**从区间起点 `lo` 逐字节推进，遇 `FF/00/F7+` 跳过，第一个可打印字节即串首。**
实测起点偏移 0xF00 字节，后续串完全一致。所以 scan 切子区间是精确的。

真正的坑是：**起点若落在数据区，会把数据解成乱码**（`0x3B2000` 那 129 条就是这么来的）。
选起点前必须先证实「该位置是文本」，见第 4 条。

**4. 给区间前必须先测密度**

任何「某区间里有 N 条文本」的说法，**必须先在 ROM 上实测该区间的文本密度**，
不能从别处（旧报告、他人转述、自己上一版结论）拿数字直接用。

已踩坑：

| 错误 | 真相 |
|---|---|
| 「`0x3DA000..0x3DC000` 有 388 条战斗提示」 | 该区间在 ROM 里几乎为空（密度 0～1 条/0x400）；那 388 条是 `\CC08xx` **地图名提示**，多挂 `UI界面` |
| 「`0x3B2000..0x3B2A00` 有 67 条特性名副本」 | 该段前半是数据区；真词库 `0x3B219B..0x3B3900` 共 **926 条** |
| 「`scan` 切子区间会打断串边界」 | 不会。`extract.py:1041-1055` 是从 `lo` 逐字节推进、遇 `FF/00/F7+` 跳过，起点偏移不影响后续串 |
| 「`0x3B2` 词库无指针表」 | **有**：22 项 @`0x3B3E64`，被 9 处代码字面量引用。漏检原因是**扫描窗口只查了 4 个固定位置**，没覆盖 `0x3B3E64` |

**扫描全 ROM 找结构时，不要用几个固定窗口「抽样」——必须穷举全 ROM。**
漏检 `0x3B3E64` 的教训：`texts_55` 只查了 `0x3B2100`/`0x3B2800`/`0x3B3900`/`0x3B3A00`
各 `0x200`，而表在 `0x3B3E64`，正好落在所有窗口之外。

**这三条与我踩的「`end` 含末字节」是同一类错误：数字来自别处，就必须在自己这边重新验证。**

测密度的方法见 `scripts/research/ruby/texts_54_battle_bound.py`
（按 0x400 分桶统计每桶里「形态干净」的串数，画成直方图一眼看出哪里真有文本）。
