**三个最严重的问题**（按影响排序）：

1. **`树果名` 步长错一倍**——声明 `stride=56`，ROM 实际 `28`。只收到 21/43 条，漏掉 22 个树果名（改 stride 的同时 `end` 要改成 `0x3A1503`，否则仍丢末条 `ナゾ`）。

3. **`剧情` / `补漏剧情` / `UI界面` 三个模块都声明 `start=0x0 end=0xFFFFFF`**——机制上靠 filter 互斥，区域定义形同虚设，是「模块重复覆盖」的根源。

## 2. 两个几何错误（字节级证据）

### 2.1 树果名：stride 应为 28，不是 56

**声明**：`start=0x3A1050  end=0x3A14E8  entry_size=56  name_offset=0  n=21`

**ROM 实际字节**（`0x3A1050` 起，每 28 字节一个名字）：

```
0x3A1050  58 77 9a ff                    'クラボ'
0x3A106C  56 8b ff                       'カゴ'        ← 被 stride=56 整个跳过
0x3A1088  73 73 7e ff                    'モモン'
0x3A10A4  61 ae 8b ff                    'チーゴ'      ← 被跳过
0x3A10C0  65 65 5c ff                    'ナナシ'
0x3A10DC  6b 72 78 ff                    'ヒメリ'      ← 被跳过
...
0x3A14B0  5b 7e ff                       'サン'
0x3A14CC  5d 60 ae ff                    'スター'      ← 被跳过
0x3A14E8  65 90 ff                       'ナゾ'
0x3A1504  00 00 00 00 ...                ← 表外（指针区）
```

**结论**：真实步长 `28`，`0x3A1050`..`0x3A14E8` 覆盖 `クラボ`…`ナゾ` 共 **43 个树果槽**。
当前 `stride=56` 只能命中其中**偶数位**的 21 条，**漏掉 22 条树果名**（カゴ／チーゴ／ヒメリ…ナゾ 的另一半）。

**⚠️ 光改 stride 还不够**：`end` 也必须一起改。实测（`texts_21_fix_boundaries.py`）：

```
stride=28, end=0x3A14E8  ->  42 条，末条 'スター'@0x3A14CC
stride=28, end=0x3A1503  ->  43 条，末条 'ナゾ'  @0x3A14E8   ← 正确
```

因为 `end` 含末字节（条数 = `(end-start+1)//28`），`0x3A14E8` 只能容纳 42 个槽，
末槽 `ナゾ` 会掉出去。`0x3A1504` 起是 `00 00 00 00 …` 指针区，不能再往后。**正确 end = `0x3A1503`。**

**同时**：`desc_ptr_offset=12` 与 28 字节步长下的布局不符——第 0 槽 `0x3A105C` 是 `02 14 00 03`，第 12 字节 `0x3A105C` 处是 `02 14 ...` 而非指针。真实描述指针在 `+0x10`（`0x3A1060` = `79 09 3a 08`）。**若按 28 重规划，`desc_ptr_offset` 必须一并改 0x10。**

### 2.2 性格名：基址应为 0x3971E8，不是 0x397168

**声明**：`start=0x397168  end=0x39734C  stride=4  n=32`（指针表）

**ROM 实际**：`0x397168` 处是**名字正文**（`がんばりや` 等连续 FF 结尾串），不是指针表：

```
0x397168  37 2e 46 28 24 ff        'がんばりや'
0x39716E  0b 20 0c 37 28 ff        'さみしがり'
0x397174  25 03 06 2e ff           'ゆうかん'
...
0x3971E3  07 1f 39 2a ff           'きまぐれ'
```

真正的指针表从 `0x3971E8` 开始，25 个 u32 正好指向上面这 25 条：

```
0x3971E8 -> 0x397168  がんばりや
0x3971EC -> 0x39716E  さみしがり
...
0x397244 -> 0x3971DD  しんちょう
0x397248 -> 0x3971E3  きまぐれ      ← 第 25 个（索引 24）
0x39724C = 0x020EFF15          ← 表结束（非指针）
```

**结论**：
- 正确的 start = `0x3971E8`，正确条数 = **25**（性格总数，索引 0..24），不是 32
- 正确的 end = `0x39724C`。注意 `end` 含末字节：实测 `end=0x397248` 只得 24 条（丢末条 `きまぐれ`），
  `0x39724C` 才收满 25 条；`0x39724C` 处的指针值是 `0x020EFF15`，本身不是有效指针。
- 当前配置之所以还能拿到 25 条正确性格，是因为 `is_pointer_based` 那条路径恰好从 `0x0` 偏移按 FF 串扫到了它们
- **多收的 7 条（第 25~31 条）全部是能力页 UI 串**，来自 `0x397330` 附近的第二张指针表：

```
第 25 条 0x083EA787 'ポケモンじょうほう'   ← 指针源 0x08397330
第 26 条 0x083EA791 'ポケモンのうりょく'   ← 0x08397334
第 27 条 0x083EA79B 'たたかうわざ'         ← 0x08397338
第 28 条 0x083EA7A2 'コンテストわざ'       ← 0x0839733C
第 29 条 0x083EA782 'いれかえ'             ← 0x08397340
第 30 条 0x083EA7AA 'きりかえ'             ← 0x08397344
第 31 条 0x083E9ACB 'やめる'               ← 0x08397348
```

这 7 条与性格无关，是**详情页/能力页的 UI 标签**，且每条都有真实指针指向
`0x397330` 起的第二张指针表（`0x397330→ポケモンじょうほう`、`0x397334→ポケモンのうりょく`…
`0x397340→いれかえ`、`0x397344→きりかえ`），最后一条 `やめる@0x3E9ACB` 还有 4 个引用点。
**它们是需要翻译的真实 UI 文本，不能直接删**——应从 `性格名` 移出，归入新的详情页 UI 模块。

## 3. 模块重复覆盖（真实情况）

### 3.1 先澄清一个反直觉事实

**按「同一 ROM 字节」算，重复覆盖 = 0。**

| 度量 | 结果 |
|------|------|
| 被 ≥2 模块收录的字节 | **0 / 376,547** |
| 条目地址完全相同 | 0 |

原因：`export_texts()` 里有 FCFS 排除机制——后扫描的模块会跳过已被前面模块导出的字节带（`exported_bands`）。
**所以「重复」不在字节层面，而在「模块职责定义」层面。**

### 3.2 真正的重复：三个 scan 模块声明同一片全 ROM

```json
"UI界面":   { "start": "0x0", "end": "0xFFFFFF", "type": "scan" }
"剧情":     { "start": "0x0", "end": "0xFFFFFF", "type": "scan" }
"补漏剧情": { "start": "0x0", "end": "0xFFFFFF", "type": "scan" }
```

三个模块**声明区间完全相同且覆盖整片 ROM**。它们之间的边界完全由 filter 顺序决定（谁先跑谁认领），
一旦调整模块顺序或改 filter，归属立刻变化。这是配置里最脆弱的部分。

实测真实占用：

| 模块 | 条目 | 实际占用字节 | ROM 占比 |
|------|-----:|-------------:|--------:|
| UI界面 | 503 | 8,939 | 0.11% |
| 剧情 | 6,983 | 244,533 | 2.92% |
| 补漏剧情 | 1,561 | 49,057 | 0.58% |
| **合计** | 9,047 | 302,529 | 3.61% |

12,697 条条目里，这三模块占了 **9,047 条（71.3%）**。

### 3.3 剧情模块侵入名表区（68 条）

`剧情` 是全 ROM scan，实测有 68 条落在定长名表的槽内，且**这些槽被对应名表模块用空槽规则跳过**：

| 被侵入模块 | 剧情侵入条数 | 具体情况 |
|-----------|------------:|---------|
| 道具名 | 67 | `0x39A648` 等 67 个 `？？？？？？？？` 空槽 |
| 宝可梦名 | 1 | `0x1CA354` 的 `？？？？？` |

这 67+1 条全是纯占位符，**无翻译价值**，属于 `garbage_heuristic_filter` 没挡住的情况。

### 3.4 0x3B2xxx 隐藏词库区（68 条，67 条零指针）

`剧情` 在 `0x3B2000..0x3B2A00` 收录 68 条，其中 **67 条没有任何指针指向**（全 ROM 扫 u32 确认）：

```
0x3B2804 'きみにきめた！'
0x3B2810 'こうかん'
0x3B2815 'サファイア'
0x3B2823 'せいかく'
...
0x3B286D 'あくしゅう'    ← 与 0x1CBC4C 特性名表内容相同
0x3B2881 'あめふらし'
...
```

这是 ROM 里的一套**词库副本**（含 44 条与特性名表同文），游戏的 UI/存档界面临时用到。
它有意义（翻出来能翻对界面），但**不应由「剧情」模块承载**——它是词库，不是剧情。

### 4.3 内容重复：1271 条冗余，但**不能一刀切删**

严格按「同 `original_hex` 出现多次」统计：659 组、1,271 条冗余。**但其中绝大多数不能删**：

| 类型 | 组数 | 涉及条目 | 能否删 |
|------|-----:|---------:|--------|
| **N1 同模块内重复** | 492 | 1,482 | ❌ **不能删** |
| **N2 跨模块重复** | 167 | 448 | ⚠️ 按语义判断 |

**N1 为什么不能删**——名表里重复出现是正常现象：

```
x68  [剧情]     '？？？？？？？？'   ← 空槽（可删，已计入 §4.2）
x26  [补漏剧情] 'むい'              ← 不同地址的不同表项
x25  [宝可梦名] '？'                ← 空槽（可删）
x13  [补漏剧情] 'え あ '            ← 数据碎片
x10  [剧情]     'おおきな ぬいぐるみ…' ← 装饰品说明，10 个装饰品共用同一句
x7   [图鉴分类名] 'ドラゴン'         ← 7 只龙系宝可梦共用分类名「ドラゴン」
x6   [训练家个人名] 'マリとダイ'     ← 6 个训练家槽位同名
```

「ドラゴン」×7 删到 1 条，就有 6 只宝可梦的图鉴分类变空。**这类必须保留。**

**N2 跨模块重复按模块对**：

| 模块对 | 组数 | 判断 |
|--------|-----:|------|
| 剧情 vs 特性名 | 65 | 剧情误收了 `0x3B2xxx` 特性名副本 → **应删剧情侧**（特性名权威表在 `0x1CBC4C`） |
| 剧情 vs 地点名 | 19 | 地点名在剧情对话里被引用，语义不同 → **保留** |
| 剧情 vs 宝可梦名 | 15 | 同上 → **保留** |
| 招式名 vs 招式名-华丽大赛 | 12 | 同一招式在两个表里都出现 → **保留**（两张表都要能翻） |
| 其余 | ~56 | 多为 1~4 组，语义各异 → **逐条判断** |

### 4.4 开发残留：390 条候选，需人工复核

按「全角拉丁/数字占比 ≥80% 且 ≤16 字」+ 工程关键词匹配，命中 390 条（剧情 359 / 补漏剧情 28 / UI界面 3）：

**确凿的开发残留**（有明确工程语义）：

```
0x081E04F9 [剧情] 'ＯＢＪテキストセット'      ← 原始字节：c9 bc c4 63 57 5d 64 bb be be
0x081E0513 [剧情] 'ＯＢＪテキストＡＤＤ'      ← 紧邻上一条，是 OBJ 文本资源的标记
0x081EC1B4 [剧情] '２Ｐｏｋ'
0x081EC1BA [剧情] '３Ｐｏｋ'
0x081EC1C0 [剧情] '４Ｐｏｋ'
0x083A57C6 [剧情] 'Ｒ‥ＤＲＩＶＥＲーＴＥＳＴ'
0x083E7772 [UI界面] 'デバッグプレイ'          ← 调试播放
0x0839DE83 [UI界面] 'ＢＰ．'
```

`0x081E04F9` 附近原始字节：

```
0x1E04F0  51 52 5a 7e 5e a0 64 ff 00 c9 bc c4 63 57 5d 64  |アイコンセット|
0x1E0500  5e a0 64 ff 00 00 5e 79 5e a0 64 ff 00 00 00 00  |セット|
0x1E0510  00 00 00 c9 bc c4 63 57 5d 64 bb be be ff 00 00  |   ＯＢＪテキストＡＤＤ|
```

这是**图标资源名表**（`アイコンセット` 后面跟着一串 OBJ 标记），被 scan 当成剧情收了。

**但这批不能盲目删**：`0x083A5xxx` 那一段（`ＳＴＯＰ`／`ＦＩＥＬＤ１３`／`ＫＡＣＨＩ２２`／`ＤＯＯＲＯ１` 等）
是**事件脚本用的标识符**，`0x3A57C0` 原始字节显示它们是连续的资源名字符串表。它们不翻译，但删不删对游戏无影响——建议**单独剔出，不删也不翻**。

## 5. 清理提案

### 5.1 必改（几何错误，2 处）

| 模块 | 现状 | 改为 | 影响 |
|------|------|------|------|
| 树果名 | `0x3A1050..0x3A14E8` `entry_size=56` `desc_ptr_offset=12` | `end=0x3A1503`<br>`entry_size=28`<br>`desc_ptr_offset=0x10` | **21 → 43 条**，补回 22 个树果名（含末条 `ナゾ`） |
| 性格名 | `start=0x397168  end=0x39734C` | `start=0x3971E8`<br>`end=0x39724C` | **32 → 25 条**；移出的 7 条（都有真实指针）建新模块 `UI-详情页`，不要直接删 |

> 性格名 `end` 必须是 `0x39724C` 而不是 `0x397248`——`end` 含末字节，
> 实测 `end=0x397248` 只得 24 条（丢末条 `きまぐれ`），`0x39724C` 才是 25 条。

### 5.2 建议修（边界问题，3 处）

| 模块 | 现状 | 改为 | 实测结果 |
|------|------|------|---------|
| 地点名 | `start=0x3BECB7` | `start=0x3BECB0` | **78 → 79 条**，首条变成 `ミシロタウン` ✅ |
| 训练家名 | `ranges[0].start=0x1C4A10` | `ranges[0].start=0x1C4A1F` | **60 → 59 条**，碎片 `ぼあ  ポケモントレーナー` 消失，首条变 `ポケモントレーナー` ✅ |
| 道具说明 | `end=0x39A647` | `end=0x39A63E` | 剔除表尾空槽 `ac ac ac ac ac ff`（`？？？？？`） |

（以上三项均已用项目自带 `extract_module()` 实测确认产出条数与内容。）

> **已排除的两条（曾误判，经抽取器实测证伪）**：
> - ~~道具名加 `name_offset=0x28`~~ —— 错。第 0 槽 `0x39A648` 就是 `？？？？？？？？` 占位符，
>   `name@0` + 跳过占位符 已精确取到 281 条（`texts_21` E1 验证）。
> - ~~宝可梦名 `end` 收到 `0x1CACF5`~~ —— 错。末槽 `チリーン` 是真名字（词表命中、译「风铃铃」），
>   收窄会删掉一个真宝可梦（`texts_21` E2 验证）。

### 5.3 建议删（纯占位条目，112 条）

| 模块 | 条数 | 判据 |
|------|-----:|------|
| 剧情 | 75 | 解码后仅 `？`/`ー`/`…`/空格 |
| 宝可梦名 | 25 | `ac ff 00 00 00 00` 空物种槽 |
| 补漏剧情 | 10 | 同上 |
| 属性名 | 1 | 槽 9 `？？？`（无属性，保留槽位） |
| 道具说明 | 1 | 表尾空槽 |

**注意**：属性和宝可梦名的空槽是表结构的一部分，**只删条目记录，槽位必须保留**，否则重建表会错位。

### 5.4 建议合并 / 重划（模块级）

现行 22 个模块里，真正的问题在**三个全 ROM scan 模块**。建议重划为按地址带定义：

#### 方案 A（保守，只收窄区间）

| 新模块 | 区间 | 来源 |
|--------|------|------|
| `剧情-脚本` | `0x100000..0x1C4A00` | 剧情（脚本区） |
| `剧情-后期` | `0x3E9600..0x7FFFFF` | 剧情（后期与高位区） |
| `UI-菜单` | `0x1E0000..0x1FFFFF` + `0x3DC000..0x3EAFFF` | UI界面 |
| `词库-0x3B2` | `0x3B2000..0x3B2A00` | 从剧情拆出（0x3B2 词库区，67 条零指针） |
| `UI-详情页` | 指针表 `0x397330..0x397348` | 从性格名移出的 7 条能力页标签 |
| `补漏剧情` | 合并进 `剧情-脚本` / `剧情-后期` | — |

#### 方案 B（激进，全部改为地址带 + 明确排除名表）

按 `docs/MODULE_BANDS.md` 的台账，把剧情拆成 `script_rare` / `script_14`…`script_18` / `script_19lo` 等带，
UI 拆成 `ui_menu` / `battle_prompt` / `bag_ui` / `summary_ui`，与台账对齐。

**建议先做 A**——它不改 filter 逻辑，只收窄 `start/end`，风险最低；同时能立刻消除「三个模块声明整片 ROM」的问题。
