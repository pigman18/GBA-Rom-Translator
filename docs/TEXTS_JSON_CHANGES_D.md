## 二、逐项改动与 ROM 证据

### 2.1 道具名：补 `name_offset: 0`（显式声明）

| | |
|---|---|
| 改前 | `read: {entry_size: 40, desc_ptr_offset: 16}` |
| 改后 | `read: {entry_size: 40, desc_ptr_offset: 16, name_offset: 0}` |

**ROM 证据**（base=0x39A648，stride=40）：

```
槽0 @0x39A648: ac ac ac ac ac ac ac ac ff ...  → ？？？？？？？？（空槽）
槽1 @0x39A670: 6f 5d 60 ae 9a ae 79 ff ff 00    → マスターボール
槽2 @0x39A698: 6a 52 9b ae 9a ae 79 ff ff 00    → ハイパーボール
槽3 @0x39A6C0: 5d ae 9b ae 9a ae 79 ff ff 00    → スーパーボール
```

名字在**槽首**（`+0x00`），不是 `+0x28`。
按 `name_offset=0` 读：348 槽 → 281 条有效 + 67 槽「？？？？？？？？」占位，
与 `tables_ground_truth.py` 实测的 281/348 完全一致。

> 更正记录：本审计报告初版曾写「name_offset 应为 0x28」，那是把「槽 1 的起始地址
> 0x39A670」误当成「槽 0 的 +0x28 偏移」。已修正。

**`name_offset: 0` 保留为显式声明**（而不是依赖默认值）——这条坑过一次，写出来防止重犯。

### 2.2 树果名：`entry_size` 56 → 28，`end` 0x3A14E8 → 0x3A1503，`desc_ptr_offset` 12 → 0x10

**ROM 证据**（`0x3A1050` 起，每 28 字节一个名字）：

```
0x3A1050  58 77 9a ff        → クラボ
0x3A106C  56 8b ff           → カゴ        （stride=56 时整个跳过）
0x3A1088  73 73 7e ff        → モモン
0x3A10A4  61 ae 8b ff        → チーゴ      （被跳过）
...
0x3A14E8  65 90 ff           → ナゾ        （第 43 条）
0x3A1504  00 00 00 00 ...    → 表外
```

**为什么 `end` 必须一起改**：条数 = `(end − start + 1) // entry_size`（`end` 含末字节）。

| 配置 | 实测条数 | 末条 |
|---|---|---|
| `stride=28, end=0x3A14E8` | 42 | スター |
| `stride=28, end=0x3A1503` | **43** | **ナゾ** ✅ |
| `stride=56, end=0x3A14E8`（原） | 21 | スター |

`desc_ptr_offset` 随步长一起改：28 字节槽内描述指针在 `+0x10`
（`0x3A1060` = `79 09 3a 08`），不是 `+12`。

**效果**：21 → 43 条，补回 22 个树果名。

### 2.3 性格名：`start` 0x397168 → 0x3971E8，`end` 0x39734C → 0x39724C

**ROM 证据**：`0x397168` 是**名字正文**起点，不是指针表。

```
0x397168  37 2e 46 28 24 ff   → がんばりや
0x39716E  0b 20 0c 37 28 ff   → さみしがり
...
0x3971E3  07 1f 39 2a ff      → きまぐれ（第 25 条）
```

真正的指针表从 `0x3971E8` 开始，25 个 u32 依次指回这些正文：

```
0x3971E8 -> 0x397168 がんばりや
0x3971EC -> 0x39716E さみしがり
...
0x397244 -> 0x3971DD しんちょう
0x397248 -> 0x3971E3 きまぐれ       ← 第 25 个（索引 24）
0x39724C = 0x020EFF15               ← 非指针，表尾
```

**`end` 含末字节的坑（第二次）**：

| 配置 | 实测条数 | 末条 |
|---|---|---|
| `end=0x397248` | 24 | しんちょう |
| `end=0x39724C` | **25** | **きまぐれ** ✅ |

**移出的 7 条**（原第 25~31 条）不是性格，是能力页 UI 串：

```
0x083EA787 ポケモンじょうほう   指针源 0x08397330
0x083EA791 ポケモンのうりょく   指针源 0x08397334
0x083EA79B たたかうわざ         指针源 0x08397338
0x083EA7A2 コンテストわざ       指针源 0x0839733C
0x083EA782 いれかえ             指针源 0x08397340
0x083EA7AA きりかえ             指针源 0x08397344
0x083E9ACB やめる               指针源 0x08397348（另有 4 个脚本引用点）
```

它们每条都有真实指针，指向 `0x397330` 起的第二张指针表（槽 7 = `0x0100FF00` 是表尾）。
**这些是待翻译的真文本，没有删除**，存于 `work/_reserved_ui_detail.json`，
待建 `UI-详情页` 模块时收编。

**效果**：32 → 25 条。

### 2.4 删除 `write.*` 与 `reuse_slot_padding`（妥协产物）

删除了 7 个模块的 `write` 块：

| 模块 | 被删内容 |
|---|---|
| 宝可梦名 | `{relocate: false, replace: false, slot: true}` |
| 训练家名 | 同上 |
| 训练家个人名 | 同上 |
| 补漏剧情 | 同上 |
| UI界面 | `{relocate: false, replace: true, slot: true}` |
| 秘密基地装饰名 | `{byte_length: 5, relocate: true, replace: true, slot: true}` + `reuse_slot_padding: true` |
| 图鉴分类名 | 同上 |

**为什么删**：这些是为「全走 replace + 运行时查表」加的写入策略开关。
新方案是「判断归属后自动划分写入」，不需要人工开关。

**代码依赖（Chief 已核实，此处记录在案）**：

- **新流水线完全不读**：`src/meowth/auto_layout.py` 第 6 行注释明写「不依赖 texts.json 的
  write.\* 人工开关」；`src/meowth/text_pipeline.py` 全文无 `write`/`slot`/`relocate`/
  `reuse_slot_padding` 的读取。
- **旧引擎会读**（已确认可接受）：
  - `src/meowth/translate_plan.py:97` `_write_switch()` 读 `meta["write"][key]`
  - `src/meowth/translate_plan.py:611` `_reuse_slot_capacity()` 读 `reuse_slot_padding`
  - `src/meowth/translate_plan.py:615` 读 `write.byte_length`
  - `src/meowth/config_loader.py:345` 读整个 `write` 块
- **删除后的行为变化（预期内）**：旧引擎这些读取会走默认值
  （`_write_switch` 的 `default=True`，即 relocate/replace/slot 全部视为 true）。
  这是可接受的，因为旧引擎本就要被新流水线替代。
  **不为兼容旧引擎保留字段**——那正是用户所说的「妥协产物」。

**保留 `type` 与 `read`**：它们是几何语义（怎么从 ROM 读出文本），
新流水线 `auto_layout.classify_entry` 要靠 `read` 的几何做判定。`read` ≠ `write`，不能一起删。

## 五、待办 / 需要拍板的事项

### 5.1 `剧情` 模块里的 fallback 71 条（尚未处理）

这 71 条由 `剧情` 的 `fallback_filters` 放行（带 `fallback: true` 标记）。
它们混了三类东西，**不适合按同一条规则处理**：

| 类别 | 条数 | 样本 | 判断 |
|---|---|---|---|
| `0x3DA000-0x3DC000` 战斗提示池 | 36 | `\0Dは \16で\nじめんタイプの わざが あたらない！` | **正常日文**，只是被剧情模块误收，应归 UI/战斗模块 |
| `0x3D0000` 其他 | 7 | `つかまえた \03に\nニックネームを つけますか？` | **正常日文**，同上 |
| `0x1D0000` 段 | 18 | `わいんいゃせろはざらやぇ？ずせぱチカゅツ` | **待裁定**：字节形态像压缩数据（`xx 02` 高频成对），但也可能是未启用占位台词 |
| 其他区段 | 10 | `ＺパほくＢネほく た」な」な「な…` | **可疑**，同 `0x1D` 段 |
| 与正常文本完全重复 | 1 | `はを くりだした！` | 可直接去重 |

**我没有对这批做伪判**。前 6 版启发式（假名占比 / 裸 F7F8 / 片段命中率 /
长片段词表覆盖 / 邻域结构 / 字节形态）全部出现误杀或漏判：
假名占比会把 `は からを うばいとった！` 判成乱码（正常战斗提示），
字节形态会把正常提示也判成数据。**在不误伤真台词的前提下我没找到可靠判据**，
所以只给客观分组，交给你裁定 `0x1D`/`0x1E9`/`0x36C` 那 28 条是否删除。

### 5.2 已建 / 未建的新模块

  详见 `MODULE_PLAN_E.md` §4.4。

### 5.3 `补漏剧情` 的定位问题

它和 `剧情` 的 filter 语义高度重叠（都要求指针），实测基线模拟里
`剧情 6987 + 补漏剧情 1797`，而文件里是 `6983 + 1561`。
两者职责边界不清，长期看应该合并或明确分工。这次只做了区间收窄，没动职责。
