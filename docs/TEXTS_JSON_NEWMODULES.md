## 二、三个新模块：一个可建、两个卡住

### 2.1 `UI-详情页` —— ✅ 可建（但总数会变，需拍板）

**验证通过**：`stride_ptr @0x397330, stride=4, end=0x39734C` 用项目抽取器实测**正好 7 条**：

```
0x083EA787 'ポケモンじょうほう'    ← 0x397330 指向
0x083EA791 'ポケモンのうりょく'    ← 0x397334
0x083EA79B 'たたかうわざ'          ← 0x397338
0x083EA7A2 'コンテストわざ'        ← 0x39733C
0x083EA782 'いれかえ'              ← 0x397340
0x083EA7AA 'きりかえ'              ← 0x397344
0x083E9ACB 'やめる'                ← 0x397348
```

`0x39734C` 处是 `0x0100FF00`，非指针，正好是表尾。

**但总数会从 12,712 变成 12,719（+7）**——这 7 条是我在 2.3 步从 `性格名` 移出的，
当时没直接删、存进了 `work/_reserved_ui_detail.json`。现在建模块把它们收回来，
总数就回到「性格名 32 条拆分后」的正确值。

**这不是增删内容，是恢复**：改动前（备份）这 7 条存在于 `性格名`，累计在 12,697 里。
拆成两个模块后：

```
性格名      32 -> 25   (-7)
UI-详情页   0  ->  7   (+7)   ← 本轮新增
树果名      21 -> 43   (+22)
--------------------------------
合计   12,697 -> 12,719 (+22)
```

净增的 22 条全部来自树果名修复。**没有新增或丢失任何 ROM 内容。**

> ⚠️ 按你的规则「总数一变立刻停下」，我停在这里没有写入。
> 需要你确认：这个 +7 是可接受的（因为它是把移出的条目收编回来，不是凭空增加）。

### 2.2 `词库-0x3B2` —— ❌ 卡住，scan 机制做不到

**目标**：`0x3B2000..0x3B2A00` 的 68 条（现属剧情）切给新模块。

**实测三个障碍**：

1. **该区段 73 条无指针**——任何指针类 filter（`require_pointer` / `story_pointer`）
   都只收到 **1 条**。剧情能收到这 68 条，靠的是 `fallback_filters` 里的
   `dialogue_shape_filter`（`pointer_ok: false` 允许无指针文本通过）。

2. **裸 scan 收 129 条，精确率仅 57%**——多出的 55 条是 `0x3B2000~0x3B20xx`
   的乱码碎片。用剧情同款 fallback 通道也一样（129 条）。

3. **串起点错位**：`extract_scan` 从「start 之前最近的 FF 之后」定串起点。
   `0x3B2000` 之前最近的 FF 在 `0x3B1FF3`，所以起点落在一条串的中间：

```
0x3B1FF3: FF
0x3B1FF4: 'アへ パ ずゾｋっのむごたパみＱｍゾソ １っうＵ…'   ← 真实串起点
0x3B2000: 'たパみＱｍゾソ １っうＵ\nｚＴ‥ｊミ'                ← 错位起点（当前 start）
```

把 start 对齐到 `0x3B1FF4` 也还是 129 条，因为 FF 边界把整段切碎了。

**结论**：用 `scan` 按区间圈这块**做不到**。要精确切出这 68 条，需要一个
「按地址白名单」的机制——现有 `extract_module` 的 type 里没有
（只有 `stride` / `struct` / `stride_ptr` / `scan` / `addr_bands`，后者的语义我需要再确认）。

**我没有硬做**。硬做的后果是把 55 条乱码碎片从一个模块搬到另一个模块，
总数还会变，违背「只迁移不增删」。

### 2.3 `战斗提示` —— ⚠️ 部分可行，但会改变内容

**实测**：`scan 0x3DA000..0x3DBFFF` 裸扫收到 **389 条**，与文件现有 388 条的交集是 339 条：

```
收到 389   命中文件 339   精确率 87%
会多收 50 条（0x3DA2D4 起的一批乱码/碎片）
会漏 49 条（0x3DA6AE 起，因串起点错位切成了不同起点）
```

**问题实质**：文件里该区段的 388 条是**剧情整段扫出来的**（起点由 FF 链决定），
新模块局部扫会得到**不同的起点切分**，于是「多 50 / 漏 49」——不是简单迁移。

同 2.2 的根因：**局部 scan 与整段 scan 的串边界不一致**。

---

## 三、根因总结

两个卡住的模块是同一个问题：

> **`scan` 类型的串边界由 `start` 之前的 FF 决定。**
> 从整段扫里「切一块」给新模块，必然改变串起点，
> 结果不是精确迁移，而是「多收一批碎片 + 漏掉一批原文」。

这说明「靠新建局部 scan 模块来抢归属」这个思路对 **scan 区段**不成立。
它对 `stride_ptr`（`UI-详情页`）成立，因为那是定长指针表，边界由表几何决定，与 FF 无关。

   我倾向 **a 或 b**，但 b 需要先验证机制。
