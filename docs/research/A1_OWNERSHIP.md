## 二、NO_PTR 4,270 条的真实情况

### 2.1 排除项

| 检查 | 结果 |
|---|---|
| 5 字节内（±4）有指针对齐站点 | **仅 90 条** |
| 完全无任何引用（任意对齐） | 1,490 条 |
| **被任意对齐位置引用** | **2,780 条（65.1%）** |

### 2.2 那 2,780 条的引用形态

引用位置**全部非 4 对齐**（0 个 4 对齐）：
```
引用位置 4 对齐:   0
引用位置非对齐:  2,959
```

引用位置前 2 字节分布：
```
0f00: 大量    1708: 89    1808: 54    0267: 36
1608: 22      0867: 16    1508: 14    0067: 13
```

### 2.3 结构确认

观察连续上下文：
```
0x145AE2: ... 02 0f 00 | fc de 14 08 | 09 04 68 2a ...
0x145B21: ... 6c 02 0f 00 | 92 5d 14 08 | 09 02 02 13 ...
0x145B79: ... 03 02 0f 00 | 44 5f 14 08 | 09 03 02 0f 00 | cd 5e 14 08 ...
```

**模式 `?? ?? 0f 00 <ptr32>` 反复出现**：
- `0f 00` 是 2 字节标记
- 紧跟 4 字节 GBA 指针
- 因此指针**自身是 4 字节对齐的**，但这个 4 字节窗口相对元素起点错位

全 ROM「`0f 00 <ptr32>`」模式命中 **3,020 处**，其中 2,978 在 `0x100000-0x1C0000`。

### 2.4 间歇规律

相邻「0f 00」间距分布（前 5）：
```
9 字节: 431    10 字节: 359    23 字节: 277    21 字节: 82    14 字节: 76
```

**间距不固定 ⇒ 不是等距表，而是「变长结构里夹指针」**。

典型形态是游戏脚本数据结构：每个元素带少量头部 + 一个文本指针。

### 待解决的最后一项

`NO_PTR 真无引用 1,490 条` 继续拆解：

| 形态 | 条数 |
|---|---|
| **前一字节是 FF（独立串）** | **919** |
| 前一字节非 FF（长串中部） | 571 |
| 紧邻前一条目（疑似切开） | 4 |

**919 条是「前面就是 FF、本身是完整独立串、但没有任何指针引用」** —— 这是真问题。

样本：
```
0x14A94C 原文字: 'ダイゴ『\01\05\nきみも きたのか\lこんな ひどい あめ なのに‥‥...'
0x14A983 原文: 'わたしは ミクリ\nこの まちの ジムリーダー\n...'
0x14DF5F 原文: 'ふふふ みてて ごらん！'
```

这些是剧情对话文本，内容完整，但 ROM 里搜不到任何指向它们的 u32（任意对齐都没有）。

**可能原因**：
- 被压缩/加密引用（如 LD 压缩包里的指针表）
- 通过「基址 + 索引」访问的文本表（表中存的是偏移，不是绝对地址）
- 被脚本 VM 用相对地址访问

**这是 A1 唯一未解项，需要单独查。**

### 连块情况补充

- 相邻 NO_PTR 条目**首尾相接**：2,511/4,269（58.8%）
- 形成 **1,759 个连续块**
- **块首有指针的：0 / 1,759（0.0%）**

⇒ 这些文本确实不是靠「块首指针」引用的，而是靠上述「元素内嵌指针」。

## 三、结论：归属已全部明确

| 容器 | 条数 | 定位方式 | 处置 |
|---|---|---|---|
| FIXED_TABLE | 1,178 | 已知表基址 + stride | **整表换指针表**（改代码里 `index×stride`） |
| PTR_ARRAY | 1,034 | 站点前后也是指针 | **整数组搬 + 改数组值** |
| CODE_LITERAL | 298 | `ldr rX,[pc,#n]` | **逐条改字面量** |
| FREE_TEXT | 259 | 无容器特征 | **relocate** |
| NO_PTR_BLOCKED | 105 | 指针落正文体 | 待查是否误伤 |
| **NO_PTR（脚本内嵌）** | **2,780** | `0f 00 <ptr32>` 形态 | **改这些内嵌指针即可** |
| NO_PTR（真无引用） | 1,490 | 无任何引用 | **需进一步查或缩句** |

### 待解决的最后一项

`NO_PTR 真无引用 1,490 条` 是唯一还没定位的。

样本地址：`0x14A94C, 0x14A983, 0x14A9D5, 0x14A9F6, 0x14AA79, 0x14AB01...`

**下一步**：查这 1,490 条是否为
- 长串被切开的片段（前一条目未到 FF）
- 或真的无引用（需缩句）

## 四、按容器的工作量分配

```
FIXED_TABLE   1,178  → 5~6 张表，每张一次改动
PTR_ARRAY     1,034  → 按数组批量改（数组数待统计）
NO_PTR 脚本内嵌 2,780 → 改内嵌指针（形态统一，可批处理）
CODE_LITERAL    298  → 逐条
FREE_TEXT       259  → relocate
NO_PTR 真无引用 1,490 → 待查
NO_PTR_BLOCKED  105  → 待查
```

**前 5 项合计 6,549 条（91.7%）都有明确的容器归属和统一处置方式。**
真正需要逐条决策的只有 `FREE_TEXT 259 + 待查 1,595` 约 1,854 条。
