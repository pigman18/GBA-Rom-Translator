# BUG-1 战斗对话框空白：真实数据核查（2026-11-18）

> 本文只记录**实测数据**，不写推测。前面几轮的错误结论也一并记录，避免重犯。

## 一、已确认的事实

### 1. 战斗窗参数（origin 与 translated 相同）

| 项 | 值 | 来源 |
|---|---|---|
| 模板 | `0x081BB3F4` | GDB 实测 |
| `TB` | `0x01B8` | 两侧 RAM 一致 |
| `cursor_ty` | 35 | 同上 |
| `grid_row` | 17 | `(35)>>1` |
| `band` | 1 | `17 & 7` |
| 网格公式 t0 | `0x1B8+2+1*62 = 0x1FC` | 计算 |
| `GRID_TILE_LIMIT` | `0x1F0` | 代码常量 |

⇒ **origin 的 t0 也是 0x1FC，同样超过 0x1F0。**

### 2. origin 战斗框的 tilemap 实测

在 `0x0600C800` 找到含 `0x1B8` 的表：

```
(2,3) = 0x1B8  (3,3) = 0x1BA  (4,3) = 0x1BC ... (13,3) = 0x1CE
(2,4) = 0x1B9  (3,4) = 0x1BB ...
```

⇒ 布局是**线性**：`tile = TB + 2*(x-2)`，y=3/y=4 是同一行文字的上下半，
跨列步进 2，与 `band*62` 无关。

**但**：这个 tilemap 地址 `0x0600C800` 没有匹配到任何活跃窗模板
（扫全部窗口，没有 `tpl+0x10 == 0x0600C800` 的）⇒ 可能是残留。

### 3. VRAM 差异（origin vs translated，帧 044）

```
0x06001280: O=f11181ff118811f8  T=ffffffffffffffff
0x06001290: O=81ff818188ff1188  T=ffffffffffffffff
0x060012C0: O=ffffffffffffffff  T=0000000000000000
0x060012D0: O=81ff1ff881111181  T=0000000000000000
```

- 差异区 `0x06001280..0x06001400` ⇒ **tile `0x94..0xA0`**
- 我们的渲染器算的 t0 = `0x1F8`
- **`0x94` ≠ `0x1F8`** ⇒ 这块差异**不是**我们的渲染器写的

⇒ 战斗框空白的直接原因是：**原版字模（在 tile 0x94 区）被清空，之后没人重打**。

### 4. 渲染器确实在跳过

诊断探针（`grid_emit` 入口记录）实测帧 043/044：

```
TB=0x0090 row=7  cx=2  cy=15 → t0=0x0248 OVER
TB=0x0190 row=17 cx=19 cy=35 → t0=0x01F6 OVER
TB=0x0190 row=18 cx=19 cy=35 → t0=0x0234 OVER
TB=0x01b8 row=17 cx=2  cy=35 → t0=0x01fc OVER
```

⇒ 四个战斗窗**全部**因 `t0 > 0x1F0` 被跳过，一个字都没画。

## 三、下一步该做什么（未执行）

**核心矛盾**：`GRID_TILE_LIMIT = 0x1F0` 对战斗窗是错的判据
（origin 自己用 0x1FC 都合法），但简单放宽又会撞坏别的窗口。

必须先回答一个可测量的问题：

> **tile `0x1F0..0x400` 这段到底被谁占用？**

已知线索：
- `0x1F0/0x1F1` = 菜单 ▶ 固定对（`DESIGN_TEXT_12PX_GRID.md` §9）
- `0x1E8..0x1FB` = Summary 提示图标
- `0x1FC..0x1FF` = 图鉴编号/精灵球图标

⇒ 这些是**绝对位置**。如果战斗窗写到 `0x1FC`，就会踩图鉴图标。

**但 origin 自己就写到 0x1FC** —— 说明战斗场景下这些图标**不在屏幕上**，
所以可以安全覆盖。

⇒ **正确判据应该是「按场景/窗口判断，不是全局绝对上限」**，
而不是简单改一个常量。

验证方法（待做）：
1. 在战斗帧里检查 `0x1E8..0x1FF` 的 tile 数据是否为空
2. 若为空 ⇒ 战斗场景下这段可安全使用
3. 给 `grid_arena_hi` 加条件：仅当目标区 tile 数据为空时才允许越过 0x1F0
