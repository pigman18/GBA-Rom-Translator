# BUG-9 存档框「118号道路」乱码 —— 调研全过程（2026-11-20）

> 状态：**未修**。两次尝试均失败并已回滚。本文记录已确证的事实与被证伪的假设，
> 供下一次接手时不必重复踩坑。

## 现象

`save_confirm` 第 20 帧，左上信息框：

| 行 | origin | translated |
|---|---|---|
| 1 | `118 ばん どうろ` | `[残]吗？号道路` |
| 2 | `ユウキ` | `玩家` ✓ |
| 3 | `5こ` | `5个` ✓ |
| 4 | `55まい` | `5,` ✗ |

⇒ **单个数（`5个`）正常；连续两个以上 8px 数字（`118`、`55`）就坏。**

## 已确证的事实（动态 GDB + 静态反汇编 + VRAM 逐字节）

### 1. 窗口参数（origin 与 translated 完全一致）

```
win=0x0202E658  textMode=3  fontNum=3  TILE_BASE=0x0001
tileData=0x06008000  tilemap=0x0600F800
```

### 2. 字节流正确

```
a2 a2 a9 | f7 00 04 eb | f7 00 03 07 | f7 00 08 e8 | ff
└ 118 ┘     └─ 号 ─┘      └─ 道 ─┘      └─ 路 ─┘
```

`charmap.txt`：`A1=0 A2=1 A9=8`；`Charmap.encode_char()` 实测 `'1'->a2`。
**数据层与编码层都正确。**

### 3. 字模取对了

临时诊断（已删除）在 `grid_draw_pcs` 里 `GetGlyphTilePointers_Origin` 之后读值：

```
glyph=0xA2  fn=3  shadowed=1
up = 0x081B956C
up[0..3] = 00000000 00000000 00000000 00EFF000   ← 数字「1」的竖笔
```

font3 字库基址 `0x081B6D2C`、分支代码 `0x080037AC` 在 origin/translated 中**逐字节相同**。

### 4. 但屏幕 tile 是汉字

`charBase=0x08000`，`tilemap row=1`：

| 版本 | col=3..8 的 tile |
|---|---|
| origin | `022 023 024 025 026 027`（间距 1） |
| translated | `004 005 006 00B 00D 00F`（前 3 个间距 1，后 3 个间距 2） |

`tile 0x005` 内容 `11FFFFFF 818F111F F18F1818` = **汉字笔画**，不是数字。

### 5. 诊断证明写入的 `p0` 是纯背景

```
col=3  t0=6  p0[0]=0xFFFFFFFF  p0[1]=0xFFFFFFFF
```

**`grid_pair_store` 写进去的是纯背景，但最终 tile 6 有正确的数字「8」。**
⇒ **写入之后又被别的东西改了。**

## 根因（已定位到机制，未验证到具体代码行）

**`grid_tile()` 用 `TB + 2 + (row&7)*62 + 2*col` —— 每字符列 2 个 tile。**

这是**故意的交错布局**：两行共享同一个 band 时，偶数 tile 归一行、奇数归另一行，
从而**避免行间 tile 冲突**。

实测证据（本次修复尝试的中间结果）：

```
row=1: 004 005 006 | 00B 00D 00F   ← 118号道路
row=2: 005 006 007 | 00C 00E 010   ← 16:41
              ↑↑↑ 两行 tile 直接重叠
```

改成 `step=1` 后，两行都从低位开始分配，**直接撞车** →
第一行仍是乱码，「16」还被压扁。

⇒ **`2*col` 不是 bug，是行间隔离机制。8px 字借用 12px 的槽位后，
相邻行的 8px 字就会互相覆盖。**

## 已证伪（不要重试）

| 假设 | 证伪方式 |
|---|---|
| `0x0809101C` HandleDrawSaveWindowInfo 是入口 | 断点 **0 命中** |
| 存档框不走 `0x080032F8` | 错。`SaveBoxWinDump` 抓到 213 条 |
| textMode 3 落址公式错 | 改成 `TB+2+col+30*row` → **全局乱码，已回滚** |
| font3 字库被汉字表整体占用 | 错。`0xA6`（5）正常；字库逐字节相同 |
| 数据层漏翻 | 错。译文存在且编码正确 |
| 同一行被绘制两次互相覆盖 | 错。两次是不同帧/不同功能（训练家卡 vs 存档框） |
| `grid_phase_adv` 步进不一致 | 错。代码已是 `CHS_GLYPH_ADVANCE_JP_PX`（8px） |
| `tile_step=1`（8px 字一列一 tile） | **造成行间 tile 重叠，已回滚** |

## 下一步方向（供参考）

问题的本质是：**8px 字与 12px 汉字共用同一套「字符列 → tile」映射，
而该映射以 2 tile/列为单位做行间交错。**

可行方向：

1. **给 8px 字单独的 band 区间**（例如把 band 上限拆成两段：
   12px 用 `TB+2..TB+2+62*8`，8px 用另一段），彻底不与汉字争 tile。
2. **查清 `grid_pair_store` 之后谁改写了 tile** —— 诊断显示写入的是背景，
   但最终有内容，说明有第二条写入路径（可能是 `grid_load` 的 phase 分支
   或原版 `UpdateTilemap` 的回写）。先把这条链查清，再决定改法。
3. **绕过渲染层**：把译文里的数字也改成 F7 汉字编码（`0-9` 加 10 个 F7 槽位），
   让 `118` 走 12px 路径。**代价最小、风险最低**，但需要重编所有数字串。
