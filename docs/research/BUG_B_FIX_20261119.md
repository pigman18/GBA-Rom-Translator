# BUG-B 修复记录：图鉴列表跨行 tile 撞字（2026-11-19）

> 台账 BUG-3。用户实测原话：「初始进来是 003，往下移动到 006 位置的时候，003 处就会被替换为 011。」
> 状态：**已修复**，全程反汇编 + GDB + bot 字节级取证。

---

## 一、现象

| 状态 | 顶行 | 说明 |
|---|---|---|
| 刚进图鉴（f016） | `No003 妙蛙花` | 正常 |
| 向下滚 3 格（f043） | `No011 ------` | **BUG**：顶行编号被改成 No011，名字丢成横线 |
| 同帧 origin | `No003 フラキけ` | 原版正常，且列表**不整体滚动**（只有光标移动） |

下方行序仍是 `No004 / No005 / ...` 连续 —— 说明不是数据错，是**顶行的字模被别处覆写**。

---

## 二、根因（双证据，非推测）

### 2.1 公式只有 8 个 band

`text_grid.h` / `PrintNextChar_hook.c` 的纯函数网格：

```
row  = (CURSOR_Y + CURSOR_TILE_Y) >> 1
tile = TILE_BASE + 2 + (row & 7) * 62 + col * 2
GRID_SEG_COUNT = 8    GRID_SEG_TILES = 62    GRID_TILE_LIMIT = 0x1F0
```

`row & 7` 只有 **8 档**。图鉴列表要画 **11 行**（GDB 实测 `curY` 从 10 到 30，即 `row` 5..15）。

### 2.2 GDB 打印序列（`InitTextPrinter`，run `20261119T115109_111081`）

| 内容 | curY | row | band = row&7 | 公式 tile |
|---|---|---|---|---|
| `００３`（第 1 行） | 10 | 5 | **5** | **`0x0A9`** |
| `０１１`（第 9 行） | 26 | 13 | **5** | **`0x0A9`** ← 同一个 |
| `０１２`（第 10 行） | 28 | 14 | 6 | 与 row 6 同 |
| `０１３`（第 11 行） | 30 | 15 | 7 | 与 row 7 同 |

第 9~11 行的 `row & 7` 回绕到 5/6/7，与第 1~3 行落进**完全相同的 tile**。

### 2.3 tilemap 字节级确认（`f043.vram.bin`，run `20261119T114607_970307`）

```
r10: 15f 161 163 165 167 169 16b 16d     ← 第 1 行
r11: 160 162 164 166 168 16a 16c 16e
...
r26: 15f 161 163 165 167 169 16b 16d     ← 第 9 行，同样的 tile
r27: 160 162 164 166 168 16a 16c 16e
```

`0x15F..0x16E` 共 **16 个 tile 被 `r10/r11` 与 `r26/r27` 双重引用**。
第 9 行的 `０１１` 字模写进这批 tile，第 1 行的 `００３`/`妙蛙花` 就被覆盖 —— 与画面「顶行变 No011 ------」完全对应。

### 2.4 为什么现有规避机制没拦住

`grid_tile_resolved` → `grid_cell_points_to(win, col, t0)` 判定「这对 tile 就是本格上次写的，可原地重用」。
图鉴第 9 行与第 1 行**屏幕列相同**（都在 col 19..26），于是第 9 行被误判成「本格旧 tile」，直接覆写。

`grid_tile_is_other_col_natural` 只能防「同 band 内**不同列**」互抢，防不住「同列、不同行、band 回绕」。

## 三、修复

### 3.1 改法：回绕行的存储列翻半区

```c
static unsigned grid_store_col(unsigned row, unsigned col)
{
    if (row < GRID_SEG_COUNT)
        return col;
    return col ^ 16u;      /* 只翻低 4 位，仍在 [0, GRID_COLS_PER_SEG) */
}

static uint16_t grid_tile(TextPrinter *win, unsigned col)
{
    unsigned row = grid_row(win);
    return (uint16_t)((unsigned)tb + 2u
            + (row & (GRID_SEG_COUNT - 1u)) * GRID_SEG_TILES
            + 2u * grid_store_col(row, col));
}
```

**为什么成立**：
- `col ^ 16 != col` 恒成立 ⇒ 同 band 内两行的存储列必然不同 ⇒ 不再同 tile
- 屏幕位置由 tilemap 表项决定，与存储 tile 号无关 ⇒ 画面位置不变
- `row < 8` 时 `grid_store_col` 原样返回 ⇒ 绝大多数窗口行为零变化
- 图鉴 11 行时最多 2 行共享一个 band（row 5/13、6/14、7/15），翻半区足够

`grid_tile_is_other_col_natural` 同步改用 `grid_store_col(row, except_col)` 比较，
否则「本格本征」判定会与新的存储列错位。

### 3.2 改动文件

- `configs/POKEMON_RUBY_AXVJ00/hook/src/text/PrintNextChar_hook.c`
  - 新增 `grid_store_col()`
  - `grid_tile()` 改用存储列
  - `grid_tile_is_other_col_natural()` 同步

  日志只出「意外 PC」）

## 五、方法论教训

1. **「同列不同行」是 tile 网格的盲区**：现有规避机制全部围绕「同 band 内的列冲突」，
   而 band 回绕导致的是「同列跨行冲突」，两者判据完全不同。
2. **`row & 7` 的隐含前提是「窗口不超过 8 个行段」**。图鉴 11 行打破了这个前提，
   但代码里没有任何断言或注释提示这一点 —— 后续若出现更多行长窗口（如图鉴按字母分组、
   长列表菜单），都会撞同一堵墙。`grid_store_col` 只解决「2 行共享一个 band」，
   若将来出现 3 行共享一个 band（>16 行窗口）需要再扩一档。
3. **GDB 打印序列比看画面更快定位**：`InitTextPrinter` 的 `curY` 直接暴露了行号回绕，
   比逐帧看图快一个数量级。
4. **断点地址的奇偶性**：thumb 断点必须落在偶数地址，写奇地址不会报错，
   只会让 `by_pc` 匹配失败、日志出现「意外 PC」。这个坑值得记进工具文档。
