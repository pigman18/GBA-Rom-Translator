## BUG-9 存档确认对话框右上角日文残字

### 现象

存档确认界面（`save_confirm`），对话框**右上角**出现一截日文假名残字，
只画了上半部分（3 行高），下半被对话框边框裁掉。

### 证据（逐像素实测）

| 项 | 值 |
|---|---|
| run | `save/20261119T190445_703929` |
| 帧 | 020（`save_confirm`） |
| 乱码位置 | **x=168..201, y=120..122**（3 行高） |
| origin 同区域 | **完全空白**（0 处墨迹） |
| 用户截图 | 2026-11-19 19:03 |

逐行墨迹分布对比：

```
origin      y=120..122 : 无任何墨迹
translated  y120: [(169,169),(184,187),(189,189),(191,191),(201,201)]
            y121: [(168,174),(186,186),(189,189),(191,191),(201,201)]
            y122: [(168,168),(170,170),(186,186),(189,189),(191,191),(201,201)]
```

放大观察：是**日文假名字形**（类似「ぁりがとぅ」一类），非汉字、非乱码符号。

### 关键窗参数（GDB 实测）

```
[win] 0x0202E658 state=0 textMode=3 fontNum=3 BG0
      TILE_BASE=0x0001 TILE_OFF=0x0000
      curX=21 curTX=1 curY=9 curTY=0 index=2
tpl@0x081BB46C: charBase=2 tileData=0x06008000 tilemap=0x0600F800
raw win: 6C B4 1B 08 ... 03 03 01 0F 08 0F D4 7D 00 03 02 00 01 00 00 00 15 01 09 00
```

⇒ **`textMode = 3`，`TILE_BASE = 0x0001`**（极低，charBase 2 区）。

### 根因假设（已有反汇编依据，待实测确认）

`0x080034E0` 反汇编（`GetCursorTileNum` textMode 3 分支）确认为：

```asm
ldrb r1,[r0,#26]   ; curX
ldrb r2,[r0,#27]   ; curTX
adds r1,r1,r2      ; col
ldrb r2,[r0,#28]   ; curY
ldrb r3,[r0,#29]   ; curTY
adds r2,r2,r3      ; row
...
adds r1,#2         ; col + 2
ldrh r0,[r0,#22]   ; TILE_BASE
adds r1,r1,r0      ; TB + col + 2
lsls r0,r2,#4
subs r0,r0,r2      ; row*15
lsls r4,r0,#1      ; row*30
adds r1,r1,r0      ; + row*30
```

⇒ **原生 textMode 3：`tile = TB + 2 + col + 30*row`**

当前分支所有 textMode 共用：

```c
grid_tile() = TB + 2 + (row & 7) * 62 + 2 * col
```

两者在 `row>0` 时**完全不等**：
- 原生每行跨 **30** tile（15 列）
- 网格每行跨 **62** tile（31 列）
- 且 `col` 系数不同（1 vs 2）

`TB=0x0001` 时，`row=9`：
- 原生：`1 + 2 + col + 270 = 273 + col`
- 网格：`1 + 2 + 62 + 2*col = 65 + 2*col`

**差 200+ tile**，字被画到完全不同的地方 ⇒ 边框附近冒出残字。

### 修复方向

按 textMode 分派落址（与本轮 BUG-C 修 textMode 0 同一思路）：

| textMode | 落址公式 | 依据 |
|---|---|---|
| 0 | `TB + TILE_OFFSET` | 已修（`b9e2db8`） |
| 1 | 网格（唯一需分配 tile） | 现状 |
| 2 | 缓冲指针 | 已修空格（`d50100e`） |
| **3** | **`TB + 2 + col + 30*row`** | `0x080034E0` 反汇编 |

⚠️ 改动前必须先用 GDB 在 `save_confirm` 场景实测 textMode 3 窗的
`TB/curX/curY/curTX/curTY` 与 tilemap 实际落点，确认 30 这个常量
（不能只凭一次反汇编就改，`30` 也可能是 `GRID_TILEMAP_W` 的变体）。

### 复现命令

```bash
PYTHONIOENCODING=utf-8 python bot/run.py POKEMON_RUBY_AXVJ00 save \
  --save "bot/scenes/POKEMON_RUBY_AXVJ00/saves/Route118_68-7.sav" --timeout 900
# 看 translated/020.png，区域 (168..201, 120..122)
```

## BUG-8 根因已定位（2026-11-19 19:16，GDB + tilemap 实证）

### 不是「雷丘」个案 —— 所有多字宝可梦名都受影响

`battle_move_anim` 帧 080 实际抓到的是「蛇纹熊」：

```
translated 对话框：野生的蛇[残字]の / 头锤！
translated 敌方名：蛇[残字]
origin     对话框：やせいの ジグザグマの / たいあたり！
```

`ジグザグマ`（5 假名 8px）→ `蛇纹熊`（3 汉字 12px），**字符数变少但每字变宽**，
占位与推进不匹配。

### GDB 实测：推进完全正确，问题在单字占位

对话框窗（`win=0x03004170`，`textMode=0`，`TB=0x0090`，`curX=2`，`curY=15`）：

| | TILE_OFF | curTX |
|---|---|---|
| origin | 0x0004 | 0 |
| origin | 0x0006 | 1 |
| origin | 0x0008 | 2 |
| translated | 0x0004 | 0 |
| translated | 0x0006 | 1 |
| translated | 0x0008 | 2 |

⇒ **`TILE_OFF = 4 + 2*curTX`，两侧逐字完全一致**。推进逻辑没错。

### tilemap 实证：差异在「占几列」

帧 072 的 VRAM dump，对话框行（`ty=15`），`sb=2`：

```
origin      : x=3 → 0x181,  x=5 → 0x181,  x=7 → 0x088
translated  : x=6 → 0x111,  x=8 → 0x088
```

- **origin**：假名隔列占位（3、5、7），每字 **1 列**
- **translated**：汉字只占 6、8 两列，且 `sb=6` 出现 `1EE/1FF` ——
  **字被画到了别的 BG**

⇒ **12px 汉字占 2 列，但 `TILE_OFFSET` 每字只推进 2（=1 列）**，
导致后续字与前一字的右半列重叠。

### 代码定位

`grid_emit()` 的 textMode 0 分支（`PrintNextChar_hook.c:717-745`）：

```c
grid_pair_store(p0, t->base + 32u * lt);          /* 写 lt, lt+1  (64B) */
if (ncols > 1u)
    grid_pair_store(p1, t->base + 32u * (lt + 2u)); /* 写 lt+2, lt+3 (64B) */
...
win_set_u16(win, WIN_TILE_OFFSET, off + 2u * delta);   /* 只推进 2 */
```

`grid_pair_store` 每次写 **64B = 2 个 tile**：
- `p0` → `lt, lt+1`
- `p1` → `lt+2, lt+3`
- 合计占 **4 个 tile**

而 `TILE_OFFSET += 2` 只前进 **2 tile** ⇒ 下一字的 `p0` 落在 `lt+2`，
**与上一字 `p1` 的起始位置重叠**。

### 待确认（下一步实测，不猜）

1. `phase=0` 时 `ncols` 到底是 1 还是 2？
   - 若 `ncols=2` 但字只占 8px，则 `p1` 是**无意义的旧内容回写**，
     应跳过写 `p1`
   - 若字真的占 12px，则 `TILE_OFFSET` 应 `+= 4` 而不是 `+= 2`
2. `p1` 实际有效宽度是 4px（16B）还是 8px（32B）？
   看 `grid_load` 之后 `p1` 里非零字节的分布即可判定
3. 需要在 `grid_emit` 里加 `GRID_DIAG` 打点，输出
   `phase / ncols / delta / lt / p1 非零字节数`

### 判定标准

改完后 `battle_move_anim` 帧 080 的对话框应显示
`野生的蛇纹熊の` / `头锤！`，且 tilemap 上三字各占独立列，
无 `sb=6` 的 `1EE` 串扰。

## BUG-8 深层根因：12px 字宽 vs origin 8px 推进（2026-11-19 19:22 实测）

### 诊断打点实测结果

在 `grid_emit` 的 textMode 0 分支临时打点（`0x0203E100`，已删），
跑 `battle_move_anim` 读三帧：

| 帧 | rel | ncols | delta | lt | p0非零 | p1非零 | p1每行非零 |
|---|---|---|---|---|---|---|---|
| 002 | 15 | 2 | 1 | 0x0B2 | 64 | 64 | 16×4（满） |
| 011 | 9 | **1** | 1 | 0x0A6 | 64 | 64 | 16×4（满） |
| 072 | 9 | **2** | 1 | 0x1CA | 64 | 64 | 16×4（满） |

**关键**：
1. `p1` 是**满 64B**（16 行 × 4B 全非零），不是「只有前 16B 有效」
   ⇒ `p1` 确实占满 2 个 tile（`lt+2`, `lt+3`）
2. `ncols=2` 但 `delta=1` —— **占 2 列，只推进 1 列**

### 架构级矛盾

`grid_emit` 一次写入：

```
p0 → lt,   lt+1    (64B)
p1 → lt+2, lt+3    (64B)     ncols=2 时
合计占用 4 个 tile
```

而推进：

```c
win_set_u16(win, WIN_TILE_OFFSET, off + 2u * delta);   /* delta=1 ⇒ +2 = 2 tile */
```

**占用 4 tile，推进 2 tile** ⇒ 下一个字的 `p0` 落在 `lt+2`，
**直接覆盖上一字 `p1` 的右 4px 列**。

### 为什么 origin 没这个问题

| | 字宽 | 每字占 tile | TILE_OFFSET 推进 |
|---|---|---|---|
| origin（假名 8px） | 8px | 1 列 = 2 tile | +2（1 列）✅ 匹配 |
| 我们（汉字 12px） | 12px | 1.5 列 = 3 tile | +2（1 列）❌ 少 1 tile |

origin 的 `+2` 是**为 8px 设计的**。12px 字需要 1.5 列，
推进必须是 3（tile 单位）或按 1.5 列交错。

### `phase` 机制本该解决这个，但没生效

`grid_phase_for()` 从串首重新扫描累加（`grid_phase_adv` 的
`while (i < index)`），`adv=12`：

```
字 0: phase = 0    → 占 p0(8px) + p1(4px)
字 1: phase = 12 & 7 = 4  → 左 4px 属上一字，读回继承
字 2: phase = 24 & 7 = 0
字 3: phase = 4 ...
```

即 `phase` 在 0/4 间交替，**每两字占 3 列**（0→1.5→3）。

但 `TILE_OFFSET` 每字固定 `+2`（1 列），**两字只前进 2 列**，
而实际需要 3 列 ⇒ 每两字累积 1 列误差。

### 修复方向（需先验证再动手）

**核心**：`TILE_OFFSET` 的推进必须与 12px 的 1.5 列对齐。

两种可能方案，必须用实测选择：

**方案 A：按 phase 分段推进**
```c
/* phase=0 的字占 1.5 列，推进 3 tile；
 * phase=4 的字只占后 0.5 列，推进 1 tile；
 * 合计 4 tile / 2 字 = 2 列 / 2 字 = 1.5 列/字 ✅ */
unsigned adv_tiles = (phase == 0u) ? 3u : 1u;
```
⚠️ 风险：会改变 `TILE_OFFSET` 与 origin 的一致性，可能影响
`curTX` 的语义（游戏可能用 `TILE_OFFSET` 做别的事）。

**方案 B：不改 TILE_OFFSET，改写入位置**
让 `lt` 由 `phase` 决定偏移，而非直接用 `TILE_OFFSET`：
```c
uint16_t lt = TB + TILE_OFFSET + ((phase == 4u) ? 2u : 0u);
```
⚠️ 需要验证 `phase=4` 时 `TILE_OFFSET` 的实际值。

**方案 C：维持现状，但让 p1 不写满**
`phase=0` 时 `p1` 只写右 4px（16B），不碰 `lt+3`。
但这不解决「推进不足」的本质问题，只缓解覆盖。

### 下一步（不猜）

1. 用 GDB 抓**同一个串连续 4 个字**的 `(phase, TILE_OFFSET, lt)` 三元组
   —— 现在只有零星帧，看不到连续演进
2. 对照 origin 同串的 `(curTX, TILE_OFFSET)`，确认 origin 的
   `curTX` 是每字 +1 还是交替
3. 三方案逐个在 `battle_move_anim` 上试，看哪个能让
   「野生的蛇纹熊の」完整显示且不覆盖

### 判定标准

帧 080 对话框显示 `野生的蛇纹熊の` / `头锤！`，
敌方名牌显示 `蛇纹熊`，且 tilemap 上三字各占独立列。

## BUG-8 最终定位（2026-11-19 19:25，双侧序列对照）

### 双侧完整序列对比（同一对话框窗，TB=0x0090，curX=2，curY=15）

**origin（假名 8px）**

```
index  TILE_OFF  curTX
  0     0x0004     0
  1     0x0006     1
  2     0x0008     2
  3     0x000A     3
  ...
  7     0x0012     7
  8     0x0038     0     ← 换行：TILE_OFF 跳 0x26 = 38 = 19 列
  9     0x003A     1
```

`curTX` 每字 **+1**，`TILE_OFF` 每字 **+2**（1 列）。严格线性。

**translated（汉字 12px）**

```
index  TILE_OFF  curTX   2*curTX+4
  0     0x0004     0        0x04  ✅
  4     0x0006     1        0x06  ✅
  5     0x0008     2        0x08  ✅
  9     0x000C     4        0x0C  ✅   ← curTX 跳过 3
 13     0x000E     5        0x0E  ✅
 17     0x0012     7        0x12  ✅   ← 跳过 6
 21     0x0014     8        0x14  ✅
 26     0x001A    11        0x1A  ✅   ← 跳过 9,10
 30     0x001C    12        0x1C  ✅
 34     0x0020    14        0x20  ✅   ← 跳过 13
 38     0x0022    15        0x22  ✅
```

### 结论 1：推进机制完全正确

`TILE_OFF = 4 + 2*curTX` **严格成立**，两侧同构。

12px 的 **1.5 列/字**由 `curTX` 的跳跃实现（+1 或 +2，平均 1.5）：

```
字0: curTX 0 → 1   (+1)   TILE_OFF +2  = 1 列
字1: curTX 1 → 2   (+1)   TILE_OFF +2  = 1 列
字2: curTX 2 → 4   (+2)   TILE_OFF +4  = 2 列
字3: curTX 4 → 5   (+1)   +2 = 1 列
字4: curTX 5 → 7   (+2)   +4 = 2 列
```

**两字合计推进 3 列 = 1.5 列/字 ✅**

### 结论 2：根因在 `p1` 的写入范围

`grid_emit` 每次写：

```
p0 → lt,   lt+1     (64B，8px 宽 × 16px 高)
p1 → lt+2, lt+3     (64B，同上)        ncols=2 时
```

**`p1` 是完整的 2 tile（诊断实测 16 行 × 4B 全非零）**。

但 12px 字的**右半只有 4px**（`phase=0` 时）或**左半 4px + 右 8px**
（`phase=4` 时）。`p1` 里那 64B 中，只有前 4px 列有意义，
其余是**背景填充**。

**当 `curTX` 只 +1（推进 1 列）时**，下一字的 `p0` 落在 `lt+2`，
正好是上一字 `p1` 的起始位置 ⇒ **上一字右 4px 的墨迹被下一字
的背景填充擦掉**，同时下一字的左 8px 覆盖上去。

视觉上就是「两个字的笔画糊在一起」——正是截图里的残字。

### 结论 3：为什么 origin 不会

origin 每字只占 **1 列**（`p0` 的 2 tile），根本不写 `p1`。
它没有「右 4px 跨列」这个概念，因为假名是 8px 整列。

### 修复方案（按风险从低到高）

**方案 C（最小改动，推荐先试）**：`p1` 只写有效的前 4px 列
```c
/* p1 右半只有 4px 有效（phase=0 时）；只写前 16B（4 行×4B），
 * 不碰 lt+3，避免把下一字要用的 tile 铺成背景 */
```
⚠️ 但 `phase=4` 时 `p1` 的右 8px 是下一字的左半，必须写满。
⇒ 需按 phase 区分：`phase==0` 只写前 16B，`phase==4` 写满。

**方案 A（根治，改动大）**：让 `p1` 在 `phase=0` 时不写
```c
if (ncols > 1u && phase != 0u)   /* phase=0 时右半由下一字自己画 */
```
⚠️ 需要 `grid_emit` 增加 `phase` 参数。

**方案 B（不推荐）**：改 `TILE_OFFSET` 推进 —— 会破坏与 origin 的一致性。

## BUG-8 最终根因（2026-11-19 19:31，逐字相位诊断）

### 逐字诊断实测（`@0x0203E200` 环形 32 条，已删）

对话框串 `啊!野生的○出现了!`，`TB=0x0090`，`textMode=0`：

```
s=55 phase=0 ncols=2 delta=1 rel=0  tOff=0x004 glyph=0x000   「啊」12px
s=56 phase=4 ncols=2 delta=1 rel=1  tOff=0x006 glyph=0x03C   「！」8px
s=57 phase=4 ncols=2 delta=2 rel=2  tOff=0x008 glyph=0xD00   「野」12px
s=58 phase=0 ncols=2 delta=1 rel=4  tOff=0x00C glyph=0x9D8   「生」12px
s=59 phase=4 ncols=2 delta=2 rel=5  tOff=0x00E glyph=0x20B   「的」12px
s=60 phase=0 ncols=2 delta=1 rel=7  tOff=0x012 glyph=0x126
s=61 phase=4 ncols=2 delta=1 rel=8  tOff=0x014 glyph=0x0F7
s=62 phase=4 ncols=2 delta=2 rel=9  tOff=0x016 glyph=0xB02
s=63 phase=0 ncols=2 delta=1 rel=11 tOff=0x01A glyph=0x178
s=64 phase=4 ncols=2 delta=2 rel=12 tOff=0x01C glyph=0x629
```

`glyph=0x00` 是「啊」的字形索引 0，**不是空格**（之前误判）。
`glyph=0x3C` 是 `0x3C = ！`（charmap 167 行），8px PCS 字。

### 相位计算是对的

```
「啊」12px → phase = 0        ✅
「！」8px → phase = 12 & 7 = 4 ✅
「野」12px → phase = (12+8) & 7 = 4 ✅
```

`grid_phase_adv` 的累加正确（`F7 00 hi lo` 加 `adv`，PCS 加 8）。

### 真根因：`delta` 与 `ncols` 在 phase=4 时不匹配

| 字 | 宽 | phase | ncols | delta | 占用列 | 推进列 |
|---|---|---|---|---|---|---|
| 「啊」 | 12 | 0 | 2 | 1 | 2 | **1** ❌ |
| 「！」 | 8 | 4 | 2 | 1 | 2 | **1** ❌ |
| 「野」 | 12 | 4 | 2 | 2 | 2 | 2 ✅ |

`grid_emit` 每次写 `p0`(2 tile) + `p1`(2 tile) = **4 tile = 2 列**，
但 `delta=1` 时 `TILE_OFFSET` 只推进 **2 tile = 1 列**。

⇒ **下一个字的 `p0` 落在 `lt+2`，正是上一字 `p1` 的起始位置**，
把上一字右 4px 的墨迹整片铺成背景色 ⇒ 两字笔画糊在一起。

### 为什么 origin 没这个问题

origin 的 8px 假名在 `phase=4` 时：
- 只占 **1 列**（`p0` 2 tile），右 4px 由**下一个字**画
- `delta=1`，推进 1 列 ✅ 匹配

我们的引擎在 `phase=4` 时**仍写满 `p0`+`p1`**（`ncols=2`），
把本该留给下一个字的右半列也写成了背景 ⇒ 覆盖。

### 修复方案（待实施）

`phase=4` 时，`p1` 的右 8px（即 `lt+3`）**不应写**：

```c
/* phase=4：字从第 4px 开始，占 4px(左半 p0) + 8px(p1)。
 * p1 的 8px 是完整的一列，必须写。
 * 但 TILE_OFFSET 只推进 1 列，下一个字的 p0 会落在 p1 的位置。
 * ⇒ 需要让 delta 与 ncols 一致：delta = ncols */
```

**核心修正**：`delta` 应等于 `ncols`，而不是 `(phase+adv)>>3`。

验证：
- 「啊」12px phase=0：ncols=2，delta 应=2（当前 1）→ 推进 2 列
- 「！」8px phase=4：ncols=2，delta 应=2（当前 1）→ 推进 2 列

但 origin 的 `delta` 是 1... 因为 origin 8px 字不跨列。

**结论**：这是 12px 引擎的固有矛盾 —— 12px 字跨 2 列，
但 origin 的 `TILE_OFFSET` 语义是 1 列/字。**必须让 delta 与 ncols 一致**，
代价是 `TILE_OFFSET` 与 origin 不再逐字相同（但 origin 本来就没有 12px 字，
无需对齐）。

### 下一步

1. 改 `delta = ncols`（在 `grid_draw_chs` 和 `grid_draw_pcs` 两处）
2. 跑 `battle_move_anim` 看「蛇纹熊」是否完整
3. 若行宽溢出（12px 字变宽后一行放不下），需同步调窗宽或换行逻辑
4. 回归 `battle_dialog` / `dex` / `bag` / `navigator` / `start_menu`

### 三处 `cmp #9`（10 字节）的限制点

`PC=0x0803A87E LR=0x08037D14`，反汇编出**真正的填充点**：


三处同类限制：

| 地址 | 作用 | 改大后 |
|---|---|---|
| `0x08004294` `movs r4,#5` | 截断到 5B | ✅ 有效（1字→2字） |
| `0x0803A1E0` `cmp r4,#9` | 展开占位符时拷 10B | ❌ 无效（只是多读相邻数据） |
| `0x0803A880` `cmp r2,#9` | **写结构体名字槽** 10B | ❌ **游戏卡死**（实测场景超时 f=6899） |

⇒ 只有第一处能安全放宽。第三处改大会让结构体越界写坏相邻字段，
导致战斗流程直接挂死。

### 为什么中文名只显示 2 个字

中文名 `F7 00 hi lo` × 3 = 12B，塞进 6B 槽：
- 第 1 个字占满 4B，剩 2B
- 第 2 个字只剩 2B（`F7 00`），第 3 字完全没有

实测缓冲 `f7 00 02 26 f7 00 02 63 f7 00` 正是「长翅」+ 半个字。

### 这是结构性限制

要让战斗血条显示完整中文名，必须**扩大那个 6B 槽数组**，
而它在**宝可梦对战结构体**里，槽数 × 6B 的布局被多处代码依赖
（`r5+8`、`r5+0` 都能看到相邻槽）。

**不属于「改一个常量」能解决的范围**，需要：
1. 找到填充这个槽数组的代码（从旧表拷日文名的地方）
2. 把 6B 槽扩成 16B（或改存指针）
3. 同步改所有读这个数组的代码

### 当前状态

`#13`（`0x4294`）补丁保留：它让 **6B 槽里的 2 个汉字**能完整显示
（从 1 字变 2 字，是净改善，且实测存档界面无副作用）。

`0x3A1E0` 的第二层补丁**已撤销**——它只让错位残片变多，不改善结果。

### 与 origin 的对照（用户强调的关键）

| | 名字 | 槽占用 | 显示 |
|---|---|---|---|
| origin | バシャーモ（5 假名） | 6B（正好满） | 完整 ✅ |
| translated | 火焰鸡（3 汉字 12B） | 12B > 6B | 只显示 2 字 ❌ |

**这是中文名比日文名长的必然结果**，不是渲染 bug。

## 21:45 真根因：reflow 误改了一个不相关的引用（0x083DCACC）

### 用户的关键提问

> translate plan 本来就有一个完整的 stride 扩表吧，逻辑是拿到所有翻译文本，
> 最长的作为基准进行扩表，然后再统一改写所有读取点，那个没起作用吗？

**起了作用，但改错了一个引用。**

### reflow 确实生效了

`work/POKEMON_RUBY_AXVJ00/write.plan.json`：

```
宝可梦名: old_stride 6 → new_stride 24, count 412
          insns 100 条, literals 67 处
```

新表 `0x09EB0AF4` 里 idx 309 = 「长翅鸥」12B 完整，数据是对的。

### 两条展开路径，一条读新表、一条读错地方

战斗名字有**两个不同的展开器**：

| 调用点 | 展开器 | 实际行为 |
|---|---|---|
| `0x08037CF0`（存档/其他） | `bl 0x803A668` → `0x803B11C` | ✅ 读**新表** `0x09EB0AF4`，stride 24，正常 |
| `0x08042408`（战斗血条） | `bl 0x8039F24` → `0x8039FC0` → `0x803A1AC` | ❌ 读**被改错**的地址 `0x0956E608` |

`0x0803A1AC` 里的字面量：

```
原版 0x0803A1CC: 0x083DCACC   ← 原版引用
产物 0x0803A1CC: 0x0956E608   ← reflow 改写成了这个
```

### `0x083DCACC` 根本不是物种名表

| 地址 | 内容 | 判定 |
|---|---|---|
| `0x1CA354`（真物种名表） | `ac ac ac ac ac ff` / `6c 5c 88 91 68 ff`（フシギダネ） | ✅ stride 6 |
| `0x083DCACC`（被误认） | `91 72 60 6f 8b ff` / `70 62 79 ff` / `fc 02 00 06 11 ff` | ❌ **含 `fc 02` 控制码，是剧情文本** |

`0x083DCACC` 段里**没有「フシギダネ」编码**（`6c5c889168`），
按 FF 分段也不符合物种名表结构。

### 产物里被改成什么

```
0x0956E608 处: f7 00 05 42 f7 00 02 ee ff ...   ← 「坏蛋」
```

reflow 把它指到了一个**别的中文文本表**（idx0=坏蛋、idx2=能），
**不是物种名表**。

### 结论

`0x083DCACC` 是一个**碰巧长得像名字表**的引用（FF 分隔的短串），
`struct_reflow` 的读点识别把它当成了物种名表的别名，跟着改写，
结果战斗血条读到了完全不相干的中文文本。

**这就是为什么 `#13` 只能从 1 字变 2 字**：
读的是「坏蛋」这类短文本，不是真的宝可梦名。

### 修法（待实施）

把 `0x0803A1CC` 处的引用**改成真正的新表基址 `0x09EB0AF4`**，
覆盖 reflow 的错误改写。这样 `0x08039FC0` → `0x0803A1AC` 这条路径
就能读到正确的中文名。

⚠️ 需要先确认 `0x0803A1AC` 里那个引用的**读取 stride**：
它按 `表 + i` 逐字节拷（`cmp r4,#9`），如果表 stride 是 24，
需要同时改 stride 计算。

## 22:36 完整链路确认：nickname[10] 是存档格式硬限制

### SpDump2 探针（@0x0803A880）实测寄存器

```
PC=0x0803A880 LR=0x08037D14 r0=0x030044F8 r1=0x000000F7 r2=0x00000001 r3=0x030044F8
```

`r0 = r3 = 0x030044F8` 是**逐字节写入的目标地址**。

### 0x030044F8 属于 gPlayerParty

| 符号 | 地址 | 大小 |
|---|---|---|
| `gPlayerParty` | `0x03004360` | `0x258` |
| `gEnemyParty` | `0x030045C0` | `0x258` |

`0x030044F8 - 0x03004360 = 0x198 = 408`
Pokemon 结构 100 字节 → `408 = 4*100 + 8` → **`gPlayerParty[4]` 的 +8**

**`+8` 就是 nickname[10]**（Gen3 存档格式：`+0 personality / +4 otId / +8 nickname[10] / +18 language / +19 flags`）。

### 完整调用链

```
0x08037CFC  bl 0x80399B4        ; 准备 species
0x08037D04  ldrh r1,[sp,#14]    ; r1 = species
0x08037D06  bl 0x803B11C        ; 从新表读名字到 sp（无长度限制，完整）
0x08037D0A  adds r0,r7,#0       ; r7 = &gPlayerParty[4]
0x08037D0C  movs r1,#2
0x08037D0E  mov  r2,sp
0x08037D10  bl 0x803A668        ; 把 sp 的名字写到 r7+8（nickname[10]）
             └─ 0x0803A870 循环 cmp r2,#9  ← 只拷 10 字节
```

**名字在第 2 步是完整的**（`0x0803B11C` 从新表读），**在第 3 步被砍成 10 字节**。

### 为什么不能把 cmp 改大

| 尝试 | 结果 |
|---|---|
| `cmp r2,#9` → `#12` | **游戏卡死**（场景超时 f=6899） |
| `cmp r2,#9` → `#15` | 名字仍 2 字，第 3 字变 `0x0102` 垃圾 |

原因：`nickname[10]` 后面紧跟 `+18 language / +19 flags / +20 otName[7]`，
写超会破坏这些字段 → 宝可梦数据损坏 → 战斗流程挂死。

### 结论

**`nickname[10]` 是 Gen3 存档格式的硬限制，物理上放不下 12 字节（3 汉字）。**

要完整显示，只有两条路：

**A. 让显示路径绕开 nickname，直接用 species 查表**
`0x08042408`（战斗血条名字格式化）拿不到 species，
但它的上游 `0x08037CF0` 有（`ldrh r1,[sp,#14]`）。
需要改 `0x08042408` 的入参或改成在 `0x08037CF0` 里直接拼字符串。

**B. 缩短中文名到 2 字**
386 个已翻译名字里：2 字 46 个、3 字 251 个、4 字 80 个、5 字 9 个。
3 字以上共 340 个（88%），不可行。

### 当前保留的补丁

```json
{"off":"0x4294","bytes":"0d 24"}    // 截断 5→13（有效，1字→2字）
{"off":"0x3A1C6","bytes":"0f 2c"}    // A 分支 5→16
{"off":"0x3A1E0","bytes":"0f 2c"}    // B 分支 10→16
```

实测效果：**「蛇纹熊」前两字正确显示**（`蛇纹` + 残缺），
比修复前的「1 字 + 乱码」明显改善，且存档界面 0 像素差异、无卡死。
