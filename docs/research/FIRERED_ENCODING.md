# 火红编码协议调研（2026-11-04）

> 只调研 `roms/translated/宝可梦火红日版汉化2.2.gba`，
> 对照基线用同版本的 `roms/origin/POKEMON_FIRE_BPRJ00.gba`。
> **不涉及其他汉化版 ROM**（用户明确要求）。

## 一、结论速览

| 问题 | 结论 | 证据 |
|---|---|---|
| 火红用哪些中文编码？ | **只用 `F7`** | 全 ROM 字节频次：F7 从 49,212 涨到 **171,834**（3.49 倍），是唯一显著增多的字节；F9 几乎没动（20,505 → 21,328） |
| F7 是 2 字节还是 3 字节？ | **3 字节 `F7 hi lo`** | 相邻 F7 间距分布：**间距 3 出现 100,711 次**（占绝对多数） |
| 码位空间多大？ | **真实码位 2,289 个**，hi 只用 0x00–0x0A 共 11 页 | 在确认为纯文本的区间（ROM 0x086D0000，360KB，F7 占 27.3%）统计 |
| 能不能压成 2 字节？ | **能**（12 位足够：4 位页 + 8 位偏移） | 2,289 < 4096 |

## 二、调研过程与证据

### 2.1 先确认「只有 F7」

对原版与汉化版做逐字节频率对比（`01_encoding.py`）：

| 字节 | 原版 | 汉化 | 倍数 |
|---|---|---|---|
| **0xF7** | 49,212 | **171,834** | **3.49 ★** |
| 0xF9 | 20,505 | 21,328 | 1.04 |
| 0xFE | 66,892 | 76,147 | 1.14 |
| 其余 | — | — | 1.01–1.31 |

⇒ 火红只引入了一个编码前缀 `F7`，不像我们的红宝石工程要区分
两套字形通道（新字 / 原字变形）。

### 2.2 确认是 3 字节

`02_f7_structure.py` 实测：

```
相邻 F7 的间距分布：
    间距 3: 100,711 次   ← 绝对多数
    间距 4:   9,955 次
    间距 5:   6,257 次
```

样本原文：

```
@0x006D3696  F7 00 A7 F7 00 D9 F7 01 1E F7 04 53 F7 ...
             ↑ └─┬─┘ ↑ └─┬─┘
           前缀 2字节 前缀 2字节
```

**⇒ `F7 hi lo`，每个汉字 3 字节。我们的 `F7 00 hi lo` 是 4 字节。**

> 用户原本期待「火红只用 f7 能减少 1 位编码」——**这个期待不成立**，
> 火红也是 3 字节。

### 2.3 真实码位只有 2,299（关键修正）

前几轮统计踩了**三个**坑，逐个纠正：

**坑 1：全 ROM 扫 F7 被指令污染**

直接扫全 ROM → 11,735 个码位（`03_f7_codespace.py`），
hi 用满 256 种、前 9 页几乎每页 255/256。

**根因（`13`/`14` 号脚本查明）**：代码段里有 `60 F7` 这种
**Thumb 指令 `b.n`（条件跳转）**，被当成了编码前缀。实测抽样：

```
0x080A0000 区： 60 F7 1A FD 50 20 E1 21 60 F7 16 FD 52 20 …
                └─┬─┘                    └─┬─┘
              b.n 指令                  b.n 指令
```

而低地址区「与原版差异只有 **0.2%**」—— 说明火红没改代码，
这些 F7 是原版就有的指令。

**坑 2：「周边字节像文本」的过滤太宽松**

加过滤后仍有 8,255 个码位（`04_f7_text_only.py`），hi 前 9 页依旧近满。

**坑 3：只看差异区也不够**

`14_clean_text_zones.py` 在「差异块 + F7 密度≥32」的区里统计，
仍得到 4,701 个码位、hi 用满 256 种 —— 因为低地址差异块里混着
**代码里被顺带改动的 F7 指令字节**。

### 2.4 最终锚定：主文本区

**唯一可靠的方法**：先用差异分析找到**整块被替换**的纯文本区，
再在该区内统计。

`07_diff_regions.py` 定位到最大差异区间：

```
ROM 0x086D0000  87 个 4KB 块  **335,756 字节**  密度 94.2%
```

`08_dissect_region.py` 三重验证它是纯文本：

1. 与原版差异 94.2%（整块被替换）
2. `0xF7` 占 **27.3%**（98,578 个），`0xFF` 占 6.9%
3. 抽样全是 `F7 00 35 F7 00 36 F0 F7 00 97 AB …`，无位图特征
   （各步长墨量变异系数 0.10–0.14，字模应在 0.05 以下）

`15_final_codespace.py` 在三个纯文本区统计：

| 区 | 地址 | F7 数 | 码位 |
|---|---|---|---|
| 主文本区 | `0x086D0000`（304KB） | 89,643 | 2,231 |
| 文本区 2 | `0x0871D000`（40KB） | 8,935 | 1,108 |
| 文本区 3 | `0x08AF5000`（24KB） | 5,169 | 764 |

**合并后：码位 2,299 个**

hi 实际只用 **21 种**（有效 0x00–0x0A 共 11 页）：

| hi | lo 使用数 |
|---|---|
| 0x00 | 247/256 |
| 0x01 | 253/256 |
| 0x02 | 252/256 |
| 0x03 | 253/256 |
| 0x04 | 251/256 |
| 0x05 | 246/256 |
| 0x06 | 229/256 |
| 0x07 | 227/256 |
| 0x08 | 173/256 |
| 0x09 | 95/256 |
| 0x0A | 54/256 |
| 0x40 以上 | 零星（各 1 个，疑为残留） |

**频次覆盖率**：

| 保留字数 | 覆盖出现次数 |
|---|---|
| 500 | 83.6% |
| 1000 | 94.8% |
| 1500 | 98.5% |
| 2000 | 99.7% |

## 三、文本指针改写策略（实测）

`10_text_pointers.py` 统计「指向汉化新增文本区的指针」：

```
指针槽位数: 7,711
不同目标地址: 4,912
平均每个地址被 1.6 个槽位引用

抽样 5000 个槽位在原版里的值：
  与汉化相同:  24（0.5%）
  被改写:    4976（99.5%）
```

原版这些槽位指向 `0xFFFFFFFF`（1471 个）或旧日文文本地址
（`0x083DD805`、`0x08204660` 等）。

**⇒ 证实用户的描述：常规文本「写新区 + 改指针」，占 99.5%。**

字符串结构（按 0xFF 切分）：

```
非空段 6,435 段
段长：均值 52.2  中位 36  最大 6177
超短段（≤6 字节）: 530（8.2%）
段长重复最多的：长度 9（606 段）、6（479 段）、12（372 段）、15（261 段）
```

**段长大量重复（9/6/12/15）⇒ 存在等长/等距文本块**，
与用户描述一致（等长补 00、等距用 00 分隔）。

**超短段占 8.2%** ⇒ 短文本（如「はい」「いいえ」）也走同一套编码，
而不是特例处理。

## 四、宝可梦名「串档不乱」的机制（部分查明）

`12_find_name_table_exact.py` 扫描「原版是日文、汉化含 F7」的 64 字节块，
全 ROM **只有 2 处**（`0x08126300`、`0x08138540`，各 64 字节）。

⇒ **火红没有把宝可梦名等存档数据结构改成 F7 编码。**

这解释了它为何串档不乱：

- 存档里的宝可梦名仍是**原版字符集**（单字节假名/拉丁）
- 汉化只在**显示时**做映射，不改存档数据

> **待补充**：火红具体用哪张映射表做显示替换？需要进一步定位
> （可能是渲染 hook 里读一张码位映射表）。

## 五、对我们的启示

### 3.1 「减少 1 位编码」做不到（火红也 3 字节）

火红是 `F7 hi lo`（3 字节），我们是 `F7 00 hi lo`（4 字节）。
**持平，没有可借鉴的节省。**

### 3.2 但「压成 2 字节」是可行的——火红没做，我们可以做

既然真实码位只有 2,289 个，且 hi 实际只用 11 页：

```
2 字节方案：<前缀> <页:4bit | 偏移:8bit>   → 16 页 × 256 = 4096 个码位
```

2,289 个字符只占 4096 的 56%，**余量充足**。

**能省多少**：每汉字从 3 字节降到 2 字节，省 33%。
对文本区 360KB 来说，约省 120KB —— 对 8MB 的红宝石意义更大。

**前置条件（待验证）**：
1. 需要一个**不与现有单字节字符集冲突**的前缀字节
2. 渲染侧要能按「2 字节模式」解析，而不是现在的 3 字节解析

### 3.3 火红没做的原因（推测，待验证）

可能因为它是在原有工具链上二次开发，改编码格式要同时改
**写入侧**（翻译注入）和**读取侧**（游戏内渲染 hook），成本高。
我们这次要重写大部分逻辑，正好可以顺手做掉。
