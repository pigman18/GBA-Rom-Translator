# 火红有没有 SLT2 等价物？宝可梦名怎么防串档乱码？

> 2026-11-04 实测定案。对照 `roms/origin/POKEMON_FIRE_BPRJ00.gba` 与
> `roms/translated/宝可梦火红日版汉化2.2.gba`，逐字节验证。
> 脚本：`scripts/research/firered/probe_species_chain.py`、`probe_species_code.py`、
> `probe_orig_species2.py`、`probe_species_table_204660.py`、`probe_save_name.py`。

---

## 一、直接回答

**火红没有任何类似 SLT2 的运行时替换机制。**

证据（`FIRERED_ENCODING.md:11` 实测）：火红全 ROM 只有 `F7` 一种中文编码前缀，
`F9` 频次几乎没变（20,505 → 21,328），没有引入第二套编码通道，也没有哈希查表。

**宝可梦名防乱码靠的是「换表不换数据」：原版名字表一个字节不动，只改代码里的
31 处字面量指向新建的中文表。**

---

## 二、完整链路（实测）

### 第 1 步：原版名字表在哪

从汉化版里 35 处指向中文表 `0x0871F444` 的代码字面量反查，**同一位置在原版里指向
`0x08204660`**（31 处）。

```python
# probe_orig_species2.py
汉化版里指向 0x71F444 的 4 对齐位置: 35 处
  31 处 → 0x204660   （原版的目标）
   4 处 → 0xFFFFFFFF  （非指针，填充）
```

### 第 2 步：原版名字表有没有被改

**完全没动。**

```
0x204660 区域：
  412 项 × 11B 差异 0/4,532 (0.0%)
  前 4KB        差异 0/4,096 (0.0%)
```

### 第 3 步：代码怎么改的

```
0x204660 被引用：原版 32 处 → 汉化 1 处
0x71F444 被引用：原版  0 处 → 汉化 35 处（代码段 31 处）
```

**31 处代码字面量从旧表地址改成新表地址，一次批量替换。**

### 第 4 步：中文表放在哪

`0x0871F000..0x0871F446` 是**原版全 FF 空白区**（非 FF 字节 = 0），
中文表从 `0x71F444` 起：

```
0x71F446: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 f7 02 cf f7 02 71 ff ...
                                                                 ↑ 2 个汉字后 FF
0x71F45E: 00 00 00 00 00 00 f7 01 aa f7 01 e2 f7 02 77 ff ...
                                              ↑ 3 个汉字后 FF
```

结构 = `00 右对齐填充 + F7 中文串 + FF 结束`，**变长**，汉字 1~5 个。

### 第 5 步：存档里存的什么

**存档里存的原版编码，不是中文。** 验证：

```
原版 sav: 0xF7 出现 0 处
汉化 sav: 0xF7 出现 134 处
```

那 134 个 F7 看着吓人，但看上下文就知道不是名字：

```
0x06060: ... fb ff ff ff f7 ff ff df ff f7 ff ff ff f7 ff 8f 17 ...
               ↑ 勾选框标记，F7 夹在 FF 之间
0x070C0: ... cb fa 99 99 f7 8c d8 a4 d8 a4 d8 a4 d8 fa ca ...
               ↑ 加密/校验区
```

**都是二进制数据碰巧等于 0xF7，不是宝可梦名文本。**
宝可梦名在存档里仍是原版日文编码——所以换回日版不会乱。

---

## 三、为什么这套机制能防串档乱码

```
存档写入：用原版编码（数据表 0x204660 一个字节没动）
   ↓
存档读取 + 显示：代码读的是 0x71F444（中文表）
   ↓
换回日版 ROM：代码又指回 0x204660，读到的还是原版编码 → 名字正常
```

**关键：显示用的表和存档格式完全解耦。**
原版表不删不改（只是没人引用它了），中文表是纯新增。

---

## 四、和 ruby 的 SLT2 对比

| 维度 | 火红 | ruby（现状 SLT2） |
|---|---|---|
| 原数据表 | **一字节不动** | 一字节不动 |
| 中文从哪来 | 新增 ROM 静态表 + 改 31 处代码字面量 | 运行时 FNV 哈希查表 |
| 运行时开销 | **零** | 每字符一次查表（用户实测 1,000 条以上变卡） |
| 表放哪 | 原版空白区 `0x71F444` | `0x09EA0000`，256 桶分桶 |
| 代码改动 | 31 处字面量 | 完整查找实现 `slot_lookup_v2()` |
| 新语种/换字 | 改表即可 | 改表即可 |
| 失败风险 | 字面量漏改 → 该处显示日文 | 哈希冲突/桶损坏 → 乱码 |

**两者解决的是同一个问题（原数据不能动），但火红选了「换表」，
ruby 选了「运行时替换」。火红的方案零运行时成本，这正是不卡的原因。**

---

## 五、对 ruby 的结论

**SLT2 的「不动原数据」原则必须保留**（否则 1,098 条宝可梦名/训练家名串档必乱），
但**实现方式可以照火红改成静态表 + 改读取路径**：

1. 建一张中文名表，放扩展区
2. 找到 ruby 里读物种名的地方（对应火红那 31 处字面量）
3. 把字面量改成指向新表
4. 删掉 `slot_lookup_v2()` 运行时查找

**待确认**：ruby 的物种名读取路径在哪里、有多少处。
这需要单独查（`configs/POKEMON_RUBY_AXVJ00/symbols/pokeruby_jp.sym` 已有 `gSpeciesNames`）。

**注意一个陷阱**：火红原版日文是 1 字节/字，中文名表用 `F7 hi lo` 3 字节；
ruby 原版是 2 字节编码，中文用 `F9 00 hi lo` 4 字节。所以 ruby 的中文名表会比
火红的更大（同样字数下 4B vs 3B），但都是变长表，不影响可行性。
