# 推进方法论：为什么进度慢，怎么改（2026-11-18）

> 用户原话：「按道理来说，反汇编、gdb、bot、网络搜索啥条件都给你了也随时有验证手段，
> 但是现在推进进度还是不太行」。
> 这份文档是自我诊断 + 操作规约，不是给用户看的汇报。

---

## 一、进度慢的四个真实原因

### 1. 从机器码反推意图，而不是让执行结果自证

`STRIDE_FAILED_4TIMES.md` 已经写明：同一件事做了 4 次模式匹配（手抄站点 / ldr 前找 lsls /
按 addr_reg 追踪 / 按 index_reg 累计），覆盖率 7% → 57% → 80% → 41%，**越改越差**。

反推语义需要完整数据流分析，用启发式硬凑必然覆盖不全。
正确做法：**改 → 跑 bot → 看结果**，用输出证伪，不靠推理证明。

**操作规约**：任何「补丁打在哪」的判断，必须在 10 分钟内落到一次 bot 实测；
写不出可证伪假设就不许继续翻反汇编。

### 2. 同一块地反复回滚，不记录「为什么回滚」

仓库里 `HANDOFF_BATTLE_BAG_20261116.md` 记录了 7 条「失败过的路线」，
但每一条都只写「已回滚」，没写「回滚时的具体症状 + 当时的代码 diff」。

后果：下一次接手（包括我自己）会重新试一遍同样的路。

**操作规约**：每次回滚必须在 `docs/research/` 落一份
`ROLLBACK_<日期>_<主题>.md`，含：改了什么 diff、bot 哪个场景哪一帧坏了、坏成什么样（截图路径）。

### 3. 文档之间互相矛盾，没有单一事实源

实例（本轮亲历）：
- `DESIGN_TEXT_12PX_GRID.md` §9 写「禁止扩容 charBase / tile 分配器」
- `BATTLE_EMPTY_TEXT.md` §6 写「已实施 `grid_arena_hi(tb) = tb + 0x1F0`」并验收通过

两份都自称有效，我按后者改了，然后被用户回滚。
**根因**：没有「当前有效结论」的唯一索引，读者只能靠 commit 时间猜。

**操作规约**：新增结论必须写进 `docs/CURRENT_STATE.md`（单一事实源），
旧文档只在头部加 `> ⚠️ 已被 CURRENT_STATE.md §X 取代`，不删不改正文。

### 4. 拿「局部验证通过」当「任务完成」

本轮实例：战斗对话框出字了、背包/详情/训练家之眼回归通过，我就提交了。
但同一屏的菜单还有「背包→一モ」的残缺，用户一眼看出。

**操作规约**：UI 类修复的完成判据是「**用户能验收的那一屏整屏正确**」，
不是「我关注的区域正确」。提交前必须整屏截图自己先看一眼。

## 二、这个仓库里已被证明有效的工作方式

从成功案例（红框 BUG、图鉴 P24、背包排除）归纳：

| 有效 | 无效（反复失败） |
|---|---|
| 用户一句话指路 + 字节搜索几分钟定案 | 连续两晚在符号表/反汇编/指针表绕 4 小时 |
| 定量证据（110→0 纯红像素、128→0 差异像素） | 目测「看起来像」 |
| 单个最小改动 + 立刻 bot 实测 | 一次改一堆，坏了不知道哪个 |
| 从 origin 同屏反推「原版怎么显示的」 | 从自己 hook 的假设出发推 |

**共性**：有效路径都是「**用可测量的事实缩小范围**」，无效路径都是「**在脑内建模**」。

## 四、每轮工作的固定节奏

```
1. 选一个 BUG，写清「可测量判据」（一句话，带数字）
2. 用最小改动实现（单文件、单函数）
3. build.bat → 打包 → bot 采该场景
4. 量那个判据的数字，对比 origin
5. 通过 → 整屏看一遍 → 汇报（不提交）
   不通过 → 回滚该改动，落 ROLLBACK 文档，换假设
6. 用户说「提交」才 commit
```

**禁止**：
- 连续 3 次工具调用没产出数字（违反 AGENTS.md 三连卡死即停）
- 同一 BUG 试超过 3 个假设还不汇报（该问用户了）
- 改完不量数字就「感觉对了」
