## 二、逐 BUG 档案

### BUG-0 静态变量落 BSS（地基级）
- **现象**：每字形都分配到同一对 tile → 全屏同一字形
- **根因**：引擎分配游标用 C 静态变量；game.bin 是裸二进制无 crt0，
  BSS 不落位——写 ROM 被忽略、读为垃圾
- **修复**：状态一律固定 EWRAM 地址（game_addrs.asm 登记）
- **教训**：**引擎内禁止 C 静态/全局可变状态**；这是多条「每字同形」怪象的总根因

### BUG-1 队伍名称空白（Build A）
- **现象**：六行队伍名全部空白
- **根因**：把 tm=1+fn=4 当成 win[0x20] 指针缓冲——实际日版 tm=1 是
  FontFunc[1]+SubTable[4]（静态块 map 写表项），win[0x20] 是陈旧值
- **修复**：is_buffer_printer 收窄到 tm==2
- **教训**：**未反汇编就按假设实现**。tm=1 真实语义（SubTable 静态块）一周后才定案

### BUG-2 队伍名六行同名＋首字缺左半＋字大（Build B）
- **现象**：六行全显示最后一个名字；首字只有右半；字号比原生大一倍
- **根因①**：InitTextPrinter 每次清零 TILE_OFFSET，Field Linear 用它分配
  → 六行全部落在同一批 tile，表项又都指向那里
- **根因②**：12px 汉库 vs 原生 font4 8×8 小字——**队伍名是混合字体流**
  （全角拉丁/假名 8px 小字），尺寸维度被当成窗口常量忽略
- **修复**：TextMode1 独立行（EWRAM 游标分配）；尺寸问题记账未解
- **新引入**：TX+=2 → 16px 字距（后为 BUG-6 的一部分）

### BUG-3 请选择「择择择」＋战斗数字 dst=0（Build C/D）
- **现象**：请选择三格同一字；战斗/槽位数字区闪烁乱码
- **根因①**：charblock2 tile 预算超订——开始菜单网格(85..509) 与
  tm1 分配(257+) 重叠互踩
- **根因②**：战斗数字经 0x02CFC 包装打印，从不设 win[0x20]（恒 0）→
  **幻影打印**（原生 FontFunc[2] 写 0=BIOS 忽略）；可见数字另有通道（至今未定位）
- **修复**：dst==0 守卫；分配上界按 charBase
- **教训**：tile 预算按场景核算并硬上界；幻影打印必须显式建模而非碰运气

### BUG-4 详情页乱且非 12px（Build E）
- **现象**：详情页字段错位重叠，字形是 font3 原生残留（非我们的 12px）
- **根因**：详情页 = **tm0 + 每字段专属 TILE_BASE(0x290~0x330) +
  cursorY 55/57 字面行**（Linear 语义）；场景门控（font3+charBase2→
  menu_wants_mode2）把它误判进 Mode2 网格 → idx≈2400 全错位
- **修复**：tm3 拆行（TextMode3 网格），TextMode0 回纯 Linear
- **教训**：tm0/tm3 是两种原生语义；**合并进一行 + 场景门控二次分发 =
  错误放大器**（门控每多一条，误判面越大）

### BUG-5 TextMode2 直接实现翻车（Build D）
- **现象**：按 FontFunc[2] RE 实现缓冲写入后，详情页乱序加重
- **处置**：回滚到桩
- **教训**：缓冲路径的调用时序/布局未吃透（0x02CC0 与 0x02CFC 两种包装
  的区别当时未知）；先读 battle_interface/summary 渲染链再动手

### BUG-6 16px 全局字距＋隔离破坏（Build H，最严重）
- **现象**：标题菜单蓝条、诮选择、４０４４０４ 分裂、字距 16px——全面恶化
- **根因**：为修 16px 字距，让 tm1/tm3 走 Field Core 并**写 WIN_TILE_OFFSET**
  ——TILE_OFFSET 是 **tm0 Linear 的专属状态字段**，tm1 每字形覆写它 →
  tm0/tm1 交替打印时分配区互踩 → 修 A 坏 B
- **处置**：回滚
- **教训**：**这正是用户坚持「tm/fn 分发 + 独立 GetGlyph + UpdateTilemap
  分发」的原因——行间隔离。任何跨行写共享状态都是架构违规**，
  「越修越乱」的机制就是修复通过共享状态泄漏到其他模式

### BUG-7 进页偶发整屏随机乱码（Build D/G 偶发）
- **根因**：AllocGlyphTiles 无上界 → 游标越过 448（screenblock30 =
  请选择 tilemap）/960（screenblock31）→ **字形像素写进表项区**，
  表项变字形字节 → 随机 tile
- **修复**：按 charBase 硬上界（cb1≤447/cb2≤507；随回滚一度移除，
  text.c 设计中恢复）
- **教训**：tile 预算硬上界必须常在，不能因回滚连带丢掉

## 三、元规律：为什么越修越乱

1. **共享可变状态跨模式读写**（TILE_OFF、全局分配游标、pitch 槽被
   非 所属行操作）——修复 A 的副作用通过共享状态泄漏到模式 B，
   表现为「修好一个坏一批」
2. **未 RE 的语义用假设填充**——tm1 静态块、幻影打印、详情页
   per-field TILE_BASE，全是先写错后定案；错误模型上的修复必然再错
3. **多 fix 叠加不回滚归因**——D/E 两轮三项叠加后无法定位新问题由谁引入，
   直到分游戏日志对照才破案；应小步+单场景验证
4. **场景门控是对分发缺失的补丁**——门控每多一条，tm0 行的误判面越大；
   正解是拆行（一行一语义），不是加条件
5. **把字体/尺寸当窗口常量**——队伍名实为逐字形混合字体流
   （全角拉丁+假名+汉字），任何「本窗口是 X 字体」的假设都会在混排处崩

## 四、text.c 设计的对应防线

| 元规律 | 设计防线（docs/ruby_jp_design.md） |
|--------|-------------------------------------|
| 1 共享状态 | 行间零共享可变状态；TILE_OFF 归 tm0；分配池按 charBase 分区+上界 |
| 2 未 RE 先写 | UNKNOWN 诊断行：未验证组合消费不画，缺字即排查信号 |
| 3 叠加无归因 | 实施顺序按场景逐步开验证（设计文档 §八）；分游戏日志对照常态化 |
| 4 门控补丁 | 一行一语义（tm0/1/2/3 = 四种原生语义一一对应），行内无二次分发 |
| 5 字体常量假设 | GetGlyph 逐字形返回 {tiles, width, bank}；混合字体流按字形属性处理 |
