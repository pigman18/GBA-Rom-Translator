> 用户问：「你确定全网搜索过了，没有其他方案？」

## 一、先说结论（三句话）

1. **"全网"是做不到的**。可检索的部分我做了两轮共 **16 次查询 + 3 次原文抓取**；
   真正的一手经验大量沉淀在**贴吧 / B 站 / QQ 群 / Discord / 日文改造论坛**，
   这些**不被搜索引擎有效索引** —— 这是永久盲区，谁也无法宣称"搜完了"。
2. **但结论不依赖"有没有别的做法"**。见 §四：这是个**不等式**，不是技术选型问题。
   本轮新增了 6 条上次没有的具体实现与先例，**没有一条改变结论**。
3. **本轮真正的产出**：把"要不要继续找新方案"这件事，换成一个**可测的数字**（§六）。

## 二、检索空间穷举（这是"全网"的实际形状）

任何"让 GBA 显示中文"的方案，必然落在下面 4 个维度上。**没有第 5 个维度。**

| 维度 | 含义 | 已被考虑的形态 |
|---|---|---|
| **A 扩容量** | 让同屏能驻留更多字形 tile | A1 回收官方图集 / A2 走 OBJ / A3 换 charBase 重排 / A4 HBlank 流式 / A5 缩小字号 |
| **B 降需求** | 让同屏需要更少字形 tile | B1 版式重排减字 / B2 静态部分转图片 / B3 ASCII 回官方 8px 图集 / B4 改 UI 布局 |
| **C 换地基** | 不用现有引擎 | C1 全引擎移植 / C2 改 16px 步进 / C3 换现成第三方引擎 |
| **D 混合** | 上述组合 | 传统汉化的"混合方案" |

**关键**：v13/v14 已覆盖 A1–A4、B1、C1–C2。本轮补搜后新增的是 **B2/B3 的真实先例**、
**C3 的真实可跑实现**、以及 **A2 在真实汉化里被用过的证据**。

## 三、本轮新增（上次调研里没有的）

### 3-1 🔴🔴 `startfliing/gba_text_engine` part3 —— "THE Text Engine" [读原]
> "a variable-width font to **render characters across tile boundaries**"

2025-09/2025-11 的新项目，devkitARM + C++，**就是"变宽字形跨 tile 边界"这件事本身**。
带独立 `font class`（字形数据 + 字宽表）。三个 part 递进：贴图 → 定宽终端 → **变宽跨边界**。
⇒ 这是我们渲染层（R2）的**现代可跑对照实现**。来源：https://github.com/startfliing/gba_text_engine

### 3-2 🔴🔴 Tonc Text Engine（TTE）`chr4c` 渲染器 [读原]
Tonc 的成熟文本引擎，**7 个渲染族**，其中两个正是我们要的：

| 渲染族 | 布局 | 用途 |
|---|---|---|
| **CHR4C** | 字符 4bpp、**列主序** | **变宽字体画到 tile 背景上**（明确推荐） |
| CHR4R | 字符 4bpp、行主序 | 同上 |
| SE | 屏幕项 | 常规 tilemap 文字（含 **`se_drawg_w8h16`** 专用 8×16 绘制器 —— 正是官方画布尺寸） |
| ASE / BMP8 / BMP16 / OBJ | — | 仿射 / 位图 / 精灵 |

字体格式 = **tile-strip（瓦片条）1bpp**，带 `widths[]` 字宽表支持变宽；
`tte_write()` **原生吃 UTF-8**（"you're not limited to 256 characters"），
并有 `charLut` 做字符→字形号映射（＝我们的 charmap）。

🔴 **Tonc 原话：「VWF for tilemaps makes little sense」** —— tilemap 模式下每字 1 tile，
变宽无意义。**这是对"按字符码定号"（路线 B）的权威否定**，与我们 v14 的结论一致。

TTE 的 `chr4c_drawg_b1cts_c_8p` 与我们的 `extract_cols` + `blend_glyph_4bpp`
**是同一类操作**（1bpp→4bpp 展开 + 跨 tile 双写）：

```c
// TTE 的 8 像素批量解包（原文）
raw = *srcL++;
if(raw) {
    raw |= raw<<12;  raw |= raw<<6;      // 1bpp → 4bpp 位平面展开
    px = raw & mask<<1;  raw &= mask;
    px = raw | px<<3;
    pxmask = px*15;      px *= ink;
    dstL[0]     = (dstL[0]     &~ (pxmask<<lsl)) | (px<<lsl);   // 左 tile
    if (px &~ shiftMask)                                         // 跨边界
        dstL[dstP] = (dstL[dstP] &~ (pxmask>>lsr)) | (px>>lsr);  // 右 tile
}
```

来源：https://www.coranac.com/2025/08/deep-dive-into-tile-text-renderers/ ｜
https://gbadev.net/tonc/tte.html ｜ https://deepwiki.com/gbadev-org/tonc/5.2-text-rendering-systems

### 3-3 🔴🔴 TTE 实测性能基线（2025-08，硬件 + 4 个模拟器）[读原]

单字形（8 像素宽的 strip）绘制周期数：

| 配置 | 1p（逐像素） | 8p（8 像素批量） |
|---|---|---|
| Thumb + **ROM** | 2411 | 1585 |
| Thumb + IWRAM | 904 | 583 |
| **ARM + IWRAM** | 715 | 483 |
| 手写汇编 ARM+IWRAM | **499** | **369** |

- **ARM+IWRAM 比 Thumb+ROM 快约 3.4×**（最大单一收益）
- 8 像素批量解包再 **+50~100%**
- 手写汇编再 **+30%**
- ⚠️ "Do **not** put ARM code in ROM"（ARM 32 位指令走 16 位 ROM 总线，反而比 Thumb 慢）
- Mesen 与真机**逐周期完全一致**；mGBA/VBA 对 ROM 代码快约 1~3%

⇒ **意义**：我们的渲染/流式路线**性能预算可以放宽 3~5 倍**。此前对 A4（HBlank 逐带流式）
"时间不够"的顾虑，建立在 C/Thumb/ROM 的实现上 —— 换个实现就宽松了。

### 3-4 🔴🔴 Mother 3 英化：**与我们一模一样的病** [读原]

原文（Ars Technica 访谈，Tomato）：
> "The biggest problem was that the developers designed each 'system' (menu, battle, main text)
> in such a strange, rigid way that **there simply wasn't enough space in memory to allow for
> enough text on the screen at once**."
>
> "those [VWF] hacks were pointless **until we went in and actually allowed for more text to be
> displayed at once**."
>
> "**No text display routine wound up untouched**, and there were probably 10-20 different ones at least."

他们的实际动作（gamebrew 版本日志）：
- 主脚本**每行字数 22 → 50**
- 笔记菜单 / 调试菜单**增加每屏行数**
- **"Lowered the OAM footprint of names in the overworld"** ← **用 OBJ 画名字**（A2 被真实用过）
- "Added program that allows for more custom text lines"

⇒ **最强外部印证**：GBA 上最著名的自写文本引擎项目，卡点**不是字形渲染，是同屏可驻留文字量**，
解法是**逐个系统重写显示例程 + 扩大同屏容量**。耗时 1000+ 人时，10~20 套例程。

来源：https://arstechnica.com/gaming/2008/10/no-edits-junk-test/ ｜
https://mother3.fobby.net/blog/page/10/ ｜ https://www.gamebrew.org/wiki/Mother_3_GBA

### 3-5 🔴 rh-hideout-chinese 官方 README：他们的 R2 是靠**改文本**解决的 [读原]
> 「**修改了部分与汉化后文字展示相关的代码**」
> 「修正原汉化文本**单行字数溢出换行**的问题，**换行符数量超标导致的文字显示不全**的问题」

⇒ 这个被我们当"标杆"的项目，明确承认**动了展示代码**，且其"单行溢出/行数超标"

### 3-6 🔴 GBA 汉化的通行档位不是 12×12，而是 **8×8 / 8×16** [读原]
- `suhli/gba-narutorpg-chs`（GBA 火影 RPG 汉化工程）：**8×8 小字 + 8×16 大字**，
  大字用 **MuzaiPixel 8×12 提取后 pad 到 8×16**，`--8x16-scale pad`。
- 传统做法（itcher/GB Studio 讨论、百度文库《自己动手汉化GBA游戏》）：
  **汉字写进 16×16 方块，等分成 4 个 8×8 tile，tilemap 写 4 项**。
- FE GBA 汉化链（`laqieer/FEHRR` + FEBuilderGBA）：**Draw utf-8 patch + Anti-Huffman +
  字模按需生成入 ROM + 跨 ROM 拷字模**；字宽表（Width Table）决定 ASCII 半宽 / 汉字全宽。

⇒ 三件事：
1. **每字 4 tile 是 GBA 汉化的常态**，我们并不特殊；
2. **8×16 是实际通行档**，我们走 **11×11 比通行档更宽更豪华** —— 这也是为什么空间更紧；
3. **字宽表（Width Table）是标准件** —— 即"变宽字体"在 GBA 汉化里是常规做法，
   不是我们在创新。这提示 **B3（ASCII/数字走 8px 官方图集）** 是传统做法，我们没试过。

来源：https://github.com/suhli/gba-narutorpg-chs ｜ https://github.com/laqieer/FEHRR/issues/2 ｜
https://itch.io/post/7952790 ｜ https://blog.sina.com.cn/s/blog_49968e33010006ri.html

## 四、为什么"再找新方案"改变不了结论

所有 A/B/C 维度的方案，都在解**同一个不等式**：

```
同屏需要驻留的字形 tile 数   ≤   单层可寻址 tile 号  −  官方占用 − 窗框 − 静态美术
```

代入实测值：

| 项 | 值 | 依据 |
|---|---|---|
| 单层可寻址 tile 号 | **1024** | tilemap 表项 10 bit（GBATEK 硬上限） |
| 官方日文图集 | **−512** | font0/3 cap=512，每窗口预载 |
| 窗框 | **−23** | 实测 |
| 领航员静态美术（VRAM+0x5000） | **−64** | 落在"池"内部，`v8_official_end` 看不见 |
| ⇒ 实际可用 | **≈425** | |
| 一行 20 字（240px = 30 列 × 上下 2 行） | **60** | 11×11 步进 12px ⇒ 横跨 2 列、纵跨 2 行 |
| 领航员需要 9~12 行 | **540 ~ 720** | |
| **缺口** | **≈1.7×** | |

**这个不等式与"用什么渲染方式 / 什么分配算法 / 什么编码"无关。**
所以：

- 换渲染器（TTE / startfliing / 自写）⇒ **不改变**左边和右边，只改变速度。
- 换定号方式（格子 / 字符码 / 内容）⇒ **不改变**数量，只改变冲突形态。
- 换分配器（v8→v12 全部）⇒ **不改变**总量，只是把冲突搬家。

**只有三类动作能改变这个不等式**：
① 增大右侧（A1 回收 512 / A2 走 OBJ 的独立 1024 / A3 重排 VRAM / A4 时间换空间）
② 减小左侧（B1 减字 / B2 静态转图片 / B3 ASCII 回 8px / B4 改布局）
③ 换步进（C2 16px ⇒ 号=字符、免相位；但每字仍 4 tile，**不省量**）

⇒ **用户提出的三条前提（自定义 tilemap / 日文同链路 / 自定义分配）正是"只搬冲突不改量"的三次尝试**，
这解释了为什么每次都是"换了种撞法"。**跳出这三条 = 去做 ①②③，而不是继续找第四种搬法。**

## 六、本轮真正的产出：把争论变成数字

现在所有分歧都是**估算 vs 估算**（"425 号够不够""领航员要 12 行"）。
下一步应该是**实测**，两个数字：

### 6-1 实测 A：领航员到底需要多少个**不同的**字形 tile？
不是理论值 720，而是**逐行统计**：
- 领航员每个页面实际有多少行、每行多少字、全屏多少**不重复**汉字
- ⇒ 得出**真实需求 N**，直接和**真实可用 M**比

如果 N ≤ M，那**根本不需要 ①②③，只需要修 B1 排版**（零 ROM 风险）。
如果 N ≈ 1.2M，可能 **B3（ASCII 回官方 8px 图集）就够**。
如果 N ≥ 1.7M，才必须动 A1/A2/A3。

**这个数字目前谁都没有。它比再找 10 篇调研都值钱。**

### 6-2 实测 B：领航员场景的 VRAM 实际占用图
逐窗口打印 `font / TILE_BASE / charBase / official_end`，
并把 `0x06000000~0x0600FFFF` 按 32B 粒度标出"谁在用"。
⇒ 把"可回收区间"从推算变成实测，同时验证：**领航员 BG1 关闭 ⇒ 那段 VRAM 是否真空闲**（A3 的可行性）。

### 建议顺序
1. **实测 A**（纯静态扫描，零 ROM 风险）—— 定生死
2. 若 N ≤ M ⇒ 做 **B1 排版**（零 ROM 风险）
3. 若必须扩容 ⇒ **A1（回收 512 图集，实现面 = 1 函数 + 1 调用点）** 优先，
   **A3（BG1 独享画布）** 并行实测，**A2（OBJ）** 作为不动 BG 的回退路
4. 性能顾虑按 §3-3 重估：换 ARM/IWRAM 实现可放宽 3~5×
