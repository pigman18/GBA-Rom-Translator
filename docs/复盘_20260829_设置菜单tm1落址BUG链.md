## 1. 结论速览

| # | 现象 | 真因 | 修法 |
|---|------|------|------|

**死路（勿重试）**：找 `InitWindowTileData` 的调用方——`InitWindowTileDataRet` 读到的
`LR=0x08003928` 处是 `bl 0x081B1294`，那是 `swi 0x0B`(CpuSet) 的跳板，不是调用点；
扫遍 0x08002000–0x08006000 **没有任何 BL 指向 0x08002A50**（间接调用）。
**需要的是 hook 函数本体，不是调用方。**

## 2. 背景事实（一手实测，可直接引用）

### 2.1 tm1 的字库占满整个 charblock

```
InitWindowTileData(tpl=0x081BB874, startOffset=1, glyph 0..255)
  → 256 次调用，返回 r1 = 0x06008060 / 0A0 / 0E0 / …（每字形 +0x40 = 2 tile）
  → 落址 tile = startOffset + glyph*2 ，实占 [1, 513)
```

tm1 的设计前提就是「字库独占 charblock、文本零 VRAM 分配」，天生没给动态字形留位置。

> ⚠ **引用稀疏 ≠ 占用稀疏**。「本菜单只引用 22 个字模」是 tilemap 引用集合，
> 不是 VRAM 占用。v5–v8 整段「安全块 [121,322] 有 202 tile」的地基因此不成立。

### 2.2 关键时序（决定"要不要削字库"）

```
预渲染循环   日志行 698 – 4013
首个文本打印 日志行 4026
```

预渲染整个跑在打印**之前**且只跑一次 → **永远不会覆盖中文**。

### 2.3 设置菜单几何（以 `[CFF]` 行为准）

- 窗口模板 `0x081BB874`；tm=1、fontNum=3、`TILE_BASE=1`
- `win[0x1A]` = **本次会话的起始列**（不是窗口左边距）；`win[0x1B]` = 行内推进
- 标题 curY=1（curX=4）；菜单行 curY = 5,7,9,11,13,15,17（curX=4）
- 候选 curX ∈ {15,18,19,20,22,23}；**每行 2~3 个并列候选**，各是一个独立 ITP 会话

### 2.4 tile 账目（v9.2 修正后）

| 字宽 | 每趟 off 推进 | n 字占 tile | 备注 |
|---|---|---|---|
| 12px | pass1 +2 / pass2 +（sp==0?0:2） | **2n+4**（n≥2） | 相邻字**共享**一格 |
| 8px  | 只有 pass1，+2 | **2n** | 无 spill、无共享 |

4 字标签 = 12 tile；3 字候选 8px = 6 tile。
**值列必须 8px**：12px 时 16+12+8+12 = 48/行，7 行 336 tile，装不进可用区间。

### 2.5 "哪些 tile 不能盖"

原生字形落址 `tile = 1 + PCS*2`（font0/3 无重映射，PCS 即字形号）。
设置菜单实测被引用到的 tile（各占 2 格）：

```
1 33 49 111 119 | 139 | 255 | 323 325 327 329 331 333 335 337 339
345 349 369 397 409 439 447 451
```

> ⚠ 这份清单来自 v3 老日志 + v9 截图反推，**仍可能不完整**。
> 连续空档只有 `[3,33)=30 / [51,111)=60 / [141,255)=114 / [257,323)=66`，
> **单块装不下 7 行** → 必须按行给基址。

## 3. 逐条 BUG

### B1 「安全块 [121,322]」地基错误

- **误判**：以"只引用 22 字模"推出最大安全连续块 [121,322]，并据此设计了 v5–v8 全部布局。
- **真因**：字库是**写满**的（§2.1），那 202 个 tile 上压着 128 个真实字形。
- **修法**：中文区改为避开 §2.5 的引用 tile；引用集要标注来源与完整性。

### B2 日志行的 curX/curY 是上一会话残留

- `[InitTextPrinter] … curX/curY` = 打印**前**的 win 字段（上一会话结尾）
- `[CFF] … curX/curTX/curY/curTY` = 打印**时**的真值
- 之前推出的「顶窗 curY=0 / 标签 curY=1,5,7…」整体偏一位，布局跟着全错。

### B3 值槽兜底分支把 col23 并进 col15

```c
if (cx < 23u) return TM1_VAL_SLOT * 3u;
return 0u;          /* ← curX=23 落进兜底槽 0 */
```
第 5/7/13 行都是 `col15 + col23` 组合 → 两者完全同址 → 「快 快」「换换」「底底底」。
v7 是 `<17/<21/else`（col19 与 col23 一起塞 else），v8 换成 col23 落槽 0——**只是换了个撞法**，
所以用户实测「没啥变化」。

### B4 槽跨度小于单字推进量

`span = TM1_VAL_SLOT(2)`，但 12px 单字 off 推进 4。
`chs_blit` 的复位判据 `off >= start+span` 会在第 2 个字触发回卷 → 覆盖第 1 个字。
**span 必须 ≥ 该槽最大字数所需的推进量。**

### B5 tile 账目用错式子

v8 修掉 pass2 的 off bug 后，账目从 `2n+2` 变成别的值；中间还一度按 16 tile/4 字预算。
正解见 §2.4。教训：**渲染推进逻辑一改，容量预算必须重算**。

### B6 削字库：前提错误 + 反向有害

- 前提错：预渲染跑在打印之前（§2.2），根本不会被覆盖，无需腾地盘。
- 反向有害：被跳区间含 tile 139 / 255，正是菜单在用的字形 →
  按键模式行首显示「普通」、窗口行首显示「类型」、其余位置纯蓝实心方块。
- **修法**：`InitWindowTileData_Hook` 改为直通（不跳过任何字形），
  钩子与入口桩保留以便日后需要时恢复。

### B7 P24 跳板冲毁实参寄存器 ⭐ 本轮最致命

原生入口（被 P24 覆盖的是前 8B）：

```
0x08002A50 push{r4-r6,lr}   0x08002A52 sub sp,#8
0x08002A54 adds r4,r0,#0    0x08002A56 lsls r1,r1,#0x10
0x08002A58 lsrs r3,r1,#0x10
0x08002A5A lsls r2,r2,#0x18    ← r2 就是 glyph
```

r0/r1/r2 是三个实参，而：
- P24 覆盖指令 `ldr r1, =(EngineIwtdEntry|1)` → 冲掉 **startOffset**
- Origin 桩 `ldr r2, =0x08002A59` → 冲掉 **glyph**

结果 256 次预渲染画成同一个字形且落点错误 → **整本字库全空** → 值列 ＬＲ / ７ 全透明。
**副作用**：字库一直是空的，导致此前所有"字库侧改动"的观测都失去意义（表现为"改了没变化"）。

**修**：暂存一律用 **r3**（caller-saved，且 0x08002A58 第一句就重写它）。
二进制校验：`4B00 4718` = `ldr r3,[pc,#0]; bx r3`（错误的旧值是 `4900 4708`）。

> 纪律：写 ROM 入口跳板前，把**被覆盖点之后前 8 条**用到的寄存器列出来；
> `ldr rX, =addr` 的 rX 只能取这之外的 caller-saved 寄存器。
> **caller-saved ≠ 可以随便用**（r1/r2 同样是 caller-saved，但它们是实参）。

### B8 12px 相位共享被破坏 → 透明格子

文档 `FONT_12PX_DRAW.md`：「右缘填 D，**不碰左缘**」= 相邻字共享 tile
（字 N 的右 4px 与字 N+1 的左 4px 同处一格）。

正确关系统式：

```
off ≡ sub_start + 2*(px >> 3)

pass1 off = sub + 2*(px>>3)
pass2 off = sub + 2*((px+8)>>3)  = pass1 + 2            （sp=0/4 都成立）
下一字 pass1 = sub + 2*((px+12)>>3)
   sp==0 → 相对 pass2 需 **+0** ； sp==4 → **+2**

⇒ pass2 之后：chs_off_add(win, (startPixel == 0u) ? 0u : 2u);
```

v7 为治"白条"改成恒定 `+2`（那个白条实为 v6 分区撞车所致，修错了地方）。
后果：off 比正确值大 2 并累积 → 字 N+1 的 pass1 落到一格**新** tile，
其左 4px 从未被写过（本该放上一字的右 4px）→ **背景透明格子**，且 4 字标签多耗 4 tile。

自检：修正后占用从 146 tile 降到 **120**，无重叠、不踩引用字形；
各子区 off 序列均在 span 内（标签 4 字 `[0,2,6,8]`、值 3 字 `[16,18,20]`）。

## 4. 方法论

1. **先问"这段数据什么时候写"，再问"写多少"。**
   一直在算 tile 预算却没确认预渲染时序，整条"削字库"路线建立在错误前提上。
   改 ROM 侧批量写入前，先用日志行号确认它与目标绘制的**先后顺序**。

2. **"看起来没变化"往往是新 BUG 盖住了旧 BUG。**
   改 A 无效时，先怀疑是不是 B 把 A 的效果吞了（本轮 B7 就是）。

3. **"引用集"类清单必须标注采集来源与完整性。**
   凡按"实测引用集"划安全区的，都要假设它不完整，并留出**可改的旋钮**
   （现在的旋钮是 `TM1_ROW_TAB` 基址表）。

4. **跨抽象层的"虚拟基址"改造要追到真正算 tile 的那一行。**
   只把 `chs_blit` 调对不算完 —— `chs_tile_num` 里多加了 `win[0x16]` 就全盘偏移。

5. **渲染推进逻辑一改，容量预算必须重算**（B5）。
