# 复盘：设置菜单「类型 9」渲染成「9 型 9」

> 日期：2026-08-30 ｜ 现象截图：`bug/20260830/13.PNG`、`14.PNG`
> 结论：**已修复**（用户实测通过）。16px 步进保持正常，首字不再被覆盖。
> 关键词：**混排**、**多文本块**、**`win[0x18]` 归零**、**DYN 游标**

---

## 1. 现象

设置菜单第 7 行「窗口」的候选列：

| 期望 | 实际 |
|------|------|
| `类型 9`   | `9 型 9`   |
| `类型 1`   | `1 型 1`   |
| `类型 10`  | `10 型 10` |

点阵判读：候选列**首格显示的是末字符**，中间「型」正确，末位数字正确。

关键观察：**只有首字错、其他字都对**。这一条直接排除了「字距/步进算错」——
步进错会让整行整体错位，不会精确地只错一个字。

---

## 2. 判决性证据

来源：`src/util/work/POKEMON_RUBY_AXVJ00/gdb_patcher_log.log` 第 25990–26075 行
（14:33 采集段，`curY=15` 即菜单第 7 行）。

```
块1  InitTextPrinter(cur_x=15)   ← 新文本块
     [CFF] + [Note]  类    OFF=0x0000  curTX=0
     [CFF] + [Note]  型    OFF=0x0004  curTX=3
                                        【块1 结束时 OFF = 6】

块2  InitTextPrinter(cur_x=18)   ← 又一个新文本块
     [Note]  0x03AA「9」  OFF=0x0000  curTX=0     ← ⚠ OFF 归零
     [Note]  0x0300          OFF=0x0004  curTX=1     ← 同一个字又画一遍
```

两个事实：

1. **`OFF` 从 6 掉回 0** —— 块 2 的落址起点回到了行基址，正是「类」的 tile。
2. 块 2 的字符**只有 `[Note]` 没有 `[CFF]`** —— 它没有 `0x8000` 标记，
   不是 F9 汉字。

---

## 3. 根因

### 3.1 两段的来源不同，是两个独立的打印会话

- `类型` = 翻译文本里的 F9 双汉字短语（`\CC050F类型`，见
  `work/…/translate.build.json`），带 `0x8000` 标记 → 走 PTR/DYN 落址。
- `9` / `1` / `10` = **游戏运行时动态生成的数字**（当前窗口编号），
  不在任何翻译文本里，是原生日文半角 ASCII → 走 `PcsPrint_Custom`
  → `DrawGlyphTiles`（与全角同一路径，只是没有 `0x8000` 标记）。

游戏为它们各调了一次 `InitTextPrinter`（`cur_x` 分别 15 / 18）。

### 3.2 `InitTextPrinter` 会把 `win[0x18]`（行内 tile 偏移 off）清零

DYN 区的落址公式是：

```
tile = 行基址(kOptRows[r]) + win[0x18](off) + 2*xOff + yOff
```

块 1 画完「类型」后 `off = 6`。块 2 一进来 `off` 被清零 ⇒ 「9」落到
`行基址 + 0`，**正好是「类」占用的那 4 个 tile** ⇒ 「类」被覆盖。

于是屏幕上看到的就是「9」+「型」+「9」。

### 3.3 为什么「型」没事

`off` 归零后块 2 仍然按 12px 继续推进，第二个字符（那个被画两次的
`0x0300`）落到 `off=4`——恰好也是「型」的 tile，但内容相同所以看不出来。

---

## 4. 修法：给 DYN 游标加「行键」，跨块延续而不是归零

新增 EWRAM 变量 `CHS_LAST_ROW_KEY @ 0x0203FF8C`，记当前行的三元组
`(tileBase, curY, zone_id)`，配合已有的 `CHS_LAST_OFF @ 0x0203FF82`
（上一块结束时的 `off`）：

- pitch 槽键：`tileBase ^ curY<<8 ^ curX<<4 ^ curTY ^ tpl`
  → **`tileBase ^ curY<<8 ^ zone_id<<4 ^ curTY ^ tpl`**
  （`curX` 换成 `zone_id`：同一 zone 内的多个文本块共享同一槽，
  `curX` 变化不再导致槽失效）
- 行首（`chs_px == 0`）时：
  - 行键**未变** ⇒ 说明还是同一行的后续文本块 ⇒ **不复位 off**，
    把 `win[0x18]` 恢复成 `CHS_LAST_OFF`，接着上一块继续画；
  - 行键**变了**（换行 / 换 zone）⇒ 归零重来。

这样块 2 的「9」从 `off = 6` 继续，落在「型」之后，不再覆盖「类」。

改动文件：`hook/src/text/text_render.c`（+行键逻辑）、
`hook/src/text/text_scene.c`（`ADDR_SCENE_PTR_BASE` 由 `0x0203FF8C`
下移到 `0x0203FF8E`，让位给行键）。

---

## 5. EWRAM 自定义地址分配表（`0x0203FFxx`）

⚠ **新增任何可写 static 前必须先查这张表**，`0x0203FFD2` 起为游戏数据区
（旧页表死机根因），严禁占用。

| 地址 | 用途 | 大小 |
|------|------|------|
| `0x0203FF80` | `ADDR_CHS_PITCH_CTRL`（gen 字节，LRU 驱逐） | 12 B |
| `0x0203FF82` | `CHS_LAST_OFF`（上一块结束时的 off，借用 ctrl 区 pad） | 2 B |
| `0x0203FF8C` | `CHS_LAST_ROW_KEY`（行键：tileBase^curY^zone_id） | 2 B |
| `0x0203FF8E` | `ADDR_SCENE_PTR_BASE`（PTR 固定槽基址） | 2 B |
| `0x0203FF90` | `ADDR_CHS_PITCH_SLOTS`（8 槽 × 8 B） | 64 B |
| `0x0203FFD0` | `ADDR_OPT_PALETTE_OVERRIDE` | 1 B |
| `0x0203FFD1` | `ADDR_OPT_FG_COLOR` | 1 B |
| `0x0203FFD2` | `ADDR_GLYPH_PAGE_CURTAB` ⚠ **游戏数据区，占用即死机** | — |
| `0x0203FFF8` | `ADDR_GLYPH_ALLOC_NEXT` | — |

**剩余空隙**：`0x0203FF8C`/`FF8E` 已占满 `FF80–FF8F` 区间。
后续若还要加可写状态，只能挤 `PITCH_CTRL` 的 pad，或缩减 PITCH_SLOTS 槽数。

## 6. ⚠ 教训

### 方法论

1. **「某个字被盖」优先怀疑 tile 分配踩踏，不是字距步进。**
   步进错 → 整行整体错位；踩踏 → 只错被踩的那个字。
2. **判断「是不是同一个文本块」要看 `InitTextPrinter` 的 `cur_x`，
   不是看屏幕位置。** 视觉上相邻的两段文字（译文汉字 + 游戏动态数字）
   完全可能是两个独立打印会话。
3. **用户给的假设要优先去日志里验证。** 本次用户提出
   「原字库的字 x 坐标从 0 开始并且打印了 2 次」——日志证实
   `OFF=0x0000` 且 `0x0300` 确实画了两次，方向完全正确。

### 流程

4. **删掉复位分支 ≠ 简化逻辑。** 上一轮重构把 managed 分支写成
   「只捕获 `base_tx`、从不复位 `chs_px`」⇒ `chs_px` 无界累加 ⇒
   全屏无限重复打印（`bug/20260830/15.PNG`）。
   **游标类状态，任何分支都必须保留至少一条归零路径。**
5. **改完必须走完整流水线**：`build.bat` → `meowth full` 打包 →
   `scripts/check_rom_hook.py`。
6. 打包时若旧 ROM 被模拟器占用，产物会落到 `..._translated_new.gba`；
   自检脚本需显式传路径，或直接 `mv -f` 覆盖。
