# 整体按美版重排 —— 窗口/文本引擎移植方案

> 决策日 2026-09-09。用户拍板：① 四个 BG 的 charblock 全部纳入窗口分配器；② BG↔cb 布局整体按美版重排。
> 本文是「怎么落」的施工方案。所有结论来自自己反汇编 + decomp 源码，不接受记忆漂白。

## 一、美版分配器完整契约（源码 + 反汇编，钉死）

来源：`tools/pokeruby/src/text.c` + `menu.c` + `text_window.c`。

### 1. 窗口模板 28B —— 声明「池」而非「地址」

```
struct WindowTemplate {
    u8  bgNum;            // +0  所属 BG 层
    u8  charBaseBlock;    // +1  该窗口 tile data 落在哪个 charblock
    u8  screenBaseBlock;  // +2  该 BG 层 tilemap 落在哪个 screenblock
    u8  priority;         // +3
    u8  paletteNum;       // +4
    u8  foregroundColor;  // +5
    u8  backgroundColor;  // +6
    u8  shadowColor;      // +7
    u8  fontNum;          // +8
    u8  textMode;         // +9
    u8  spacing;          // +10
    u8  tilemapLeft;      // +11
    u8  tilemapTop;       // +12
    u8  width;            // +13  ← 画布宽（tile 数，行距）
    u8  height;           // +14  ← 画布高（tile 数）
    void *tileData;       // +15  ← BG_CHAR_ADDR(charBaseBlock) 硬编码指针
    void *tilemap;        // +19  ← BG_SCREEN_ADDR(screenBaseBlock) 硬编码指针
};
```

58 个美版模板实测分布：BG0 的 charBaseBlock 跨 `{0,1,2,3}`、BG1 跨 `{0,1}`、BG2 跨 `{0,1,2}`、BG3 跨 `{0,2,3}`。
**证明：同一 BG 层在不同场景/窗口下会切换 charblock，charblock 不是 BG 层的固定属性，而是窗口模板声明的分配池。**

### 2. UpdateBGRegs —— 「BG 层读哪个 cb」是窗口驱动的

`text.c:1735`：
```c
static void UpdateBGRegs(const struct WindowTemplate *t) {
    u8 bg = t->bgNum;
    *gBGHOffsetRegs[bg] = 0;
    *gBGVOffsetRegs[bg] = 0;
    *gBGControlRegs[bg] = t->priority | (t->screenBaseBlock << 8) | (t->charBaseBlock << 2);
}
```
**开窗时把模板的 charBaseBlock/screenBaseBlock 写进 BGxCNT。** 这是与日版「main 里静态设死 BGxCNT」的本质区别。

### 3. InitWindowTileData —— 链式游标（返回值 = 下一段起点）

`text.c:1763`：按 textMode 分发。
- `UNKNOWN2` → `InitVariableWidthFontTileData`：写 blank×2，**返回 `startOffset + 2 + width*height`**。
- `MONOSPACE` → `LoadFixedWidthFont`：载 256 字形，返回 256（font 0/3 乘 2 → 512）。

### 4. 开窗链（menu.c `InitMenuWindowInternal`）

```
tileOffset = 1
  → InitWindowTileData(win, 1)                = 1 + 2 + w*h   (文本画布)
  → TextWindow_SetBaseTileNum(↑)              = ↑ + 9          (标准框 9 tile)
  → TextWindow_LoadStdFrameGraphics(win)                        (装框)
  → TextWindow_SetDlgFrameBaseTileNum(↑)      = ↑ + 14         (对话框框 14 tile)
```

单调递增，**从不问「哪里空」**。开窗复位游标、关窗整段作废复用。

### 5. tileData 指针 = 固定公式

`tileData = BG_CHAR_ADDR(charBaseBlock) = 0x06000000 + cb*0x4000`，模板里硬编码。分配 = 在该 cb 内从 startOffset 起单调递增。

## 二、日版 AXVJ 现状（已确证，非美版分配器）

1. **符号表有同名函数，但逻辑已被改写**（反汇编铁证）：
   - `InitVariableWidthFontTileData @0x08002DF0`：不再是「返 start+2+w*h」，改为写 `win[0x1B]/win[0x1D]` 游标字段 + 图集寻址。
   - `InitWindowTileData @0x08002D68`：不再分发链式分配，改为按写死 tile_base 写图集 + `win[0x18]=4`。
   - ⇒ **重排 = 重新实现，不是接线。**

2. **模板 24B 缺 4 字段**：width/height/tileData*/tilemap* 缺失（tileData@0x0C 是写死绝对地址，非「池指针」）。

3. **BGxCNT 静态设死**：日版 main 一次性设置，窗口不做动态 charblock 切换。

4. **落址写死**：tm1 图集 `[1,513)`、tm3 网格 `base+0x25A`；v8 分配器 `tile_alloc.c` 是「找空闲」死路（已封禁）。

## 三、重排方案（分阶段，每阶段可独立截图验收）

### 阶段 0：模板结构对齐（24B → 28B）
- 把日版窗口模板扩到 28B，补 width/height，tileData/tilemap 指针按美版公式填 `BG_CHAR_ADDR(cb)`/`BG_SCREEN_ADDR(sb)`。
- **截图预期**：无视觉变化（纯数据结构对齐，未改渲染路径）。

### 阶段 1：分配器重新实现（链式游标）
- 新写 `InitVariableWidthFontTileData`（返 `start+2+w*h`）+ `InitWindowTileData` 分发，替换日版改写版。
- 挂到日版 `InitMenuWindowInternal` 对应物，恢复 `1→+9→+14` 链。
- **截图预期**：菜单窗/对话窗正常渲染，字形来自字体 ROM 重合成（非图集）。

### 阶段 2：BG 动态重排（UpdateBGRegs）
- 日版开窗时按模板 charBaseBlock/screenBaseBlock 写 BGxCNT，取代 main 静态设死。
- **截图预期**：大地图→菜单→战斗→对话，BG 层 charblock 正确切换，无花屏/串层。

### 阶段 3：UI 全面接管 + 退役旧方案
- 队伍/背包/图鉴/战斗UI/地图名/血条等全部走窗口分配器。
- 退役 v8 `tile_alloc.c` 与 tm1 图集、tm3 写死网格。
- **截图预期**：全 UI 文本窗由分配器统一管理，复杂场景（领航员）不再溢出。

## 四、下一步建议（请确认切入点）

阶段 0（模板 28B 对齐）是其余阶段的共同地基，且风险最低（不动渲染）。建议从它切第一刀。
但阶段 0 会牵动所有读模板的代码（InitTextPrinter 序言只拷 `[4..9]`、tm 落址读 `[0x0C]` 等），需要先枚举日版所有模板消费者。
