## 0. 为什么要 v10 —— 五代分配器的演进史

> 这张表是本方案存在的理由。每一代都解决了上一代的问题，却又在**同一个地方**摔倒：
> **「官方的 tile 和我们写的字，住在同一块没有所有权的 VRAM 里」。**

| 阶段 | 主要内容 | 缺陷 | 为什么最终是死路 |
|---|---|---|---|
| **v6** | 屏蔽文字打印，用 `gdb_patcher` 采集**静态避让带** | 难以应对动态类 UI（商店买卖窗口等），漏采集了就撞 UI | 避让带是**离线快照**，UI 是**运行时生成**的 ⇒ 快照永远落后于现实 |
| **v7** | 预打印并在 `UpdateTilemap` 阶段**重组 cb** | **无法分辨 UI 与文字瓦片**；自动重绘界面严重互撞 | 重组的前提是「能认出哪些 tile 是文字」——而在没有归属信息的 cb 里**根本认不出** ⇒ 完全没法用 |
| **v8** | **高水位 + 非空检测**（顺序分配器） | 空间不够 | 在官方 cb0 里「往上找 32 B 全空的位置」；官方占 97% ⇒ 找不到竖直对 |
| **v9** | v8 算法原样 + **队列记账层**：(win, 模板) 双键，切换即游标置首；v9.1 把 ours 换成 96 B 持久位图 + 场景签名清空；v9.2 签名剔除 DISPCNT | 记账仍是**启发式猜归属**（场景签名 / 活引用 / 非空）；官方图形与我方旧字在 cb0 内**物理混居** ⇒「非空」不含归属信息；v9.1 的签名还**咬了自己**（DISPCNT 一变即误清 `ours`，186→10） | 实测 cb0 非空 **509/512**、cb1 **490/512**；arena 768 里真空闲只有 **72**、死数据 **590** ⇒ 池子见底后无解 |
| **v10（本方案）** | **「号」由我们发放**：① **号发放器**（唯一游标，**不建账、不登记、不扫 VRAM**）② 开窗按模板`bgNum`写 `BGxCNT`（＝**复刻**美版 `UpdateBGRegs`）③ 文本与 UI（框）走**同一条发号路径**（官方本来就是这样）④ 窗口重建时**整段还号** | — | **号一旦由我们发，"这块 tile 是谁的"这个问题就不成立** ⇒ 不需要登记、不需要猜归属。容量是**发出来的**，不是**找出来的** |
| **v9′（曾拟，已废）** | v10 初稿：「归属表 —— **只由我们登记**」 | **与 v9 同一个错误**：出发点仍是「我管不了号的发放，只好自己记账再猜哪些是我占的」 | 只要出发点不变，就必然长出 **避让带 → 池子公式 → 记账猜归属** 这三样（v6/v8/v9 各自的名字）。**2026-09-11 用户指正后整章废弃** |

**一句话**：`v6~v9` 都在回答「怎么在官方的地盘上**找缝**」——避让带、划池子、记账猜归属，是**同一个错误的三件外衣**；
v10 把问题换成「**让号由我们发**」。

**判死依据（v92 实测 `[JUNK-HEX]`）**：tile `563 / 647 / 724` 是 **32/32 全满字节**的官方图形，
而 `256 / 329 / 407` 是我们稀疏的 8 px 汉字——**两者物理混居在同一区间**。
所以任何「看内容猜归属」的方案都只能**逐场景调参**。这就是「采集三轮以上仍拿不出通用方案」的根本原因：
**不是算法不够聪明，是判据本身不携带归属信息。**

## 1. 正面回答：现在这条路为什么不可持续

先认账：`v8 → v9 → v9.1 → v9.2` 四轮全都在**同一个错误地基**上打补丁——在官方 cb0 里找缝，
再用一个启发式（场景签名 / 活引用 / 非空）去**猜**哪块 tile 是官方的、哪块是我们的。

v92 日志把「猜」这条路判死了：

| 证据 | 数值 | 含义 |
|---|---|---|
| arena `[256,1024)` = cb0+cb1 的 768 tile | 真·空闲 **72** / 活引用 106 / **★死数据 590** | 官方占 97%，缝是动态的 |
| `[JUNK-HEX]` 抽样 tile 563 / 647 / 724 | 非零字节 **32/32**、高半字节非零 32/32 | **密实官方图形**（不是我们的 8px 字） |
| 同批抽样 tile 256 / 329 / 407 | 非零 13~18/32、高半字节 10~11/32 | 我们的稀疏汉字 |
| ⇒ 结论 | 「非空」这一位**根本区分不了**归属 | 官方图形与我们旧字**物理混居**在同一区间 |

**这就是「三轮以上仍无通用方案」的原因**：不是算法不够聪明，是判据本身不携带归属信息。
只要文字层和官方图形共用同一个区段，任何方案都只能**逐场景调参**。

**唯一的出路：不是"圈一块地"，而是把「号」的发放权拿回来。**
号由我们发 ⇒ 官方与我们共用同一段地址空间也没关系（顺序本来就是我们的）；
反过来说，只要号不归我们发，**再多的账本也只是事后追认一个既成事实**。

## 2. 已确认事实（v92 实测 + 静态反汇编）

### 2.1 领航员场景的四层 BG

| 层 | priority | charBase | screenBase | tilemap 地址 | 引用 tile 数 | 该层引用的 tile 是谁的 |
|---|---|---|---|---|---|---|
| BG0 | 1 | **cb0** | sb31 | `0x0600F800`（= 模板 `B7B4`） | 60 | **60/60 全部是我们写的字** |
| BG1 | 0 | cb3 | sb27 | — | 75 | 官方地图/底图 |
| BG2 | 2 | cb2 | sb29 | — | 12 | 官方图形 |
| BG3 | 3 | **cb0** | sb30 | `0x0600F000`（= 模板 `B7E4`） | 138 | **136/138 是我们写的字** |

DISPCNT = `0x3F40`（4 层全开）。

### 2.2 两条关键推论

1. **领航员的 BG0 与 BG3 就是「纯文字层」**——它们引用的 tile 几乎全部是我们自己写进去的汉字
   （`⊕ BG0 ∩ BG3 = 60`，且 BG0 的 60 个是 ours 的子集）。
   ⇒ **把这两层的 charBase 换到别的 cb，不需要搬迁任何官方图形。**
2. **两层文字层共用同一个 charblock（cb0），必然互相踩**——
   26 条标签抢同一段 tile，后画的覆盖先画的。这就是「容纳变少」的物理根源。

### 2.3 模板结构携带「该用哪个 cb」（静态确认）

- 日版模板 24 B：`charBase@1`、`screenBase@2`、`fontNum@8`、`textMode@9`、`tileData@0x0C`、`tilemap@0x10`
- 实测：模板 `B7E4.tilemap = 0x0600F000` ⟷ BG3 的 `screenBase = sb30`；
  模板 `B7B4.tilemap = 0x0600F800` ⟷ BG0 的 `screenBase = sb31`
  ⇒ ~~**「模板 ↔ 哪一层 BG」由模板的 `screenBase` 决定**~~ ⇒ 🔴 **2026-09-11 修正：直接由模板第 0 字节 `bgNum` 决定**
  （美版 `UpdateBGRegs` 原文：`u8 bgNum = winTemplate->bgNum;`）。`screenBase` 只是**层被选中后的副产品**
  （层选中后它的 sb 自然等于模板 sb），**不是定位依据** —— 详见 §3 层 2。
  🔴 **2026-09-11 第二条独立证据（13 个模板全覆盖）**：模板还自带 `tilemap@0x10`，

  互相印证。⚠ **但它们只能证明「模板的 sb 与层的 sb 一致」，不能证明「sb 是定位依据」**——

### 2.4 GBA 硬件机制：tile 号跨 charblock（**决定一切的一条**）

```
物理地址 = charBase × 0x4000 + tileNum × 0x20     （tileNum = tilemap 里的 10 bit 字段）
⇒ tileNum ∈ [0,1023]，但 charBase 只有 4 档 ⇒ tileNum ≥ 512 会「溢出」到下一个 charblock
```

| 层 | `BGxCNT` | charBase | 可寻址绝对范围 | **实测引用的 tile** |
|---|---|---|---|---|
| BG0（文字·训练家名） | `0x1F01` | **cb0** | `[0, 1024)` = cb0+cb1 | tileNum `360..849` ⇒ **物理落在 cb1** |
| BG1（背景/地图） | `0x1B0C` | **cb3** | `[1536, 2560)` | tileNum `1..124` ⇒ 只占 cb3 低位 **124 个** |
| BG2（官方图形） | `0x1D0A` | **cb2** | `[1024, 2048)` | tileNum `1..16` ⇒ 只占 cb2 低位 **16 个** |
| BG3（文字·路线名） | `0x1E03` | **cb0** | `[0, 1024)` = cb0+cb1 | tileNum `360..1022` ⇒ **物理落在 cb1** |

**三条决定性事实**：

1. **两个文字层（BG0 / BG3）`charBase` 都是 cb0，且 tileNum 都在 360~1022**
   ⇒ 它们的字**物理上落在同一个区间** `cb0[360,512) + cb1[0,511)`，**必然互相覆盖**。
   这就是「容纳变少」的物理根源——**与场景无关、与字号无关、与分配算法无关**。
2. **BG1 只用 cb3 的 `[1,124]`、BG2 只用 cb2 的 `[1,16]`**
   ⇒ **cb2 / cb3 的绝大部分在领航员场景下是空的**（实测 cb2 空 398、cb3 空 151）。
3. `cb0`/`cb1` 实测非空 999/1024，但**当前 4 层 BG 只引用了 225 个**
   ⇒ 约 **774 个非空 tile 无人引用**（官方为其他场景/图层预载，或陈旧残留）——这一块的性质由 **S1 ②** 判定。

### 2.5 各 charblock 的实测占用（v92 日志 `[VRAM cbN]`，绝对 tile 号）

| cb | 绝对区间 | 非空 | 空闲 | 空闲率 | 谁在用 |
|---|---|---|---|---|---|
| **cb0** | `[0, 512)` | **509** | **3** | 0.6% | 官方 + 我们的字（**混居**） |
| **cb1** | `[512, 1024)` | **490** | **22** | 4.3% | 官方 + 我们的字（**混居**） |
| **cb2** | `[1024, 1536)` | **114** | **398** | 78% | BG2 占 `[1,16]`；其余 ≈ 官方残留 |
| **cb3** | `[1536, 2048)` | **361** | **151** | 29% | BG1 占 `[1,124]`；其余 ≈ 官方残留 |

**结论**：v6~v9 用的 `[256, 1024)` 这 768 个 tile，**正是 `cb0` 高位 + `cb1` 全部**，
与官方图形**完全混居**——所以「调区间」的正确做法不是把 `lo` 往下挪，而是**换到 cb2/cb3**。

文字层的 tileNum **由我们自己写**，所以可以把两个文字层分别指到**官方占用最少**的两个 cb：

| 文字层 | 现状 | 目标 `charBase` | 可用 tileNum 区间 | 池大小 |
|---|---|---|---|---|
| BG0（训练家名等） | cb0 | **cb2** | **`[44, 512)`** | **468** |
| BG3（路线名等） | cb0 | **cb3** | **`[128, 256)`** | **128** |
| | | | **合计** | **≈ 596 tile**（≈ 298 个 Middle 汉字） |

- 关键前提：tileNum **限制在 `[0,512)`** ⇒ `charBase` 唯一决定物理 cb，**不再溢出串门**
- **`cb3[256,512)` 是禁地**：它是 `sb28..31` 的**屏幕映射区**（`sb30`/`sb31` = BG3/BG0 自身的 tilemap，
  首采实测又见 `sb28`/`sb29` 被整屏写入）⇒ 不能放 tile 图形
- `cb3[0,124]` 是 BG1 占的（S1.5），原样不动
- `cb0`/`cb1` 交还官方（我们的字撤出）；那 774 个「非空无引用」的性质不影响本方案
- **对比现状**：v8/v9 在 cb0/cb1 的 arena 768 里**真空闲只有 72 tile** ⇒ 596 是**8 倍以上**的改善，
  且**不与官方图形混居**（~~归属表判定~~ → **该判定已废弃**，见本节纠正）

### 3.0 接管点：日版全部分配途径 —— **这才是「接管」的实体**

> 然后进行自定义分配**；不能只改目前代码然后盲着进行分配。」
>
> **现状核对**：现有 ROM hook **只有 2 个挂载点**（`configs/.../hook/src/text/hooks_origin.s`）——
> `PrintNextChar`（中文打印层）与 `InitTextPrinter`（块边界）。下表 ①~⑨ **一个都没挂**。
> ⇒ 官方该分配还是自己分配，我们只是在它划定的地盘里"找空位"。
> **这就是避让带问题的技术根源**，也是 v10 与 v6~v9 的分界线。

**日版引擎的「分配」长什么样**（**S1.7 实机采集 + 反汇编双证，2026-09-11**）：

```
官方 TextLoadWindowTemplate @0x08002950        （①：主链，重置三个游标槽）
官方 ChsAllocTplMenu        @0x080028BC        （②：菜单孪生，不碰游标槽；两者签名同构）

  ①/② 的第一步完全一样：
     win[0x16] = tileOffset                     ← r1，**实测调用方恒传 1**
  ① 额外多三步（重置游标）：
     *0x0300032E = 0                            ← 图集游标归零
     *0x03000328 = win[0]        (= tpl 指针)
     *0x0300032C = tileOffset

  然后按 textMode / fontNum 分派，**返回值 = 「帧图形的起始 tile 号」**：
     tm3        → bl 0x08002BD0  → 写 2 个 tile，**返回 tileOffset + 602**   (literal 0x25A)
     tm1 font0,3 → bl 0x08002AF4 → 装 256 字×2 tile = 512 tile → **返回 512**
     tm1 font1,2,4,5 → bl 0x08002B2C / 0x08002B60 / 0x08002B9C（256 字×1 tile）→ **返回 256**
     tm0 / tm2  → 什么都不做 → **返回 0**

  调用方（0x0806F074 / 0x0806EFFC 两处）随后：
     *0x0202E6F0 = ①/② 的返回          ← ★中转槽
     ⑤( *0x0202E6F0 )                  → *0x03000514 = base，返回 base+9  → *0x0202E6F2
     ⑦( win )                          → dst = tpl->tileData + gFrame9Base*32
     ⑥( *0x0202E6F2 )                  → *0x03000516 = base+9，返回 base+23
     ⑧                                 → dst = tpl->tileData + gDlg14Base*32
```

**⇒ 三条硬事实（推翻原设计的两处假设）**：

1. 🔴 **官方「分配」是纯函数，没有账本**：`①/②` 只是**算出一个号**（`tileOffset+602` / 512 / 256），
   既不查谁空、也不登记。所谓「官方分配器」实为**固定公式**（0/1/2/9/14/512/602 全是常量）。
2. 🔴 **决策点只有 ① 和 ② 两处**。⑤⑥⑦⑧ **不独立决策**——它们拿的号就是从 ①/② 返回值经中转槽
   `0x0202E6F0` 传过来的。**改了 ①/② 的返回值，⑤⑥⑦⑧ 自动跟随。**
   （实测：⑤ base ∈ {512, 603}，⑥ = ⑤+9 ∈ {521, 612}，两组都成立。）
3. 🔴 **一切物理目的地 = `模板tileData + 号*32`**（图集、tm3 图形、⑦⑧ 框全都如此；
   ⑦ 内部 `bl 0x08004254(win)` 就是 `win[0]->tpl->tileData`）。`tileData` 是**模板 @0xC 的绝对 VRAM 指针**。

**⇒ v10 要改的只有两件事**：
**(a)** 把 `①/②` 的**入参 `tileOffset`**（装载起点，官方恒 1）换成分配器给的号；
**(b)** 把 `①/②` 的**返回值**（帧基址）换成分配器给的 `号 + 用量`。
**⑤⑥⑦⑧ 一行都不用改**；⑨ 已判死；⑩ 是 LZ77 蹦床（被人调），不是分配点。

|---|---|---|---|

| 场景 | 官方**声明**（返回号推走多少） | 官方**实际写** | 落点 |
|---|---|---|---|

| ⑧ 对话框框 | — | **14** | `tileData + (base+9)*32` |

> （如 ⑨ 那类绘制热函数）乱改，就会让 ⑤ 拿到一个大号（如 603），把框推到 `tileData + 603*32`

static void UpdateBGRegs(const struct WindowTemplate *winTemplate)

### 层 3 — 号发放器（**替换官方固定公式**，文本 + UI 同一条路径）

**模型一句话：号的发放权归我们；顺次发，发尽了就按规则回收再发。**
（既不是高水位「只涨不落」，也不是「找不到就 return 0 放弃」，更**不是**「在官方缝隙里找空位」。）

- **管辖范围 = 全部 4 个 charblock**（cb0..cb3，2048 tile）。**不预先划「我方区间」**——
  §3.0 之后官方与我们的号走同一条路径，不存在需要划定的边界
  （§2.6 的 `[44,512)` / `[128,256)` 及 596 总数**不作为输入**，见该节方法论纠正）
- **接管方式 = 替换官方的固定公式**（§3.0 决策点 ①/②）：

  | 官方原逻辑（固定常量） | v10 |
  |---|---|
  | `tileOffset` 恒传 1、返回按 fontNum 恒 512/256 | `offset = vram_alloc(用量)` |
  | 框基址 = 上游返回值（`+9` / `+14`，由 ⑤⑥ 自动跟随） | 无需额外挂钩子 —— 号本来就是我们的 |
  | 装载目的地 = `tileData + 32*号` | = 发号器给出的号（`tileData` **不动**） |

- **唯一静态保留区 = 屏幕映射区**：`tilemap` 数据本体（`B7E4.tilemap=0x0600F000`=sb30、
  `B7B4.tilemap=0x0600F800`=sb31，以及 S1.6 实测被整屏写入的 sb28/29）——
  这是**硬件结构**（屏上格子的表项），不是「官方占的地盘」，与官方行为无关，
  必须**静态**排除，永不作 glyph/图形目标
- ⚠ **不做「跨 cb 借」**：`tileNum` 是 10 bit 无符号，只能往高地址溢出、不能往低回溯 ⇒
  两个 cb 之间的空闲**不能直接互借**（用哪一层由模板 `bgNum` 决定，见层 2）
- **可用性 = 游标说了算**（层 1 的唯一状态）：游标没走过的号就是可用的，**不需要查任何表**；
  号全是我们发的 ⇒ 不存在「官方占的号」这个类别（§3.0：官方与我们要走同一条路径）
- 接口：
  - `vram_alloc(n_tiles) -> tile_abs` + `vram_free(handle)`
  - **文本的 `print_glyph_px` 与 `①/②` 的发放点都调它**（⑤⑥⑦⑧ 自动跟随，不必单独挂）

#### 3.1 发尽 ⇒ 自动回收 ⇒ 重发（**这是与 v8/v9 的分水岭**）

```
vram_alloc(n):
    if 游标 + n ≤ 上界 : return (游标, 游标 += n)      # 主路径：顺序发号，零查询
    if !reclaim_one_pass() : return 0                  # 游标到底 ⇒ 先回收，还不行才放弃
    return vram_alloc(n)                               # 回收后有空间 ⇒ 重发（限次，避免活锁）
```

`reclaim_one_pass()` —— **回收规则（按优先级，从安全到激进）**：

| 优先级 | 对象 | 依据（**读官方自己的字段**） | 说明 |
|---|---|---|---|
| 1 | **当前窗口自己上次占的那一段** | `win->tileDataStartOffset` / `sTextWindowBaseTileNum` / `sDialogueFrameBaseTileNum` | 窗口重建时官方**会再调那两个号函数** ⇒ 天然回收点。**这是主力** |
| 2 | 已关窗、但仍挂在官方字段上的旧段 | 官方字段 × 当前窗对比 | 谨慎回收，**默认关闭**，S6 视情况开 |
| 3 | — | — | **绝不回收**：当前窗口正在用的段 |

> 🔴 **关键：回收依据是「官方字段」，不是「我们的账本」** ——
> `win->tileDataStartOffset`（`Window` 结构体字段）、`sTextWindowBaseTileNum`(`0x03000514`)、
> `sDialogueFrameBaseTileNum`(`0x03000516`) **都是官方自己维护的字段**，每次重建窗口官方都会重写它们。
> ⇒ 我们只是**把它们读回来**，**不需要另建一套账**。

- 回收粒度两档：**整段**（cb / 区间）与**单 tile**（碎片整理，把死块凑成连续 n 个）
- **回收只动「我们上次发出去的那一段」** ⇒ 官方图形永远不在候选集内 ⇒ 不会砸官方画面
- 判据是**官方字段 + 我们自己的游标**，**不猜、不需要采集** —— 这正是 v8/v9 做不到的那一步：
  它们面对象「非空但无引用」的 590 个死 tile 时，因为不知道归属而不敢动手

### 层 4 — 按条件回收（= 层 3 内建回收器的显式出口）

`vram_release_cb(cb, mode)` 把层 3 的 `reclaim_one_pass()` **对外暴露**，供场景切换/卸载时主动腾地：

```
vram_release_cb(cb, mode)
  mode = NONE_ALIVE     该 cb 上的号已全部不被任何窗持有 ⇒ 整段释放（= 优先级 1 的整体版）
  mode = RANGE(lo, hi)  释放指定号段（满足「按条件回收指定 cb 块」的字面要求）
  mode = TEARDOWN       场景卸载钩子触发（需 hook 引擎的卸载函数）
```

- 层 4 与层 3 共用同一套判据（**官方字段 + 游标**）—— **不是两套回收逻辑**
- 区别只在触发方式：层 3 是**分配失败时被动触发**，层 4 是**外部主动触发**
