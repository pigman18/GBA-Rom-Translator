## 0. 一句话结论

**不是几何问题，也不是「Middle 比 Big 省 tile」没生效——是 tile 池（arena）被打空后
分配全数失败。** 从第 13 条串起，每一次领号都返回 0，`chs_claim_tile()` → 0 ⇒
`print_glyph_px()` 直接 `return adv`（既不画字、也不写 tilemap）⇒ **整条标签静默不出现**。

池子打空的原因不是「一条串太宽」，而是 **ours 账本只有 19 段（≈152 tile）且 FIFO 淘汰：
我们自己写过、后来又被挤出账本的 tile 会被永久当成「官方数据」锁死，池子只出不进。**

## 2. 机制链条（为什么「换窄字体」救不了）

1. `v8_tile_usable()` 的判定是 **位图未标（活引用）+（VRAM 全空 ∨ 在 ours 段表内）**。
2. `v8_ours_add()` 只有 19 个槽，装满后**淘汰最旧段并整体前移** ⇒ 账本最多记住 ~152 tile。
3. 我们前几屏写过的字一旦被挤出账本，VRAM 里仍然非空 ⇒ 被判定为「官方数据」⇒
   当场**negative-cache 进位图**，本会话内再也不碰；下个会话 `begin` 重建时再被同样判死。
4. 于是 arena 单调流失：bump 指针到 1024 就再也回不去（回卷后能复用的只有账本里那 152 个，
   而那 152 个恰好都还挂在屏上 = 被活引用层再次挡住）。
5. **最终态：可用池 0。** 之后每条串的每个字都 `t0==0`。
6. 与字号无关：Big 3 tile/字、Middle 2 tile/字，只是把池子打空的速度从 N 条串变成 1.5N 条串，
   **池子一旦见底，两者都是 0**。这就是「换成 Middle 并没有容纳更多」的物理原因。

## 4. 方案（三选一，均属分配层，需用户拍板）

### 方案 A（推荐）— 记账层扩容 + 场景签名失效
- 把 `ours` 段表换成**持久位图**（EWRAM 再开 128 B，与 `0x0203FEC0` 同构），
  `v8_in_ours()` 改查位图；`v8_ours_add()` 退化为置位。
- 加**场景签名**（`DISPCNT & 0x1F00` + BG0..3CNT）在 `v8_alloc_begin` 里比对，
  签名一变即清空持久位图 —— 防「上个场景的 tile 被官方回收后再被我们误认成自己的」。
- **不改** `lo` / 活引用重建 / VRAM 非空校验 / screenblock 保留 —— 只换账本的容量与失效时机。
- 预期收益：>= 580 tile 可回收（占 arena 76%）。
- **预计实机效果**：领航员地图上**全部**路线名标签都出现且不互相覆盖（现在只有前 1~2 条能画）；
  反复进出/滚动地图不再越来越空。

**A+（可选叠加，只在本场景需要时再开）**：把 `v8_tile_usable()` 里的判定顺序改成
**「在 ours 里 ⇒ 直接可用（哪怕被活引用）」优先于活引用位图**。
理由：本场景 `活引用 ∩ 账本 = 152/152` —— 账本里的 tile 全部挂在屏上，
而这些「挂在屏上」的正是同一个窗自己上一轮画的标签，重画时覆盖自己 100% 安全。
风险：同窗多模板（B7B4/B7E4）会互相覆盖对方的标签 ⇒ 只建议在「同一模板的同一次重画」
语义下启用，或把 ours 再按 (win,模板) 分段。**默认不开。**

### 方案 B — per-window(private) arena
照美版 `InitWindowTileData` 的 `w*h+2` 逐窗预留。障碍：日版 `win[0x16]` 在本场景恒为
`0x0001`（日志 `r2.tile_base=0x0001` 每条串都一样），拿不到 per-window 基址 ⇒
必须先把「窗装载 / BG 层接管」做完（＝路线里的阶段 3）。

### 方案 C — 换 charblock
cb1 在本场景**没有任何 BG 使用**（BG0/BG3=cb0、BG2=cb2、BG1=cb3）。把中文文字挪到 cb1，
再把承载文字的 BG 的 `BGxCNT.charBase` 改成 1（＝路线里的阶段 2「接管 BGxCNT」）。
需先实测 cb1 的官方占用（本日志没扫 cb1）。

### 推荐顺序
**A → 实机截图验收 → 若收益不足再做 C。** A 是当前唯一「不动 BG 布局就能立刻回血」的方案，
且正好落在用户允许改动的「记账层」。

### 8.4 为什么 102 个「真·空闲」也救不了场

arena 里**每一对相邻的空 tile 都被 BG3 的 tilemap 引用**（上表那些空洞就是）

## 9. v10「按格子定号」（2026-09-20 实施 —— **放弃在 v8/v9 池内打补丁，改用官方模型**）

### 9.1 为什么前面 A / B / C 都治不住

前面 §4 的三条方案（A 记账层扩容 / B per-window arena / C 换 charblock）**全都默认
「池子不够」这个前提**。2026-09-20 外部查证推翻了这个前提：

> `pret/pokeemerald` wiki · *How Menus Work Part 2*：
> 「窗口会为该矩形区域**预留**所需数量的 tiles」「A window will use **width × height** many tiles」
> 「5×2 tile 的文本区 ⇒ 需要 10 个 tile」

⇒ **官方 tile 号 = 屏幕格子的函数**，与「这一格画过多少个字」无关，**同格重画零消耗**。
而我们自建的是「**按字领号**」的全局池 —— 每画一个字吃掉一个新号，翻页/重画不回收。
**这才是缺空间的根因**（§1 的「真·空闲=72 / 无引用无账本=590」正是这个模型的产物）。

🔴 推论：中文 12px 一行占的**格子列数与日文 8px 相同**（tile 按格子算，不按字算）
⇒ **中文不比日文多花一个 tile**，代价只是「一行汉字数 = 日文的 2/3」。
所以「空间不够」是我们绕开官方窗口模型造成的，**不是汉字的固有代价**。

❌ 另：「绕过 cb 区」已被硬件否死 —— 位图 Mode3/4/5 要重做整个渲染（引擎全程 Mode0/1）；
OBJ 虽独立 1024 tile 但 OAM 上限 **128 精灵/帧**、单行 ≤32 ⇒ 一屏 80~180 汉字放不下。
**GBA 的 BG 文字物理上必须走 VRAM tile。**

## 10. v10.1 —— v10.0 实机「成片重复片段」事故与修复（2026-09-20 同日）

### 10.1 现象

用户截图：领航员页面右侧面板 **8 行内容完全相同**（`示 :愛戻乐部  光 ; 短帰` 逐行重复），
左侧面板出现同一串片段 ⇒ 典型「**多个格子引用同一个 tile**」。

### 10.2 根因：v10.0 两条改动叠加，把面板底纹 tile 变成了字形槽

1. `v8_tile_usable` 第 ④ 条「非空 + 无活引用 + 不在账本 ⇒ **认领为 ours**」。
   面板底纹 tile（整块面板**同号平铺**、实心非空）在场景切换那一帧**暂时无引用** ⇒ 被认领。
2. v10 同时把 `ours` 改为**持久不清** ⇒ 该底纹号**永久**留账。
3. 标签窗口的格子里装的正是这个底纹号。§1 证据 #11/#12 已证：两个窗口的 tilemap 就是
   **BG0/BG3 的 screenblock，且两层 charBase 都是 cb0**（读同一批物理 tile）。
4. ⇒ `chs_claim_tile` 读回底纹号 → 命中 `v8_ours_has` → **每一格都返回同一个号**
   ⇒ 所有汉字叠进同一个 tile ⇒ 整块面板显示累积字形条带（水平周期 = 底纹重复周期，
   垂直每行相同 = 每行格子指向同一批号）。

### 10.3 修法（v10.1，改 3 文件 + 2 处注释）

| 文件 | 改动 |
|---|---|
| `tile_alloc.c::v8_tile_usable` | 删 ①「ours ⇒ 无条件可用」与 ④ 里的 `v8_ours_add`（**投毒入口**）；④ 仍返回可用 ⇒ 容量不变。账本只由 `v8_alloc_n` 真实领号写入 |
| `PrintNextChar_hook.c` | 新增 `chs_cell_slot`：**竖直对自洽**闸门（下方一格表项 == 本格号 + dlow）；删掉已无用的 `chs_cell_tile`；加「左右半格不得撞车」保护 |
| `game.h` / `tile_alloc.c` | 注释记录 v10.1 与投毒机理，防复活 |

🔴 **闸门是结构性判据**（不依赖账本是否干净）：`UpdateTilemap` 对真正的字形槽写
「本格 t + 下一行格 t+dlow」；底纹是 `(P, P)` **同号平铺**，**结构上不可能**满足「下方格 == P+1」。
⇒ 即使 `ours` 已被污染，也不会复用它。
