# 引擎移植方案（2026-09-08）

> 用户拍板：走引擎移植。目前最薄补丁还是出现各种问题（撞 tile、打印残留、逐场景追补丁）。
> 本文回答三件事：① 现状补丁的问题根源 ② 美版源码与美版汉化先例的引擎机制研究结论 ③ 移植路线与工作项。

## 0. 一句话结论

**「引擎移植」的本质不是搬更多代码，而是换渲染模型：从「每字领号 + blend 写像素」换成
「窗口私有网格 + 像素游标 + mask 拆列合并」。** 这正是美版引擎的模型，也是全部美版汉化
先例（pokeE / pokeFRLG / pokeRS / CHPLUS）能「只 hook 三五个点就干净渲染中文」的原因——
它们站在引擎的宽度间接层和窗口私有区上。日版引擎被编译期裁掉了这两样，我们过去一年
的 v8/相位/避让全部是给等宽引擎代偿 VWF 语义的补丁层。移植方案 = 把这层代偿换成正装。

## 1. 现状问题清单与根源（最薄补丁为什么一直出事）

| # | 现象 | 机制根源 |
|---|---|---|
| 1 | 打印残留（新文本比旧短，旧字迹留在屏上） | blend 只写新字形格，不清旧格；tilemap 旧引用未解除 |
| 2 | tm1 菜单撞 UI | tm1 = 全局共享图集（cb0/cb1 字库区），窗口无私有区 → 每字动态领号 → 与图集常驻字形/其他窗口竞争 |
| 3 | v8 分配器复杂度（三层探测+负缓存+ours 段表+begin 重建） | 共享图集上模拟「窗口私有区」的代偿，状态全落 EWRAM 自管理 |
| 4 | 相位/换行/游标散落（v8_phase_*、FE 拦截） | 日版游标是 tile 级（cursorTileX），像素游标（cursorX）只能自建 |
| 5 | 逐场景追补丁（4 个模块 hook + 场景 gate） | 没有「统一绘制入口」，每个非标准路径都要单独接管 |
| 6 | 12px 中文每字占 2~3 tile，密度高 | 每字独立 tile 对模型，行 tile 消耗 ∝ 字数；美版模型下行消耗 ∝ 行像素÷8，与字数无关 |

根源一句话：**日版引擎是美版引擎的等宽裁剪版**（宽度表、像素游标、mask 拆列在编译期
全部裁掉，见 §2.1），我们在它上面模拟 VWF 语义，代偿层越积越多。

## 2. 引擎机制研究结论

### 2.1 美版引擎全貌（pret pokeruby src/text.c 一手判读，2026-09-08）

美版引擎是一个**自包含、自驱动的文本操作系统**，日版引擎只是它的等宽简化前身。
按源码顺序钉死其结构与机制：

**① 数据结构（text.c L41~70, text.h L6~59）**
```c
struct Font   { u32 type; u8 *glyphs; u16 glyphSize; u16 lowerTileOffset; };   // 字库描述
struct GlyphBuffer { u32 pixelRows[16]; u32 background; u32 colors[16]; };     // 128B IWRAM 工作区
struct GlyphTileInfo { u8 textMode, startPixel, width; u8 *src; u32 *dest; u32 *colors; };
struct Window { textMode/fontNum/language/colors/.../cursorX(u8 像素!)/cursorY/left/top/state/tileDataStartOffset/tileDataOffset/textIndex/text/tileData/tilemap/template };  // 0x2C
```

**② 字库体系（L417~435）**：`sFonts[14]`（7 日文 + 7 拉丁，按 `language` 索引），
5 种寻址 type（`GetGlyphTilePointers` L2676~2715：0=线性、1=sFontType1Map 间接、
2=公共上半+线性下半、3=Type3Map、4=16 合字形）。宽度和字形都挂在这个表上，
**换字库=改表，不动引擎**——这就是美版汉化只需改数据的结构原因。

**③ 窗口初始化（InitWindowTileData L1763~1858）**
- VWF（TEXT_MODE_UNKNOWN2）：只写 2 个 blank tile + 预留 `width×height` tile 网格
  （返回 startOffset+2+width*height = 下一窗起点）——**窗口自留网格的出处**；
- MONOSPACE（tm1 等价物）：`LoadFixedWidthFont` 把 **256 个字形逐个解压着色写入
  窗口私有 tile 区（64B/字 = 16KB VRAM/窗）**，成本高到需要 `MultistepLoadFont`
  分帧（每帧 16 字，L1885~1903）。
  → 日版 AXVJ 没有这一步，改成 ROM 常驻共享图集——这就是日版 tm1 撞 UI 的结构性根源。

**④ 每帧驱动**：游戏主循环调 `Text_UpdateWindow*` → `UpdateWindowText` 状态机
（11 态：BEGIN/NORMAL/PAUSE/CHAR_DELAY/WAIT_BUTTON/WAIT_CLEAR/WAIT_SCROLL/NEWLINE/
PLACEHOLDER/WAIT_SOUND/END，L2405~2518）→ `PrintNextChar`（L2080）→
`sPrintGlyphFuncs[textMode]`。**状态机与日版 0x080032F8 完全同构**（state 编号、
FA..FF 语义一一对应），日版是它的裁剪版。

**⑤ VWF 绘制链（tm0/tm2 路径，L2571~2638）**
```
PrintGlyph_TextMode0 → DrawGlyph_TextMode0:
    width = GetGlyphWidth(win, glyph)          // 宽度间接层（L3410：spacing 覆盖 > sFontXWidths 逐字符表）
    tilesWidth = DrawGlyphTiles(win, glyph, width)   // L4321：写像素
    UpdateTilemap(win, tilesWidth)             // L4360：写 1~2 列 tilemap 条目
    return width → AddToCursorX(win, width)    // L2804：cursorX+=width；跨列才 tileDataOffset+=2
```

**⑥ mask 拆列核心（L4090~4260+）**——「相邻字共享列」的物理实现：
- `DrawGlyphTile_ShadowedFont`：**先读后写**——用 `sGlyphMasks[width][startPixel][3]`
  把目标 tile 现有像素保留进 pixelRows（`buffer[i] & (masks[0]|masks[2])`），
  跨列时把右列 buffer[16..23] 同样保留；
- `sShiftGlyphTileShadowedFuncs[width]`（Width0~8 九档）：按
  `sGlyphShiftAmounts[startPixel].left/right` 双向位移，把字形 nibble 经 colors[] 着色
  后 **OR 进 pixelRows[0..7]（左列）与 [8..15]（右列）**；
- 写回 VRAM；返回 `(startPixel+width)/8` = 本字消耗的列数（供 UpdateTilemap）。
  startPixel=`(win->left+win->cursorX)&7`——**半列相位不是状态，是纯函数**。
  对比：我们的 print_glyph_px 相位两段式 + v8 每字领独立 tile 对，就是这一段的
  低配手写版，且因为先领号后写、无「先读后写」，才需要整套相位/避让状态。

**⑦ 清窗/滚动/擦箭头（L2996~3260）**：`Text_ClearWindow` = tilemap 整片填
`GetBlankTileNum|palette` + 游标归零 + `tileDataOffset=2`——**官方清窗清的是
tilemap 引用不是 tile 数据**。打印残留 BUG 的机制性答案：我们没接管清窗/重绘入口，
旧 tilemap 引用没人清。

**⑧ 测量层（GetStringWidth L3609~3674）**：解析占位符/FC 控制码（含字体切换码 6/7、
spacing 码 0x14、语言码 0x15/0x16）+ 逐字 GetGlyphWidth 累加；`Text_InitWindow_Centered/
RightAligned`（L3676~3699）用它做居中/右对齐——测量与绘制正交但同一宽度来源。

**⑨ 外部依赖（移植的真实工作量所在）**：状态机访问 `gMain`（JOY_NEW/JOY_HELD 按键）、
`PlaySE/IsSEPlaying`（等待音效）、CpuFastFill——AXVJ 侧需要标定 gMain/按键掩码/音效
函数地址（一次性，量小）。

**ABI 对照沿用 2026-08-28 定论**：美版 text.c 4393 行不可原样编译接入
（struct Window 字段全错位），但引擎是**自包含模块**——正确移植形态不是「在日版
Window 上调美版函数」，而是**让美版引擎连自己的 struct Window 一起整体进来**，
日版侧只留薄适配层（见 §3.1）。

### 2.2 美版汉化先例（四工程调研定论）

| 工程 | 底版 | 形态 | 中文接管点 | 宽度 | tile/窗口处理 |
|---|---|---|---|---|---|
| pokeE | 美版 E rev1.0 | armips 补丁 | `RenderText+0xC4` hook → ChineseCodeCheck 双字节判定 → DecompressGlyph_Chinese → Convert1bppTo2bpp → ×4 DecompressGlyphTile → 跳回 CopyGlyphToWindow | 硬编码大 12/小 10（GetChineseFontWidthFunc） | 复用原引擎窗口私有区管理，**零自建分配器** |
| pokeFRLG | 美版 FR rev1.0 | armips 补丁 | `RenderText+0xB2` 同上 | GetStringWidth hook | 同上 |
| pokeRS | 美版 Ruby | armips 补丁 | `DrawGlyphTiles+2` / `GetGlyphWidth+2` / `GetStringWidth` 三点 | GetGlyphWidth 返回值改 12/10 | GetCursorTileNum→DrawGlyphTile_ShadowedFont→UpdateTilemap 原链 |
| CHPLUS(旧) | 美 R/G/FR | 初代发布 | 同源前身 | — | — |

四个先例**没有一家写了 tile 分配器**——因为美版底版上：
① tm0/tm2 文字落在窗口私有区，物理撞不了别人；
② tm1 等宽路径的中文以「窗口私有预渲染字库副本」或「8px 等宽单列」形态进入；
③ 宽度间接层让 advance 语义自洽。

共同技术资产（与我们现状同构度极高）：
- **字库格式就是我们在用的 pokeE 1bpp 位流**（大 11×11=16B/字、小 9×9=11B/字）；
- glyphId 公式 = (hi 调整)×0xF7 + lo（hi 0x01~0x1E 排除 06/1B）——我们 charmap 已同构；
- 中文标点 0x36~0x3E 单字节独立符号库——已同构。

**结论：先例证明了「窗口私有网格 + 固定 advance 双档」这条路的终态；我们要补的不是
字库/编码/绘制原语（全有了），而是把渲染落位模型换成窗口网格 + 像素游标。**

### 2.3 FRLG 二代引擎（远期蓝本）

`FontInfo{fontFunction, maxLetterWidth, maxLetterHeight, letterSpacing, lineSpacing}` +
`gFonts` 指针池 + `CopyGlyphToWindow`（四象限任意 w≤16/h≤16 切 tile）+ GlyphWidthFunc 表。
单一绘制路径、全窗口私有网格、无四套 writer、无共享图集。这是「完整引擎移植」的理想
形态，但整体替换 = 重建 AXVJ 全部窗口创建/模板代码，工作量一个大版本，只作为 P2 落地
后的远期演进方向。

### 3.1 P2 目标架构：美版引擎模块整体移植 + 日版薄适配层

核心设计：**不再「在日版 Window 上调自家散装函数」，而是把美版引擎连它的
struct Window 一起整体搬进来**——引擎内部全部用美版 ABI 自治运转（像素游标、
宽度层、状态机、清窗全是美版原生），日版侧只做两件事：①入口参数翻译
（日版 printer/模板 → 美版 Window 构造）②VRAM/输入/音效等外部依赖桥接。

```
日版 ROM 侧（保留，薄适配层 ~150 行）
  ├─ InitTextPrinter_hook：日版 printer 字段（0x0A/0x0B/0x0C..0x10/0x14/0x16..）
  │    → 翻译构造美版 struct Window（template 翻译含 left/top/width/height/tilemap）
  ├─ 每帧驱动 hook：原 PrintNextChar 调用点 → 改调美版 UpdateWindowText(美版win)
  └─ 外部依赖桥：gMain 按键位、PlaySE/IsSEPlaying、CpuFastFill → AXVJ 地址

美版引擎模块（game.bin 内，C 源级移植，按移植形态分四类）
  ├─【原样搬运】sGlyphMasks[9][8][3]、ShiftGlyphTile_* 全家 18 函数、
  │    sGlyphShiftAmounts、DrawGlyphTile_{Un,}ShadowedFont、ApplyColors_*、
  │    GetCursorTileNum、GetCursorTilemapPointer、UpdateTilemap(win,tilesWidth)、
  │    AddToCursorX/SetCursorX/AddToCursorY、GetGlyphTilePointers 骨架、
  │    Text_ClearWindow/ClearWindowTextLines/ScrollWindowTextLines 家族、
  │    TryEraseDownArrow、UpdateWindowText 状态机、PrintNextChar、
  │    HandleExtCtrlCode+sExtCtrlCodeFuncs、GetStringWidth、
  │    Text_InitWindow_Centered/RightAligned
  ├─【改数据不动码】sFonts[] → 换成中文字库表：
  │    中文双字节 → 1bpp 位流大库(11×11)/小库(9×9)（现用 bin 原封不动）；
  │    GetGlyphWidth 中文分支 → 固定 12/10（对齐 pokeE 先例硬编码双档）
  ├─【替换实现】字形解码：DecompressGlyph 类改为 Convert1bppTo2bpp→4 tile
  │    （pokeE 语义，代码现成）——1bpp 位流进 GlyphBuffer，mask 引擎照常拆列
  └─【砍掉】sMultistepLoadFont/MultistepInitWindowTileData（MONOSPACE 每窗
       16KB 全库预渲染——中文 7000 字不适用，tm1 用 §3.2 方案）、
       日文/拉丁双库（language 分支折叠）、gStringVar1..4（消息格式化不带）

结果：四路 textMode 的差异被美版原生模型吸收——
  tm0/tm2/tm3 类窗口 → VWF 路径（窗口自留网格 + mask 共享列）；
  tm1 类窗口 → §3.2 决策点（私有化 or 共享图集+精简分配）。
```

关键点：
- **mask 拆列模型下没有「半列相位状态」**——startPixel 是纯函数
  （`(left+cursorX)&7`），先读后写保住相邻字已写的像素。v8_phase_*、FE 换行拦截、
  相位复位失去存在理由。
- **清窗进入口**：Text_ClearWindow 是引擎内建（tilemap 填 blank tile + 游标归零），
  每次重绘走 BEGIN 状态自动清窗——打印残留从机制上消失。
- **控制码**：美版 FC+code 双字节体系整套进来（sExtCtrlCodeFuncs 23 项 +
  sExtCtrlCodeLengths 表），译文编码层切到美版码制（charmap 已有同构基础）；
  日文回落=不进双字节区按官方单字节画（GetGlyphWidth 返回 8）。
- **验收锚点**：vendored 的 x86 host oracle 可先在 PC 上对拍 mask 引擎逐字节输出
  （不依赖实机），实机四步法逐场景跟进。

### 3.2 决策点：tm1（菜单/导航/血条名）怎么办

tm1 是唯一结构性差异，二选一：

- **T-a 私有化**：给每个 tm1 窗口在 VRAM 圈私有 tile 区（含 cb1 上部独占带
  [0x2D2,0x400)≈302 tile + 各窗现成 tileData 区），中文按需写入、窗口关闭即弃。
  - 优点：与美版模型一致，撞 UI 物理不可能；v8 分配器退役。
  - 风险：需要逐窗 VRAM 预算勘测（gdb 逐场景采窗口 tile 区边界）；窗口复用/重叠
    生命周期要标定。这正是 v9 调研的「场景→空闲块分级表」，但这次是给「窗口私有区」
    而不是「独占字形带」，语义干净得多。
- **T-b 保留共享图集 + 精简分配**：tm1 继续用图集+分配器，只把分配单位从「每字 2~3
  tile 独立对」改成「行级连续段」。
  - 优点：不碰 VRAM 预算。
  - 缺点：v8 复杂度降不了多少，撞 UI 风险仍在。

**推荐 T-a**。理由：先例（美版 tm1=窗口私有预渲染）+ 先例零分配器 + 用户目标是
「换地基」而不是「继续补」。实施上 T-a 先做勘测（W1），勘测不通过的窗口退回 T-b。

## 4. P2 工作项分解

### W1 外部依赖标定 + VRAM/窗口预算勘测（P0 前置）
- 依赖标定（一次性）：AXVJ 的 gMain/按键掩码、PlaySE/IsSEPlaying、CpuFastFill 地址
  （状态机 WAIT_BUTTON/WAIT_SOUND 分支需要；pokeruby.sym 逻辑对照 + 同文件锚点法）。
- VRAM 勘测：逐场景采各窗口 template.tileData 落点、宽×高、tile 区边界、cb0/cb1
  空闲带，产出「窗口→私有区」分配表；tm1 窗口标注「可私有化 / 需 T-b」。
预计效果：一张标定表 + 一张 VRAM 预算表，W2~W5 全部依赖它。

### W2 美版引擎可移植子集落地（纯代码搬运 + host 对拍）
§3.1【原样搬运】清单全部落进 hook 模块（freestanding：无 RAM 段 → GlyphBuffer/
Window 实例落 EWRAM 已验证空闲区，全局 const 落 ROM）；sFonts 换中文字库表；
1bpp→GlyphBuffer 替换实现接上。
**先在 PC 上用 vendored x86 host oracle 对拍**：构造样例窗口 + 中文字符串，逐字节
比对 pixelRows/VRAM 输出（不依赖实机）。
预计效果：oracle 全绿 + 单字「号/道」类 11px/9px 字形在样例 tile 上与手算一致。

### W3 薄适配层 + 引擎切换（含原 P1）
- 入口适配：InitTextPrinter_hook 翻译构造美版 Window；PrintNextChar 调用点改调
  美版 UpdateWindowText（一次切换，不再逐 tm 换 writer——美版引擎自带四路分发）。
- 控制码层：译文编码切美版 FC+code 双字节制；日文回落=官方单字节原样。
- 分阶段回退：可先只切 tm0 类窗口（对话框）验收，tm1 类暂留旧路径，逐路切换。

重绘后无残留（BEGIN 状态自动清窗生效）。

### 与「打印残留 BUG」的关系
用户今天报的残留（新文本比旧短，旧字迹留存）有两个处置选项：
- **立即修（不移植）**：在 v8_alloc_begin 末尾加「本窗 tilemap 清 ours 字形」步
  （方案已构想，1 处改动）；先解燃眉。
- **移植消除**：W3 落地后，每次文本重绘走统一引擎入口，入口先做行清底
  （官方 Text_ClearWindow 语义 + 窗口网格全量重写），残留类 BUG 机制性消失。
推荐：残留若影响验收，先做立即修；移植完成后随 W6 退役该补丁。
