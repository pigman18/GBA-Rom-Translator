# 火红「队伍名字汉化 + 串档不乱」机制解剖（GDB 实测定案）

> 对象：`roms/translated/宝可梦火红日版汉化2.2.gba`
> 基线：`roms/origin/POKEMON_FIRE_BPRJ00.gba`（同版本日版，16 MB）
> 方法序：**GDB > 反汇编 > 文档 > 网络**（本轮以 ROM 逐字节 diff + Thumb 反汇编 + EWRAM 实测为主）
> 脚本：`scripts/firered/310_nick_slot_gdb.py`、`311_party_ewram.py`
> 场景：`bot/scenes/POKEMON_FIRE_BPRJ00/fr_party_dump.lua`

---

## 零、一句话答案

**火红用的是「412 项指针表 + 只改取名字入口」，不是运行时「日文→F7」查表。**

和 master 的 SLT2 是**完全不同的两条路**：

| | SLT2（master 早期，已删） | 火红 |
|---|---|---|
| 机制 | 在 `PrintNextChar` 里拿当前日文字节串去**哈希表查** | 建一张 **412 项 u32 指针表**，每项指向一条独立中文串 |
| 数据形态 | 一张 `key=日文 / value=F7串` 映射表 | 412 条**独立串**（各自 `FF` 结尾），零查找 |
| 改动位置 | 渲染器（每字符一次哈希 + 前缀比对） | **取名字的那 9 个调用点**（改一个 `bl` 目标） |
| 存档 | 需另处理写路径 | **完全不碰**（原表一字节未动） |
| 运行时开销 | 每字符哈希 + 流窗口封顶 | **零**（一次 `ldr [表+idx*4]`） |

## 一、实测证据链（本轮新做）

### 1.1 两版队伍截图对照（决定性）

同一个 `.sav`，同一场景 `fr_party_dump.lua`（进队伍界面，`DISPCNT=0x1740`）：

| 槽位 | 原版 BPRJ00 | 汉化 2.2 |
|---|---|---|
| 1 | `リザードン` | **喷火龙** |
| 2 | `ニャース` | **喵喵** |
| 3 | `ピジョット` | **大比鸟** |
| 4 | `ニドちゃん` | `ニドちゃん` ← **完全相同** |
| 5 | `モンジャラ` | **莫麻怪** |

**第 4 只不变**，因为那是**玩家自定义昵称**（不是物种名）。
⇒ 火红只替换「按物种取名字」这条路径，**自定义昵称原样保留**。

### 1.2 EWRAM 里只有 1 条 F7 串，但屏上 5 个中文名

队伍界面 dump 整个 EWRAM(256KB)：

```
EWRAM 里 0xF7 总数: 98
真正成串的（≥2 字 + FF 结尾）: 仅 1 处
  0x02021C88: f7 00 e8 f7 00 f0 f7 00 b9 f7 00 02 f7 00 03 f7 00 04 ff
              （6 字，18B，正好是选中槽的详情名）
其余 97 个 F7 全是单字节巧合（图形/随机数据）
```

**屏上 5 个中文名只有 1 个进了 EWRAM。**
⇒ **名字不是复制到内存再渲染的，而是渲染时直接从 ROM 指针表读。**

### 1.3 原版跑同一场景：EWRAM 结构几乎一样

| ROM | EWRAM F7 数 | 日文名命中 |
|---|---|---|
| 汉化 2.2 | 98 | 6 |
| 原版 BPRJ00 | 92 | 6 |

**两版内存几乎无差异**（差 6 个 F7 = 那 1 条详情串）。
⇒ 再次证明：**名字根本没走「复制到 EWRAM」这条路**。

## 二、机制全貌（静态已证）

### 2.1 原版日文名表：一个字节没动

```
原版 0x203CB8  412 项 × 6B（stride 6）  ← 真·物种名表
  [0]   ac ac ac ac ac ff   （占位）
  [1]   6c 5c 88 91 68 ff   （フシギダネ）
  [6]   78 8c ae 95 7e ff   （リザードン）
  [18]  9c 8d 86 a0 64 ff   （ピジョット）
  [52]  66 84 ae 5d ff 00   （ニャース）
```

汉化版同一区域：**差异 0 字节**。
⇒ **存档里存的 nickname 永远是这套原版编码**，串回日版不乱码。

### 2.2 新增 412 项指针表

```
0x0871BFB0  412 × u32（原版该区 100% FF，汉化新增）
  [  0] 0x08203CB8   ← 仍指原版日文表（占位项）
  [  1] 0x0871A42C   → f7 01 55 f7 01 57 f7 00 40 f7 00 71 ff   (4字)
  [  6] 0x0871A46C   → f7 02 92 f7 01 51 f7 01 54 ff            (3字 喷火龙)
  [ 18] 0x0871A4F8   → f7 00 35 f7 00 c6 f7 03 ab ff            (3字 大比鸟)
  [ 52] 0x0871A674   → f7 03 cb f7 03 cb ff                     (2字 喵喵)
  [114] (指向)        → f7 04 38 f7 03 6f f7 02 c0 ff            (3字 莫麻怪)
  [252] 0x082042A0   → ac                                     （占位，仍指原表）
  [276] 0x08204330   → ac                                     （占位，仍指原表）
非零项 412/412（全覆盖，占位项指回原表）
```

**索引与原版 stride-6 表 100% 对齐**（`idx 6` 在两表里都是喷火龙/リザードン）。

**每项是一条独立、`FF` 结尾的中文串，长度 10~22B 变长。**
⇒ **中文名不受 6B / 10B 槽限制，因为槽里装的是指针，不是名字。**

### 2.3 改动只发生在「取名字」这一层

#### 原版取名字函数（`0x08053358`）

```asm
08053358  push {r4,r5,lr}
0805335A  ldr  r0,[pc]        ; 0x02036FF4（当前队伍槽号）
0805335C  ldrh r0,[r0,#0]
0805335E  lsls r4,r0,#4
08053360  subs r4,r4,r0
08053362  lsls r4,r4,#2       ; r4 = slot * 60  ← 结构体 60 字节
08053364  ldr  r0,[pc]        ; 0x0822D2F8（队伍基址表）
08053366  adds r4,r4,r0
08053368  ldr  r0,[pc]        ; 0x02021C4C  ← 目标缓冲
0805336A  ldrh r2,[r4,#56]    ; r2 = *(slot+0x38) = species
0805336C  lsls r1,r2,#1
0805336E  adds r1,r1,r2
08053370  lsls r1,r1,#1       ; r1 = species * 6   ← 原版 stride 6
08053372  ldr  r5,[pc]        ; 0x08203CB8  ← 原版日文名表
08053374  adds r1,r1,r5
08053376  bl   0x08008900     ; StringCopy(dst, src)
```

#### 汉化版同一处：**只换了一个 `bl`**

```asm
08053376  bl   0x0810935E     ; ← 唯一改动
```

`0x0810935E` 是 `bx r3` 尾调用桩 → `0x087C04DC`。

#### 新入口 `0x087C04DC` → 扫描器 `0x087C04F6`

```asm
087C04F6  push {r4,r5,lr}
087C04F8  movs r1,#0          ; r1 = 换行计数
087C04FC  ...
087C0500  ldrb r2,[r0,#0]
087C0502  cmp  r2,#0xFF       ; 串尾
087C0504  beq  →087C053C
087C0506  cmp  r2,#0xF7       ; F7 前缀 → 前进 3
087C0508  beq  →087C0528
087C050A  cmp  r2,#0xFC       ; FC 控制码 → 查参数长度表
087C050C  beq  →087C052C
087C050E  cmp  r2,#0xF8/0xF9/0xFD/0xFE → 前进 2
087C0520  adds r0,#1          ; 普通字节前进 1
...
087C053C  movs r0,#17         ; 返回 17
087C053E  cmp  r1,#0
087C0540  beq  →087C054A
087C0542  movs r0,#10         ; 返回 10
087C0544  cmp  r1,#1
087C0546  beq  →087C054A
087C0548  movs r0,#3          ; 返回 3
```

**返回 3 / 10 / 17 —— 都是「10 字节昵称槽」的合法长度**
（`3` = 2 汉字 + FF；`10` = 满槽；`17` 对应更长串的截断档）。

⇒ 火红在这里做的是**把中文串裁到能塞进 nickname[10] 的长度**，
用于**写存档副本**，而**不是**显示串。

### 2.4 40 处 `0x08203CB8` 引用，9 处换成新代码

| 改动 | 处数 | 说明 |
|---|---|---|
| 保持 `0x08203CB8` | 31 | 原版路径不动（存档/内部逻辑仍读日文表） |
| → `0x08FFD535` | 7 | 新增「带 stride 反解 + 指针表」取名字 |
| → `0x08FFD539` | 1 | 同上（+4B，另一分支） |
| → `0x08FFCF01` | 1 | 另一新增变体 |

#### 新增取名字 `0x08FFD534`

```asm
08FFD534  movs r2,#20         ; 分支 A：长度上限 20
08FFD536  b    →08FFD53C
08FFD538  movs r2,#17         ; 分支 B：长度上限 17
08FFD53C  push {r4,r5,r6,lr}
08FFD540  adds r5,r1,#0       ; r5 = species
08FFD544  ldr  r3,[pc]        ; 0x08044985
08FFD548  muls r0,r3          ; ★ 0xAAAB 魔数
08FFD54A  lsrs r0,r0,#18      ; r0 = species / 6   ← 反解 idx
08FFD54C  lsls r3,r0,#1
08FFD54E  adds r3,r3,r0
08FFD550  lsls r3,r3,#3       ; r3 = idx*24（校验）
08FFD552  cmp  r3,r5
08FFD554  bne  →08FFD580      ; 不整除 → 原表
08FFD558  cmp  r0,#0 / #411 / #252..#276  → 原表（占位项）
08FFD56A  lsls r0,r0,#2
08FFD56C  ldr  r3,[pc]        ; 0x0871BFB0  ← 指针表
08FFD56E  ldr  r0,[r3,r0]     ; 取指针
08FFD578  bl   0x08FFD592     ; 带上限检查的拷贝
08FFD580  adds r0,r4,#0       ; 失败兜底：原版日文表
08FFD582  ldr  r1,[pc]        ; 0x08203CB8
08FFD588  bl   0x08FFD5B8     ; StringCopy
```

#### 拷贝 `0x08FFD592`（带 FF 终止 + 上限）

```asm
08FFD592  push {r4,r5}
08FFD596  ldrb r4,[r0,r3]     ; 从中文串读
08FFD598  cmp  r4,#0xFF
08FFD59A  beq  →08FFD5A6
08FFD59E  cmp  r3,r2          ; 上限
08FFD5A0  bcc  →08FFD596
08FFD5A2  movs r0,#0          ; 超长 → 返回 0（失败）
08FFD5A6  ...                 ; 逐字节拷到 r1
08FFD5B2  movs r0,#1          ; 返回 1（成功）
```

## 三、这套机制如何解决「完整显示」

### 3.1 关键洞察：显示与存档彻底解耦

| | 红宝石（我们 v8） | 火红 |
|---|---|---|
| nickname 槽 | 10B **存名字本身** | 10B **存名字**（存档格式，两版一样） |
| **显示路径** | 从 nickname 槽读名字 | 从 **species 查指针表**读名字 |
| 中文名长度限制 | **受 10B 槽物理限制** | **不受限**（指针表里是变长串） |

⇒ 火红把「显示名字」和「存档名字」**彻底分开**：
- **存档**：写 `nickname[10]`，内容是原版编码（截断到 10B）→ 串档不乱
- **显示**：`species` → 指针表 → 完整中文串 → 直接渲染（不落 EWRAM）

### 3.2 为什么我们做不到（当前 v8 的困境）

`0x08042408`（战斗血条名字）拿到的是 **`gBattleTextBuff2` 指针**，
**不是 Pokemon 结构指针，拿不到 species**，所以只能从 `+8` 的 10B 槽读。

火红的对应函数（`0x08053358`）**同时拿到了 species 和 dst 缓冲**，
所以它能改成「按 species 查指针表」。

## 四、和 SLT2 的对比（回答「是不是同一个思路」）

### 4.1 SLT2 是什么（master 早期，`git show 7ed443e`）

```c
/* SlotTable 格式：jp_len(1B) | jp_bytes(jp_len) | chinese_bytes(... FF)
 * 以 0x00 哨兵结尾。 */
static int slot_lookup_and_draw(TextPrinter *win, uint32_t cur_char)
{
    /* 从 text stream 读出当前 JP 字节序列（最多 SLOT_MAX_JP_LEN 字节），
     * 与表中 jp_bytes 逐条比对。匹配则内联绘制中文 F9 流并推进
     * WIN_TEXT_INDEX 跳过被替换的原始 JP 字节，返回 1。 */
}
```

**这就是用户记忆的「slt2 / slot_table」**：`key=日文, value=F7串`，
`PrintNextChar` 里遇到日文就查表。

### 4.2 火红不是这个思路

火红**没有任何运行时查表**：

```
species ──► 指针表[species] ──► 一条独立中文串 ──► 直接渲染
```

**零哈希、零比对、零流窗口、零 EWRAM 复制。**

### 4.3 为什么火红能这么干、SLT2 当年不行

| | SLT2 | 火红指针表 |
|---|---|---|
| 前提 | 拿不到 species，只能看到「当前日文字节」 | **拿得到 species**（`ldrh r2,[r4,#56]`） |
| 代价 | 每字符一次哈希 + 前缀匹配 | 一次 `ldr [表+idx*4]` |
| 风险 | 日文串有歧义（同前缀不同名） | 无歧义（按索引直取） |
| 存档 | 需保证写路径不被污染 | 完全绕开写路径 |

**核心差异：火红改的是「取名字函数」，SLT2 改的是「渲染器」。**

### 4.4 补充：master 的 SLT2 其实在 11-04 就被换掉了

`git show f33208f` 之前的 `UnusedPrintMonName_hook.c` 注释已经写着：

> 图鉴分类名和宝可梦名的文本用**直接搬运 + 改指针**，
> 内存里的字符串本身就是 `F7 00 hi lo` 单字流。本 hook 不展开任何表。

⇒ 用户记忆中「master 队伍渲染有 BUG 但也是中文」的阶段，
可能已经是「改指针」而非「SLT2 查表」了。SLT2 主要用在图鉴分类名那类
**拿不到 species 的短串**上。

## 五、对红宝石 v8 的直接启示

### 5.1 可复制的做法（推荐）

**把「按 species 取名字」这一层加进去，而不是继续在 10B 槽上做文章。**

红宝石里**已经有这个模式**，在 `0x08037CF0`：

```asm
08037CFC  bl   0x80399B4     ; 准备
08037D04  ldrh r1,[sp,#14]   ; r1 = species
08037D06  bl   0x803B11C     ; ★ 从新表读完整中文名到 sp（无长度限制）
08037D0A  adds r0,r7,#0      ; r7 = &gPlayerParty[n]
08037D0C  movs r1,#2
08037D0E  mov  r2,sp
08037D10  bl   0x803A668     ; 把 sp 写到 r7+8（nickname[10]）← 这里截断
```

**`0x0803B11C` 已经读到完整名字了，只是又把它塞回 10B 槽。**

`0x0803B11C` 实测（我们产物里）：
```asm
0803B11C  push {r4,r5,r6,r7,lr}
0803B11E  adds r6,r0,#0      ; dst
0803B120  lsls r1,r1,#16
0803B122  lsrs r4,r1,#16     ; species
0803B12C  lsls r0,r4,#1
0803B12E  adds r0,r0,r4
0803B130  lsls r0,r0,#3      ; idx * 24  ← 新 stride
0803B134  adds r3,r0,r5      ; src = 新表 + idx*24
0803B144  ldrb r0,[r3,#0]    ; 逐字节拷
0803B14A  cmp  r0,#255       ; 遇 FF 停 ← 无长度上限
```

### 5.2 具体改造方案

**在 `0x08037D06` 之后，把「用 sp 渲染」与「写 nickname」分开：**

- **显示路径**：`0x08037D06` 得到的完整名字在 `sp` 里，
  直接把 `sp` 交给渲染器，**跳过 `0x0803A668`（写 10B 槽）**
- **存档路径**：`0x0803A668(r7, 2, sp)` 保持原样（只写 10B，存档不乱）

这样：
- 显示：完整中文（`sp` 里 12~20B 都能用）
- 存档：`nickname[10]` 原版编码 → 串档不乱

**关键前提**：确认 `0x08037CF0` 这条路径是**队伍界面**用的，
而战斗血条走的是另一条（`0x08042408`，拿不到 species）。

### 5.3 战斗血条的另一条路（参考火红的「兜底」）

火红 `0x08FFD580` 有一个**兜底分支**：查表失败就回原版日文表。
这给了我们一个启发：

**`0x08042408` 虽然拿不到 species，但它的 `r5`（`gBattleTextBuff2`）里
`+0` 是 personality，`+4` 是 otId。**
理论上可以用 personality 反查队伍，但代价太高。

**更实际的做法**：让上游（`0x08042E82` 的调用者）在调 `0x08042408` 之前，
把 species 或「完整名字指针」放进 `gBattleTextBuff2` 的某个空闲位，
再让 `0x08042408` 直接用。

### 5.4 不要照抄的部分

| 火红做法 | 不照抄的原因 |
|---|---|
| 412 项额外指针表 | 我们的 reflow 已把表搬到 `0x1EB0AF4`（stride 24），可以直接在表内放变长串，不需要第二张表 |
| 改 9 处 `0x08FFD535` | 我们只有一条血条路径，改一处就够 |
| `movs r0,#17` 裁长度 | 火红裁的是**存档副本**，不是显示串。我们若裁显示串就白做了 |

## 八、红宝石侧「能不能照搬」的实测判断

### 8.1 `0x08037CF0` 不是队伍界面专用

`0x08037BA4`（批量遍历队伍的那个函数）有 **22 个调用者**：

```
0x8008e66 0x800cd6c 0x800cdfe 0x800cec4 0x800cf62
0x8037f3c 0x803803a 0x80380a6 0x80380da 0x803811a
0x8038196 0x8038212 0x803af72 0x803f306 0x803f3b6
0x803fb9c 0x804514e 0x804abda 0x80c0488 0x80c05e6
0x810a61a 0x812efe4
```

⇒ 它是**通用「设置宝可梦结构字段」函数**，不只服务队伍界面。

**这解释了火红为什么要改 9 处而不是 1 处**：
它必须在**每一个「按 species 取名字」的调用点**都做替换。

### 8.2 所以我们的改造点应该是「取名字的原子函数」

不要改上层业务函数（有 22 个调用者，改不完），
而是改**真正做 `species*stride + 名表` 那一行**所在的函数。

红宝石里这个「原子取名字」就是：

```asm
0803B11C  lsls r0,r4,#1
0803B12E  adds r0,r0,r4
0803B130  lsls r0,r0,#3      ; idx*24
0803B134  adds r3,r0,r5      ; src = 新表 + idx*24
```

**它已经是「按 species 从新表读完整名字」了 —— reflow 已经帮我们做完了。**

### 8.3 真正的瓶颈只有一个

```
完整名字（在 sp 里，12~20B）
        ↓
0x0803A668(r7, 2, sp)   ← 只拷 10B 到 nickname[10]
```

**只要不改这个 10B 写入，显示就永远只有 2 字。**

火红的解法是：**显示路径根本不经过这个 10B 槽**。
我们的解法必须是同一个思路：

**找到「把 sp 里的名字送去渲染」的那一步，绕过 0x0803A668。**

### 8.4 下一步（待做，需要 GDB 确认）

**方案 B（兜底）**：仿火红 `0x08FFD580` 的兜底思路 ——

## 九、首次 hook 尝试失败：GetMonData(mon,11) 不能随便调（2026-11-20）

### 做了什么

照火红的思路，把 `0x08042430` 的 `bl GetMonData(mon, 2, sp)`（读 nickname）
换成「先取 species，再按 species 查新表」：

```asm
NickFullName_Hook:
    push {r4, r5, lr}
    sub  sp, #16
    add  r4, sp, #28            @ 调用者名字缓冲
    adds r0, r5, #0
    movs r1, #11                @ MON_DATA_SPECIES
    add  r2, sp, #0
    ldr  r3, =0x08039F24
    bl   bx_r3
    ...
```

### 结果：遇敌崩溃

```
mGBA Crash: Jumped to invalid address: E3A02004
```

`E3A02004` 是 ARM 指令编码 `mov r2, #4`，说明**执行流跑进了数据区**。

### 根因

`0x08039F24` 不是轻量的「取一个字段」，而是**substruct 全解密器**：

```asm
08039FB4  adds r0, r3, #0       ; r0 = mon
08039FB6  bl   0x8039FC0        ; ← 解密 substruct 并读**所有**字段
```

`0x08039FC0`：
```asm
08039FC0  push {r4,r5,r6,r7,lr}
08039FC2  mov  r7, sl
08039FC4  mov  r6, r9
08039FC6  mov  r5, r8
08039FC8  push {r5,r6,r7}       ; 保存高寄存器别名
08039FCC  mov  r9, r0           ; r9 = mon
08039FE0  ldr  r1, [r0, #0]     ; personality 作密钥
08039FE4  bl   0x80399FC        ; 解密 field 0
08039FEA  mov  r0, r9
08039FEC  ldr  r1, [r0, #0]
08039FEE  movs r2, #1
08039FF0  bl   0x80399FC        ; 解密 field 1
...                              ; 一路解到 field 11+
```

**它对 `r2`（dst）的要求很高，而且会遍历所有字段。**
我在 hook 里用 `sub sp,#16` 给的局部缓冲太小，
解密过程中越界写到栈帧外 → 破坏返回地址 → 跳到数据区。

### 关键教训

| # | 教训 |
|---|---|
| 1 | **`0x08039F24` 是重函数**（全 substruct 解密），不能在栈上随便给 16B 缓冲 |
| 2 | `0x08042408` 自己在 `0x08042460` 调它时，`r2` 传的是什么**必须先看** |
| 3 | 崩溃地址 `E3A02004` 是 ARM 指令编码 —— 看到这种值就是「跑进数据区」 |
| 4 | **改 hook 前先确认原调用点的完整寄存器约定**，不能只看到 `r1=11` 就照抄 |

### 下一步（更安全的做法）

**不要自己调 `GetMonData(mon,11)`**。改为：

**方案 A（推荐）**：复用 `0x08042408` 自己那次调用。
它在 `0x08042460` 已经拿到 species（存在 `r2`/`r0`），
可以在 `0x08042464` 之后插 hook，用那个现成的 species。

**方案 B**：`0x0803B11C` 的入参是 `(dst, species)`。
在 `0x08042408` 里，species 在 `0x08042460` 之后才可得，
所以 hook 点应该在 `0x08042464`，而不是 `0x08042430`。

## 十、第二次尝试：数据层打通了，但撞上 UI 布局墙（2026-11-20 10:10）

### 10.1 上一轮崩溃的真根因（比"栈太小"更简单）

**`bx` 到偶数地址 → CPU 切 ARM 模式。**

```asm
ldr r3, =0x08039F24     @ ← 偶数！
bl  _Nick_bx_r3         @ bx r3
```

Thumb 函数地址是偶数，但 `bx` 到偶数会让 CPU **切到 ARM 状态**，
把后面的 Thumb 字节当 ARM 指令解码 → 乱码跳飞 →
mGBA 报 `Jumped to invalid address: E3A02004`
（`E3A02004` 其实就是 ARM 的 `mov r2, #4`，是数据区字节被误读的结果）。

**修法：所有 `ldr r3, =0x08xxxxxx` 必须 `|1`。**

### 10.2 第二个坑：`0x0803B11C` 硬编码 11 字节上限

```asm
0803B144  ldrb r0, [r3, #0]
0803B146  strb r0, [r2, #0]
0803B14A  cmp  r0, #255
0803B14C  beq  →0x803B158
0803B14E  adds r2, #1
0803B150  adds r3, #1
0803B152  adds r1, #1
0803B154  cmp  r1, #10        ; ★ 最多 11 字节
0803B156  ble  →0x803B136
0803B158  adds r1, r6, r1
0803B15A  movs r0, #255
0803B15C  strb r0, [r1, #0]   ; 强行补 FF
```

名字需要 12 字节（3 汉字），**第 12 字节被强行写成 FF**，
所以 `f7 00 05 91` 变成 `f7 00 05 ff`。

**不能直接放宽 `cmp r1,#10`**：它有 3 个调用者
（`0x08037D06` 队伍 / `0x0803FC68` / `0x0811CA60`），
队伍路径的 dst 之后紧跟 `nickname[10]`，放宽会写坏结构体。

**解决：hook 里自己实现拷贝**（r3 = 表基址 + species*24，逐字节到 FF 停）。

### 10.3 数据层已完全打通（GDB 实测证据）

`NickHookMid` @`0x08800066`（拷贝循环结束后）实测：

```

                    = 「蛇纹熊」3 字完整 ✅
```

`NickAfterCopy` @`0x08042444`（`StringCopy` 之后）实测：

```
r4-3 (=0x0202362C) = fc 02 02 | f7 00 05 7d f7 00 0e cf f7 00 05 91 ff
                     ↑前缀    └──── 火焰鸡（完整 3 字）────┘
```

**⇒ 名字数据已经 100% 正确地写进了目标缓冲。**

### 10.4 但画面坏了：UI 布局装不下 13 字节

截图显示血条里只剩一个「级」字，`Lv : 24` 被推走/遮挡。

原因在 `0x08042452` 之后：

```asm
08042452  adds r0, r5, #0
08042454  bl   0x803987C      ; 取某个单字节字段（返回值低 8 位）
08042458  lsls r0, r0, #24
0804245A  lsrs r4, r0, #24    ; r4 = 该字节
```

`0x08042408` 的后续排版（血条、`Lv`、HP 数字）依赖这个值来定位。
名字从 5 字节变 13 字节后，**排版基准没跟着变**，于是全错位。

### 10.5 结论：这不是"改个长度"能解决的

火红能这么做，是因为它的**整个 UI 排版按字符格计算**
（`docs/research/FIRERED_RENDER_FINAL.md`：11×11 字形、步进 13、按字符格排版）。

红宝石的血条名字是**按固定 5 字节槽位**设计的，
把名字塞成 13 字节必然撞坏后续元素。

## 十一、正解：hook `0x0811C776`（对战文本汇合点）— 2026-11-20 11:00 完成

### 11.1 之前所有尝试都错在哪

| 尝试 | 挂载点 | 为什么错 |
|---|---|---|
| 第一次 | `0x08042430` | 血条名字路径，不是遭遇对话框 |
| 第二次 | `0x0803A1AC` | 这是 `GetMonData` 的 **field 2 处理器**（nickname），不是占位符展开 |
| 第三次 | `0x0811C7AA` | 这是 `FD` 分发后 **某一条 param 分支**，只覆盖部分场景 |

**"只看到我方 species 282"** 就是第三个错的直接证据 ——
`0x0811C7AA` 那条路走的是 `0x03004290`（我方槽基址）。

### 11.2 真正的架构（静态反汇编定案）

```
0x0811BE94            对战文本框渲染器主函数
  ├ 0x0811BEA2  mov  r9, r0         ; r9 = 文本读指针
  ├ 0x0811BEB6  cmp  r1, #0xFD      ; 遇到 FD
  ├ 0x0811BEC2  mov  r2, r9
  ├ 0x0811BEC4  ldrb r0, [r2, #0]   ; 读 FD 后面的参数
  ├ 0x0811BEC6  cmp  r0, #41        ; 0x29
  └ 0x0811BED6  mov  pc, r0         ; ★ 跳表分发（基址 0x0811BEDC）

FD 参数跳表 0x0811BEDC:
  param 0 → 0x0811BF84
  param 1 → 0x0811BF98
  param 2 → 0x0811BFBE
  param 3 → 0x0811BFE4   ★ 「野生的XXX」用这个
  param 4 → 0x0811C008
  ...
  param 11 → 0x0811C1A0
```

`FD 03` 处理器 `0x0811BFE4`：

```asm
0811BFE4  movs r0, #1
0811BFE6  bl   0x08075870          ; 取阵营/槽
0811BFEA  ldr  r1, =0x020247CA      ; 槽索引表
0811BFEE  lsrs r0, r0, #23          ; *2
0811BFF0  adds r0, r0, r1
0811BFF2  ldrh r1, [r0, #0]         ; 槽索引
0811BFF4  movs r0, #100
0811BFF6  muls r0, r1               ; idx*100
0811BFF8  ldr  r1, =0x030044F0      ; ★ 敌方 gBattleMons 基址
0811BFFA  adds r0, r0, r1           ; mon 指针
0811BFFC  b    0x0811C772           ; ★ 汇合到通用输出
```

**所有 param 分支都汇合到 `0x0811C772`：**

```asm
0811C772  movs r1, #2               ; MON_DATA_NICKNAME
0811C774  mov  r2, sp               ; dst = sp
0811C776  bl   0x08039F24           ; ★ 唯一取名字的地方 ← 本 hook
0811C77A  b    0x0811C7AE
0811C7AE  mov  r0, sp
0811C7B0  bl   0x08004290           ; StringCopyN(sp, 5)
0811C7B4  mov  r4, sp               ; 名字源
0811C84A  ... 逐字节拷到 buffer，遇 FF 停，无上限
```

### 11.3 最终实现 [P12]

**只替换 `0x0811C776` 一条 bl**，逻辑在 `src/battle/NickSlot_entry.s`：

```
进入: r0 = mon, r1 = 2(MON_DATA_NICKNAME), r2 = sp = dst
  species = GetMonData(mon, 11, localbuf32)
  若 1 <= species <= 411:
      src = 0x1EB0AF4 + species*24
      逐字节拷到 dst，遇 FF 停（含 FF）
  否则：
      退回原逻辑 GetMonData(mon, 2, dst)
返回: 保持 r4/r5/r6/r9 不变
```

- 挂载：`0x0811C776` → `bl 0x081B504C`（1.5MB，bl 可达）→ `ldr/bx 0x0880003C`
- `0x0811C77A` 保持原版 `e018`（`b 0x0811C7AE`）不动
- 血条 `0x08042430` 保持原版
- `0x4294` 仍为 `0d24`（5→13）

### 11.4 实测结果

**「啊！野生的长翅鸥跳出来了！」** —— 3 个字完整显示 ✅

- `battle_dialog`：314 帧正常
- `battle_full`：127 帧正常，16 秒完成，无崩溃

### 11.5 关键教训（写给下一次）

1. **`0x0803A1AC`/`0x0803A1E6` 是 `GetMonData` 的字段处理器，不是占位符展开器。**
   用 `cmp r1,#0x37` 的跳表（`0x08039F24`）才能确认。
2. **`FD XX` 的分发在 `0x0811BED6`，跳表基址 `0x0811BEDC`。**
   不要再从 `0x0803A6FC` 那类「param 跳表」去猜。
3. **改 hook 前先确认「这条路径的 mon 基址是 0x03004290 还是 0x030044F0」。**
   前者我方、后者敌方，差 0x260。
4. **`GetMonData(mon, 11)` 的局部缓冲至少 32 字节**，8 字节会返回值异常。
