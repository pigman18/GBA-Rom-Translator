## 一、调研收口：五条硬结论

详细证据与引用清单见 `docs/调研_20260921_竞品cb扩容与非8x16字体实证.md`。

1. **没有先例。** 已知 GBA 汉化工程（含围炉 Go / 精灵宝可梦汉化教程系列 / pokeemerald 系 decomp）**没有任何一家做「绕过或扩展 cb 区」**。全部走「换码位 + 换字形 + 在原有 1024 砖里排版」。
2. **术语陷阱（解释了过去几轮为什么搜不到东西）**：中文圈说的「字库扩容」= **ROM 里码位/字形表的扩容**，不是 VRAM charblock。搜「cb 区 扩容方案」零命中是**术语错位**，不是知识盲区。
3. **借 OBJ VRAM（cb4/cb5）给 BG 用 = 假路径。** tonc 一手结论：OBJ 字符区只有 OBJ 硬件通路能读，BG 读不到；模拟器上"看起来能用"是仿真宽松。**真机不可见 ⇒ 这条在硬件层面死，与工程难度无关。**
4. **官方对「非整 tile 宽」的唯一答案 = 半 tile 合成。** pokeemerald 实证链：`DecompressGlyph_Normal/Short/Bold` → `gCurGlyph.gfxBufferTop/Bottom` → `CopyGlyphToWindow`，宽度 >8 时 `GLYPH_COPY` 同时写 `currX` 与 `currX+8`；`GenerateFontHalfRowLookupTable` / `DecompressGlyphTile` + `sFontHalfRowOffsets` 把一行 16bit 拆成两个 4px 半格。**⇒ 官方引擎原生支持 1~16px 任意墨宽，靠的就是 4px 相位拼合。** 我方 `blend_glyph_4bpp` + `PrintNextChar_hook.c` 的相位两段式（`print_glyph_px:158-252`）**已经是同一机制**，不缺骨架、不需要新渲染器。
5. **规格锚点。** 日版商用 GBA 汉字实测 **16×12**；中文工具链事实标准 **11×11 / Zpix**。⇒ 我方 11×11@12px 步进在业界区间内，**字形规格本身不是问题**；今天所有症状的成因都在**落号坐标系**（见第三节）。

## 三、三份在案方案的归并（这是本轮最重要的产出）

| 在案方案 | 结论 | 处置 |
|---|---|---|
| **21e**「块内号 [514,1024) ⇒ 物理 charBase+1」 | **几何判据成立，且已实施** | ✅ **结案保留**。它的 §7 三行段表是针对旧树的，作废 |
| **v23**「根因 = 键错：我方位置键 vs 引擎字形键」 | **诊断成立，处方不成立** | ⚠ 取"必须换键"的结论；弃"换成字形键（J1/J2）"的做法 |
| **定号重构** 方案 S「屏幕格定号 + 装得下判据」 | **今天唯一同时满足四条硬要求的键** | ✅ **采纳为落号键**，但坐标系改挂到 21e 的私有池上 |

### 为什么「字形键」（v23 J1/J2）不能做
`定号重构` §四 已量化证否，理由与两份文档一致且不可绕过：
- 官方 `号 = TILE_BASE + 2c` 能成立的前提是**墨宽正好 8px = 一个 tile**；
- 我方墨宽 11 > 8 ⇒ 跨 2 tile 列；按 code 定号时相邻两字必不同号 ⇒ **尾列无法共享**
  ⇒ 被迫 16px 步进（版式变松，用户明确不要）；
- 满屏实测 A 方案 cap=128 溢出 288 次（3951 像素差），cap=256 用 791 号。

### 为什么「格键」（S）是对的
- 同一格天然同号 ⇒ **重画零消耗**；不同格天然不同号 ⇒ **不覆盖**；
- **号需求上界 = 格子数**，与「这屏打了多少字 / 字库多大」**解耦** ⇒ 加字不涨号；
- 纯函数 ⇒ **零扫描、零采样**；
- 12px 步进**完全不动**（相位两段式通路一行都不用改）。

### 三者合并成一句话
> **几何** = 我方私有池 `[514,1024)`（物理 charBase+1，已在码内）；
> **键** = 格定号（不再每字领游标）；
> **段** = 按「窗口面积」一次领一段，关窗/换模板整段回收 —— 这正是 `.cursor/rules/axvj-no-avoidance-band.mdc` 指定的唯一正解（美版 `TextWindow_SetBaseTileNum` 的所有权 + 生命周期语义）。

## 四、接下来的修改方案（一处改动 + 一处删除 + 一个构建期脚本）

### Step 1（核心）：tm1 从「每字游标」改为「每窗一段 + 段内格定号」

只动 `tile_alloc.c` 的 tm1 通路，**渲染侧 `print_glyph_px` 一行不改**（相位、共享尾列、`blend_glyph_4bpp`、`UpdateTilemap` 全保持）。

```
旧：每字 → v8_alloc_n(win, glyph_len) → 游标 += n            （字数驱动，会回卷覆盖自己）
新：每窗（InitTextPrinter 归属变化时）→
        span   = 窗口面积格数 × 2 砖        ← 一次领段，与文本长度无关
        base   = 池内游标；游标 += span     ← 关窗/换模板整段回退 = 生命周期
    每字 → 号 = base + cell(行, 列) × 2     ← 纯函数；下半 = +1（现有 chs_lower_delta 不变）
```

- **`cell` 用窗口内格坐标**（由 `win[0x1A]/[0x1C]` 起点 + `win[0x1B]/[0x1D]` 游标，`GetCursorTilemapPointer 0x08003708` 实证 stride=32 的那一族字段）。
  `定号重构` §十 的「`TILE_BASE + n ≤ 1023` 装得下判据」在本方案里**变成池内判据**：`base + span ≤ 1024`。
- **不退步保证**：`span` 装不下 ⇒ 该窗口**退回现有游标通路**（行为与今天完全一致，不会更差）。
- **容量账**：池 = 510 砖 = **255 格/层**。对话窗 20×4 = 80 格（160 砖）；长文本窗 20×8 = 160 格。
  超出 ⇒ 走退回分支。这条账**必须在 Step 3 的脚本里静态复算**，不许拍脑袋。

### Step 2：删掉运行时探测 `chs_collect_blocked`

`tile_alloc.c:43-91,167,186-193` 现在每次领号读 `REG_DISPCNT` + 四个 `REG_BGxCNT`、求 tilemap 跨度再逐砖跳过。两处硬伤：
1. 它就是 `.cursor/rules/axvj-no-avoidance-band.mdc` 判定表第 4 行的形态（运行时看外部占用再决定塞哪），**违规**；
2. `调研_20260921e` §6 已把这条判据静态化并实测完：**80 个配层点 → 32 个界面，「下一块」全部干净，0 真实冲突**（引擎自己从不让两个 BG 层用相邻 charBase）。

⇒ **依据已在，运行时探测没有存在理由**：整段删除，改为 Step 3 的构建期检查。
（真正需要防的是「本层 tilemap 恰好落在 charBase+1 块」—— 静态可读：`tpl[+0x02] screenBase` vs `tpl[+0x01] charBase+1`，构建期一条减法判完。）

### Step 3：把两条静态判据脚本化入仓，做**构建期闸门**

新建 `scripts/verify_chs_pool_static.py`（复用 21e 留下的 `.tmp/tpl_fields.py`、`.tmp/bg_layer_map.py` 逻辑，收进 `scripts/` 常驻）：

| 检查 | 判据 |
|---|---|
| A 模板自洽 | 53 条 `tpl[+0x0C] == VRAM + tpl[+0x01]*0x4000`、`tpl[+0x10] == VRAM + tpl[+0x02]*0x800` |
| B 下一块干净 | 对每个界面的每一文本层：无另一层 charBase ∈ `{C, C+1}`；且**本层 tilemap 不落在 charBase+1 块**（若落 ⇒ 池起点在构建期往后挪，或该模板标记不画） |
| C 池容量 | 每个文本窗口 rect 的 `格数×2 ≤ 510`，列出超容窗口清单（走 Step 1 退回分支） |
| D 引擎预取上界 | 复算 `0x080029E0` 写砖范围 `[1,513)`，断言与 `CHS_POOL_LO` 无交 |

出 ROM 前三道老闸保持：`build.bat` → `scripts/check_hook_in_rom.py` → `scripts/verify_v21_final_rom.py`。

### 明确「不动」的东西（单任务原则）
- `print_glyph_px` / `tm2_print_px` / `blend_glyph_4bpp` / `extract_cols` —— 渲染通路一字不改；
- tm0、tm3 落号通路 —— 不改；
- **P32 预取短接继续保持不打**（我方池已在物理上隔到 charBase+1 块，预取写不到；而短接会带走队伍页 `Lv/HP` 数字 —— 实测教训在 `15-2` / `v23`）；
- 字体、charmap、翻译流水线、`build.bat` 模块清单 —— 不碰。

## 五、一处需要用户裁定的冲突（不阻塞 Step 2/3，阻塞 Step 1 的"合法性"）

`.cursor/rules/axvj-no-avoidance-band.mdc`（工作树里被加强过、未提交）的字符串级判定表第 1 行：

> 任何形如 `*_LO` / `*_BASE` / `*_START` 且赋值为 `0x1~0x3FF` 的起点常量 ⇒ 抬水位（违规，不看动机）

当前代码 `tile_alloc.c:34 #define CHS_POOL_LO 514u` **字面命中**，注释里「池起点取 514、避开引擎预取区」的措辞也命中第 3 行。
⇒ 按现行闸门，**今天已经在树里跑通的这一版就该停包**。

我的建议（推荐，不擅自动规则文件）：给该 rule 补一条**构造性豁免**，把"违规"与"合法"的分界从**措辞**换成**证明**：

> 起点常量若同时满足 ①**由引擎自己的写入公式反推**（如 `0x080029E0` 只写 `[1,513)`）、
> ②**号需求有上界且与文本量/字库量无关**、③**有构建期脚本可复算**（Step 3），
> ⇒ 不属抬水位；缺任一条件即按违规处理。

理由：抬水位的死因是"拍的常量 + 无上界 + 靠观测"，这三条恰好把本方案与 v8~v21 那一族区分开；
只按措辞封杀会连几何正确的方案一起封掉（21e §8 的论证方向正确，但拿不出闸门能验的形式）。
