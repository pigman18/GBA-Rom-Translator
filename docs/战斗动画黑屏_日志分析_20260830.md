日志：`work/gdb/origin_move.log`（2034 行 / 637 事件）、`work/gdb/han_move.log`（371 行 / 159 事件）

## 一、结论速览

**首轮日志没有采集到「放技能」的过程**，录到的是**读档后继续跑的、已损坏的动画循环**。
证据链高度指向：**即时存档（save state）在动画中途存/读 → EWRAM 动画状态机残留 → 脚本指针变野 → 反复刷背景 → 黑屏**。与汉化无关。

| 判据 | 结果 |
| --- | --- |
| `DoMoveAnim` 命中 | **0 次**（地址有效，有 3 处 BL 调用点，但本轮没走到） |
| `LaunchBattleAnimation` 命中 | **0 次**（地址有效，1 处 BL 调用点） |
| 脚本命令循环 | **在跑**：`loadspritegfx` 288 + `waitbgfadein` 142 + `changebg` 142 |
| `sBattleAnimScriptPtr` | **0x04030201**（IO 区野指针，非 ROM） |
| `gAnimScriptCallback` | 有效函数地址 → 状态块**被部分踩坏**，不是整体未初始化 |
| 原版 vs 汉化 | 事件结构、次数比例、垃圾值 **完全一致** |
| 代码/动画表/脚本本体 | 逐字节一致（见埋点手册） |

## 二、三个关键发现

### 1. DoMoveAnim / LaunchBattleAnimation 0 命中 —— 说明动画不是本轮启动的

两个地址都已验证**有效**（`DoMoveAnim@0x08071D98` 有 3 处 BL 调用点；
`LaunchBattleAnimation@0x08071DCC` 有 1 处）。0 命中只有一个合理解释：

> **动画在采集开始前就已经启动了** —— 是即时存档里带过来的，读档后继续跑，
> 自然不会再经过 `DoMoveAnim` / `LaunchBattleAnimation`。

这与用户观察「用即时存档加载日版也会触发黑屏」完全吻合。

### 2. 事件时序是一个 142 次的死循环

```
ABG(loadspritegfx) → waitbgfadein → ABG → changebg → ABG → waitbgfadein → ABG → changebg → ...
```

`waitbgfadein` 与 `changebg` 各 142 次严格交替，且 **288 条 `[ABG]` 记录内容逐字节相同**
（`move=#1027 bgfade=2 turn=1 vis=15`，参数 `00 00 00 17 40 00 00 01 00 00`）。

**状态完全冻结 + 反复执行背景命令 = 黑屏的直接原因**（背景被反复切换/淡入淡出刷成黑）。

### 3. 找到了真正的脚本命令循环体

`waitbgfadein` / `changebg` 的 `LR = 0x08077C3E`，落在 **`sub_08077C20`**：

```
0x08077C20: B530        push {r4,r5,lr}
0x08077C22: bl  0x08077C50      ← 循环体起点（取命令字节）
0x08077C26: lsl r0,r0,#24 ; lsr r0,r0,#24
0x08077C2A: cmp r0,#0x10        ; 命令上限
0x08077C2E: ldr r5,[pc,#0x1c]   ; 命令表基址
0x08077C38: ldr r1,[r4,#0]      ; 取函数指针
0x08077C3A: bl  0x081B12D8      ; veneer: bx r1  ← 通过函数指针调 ScriptCmd
0x08077C42: bne 0x08077C22      ← 回边，do-while 循环
0x08077C48: bx  r0
```

`0x081B12D8` 处是 `4708 46C0 4710 46C0 ...` = `bx r1 / bx r2 / ...` 的 **veneer（跳板）**，
这是编译器为函数指针表生成的 thunk —— 印证 `sScriptCmdTable[...]()` 的调用方式，
所以全 ROM 扫不到任何 `BL ScriptCmd_xxx`（changebg/waitbgfadein/setbldcnt 均为 0 处 BL）。

> ⚠ **符号表 `pokeruby_jp.sym` 不可信**：
> `08072044 l 00000040 RunAnimScriptCommand ; US=0x080759D0 UNVERIFIED(seg=RedrawMenuCursor)`
> —— 段名标成了 `RedrawMenuCursor`，且它给出的 `0x08072048` 在本轮 0 命中，
> 而实际循环在 `0x08077C20`。

## 三、黑屏机制（推断）

```
存档时：gAnimScriptActive=TRUE，sBattleAnimScriptPtr 指向脚本中间
   ↓
读档后：EWRAM 原样恢复，但指针/关联资源已失效（ptr=0x04030201，落在 IO 区）
   ↓
解释器 sub_08077C20 继续跑 do-while：
   ldr r1,[r4] → bl veneer → bx r1 → 执行 ScriptCmd
   ↓
从野指针 0x04030201 读到的命令字节恒定（open bus）
   → 反复执行 loadspritegfx / changebg / waitbgfadein
   → 指针从不推进（写回 IO 区不生效 / 命令处理器递增无效）
   ↓
背景被反复切换 + 淡入淡出 → 全屏刷黑
```

**为什么「偶发」**：取决于存档那一刻是否正好在动画中。
**为什么日版也复现**：这是 save state 的固有行为，与 ROM 内容无关。

### 一个待解细节

状态块 dump 显示 `+0x00` 与 `+0x20` 的内容**完全相同**（都是 `01 02 03 04`）：

```
+00: 01 02 03 04 00 00 00 00 48 20 07 08 00 01 0f 00
+20: 01 02 03 04 00 01 00 00
```

- `+00` = `sBattleAnimScriptPtr` = 0x04030201（野）
- `+08` = `gAnimScriptCallback` = 0x08072048（**有效**）
- `+20` = `gAnimMoveTurn`=1 / `sAnimBackgroundFadeState`=2 / `sAnimMoveIndex`=0x0403

回调有效而指针失效 ⇒ **不是整块未初始化，是部分被踩**。
`01 02 03 04` 这个递增模式的具体来源尚未定位（可能是 mGBA 读档填充、
也可能是某段循环写入）。**不影响主结论**，留作后续。

### 三条判据（`[ASL]` 前缀）

1. **★野指针** —— `sBattleAnimScriptPtr` 脱离 `0x08xxxxxx`

首命中即报野指针，第 4 次报停滞；正常动画（ptr 在 ROM 且递增）**无误报**。

## 六、方法论沉淀

1. **符号表 `pokeruby_jp.sym` 只能当线索，不能当依据** —— 标 `UNVERIFIED`
   的地址普遍错，且段名会张冠李戴（`RunAnimScriptCommand` 标在
   `RedrawMenuCursor` 段）。凡是要设断点的地址，**必须验证**。
2. **验证函数地址最快的方法**：扫全 ROM 的 `BL` 调用点。有调用点 = 地址对且确实被用；
   0 处 = 要么地址错，要么只走函数指针（`bx`）。
3. **函数指针调用要顺藤摸到 veneer**：编译器会生成 `bx rX` 的 thunk，
   看到 `bl` 跳到一片 `4708 46C0 4710 46C0` 就是它。
4. **采集前先确认「录到了什么」**：本轮如果一开始就看 `[MVA]` 计数，
   能立刻发现 0 命中、白跑一趟，省掉后面全部分析。
   ⇒ **以后开跑后先扫一眼各埋点计数，再决定要不要继续操作**。
