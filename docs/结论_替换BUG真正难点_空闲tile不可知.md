# 结论：替换 BUG 的真正难点 —— 日版引擎「空闲 tile」不可知

> 一份可直接转发给其他 AI / 协作者阅读的定论文档。综合了本项目（GBA 红宝石
> 日版 AXVJ00 汉化）对官方文本引擎的反汇编实证、v6 渲染层现状，以及「高水位
> 分配器」方案的纠偏。
>
> ⚠ 本文是对「tile 号独立分配」早期结论的**更正版**：早期结论把「高水位分配器」
> 当治本，实为偷换问题。本文说明为什么「空闲 tile 不可知」才是根子。

---

## 1. 一句话结论

替换 BUG 的病灶不在 `UpdateTilemap`（写屏幕位置那条腿），而在 tile 号从哪来
（写像素那条腿）。但**"从哪来"这个问题的真正难点是：日版引擎根本不维护 tile
生命周期，所以"哪块 tile 现在空着"在物理上不可知。** 任何声称"知道空闲 tile"
的方案——包括"高水位分配器"——都是在偷换问题；真正可走的路只有两条，都要付出
代价（见 §5）。

---

## 2. 背景：GBA 上"画一个字"永远是两步

GBA 是 tile 模式（mode 0），屏幕上的每个 8×8 像素块，都是靠 tilemap 表项去引用
VRAM 里某块 tile data 才显示出来的。所以"画一个字"恒等于两件事：

1. **写 tile data**：把字模像素存进 VRAM 的某块（charBlock 内某个 tile 号）。
2. **写 tilemap**：把"这块 tile 号"登记到屏幕对应的格子。

所谓"绕过 tilemap 直接画到屏幕"，唯一技术上可行的等价做法是切 GBA 位图模式
（mode 3/4/5，直接写 framebuffer）。但宝可梦整屏的 BG 分层、OBJ、窗口都建立在
tile 模式上，切过去等于毁掉全屏。**这条路硬件上走不通，排除。**

---

## 3. 两条腿各需要什么，哪条会出错

| | 需要什么 | 谁在管 | 现状评价 |
|---|---|---|---|
| 写 tile data | **tile 号** | 官方 `TILE_OFFSET` 游标 | ❌ 每行清零 → 复用 → 替换 |
| 写 tilemap | **屏幕位置** | 官方屏幕光标 `cursorX/Y/TileX/TileY` | ✅ 管得对，保留 |

- `UpdateTilemap`（官方 @0x080036DC）内部是**忠实的**：拿官方屏幕光标算出
  "当前这格该写进 tilemap 的哪个位置"，把喂给它的 `tile` 号写进去。它管的是
  "字显示在屏幕哪"，这条腿官方管得**对**，不必绕过。
- 病灶在第一条腿：`tile = base + TILE_OFFSET`。`TILE_OFFSET` 是官方线性游标，
  **每行 `AddTextPrinter` 都清零** ⇒ 每行都从 `base+0` 开始分配 ⇒ 所有行复用同一批
  tile ⇒ 行 2 的字写进 `base+0` 盖掉行 1。**这才是替换。**

> 推论：就算绕过 `UpdateTilemap` 自己写表项，只要喂进去的 tile 号还是
> `base + TILE_OFFSET` 这套复用号，**替换照旧**——被盖的是 tile data，不是表项。

---

## 4. 核心难点：日版引擎里「空闲 tile」不可知

这是本文与早期结论的关键差异所在。

日版引擎假设**所有字模都在窗口创建时预渲染好、永久常驻 VRAM**，所以它从未实现
"分配 → 回收"这套机制——它不需要。汉化一旦要让汉字"临时找地方画"，就撞上这个
空白：**没有任何实体能告诉你"现在哪块 tile 空着"。**

"找空闲 tile"只有三条路，每条都有硬伤：

| 路 | 做法 | 硬伤 |
|---|---|---|
| 1 · 官方游标 | `base + TILE_OFFSET` | 每行清零 → 给的是假空闲 → 替换（现状） |
| 2 · 跟踪引用 | 扫 tilemap 找没被表项引用的 tile | 引擎**不通知"释放"**，窗口重绘时机未知 → 扫出来的是"假空闲"，写进去照样撞 |
| 3 · 固定区间高水位 | 划一块固定区间，只增不减 | **没解决"何时能回收"**；字符一多吃满 charBlock，之后还是复用 → 替换推迟复发 |

**「高水位分配器」的真相**：它只解决了"行与行之间别清零复用"，**没有解决"tile
何时能回收"**。它是只增不减的游标，字符多到吃满 charBlock 后必须复用，复用即
替换。所以它是**把 bug 触发点从"每行"推迟到"charBlock 用尽时"**，是可接受的
治标，不是治本。早期文档把它包装成治本，是错的。

---

## 5. 两条真正可走的路（都要付代价）

既然"空闲 tile 不可知"，汉化日版就绕不开这个问题，只能二选一：

### 方案 A · 照搬美版"窗口独占 + 每帧重绘"语义

美版引擎之所以能"不知道全局空闲却永不撞"，靠两件日版没有的武器：

- **A1 窗口独占 charBase**：每个文本窗口有自己一块专属 tile 区，别的窗口不用
  你的 tile。于是"空闲"这个词**在窗口边界内重新有了意义**——只需在自己的池子里
  往下排，不用跟全屏抢。
- **A2 每帧全量重绘**：每帧把整块 tileData 从头 blit，写入顺序 = 文本顺序，
  上一帧残影整块覆盖，**不需要"回收"这一说**。

**代价**：要动官方窗口创建 / 重绘流程（`InitWindowTileData` 的 charBase 分配、
每帧重绘调用点）。工程量集中在"给每个文本窗口重新登记/分配 charBase"。

### 方案 A 的关键动作：自研绘制通道（一条龙接管渲染链）

方案 A 不等于"照抄美版代码"，而是**自己实现一条统一的绘制通道，把渲染链从头
到尾接管**——这正是美版 `pokeRS` 的做法：它没有去"修"日版引擎，而是把
`DrawGlyphTiles` 整个换成自己的，字模、宽度、落点全自己说了算。日版四套
textMode（tm0 线性 / tm1 查表 / tm2 缓冲 / tm3 网格，见
`调研_20260828_原生tm0协议与替换BUG根.md` §6.4）的绘制逻辑差异，都可以收进
这一条自研通道里，不再逐窗桥接官方残缺逻辑。

自研绘制通道由五段组成，其中四段是**自给自足的纯计算、完全可控**，一段不可控：

| 段 | 动作 | 可控性 |
|---|---|---|
| ① 取字模 | 索引 → 地址纯函数（ROM 字库 @0x09xxxxxx） | ✅ 可控 |
| ② 算宽度 | 字库墨迹实测，推进量自己定 | ✅ 可控 |
| ③ 混合写入 | `blend_glyph_4bpp` RMW 原语，tile 无所有权 | ✅ 可控 |
| ④ 写表项 | 屏幕位置交官方光标（`UpdateTilemap`） | ✅ 可控 |
| ⑤ **落址** | 写进**哪个 tile 号** = 需要"空闲 tile"信息 | ❌ 不可控 |

- ④⑤ 是"画一个字"缺一不可的两条腿（见 §2/§3）。④（屏幕位置）官方管得对，保留；
  ⑤（tile 号）才是病灶——它依赖"哪块 tile 空着"这个日版不提供的信息（§4）。
- 所以**"按实际宽度精确排放 tile"这句里，"精确"要拆开看**：横向（一个字占几列、
  字距多少）经自研通道后**完全可控**；纵向（写进哪个 tile 号）**绕不开"空闲不可知"**。
  自研通道解决的是横向 + 渲染差异，落址那一问仍需 A1/A2 去补。
- **结论**：自研绘制通道是方案 A 的**必要但非充分**部分。真正不可控、真正要啃的
  是 A1/A2 这两件"补 tile 生命周期"的武器——**不是渲染，是窗口语义。**

### 方案 B · 接受"撞文本"，固定区间 + 高水位

划固定区间 + 高水位，把替换**降级成"吃满才复用、复用才叠"**。赌的是经验假设：
"单个文本窗口的汉字数不会把 charBlock 塞满"。

**代价**：本质是治标，极端场景（长文本、多行）仍会复发；且"叠起来"其实是两个
字像素糊在一个 tile，屏幕上看也看不懂，只是比"整字被替换"稍微好接受一点。

---

## 6. 关于"叠起来比替换好接受"

现状里 blend 混写原语被以 `startPixel=0, width=8` 调用（整列 8 像素全重写），
RMW 退化成"整块覆盖"，所以 tile 号冲突时表现是**替换**。想让冲突退化成"叠加"，
需改成**部分宽度 RMW**（一个 tile 里只写自己那几列、留出别的字占的列）。

但注意：

1. **这是兜底，不是正解。** "叠加" = 两个字像素混在同一个 tile，屏幕上两个字的
   墨迹糊在一起，看也看不懂。
2. **优先级**：先让 tile 号在窗口边界内唯一（方案 A1），替换直接消失；"叠加"
   只作为"tile 空间不够用"时最后的降级手段。

## 7. 术语速查

| 术语 | 含义 |
|---|---|
| tile data | VRAM 里存字形像素的块（charBlock），每 tile 32 字节（4bpp） |
| tilemap | 屏幕格子 → tile 号的映射表 |
| `UpdateTilemap` | 官方函数 @0x080036DC：写 tilemap 表项（管屏幕位置） |
| `TILE_OFFSET` | 官方线性游标（win 偏移 0x18），每行清零 |
| `TILE_BASE` | 窗口 tile 基准（win 偏移 0x16） |
| RMW / blend | 逐像素读改写混合写入；`blend_glyph_4bpp` 是复刻官方语义的像素原语 |
| 高水位分配器 | 自己维护、只增不减、随进程（不随每行）存续的 tile 号游标 |
| 窗口独占 charBase | 方案 A1：每个文本窗口划死一块专属 tile 区 |

---

## 8. 待核实的关键事实（决定方案 A 可控性）

方案 A 是否"顺手能做"还是"得重构窗口创建"，取决于一个尚未核实的事实：

> **日版每个文本窗口现在 `InitWindowTileData` 是怎么分配 charBase 的？有没有
> 空闲的 charBlock 能划给"窗口独占"？**

这是判断 A1 工程量的下一个关键，需反汇编 `InitWindowTileData` 定案，不能靠推断。
