# 评估_20260829 — text 重构（8-28 textMode 分派制）合理性反汇编复核

> 证据：原盘 AXVJ00 反汇编（capstone）+ 两轮 gdb_patcher 日志 + bak/text_original
> 对照 + 设置菜单三轮 BUG 实测。结论按「立住 / 有错 / 待验证」三级给出。

## 一、反汇编新发现（评估过程中推翻/修正的既有认知）

### N1. ⛔ 已作废：原调研文档的 lower=upper+1 才是对的（2026-08-29 gdb 推翻）
我此前把 `FontSub[0]@0x08003584` 的
```
lsls r2,r2,#0x10            ; ← upper 已被移到高 16 位
movs r3,#0x80 ; lsls r3,#9  ; r3 = 0x80<<9 = 0x10000（不是 0x100！）
adds r2,r3 ; lsrs r2,#0x10  ; 高16位 +1
```
误读为 `lower = upper + 0x100`。两处算术/语义错误：① `0x80<<9 = 65536 = 0x10000`
≠ 0x100；② 加 0x10000 作用在已左移 16 位的 r2 上，等于**高 16 位 +1**。

**gdb 铁证**（LR=0x0800359C = FontSub[0] 的返回点，89 条原生调用）：
`u=1,l=2` / `u=33,l=34` / `u=49,l=50` / `u=111,l=112` / `u=349,l=350` —— **差恒为 1**。
UpdateTilemap 全 519 条差值分布：**469 条差=1（tm1）、50 条差=30（tm3 grid）**，
无一条 +0x100。

→ 字库布局 = **每字模 2 个连续 tile**（upper=1+2g，lower=2+2g），与
InitWindowTileData 实测（每次写 2 tile、VRAM 指针 +0x40）吻合。

**代价**：v4/v4.1 的「偶数槽安全」建立在这个错误前提上——把中文搬到偶数槽，
实际是搬到**字模的下半行 tile**，直接破坏字模。这是 v4 全屏"1"、v4.1 继续恶化
的深层原因。教训：**反汇编的立即数必须验算，且必须与运行时数据交叉验证**，
单一证据源下的"修正"风险极高。

### N2. ⛔ 同上作废：tm0 表项也是 lower = upper + 1
不存在 tm0/tm1「上/下半行分离」布局；只有 tm3 是 grid（idx+30）。

### N3. UpdateTilemap@0x080036DC 语义定案
表项值 = `tile | (win[0xF]<<12)`（palette 拼高 4 位）；lower 表项写在
**tilemap 下一行同列**（表项地址 +0x40 字节）。表项「值差」与「地址差」是两回事：
值差由调用方决定（实测 tm1 为 +1、tm3 为 +30），地址差恒为 +0x40。

### N4'. 修正后的风险：字库占满 charBase，但**实际引用极其稀疏**（数据驱动解）
预渲染写满 [1,0x201)（512 tile），字库在形式上占满整个 charBase 2。
但**设置菜单实际只引用 22 个字模**（实测原生 upper 去重集合）：
```
1 33 49 111 119 323 325 327 329 331 333 335 337 339 345 349 369 397 409 439 447 451
```
每字模占 (g*2+1, g*2+2) 两个连续 tile → 实际占用仅 44 个 tile。
**安全连续块**：`[121, 322]`（202 tile）为最大块，另有 [3,32]、[51,110]、
[453,512] 等小块。→ 中文只要落在 [121,322] 内即零冲突，而非依赖"奇偶"猜测。
（注：此集合是**设置菜单场景**实测，其他 tm1 场景需各自采集。）

## 二、重构五项决策逐项评估

| # | 决策 | 判定 | 依据 |
|---|---|---|---|
| 1 | 按 textMode(win[0x0A]) 分派，删场景识别 | **✅ 立住** | FontFuncTable 恰 4 项（0x081BB3AC：0x08003569/0x0800360D/0x0800338D/0x08003495），textMode 就是原生分派键；旧版 scene_* 启发式（tpl[1]、cursorY 阈值）本质是在反推它，穷举不可持续。三轮 BUG 无一源于分派制本身 |
| 2 | 四套协议逐条复现、只换「绘制」 | **✅ 立住** | tm1（查表+0x1B++、零 win[0x18] 零 VRAM 写）、tm0（win[0x16]+win[0x18]<<5 → dst，0x8003630，表项 +0x100）、tm2（win[0x20]+=0x40）、tm3（+2+col+row*30）全部反汇编吻合；仅文档两处 +1 笔误（N1/N2） |
| 3 | **tm1 中文「借用线性分配」** | **❌ 重构最大错误** | 借用 win[0x18] 本身安全（tm1 确实零读写），错在**线性分配模式**与 tm1 场景结构冲突：gdb 实证设置菜单每行选项是独立 ITP 会话、原生每会话把 win[0x18] 重置为 0x100+(curTX-1)*2（两轮日志全部样本吻合），线性游标的载体每会话被清。三轮 BUG（v0 行间碎片 / v1 持久游标铺满全屏 / v2 槽轮转串换）全部由此决策派生 |
| 4a | 删页游标制 | **✅** | 其互踩根因是按 charBase 记账粒度错误；且它依赖的场景识别同被删 |
| 4b | **删 scene_remap_tile（UI 章重映射）** | **⚠️ 未验证就删** | 调研 §7.4 自己列为残余风险但未实测。UI 章（▶ [0x1E0,0x1E1]、图标 [0x1E8,0x1FF]）客观存在；v3 中文区 [0x100,0x190) 暂未撞上属区间巧合。另据 N4，字库下半区重叠才是更大暴露面 |
| 5 | 非中文也走相位（native_via_phase） | **✅** | 28.PNG「假名被汉字吞掉」实证；startPixel 移位对所有字符一致才不覆盖相邻字 |

### 与 bak 的对照结论
bak 的场景识别代码不值得恢复，但它的**两个哲学判断是对的**，且都被重构丢掉：
1. **位置式寻址优于分配器**（menu_mode2 走 grid：tile 位置由窗体 cursor 决定，
   重绘幂等，无游标可漂移）——v1/v2 的失败本质是分配器路线的失败，v3 的
   确定性分区（base=f(curY,curX)，无状态）实际上是把位置式哲学手工搬回 tm1。
2. **实测章位必须声明式保留**（scene_remap_tile / 槽位表）——删代码可以，
   知识应沉淀为数据表，而不是连同机制一起丢。

## 四、建议

1. **短期**：维持 v3 确定性分区（方向正确：无分配器、幂等）；若残留显眼，
   会话开始时清子区 8 tile（256B 写，代价可接受）。
2. **中期正解**：为 tm1 中文重建**位置式落址**——先 gdb 采设置菜单 BGCNT
   （charBase）与 tilemap 表项值域，确认「tile 索引=格子索引」是否对 tm1 窗
   成立（tm3 已证成立）。成立则中文直接写格子 VRAM，彻底摆脱自由区假设（R1/R2/R4 一起消解）。
3. **文档**：修正调研_20260828 §6.1/§7.2 的 +1 笔误（本文件 N1/N2）；
   bak 的场景启发式实测数据（screen_shop_bag 的 tb 区间等）沉淀为章位表。
4. **纪律**：今後删除旧机制前，调研文档的「残余风险」节必须逐条实测关闭，
   不得带着未关闭风险合入（4b 的教训）。
