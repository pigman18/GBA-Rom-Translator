# 调研 2026-08-27 — pokeRS「类12px」机制全解与日版 AXVJ00 接入可行性

> 目的:固化对 `tools/Pokemon_GBA_Font_Patch/pokeRS`(宝可梦红蓝宝石美版中字增益优化版)的
> 全链路分析,以及把该方案接到日版 AXVJ00 的可行性结论。
> 所有反汇编均为静态分析(capstone),证据可复核;标注体系:
> 【已验证】本轮一手反汇编/字节比对;【sym 前人结论】`configs/POKEMON_RUBY_AXVJ00/symbols/pokeruby_jp.sym`
> 的 UNVERIFIED/DISPROVED 标注(2026-08-22 排查);【待标定】尚未完成。

## 0. 一句话结论

pokeRS 是**纯补丁工程**(armips 覆盖三个引擎函数 + 外挂字库),其"12px"是
**16×16 四 tile 容器 + 横向 12px 口径**的产物——不是任何 ROM 原生能力。
日版 AXVJ00 缺少它的两个核心注入点(`GetGlyphWidth`/`GetStringWidth` 未编译),
第三个(`DrawGlyphTiles`)在日版根本不存在 → **不可原样移植**;
但其**字库格式(128B×7168)、四象限几何、hook 单点思想**可被现有
`render_inplace12` + `PrintNextChar_hook` 路线吸收(该路线本就是 pokeRS 的日版同构物)。

## 1. pokeRS(美版基准)完整链路

工程:`tools/Pokemon_GBA_Font_Patch/pokeRS/`,`main_R.asm` 编排 armips 构建。

### 1.1 字库资产【已验证】

| 文件 | 大小 | 内容 |
|---|---|---|
| `graphic/fonts/PokeRSFontChsNormal(0xE0000).bin` | 0xE0000 = **7168 字模 × 128B** | 4bpp,每字模 4 tile = 16×16 容器,布局 `[TL][BL][TR][BR]` 各 32B |
| `PokeRSFontChsSmall(0xE0000).bin` | 同上 | 小字窗用 |
| `PokeRSFontChsSym(0x240).bin` | 576B | 中文符号字库 |

- 字库放置:**ROM 扩容区**(非原 8MB 内):`PokeRSFontChsNormal=0x09000000`、
  `Small=0x09100000`(main_R.asm 注释"扩容至32MB");hack 函数代码藏于
  `gMiscBlank_Gfx`(HackFunctionAddresses equ 0x082089DC);
  Sym 库直接覆写 `gFont3LatinGlyphs + 0x40*0x36`(0x08EA39C4)某段。
  本项目 `chinese_text.c` 的 `CHS_FONT_GLYPH_MAX 7168` 即来自这套容量约定。
- 墨迹实测(抽样 136 个字模统计行分布):
  Normal 墨迹集中在容器行 2–15(**≈12px 高**,上部留白 2 行);
  Small 集中在行 6–15 + 少量下垂(**≈10px 高**)→ HP框补丁注释
  "32 会遮掉 10px 汉字字体上半部分"与此吻合。
- 点阵可视化样例(Normal glyph3-5,UP/DN 各 8 行)= 标准 12px 汉字形态。

### 1.2 三内联 bl 注入点(main_R.asm / src/HookInOrigin)

| Hook | 美版地址 | 目的 |
|---|---|---|
| `.org GetGlyphWidth+2` | 0x080048EA | 中文宽度查询替换 |
| `.org GetStringWidth+0x100` | 0x08004CCC | 含中文句宽计算替换(函数体中部 hook,push lr/bl/pop r0/mov r14,r0/b 回 +0x112) |
| `.org DrawGlyphTiles+2` | 0x08006876 | 渲染替换 |

### 1.3 核心绘制 DrawGlyphTilesChinese(src/HackFunction/DrawGlyphTilesChinese.s)

中文命中条件(全部满足才接管,否则退回原函数):
1. `win->fontNum != FONT_BRAILLE`;
2. `win->language != LANGUAGE_JAPANESE`;← 日版移植必须翻转/删除此门(pokeRS 的第 6 关卡)
3. glyph 参数 ∈ [1,0x1E] 且 ≠0x06、≠0x1B(双字节伪编码首字节区 = 美版重音字母空隙);
4. `win->text[win->textIndex] ≤ 0xF6`(双字节次字节);

字形索引:`((glyph 调整值)<<8) | 次字节`(首字节按 [1..5]/[7..1A]/[1C..1E] 区间分别 -1/-2/-3),
×128 取字模;fontNum∈{0,3}→Normal 库,{1,2,4,5}→Small 库。

绘制流程(width 恒锁 8,startPixel=(left+cursorX)&7,借原生
`DrawGlyphTile_ShadowedFont` + `GetCursorTileNum` + `UpdateTilemap`):

```
TL(win,c0,r0) → BL(c0,r1) → UpdateTilemap
→ win->cursorX += 8 → win->[0x1C](tileDataOffset)+=2(textMode!=MONOSPACE 才加)
→ TR(c1,r0) → BR(c1,r1)
```

**游标总步进拼图**(为什么叫"类12px"):
外层原生 `PrintGlyph_TextMode0` = `AddToCursorX(win, GetGlyphWidth())`
(pokeruby src/text.c:2571-2584),而 `GetGlyphWidthChinese` 对中文返回
**4(Normal)/2(Small)**:
- Normal:手动 8 + 返回 4 = **12 px/字**
- Small :手动 8 + 返回 2 = **10 px/字**

### 1.4 度量口径 GetStringWidthChinese

双字节汉字:Normal **+=12**、Small **+=10**,并 `i++`(跳过次字节)。
即菜单居中/换行判定全部按 12px(大字)/10px(小字)口径。

### 1.5 场景级附带 patch(非文本引擎核心,移植时逐场景搬迁)

- `UpdateNickInHealthbox+0x1EA`:HP框名字 gfx 拷贝 32→20/24 字节,防遮汉字上沿;
- `UpdateSafariBallsTextInHealthbox+0x30`:狩猎球名(r1=4,"狩猎球"3 字仅占 4 tile);
- `UpdateLeftNoOfBallsTextOnHealthbox+0x5A`:剩余球数;
- 寄放系统持有物:`PrintDisplayMonInfo+0x11A`(r3=0x12)、`sub_8097F58+0x2E`(r0=0x9C)坐标调整。

### 1.6 编码空间

b1 ∈ {0x01–0x1E}\{0x06,0x1B} × b2 ≤ 0xF6 ⇒ 容量 ~30×246≈7380,实际 7168。
安全性前提:**美版 charmap 中 01–1E 是重音西文字母('À'=01…'ì'=1E),正文不出现**。

## 2. 日版 AXVJ00 引擎现实

背景代差见 `docs/START_HERE.md` §3.5、上一轮调研(RS 初代引擎 cell 写死 16px 双 tile、
JP 与 US 的 font0 字库逐字节相同等)。本轮聚焦"接缝存在性":

### 2.1 三个注入点的存亡【sym 前人结论 + 本轮独立复核】

| 美版函数 | 日版候选(sym) | 结论 |
|---|---|---|
| GetGlyphWidth (US 0x080048E8) | 0x08004228 | **DISPROVED**:实为 {u32,u32} 表查映射(表@0x081BB8D4);日版打印步进由打印路径硬编码 |
| GetStringWidth (US 0x08004BCC) | 0x0800450C | **DISPROVED**:0x450C 非函数起点;全 ROM 无 FC 控制码 switch → 该函数未编译 |
| Text_GetStringWidthFromWindowTemplate | 0x08003770 | DISPROVED(实为已验证 GetGlyphTilePointers@0x3730 体内) |
| DrawGlyphTiles (US 0x08006874) | sym 曾列 0x08005178 | **本轮证伪**:反汇编为控制码处理器(strh 入 IWRAM literal、cmp r7,#0xC4 等);且 BL 全图扫描 `bl 0x08005178` 零调用者 |
| 对照组 UpdateTilemap JP=0x080036DC VERIFIED | — | BL 扫描有 **7 个真实调用方**(0x080034D6/355A/3598/35BC/35DC/3600/3EAE)——扫描方法有效性的对照证明 |

原因:美版为西文比例字体(VWF 1–8px/字符)需要 per-char 宽度查询;日版全等宽假名,
宽度机制被编译期裁除。根因与 `docs/START_HERE.md` 逆向教训一致:**不要假设日美同构**。

### 2.2 日版真实接缝清单【已验证 / 待标定】

- `PrintNextChar(=ProcessCurrentChar)` **JP=0x080032F8 VERIFIED**(0xA0)
  —— 项目符号表锚注:US PrintNextChar=0x08002FE0,delta +0x318。
  这是每字符主入口,**就是现行 PrintNextChar_hook 所站点**,功能地位 ≙ pokeRS 的 DrawGlyphTiles+2。
- `HandleExtCtrlCode`@0x08003398 及 ExtCtrlCode_* 家族齐全(0x080033C4–0x08003554)。
- 调色展开拷贝原语 **@0x080038A0**【已验证】:签名 `(src, dst, fg, bg, shadow∈栈)`
  按 nibble 解析,0xF0/0xE0 为阴影/背景特殊码 —— FRLG/E 血统"解码进缓冲→二次拷贝入窗"
  风格;pokeRS 把 128B 字模按 `[TL][BL][TR][BR]` 四块 32B 连喂这类原语的画法在此逐块对应。
- 窗口写入现场(0x08003E70 区 caller):`ldrh r0,[r5+0x16]; adds #0xfe`(tile 计数 -2)
  → `<<5` 定 tile;两次 `bl 0x080038A0`(dst 步进 +0x20 = upper/lower);随后 `UpdateTilemap`。
- 由此读出的日版结构偏移(**不等于美版!**):`[[r5]+0x0C]`=窗 tileData 基址、
  `[r5+0x16]`=u16 tile 计数(±2 步进)。完整 Window/打印状态块字段表【待标定】。
- 居中/测宽的现实替代:sym 另有
  `GetStringWidthInMenuWindow` JP=0x0806FFC0、
  `GetStringWidthInTilesForScriptMenu` JP=0x080B1690(均 UNVERIFIED,菜单专用、等宽口径);
  或自算(CHS×12 + 其他×8,vfw12 注释已声明居中偏差可接受)。
- 编码冲突(硬约束):日版 `'あ'=0x01` 起(charmap 第159行;`ぁ`=2F、`ィ`=80),
  假名正铺满 pokeRS 双字节首字节区 ⇒ **pokeRS 编码不可照搬**,沿用本项目自有编码
  (chinese_text.c 伪 glyph F900/F980/slot 家族)。

### 2.3 判定

- ❌ pokeRS 三 hook 点原样移植:两个不存在、一个函数本身不存在,Window 布局不同,编码区间冲突。
- ✅ 可吸收:128B×7168 字库格式 + `[TL][BL][TR][BR]` 布局(`PokeRSFontChs*.bin` 可原样 incbin,
  `Convert1bppTo4bpp.s` 构建链可搬);四象限 12px 几何口径;"单点接管 + 手工步进"架构
  (pokeRS 自己也是 cursorX+=8 + tileDataOffset+=2 + 返回值凑 12 的组合拳)。
- ✅ 现行路线(PrintNextChar_hook + render_inplace12)就是上述吸收后的正确形态;重构时
  以五文件目标收敛即可(docs/REMOVE_F980_HOOK_REFACTOR_REQ.md 相关诉求见该文件)。

```
src/text/
├── entry.s / hook_origin.s        不动
├── PrintNextChar_hook.c           状态机 + 步进/落位(f900/f980 判别入口)
```
