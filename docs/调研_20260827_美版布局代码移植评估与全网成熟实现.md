## 0. 一句话结论

- 布局代码:**二进制级搬运不划算、C 源算法级移植可行且正是重构该走的路**(详见 §2 路线表)。
- 全网:**"日版 RS 无宽度函数怎么补"没有任何公开解——我们的自绘路线全网范围看是孤例**;
  最有价值的两个参照系(源码层 = rh-hideout-chinese,美版二进制层 = Wokann/Pokemon_GBA_Font_Patch)
  本项目均已踩点,剩余收益主要是标点复用与字库工具链。

## 1. 本轮新解剖:日版打印真实形态(为何美版布局引擎接不上)【已验证】

`PrintNextChar` @0x080032F8(VERIFIED 锚点,0xA0)全貌:

```
textIndex(u16)@ [win+0x14]   ; text 指针 @ [win+0x10]
r3 = *ptr                      ; 取字符
c−0xFA ≤ 5 ?                   ; 扩展控制码 = 自家 0xFA–0xFF 六路 jump table(vtable)
   FB → [win+4]=7/6 (状态机字段)
   FC/FD → bl 0x08003F4C 后 [win+4]=8/9
   FF → bl 0x08003110(HandleExtCtrlCode 家族,色值取自 [win+0xC/0xD/0xE])
default → 按 [win+0x0A](fontNum)<<2 选 FontFunc 表(@0x081B12DC, ROM 高区)
          bl <FontFunc>(win, char)     ← 绘制 + 等宽步进全在里面(硬编码)
返回值 = 字节步进(普通字符恒 1),不是像素
```

三条推论:
1. **主渲染链从不查询字符宽度**:每字号一个固定 FontFunc,sym 前人注释
   "日版打印步进由 FontFunc 硬编码"得到直接反汇编证实 ⇒ 美版式 `GetGlyphWidth`
   在日版主链上**没有自然挂点**。
2. 日版控制码体系(`FA–FF` 单字节)与美版(`FC`+code 双字节)完全不同
   ⇒ 美版 `GetStringWidth` 的转义解析循环不可复用;好在译文码制完全由我们自己写,
   只需按用到的几个码位写窄解析。
3. 唯一正确的介入点仍然是 `PrintNextChar` 层(现行 `PrintNextChar_hook.c` 已站住),
   之后走自己的布局库——即 pokeRS "hook 单点 + 手工步进"思想的延续。

美版函数耦合面量化(决定二进制搬运成本)【已验证】:
| 函数 | 访问的 Window 字段 | 其他依赖 |
|---|---|---|
| `GetGlyphWidth`(US 0x080048E8) | `[win+0x01]fontNum` `[win+0x02]language` `[win+0x0E]spacing` — 共 3 个 | sFont*Widths/sFonts 宽度表指针池 ×N |
| `DrawGlyphTiles`(US 0x08006874) | `[win+0x00/01/02/10/12/24]` — 共 6 个 | callee: GetGlyphTilePointers(**日版 VERIFIED 存在@0x3730**)/DrawGlyphTile_{Un,}ShadowedFont(sym 候选 0x039B0/0x03F84 UNVERIFIED)/sGlyphBuffer IWRAM 地址 |

理论上"incbin 美版两函数 + 改 9 个字段常数 + 重定向 literal pool"可控;
**但搬进来仍无人调用**——要生效必须同时接管 FontFunc 虚表与
ProcessCurrentChar 步进,绕一圈回到 hook 自绘路线。故二进制搬运判否。

FRLG/Emerald 第二代引擎的可取处:高度参数化
(`struct FontInfo{maxLetterWidth,maxLetterHeight,lineSpacing}`)+
`CopyGlyphToWindow` 四象限按任意 w≤16/h≤16 切 tile;Emerald 日文本体六字体中
font0=8×12、fonts2–5=高12(假名字库原生 12px 格,`asm/text.s` 解码器写高度 0xC)
即"官方原生 12px"先例。⚠️ 只摘坐标数学(几十行 C),**不要搬整套 TextPrinter/
Window 体系**:全局状态依赖 + game.bin 为 freestanding 平坦镜像、全局落 ROM 写无效
(`chinese_text.c` 头注已记此坑)。

## 2. 三条路线评估

| 路线 | 内容 | 成本 | 判定 |
|---|---|---|---|
| A. 二进制抽搬美版 RS 布局函数 | incbin blob、改 9 个字段常数、pool 重定向、确认 3 个 callee | 中 | ❌ 无挂点生效不了,还要换 FontFunc 虚表 |
| **B. C 源级移植 pret pokeruby `src/text.c` 布局三件套**(GetGlyphWidth 宽度表机制 / DrawGlyphTiles 双 tile 语义 / GetStringWidth 循环骨架)进 `hook/src`,常量改日版标定偏移 | 低-中 | ✅ **推荐**:权威算法替换手写散落逻辑,天然落位 text_render.c 的 `GetStringWidth()` 服务 |
| **C. 摘 FRLG/E `CopyGlyphToWindow` 几何 + FontInfo 高度思想** 进 render_inplace12 | 低 | ✅ 与 B 叠加,为将来多字号档留形 |

## 3. 全网调研五类发现

### 3.1 pokeemerald 中文版 —— 最大发现
- **[rh-hideout-chinese/pokeemerald-expansion](https://github.com/rh-hideout-chinese/pokeemerald-expansion)**:
  GitHub API 核实,建于 2022-04,push 至 2026-08-24(每日跟踪上游),56 stars/16 forks,
  附 [CONTRIBUTING_ZH.md](https://github.com/rh-hideout-chinese/pokeemerald-expansion/blob/master/CONTRIBUTING_ZH.md)、
  [pmcenter 发布帖 tid=113279](https://www.pmcenter.cn/forum.php?mod=viewthread&tid=113279)、
  [Gitee 镜像](https://gitee.com/bubble128/pokeemerald-expansion_chinese)(停 1.11.1)。
- 逐文件核实的技术形态:`src/text.c` 双字节合并 `(currChar<<8)|nextChar` → `IsChineseChar`
  → `DecompressGlyph_Chinese`;**GetStringWidth 改造为汉字先走 `GetChineseFontWidthFunc`**;
  核心独立成 `src/chinese_text.c`:四块 8×8 子块拼 cell、Normal 12px / Small 10px 宽度
  switch 硬编码;字模 `graphics/fonts/chinese_*.png` 经 .latfont 构建;自定义双字节序号制
  (高字节 0x01–0x1E 排除 06/1B,≈7000 槽,非 GBK);中文标点单字节占位复用 Latin 表。
- **本项目 `configs/.../hook/src/chinese_text.c` 文件头注释所写 upstream 正是这个 repo**
  ——独立调研与既有 vendored 代码互证。"双字节判定 → DecompressGlyph_Chinese →
  GetStringWidth 宽度挂接"三段式即注入层蓝图;标点复用 Latin 表的做法可直接借来省一套符号字模。
- ⚠️ 该 fork 未带 license 头;上游 pokeemerald-expansion 为 GPL-3.0,vendored 沿用需保持一致。
- 个人 fork [kuchannn/pokeemerald-expansion](https://github.com/kuchannn/pokeemerald-expansion)(仅记录)。
