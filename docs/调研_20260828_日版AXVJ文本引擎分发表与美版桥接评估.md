# 调研 2026-08-28 — 日版 AXVJ 文本引擎分发表实测 / 美版桥接可行性 / pokeRS 点位不可移植

> 目的：回答两个问题 —— (A) 能否接入 `tools/pokeruby/src/text.c` 做"完全版桥接"；
> (B) 能否模仿 pokeRS 只 hook 少量函数完成 12px 汉字打印。
> 方法：**全部静态**（capstone 5.0.7 反汇编 + ROM 字节比对），未启动模拟器。
> 复核工具：`scripts/dis_axvj.py`（本轮新增，见 §6）。

## 0. 三句话结论

1. **方案 A（接入美版 text.c 完全桥接）否决。** 决定性理由是 **ABI 不同构**：
   pokeruby `struct Window`（即 TextPrinter）与 AXVJ 打印块字段**全错位**
   （见 §2.1 对照表）→ 4393 行里每个 `win->x` 都会读写错字段。
2. **方案 B 的"精神"成立、"点位"要换。** 日版没有 pokeRS 的三个注入点
   （GetGlyphWidth / GetStringWidth / DrawGlyphTiles），但**日版自己有一套与美版
   同构的两级分发表，而且是 ROM 里的纯指针**——改数据即可换实现，比 pokeRS
   在函数体中间插桩更干净。
3. **hook 数早已是 pokeRS 量级**（本项目 ≈10 处 vs pokeRS ≈8 处）。
   真正的问题不是 hook 太多，而是**被 hook 的那个函数里手写了太多引擎该干的事**。

### 0.1 对上一轮结论的修正（重要）

上一轮口头结论中我把 tm0 的内层调用说成 `0x08002D50`，**错了**。
capstone 复核后正确值是 **`sub_8003520`（0x08003520）**。
（我手工解码 Thumb-2 BL 的 `imm32` 时十进制算错了一位，差 0x7D0。）
`0x08002D50` 是另一个函数的中段，与 tm0 无关。本文所有地址均以 capstone 输出为准，
可用 `scripts/dis_axvj.py` 逐条复核。

## 1. 日版原生文本引擎全貌（本轮一手反汇编定案）

### 1.1 每字符主循环

`PrintNextChar` @ **0x080032F8**，**仅 144 字节**（0x080032F8–0x08003387）：

```
080032F8  push {r4, lr}
080032FA  mov  r4, r0                     ; win
080032FC  ldrh r0, [r4, #0x14]            ; textIndex
080032FE  add  r1, r0, #1
08003300  strh r1, [r4, #0x14]            ; textIndex++
08003302  lsl  r0, r0, #16 ; lsr r0,#16   ; u16 回绕
08003306  ldr  r1, [r4, #0x10]            ; text
08003308  add  r1, r1, r0
0800330A  ldrb r3, [r1]                   ; c
0800330C  mov  r0, r3 ; sub r0,#0xFA ; cmp r0,#5 ; bhi → 可印分支
08003314  ldr  r1, [pc,#8]                ; = 0x08003324 跳转表
08003318  add r0,r1 ; ldr r0,[r0] ; mov pc,r0
```

跳转表 @0x08003324（6 项，索引 = c − 0xFA）：

| 码 | 目标 | 语义 |
|---|---|---|
| FA | 0x08003354 | `bl 0x0800304C`（DrawInitialDownArrow）→ state = 9（WAIT_SCROLL） |
| FB | 0x0800334A | `bl 0x0800304C` → state = 8（WAIT_CLEAR） |
| FC | 0x08003362 | `bl 0x08003110`（**HandleExtCtrlCode**）→ 返回其返回值 |
| FD | 0x08003342 | state = 7（PLACEHOLDER） |
| FE | 0x08003346 | state = 6（NEWLINE） |
| FF | 0x0800333C | state = 0（END）→ 返回 0 |

可印分支（c < 0xFA）：

```
0800336E  ldr  r0, [pc,#0x18]   ; [0x08003388] = 0x081BB3AC  FontFuncTable
08003370  ldrb r1, [r4, #0x0A]  ; textMode
08003372  lsl  r1, r1, #2
08003374  add  r1, r1, r0
08003376  ldr  r2, [r1]         ; FontFuncTable[textMode]
08003378  movs r0, r4           ; win
0800337A  movs r1, r3           ; c
0800337C  bl   CALL_VIA_R2      ; = 0x081B12DC
08003380  movs r0, #1           ; return 1
```

> 这与现役 `PrintNextChar_hook.c` 里的 `AXV_STATE_*` 枚举、`FC_*` 定义、
> 各分支返回值**逐一吻合** —— 现役实现是原生语义的忠实重建，行为上没有偏差。

### 1.2 两级分发表（**本轮最重要发现**）

| 表 | 地址 | 项数 | 内容 |
|---|---|---|---|
| `FontFuncTable` | **0x081BB3AC** | 4 | tm0 `0x08003569` / tm1 `0x0800360D` / tm2 `0x0800338D` / tm3 `0x08003495` |
| `FontSubTable` | **0x081BB3BC** | 7 | font0,3 `0x08003585` / font1,4 `0x080035A1` / font2,5 `0x080035C9` / font6 `0x080035E5`（盲文） |

ROM 原字节：

```
081BB3AC  69 35 00 08  0D 36 00 08  8D 33 00 08  95 34 00 08
081BB3BC  85 35 00 08  A1 35 00 08  C9 35 00 08  85 35 00 08
081BB3CC  A1 35 00 08  C9 35 00 08  E5 35 00 08  08 04 01 00   ← 第 8 word 非指针，表长=7
```

**引用点（全 ROM 扫描，各 2 处，均为 literal pool 取址，无 memcpy → ROM 直改有效）**：

| 表 | 引用位置 | 说明 |
|---|---|---|
| 0x081BB3AC | 0x080032B0 | 另一条打印路径（`FontFuncTable` 的第二用户，**未标定**） |
| 0x081BB3AC | 0x08003388 | `PrintNextChar` 的 literal pool |

### 1.3 四种 textMode 的原生实现（全部反汇编定案）

**tm0 @0x08003569（线性滚动光栅，对话/战斗详情）**

```c
void tm0(win, glyph) {
    sub_8003520(win, glyph);          // 0x08003520
    win->tileDataOffset(0x18) += 2;   // 8x16 = 2 tile
    win->cursorTileX(0x1B)   += 1;
}
```

**tm1 @0x0800360D（等宽，菜单/队伍）**

```c
void tm1(win, glyph) {
    FontSubTable[win->fontNum(0x0B)](win, glyph);
    win->cursorTileX(0x1B) += 1;
}
```

**tm2 @0x0800338D（指针缓冲，血条/名字）**

```c
void tm2(win, glyph) {
    sub_8003630(glyph, win->buffer(0x20), win->fontNum(0x0B),
                win->fg(0x0C), win->bg(0x0D), win->shadow(0x0E));
    win->buffer(0x20) += 0x40;        // 2 tile
}
```

**tm3 @0x08003495（固定网格，菜单/对话主窗）**

```c
void tm3(win, glyph) {
    sub_8003464(win, glyph);
    win->cursorTileX(0x1B) += 1;
}
```

### 1.4 两个可直接复用的官方原语（**方案的核心资产**）

**① `sub_8003520(win, glyph)` — 定位 + 绘制 + 写表项，一条龙**

```c
void sub_8003520(win, glyph) {
    dst = template->tileData(0x0C)
        + ((win->tileDataStartOffset(0x16) + win->tileDataOffset(0x18)) << 5);
    sub_8003630(glyph, dst, win->fontNum(0x0B), win->fg(0x0C),
                win->bg(0x0D), win->shadow(0x0E));
    t = win->tileDataStartOffset(0x16) + win->tileDataOffset(0x18);
    UpdateTilemap(win, t, t + 1);
}
```

**② `sub_8003630(glyph, dst, fontNum, fg, bg, shadow)` — 字形 → dst，`dst` 是参数！**

```
08003630  push {r4-r7,lr} ; sub sp,#0xC
0800363E  ldr r0,[sp,#0x28]   ; bg     （栈参）
08003640  ldr r1,[sp,#0x2C]   ; shadow （栈参）
          ; r0=glyph  r1=dst  r2=fontNum  r3=fg
08003660  bl  GetGlyphTilePointers      ; (fontNum, glyph, &upper, &lower)  ← 4 参，无 language
08003664  cmp r5,#6 ; bhi ...           ; fontNum 0..6 跳转表
          ... CopyGlyph1bppTo4bpp(upper, dst,       fg, bg)
          ... CopyGlyph1bppTo4bpp(lower, dst + 0x20, fg, bg)
```

调用点三处，全部实证：

| 调用者 | dst |
|---|---|
| `sub_8003520`（tm0） | VRAM `tileData + (tileBase+tileOffset)<<5` |
| `tm2`（0x0800338D） | `win->buffer`（+0x20） |
| `InitWindowTileData`（0x08002AF4 分支） | `tileData + startOffset*32 + glyph*64`（预渲染 256 字 × 2 tile） |

> **这是"少写代码"的关键**：官方的字形渲染原语把 dst 做成了参数，
> 意味着同一个函数既能画进 VRAM、也能画进内存缓冲、也能预渲染字体。
> 现役引擎在 `text_render.c` 里手写了 `vram_tile` / `map_at` /
> `GetCursorTileNum_Linear` / `GetCursorTileNum_Mode2` 等一堆等价物。

**③ `sub_80034A8(win)` — tm3 的 tile 号计算**

```c
t     = win->cursorTileX(0x1B) + (win->cursorX(0x1A) + 2)
      + win->tileDataStartOffset(0x16) + row * 30;      // row = cursorY(0x1C)+cursorTileY(0x1D)
lower = (row + 1) * 30 + ...;
UpdateTilemap(win, t, lower);
```
印证了 `game.h` 的 `CHS_TILE_GRID_W 30`。

### 1.5 `FontSubTable` 三项的签名（纯净，可直接调用）

```c
/* 0x08003585，font0/font3 —— 纯 tilemap 写，零像素绘制 */
void FontSub_f0_f3(win, glyph) { UpdateTilemap(win, tileBase + glyph*2, tileBase + glyph*2 + 1); }

/* 0x080035A1，font1/font4 */
void FontSub_f1_f4(win, glyph) { UpdateTilemap(win, tileBase + FontType1Map[glyph*4],
                                                    tileBase + FontType1Map[glyph*4 + 1]); }
```
> 注意 `FontType1Map` 步长是 **4 字节/项**（`lsls r3,r3,#2`），不是 2。

**`sub_8003EE0`（FontSubTable 的第二用户，箭头擦除，【待标定】）**

```
08003EF0  bl sub_8003964(win) ; if (==1) return;
08003F00  switch (win->textMode(0x0A)) {
          case 0: sub_8003520(win, 0); break;      // 画空格擦 ▼
          case 1: 0x08003F24  ...                  // 【待反汇编】
          case 2: return;
          case 3: 0x08003F3C  ... FontSubTable ... // 【待反汇编】
          }
```
形态与 pokeruby `TryEraseDownArrow` 对应。**替换 FontSubTable 前必须标定此函数**，
否则擦箭头会走错路径。工作量：约 0x60 字节。

## 2. 方案 A：接入美版 text.c —— 否决

### 2.1 决定性证据：TextPrinter 布局全错位

| 字段 | pokeruby（US） | AXVJ（JP，`include/game.h`） |
|---|---|---|
| template | 0x2C | **0x00** |
| state | 0x16 | **0x04** |
| downArrowCounter | 0x18 | **0x06** |
| delayCounter | 0x0D | **0x09** |
| textMode / fontNum | 0x00 / 0x01 | **0x0A / 0x0B** |
| fg / bg / shadow | 0x03 / 0x04 / 0x05 | **0x0C / 0x0D / 0x0E** |
| paletteNum | 0x06 | **0x0F** |
| text | 0x20 | **0x10** |
| textIndex | 0x1E | **0x14** |
| tileDataStartOffset | 0x1A | **0x16** |
| tileDataOffset | 0x1C | **0x18** |
| cursorX | 0x10 | **0x1A** |
| cursorTileX | — | **0x1B** |
| language | 0x02 | **不存在**（`GetGlyphTilePointers` 是 4 参，见 §1.4） |

字段**集合**几乎相同、**顺序**完全不同 ⇒ 日版是美版的前代（美版后来重排并补了
`language`/`left`/`top`/`spacing`）。要接就得为 US text.c 写一个 JP 布局 shim，
等于把 4393 行重写一遍，写出来的语义还仍然是日版的 —— **投入 = 完整移植，产出 = 0 语义增量**。

### 2.2 其余三条硬约束

| # | 约束 | 证据 |
|---|---|---|
| 1 | **WindowTemplate 也不同，且被非文本代码共用** | US 0x1C 字节（tileData 0x10 / tilemap 0x14，含 spacing/tilemapLeft/tilemapTop）；JP 0x14 字节（tileData 0x0C / tilemap 0x10）。模板同时被 bg/window 绘制代码读 → 改布局会级联到移植 window.c/bg.c |
| 2 | **没有 RAM 段** | `link/game.ld` 仅 `ROM : ORIGIN=0x08800000, LENGTH=0x10000`，无 `.data/.bss`。US text.c 需要 `sGlyphBuffer`(132B 可写)、`gStringVar1..4`、`gBGTilemapBuffers[4][0x400]`(8KB)。现役连字形缓冲也只能放栈上 |
| 3 | **数据资产全不对** | `sFonts[]` 指向 `gFont3LatinGlyphs` 等 US 地址；编译还会吐出 ~100 个 `gWindowTemplate_81E6xxx`（各 0x1C 字节 ≈ 3KB）死重 |

> ROM **空间**不是瓶颈（已扩到 0x09EA0000+，game.bin 仅 15,032 B / 65,536 B）。

### 2.3 唯一真实收益已经拿到了

绘制数学（phase/mask/OR）已 vendored 完毕，无需拖进整个引擎：

- `reference/pokeruby/draw_glyph_tile.c`（~700 行，含 `sGlyphMasks` 全族 + 分发表 + `equivalence_refpr.py`）
- `reference/pokeemerald/copy_glyph_to_tiles.c`（`GLYPH_COPY` 参数化件）
- `reference/pokeruby/_host/`（x86 host 对照器，`oracle*.exe`）

## 3. 方案 B：pokeRS 式少量 hook —— 精神成立，点位要换

### 3.1 pokeRS 为什么能只 hook 3 点

它站在**美版的宽度间接层**上：

```
PrintNextChar → PrintGlyph_TextMode0 → { DecompressGlyph, DrawGlyphTiles, AddToCursorX(GetGlyphWidth()) }
                                                                          ↑ 改返回值 8→4，即得 12px
```
三个注入点：`GetGlyphWidth+2`（宽度）、`GetStringWidth+0x100`（测量）、`DrawGlyphTiles+2`（绘制）。

日版**没有**宽度函数——等宽假名，编译期把宽度机制裁掉了。证据：tm0 的步进是
**内联常量**（`tileDataOffset += 2` @0x08003572、tm3 `+1` @0x0800349E），不是函数调用。

### 3.2 日版的等价物：改表比插桩更干净

日版的绘制分发是 **ROM 里的纯指针**（§1.2）。改 11 个 word 即可换掉整个绘制链：

```asm
; armips，纯数据补丁，零跳板、零压栈、零寄存器争夺
.org 0x081BB3AC
    .word Chs_Tm0|1
.org 0x081BB3B0
    .word Chs_Tm1|1
...
```

对比 pokeRS 在 `GetStringWidth+0x100` 函数体中间插桩——那里要手写
`push lr / bl / pop r0 / mov r14,r0 / b 回 +0x112` 才能保住寄存器。
**日版这条路在洁净度上是占优的。**

### 3.3 代价：省不掉的部分

换表后**光标推进与半列相位归你负责**。原生步进是硬编码的（`tileDataOffset += 2`、
`cursorTileX += 1`），没有可 hook 的宽度函数。12px 推进 + pitch 相位
**无论走哪条路都要自己写**——这是本工程的固有复杂度，不是架构选型能消掉的。

### 3.4 一个反直觉的事实：hook 数已经是 pokeRS 量级

| 项目 | 引擎点 | 场景点 | 合计 |
|---|---|---|---|
| pokeRS | 3（宽度/测量/绘制） | 5（HP框×3、寄放系统×2） | **8** |
| 本项目 | 1（PrintNextChar）+ 1（MapNamePopup 长度） | 4（UnusedPrintMonName、DrawOptionMenuChoice、UpdateNickInHealthbox ×4 处） | **≈10** |

**所以问题从来不是"hook 太多"，而是"被 hook 的那个函数内部手写了太多引擎该干的事"。**
换分发点只是搬代码位置——但搬对了能删掉重建原生语义的那部分（见 `PLAN_ROM_DISPATCH_BRIDGE.md`）。

### 3.5 测量侧与打印侧正交（不可回避）

居中 / 换行判定**不走 PrintNextChar**，它们走独立的测宽函数。这是 pokeRS 要 hook
`GetStringWidth` 的原因，也是本项目已挂 4 个场景钩子的原因。
**无论方案 A 还是 B，这一块一个钩子都少不了。**
