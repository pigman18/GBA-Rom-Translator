# 调研：12px 更省 tile 的绘制方案（全网检索）

日期：2026-09-07
背景：当前紧凑 12px = 每字 3 tile（水平相位 0/4 共享列 → 平均 1.5 tile 列/字 × 垂直 2 tile 行），
需要维护相位三件套（PHASE / LAST_TILE / PHASE_ROW），历史上「壤切半」「冒号鬼影」「缺角」
BUG 均源于此。用户问：有没有更省 tile 的写法。

## 一、数学极限先封顶（静态推演，已交叉验证）

4bpp tile 网格粒度 = 8px。设字形宽 W、高 H、步进 S（=12，行内字数要求）：

- **水平**：均值步进 12px 的约束下，任何步进序列每步 ≥12（再小会叠字），故相位 mod 8
  序列被唯一固定为 0,4,0,4… → **1.5 tile 列/字是水平极限，当前已达成**。
  （若步进取 16/8 交替来对齐 tile：第二字起点 16、第三字 24 < 16+12 会重叠，数学上不成立。）
- **垂直**：⌈12/8⌉ = 2 tile 行，由墨迹高度决定，不可省。行距共享（两行文本挤进同一
  tile 行）需行距 <8px，官方行高 16px 且会破坏清行/擦字语义，不可行。

**结论：12×12 字形在 tile 网格内的极限就是 3 tile/字，现状已是极限。**
要再省，只能改字形本身（宽度 ≤8）或换渲染空间（OBJ/位图模式，不省只转移）。

## 二、方案对比（含本轮新发现）

| 方案 | tile/字 | 状态量 | 每行字数(224px) | 观感 | 改造量 |
|---|---|---|---|---|---|
| 现状：12×12 紧凑 | **3** | 相位三件套 | 18 字 | 基准 | — |
| 改良：12×12 一次调用连写两趟 | 3 | **零状态** | 18 字 | 基准 | ~30 行（blend 两次调用合一，删 PHASE/LAST_TILE 读写） |
| 16×16 整格 | 4 | 零状态 | 14 字 | 最大最清晰 | ~10 行（chs_rasterize 16px 分支现成） |
| **★8×12 窄字形（新发现）** | **2** | **零状态**（宽 8 整列对齐，相位恒 0） | 步进 8px → 28 字 | 瘦高小字，可读性待实机评估 | 引擎 ~40 行 + **字形重制** |
| 8×8（现有 FontChsSmall） | 1 | 零状态 | 28 字 | 太小 | 无（已存在） |

### ★ 8×12 窄字形（本轮全网检索的关键发现）

- **先例**：寒蝉点阵体 7px（OFL 开源，基于美咲フォント，GB2312 覆盖 13600 字符）与
  美咲フォント本体证明 **7~8px 宽的中文点阵是成熟可读的设计**（嵌入式屏幕标准做法，
  腾讯云开发者社区《嵌入式的汉字显示》：12×12 汉字配 12×6 半宽 ASCII 是行业惯例，
  宽度减半是常态而非异端）。
- **为什么它同时「更省且更简单」**：宽 8 = 整 tile 列对齐 → 相位恒 0，
  **相位三件套整体删除**（含全部历史 BUG 类别）；每字 2 tile（1 列 × 2 行）比现状省 33%。
- **代价**：字形要重制。现有 12×12 字库不能简单横向压缩（笔画粘连）。
  路线：以寒蝉点阵体 7px 为底（OFL 允许修改再分发），栅格到 8×12 网格
  （上 8 行 + 下 4 行两段，或垂直居中留边）；或用 zimo 类工具从现有 12×12 逐字重描。
  **工作量在字形不在引擎**——引擎侧走现有 8px 宽路径（font4/tm2 同款），只需让
  glyph_len=2 且支持第二 tile 行（~40 行）。
- **风险**：观感（瘦高小字）必须实机评估；若不可接受则路线作废，字形工作量沉没。

### 补充发现：VCOUNT 中断切 charBase（等效扩容，与 12px 无关但呼应路线①）

GBATEK/manualslib 确认：DISPSTAT VCount IRQ 每扫描线可触发，BGxCNT 可写
（charBase 2bit）⇒ **按行切 charBase 使同一 tile 号映射不同 charBlock 是硬件可行机制**
（HBlank DMA 惯例目标虽是 BG2X/Y/矩阵/MOSAIC，但手写 BGxCNT 同理成立，无知名游戏先例）。
适用面：单 BG 文本行的 UI 图形需与文本不同 charBlock 时才安全，约束多；
仅作为将来「战斗 UI cb3=0」类死局场景的备选，不进主线。

### 汉化圈旁证

Wokann（Pokemon_GBA_Font_Patch / pokeE / pokeFRLG）与 rh-hideout-chinese
（绿宝石 expansion 中文）**全部走 16px 字库**（4 tile/字）——美版/改版窗口大，
无省 tile 诉求。我们日版追求 12px 是为行内字数，省 tile 诉求是本项目特有，
无现成轮子可抄，但也没有人证明过「更省」的存在——数学上 3 tile 已封顶。

## 三、建议

1. **第一步（低成本高确定性）**：先做「12×12 一次调用连写两趟」——tile 预算不变、
   零状态化（删相位三件套），把整类相位 BUG 连根拔掉，观感零变化。
2. **第二步（观感实验）**：用寒蝉 7px 重制一小批 8×12 试验字形（常用 100 字），
   出实验 ROM 实机看观感；可接受再全量重制 + 引擎 40 行改造（2 tile/字 + 零状态）。
3. 16px 整格作为「想要大字」时的备选开关保留（10 行改造随时可出）。
4. VCOUNT 切 charBase 记入备选清单，主线不碰。

所有结论中：数学极限部分为静态推演（交叉验证过步进重叠反例）；寒蝉/美咲可读性
为社区公认先例；8×12 观感与改造量为推断，未经实机。
