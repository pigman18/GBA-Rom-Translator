# 全网检索：三条路线可行性（2026-09-07）

> 触发：`调研_20260907_网格落址与12px绘制_静态验证.md` 量化出「网格非银弹（8 场景 2 个选不出 GRID_BASE）」后，
> 用户要求全网检索，看能否满足三选一：
> ①扩充 cb 上限 ②修改 tilemap 来源（自定义 cb / 直接加载字库瓦片） ③绕过 tile 分布直接打印到屏幕。
> 性质：**第①步静态分析的外部资料补充**。所有结论仍未做 gdb 动态结合与实机验证。

## 0. 结论速览

| 路线 | 硬件层 | 软件先例 | 结论 |
|------|--------|---------|------|
| 1. 扩充 cb 上限 | ❌ 死路 | 无 | BG 只能见 charBase 起 32KB；借 OBJ 区真机不可行。只有「等效扩充」（8px 字 / 腾 atlas） |
| 2. 修改 tilemap 来源 / 直接加载字库瓦片 | 逐 entry 自定义 cb ❌ | **pokeRS 实战（零分配器）**、agb VRamManager | ✅ **最强候选**：照抄 pokeRS「位置决定」路径 |
| 3. 绕过 tile 分布直接打印 | OBJ 文字 ✅；原地画 ❌；HBlank ❌ | tonc TTE obj_puts、agb ObjectTextRenderer | ✅ **补盲区**：BG 无空间的场景（战斗UI cb3=0）走 OBJ 文字层 |

## 1. 路线①「扩充 cb 上限」——硬件死路，只有等效扩充

### 1.1 硬件事实【实证-外部资料】

- **tonc**（gbadev.net/tonc/objbg.html）：
  > "Both regular backgrounds and sprites have 10 bits for tile indices... Since each charblock
  > contains 512 s-tiles, you can access not only the base block, but also the one after that."
  > BG charBase 由 BGxCNT bits[2-3] 决定，**只有 2 bit（0~3）**；tile 号 10 bit ⇒ 一个 BG
  > 最多看见 charBase 起的 **32KB（2 个 charBlock）**。BG 可用 tile VRAM 恒为 cb0~3 共 64KB。
- **借 OBJ 区（cb4/5）**：tonc 同节明确：
  > "you might be tempted to try to use the sprite charblocks (blocks 4 and 5) as well.
  > On the emulators I've tested, this does indeed work. **On a real GBA, however, it does not.**"
  ⇒ 与本项目实测一致（战斗UI cb3 相对号 512+ = OBJ 区 ⇒ 花屏）。**模拟器会骗人，真机不行。**

### 1.2 等效扩充（不扩硬件，扩软件可用空间）

- **a) 8px 中文字（FontChsSmall 已有）**：每字 1 tile 而非 3 tile（12px 紧凑），容量×2 以上。
  已在未验证清单，需实机确认可读性。
- **b)【推论】回收 atlas：tm1「字库常驻」模式的死区** 🔴 新想法，未验证：
  - 主力窗 textMode=1 的官方绘制 = tilemap entry 直接指向**常驻字库 atlas**（`tileData+2*glyph`）。
  - 若某 BG（cb2：对话框/设置/背包/继续/详情）上**所有**文本都走我们的 hook，官方
    `PrintGlyph_TextMode1` 永不再执行 ⇒ atlas（约 [BASE, +0x211+]) 变成**无人读取的死区**。
  - 回收后 cb2 整块 ~1024 tile 可用 ⇒ GRID_BASE / 16px 网格 / 任意分配全都从容。
  - **前提必须验证**：① cb2 上没有 hook 之外的读取者（非翻译目标的官方打印、数字/图标）；
    ② tilemap 残留 atlas 引用在场景边界被官方清掉（`Text_LoadWindowTemplate` 的 CpuFastFill）。
  - 验证手段：gdb 读 BGxCNT + 扫 tilemap 对 atlas 段的引用计数。

## 2. 路线②「修改 tilemap 来源 / 直接加载字库瓦片」——✅ 最强候选

### 2.1 不可行的两个变体

- **逐 entry 自定义 cb**：tilemap entry 硬件格式 = bit0-9 tile 号 + bit10-11 翻转 + bit12-15
  调色板，**没有基址字段**【实证-硬件】，❌。
- **改 BGxCNT charBase（整 BG 搬字库）**：粒度是整个 BG，已写入的 tilemap entry 全部重解释，
  须同时重写所有 entry 并补写官方字库装载目标，牵一发动全身，❌ 不推荐。

### 2.2 「直接加载字库瓦片」的实战先例：pokeRS 美版汉化 🔴 本仓库就有

`tools/Pokemon_GBA_Font_Patch/pokeRS/`（Wokann，GitHub 实名项目，红宝石美版全流程中文）：

- **零分配器**：`DrawGlyphTilesChinese.s` 直接 `GetCursorTileNum(win,0,0)` 拿**官方光标位置**
  的 tile 号，把字形数据写进 `win->tileData + 32*tile`，tilemap entry 交官方 `UpdateTilemap(win,2)`。
- 语义等价于「**把字库瓦片直接加载到窗口区**」：tile 号永远落在官方为本窗文本划定的区域——
  **官方日文/英文文本自己就在用这块区，等于免费继承了游戏自身的正确性证明**（UI 图形不会
  与官方文本区重叠，否则原版就会自相踩踏）。
- 它的已知问题（readme：「狩猎地带、电脑盒子持有物等汉字显示不完全」）正是**窗口区预算溢出**，
  按场景修——因为 16px 汉字 4 tile/字。**我们 12px 紧凑只要 3 tile/字（2字3列×2行），比它更省**，
  同样的区域装得更多。
- 对照我们：日版主力窗同为 textMode 1，走 `GetCursorTileNum` else 分支
  （`tileDataStartOffset + tileDataOffset + 2x + y`）——**机制完全同款，可直接照抄**。
- 开源引擎同构先例：**agb（Rust GBA 引擎）VRamManager**——tilemap 不动、按需重写 tile 数据
  （`replace_tile` 用于背景动画每帧换瓦片），即「字库瓦片直接加载」的工程化版本；
  tonc FAQ 亦把 "dynamically modifying tile sets" 列为文本显示的标准做法之一。

### 2.3 该路线同时消灭什么

| 现状痛点 | pokeRS 位置决定路径下 |
|---|---|
| 顺序分配器 + 128B 位图 + 避让带 | **整套删除**（tile 号 = 官方光标算出） |
| 撞 UI（商店按钮/状态图标/关闭钮） | tile 永在官方文本区，**结构上不可能撞**（含「操作后才出现的 UI」） |
| 快照时序不可靠（tilemap 清零/DMA 延迟） | 不再需要快照 |
| 网格 128~256 连续 tile 的空间需求 | 每字顺序推进，与官方文本同量空间 |
| 12px 奇偶残留 | tile 号随光标走，幂等；相位逻辑（下一字前清）原样保留 |

### 2.4 代价与待验证（第②③步，不得跳过）

1. **块间复用**：textMode1 下 `tileDataOffset` 每个文本块清零 ⇒ 后块盖前块。pokeRS 在美版
   证明了这条路全流程可用，其场景性问题按场景修；**日版哪些场景存在「前块须存活」需 gdb 实测**
   （重点：设置菜单左列标签 + 右候选、背包列表 + 说明）。
2. **窗口区边界**：`InitWindowTileData` 链式 bump 的每场景预算（第②步采集，顺带回答调研文档 §5）。
3. **12px 相位共享 + 位置决定**：共享 tile 时「下一字前清相位」逻辑照旧，但 last_tile 语义简化
   （同一光标位置的 tile 重写即可，无跨块残留）。

## 3. 路线③「绕过 tile 分布直接打印」——两条真实路径

### 3.1 ✅ OBJ 精灵文字层（硬件原生支持，先例充分）

- tonc TTE `obj_puts`、agb `ObjectTextRenderer` 都是现成实现；tonc FAQ：「using one sprite per
  letter」是标准做法之一。
- OBJ 独立资源：cb4/5 共 1024 tile（32KB）+ 独立 16 调色板 + OAM；且 R/S **自带真分配器**
  （`SpriteTileAllocBitmap@0x03002450`，见「接管可行性」调研 §3，可 hook 也可自管一段）。
- 12px 汉字 4bpp = 2×2 tile ⇒ OBJ 区可容 ~256 字缓存，够一屏对话。
- 硬约束：**128 sprite/屏、32 sprite/行**（8x8 计）、战斗场景 OBJ 被宝可梦/特效大量占用。
- **定位：补盲区，不是全面替代**——BG 空间够的场景走路线②；**BG 无空间的场景
  （战斗UI cb3=0，以及地图名 cb0 仅 62）走 OBJ 文字层**。混合架构。
  ⚠ 未验证项：战斗场景 OBJ tile/调色板余量须 gdb 采集；多行文本的 sprite 数量核算。

### 3.2 ❌ 原地画进「当前显示的瓦片」（读 entry → 写该 tile 数据）

零分配、位置决定、幂等——但有**共享 tile 致命伤**：空白 tile 0 被全屏引用，画一个字全屏花；
要修就得引用计数，又退化回分配器。❌ 不推荐。

### 3.3 ❌ HBlank 逐行换瓦片数据

带宽与工程复杂度对「整段中文文本」不现实（该技巧适合调色板渐变，不适合文字）。❌

## 5. 落地采集方案（2026-09-07 追加，埋点已接入 gdb_patcher）

### 断点与工具改动
- `src/util/configs/POKEMON_RUBY_AXVJ00.yaml` 新增 3 监听点（均 default=false）：
  `TextLoadWindowTemplate=0x080029E0`（BL 实证）、
  `MenuDrawStdWindowFrame=0x0806F224`（BL 实证）、
  `MenuLoadStdFrameGraphics=0x0806F16C`（推定）。
  ⚠ 同日勘误：旧调研文档 §3 的 TextWindow_*/Menu_LoadStdFrameGraphics 等地址
  经 BL 全 ROM 扫描**全部无效**，详见该文档 §3 勘误块。
- `src/util/gdb_patcher.py`：
  - IWTD 入口/出口配对，出口自动输出 **★窗口区预算 [startOffset, 返回值) = N tile**；
  - 新 CLI `--ui-survey`：场景签名变化时报各启用 BG 的 size 位（stride 32/64 实证来源）、
    tilemap 对字库区 [0,0x210) 的引用计数（atlas 回收判据②）、cb 字库区实际范围、
    OBJ tile 位图（0x03002450【地址待验证】）与 OAM 实测（判据③）；
    InitTextPrinter 命中时附 win 结构 0x40B dump（找 width/height）。

### 采集步骤（mGBA 打开 ROM → Tools → Start GDB stub → Pause）
1. **窗口区预算 + UI 勘验**（正常打印）：
   `python src/util/gdb_patcher.py log --functions InitTextPrinter,InitWindowTileData,InitWindowTileDataRet,TextLoadWindowTemplate,MenuDrawStdWindowFrame,MenuLoadStdFrameGraphics --ui-survey`
   → 依次走：对话框 / 背包 / 设置 / 队伍 / 图鉴详情 / 地图名 / **商店（进店→买卖→让按钮出现后再触发一次文本）**。
2. **atlas 引用对照**（需已打包 hook 的 ROM）：同上再加 `--bypass-text` 重跑一遍，
   diff 每场景 atlas 区引用计数——停印后引用≈0 ⇒ atlas 可回收（判据②成立）。
3. **战斗 OBJ 余量**：战斗中放技能 + 触发血条文本，看 `[UISURVEY]` 的
   OBJ位图/OAM 实测段（判据③）。若位图头 16B 全 0xFF 或明显是数据 ⇒ 地址推定错，改信 OAM 实测。

### 判读对照表
| 数据 | 回答的问题 | 判定 |
|---|---|---|
| ★窗口区预算 N | 位置决定路线每窗可用 tile | N ≥ 该窗最多字数×3(12px) ⇒ pokeRS 路线可行 |
| atlas 引用（停印前后） | atlas 回收（判据②） | 停印后 ≈0 ⇒ cb2 整块可回收 |
| OBJ 置位数 + OAM 精灵数 | OBJ 文字层余量（判据③） | 战斗场景 OBJ 空闲 >200 tile ⇒ 战斗 UI 可走 OBJ |
| BG size 位 | stride=32 假设 | 64x32/64x64 场景 ⇒ 网格公式 stride 要改 |
| win0x40 dump | width/height 真实偏移 | 与已知窗宽（如 28）比对找偏移 |
