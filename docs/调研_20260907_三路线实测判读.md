## 一、重大发现：官方 IWTD 落址公式（路线②的直接证据）

反汇编 `InitWindowTileData=0x08002A50`（tm1 分支 0x08002A8C 起）：

```
r5 = template->tileData([0x0C]) + (startOffset<<5) + (glyphIdx<<6)
bl loader(r0=glyphIdx, r1=dest=r5, ...)
```

⇒ **dest tile 号 = tileBase + 2×glyphIdx**。实机观测 r2（glyphIdx）连续递增
（地图名 0x081BB49C：0x51→0x5F；设置菜单 0x081BB874：0→…）。

三重含义：

1. **官方没有 tile 分配器、没有避让带**——tm1 字库 tile 的落址由 glyph 索引
   决定，与屏幕位置、UI 占用完全正交。字库区因此被官方当作「私有常驻区」。
   这正是字库区 [0x001,0x1FF] 可以整体回收的根据（§二）。
2. **pokeRS 式「位置决定」在本作有原生对应物**。我们接管后只要在
   InitTextPrinter 边界复位一个顺序游标、按 `tile = winBase + 2*idx`（16px）
   或 12px 紧凑 3tile/2字 推进，就复刻了官方自己的机制——结构上继承官方的
   正确性（官方文本自己就在用这块区）。
3. **旧「分区链/窗口预算取自 IWTD 返回值」理解作废**：IWTD 返回 void
   （各分支 `bl loader` 后直落 0x08002AE8 `pop{r4-r6}; pop{r0}; bx r0`，
   r0 从未被赋值；0x08002AEA 处 r0 恒为 thumb 返回地址 0x08002AAB）。

## 二、问①：cb 回收实证（atlas 引用计数）

| 场景 | BG0(charBase=2) tilemap 现状 | cb2 实际内容 | 判读 |
|---|---|---|---|
| 对话框 0x3140（tm3 模板 0x081BB46C） | 800/1024 零项，非零引用仅 tile0 | **非零 tile 仅 [0x002-0x002]** | 整个 cb2 除 1 个 tile 外全空 |
| 背包/菜单 0x7140（tm1） | 非零引用集中在 #204×384、#201×48、#207×48、#203×16（窗框/底色，全在 [0x200,0x210) 之外段） | [0x001-0x1FF] 满（官方字库已装载） | **字库区被装载但 tilemap 引用 ≈ 0** |

- tilemap 对 [0x001,0x1FF) 字库区的引用只在**文本正在显示时**由 UpdateTilemap
  写入——那是我们自己的中文 tile 也一样要用的机制，不构成冲突。
- ⇒ **接管全部文本绘制后，官方字库装载停掉，cb2 [0x001,0x200) 512 tile +
  atlas 上界以上部分区（0x211+ 视场景）整体可回收**。旧「地图名 cb0 只有
  62 连续、战斗UI cb3 归零」的紧张感主要来自「和官方字库/窗框抢地」——
  接管后这块地从根上让出来了。
- ⚠ 修正旧口径：之前「atlas 引用 = 800/1024 次」的数字混入了空 entry 的
  tile0 噪音；修正后非零引用才是真实判据（gdb_patcher 已改）。

## 三、问③：OBJ 余量实测（战斗 UI 等盲区）

- **战斗场景 0x9040**：OAM 实测活动精灵 tile 基址最高 0x0D8（含 64×64 精灵
  @152，即占到 ~0x197）；按尺寸逐个估算占用上界 ≈0x197，**空闲 ≈ 600+ tile**。
- **对话框场景 0x3140/0x7140**：128 个 OAM 槽全指向 tile0（隐藏/未用），
  **OBJ VRAM 全空**。
- **战斗 UI 场景 0x0200**（模板 0x081BB514 高频出现，本次采集打点 1020 次）：
  DISPCNT bit12=0，**OBJ 根本未启用**——该场景 cb3 压力只能靠 BG 侧解决。
- ⚠ 工具勘误：`OBJ位图@0x03002450` 读到的是指针数据不是位图（地址错误），
  位图读数一律不可信；**判据以 OAM 实测为准**（已改为 OAM 推算空闲）。

## 四、窗口预算来源（替代作废的 IWTD-Ret）

- `MenuDrawStdWindowFrame(bg, x, y, width)` 签名实机验证成立：底部菜单三窗
  `y=28, width=7/11/15`，x 递增（0/8/12），LR=0x08007274/28A/2A0。
  **width 即窗宽（tile）**——这是「窗口预算」的可靠来源之一。
- 日版 win 结构 0x40 dump 中**未见 width/height 字段**（0x18~0x3F 全零）；
  战斗窗 r0=0x021E0100 结构与普通 win 不同（[0] 不是模板指针，按模板解释
  出垃圾值）。窗口尺寸字段定位仍是待办。
- tilemap 实测（本日志）：各场景文本窗底色填充 tile（#204×384 等）给出了
  窗口实际占用区，可交叉验证。
