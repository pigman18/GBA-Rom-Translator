# 调研：能否「接管」UI 的 tile 分配（2026-09-07）

> 触发：实机测试发现**部分页面的 UI 是操作后才出现的**（例：商店的买卖按钮），
> 静态避让带（`scene_cfg.c:kV8AvoidScenes`）无法穷举，导致中文踩 UI。
> 问题：**能不能反过来接管游戏的 tile 分配，而不是一直猜着避让？**

---

## 0. 结论速览

| 问题 | 结论 |
|------|------|
| BG 侧能否接管？ | ❌ **不能**。R/S（含 AXVJ00）**没有集中式 BG tile 分配器**。窗口 tile 区由调用方硬编码 `startOffset` 链式传递；大量 UI 图形直接 `LZDecompressVram(gfx, VRAM+固定地址)`，根本不过任何分配器。 |
| OBJ 侧能否接管？ | ✅ **能**。`SpriteTileAllocBitmapOp` + `sSpriteTileAllocBitmap` 是完整位图分配器。但 OBJ 在 charBlock 4/5，BG 在 cb0~3，**物理隔离**，接管它对解决 BG 冲突没有直接帮助。 |
| 那还能做什么？ | 把「接管分配」降级为「**接管登记**」：避让依据从「tilemap 一次性快照」升级为「**咽喉点登记 ∪ VRAM 非空探测**」。见 §4。 |

**一句话**：这条路走不通不是因为工程量大，而是因为 R/S 的 BG UI 图形**压根没有分配器可接管**——它们是编译期写死的 VRAM 地址。

## 0.5 美版汉化对照：它们根本「不分配」（2026-09-07 追加）

本地就有 R/S 汉化的现成实现：`tools/Pokemon_GBA_Font_Patch/pokeRS/`（PMRUS_CHPLUS），
以及美版 `pokeE/`、`pokeFRLG/`。**它们没有任何 tile 分配器。**

### 落址：完全复用官方 `GetCursorTileNum`

`pokeRS/src/HackFunction/DrawGlyphTilesChinese.s:90-94`
```asm
mov r0, r6            ; win
mov r1, 0
mov r2, 0
bl  GetCursorTileNum
lsl r0, r0, 5         ; * 32
ldr r1, [r6, 0x24]    ; win->tileData
add r1, r1, r0        ; dest = win->tileData + 32 * GetCursorTileNum(win,0,0)
str r1, [sp, 0xC]     ; glyphTileInfo.dest
```
一个汉字画 4 次（左上 / 右上 / 左下 / 右下），每次都是 `GetCursorTileNum(win, x, y)`，
中间用 `win->left += 8`、`tileDataOffset += 2` 推进。**没有任何"找空闲"的动作。**

### 写表项：复用官方 `UpdateTilemap(win, 2)`

`tools/pokeruby/src/text.c:4357-4377` —— **官方原生就支持 16px 宽字符（2×2 tile）**：
```c
u16 upperLeftTileNum  = GetCursorTileNum(win, 0, 0);
u16 lowerLeftTileNum  = GetCursorTileNum(win, 0, 1);
tilemap[0]  = upperLeftTileNum  | paletteNum;
tilemap[32] = lowerLeftTileNum  | paletteNum;
if (tilesWidth == 2) {
    tilemap[1]  = GetCursorTileNum(win, 1, 0) | paletteNum;
    tilemap[33] = GetCursorTileNum(win, 1, 1) | paletteNum;
}
```
即：**日/美版引擎本来就是为 16px 宽字符设计的**，汉化只需换字模来源和宽度，
落址与写表项原封不动。

### 不冲突的保证：`GetCursorTileNum` 的「可变宽度分支」

`tools/pokeruby/src/text.c:4380`
```c
if (win->textMode == TEXT_MODE_UNKNOWN2)
    index = win->tileDataStartOffset
          + win->tileDataOffset
          + (((win->top + win->cursorY) >> 3) + yOffset) * win->width
          + (((win->left  + win->cursorX) >> 3) + xOffset);   // ← 由光标位置唯一决定
else
    index = win->tileDataStartOffset + win->tileDataOffset + 2 * xOffset + yOffset;
```
第一条分支里 tile 号**由 (cursorX, cursorY) 网格唯一决定**，行与行天然不同号，
所以**不需要知道"哪块空着"**——位置本身就是地址。

### 美版（Emerald/FRLG）额外两件武器

历史文档 `docs/结论_替换BUG真正难点_空闲tile不可知.md` §5 已定论：

- **A1 窗口独占 VRAM 区**：`AddWindow` 用 `BgTileAllocOp` 给每窗口分 `width*height`
  个 tile（`baseBlock`），窗口间物理隔离——"空闲"在窗口边界内重新有意义。
- **A2 EWRAM 缓冲 + `CopyWindowToVram` 整块 blit**：每帧全量重绘，**不需要"回收"**。

### 我们卡在哪（ROM 字节实证）

读 `roms/origin/POKEMON_RUBY_AXVJ00.gba` 的窗口模板：

| tpl | charBase | screenBase | font | **textMode** |
|-----|---------|-----------|------|-------------|
| 0x081BB5BC 宝可梦详情 | 2 | 30 | 3 | **1** |
| 0x081BB874 设置菜单 | 2 | 15 | 3 | **1** |
| 0x081BB544 背包 | 2 | 31 | 3 | **1** |
| 0x081BB46C 继续菜单 | 2 | 31 | 3 | **3** |
| 0x081BB43C 队伍窗 | 1 | 30 | 4 | 1 |

**全是 1 / 3 → 走 `GetCursorTileNum` 的 else 分支**：
`index = tileDataStartOffset + tileDataOffset + 2*x + y`，
tile 号只跟 `tileDataOffset` 走，而该游标**每个文本块（`InitTextPrinter`）清零一次**
⇒ 块间复用同一批 tile ⇒ 后一个块盖掉前一个块 = 历史文档说的**替换 BUG**。

所以：**美版能"不分配"是因为它的窗口走网格映射（或独占 VRAM）；我们走的是
游标复用分支，不得不住进"自己找空闲"这条死胡同 —— v6/v7/v8 三代分配器、
以及今天"撞 UI"的问题，全都是这一个分支差异长出来的。**

### 由此产生的新方向（待评估，未验证）

不是继续改进分配器，而是**把落址换回「位置决定」**：让 tile 号按窗口网格算出
（套用 `GetCursorTileNum` 可变宽度分支的公式）。若成立则：
- 行间、块间天然不冲突 → **v8 分配器可以整个删掉**
- tile 落在窗口自有网格 → **不会撞 UI 固定图形区**
- 屏幕位置继续交官方光标，改动只集中在一处落址函数

三个必须先验证的前提：
1. `tileDataStartOffset` 之后是否有 `width*height` 个连续 tile（不跨 charBlock、不与 UI 固定图形重叠）。
2. 汉字 2×2 tile 时 `tileDataOffset` 的推进量（官方对 `tilesWidth==2` 怎么推）。
3. 同屏多文本块（设置菜单左标签列 / 右候选列）是否各有独立窗口；若是，网格映射天然隔离。

## 1. v8 现在是怎么分的（代码事实）

`configs/POKEMON_RUBY_AXVJ00/hook/src/text/tile_alloc.c`

```
InitTextPrinter（会话边界）
  └─ v8_alloc_begin(win)
       ├─ 复位 游标 / 相位 / last_tile / NL_MARK
       ├─ 清 128B 占用位图（tile 相对号 0~1023）
       ├─ 扫 tpl[TPL_TILEMAP] 指向的 tilemap 1024 项，非零 → 标占用
       └─ 合并 scene_cfg.c 的静态避让带 kV8AvoidScenes（按 tpl 查）

每画一个字
  └─ v8_alloc_tile(win, font_px, glyph_len)
       ├─ lo = 0x100（跳过官方字库 atlas）
       ├─ hi = v8_alloc_hi(charBase) = (4-cb)*512，clamp 1024
       ├─ 从游标起顺序找首个连续 glyph_len 空闲 → 领号、推进游标
       └─ 找不到 → 回卷一次；再找不到 → 返回 0（放弃绘制）
```

关键点：**避让带只有两个来源**——「会话开始那一刻的 tilemap 活引用」+「手抄的静态 bands」。
两者都是**快照式**的，对「快照之后才出现的 UI」天然无能。

## 2. 为什么会漏（三类根因，附代码证据）

### 2.1 UI 图形是硬编码 VRAM 地址，不经过任何分配器 ★主因

`tools/pokeruby/src/shop.c:270`
```c
LZDecompressVram(gBuyMenuFrame_Gfx, (void*)(VRAM + 0x7C00));
```
`VRAM+0x7C00` → 绝对 tile `0x7C00/32 = 0x3E0`（charBlock 1，块内 0x1E0）。
随后 `shop.c:483 / 501`
```c
gBGTilemapBuffers[1][i] = ewram18000[i] + 0xC3E0;   // palette 0xC + tile 0x3E0
```
→ 商店框架/按钮图形占 **绝对 tile 0x3E0 起一整段**，是**编译期常量**。
没有任何函数"申请"这段，所以没有任何 hook 点能感知它。

同类还有 `Menu_DrawStdWindowFrame`、`TextWindow_LoadStdFrameGraphics`（窗框 9 tile）、
`OpenMoneyWindow` 等，全都是模板里写死的 `tileData`/`tilemap` 指针 + 固定偏移。

### 2.2 分配咽喉点是"链式 bump"，但分散在几百个调用点

`tools/pokeruby/src/menu.c:113`
```c
gMenuTextWindowTileOffset      = InitWindowTileData(gMenuWindowPtr, gMenuTextTileOffset);
gMenuTextWindowContentTileOffset = TextWindow_SetBaseTileNum(gMenuTextWindowTileOffset);
TextWindow_LoadStdFrameGraphics(gMenuWindowPtr);
gMenuMessageBoxContentTileOffset = TextWindow_SetDlgFrameBaseTileNum(gMenuTextWindowContentTileOffset);
```
`text_window.c:101/200` 证实了链式语义：
```c
u16 TextWindow_SetBaseTileNum(u16 base){ sTextWindowBaseTileNum = base; return base + 9;  }
u16 TextWindow_SetDlgFrameBaseTileNum(u16 base){ sDialogueFrameBaseTileNum = base; return base + 14; }
```
起点 `gMenuTextTileOffset` 由每个场景**各自传**（`menu.c:79` 传 1，`shop.c` 走模板…），
没有统一的"分配器"对象，只有"上一个函数返回什么就用什么"的约定。
要"接管"就要改每一个调用点或改 ROM 里所有模板常量——**不可行**。

### 2.3 tilemap 快照时序不可靠

- `shop.c:281` `Menu_EraseWindowRect(0, 0, 0x20, 0x20)` 会在窗口初始化后**把 tilemap 清成 0**；
- 商店视口走 `gBGTilemapBuffers[]` **RAM 缓冲 + VBlank DMA**（`shop.c:251-253`），
  RAM 里的改动要等 VBlank 才同步进 VRAM tilemap；
- 我们扫的是 `tpl[TPL_TILEMAP]`（VRAM 真 tilemap），**两边不同步**。

结论：快照那一刻的 tilemap 既可能被清过，也可能还没 DMA 过来。

### 2.4 附带漏洞：`tilemap == NULL` 的窗直接跳过扫描

`tile_alloc.c:132` `if (!tilemap) return;` —— `game.h:147` 注释「NULL=缓冲直绘」。
这类窗口**完全没有动态避让**，只剩静态 bands 兜底。

### 2.5 分配区间过宽

`lo = 0x100`、`hi = (4-cb)*512`（cb=2 时 1024）。区间横跨相对号 0x100~0x3FF，
必然覆盖到 UI 固定图形常驻的高段（0x3C0 / 0x3E0 一类）。
即便快照正确，只要 UI 尚未进 tilemap，我们就会把它领走。

## 3. 可 hook 的咽喉点清单（日版 AXVJ00 地址）

> ⚠ **2026-09-07 勘误（BL 调用点全 ROM 扫描实证，脚本 `_tmp_bl_verify.py`）**：
> 本节下列地址在日版 AXVJ00 **全部无效**（0 个 BL 调用点或非函数头）：
> `Text_LoadWindowTemplate=0x08002D4C` ✗、`InitWindowTileData=0x08002D68` ✗、
> `TextWindow_SetBaseTileNum=0x080625E0` ✗、`TextWindow_LoadStdFrameGraphics=0x080625F4` ✗、
> `TextWindow_SetDlgFrameBaseTileNum=0x080628B4` ✗、`Menu_LoadStdFrameGraphics=0x0806F504` ✗。
> **已验证锚点**：`InitWindowTileData=0x08002A50`（yaml 已有，唯一调用点 @0x08002A14）、
> 其唯一调用方 **`Text_LoadWindowTemplate=0x080029E0`**、
> **`Menu_DrawStdWindowFrame=0x0806F224`**（push{lr} 头 + 2 调用点）、
> `Menu_LoadStdFrameGraphics≈0x0806F16C`（推定，未定身份）。
> `TextWindow_SetBaseTileNum / SetDlgFrameBaseTileNum` 未能定位，暂无断点；
> 窗口区预算改由 IWTD 入口/出口配对（[startOffset, 返回值)）取得，不依赖它们。

### BG 侧（登记用，不能接管）

| 函数 | 日版地址 | 能拿到什么 |
|------|---------|-----------|
| `Text_LoadWindowTemplate` | `0x08002D4C` | 场景/窗口重建信号（内含 `CpuFastFill(0, tilemap, 0x800)`）→ **账本清零点** |
| `InitWindowTileData` | `0x08002D68` | `win->tileData`（VRAM 指针）+ `startOffset` + 返回值 = 本窗占用段 |
| `TextWindow_SetBaseTileNum` | `0x080625E0` | 内容 base tile（写 `sTextWindowBaseTileNum @0x030005AC`），+9 |
| `TextWindow_LoadStdFrameGraphics` | `0x080625F4` | 窗框 9 tile 的写入地址（`tileData + 32*base`） |
| `TextWindow_SetDlgFrameBaseTileNum` | `0x080628B4` | 对话窗框 base，+14 |
| `Menu_DrawStdWindowFrame` | `0x0806F224` | 菜单窗框绘制 |
| `Menu_LoadStdFrameGraphics` | `0x0806F504` | 菜单窗框装载 |

| 符号 | 日版地址 | 说明 |
|------|---------|------|
| `sSpriteTileAllocBitmap` | `0x03002450`（0x80 B = 1024 bit） | OBJ 全 1024 tile 的占用位图 |
| `SpriteTileAllocBitmapOp` | `0x080014B8`（0x70 B） | 位图 set/clear/find |
| `AllocSpriteTiles` | `0x0800139C`（0x11C B） | OBJ tile 申请 |
| `AllocTilesForSpriteSheet` | `0x08002630` | 精灵表批量申请 |

### 反证：R/S 确实没有集中 BG 分配器

```
pokeruby.sym       : BgTileAllocOp / gpu_tile_allocation_map_bg / gWindowTileAutoAllocEnabled → 0 处
pokeruby_jp.sym    : 同上 → 0 处
pokefirered.sym    : 同上 → 3 处  ← 集中分配器是 FRLG 才有的特性
```
且 `tools/pokeemerald/src/bg.c:294` 的 `BgTileAllocOp` 是 `return 0;` 的 stub
（`gWindowTileAutoAllocEnabled` 在 Emerald 恒为 FALSE）。

## 4. 替代方案（按推荐度）

### 方案 A — VRAM 非空探测 ★推荐（最能对症状）

把避让依据从「tilemap 有谁引用」换成「**VRAM 这块 tile 里有没有东西**」。

- `v8_alloc_begin` 除扫 tilemap 外，再扫本窗 charBlock 的 VRAM tile 数据：
  **32B 全 0 = 空闲；非零 = 有图形（官方字库 / UI 图形）→ 标占用**。
- 自动覆盖 `LZDecompressVram(gfx, VRAM+0x7C00)` 这类硬编码 UI（§2.1 主因）。
- **自画污染**：我们上一轮写的中文也是非零。解法：再开一张 `ours` 位图
  （我们自己领过的号），避让带 = `VRAM非零 − ours`；`ours` 在
  `Text_LoadWindowTemplate`（0x08002D4C）场景边界清零。
- 代价：每会话多扫 512~1024 tile × 32B（16~32KB），GBA 上可接受；EWRAM 再要 128B。
- 风险：VRAM 不会被整体清 0（`ClearBGMem` 只清 32B），陈旧非领会长期算占用 → 可用 tile 缓慢变少。
  缓解：`ours` + 场景边界全量重判，并保留「彻底无空闲就放弃」的兜底。

### 方案 B — 收紧分配区间（最小改动，先止血）

把 `lo=0x100 / hi=(4-cb)*512` 改成**按场景配置**的 `[lo, hi)`，
默认把高段（>0x2FF，或按实测的 UI 固定图形区）永久排除。
- 商店 0x3E0 那类高段 UI 天然避开，一行改动。
- 代价：可分配 tile 变少，长文本可能不够放 → 需要实测最长文本所需 tile 数。

### 方案 C — 咽喉点登记（治本，改动最大）

Hook §3 BG 侧那 7 个函数，把每次"占坑"的 tile 段记进全局账本
（EWRAM 256B，**绝对** tile 号，由 `tileData - 0x06000000)/32` 换算）。
- 精确覆盖"链式分配"的所有窗口区（含晚出现的窗口）。
- **覆盖不到** `LZDecompressVram` 硬编码地址（商店就是这种）→ 仍需 A 或 B 兜底。

### 组合建议

**先 B 止血（改 hi 上界 + 补商店场景 band），再上 A 作为通用机制，C 视 A 的效果决定是否加。**
