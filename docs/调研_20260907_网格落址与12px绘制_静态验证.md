## 一、12px 绘制：官方到底支持什么（用户提问①）

### 1.1 铁证：官方字宽硬上限 = 8

`tools/pokeruby/src/text.c`：

```c
// line 251  —— 第一维只有 9，即 width ∈ [0,8]
static const u32 sGlyphMasks[9][8][3] = { ... };

// line 468  —— 函数表只有 9 项
static const ShiftGlyphTileUnshadowedFunc sShiftGlyphTileUnshadowedFuncs[] = {
    ShiftGlyphTile_UnshadowedFont_Width0,
    ... ,
    ShiftGlyphTile_UnshadowedFont_Width8,   // ← 到此为止
};

// line 3882 —— 直接按 width 索引，无边界检查
const u32 *masks = sGlyphMasks[glyphTileInfo->width][glyphTileInfo->startPixel];
```

⇒ **width ≥ 9 必然越界**。所谓「官方原生 12px 绘制」**不存在**。
（`sShiftGlyphTileShadowedFuncs` 同样 9 项，line 484。）

### 1.2 但官方原生支持「亚 tile 拆分」——我们和它是同源的

`DrawGlyphTile_UnshadowedFont`（text.c:3877）核心：

```c
glyphTileInfo->startPixel = (win->left + win->cursorX) & 7;   // 0~7 任意相位
...
if (glyphTileInfo->startPixel + glyphTileInfo->width > 8)     // 跨 tile
{
    if (glyphTileInfo->textMode != TEXT_MODE_UNKNOWN2)
        buffer += 8;                    // mode0：溢出写 +64B = +2 tile
    buffer[8] = glyphBuffer->pixelRows[8]; ...                // mode2：+32B = +1 tile
}
return (glyphTileInfo->startPixel + glyphTileInfo->width) / 8;  // tilesWidth 1 或 2
```

- `startPixel` 任意（0~7）→ **官方本来就允许一个字跨两个 tile**。
- 溢出偏移：mode0 `+64B(2 tile)`、mode2 `+32B(1 tile)` —— 与本项目
  `blend_glyph.c` 注释「官方 mode0 右邻+64B / mode2 +32B」**完全吻合**。
- `UpdateTilemap(win, tilesWidth)` 原生支持 `tilesWidth==2`（一次写 2×2 四个 tilemap 项）。

⇒ **结论：12px 的「8+4 / 4+8 拆分」不是歪门邪道，是把官方 width≤8 的拆分机制
用在 12px 字上的自然延伸。拆分机制本身没问题。**

### 1.3 当前实现的实际布局（紧凑 12px）

`PrintNextChar_hook.c: print_glyph_px()`：

```
字1: phase=0, w0=8, w1=4 → 画 tile[col0] 全 + tile[col1] 前 4px  ; adv=1
字2: phase=4, w0=4, w1=8 → 画 tile[col1] 后 4px + tile[col2] 全  ; adv=2
字3: phase=0 ...
```

- 相位序列 `0,4,0,4,...`（12 % 8 = 4）
- **2 个字占 3 个 tile 列**；每 tile 列含上下两半（16px 高）⇒ 2 字 6 个 tile
- 字 2 复用字 1 的右半 tile（`v8_phase_last_tile()`）—— 这就是共享

⇒ 紧凑排版下「相邻字共享 tile」是**数学上的必然**，不是设计缺陷。
MEMORY 里「壤切半 / 句首冒号鬼影」等 BUG，根因**不是共享本身**，而是
**共享的 tile 号由顺序分配器给出，不可预测、可能撞 UI、跨块不复位**。

### 1.4 回答用户

> 「8+4 4+8 的方式肯定有问题，说不定官方支持原生的 12px 绘制？」

- 官方**不支持** 12px 单字宽（硬上限 8，铁证 §1.1）。
- 官方**支持** 8px 字的任意相位跨 tile 拆分（§1.2），我们的做法与之同源。
- **真正的问题在 tile 号的来源**：官方是「位置决定」，我们是「分配器决定」。
  ⇒ 修 12px 的正确方向不是改拆分，而是**把 tile 号换回位置决定**（§二）。

## 二、网格落址方案（用户提问②）

### 2.1 官方现成的公式

`GetCursorTileNum`（text.c:4371）：

```c
if (win->textMode == TEXT_MODE_UNKNOWN2)          // = 2
    index = win->tileDataStartOffset
          + (((win->top + win->cursorY) >> 3) + yOffset) * win->width
          + (((win->left + win->cursorX) >> 3) + xOffset);
else
    index = win->tileDataStartOffset + win->tileDataOffset + 2*xOffset + yOffset;
```

网格分支（textMode 2）里，tile 号 = **起始 + 行 × 宽 + 列**，行/列由光标位置唯一决定。

### 2.2 为什么它不冲突

- 同一屏幕位置 ⇒ 同一 tile 号 ⇒ **天然幂等**，重复绘制无副作用
- 不同行/列 ⇒ 不同 tile 号 ⇒ **不需要知道"哪里空着"**
- 不需要位图、不需要避让带、不需要顺序分配器、不需要 last_tile 共享

这正是 pokeRS / pokeE / pokeFRLG 汉化「零分配」的根本原因（见本文件上一章）。

### 2.3 我们能直接用吗 —— 不能，缺两样

**（a）textMode 不对。** 日版 ROM 模板实测：

| tpl | charBase | screenBase | font | textMode | tileData | tilemap |
|---|---|---|---|---|---|---|
| 0x081BB5BC 主力对话框 | 2 | 30 | 3 | **1** | 0x06008000 | 0x0600F000 |
| 0x081BB874 设置菜单 | 2 | 15 | 3 | **1** | 0x06008000 | 0x06007800 |
| 0x081BB544 背包 | 2 | 31 | 3 | **1** | 0x06008000 | 0x0600F800 |
| 0x081BB43C 队伍窗 | 1 | 30 | 4 | **1** | 0x06004000 | 0x0600F000 |
| 0x081BB514 战斗 UI | 3 | 23 | 3 | **1** | 0x0600C000 | 0x0600B800 |
| 0x081BB3F4 战斗招式 | 0 | 24 | 3 | **0** | 0x06000000 | 0x0600C000 |
| 0x081BB40C 战斗血条 | 0 | 0 | 4 | **2** | 0x06000100 | NULL |

（模板 24 字节；`tileData@0x0C`、`tilemap@0x10` 与 hook 宏 `TPL_TILE_DATA/TPL_TILEMAP`
一致；`tileData == BG_CHAR_ADDR(charBaseBlock)`、`tilemap == BG_SCREEN_ADDR(screenBaseBlock)`
两项自洽，字段解读已实证。）

⇒ 主力窗口全是 **textMode 1（MONOSPACE）**，走 else 分支。
textMode 1 下 `PrintGlyph_TextMode1` 是
`sWriteGlyphTilemapFuncs[fontNum](win, glyph)`，例如 Font3：

```c
s16 val = win->tileDataStartOffset + 2 * glyph;
WriteGlyphTilemap(win, val, val + 1);
```

**tile 号 = 字符索引 ⇒ 这是"字库常驻 VRAM"模式**（官方拉丁/日文字库只有几百字，
`2*glyph` 装得下）。中文 6000+ 字 ⇒ 12000 tile ≫ 1024，**装不下**，所以只能动态绘制。
这是 v6/v7/v8 三代分配器存在的**唯一根因**。

**（b）网格 stride（`win->width`）未知。** hook 的 `WIN_*` 宏里**没有 width/height**
（只有 CURSOR_X/TILE_X/CURSOR_Y/TILE_Y），模板 24 字节里 `0x14-0x17` 恒为 0。
⇒ 日版实际 Window 结构与 pokeemerald 反编译结构不同，width 需实测。

⚠️ **订单外发现（待查，不阻塞）**：`0x081BB46C` 的 `textMode == 3`，但
`sPrintGlyphFuncs[]` 只有 3 项（text.c:359-363）。该模板 tileData/tilemap 自洽、
确为合法模板。要么 Ruby 枚举有第 4 项、要么该模板不用于打印。**不深究**。

### 2.4 落地方案：屏幕坐标网格（绕开 stride 未知）

不依赖 `win->width`，改用 **BG 固定 stride = 32**（BG 是 32×32 tile，
由 screenBase 间隔 0x800 = 32×32×2B 实证：0x081BB5BC 用 sb30→0xF000，
0x081BB46C 用 sb31→0xF800）：

```
row = (win->top    + win->cursorY) >> 3     // 屏幕 tile 行
col = (win->left   + win->cursorX) >> 3     // 屏幕 tile 列
idx = GRID_BASE + row * 32 + col            // upper
      idx + 32                              // lower（下一行同列）
```

12px 跨列时右半落在 `col+1`，与官方 `tilesWidth==2` 一致。

### 2.4b 空间测算：**不存在统一的 0x2FF 边界**（实测 bands 已推翻初稿）

⚠️ **2026-09-07 更正**：初稿「高段 >0x2FF 永久排除」**是错的**，已作废。

用 `scene_cfg.c` 的实测避让带现算（`lo=0x100`、`hi=min((4-cb)*512,1024)`）：

| 场景 tpl | cb | 搜索区 | 最大连续空闲 | 位置 |
|---|---|---|---|---|
| 0x081BB40C 战斗血条 | 0 | [0x100,0x400) | 768 | [0x100,0x3FF] |
| 0x081BB49C 地图名 | 0 | [0x100,0x400) | **62** | [0x3C2,0x3FF] |
| 0x081BB43C 队伍窗 | 1 | [0x100,0x400) | 658 | [0x16E,0x3FF] |
| 0x081BB874 设置菜单 | 2 | [0x100,0x400) | 503 | [0x209,0x3FF] |
| 0x081BB544 背包 | 2 | [0x100,0x400) | 443 | [0x209,0x3C3] |
| 0x081BB46C 继续菜单 | 2 | [0x100,0x400) | 348 | [0x264,0x3BF] |
| 0x081BB5BC 宝可梦详情 | 2 | [0x100,0x400) | 238 | [0x212,0x2FF] |
| **0x081BB514 战斗 UI** | 3 | [0x100,0x200) | **0** | **★ 无可用** |

**推翻 0x2FF 的三条实证**：

1. **atlas 上界因场景而异，不是常量 0x209**：`0x081BB5BC`→0x211、
   `0x081BB544`/`0x081BB874`→0x208、**`0x081BB49C`→0x2D1**（远超 0x209）。
2. **0x2FF 以上恰恰是主力可用区**：背包 [0x209,0x3C3]、设置菜单 [0x209,0x3FF]
   两块**都跨过 0x2FF**；砍到 0x2FF 各只剩 247（腰斩）。
   地图名窗最大块 [0x3C2,0x3FF] 在 0x2FF **之上**，砍掉直接归零。
3. **0x2D7/0x300 附近确实有 UI 撞边界**（`0x081BB49C` 的 [0x2D7,0x301]、
   `0x081BB5BC` 的 [0x300,0x327]）—— 但那是"要避让的点"，**不是全局分界线**。

⇒ **`hi` 必须按场景从实测 bands 现算，不能写全局常量。**

### 2.4c 顺带暴露的两个隐患

- **`0x081BB514` 战斗 UI（cb3）已无可用 tile**：band `{cb3,0x003,0x208}` 覆盖了整个
  搜索区 [0x100,0x200)（`hi=(4-3)*512=512`）。该场景当前**分不到号**。
- **避让带"并集"策略过宽**：`0x081BB49C` 注释「地图名弹窗 + 淡出后场地
  （并集取更密占用）」，其 `{cb0,0x001,0x2D1}` 很可能是把**整个场地背景**算成了避让，
  导致该窗只剩 15 段 4~9 tile 的碎片。这是"避让带越加越不够用"的根源之一。

- 商店 UI：`LZDecompressVram(gBuyMenuFrame_Gfx, VRAM + 0x7C00)` = 绝对 tile **0x3E0**
  = **charBlock 1** ⇒ charBase=2 的窗口**物理上够不到**，charBase=0/1 才可能撞。
  （与 MEMORY「队伍窗 charBase=1 占用段罩住 lo=0x100」同构。）

### 2.5 网格方案能同时解决什么

### 2.5 网格方案的真实代价（2026-09-07 量化，勿乐观）

⚠️ 初稿说「避让带整个不需要了」**是错的**。网格只是把「每字找空闲」换成
「选 BASE 时找一次」，**避让带仍然需要**，且要求**更大块的连续空间**：

| | 顺序分配器（现状） | 网格方案 |
|---|---|---|
| 每次需求 | `glyph_len = 2` 个连续 | `maxRow × stride` 个连续 |
| 4/6/8 文本行 | 2 | **128 / 192 / 256** |
| 判断次数 | 每字一次 | 选 BASE 一次 |
| 撞 UI 后果 | 偶发 | **100% 稳定撞** |

按 stride=32 对照实测可用连续块：

| 场景 | 可用连续 | 4行(128) | 6行(192) | 8行(256) |
|---|---|---|---|---|
| 战斗血条 cb0 | 768 | OK | OK | OK |
| **地图名 cb0** | **62** | **✗差66** | ✗差130 | ✗差194 |
| 队伍窗 cb1 | 658 | OK | OK | OK |
| 设置菜单 cb2 | 503 | OK | OK | OK |
| 背包 cb2 | 443 | OK | OK | OK |
| 继续菜单 cb2 | 348 | OK | OK | OK |
| 宝可梦详情 cb2 | 238 | OK | OK | **✗差18** |
| **战斗 UI cb3** | **0** | ✗差128 | ✗差192 | ✗差256 |

⇒ **8 个场景里 2 个选不出 `GRID_BASE`**（地图名 62、战斗 UI 0）。
网格是「把 N 次小赌博换成 1 次大赌博」：唯一真实收益在**时序**
（定好后不受"操作后才出现的 UI"影响），**不在空间**，实际**更费空间 64~96 倍**。

| 现有 BUG | 网格方案下 |
|---|---|
| 撞 UI（商店按钮/队伍状态图标/设置关闭钮） | 只在 `GRID_BASE` 选对时成立；2/8 场景选不出 |
| 静态避让带覆盖不全（UI 操作后才出现） | 仍需避让带，但只需在**选 BASE 时算一次** |
| 12px 奇偶残留（壤切半 / 冒号鬼影） | 位置决定 tile ⇒ 同位置同 tile，天然幂等，不依赖 last_tile/相位续接 |
| 跨块状态残留 | 无跨块状态 |
