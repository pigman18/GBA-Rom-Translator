## 二、业界四大路线概览

### 路线 A：静态替换（民间汉化组主流，90% 的 GBA 汉化）
码表（TBL）→ 文本导出 → 翻译 → 新码表 → 字库改画/替换 → 文本等长写回（或扩容重指指针）。
- 前提：日文字库是全角 SJIS 槽位阵（≥1900 全角槽），汉字直接画进**不用的假名/汉字槽**，引擎零改动。
- 宽度约束：译文 ≤ 原文字节长度，超长靠润色砍字（教程原话「20 的限制就只能 10 个汉字」）。
- 扩容：字库首地址指针搜索 + ROM 末尾搬移（no$gba debug 跟踪显示程序定位读取点）。

### 路线 B：反编译改造（pret 系 + 中文 fork）
pokeemerald 源码级：charmap 增汉字映射、font 数据扩容（graphics/fonts）、`DecompressGlyph*` 缓冲扩到 16×16（4 tile）、`UpdateTilemap`/窗口逻辑适配、文本引擎重写。rh-hideout-chinese 与 bubble128 两个中文 fork 均声明「修改了与汉化后文字展示相关的代码」，文本以漫游&TGB 2011 绿宝石汉化为底。

### 路线 C：工具链化（FEBuilderGBA 生态，火纹 GBA 三部曲）
- **Draw utf-8 patch**：文本引擎改读 UTF-8 多字节 + Anti-Huffman，字体从「字库库（.fontall.txt+PNG）」运行时取模；GB2312 编码 + 字宽表（ASCII 半宽/汉字全宽）自动重建（Fix Font Width Table）。
- **缺字自动闭环**：glyph.py 检测译文缺字 → 系统字体自动生成缺字字形 → 入库复检（FEHRR issue#2 全流程）。
- **headless playtest**：`--playtest` 驱动 mGBA 0.10.5，JSON 场景（帧/按键/断言/watchdog）→ 输出判定 JSON + 最终 PNG，exit 0/1/2 三态。

### 路线 D：自建渲染层（我们所在的赛道）
- **MOTHER3 英化**：整套自建文本引擎（经典的 VWF+控制码+双 tile 布局）。
- **GBA_MultiMenu**：NFTR 字库（CMAP/CWDH/CGLP 三段）+ 逐像素 SetPixel 写 VRAM，不走 tile 引擎；1bpp/2bpp 解包。
- **tonc TTE**：可插拔 renderer（tilemap/bitmap/OBJ 三后端）+ tile-strip 列优先字形 + 逐像素位移合成。
- **本项目（hook 注入）**：F9 协议 + slot/短语 + v8 分配器，业内无公开同类。

## 三、可抄点判读（对照本项目痛点）

### ✅ 值得抄（按性价比排序）

**1. 译文字符集自动审计（FEBuilderGBA glyph.py 模式）——性价比最高**
- 业界做法：打包前扫全部译文 → 检测字库未收录字符 → 报告/自动补字 → 复检闭环。
- 我们现状：Middle 44 个符号字走 `--fallback-bdf`，但**没有「全部译文 ⊆ 字库」的打包期自动校验**；缺字现在的暴露方式是实机花屏/空白（正是用户四步法最贵的第③步）。
- 落地：打包流水线加一步——扫 translate.build.json 全部译文字符 → 对 Normal/Middle/Small 三库码表 → 输出缺字清单（零硬件依赖、纯 Python、风险零）。可再做自动 fallback 提示。

**2. headless 实机验证自动化（FEBuilderGBA --playtest 模式）**
- 业界做法：mGBA 无头驱动 + JSON 场景断言 + 自动截图，把「跑一遍验收」变成 CI 步骤。
- 我们现状：四步法第③步（实机截图）全手工，gdb 采集也要人工操作模拟器。
- 落地：mGBA 支持 `--lua`/movie + screenshot 脚本化；做一个 `verify_scene.py`（启动 ROM→定时按键序列→自动截 PNG），先覆盖最常回归的场景（对话框/血条/设置页/粉框）。与四步法互补：它管回归，gdb 管新场景勘测。【推论：mGBA Lua API 需实测确认截图+按键能力，未验证】

**3. NFTR 三值宽度表概念（CWDH：左 bearing / 墨宽 / 步进宽）**
- 我们现状：advance 固定（12/16px 全宽、8px 全宽），居中排版（血条名 r3=13、地图名）按 advance×字数算，复杂字两侧留白不准。
- 业界做法：三值分离——居中用 (bearing+ink)/2 校正，排版用 advance。
- 落地：BDF 生成时每字导出 ink 宽度表（打包期算好存 ROM），`GetStringWidth`/居中场景消费。中低优先级，等某个居中场景真实暴露观感问题再做。

### ⚠️ 已有对应物，无净收益
- **文本压缩/LZ**：我们已做 LZ 区间重注入（9510 replaced, 0 skipped），不弱于业界。
- **编码层**：主流 GB2312/UTF-8 双字节 vs 我们 F9 escape——我们的 slot+短语表（FNV 最长匹配、免重排、免指针重建）比纯码表强，不抄。
- **VWF 位移合成**：tonc TTE/MOTHER3 的逐像素右移合成 = 我们 print_glyph_px 的 extract_cols+blend 已实现（12px 亚 tile 拆分、相位 0/4），架构一致，无净收益。

### ❌ 不适用（注明原因，避免重复调研）
- **路线 A 静态替换**：前提是「汉字槽位常驻 VRAM+引擎零改动」；我们是 hook 动态注入+日文仍需在（slot 查不到要回落日文），静态替换会毁掉回落通路，且我们已超越其字数上限。
- **路线 B 反编译改造**：AXVJ00（红宝石日版）无 pret 反编译可依赖的等价物改造路径（pokeruby 存在但我们是注入架构不是重编译架构，且已实机验收的 v8 体系会全部作废）；其 DecompressGlyph 扩 4 tile、缓冲上栈的做法与我们现状相同（g128 栈上 128B、TL/BL/TR/BR 容器）。
- **GBA_MultiMenu 逐像素 SetPixel**：性能模型完全不同（菜单每帧重画 vs 打印机逐字推进），不适用。
- **官方窗口预留网格**：2026-09-08 判读文档已否（注入改不了窗口创建流程）。

## 四、结论

1. **tile 分配/防撞 UI 这个最大痛点，全网没有现成可抄方案**——主流路线根本不面对这个问题（静态=槽位常驻，反编译=改源码窗口逻辑）。v8 动态分配器在公开资料范围内无同类，只能继续走自己的 gdb 实测+场景表扩条路线。
2. 真正能立刻提升交付质量的是两件「工作流」而非「渲染」的事：**译文字符集自动审计**（消灭缺字花屏的实机暴露）与 **headless 实机回归**（把四步法第③步自动化）。
3. 三值宽度表（NFTR CWDH）作为备选改进挂账，等居中观感问题真实出现再做。
