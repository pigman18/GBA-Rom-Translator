# 调研：tile 分配器重构方案（2026-09-08）

> 目标：抛弃在现有 v8 上继续打补丁的思路，重构出一套满足两条硬指标的新方案：
> ① **尽量没有上限**（不随场景 charBase 缩水、不被历史字形吃满）；
> ② **尽量不撞 UI**（从模型上消灭时序竞争，而不是探测得更勤）。
> 本文只收录结构性方案；「写后校验/反向分配/段表扩容」等止血手段一律不作为候选，仅在文末说明为何不选。

---

## 一、现状 v8 的两个结构性缺陷（为什么必须重构）

### 1. 空间上限是「场景 × 历史」的乘积，不是「同屏需求」

- `hi = (4-cb)*512 clamp 1024`：cb0 场景满打满算 1024 tile，cb3 场景只剩 256 tile。上限随窗模板的 charBase 波动。
- ours 段表只记「我们占过哪段」，空间按**历史累计**增长；窗关闭靠 begin 全量重建才能回收。一窗同屏只需要 ~58 字（116 tile），却可能背着几千 tile 的历史包袱在 1024 上限里打转。

### 2. 三层探测全部「看现在」，防不了「未来写入」

- ①活引用层：扫 DISPCNT **当前**启用 BG 的 screenblock——新 BG 稍后才启用、官方稍后才写 tilemap 的，begin 时看不见。
- ②VRAM 非空层：校验 **alloc 那一刻**的内容——官方图形（地图图块滚动加载、状态图标懒加载）begin 之后才 DMA 进来的，alloc 时是空的。
- ③ours 段表：只防我们自己。
- 结论：**只要我们的 tile 和官方资源共处同一个 charBase 块，「撞 UI」就是概率问题，探测再细也只是降低概率。** 消灭它的唯一途径是物理隔离——两者永不同块。

### 3. 硬件边界盘点（方案必须在这个盒子里做）

| 资源 | 容量 | 约束 |
|---|---|---|
| BG VRAM | 64KB = 4 × charBase 块（每块 16KB = 1024 tile） | tilemap 表项 10bit → 一个 BG 只能引本块 1024 tile；BGxCNT.charBase 仅 2bit |
| screenblock | 32 个 × 2KB，与 charBase 块共用同一 64KB | 每块内含 4 个 screenbase 槽，选块时须连 screenbase 一起规划 |
| OBJ VRAM | 32KB = 1024 个 4bpp tile，与 BG 完全独立 | BG tilemap **引不到** OBJ tile；但 OBJ 精灵可自由叠显 |
| OAM | 128 个精灵槽 | 8×16 OBJ 恰好装下一个中文竖直 tile 对 |
| EWRAM 自留区 | FF4A~FF7F 约 54B 空闲 | 大表走官方堆 malloc（场景级生命周期），0x0203FFD2 之后严禁占用 |

关键换算：Middle 中文一个字 = 竖直 tile 对 = 2 tile。
- 独占一个 charBase 块 → **1024 tile = 512 个同屏字**（一窗两行对话 58 字仅需 116 tile，余量 4.4 倍）。
- 官方引擎实际同屏并发的字形数由窗几何决定，是有限小数；6807 总字数从来不需要同时驻留。

## 二、候选方案

### 方案 A【主推】：场景级独占 charBase + 字形按需载入（物理隔离，双目标同解）

核心思想一句话：**不再在官方的街区里找空房，而是把整条街区包下来。**

#### A1. 架构

```
场景进入（InitTextPrinter 首窗 / scene_cfg 声明）
   │
   ├─ ① 扫 DISPCNT 启用 BG 的 BGxCNT → 得出官方占用的 charBase 集合
   ├─ ② 从空闲块中选一块 C（scene_cfg 每场景静态声明首选块，运行时复核）
   ├─ ③ 重定向本窗模板 charBase → C（BGxCNT 与 tileData 指针同步改）
   ├─ ④ 窗 tilemap（2KB screenbase）也搬进 C 块内空槽（可选，彻底自持）
   └─ ⑤ 会话游标复位，分配器从 C 块 tile0 顺序推进，不再做任何「避让探测」

绘制每字：
   命中（会话位图已有）→ 直接写 tilemap 引用
   未命中 → 从 ROM 字库 DMA 128B 到游标 tile 对 → 写 tilemap → 标位图
   （128B 拷贝/字，一屏 58 字 ≈ 7.4KB，一帧内完成，无性能问题）

窗关闭/场景退出：begin 全量重建游标归零（机制沿用），块 C 整块归还池
```

#### A2. 两条硬指标怎么被满足

**不撞 UI（结构性消除）：**
- 官方引擎对块 C **零读写**——它甚至不知道这块存在。三层探测整体退役（保留一条轻量 tripwire：会话中抽检块内非 ours 数据出现即打 gdb 日志告警，用于发现未知官方模板，不参与分配）。
- 时序竞争从「概率降低」变成「不存在」：官方未来任何 DMA 都落在自己的块里。

**无上限（三重含义）：**
1. **空间恒定**：任何场景都是 1024 tile，不再随 cb3 缩到 256。
2. **空间=同屏需求**：位图按会话重建，历史字形不再累计占位。512 字/窗的同屏容量在数学上受窗几何封顶（最大文本窗 ~15 行 × 28 列 = 420 字 = 840 tile < 1024），**不会溢出**——这是硬件几何保证的，不是运气。
3. **总量无上限**：6807 字全部走「按需载入」，驻留量永远只等于当前可见字形。将来若某巨型窗真超了，加 LRU 淘汰（见 A4）即可，总量依旧无界。

#### A3. 半角字符的连带处理（重构里最容易漏的坑）

模板 charBase 重定向后，**窗内所有 tile 引用必须都指向块 C**——包括「119」这类官方原生半角字形（官方会把它们画进官方字库 atlas）。两条路线：
- **半角也接管**：hook 在官方画完 atlas 后把用到的半角 tile 32B 拷进块 C，tilemap 引用块 C 副本（每字一次 32B 拷贝，成本可忽略）；或干脆半角字形也进我们的 ROM 字库（ASCII 段已有），彻底一个来源。
- 推荐后者：一个来源、一条链路，消灭「两种字形两种归属」的中间态。

#### A4. 二期增强（非首版必需）：块内字形缓存 + LRU

首版用「会话内顺序分配 + begin 重建」已够；若实测发现高频重绘场景（粉框横幅随地图滚动反复重绘）拷贝带宽成为问题，再上：
- 字形条目表 `{code, refcount, slot}` 存官方堆（malloc/scene 生命周期），free-list 链表直接嵌在空闲 tile 数据里（agb 框架手法，零额外内存）；
- 命中免拷贝、refcount=0 优先回收、全满时逐出最旧零引用项；
- 收益：重绘免重载；成本：一张表 + 淘汰逻辑。**首版不做，避免一次性引入两个新变量导致归因困难。**

#### A5. 风险与前置确认（每条都要静态核实后才动手）

| # | 风险 | 核实方法 |
|---|---|---|
| 1 | 某场景 4 块全被官方占用（如战斗：cb0 血条/cb2 对话/cb3 战斗 UI/cb1 未知） | 逐场景列 DISPCNT+BGxCNT 清单（静态+gdb 各一遍），产出「场景→空闲块」表；无空闲块的场景走方案 B |
| 2 | 官方存在 scene_cfg 未收录的隐藏窗模板，也写块 C | A1-⑤ 的 tripwire 抽检兜底；实测阶段逐场景截图验证 |
| 3 | BGxCNT.charBase 与 tileData 指针不同步导致花屏 | 改模板一处（charBase@1/tileData@0x0C/screenBase@2 三字段联动），单场景先试点 |
| 4 | 半角字符仍写官方 atlas 导致「119」消失/错位 | A3 路线，粉框场景作为首个试点（它同时含半角+中文，是最严苛的试金石） |

### 方案 B：OBJ 精灵文字层（无块可占场景的根治路线）

核心思想：**BG 路走不通的地方，走 OBJ 路——OBJ tile 与 BG VRAM 完全独立，官方 BG 图形物理上碰不到。**

- 每个中文字 = 1 个 8×16 OBJ（恰好装下竖直 tile 对），复用现有字形数据的 tile 布局，零格式转换。
- OBJ tile 从官方精灵分配器取（hook 同一个分配器或直接调它）——和官方精灵共用一套记账，**共处但不冲突**（有账本的共存，不是猜测共存）。
- 容量：1024 OBJ tile = 512 同屏字（全场景所有窗合计）；一窗 58 字 = 116 tile + 58 个 OAM 槽（128 上限内）。对话场景官方精灵很少，预算宽裕。
- 显示层叠：OBJ priority 设为与所在窗 BG 相同，随窗显隐；窗关闭即释放。
- **成本与风险**（比方案 A 高一档，故只作 A 的补充）：
  1. OAM 竞争：官方大量精灵的场景（战斗特效）可能挤占 OAM 槽——需要实测各场景官方 OAM 峰值；
  2. 文本逐字推进要逐字生/灭 OBJ，游标、翻页、滚动逻辑全部重写一遍精灵版；
  3. 混色/窗效果：OBJ 进 WINDOW/blend 的行为与 BG 不同，血条名等已用 blend 的场景要单独适配。
- **适用判据**：方案 A 的场景分级表里「4 块全忙」的场景（预计战斗 UI 是主要客户）。

### 方案 C：官方字库 atlas 搬迁（使能器，可选）

若某场景 4 块全忙且 OBJ 路线也不合适，最后一个办法是**把官方字库 atlas（cb0 0x208~0x2D1）搬到别的块**，腾出 cb0：
- 一次性 ROM 补丁：atlas 加载目标的 tileBase 常量 + 所有指向 atlas 的模板字段 + 已烧进 ROM 的相关 tilemap 数据重写。
- 影响面大、收益只是「多一块」，**仅在前两案都不可行的场景单独评估**，不进主路线。

## 三、方案对比与推荐

| 维度 | A 独占块+按需载入 | B OBJ 精灵层 | C atlas 搬迁 |
|---|---|---|---|
| 撞 UI | **结构性消除** | 结构性消除（BG 侧） | 消除（腾块后同 A） |
| 空间 | 恒 1024/窗，几何封顶不溢出 | 1024 全场景共享 | 同 A |
| 总字量上限 | 无（按需载入） | 无 | 无 |
| 改动量 | 中（scene_cfg 扩展+模板重定向+半角接管） | 大（渲染层整体重写） | 大（ROM 级搬迁） |
| 新风险 | 场景块分级表准确性 | OAM/blend 适配 | 影响面不可控 |
| 试点难度 | 低（粉框一场景先跑通） | 高 | 高 |

**推荐分期：**

1. **第一期 = 方案 A 首版**：场景级独占块 + 会话顺序分配 + 半角字符接管同块化。先拿粉框「119号道路」试点（半角+中文混合、高频重绘，是检验两条指标的天然考场），实机四步法验收后再铺场景表。
2. **第二期**：块内 LRU 缓存（仅当重绘带宽实测成为瓶颈）；无块场景接入方案 B。
3. **全程退役**：三层探测降级为 tripwire 日志，不再参与分配决策。

**验收口径（钉死，防重蹈「模拟=证据」覆辙）：**
- 静态：场景→空闲块分级表每一行都有 DISPCNT/BGxCNT 实测数据背书；
- 动态：gdb 断点确认块 C 内整个会话零官方写入、零非 ours 字节；
- 实机：粉框「119号道路」+ 导航窗 + 血条名三场景截图逐像素与 BDF 对照；
- 任何环节只有模拟/比对通过的，一律标【推论/未验证】，不作为交付依据。

## 四、为什么不选其他路线（留档防回头）

- **写后校验（VBlank 比对重写）**：止血，治标；把故障率压低但保留故障面，且每帧 VRAM 回读成本高。不符合「重构」要求。
- **反向分配（hi→lo）+ 段表扩容**：仍是共块共存，时序竞争原样保留；只推迟碰撞不消灭碰撞。
- **HBlank 逐行搬运 / IWRAM 缓冲**：CPU 与 IWRAM 预算都不允许，复杂度失控。
- **在 v8 上继续加第四层探测**：探测层数与正确率无关（见一、2），方向本身错误。
