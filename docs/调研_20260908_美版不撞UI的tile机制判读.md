# 调研 2026-09-08：美版 Ruby「tile 领号」为什么不撞 UI（源码级判读）

> 问题：美版 Ruby 汉化（pokeRS 系）同样是「运行时领 tile 号」，为什么它不出现我们 AXVJ00 的撞 UI 问题？
> 方法：静态分析权威反编译源码 `tools/pokeruby/src/text.c` / `src/menu.c` / `src/text_window.c`（美版 Ruby，与 AXVE 1.0 对应），**未开模拟器/gdb**。
> 标注：【源码实证】= 反编译源码直接可读；【推论】= 由源码推导但未实测。

---

## 0. 一句话结论

**美版那个不叫「分配器」，叫「落址函数 + 会话级复位 + 初始化期静态分区」。**

它领的号是**屏幕位置**（第几行第几列的格子），我们 v8 领的号是**字形缓存槽**。

- 位置寻址：上界 = 窗口面积（硬上界，写在公式里），幂等可覆盖，**不需要回收**；
- 内容寻址：上界 = 会话内出现过的不同字形数 × 缓存策略（无界），**必须回收**，回收判据出错就撞邻居。

撞 UI 是后者的结构性代价，不是调参能修的。

---

## 1. 证据一：GetCursorTileNum 是坐标函数，不是分配器

`tools/pokeruby/src/text.c:4380`【源码实证】：

```c
static u16 GetCursorTileNum(struct Window *win, u32 xOffset, u32 yOffset)
{
    u16 index;
    if (win->textMode == TEXT_MODE_UNKNOWN2)          // tm2：VWF 主路径
        index = win->tileDataStartOffset
              + win->tileDataOffset
              + (((win->top  + win->cursorY) >> 3) + yOffset) * win->width
              + (((win->left + win->cursorX) >> 3) + xOffset);
    else                                              // tm0 / tm1
        index = win->tileDataStartOffset + win->tileDataOffset + 2 * xOffset + yOffset;
    return index;
}
```

两条分支的共同点：**给同一组 (cursorX, cursorY) 永远算出同一个 tile 号**。

- **tm2（主力，菜单/列表窗）= 网格落址**：`行 × width + 列`，等价于「VRAM 文本区就是窗口的帧缓冲」。
  上界 = `win->width * win->height`（窗口 tile 面积），**写死在公式与 cursorX/cursorY 的取值域里**，
  越界在数学上不可能——`DoScroll_TextMode2`(text.c:3082) 滚动时只 CpuFastCopy 内容、不推进 tileDataOffset，
  重画旧行覆盖的是同一批号 → **幂等、无泄漏、无碎片、无需 GC**。
- **tm0（对话主窗模板 81E6C58，text.c:517：font3 / textMode 0 / width 26 / height 20）= 顺序领号**，
  但推进粒度是 **8px 列** 而不是「字」：
  ```c
  // text.c:2804 AddToCursorX
  u8 x = win->cursorX;
  win->cursorX += deltaX;
  if (((win->left + win->cursorX) & 0xF8) != ((win->left + x) & 0xF8))
      win->tileDataOffset += 2;      // 仅在跨 8 像素列时 +2（上/下两个 tile）
  ```
  同一列内多个字母共享同一 tile（亚 tile 合并：`DrawGlyphTiles` text.c:4330
  `startPixel = (win->left + win->cursorX) & 7`，配 `ShiftGlyphTile_*` mask 位移合成）。
  所以 **tile 消耗 ≈ ceil(行像素长度 / 8) × 2，与每字 advance 无关**。

> 这条正是 `docs/重构_20260908_pokeRS式地基更换蓝图.md` §0 那句
> 「每行消耗的 tile 列数 = 行像素长度÷8，与每字 advance 无关」的源码出处。

## 2. 证据二：会话级复位，游标从不跨会话累积【源码实证】

| 复位点 | 位置 | 行为 |
|---|---|---|
| `Text_InitWindow` | text.c:1981 | `win->tileDataOffset = 0` |
| `Contest_StartTextPrinter` | text.c:2036 | `win->tileDataOffset = 2` |
| `Text_ClearWindow` | text.c:3123 | 清完行后 `win->tileDataOffset = 2` |

即：**每开一次窗/清一次窗，号码从头开始**。tm0 的顺序游标是「本次绘制用了几列」，
不是「全局已消耗多少 tile」。需求上界 = 一屏容量，且周期性归零 ——
不存在我们 v8「会话内单调累积 → 需要 ours-GC / 负缓存 / 回卷」这类问题。

（段头那 2 个 tile 是空白 tile：`InitVariableWidthFontTileData` text.c:1800-1809 预填
`startOffset` 与 `startOffset+1`，`GetBlankTileNum` 复用它们。）

## 3. 证据三：UI 图形和文字走同一条有序 bump 链，天然排队不重叠【源码实证】

`src/menu.c:113-122 InitMenuWindowInternal`：

```c
gMenuTextTileOffset = tileOffset;                                              // 起点（=1）
gMenuTextWindowTileOffset      = InitWindowTileData(gMenuWindowPtr, gMenuTextTileOffset);   // 字库段
gMenuTextWindowContentTileOffset = TextWindow_SetBaseTileNum(gMenuTextWindowTileOffset);    // 窗口框段
TextWindow_LoadStdFrameGraphics(gMenuWindowPtr);                               // 框画进这一段
gMenuMessageBoxContentTileOffset = TextWindow_SetDlgFrameBaseTileNum(gMenuTextWindowContentTileOffset); // 对话框框段
```

- `InitWindowTileData`(text.c:1763) 返回**下一段起点**：
  - MONOSPACE：装 256 字形（font0/3 每字 2 tile）→ `+512`；其余 `+256`（text.c:1812-1858）
  - UNKNOWN2：`startOffset + 2 + width*height`（text.c:1809）—— **按窗口面积预留**
- `TextWindow_SetBaseTileNum`(text_window.c:101) = `sTextWindowBaseTileNum = n; return n + 9;`
  （窗口框固定 9 tile）
- 其它子系统同一套路：`TextWindow_SetBaseTileNum(20)`（egg_hatch.c:416、trade.c:1081）、
  `TextWindow_SetBaseTileNum(2)`（evolution_scene.c:377、trade.c:3558）、
  `TextWindow_SetBaseTileNum(0x12/0x22)`（battle_bg.c:268-270）

**结论：VRAM 是「进入场景/开菜单时一次性切段」的静态分区**，字库段 → 框段 → 内容段 → …
每个人按顺序领一段固定长度，**段与段物理不重叠**；每次重新进入场景都从同一原点重切一遍，
所以没有长期漂移。UI 图形不是「不知道躲哪的常驻住户」，而是**链上登记过的邻居**。

我们 AXVJ00 的处境正好相反：UI 图形（血条、光标、图标、框）是各场景硬编码地址的常驻区，
**完全不参与我们的分配协议**，v8 只能在共享 charblock 里「探测谁看起来是空的」——
这就是撞 UI 的结构性来源。

## 4. 证据四：西文字符集小 → 可常驻，汉字装不下 → 被迫做 cache【推论，但数学硬】

- 美版 MONOSPACE 一上来把 **256 字形整份常驻 VRAM**（512 tile），之后 tilemap 只写索引，
  **零运行时分配**（`WriteGlyphTilemap` text.c:2594-2621：`tileDataStartOffset + 2*glyph`）。
- 汉字库 7168 字形 × 4 tile（16×16 四象限）= 28672 tile ≫ 一个 charblock 的 1024 tile。
  ⇒ **必须**在运行时把用到的字形搬进 VRAM ⇒ 必然出现「字形缓存 + 淘汰」⇒ 必然要回答
  「哪个 tile 现在没人用」这个美版根本不用问的问题。

**所以：不是美版更聪明，是它的字符集小到不需要分配器。**

## 5. 反证：pokeRS 汉化为什么也不撞

pokeRS（`tools/Pokemon_GBA_Font_Patch/pokeRS/`）只 patch 三个点
（`GetGlyphWidth` / `GetStringWidth` / `DrawGlyphTiles`），**完全沿用官方的
`GetCursorTileNum` + `UpdateTilemap` + `DrawGlyphTile_ShadowedFont`**（见
`docs/调研_20260827_pokeRS类12px机制与日版AXVJ00接入分析.md` §1.3）：

- 中文画成 16×16 四象限，按 `cursorX += 8`（手写）+ 返回 4 = **12px advance**，
  `tileDataOffset += 2` 每列；
- 号仍然是**落址出来的**，仍然落在窗口网格内 ⇒ 上界仍是窗口面积。

旁证：pokeRS 的场景级 patch 清单（同文档 §1.5）全是**坐标/拷贝长度适配**
（HP 框名字 gfx 拷贝 32→20/24 字节防遮汉字上沿、狩猎球名 r1=4、寄放系统 r3=0x12…），
**没有一条是「挪 tile 号躲 UI」**。若它存在 tile 冲突，补丁形态不会是这样。

⚠️ 【推论】但它有另一个代价：12px advance 下一行能放的字数变少，
排版/居中必须靠 `GetStringWidth` 同步改口径，否则会溢出窄窗（我们 2026-09-07 粉框花屏就是这类，
不是 tile 冲突）。

## 6. 对照表

| 维度 | 美版 Ruby（原生 + pokeRS） | 我们 AXVJ00 + v8 |
|---|---|---|
| 号从哪来 | 落址函数 `f(窗口, 行, 列)`（tm2）/ 会话内列游标（tm0） | 运行时「找空位」分配器 |
| 语义 | 帧缓冲（位置寻址） | 字形缓存（内容寻址） |
| 上界 | 窗口面积 / 一屏容量（硬） | 会话内不同字形数（软，随文本增长） |
| 是否幂等 | 是，同位置同号，可重复覆盖 | 否，同字重绘可能领新号 |
| 需要回收吗 | 不需要（会话复位即归零） | 需要（ours-GC / 负缓存 / 三层探测） |
| UI 图形关系 | 同链排队，段不重叠 | 硬编码常驻区，不参与协议 → 撞 |
| 单字 tile 成本 | ≈ 行像素/8（亚 tile 合并） | 12px：2~3 tile/字；16px：4 tile/字 |
| 复杂度代价 | 空间换确定性（窗口面积常驻） | 省空间，换来 GC 正确性负担 |

## 7. 可迁移的三条设计原则（若要抄）

1. **位置寻址优先**：tile 号 = `f(窗口, 行, 列)`，不做全局自由分配。上界自动落在窗口面积内，
   幂等 ⇒ 无需 GC、无需活引用位图、无需负缓存（v8 的全部复杂度可直接删掉）。
2. **初始化期一次性切段，UI 图形与文字共链**（或至少把 UI 常驻区登记为「禁分配区」），
   避免运行时「探测谁看起来空」。
3. **亚 tile mask 合并**：让 tile 消耗 = 行像素 / 8，与每字 advance 解耦 —— 汉字变宽只让行变长，
   不会让「每字独占 tile」。

这正是 `docs/重构_20260908_pokeRS式地基更换蓝图.md` 已拍板的方向；本调研为其补上源码级证据链。

### 迁移到 AXVJ00 的已知障碍（沿用旧结论，不重开）
- AXVJ00 **没有** `sGlyphMasks` / `DrawGlyphTiles` / `GetGlyphWidth` / `GetStringWidth`
  （全 ROM 特征字节零命中，`调研_20260908` W1 已定）→ mask 合并引擎需整表移植。
- AXVJ00 的 tm2 是 `win[0x20]` 运行指针 **+0x40/字**（真·顺序领号，会话内单调）——
  本就是缓存语义，加中文后问题被放大；换成网格落址需要**为每个窗口划出自留网格**，
  而 AXVJ00 窗口 tileData 是共享 charblock，没有现成的 per-window 段 ⇒ 这是改造的核心工作量。
- OBJ 空闲 tile 对 BG 文字物理不可用（tilemap 10bit + charBase 上限够不到 0x06010000）。

## 8. 遗留【推论/未验证】
- 美版各场景「内容段」实际分配长度与真实需求的安全余量未逐个核算（需要 gdb 采
  `GetCursorTileNum` 序列 + 窗口段表对照）。若某场景余量为负，美版同样会越界写邻居——
  只是官方调过，我们没看到。
- 美版 tm0 顺序领号在「不清窗的连续长会话」下的最坏需求未实测（理论界 = 一屏字位 × 每字列数）。
