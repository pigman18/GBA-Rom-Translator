# 调研 2026-09-09：tm1 菜单窗 w×h 映射（纯静态反推）

> 结论先行，证据自反汇编（`tools/disasm_rom.py`），不引用旧实现/旧文档。
> 四件套（Task #1）已在 config 权威树落地；本文只回答「tm1 窗的 w×h 从哪来、值是多少」。

## 一、结论（TL;DR）

1. **w×h 不是「可见框」尺寸，是文本区（tile data 图集）的预算/行距**。
   美版文本引擎里 `width/height` 是 `struct WindowTemplate` 的字段，值为 **30×20（全屏文本区）**，
   不是某个菜单框的 26×6、28×4 之类。可见框尺寸由「框几何 + tilemap + cur_x/cur_y」另算。
2. **tm1 菜单窗与 tm3 对话窗共用同一套 w×h = 30×20**。
   美版 58 个 `WindowTemplate` 中 **51 个是 30×20**；tm3 落址里写死的步长 30 正是这个 `width`。
3. 只有 **7 个特例模板**（26×20 / 8×60 / 8×64 / 16×32×3 / 32×32）需要逐窗处理，
   它们都不走 `MenuDrawStdWindowFrame` 标准框（不在 161 调用点里），属另类文本区。
4. 日版模板是 **24B 且没有 w×h 字段**（这正是要移植的根因）；移植时从**美版孪生模板**取 w×h，
   标准窗一律 `us_win_open(win, start, 30, 20)`。

## 二、证据链（全部自反汇编）

### 2.1 日版模板 24B 无 w×h —— `InitTextPrinter @0x08002C68`

```
0x08002C84: ldr r5,[r0]        ; r5 = win[0] = 模板
0x08002C86: ldrb r4,[r5,#9]    ; 模板[9]
0x08002C88: strb r4,[r0,#0xa]  ; → win[0xA]   (textMode)
0x08002C8A: ldrb r4,[r5,#8]    ; 模板[8]
0x08002C8C: strb r4,[r0,#0xb]  ; → win[0xB]   (fontNum)
0x08002C8E: ldrb r4,[r5,#5]    ; 模板[5] → win[0xC] (fg)
0x08002C92: ldrb r4,[r5,#6]    ; 模板[6] → win[0xD] (bg)
0x08002C96: ldrb r4,[r5,#7]    ; 模板[7] → win[0xE] (shadow)
0x08002C9A: ldrb r4,[r5,#4]    ; 模板[4] → win[0xF] (palette)
0x08002C9E: str r1,[r0,#0x10]  ; win[0x10] = text*
0x08002CA2: strh r2,[r0,#0x16] ; win[0x16] = tile_base
0x08002CA4: strh r6,[r0,#0x18] ; win[0x18] = tile_offset = 0
0x08002CA6: strb r3,[r0,#0x1a] ; win[0x1A] = cur_x (tile)
0x08002CAE: strb r4,[r0,#0x1c] ; win[0x1C] = cur_y (tile)
```

日版模板字段：`[4]=palette [5]=fg [6]=bg [7]=shadow [8]=fontNum [9]=textMode`，
随后 **直接跳到 `[0x0C]=tileData*`、`[0x10]=tilemap*`** —— **没有 tilemapLeft/tilemapTop/width/height**。
（对照：美版 `WindowTemplate` 在 0x0B/0x0C/0x0D/0x0E 正是这 4 个字段。）

### 2.2 美版模板 28B 有 w×h —— `struct WindowTemplate`（pokeruby include/text.h）

```c
struct WindowTemplate {
    u8 bgNum;          // 0x00
    u8 charBaseBlock;  // 0x01
    u8 screenBaseBlock;// 0x02
    u8 priority;       // 0x03
    u8 paletteNum;     // 0x04
    u8 foregroundColor;// 0x05
    u8 backgroundColor;// 0x06
    u8 shadowColor;    // 0x07
    u8 fontNum;        // 0x08
    u8 textMode;       // 0x09
    u8 spacing;        // 0x0A
    u8 tilemapLeft;    // 0x0B
    u8 tilemapTop;     // 0x0C
    u8 width;          // 0x0D  ★
    u8 height;         // 0x0E  ★
    // 0x10 tileData*  0x14 tilemap*  0x18 maybeUnused
};
```

### 2.3 美版把模板 w×h 拷进 win —— `Text_InitWindow @0x08002DC0`

```
0x08002DF6: ldrb r0,[r5,#0xd]   ; 模板[0xD] = width
0x08002DF8: strb r0,[r4,#9]     ; → win[9]  = width  ★
0x08002DFA: ldrb r0,[r5,#0xe]   ; 模板[0xE] = height
0x08002DFC: strb r0,[r4,#0xa]   ; → win[0xA]= height ★
0x08002DEE: ldrb r0,[r5,#0xb]   ; 模板[0xB] → win[7] (tilemapLeft)
0x08002DF2: ldrb r0,[r5,#0xc]   ; 模板[0xC] → win[8] (tilemapTop)
```

### 2.4 美版四件套把 w 当「行距」用

- `InitVariableWidthFontTileData @0x08002AD8`：
  ```
  0x08002B10: ldrb r2,[r4,#9]   ; width
  0x08002B12: ldrb r1,[r4,#0xa] ; height
  0x08002B14: muls r1,r2,r1     ; w*h
  0x08002B0E: adds r0,r0,r1     ; return start + 2 + w*h
  ```
- `GetCursorTileNum @0x080069D8`（textMode==2 分支）：
  ```
  0x080069F6: ldrb r1,[r3,#9]   ; width
  0x080069F8: muls r0,r1,r0     ; width * ((top+cursorY)>>3 + yOff)
  → tile = start + 2 + width*row + col
  ```
  即 `width` 是 **tilemap 行距（30）**，`left/top`（像素，=tile*8）定位可见框内原点。

### 2.5 日版四档落址对照（FontFuncTable @0x081BB3AC，7 项）

| 项 | 地址(thumb) | 落址方式 |
|---|---|---|
| tm0 | 0x08003568 | `bl 0x8003520` 后 `tile_offset+=2`、`cursorTileX+=1`（线性） |
| tm1 | 0x0800360C | `win[0xB]`(=fontNum) 查表 → `bl 0x81B12DC`（变宽字形直绘图集） |
| tm2 | 0x0800338C | `win[0x20]` 缓冲直绘，`win[0x20]+=0x40/字` |
| tm3 | 0x08003494 | `tile = base + cur_x + 2 + cursorTileX + 30*(cur_y+cursorTileY)`，**步长 30 写死** |

> tm3 写死的 30 == 美版模板 `width`==30；tm1 的 `win[0xB]` 是 fontNum（不是 w×h），
> 所以 tm1 的「尺寸」隐式来自窗口 tilemap 布局 + 变宽字体渲染，没有独立 w×h 字段。

## 三、美版 58 个模板 w×h 全量（数据 dump 自 0x081E6C3C 起）

**51 个 = 30×20**（fontNum 多为 3，textMode 多为 2）。特例 7 个：

| 模板地址 | w×h | fontNum | textMode | 备注 |
|---|---|---|---|---|
| 0x081E6C58 | 26×20 | 3 | 0 | 窄一档的线性文本区 |
| 0x081E6CAC | 8×60  | 4 | 2 | 竖条长文本（非标准框） |
| 0x081E6D38 | 8×64  | 3 | 2 | 竖条长文本 |
| 0x081E7048 | 16×32 | 3 | 2 | L=16，半宽 |
| 0x081E70F0 | 32×32 | 3 | 2 | 整张 tilemap |
| 0x081E7278 | 16×32 | 3 | 2 | 半宽 |
| 0x081E7294 | 16×32 | 4 | 2 | 半宽 |

`gMenuTextWindowTemplate @0x081E6CE4` = **30×20**（fontNum=3, textMode=2），是标准对话窗的孪生模板。

## 四、框几何（161 调用点）≠ 模板 w×h

`tools/scan_frame_calls.py` 命中 `Menu_DrawStdWindowFrame @0x0806F224` 共 **161 处**，
归属 **121 个函数**（完整表见 `tools/frame_call_map.txt`）。它们给的是**可见框**的 tile 几何：

- 主菜单/新游戏开场白：26×6（`InitMainMenu`、`Task_NewGameSpeech*`）
- RTC 时间窗：28×4（`Task_MainMenuWaitForRtcErrorAck`）
- 对话框（满屏底框）：30×6 / 30×7 / 30×20（`sub_80B95F0`、`ReceiveDaycareMailData` 等）
- 队伍 HP：24×6（`PartyMenuDoPrintHP`）
- 满屏文本区：30×20、32×32 级（`sub_80B95F0` 等）

这些是**框**，落在 tilemap；而引擎要的 `w×h` 是**图集预算**（30×20）。两者量纲不同，不可混用。
（这也是「假划界」事故的教训来源之一：拿框几何当图集预算，或者反过来，都会写越界。）

## 五、映射结论

| 文本窗类别 | w×h（喂给 us_win_open） | 依据 |
|---|---|---|
| tm3 对话窗（NPC/菜单文本） | **30 × 20** | 美版孪生 `gMenuTextWindowTemplate`；tm3 落址步长 30 |
| tm1 菜单窗（标准框） | **30 × 20** | 美版 51/58 模板统一 30×20 |
| 特例（8×60 / 8×64 / 16×32 / 32×32 / 26×20） | 见上表，逐窗处理 | 非标准框，暂不落在 161 调用点 |

**移植落地**：`InitTextPrinter_hook` 对 tm1/tm3 统一走 `us_win_open(win, start, 30, 20)`；
`cur_x/cur_y`（win[0x1A]/win[0x1C]，日版已是 tile）继续作为可见框原点，
特例模板在实测到对应窗口时再按表补 w×h。
