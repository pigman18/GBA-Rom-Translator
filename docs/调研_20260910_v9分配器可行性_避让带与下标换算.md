## 一、cb 下标互转算法（可直接落成 4 个宏）

### 1.1 三个坐标系

| 名字 | 符号 | 含义 | 值域 |
|---|---|---|---|
| **窗内相对号** | `t` | 写进 BG screen entry 的 tile 号；也是 `tileData + 32*t` 里的 `t` | `[0, 1024)` |
| **全局 tile 下标** | `g` | 物理 VRAM 第几个 32B tile（`0x06000000 + 32*g`） | `[0, 2048)` |
| **charBlock 号** | `cb` | 模板 `tpl[1]`（`TPL_CHARBASE`） | `0..3` 可用，`4/5` = OBJ |

### 1.2 正逆变换

```
正：g = (cb << 9) + t              // cb*512 + t，512 = 0x4000/32 = 每 cb 的 tile 数
逆：cb = g >> 9;  t = g & 0x1FF    // 仅对「t < 512 的规范表示」成立
跨块窗逆：t_win = g - (cb_win << 9) // cb_win 取自模板；t_win 允许 ≥ 512（溢出到后续 cb）
```

窗可寻址范围（这是上面两个逆变换必须配对用的原因）：

```
lo_g(cb) = cb * 512
hi_g(cb) = lo_g(cb) + min(1024, (4 - cb) * 512)     // = 与现有 v8_alloc_hi 完全一致
```

| cb | 窗内 t 上限 | 可寻址全局区间 |
|---|---|---|
| 0 | 1024 | `[0, 1024)` |
| 1 | 1024 | `[512, 1536)` |
| 2 | 1024 | `[1024, 2048)` |
| 3 | 512  | `[1536, 2048)` |

### 1.3 用户示例的勘误

> 用户例：`cb0, 0 => 0`（✔）；`cb1, 5 => 516`（**✘，应为 517**）

`g = 1*512 + 5 = 517`。516 = `512 + 4`，是一处差一。

### 1.4 为什么必须引入全局下标（本方案最硬的理由）

因为**同一个物理 tile 在不同窗里有不同的 `t`**：

- PSS 的 B 图标字模物理落在 `g = 522..525`（`0x20A..0x20D`，见 `game.h:CHS_PSS_B_VRAM_LO`）。
- 对 **cb0** 的窗，它是 `t = 0x20A..0x20D`（合法，t<1024）；
- 对 **cb1** 的窗，它是 `t = 0x0A..0x0D`。

⇒ 只要避让带用「相对号 + cb」记录，就**必然漏判跨块别名**；用全局下标则天然正确。**这一条同时也是「避让带必须全局下标化」的证明。**

### 1.5 落码建议（`include/tile_alloc.h`）

```c
#define CB_TILE_SHIFT   9u      /* 512 tile / charBlock */
#define CB_TILE_COUNT   512u
#define BG_TILE_MAX     2048u   /* cb0..cb3；cb4/5 = OBJ */
#define TILEMAP_T_NUMBITS 10u   /* screen entry tile 字段 */
#define TILEMAP_T_MAX   1024u

static inline uint16_t chs_g_of(uint8_t cb, uint16_t t) { return (uint16_t)(((uint16_t)cb << CB_TILE_SHIFT) + t); }
static inline uint8_t  chs_g_cb(uint16_t g)             { return (uint8_t)(g >> CB_TILE_SHIFT); }
static inline uint16_t chs_g_rel(uint16_t g, uint8_t cb){ return (uint16_t)(g - ((uint16_t)cb << CB_TILE_SHIFT)); }
static inline uint16_t chs_g_hi(uint8_t cb)             { unsigned h = (cb < 4u) ? (unsigned)(4u - cb) * CB_TILE_COUNT : 0u;
                                                          return (uint16_t)(h > TILEMAP_T_MAX ? TILEMAP_T_MAX : h); }
```

⚠ `chs_g_rel` 只在 `chs_g_of(cb,·)` 值域内自洽；调用前必须过 `[lo_g, hi_g)` 检查。

## 二、可分配空间：`0-2560` 不成立，正确值是 `0-2048`

**GBA 内存映射**：BG VRAM `0x06000000–0x0600FFFF` = 64KB = **2048 tile = cb0..cb3**；`0x06010000` 起是 **OBJ VRAM**（cb4/cb5）。`2560 = 5*512` 恰好覆盖到 cb4，**写进去就是砸精灵图**。

**ROM 自身证据**（比引用手册更有说服力）：血条模板 `0x081BB40C` 的 `tileData = 0x06010000` —— 日版引擎自己就把 tm2 血条缓冲直接画进 OBJ 区（`0x06010000 + 32*t`），随后 `CpuSet` 给精灵。这说明「`0x06010000` 之上属于 OBJ」不是外部规则，而是本 ROM 的既有约定。

另有第二重约束（已在 2026-09-09 事故中实证）：`UpdateTilemap@0x080036DC` 直接 `strh (t | pal<<12)`，**不做 `& 0x3FF` 掩码**，而 screen entry 的 tile 字段只有 10 bit ⇒ **`t ≥ 1024` 会被硬件截断成 `t & 0x3FF`**，tilemap 指向完全无关的 tile。这与全局下标无关，是**窗内相对号**的独立上限 —— 也就是 `hi_g(cb)` 里那个 `min(1024, ·)` 的来历。

**⇒ 分配域 = `[0, 2048)`，且逐窗再受 `[lo_g(cb), hi_g(cb))` 限制。**

### 2.1 静态避让带（读 ROM 模板得到，非扫描）

模板 `screenBaseBlock` 字段换算：`g_sb = sb * 64`（每 screenblock 2KB = 64 tile）。

| 模板 | cb | sb | tileData `g` | tilemap 全局区间 | textMode |
|---|---|---|---|---|---|
| 招式 `0x081BB3F4` | 0 | 24 | 0 | `[1536, 1600)` | 0 |
| 血条 `0x081BB40C` | 0 | 0 | 2048（OBJ） | 无（`tilemap=NULL`） | 2 |
| 队伍 `0x081BB43C` | 1 | 30 | 512 | `[1920, 1984)` | 1 |
| 对话框A `0x081BB46C` | 2 | 31 | 1024 | `[1984, 2048)` | 3 |
| 请选择 `0x081BB484` | 2 | 15 | 1024 | `[960, 1024)` | 1 |
| `0x081BB49C` | 0 | 31 | 0 | `[1984, 2048)` | 1 |
| 战斗 UI `0x081BB514` | 3 | 23 | 1536 | `[1472, 1536)` | 1 |
| 能力页 `0x081BB5BC` | 2 | 30 | 1024 | `[1920, 1984)` | 1 |
| 粉框 `0x081BB7E4` | 0 | 30 | 0 | `[1920, 1984)` | 1 |
| 图鉴列表 `0x081BB784` | 2 | 14 | 1024 | `[896, 960)` | 1 |
| 设置 `0x081BB874` | 2 | 15 | 1024 | `[960, 1024)` | 1 |

**合并后的静态带（4 条，共 448 tile）**：

```
[0,    64)    血条 sb0（tm2 实际不写 tilemap，保留无害）
[896,  1024)  图鉴列表 sb14 / 请选择·设置 sb15
[1472, 1600)  战斗UI sb23 + 招式 sb24
[1920, 2048)  粉框·能力页·队伍 sb30 + 对话框·49C sb31
```

剩余可分配 = `2048 - 448 = 1600` tile。**注意 `[1920,2048)` 落在 cb3，而 cb3 窗（战斗 UI）可寻址区间是 `[1536,2048)`** —— 这正是「静态带必须按全局下标而非相对号登记」的实证：若按 cb3 相对号记，`[1920,2048)` 会被误记成 `[384,512)`，与真实占用错位。

## 三、避让带列表设计

### 3.1 与禁令的边界（必须先讲清，否则本方案会被误判违规）

`.cursor/rules/axvj-no-avoidance-band.mdc` 禁止的是：

> 扫描 / 采样 VRAM 找「空闲带」再把文本 tile 塞进去 —— 被动测哪里空，测出来的是**快照**不是**契约**。

本方案的避让带是**反向的**：不探测「哪里空」，而是**由已知占用者主动声明「哪里被占」**，来源只有两个：

1. **静态登记**：读 ROM 模板 `screenBaseBlock` / 已知固定图标区间（`game.h` 里那批 `CHS_UI_ICON_TILE_*`）—— 数据源头是**配置/ROM 常量**，不是 VRAM 快照。
2. **钩子登记**：在**装载函数入口**记录「本次要写 `[start, start+n)`」—— 数据源头是**调用语义**，不是 VRAM 内容。

**判定线**：带项的 `start/len` 只要有一次是「读 VRAM 内容反推出来的」，就违规。**必须写进代码注释，作为后续维护的红线。**

但仍有一条**残留风险必须先承认**：禁令批评的第二点是「**无生命周期**」。声明式带如果只增不减，长会话下会退化为「跳过带 → 无空间 → 回卷 → 仍然无空间」。所以第四节给了 `epoch` 机制。

### 3.2 数据结构

```c
/* 一条避让带 = 全局下标区间 [start_g, start_g + len) */
struct ChsBand {
    uint16_t start_g;
    uint16_t len;
    uint16_t owner_lo;   /* (tpl, win) 双键的低 16 bit；STATIC = 0xFFFF */
    uint16_t owner_hi;
    uint16_t epoch;      /* 所属场景代次；STATIC = 0 */
};

#define CHS_BAND_N      24u                  /* 静态 4 + tm1 图集 + 窗框 + 对话框框 + 图标，留余量 */
#define CHS_BAND_STATIC 0xFFFFu
#define CHS_BAND_ADDR   0x0203FF90u          /* EWRAM；须避开 0x0203FFD2 起的游戏数据区 */
```

- **分级**：静态带与动态带同表存放，查询时**不分来源一律取并集**；`owner`/`epoch` 只用于**释放**，不参与判交。
- **表满**：沿用 2026-09-09 已定稿的策略 —— **与最近条目合并成包络，绝不淘汰**（淘汰 = 丢掉仍生效的预留 = 直接撞 UI；合并只多留白，方向安全）。
- **`(tpl, win)` 双键**：沿用 v9 队列层已踩过的坑 —— 日版复用同一 `TextPrinter` 挂不同模板（实测 `win=0x0202E658` 同时挂过 `tpl=0x081BB49C` 与 `0x081BB7E4`），只比 `win` 会漏判。

### 3.3 生命周期（回应「无生命周期」的批评）

```
场景切换 / 窗口关闭（换 tpl 且换 win）→  epoch++
                                       → 扫全表，epoch 落后者整条失效（len=0）
静态带 epoch=0，永不过期
```

一个更省事的等价做法（推荐先做这个，风险最低）：**只保留静态带 + 「按 (tpl,win) 分组、换组即整组清空」的动态带**，不引入全局 epoch 计数器。理由：日版 UI 的生命周期边界就是「换模板」，不需要更细的粒度。

## 四、分配算法（对应第 4 条要求）

### 4.1 伪代码

```c
uint16_t chs_alloc(TextPrinter *win, uint16_t n)
{
    uint8_t  cb  = win_template(win)[TPL_CHARBASE];
    uint16_t lo  = chs_g_of(cb, 0);          /* = cb<<9 */
    uint16_t hi  = chs_g_hi(cb);             /* 见 1.5，已含 10bit 与 OBJ 双约束 */
    uint16_t cur;

    if (n == 0 || hi < n || (uint16_t)(hi - 0) < n) return 0;
    if ((uint16_t)(lo) + n > hi) return 0;    /* 本窗区间装不下 n，直接放弃 */

    cur = cursor(win);                        /* 全局下标游标，随 (tpl,win) 切换置 lo */
    if (cur < lo || (uint16_t)(cur - lo) + n > (uint16_t)(hi - lo)) cur = lo;

    for (pass = 0; pass < 2; pass++) {
        uint16_t g = (pass == 0) ? cur : lo;
        while ((uint16_t)(g - lo) + n <= (uint16_t)(hi - lo)) {
            const struct ChsBand *b = band_first_intersecting(g, n);  /* 与 [g, g+n) 相交 */
            if (!b) {                                      /* 找到 */
                mark_ours(g, n);                           /* 本块已发出（跨块清空语义不变） */
                cursor(win) = (uint16_t)(g + n);
                return chs_g_rel(g, cb);                   /* 返回窗内相对号 */
            }
            g = (uint16_t)(b->start_g + b->len);           /* 跳到该带末尾 */
        }
    }
    return 0;   /* 宁缺不砸 */
}
```

### 4.2 正确性要点（三条都不能省）

1. **判交必须用区间，不是点**：`[g, g+n)` 与 `[b.start, b.start+b.len)` 相交 → 跳。只判 `g` 单点会在「n 跨带」时漏。
2. **跳带必严格前进**：相交 ⇒ `b.end > g` ⇒ `g` 单调增 ⇒ 循环必然终止（无死循环）。
3. **回卷只有一次**（pass 0→1），且 pass 1 从 `lo` 而**不是** `0`；`mark_ours` 保证不会回收自己本块刚写的 tile。

### 4.3 用户要求 4 的两处修正

| 用户原话 | 修正 | 原因 |
|---|---|---|
| 「可分配空间配置 `0 - 2560`」 | `[0, 2048)`，且**逐窗**再受 `[cb*512, cb*512+min(1024,(4-cb)*512))` 限制 | cb4/cb5 = OBJ；见第二节 |
| 「如果分配完了，则跳回开头进行分配」 | 保留，但**回卷起点必须是本窗 `lo_g`，不是 0** | 从 0 回卷会给出 `t = g - cb*512 < 0` 的非法相对号 |

另有一条**必须写进契约的补充**：`v8_alloc_begin` 的会话边界语义（位图重建 + ours 清空）与队列游标复位**是两件事**，本方案只改游标语义，**不得顺手拆掉占用校验层**（2026-09-09 拆掉校验 + 起址改 1 的实机撞 UI 事故）。

## 五、需要 hook 的 UI 分配函数登记（对应第 5 条）

### 5.1 pokeruby 侧：谁在往 charBlock 写 tile

读 `tools/pokeruby/src/text.c` + `text_window.c` + `menu.c`，**全 engine 只有 4 类主体**：

| # | pokeruby 函数 | 写入量 | 写入位置 | 是否已在日版受控 |
|---|---|---|---|---|
| 1 | `InitWindowTileData` / `MultistepInitWindowTileData` → `LoadFixedWidthFont*` | **512 tile**（font 0/3）或 **256**（font 1/2/4/5/6） | `win->template->tileData + 32*startOffset` | ✅ 已识别（`0x08002950` 出口返容量），**但当前树里没有登记进任何表** |
| 2 | `TextWindow_LoadStdFrameGraphics`（及 `OverridePal` / `OverrideStyle`） | **9 tile** | `tileData + 32 * sTextWindowBaseTileNum` | ❌ **未登记** |
| 3 | `TextWindow_LoadDialogueFrameTiles` | **14 tile** | `tileData + 32 * sDialogueFrameBaseTileNum` | ❌ **未登记** |
| 4 | `LoadFontDefaultPalette` / `ClearBGMem` | 0 tile（调色板 / 1 tile 清零） | — | 无需登记 |

链式游标契约（`text_window.c`，已核对源码）：

```

LoadStdFrameGraphics      : 写 9 tile @ sTextWindowBaseTileNum
SetDlgFrameBaseTileNum(b) : sDialogueFrameBaseTileNum = b (b = base+9);          return b + 14
```

⇒ **开窗后 30 个连续 tile 被引擎自己吃掉**（`canvas/atlas → +9 框 → +14 对话框框`）。这 30 个 tile 就是必须登记进避让带的动态带。

`Menu_DrawStdWindowFrame` / `TextWindow_DrawStdFrame` / `Text_FillWindowBorder` 只写 **tilemap 表项**（引用已有的 0..8 号框 tile），**不再占新 tile**，无需 hook。

**⇒ 登记实现路线（推荐，最小改动）**：不 hook 那 3 个 `LoadStdFrameGraphics`，而是**只 hook 一处在游标推进语句上做旁路**：

- 在 `0x08062080`（`SetBaseTileNum`）与 `0x08062366`（`SetDlgFrameBaseTileNum`）各挂 8B 桩，读到入参 `base` 后直接 `chs_band_add_static_g(base_global, 9)` / `(base_global+9, 14)`。

## 六、可行性裁定

### ✅ 可行，但必须同时满足 4 条前置条件

1. **分配域改成 `[0,2048)` 并按窗裁剪** —— 不能是 `0-2560`（第二节）。
2. **避让带必须是声明式**，且在代码注释里钉死「禁止由扫描推断」的判定线（第 3.1 节）。
3. **带表必须有生命周期**：至少做到「按 `(tpl,win)` 分组，换组整组失效」；否则长会话退化为「跳过 → 回卷 → 仍无空间」。
4. **`v8_alloc_begin` 的会话边界与队列游标复位分开改**；占用校验层（位图 / VRAM 非空 / ours）**不得顺手拆**（2026-09-09 事故）。

### ⚠ 三个必须由用户拍板的决策点

| # | 决策 | 选项 A | 选项 B |
|---|---|---|---|
| D1 | 与美版链式游标的关系 | **v9 自研分配器 + 声明式避让带**（本报告）—— 能立刻接线、风险可控，但**不解决**「BG charBase 仍为日版静态值」 | **完整复刻美版链式游标** —— 与项目既定唯一路线一致，但工作量大（含阶段 2 BG 重排），且仍要一张带表兜住链外装载（图标 / 图鉴球等） |
| D2 | 图集 512 tile 是否继续占位 | 保持现状：`0x08002950` 出口登记 `[tileOffset, +容量)` | 取消图集预留（已停图集 hook），彻底让出 512 tile —— **需实测确认无官方代码复用该区** |
| D3 | VRAM 非空校验 | 保留作兜底（方向安全，代价 32B/候选读） | 移除（更快，但与事故记录相冲） |

### 我不建议做的事

- ❌ 不要把避让带做成「扫描 VRAM 得到」的任何变体（W0 预算表 / cb-survey / `602 连续空闲`）。
- ❌ 不要为了「能装下」而放开 `hi_g` 到 `(6-cb)*512`（cb4/cb5 = OBJ，2026-09-09 事故原样）。
- ❌ 不要在没有实机验收的情况下把「避让带够用」写进结论 —— 「领航员」类大文本量场景是本方案**唯一没有数据的风险点**。

### 8.2 两条与调研报告不同的实测修正

1. **`TextWindow_SetDlgFrameBaseTileNum` 真入口是 `0x08062368`，不是 `0x08062366`**。
   `0x08062366` 处是 `ffff` 非指令字节（§5.2 表该行已勘误）。调用方交叉验证：
   `0x0806F054 bl 0x8062368` 紧跟在 `0x0806F04C bl 0x8062094` 之后，正是「框+9 → 框+14」链。
2. **`0x03000328` 存的是「当前文本模板指针」，不是 win 指针**（09-09 纪要记错）。
   `0x08002964 str r1,[r0]` 其中 `r1 = win[0] = template`。故跳板里 r3（=win）才是窗指针，
   而 `chs_cur_cb()` 从 `0x03000328` 取模板是自洽的。

### 8.3 构造推演抓到的两个致命缺陷（都已修，务必别回退）

> 方法：把 `chs_band_add` / `chs_band_end_hit` / `v8_alloc_n` 逐行等价成 Python 模型跑时序。

**① 跨 charBlock 合并会造出 `[1,2048)` 巨型包络 ⇒ 分配恒返 0 ⇒ 全白。**
四个 cb 的图集带分别是 `[1,513)` `[513,1025)` `[1025,1537)` `[1537,2049)`，**两两相接**。
原「相接即合并」规则会把它们串成一条覆盖全 VRAM 的带。
修复：`chs_band_add` 的合并只在**同一 charBlock 内**进行（`start>>9` 判定）；表满时优先
回收异 cb 条目（它们会在该窗下次开窗时重新登记），同 cb 全满才合并。

**② 动态带跨窗口累积 ⇒ 后开的窗把先开的 cb 可分配区吃光。**
cb0 窗可寻址 `[1,1024)`，正好被 cb0 图集带 `[1,513)` + cb1 图集带 `[513,1025)` 占满 ⇒ 恒返 0。
修复：`ChsAtlasWin_hook_C` 作为**本窗组开窗起点**，先 `chs_band_reset()` 整组清上一代，
再登记本窗图集带。修后实测（模型）：cb0/cb1/cb2 各窗恒有 **511 tile** 可分配，连领 12 次全成功。

### 8.4 ⚠ 新硬结论：cb3 窗（战斗 UI）在中文方案下无落脚处（【推论】，需实机确认）

`h_rel(cb) = min(1024, (4-cb)*512)` ⇒ cb3 窗只能寻址**相对 0..511**（全局 `[1536,2048)`，
再往上就是 OBJ 区，2026-09-09 已实证禁止）。而 tm1 图集容量 512（font 0/3）正好等于这 511 格
⇒ 该窗可寻址区间被图集**整段占满**，中文 tile 无处可放。

这不是 v9 引入的：v8 的 `hi` 公式完全相同，且其 `lo=0x100` 起点落在图集内部，
非空校验同样会一路跳过到底。**⇒ 战斗 UI（cb3）的中文很可能一直是空白/缺失**，
只是此前没有归因到「cb3 地址空间被图集吃满」。
建议实机核查项：进入战斗界面看招式/提示文字是否显示；若空白，则需专门方案
（例如把该窗重映射到 cb2、或该窗改用 tm3 网格 + 自有区）。

### 8.5 静态验证结果（均通过）

- **跳板编码**：objdump `out/game.bin` → `ChsAtlasWin_Entry@0x08800044`、
