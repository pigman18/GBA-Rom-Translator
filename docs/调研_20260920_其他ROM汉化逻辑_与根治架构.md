## 0. 一句话结论

**全世界所有平台的 CJK 汉化，最终都收敛到同一条机制：把「字模 → tile 号」变成纯函数，
不做运行时分配决策。** 我们过去一年做的恰恰相反（v8→v9→v10→v11→v12 全是"分配器"），
所以每修一次就换一种撞法。

**官方美版引擎自己就是这么做的**，而且有**同引擎家族已经跑通中文的开源实现**可以直接抄。

## 1. 硬件上限：先把"能不能绕过"彻底钉死

| 路子 | 结论 | 依据 |
|---|---|---|
| 单 BG 层看到 >1024 tile | ❌ **物理不可能** | GBATEK：Text BG Screen `Bit 0-9 Tile Number (0-1023)`。8bpp 不扩容（"a bit less in 256 color mode"）；affine BG 只有 256 tile。charBase 4 档只是**移动窗口** [读原] https://mgba-emu.github.io/gbatek/ ｜ https://gbadev.net/tonc/objbg.html |
| 拿 OBJ charblock 当 BG 用 | ❌ 模拟器可行，**真机不行** | tonc 原话 [读原] https://gbadev.net/tonc/objbg.html |
| 改用 OBJ（精灵）画字 | ❌ **100~200 字/屏不可行** | OAM 硬顶 **128 精灵/帧**；16×16 汉字 1 字 = 1 精灵 + 4 tile ⇒ 最多 128 字。tonc："there are only 128 OBJATTRs, and at one entry/glyph it may become prohibitively expensive if used extensively" [读原] https://gbadev.net/tonc/text.html |
| 改用位图模式 Mode3/4/5 | ❌ **是"取代"不是"共存"** | Mode 4 直接占用 `0x06000000–0x06009FFF`，BG tile 层整个不存在；原背景是 ROM tile+map，需每帧解压重画 [读原] https://www.copetti.org/writings/consoles/game-boy-advance/ |
| 两个 BG 层各 1024 → 合计 2048 | ⚠️ **只是"分片"，不是扩容** | BG VRAM 总共 64KB = 2048 个 4bpp tile，还要扣每层 tilemap（32×32×2B=2KB）⇒ 立刻爆。且只对 charBase 不同的窗口有效 [读原] https://deepwiki.com/mgba-emu/gbatek/2.3-gba-video-system |
| HBlank / VBlank 里 DMA 换字模 | ✅ **可行，唯一硬件扩容手段** | 扫描线 **1232** 周期（HDraw 960 + HBlank **272**）；每 HBlank 实用 **100~200 B ≈ 6 个 4bpp tile**。但要按 8 行条带换（tile 是 8×8，中途换会撕裂）。OBJ VRAM 走 HBlank DMA 还需设 DISPCNT bit5，代价是 OBJ 周期 1210→954 [读原] https://gbadev.net/tonc/dma.html |

⇒ **结论**：硬件上没有捷径。**唯一能动的变量是"这一层 1024 个号里，谁占哪些"。**
我们的问题从来不是 1024 太小，而是**我们和官方美术在同一层里抢号，且我们不知道官方占了什么**。

## 2. 决定性参照一：官方美版引擎 = 「窗口私有网格 + 格→号算术」

`pret/pokeemerald` `src/window.c` 原文 [读原] https://raw.githubusercontent.com/pret/pokeemerald/master/src/window.c

```c
// 建窗：向该 BG 层申请 width*height 个 tile（两阶段：先探测再提交）
allocatedBaseBlock = BgTileAllocOp(bgLayer, 0, templates[i].width * templates[i].height, 0);
gWindows[i].window.baseBlock = allocatedBaseBlock;
BgTileAllocOp(bgLayer, allocatedBaseBlock, templates[i].width * templates[i].height, 1);

// 写 tilemap：★这就是全部机制★
u16 currentRow = windowLocal.window.baseBlock
               + (y * windowLocal.window.width) + x
               + GetBgAttribute(windowLocal.window.bg, BG_ATTR_BASETILE);

// 销毁：归还
void RemoveWindow(u8 windowId) {
    if (gWindowTileAutoAllocEnabled == TRUE)
        BgTileAllocOp(bgLayer, gWindows[windowId].window.baseBlock,
                      gWindows[windowId].window.width * gWindows[windowId].window.height, 2);
    ...
}
```

**tile 号 = `baseBlock + y*width + x`，纯算术。** 一个屏幕格（8×8 像素）恒对应一个 tile；
字模像素按位 OR 写进这个窗自己的缓冲；**全程零分配决策、零扫描、零账本**。

由此推出的关键性质（也是我们 12 天前那份文档 §1 第 6 条想说的事）：

> **行 tile 消耗 ∝ 行像素 ÷ 8，与字数无关。**
> 12px 步进的汉字与 8px 步进的假名，**在同一行里占的格列数由像素宽度决定，不由字数决定** ⇒
> 中文不比日文"多花 tile"，只是"一行装得少"。

## 3. 决定性参照二：同引擎家族的中文实现 —— **零 tile 号分配**

`rh-hideout-chinese/pokeemerald-expansion` `src/chinese_text.c` [读原]
https://raw.githubusercontent.com/rh-hideout-chinese/pokeemerald-expansion/master/src/chinese_text.c

这是一个**已经跑通**的 pokeemerald 中文化工程。它的全部工作只有三件事：

```c
// ① 双字节汉字判定（高位 0x01..0x1E，排除 0x06/0x1B；低位 <= 0xF6）
bool8 IsChineseChar(u16 currChar, u16 nextChar, u8 fontId, bool32 isJapanese);

// ② 宽度返回（大字 12，小字 10，个别符号 5/6/7）
u8 GetChineseFontWidthFunc(u16 ChineseChar, u8 fontId);

// ③ 字模解码：把 2×2 共 4 个 tile 塞进引擎自己的字形缓冲
void DecompressGlyph_Chinese(u16 ChineseChar, u8 fontId) {
    gCurGlyph.width  = GetChineseFontWidthFunc(ChineseChar, fontId);
    gCurGlyph.height = (小字 ? 13 : 15);
    DecompressGlyphTile(glyphs,      gCurGlyph.gfxBufferTop);
    DecompressGlyphTile(glyphs+0x08, gCurGlyph.gfxBufferTop + 8);
    DecompressGlyphTile(glyphs+0x10, gCurGlyph.gfxBufferBottom);
    DecompressGlyphTile(glyphs+0x18, gCurGlyph.gfxBufferBottom + 8);
}
```

**整个文件里没有任何一次"申请 tile 号"。** 字形落到 `gCurGlyph` 缓冲，交回原生
`CopyGlyphToWindow` 写进窗口自己的块。跨 8px 边界的重排由一个叫 `OffsetCurrGlyph` 的
辅助函数处理（注释自嘲 `Do cursed u64 handling of double wide glyphs`）。

⇒ **一个 12px 宽的汉字横跨 2 个格、15px 高横跨 2 行格，官方模型天然支持。**
它之所以能"只 hook 三五个点就干净渲染中文"，是因为**它站在窗口私有网格上**。

同类旁证（宝可梦字库改造）：`Wokann/Pokemon_GBA_Font_Patch`（armips，静态扩容字库 +
新增 `GetStringWidth` 兼容汉字）[读原] https://github.com/Wokann/Pokemon_GBA_Font_Patch
—— 本工程已在用它，但它解决的是"字库装得下"，**不解决"tile 号发给谁"**。

## 4. 横向：其他平台怎么做的（用于确认"纯函数定号"是行业共识）

| 平台/项目 | 机制 | 来源 |
|---|---|---|
| NDS 宝可梦 DP 中文 | 字库本来是**预加载**（`Heap_AllocFromHeap(glyphSize*numGlyphs)`，改大会死机）⇒ 汉化把 `DecompressGlyphTiles_FromPreloaded` 换成 `DecompressGlyphTiles_LazyFromNarc`，即**预加载 → 按需懒加载** | [读原] https://xzonn.top/posts/Pokemon-DP-Chinese-Localization-Based-on-Pret-Project.html ｜ https://github.com/Xzonn/PokemonGen4FontPatch |
| NDS / PSP / PS2 / Wii | PSP `sceFont` `sceFontGetCharGlyphImage` 直接返回字形位图缓冲；汉化 hook 掉重定向到自制含中文的 `.pgf` | [读原] https://psp2sdk.github.io/pgf_8h.html ｜ https://docs.vitasdk.org/group__ScePgfUser.html |
| SNES | VWF 本质 = **运行时造 tile**：取字形 → 按像素挤进 WRAM tile 缓冲 → DMA 进 VRAM → **同步改 tilemap 索引** | [读原] https://www.romhacking.net/forum/index.php?action=printpage;topic=12480.0 |
| NES | MMC3 克隆 mapper + CHR RAM：CHR bank 粒度不足，留一块 CHR RAM **软件渲染文字** | [读原] https://www.nesdev.org/w/index.php?direction=next&oldid=23944 |
| 通用 GPU 字模缓存（现代做法） | 分区（静态 ASCII 永不淘汰 + 动态 CJK）＋ 顺序分配 ＋ LRU ＋ O(1) 哈希（key = 字符+字体+样式） | [读原] https://deepwiki.com/junkdog/beamterm/3.2-font-atlas-system |
| **GBA 上唯一现成的字形缓存实现** | `agb`（Rust）：`DynamicTile16` 运行时动态分配 VRAM tile、`set_pixel()` 写入、drop 即归还；文档注明 "used heavily in the RegularBackgroundTextRenderer" | [读原] https://docs.rs/agb/latest/agb/display/tiled/struct.DynamicTile16.html |
| 自写文本引擎的真实先例 | Mother 3 英化：**所有文本显示例程全部重写**（"no text display routine wound up untouched"，10~20 套），1000+ 小时。Bahamut Lagoon：自写 VWF 引擎 + 硬件乘法器预计算移位表，370KB 新汇编 | [读原] https://arstechnica.com/gaming/2008/10/no-edits-junk-test/ ｜ https://www.romhackplaza.org/translations/bahamut-lagoon-english-translation-super-nintendo |

**字模缓存的三个标准陷阱**（第三方总结，对 GBA 尤其致命）[读原] https://doc.servo.org/glifo/atlas/cache/struct.GlyphAtlas.html
1. **淘汰不回写 → 屏上已画的字变错字。** GPU 靠每帧 UV 引用所以无所谓；**GBA 靠持久 tilemap 索引，淘汰必须回写**。
2. **槽复用前不清零 → 残影/花屏。**
3. **批量替换必须在 VBlank 内完成**，且不能改正在被扫描线读的 tile。

## 5. 我们错在哪（与上面两条参照对照）

| 维度 | 官方美版引擎 / 中文 fork | 我们（v8→v12） |
|---|---|---|
| 号从哪来 | `baseBlock + y*width + x`（**纯算术**） | 运行时扫描 VRAM 猜"哪些空闲" + 账本 + 复用闸门 |
| 号的范围 | 该窗自己的块 | 全局池 `[L,1024)`，与官方美术同层抢 |
| 空间归属 | 分配器记账，**块互不重叠** | **我们不知道官方占了什么**，只能靠内容/引用/边界去猜 |
| 空格重画 | 天然幂等（号是位置的函数） | 需要"复用闸门"去识别"这格是不是我们写的" |
| 复杂度来源 | 0 | 三层探测 / 负缓存 / ours 段表或位图 / 相位层 / 场景 gate |
| 结果 | 撞车是**结构上不可能** | 每修一次换一种撞法（v9→v10→v11→v12 四个症状各不相同） |

**一句话**：官方是「**位置的函数**」，我们是「**猜测 + 账本**」。猜测一定会错，账本一定不全。

## 6. 三条候选路线

### 路线 A（推荐）「窗口私有网格」= 官方美版模型
- **做什么**：给每个窗口一块**它的屏幕格数**（W×H）的私有 tile 区；`tile = block + cy*W + cx` 纯算术；
  字模按像素 OR 写入；窗口销毁归还。删掉 v8/v9/v10 的账本/闸门/扫描。
- **外部依据**：§2 官方源码 + §3 同引擎中文实现，两条独立证据。
- **内部依据**：`引擎移植方案_20260908.md` §0/§3.2 **T-a**（"给每个 tm1 窗口在 VRAM 圈私有 tile 区…
  撞 UI 物理不可能；v8 分配器退役"）—— 该文档 2026-09-08 已给出此结论，**从未执行**。
- **收益**：`[撞UI] [串扰] [覆盖 font4]` 三类症状**同时**结构上消失；容量从"全局抢 407/745"变成"每窗按需"。
- **代价/风险**：① 日版窗口结构**没有 width/height 字段**（`0x18 TILE_OFFSET` 后直接是 `0x1A CURSOR_X`），
  需要从模板或屏幕坐标推；② 要自建"每 BG 块分配器 + 窗口生命周期钩"；
  ③ 需要一次 VRAM 预算勘测（gdb 逐场景采各窗 tile 区边界）——**这一步必须实机，我按纪律不能自己开模拟器**。

### 路线 B「字符码定号 + 声明式独占区」（路线 A 的轻量版）
- **做什么**：`tile = L(font) + slot(font, code) * 4`，slot 由一张 `(font,code)→slot` 表决定；
  区间 `[L(font), 1024)` 是**声明式独占区**（`L` 用 v12 已实证的 `official_end()`）。
  **不再读 tilemap、不再查 ours 账本、不再有复用闸门。**
- **外部依据**：§4 的 NDS/PSP/SNES 与通用字模缓存（key = 字符+字体+样式，纯哈希）。
- **收益**：不同字**结构上不可能**同号（→ 串扰消失）；号**物理上**出不了 `[L,1024)`（→ 撞 UI / 覆盖 font4 消失）；
  同字永远同号（→ 重画零消耗，且不需要"识别这格是不是我们的"）。
- **代价**：容量 = 745 ÷ 4 ≈ **186 个不同的字/屏**（大字占 4 tile）。够用但会满。
- **风险**：满槽后要么不画（现状降级），要么淘汰——而淘汰会踩 §4 陷阱 ①。

### 路线 C「整引擎移植」（09-08 文档 P2 主线）
- **做什么**：把美版 `text.c` 的**宽度间接层 + 像素游标 + mask 拆列合并 + 窗口私有网格**整套搬过来，
  日版只留薄适配层。参考 §3 的 fork 做法：把中文挂进 `sFonts` 表，换字库=改表不动引擎。
- **收益**：一次性获得原生 VWF 语义（换行/居中/测量/控制码），`GetStringWidth` 接管居中与截断，
  4 个场景 hook（地图名/血条昵称/图鉴/选项）可退役。**这才是真正的"推倒重来"。**
- **代价**：工作量大（09-08 文档 W1~W6）；但 W2 可在 PC 上用 host oracle **离线对拍**，不必先上实机。
- **外部依据**：Mother 3 英化 / Bahamut Lagoon 证明这条路走得通且是终局形态。

**推荐次序**：**B → A →（视需要）C**。
理由：B 是纯函数定号的最小落地，能立刻结构性消除全部已知症状，且改动面小、可离线判据覆盖；
A 是 B 的自然延伸（把"全局独占区"换成"每窗块"，容量从 186 字上限变为按窗精确满足，但需要勘测）；
C 是终局，等 B/A 稳住地基后再谈。

## 附：本轮调研命中但**未作为判据**的条目（透明度）

- `sGlyphMasks` / `tilesWidth == 2`：在 `pret/pokeemerald` 全仓**无命中**。日版有 `tilesWidth` 分支、
  美版无的旧认知**与外部对不上**，判为"日本版专有实现"，不作为方案依据。
- "每扫描线最多 32 个 OBJ"：**是错的**（那是 NES/SNES/DMG 的数）。GBA 每行最多 128 个 8×8，
  真正的瓶颈是 OAM 表 128 条。结论（OBJ 画字不可行）不变。
- "GBA 上有公开的「分屏字库 / LRU 淘汰」GBA 实现"：**未找到**。GBA 侧公开项目只有
  「静态扩容图集」与「OBJ 动态回收」两条；字模缓存只有 `agb`（Rust）一家。
- KaioShin 的 DQ Monsters VWF 汇编源码（romhacking.net/docs/337）：只搜到标题，**未读到源码**。
