## 0. 一句话结论（本轮最重要的一条）

**我们一直在打一场不存在的仗。**

引擎的真实模型是 **「每个窗口一块私有画布，tile 号 = 画布基址 + 位置偏移」**
（15-0b §〇 已用逐指令反汇编证实），而我们从 v8 到 v36 一直假设
**「有一个全局的官方占位区，我们需要在里面找空档」**——这个「官方占位区」是对
`cap = 512` 的**误读**产物（`cap` 是「要加载多少个字形」，不是「号区间上界」）。

外部三个可比案例（宝可梦美版补丁 / Mother 3 英化 / pokeemerald 中文 fork）**没有一家**
在用「水位 / 避让带 / 空闲池」这类办法；它们全部落在
**「字模永不作为常驻图集占 VRAM + 号由位置决定」**这一个形态上。

## 1. 硬件边界：先把「能不能绕」彻底钉死

| 问题 | 结论 | 依据 |
|---|---|---|
| 一层 BG 能看到超过 1024 个 tile 吗 | ❌ **硬件硬墙**。屏幕项 tile 号字段固定 10 bit（0-1023） | GBATEK："0-9 Tile Number (0-1023)" [读原] https://mgba-emu.github.io/gbatek/ |
| 把 OBJ 的 charblock 借给 BG | ❌ **真机禁止**。Tonc 原文：模拟器允许，真机不允许 | [读原] https://gbadev.net/tonc/regbg.html |
| 换 charBase 能扩容吗 | ❌ **只是移动起点**。CBB 单位 16KB，是「从哪个块开始计数」，不是边界；BG 区物理共 64KB = 2048 个 4bpp tile，还要与 tilemap 分 | [读原] Tonc/GBATEK 同上 |
| 存不存在「扩展 char block 区」的技术 | ❌ **不存在**。BG(0x06000000-0x0600FFFF) 与 OBJ(0x06010000-0x06017FFF) 物理隔离、不可互换。`DISPCNT bit5` 真名是 **H-Blank Interval Free**，不是 VRAM 重映射；forced blank 是 bit7 | [读原] GBATEK / Tonc |
| 8bpp 模式能扩容吗 | ❌ 号段**更小**（charblock 只放 256 tile） | [读原] GBATEK |
| Affine BG | ❌ 只有 256 tile | [读原] GBATEK |
| HBlank 里 DMA 换字模 | ⚠️ **理论可行、极其昂贵**。扫描线 1232 周期，HBlank 仅 272 周期；且换字模的最小粒度是 **8 条扫描线**（tile 是 8×8 连续存储），不是 1 行。没找到可验证的商业先例 | [读原]周期数 https://gbadev.net/tonc/dma.html ｜ 字节数为推算 [仅搜] |
| 改用 OBJ 画字 | ⚠️ **有真实上限**。OAM 硬顶 128 项/帧；每扫描线 OBJ 周期 1210（HBlank-free 时 954）。16×16 字 = 1 精灵 + 4 tile ⇒ **最多 128 字/屏** | [读原] https://gbadev.net/tonc/tte.html |
| 同样一块字模服务多层/多窗口 | ✅ **可行且常规**。CBB 是每层独立字段，多层可指同一 charblock、各用不同 tilemap；WIN0/WIN1 只是遮罩，**没有自己的字模** | [读原] Tonc/regbg |

**⇒ 硬件结论**：不存在任何「扩容」捷径。**能动的只有「这一层 1024 个号怎么分」** ——
而这正是我们花了一年却没问对的问题：**不是「分给谁」，而是「号由什么决定」**。

## 2. 决定性对照：美版引擎（同代同源）怎么定号

`tools/pokeruby`（官方美版红宝石反编译，与本工程日版 AXVJ00 同代同源）[读原]：

```c
// src/text.c:4380  GetCursorTileNum
static u16 GetCursorTileNum(struct Window *win, u32 xOffset, u32 yOffset)
{
    if (win->textMode == TEXT_MODE_UNKNOWN2)          // ← 变宽(VWF)模式
        index = win->tileDataStartOffset + win->tileDataOffset
              + (((win->top + win->cursorY) >> 3) + yOffset) * win->width
              + (((win->left + win->cursorX) >> 3) + xOffset);
    else                                              // ← 等宽(预取)模式
        index = win->tileDataStartOffset + win->tileDataOffset + 2 * xOffset + yOffset;
    return index;
}

// src/text.c:4321  DrawGlyphTiles —— 落点是「cursor 位置的号」，不是「字形号」
glyphTileInfo.dest = (u32 *)(win->tileData + 32 * GetCursorTileNum(win, 0, 0));
glyphTileInfo.dest = (u32 *)(win->tileData + 32 * GetCursorTileNum(win, 0, 1));
```

以及窗口初始化（`InitWindowTileData`）的两条分支 [读原]：

```c
case TEXT_MODE_UNKNOWN2:  retVal = InitVariableWidthFontTileData(win, startOffset); break;  // 网格
case TEXT_MODE_MONOSPACE: retVal = LoadFixedWidthFont(win, startOffset);            break;  // 预取
```

- **网格分支**（`InitVariableWidthFontTileData`）：**不加载字库**，只占 2 个控制槽，
  返回 `startOffset + 2 + width * height` —— **把「下一块画布从哪开始」交回给调用方**。
- **预取分支**（`LoadFixedWidthFont`）：`for (glyph = 0; glyph < 256; glyph++)` 把 256 个字形
  写进 `win->tileData + 32 * startOffset` 起，返回 `2 * 256 = 512`。

**⇒ 美版的关键性质**：
1. **号 = `base + 位置`（网格模式）或 `base + 字形序`（预取模式）**，两者都建立在
   **每个窗口各自的 `startOffset`** 上；
2. `startOffset` 由**调用方串联**：上一个窗口的返回值就是下一个窗口的起点 ⇒ **窗口之间天然不重叠**；
3. **窗口有「私有 tile 缓冲」这个概念**（`win->tileData + startOffset`）。

**对照本工程日版（`15-0b` 反汇编实证）**：

```
0x08002D64  adds r2,r2,r1        tile = TILE_BASE + TILE_OFFSET
0x08002D66  lsls r2,r2,#5        ×32 字节
0x08002D68  ldr  r1,[r3,#12]     tpl->tileData
```

⇒ **日版的结构与美版一模一样**：`tile = TILE_BASE + TILE_OFFSET`，
`TILE_BASE` 来自调用者（`InitTextPrinter` 的第三参数，`win[0x16]`，u16）。

### 2.1 🔴 两边唯一真正的区别：`textMode` 值域与语义

| | 美版 AXVE | 日版 AXVJ |
|---|---|---|
| 值域 | `{0, 1, 2}` | `{0, 1, 2, 3}` |
| 含义 | 0 未知 / 1 等宽预取 / 2 **变宽网格** | 0 线性 / 1 **图集寻址** / 2 缓冲直绘 / 3 **网格** |

**日版 tm3 就是网格模式**，公式（`sub_80034A8` 反汇编）[读原本工程文档]：

```
tile = cursorTileX + (cursorX + 2) + TILE_BASE + row * 30
```

**与美版 VWF 网格同构**（号 = 画布基址 + 位置）——差别只在日版 stride **写死 30**、
美版用窗口的 `width`。

**⇒ 日版**并非「没有私有画布」，而是**只有 tm3 的 2 个窗口走网格**，
其余（tm0 ×14 / tm1 ×36 / tm2 ×1）走别的落址。而**只有 tm1 会把日文字库灌进 VRAM**
（`15-0b` §一.5 逐指令实证：`0x080029E0` 只在 `textMode == 1` 时落到加载分支）。

## 3. 外部三个可比案例（都不是「避让带」）

### 3.1 宝可梦**美版红宝石**汉字补丁 —— 同代同引擎，已跑通

源码就在本工程：`tools/Pokemon_GBA_Font_Patch/pokeRS/`（armips）[读原]。

```asm
; src/HackFunction/DrawGlyphTilesChinese.s
bl GetCursorTileNum          ; (win, 0, 0) → 窗口内 cursor 位置的号
lsl r0, r0, 5                ; ×32 = 字节偏移
ldr r1, [r6, 0x24]           ; win->tileData
add r1, r1, r0               ; dest = 窗口自己的缓冲 + 位置号
...
bl UpdateTilemap             ; 再提交 tilemap
```

**它做了什么**：hook `DrawGlyphTiles`，把汉字（16×16）拆成 **2 次 cursor 位置**
（`left` 每次 +8）逐半写入，字模**来自 ROM 的 `0x09000000/0x09100000`**，从不作为常驻图集。

**它没做什么**（README 明写）：「不动 charBase、不扩容 VRAM 字库」；
且 **「海外版非美版也可以使用，需自行修改函数地址定义」** —— 即这套原理**可移植到日版**。
同一 README 也点出它**不解决**的问题域：它站在美版的「窗口私有网格」上。

### 3.2 MOTHER 3 英化 / 法化 —— 最极端的「推倒重来」，且成功

[读原] https://mother3.fobby.net/or ｜ https://mother3.fobby.net/blog?p=552 ｜ https://arstechnica.com/gaming/2008/10/no-edits-junk-test.ars ｜ 源码 https://github.com/JumpmanFR/Mother3VF

- **字库从不常驻 VRAM**：`fast_prepare_main_font` 每次按字符号 `lsl r0,r0,#5`（每字形 0x20 字节）
  从 ROM 取到栈/RAM 工作区。
- **自写 VWF 焊接**：宽度表（每字符 1 字节）+ 位拼接，`text_weld` 把当前字形右移 `curr_x`
  后 OR 进当前 tile，溢出的位左移 OR 进下一个 tile。
- **精灵文本写进 OBJ 区**：`define new_pos_base $6011800`，把精灵 tile 区改址后逐字写入。
- **代价的诚实记录**：Tomato 原话「**没有任何一个文本显示例程没被动过，至少有 10~20 套**」，
  且「最大的问题是内存根本不够，我们基本上是从零重写每一个显示例程」。
  RAM 行缓冲甚至从「每行 21 字母」改到 250。

⇒ **外部证明：日文 GBA 游戏完全放弃「常驻字库图集」这条路是走得通的**，
但代价是重写全部文本例程 + 大量内存重排。

### 3.3 pokeemerald 中文 fork —— 复用官方 glyph 管线，零 tile 号分配

[读原] `src/chinese_text.c`：全部工作只有三件事 —— 汉字判定、宽度返回、
`DecompressGlyph_Chinese` 把 2×2 共 4 个 tile 塞进引擎自己的 `gCurGlyph.gfxBufferTop/Bottom`。
**整个文件里没有任何一次「申请 tile 号」**。它成立的前提同样是
**它站在窗口私有网格上**（美版引擎）。

### 3.4 反面：其他中文 GBA 汉化

| 案例 | 方法 | 是否解决「与 UI 抢号」 |
|---|---|---|
| 火纹 FE7/FE8（FEBuilderGBA / Lawliet 补丁） | 破 Huffman 让文本可读 + **原地覆盖日文字模** + tbl 重映射 | ⚠️ 受原字库容量限制，未触及 VRAM 冲突 |
| 通用「字库扩容」教程 | 字库搬到 ROM 末尾空白区改指针 | ❌ 只解决 ROM 侧 |
| 逆转裁判 / 黄金太阳 | 只有成品，无公开技术文档 | 无结论 [仅搜] |

⇒ **「扩容字库」这个方向只对 ROM 有意义，对 VRAM 无效**。这也解释了为什么我们
「字库明明在 ROM 里、扩容也没用」——**问题从来不在字库，在落点坐标系**。

## 4. 由此推出：我们过去一年的路线为什么必然失败

| 路线族 | 隐含假设 | 为什么必败 |
|---|---|---|
| v8~v21 分配器族 | 存在一个「全局空闲号区」可供分配 | 「空闲」要从**引用/写入采样**推断，而 `15-0b` 已证**那个全局占位区本身不存在** |
| 避让带 / 采样求补集 | 官方占用集合是稳定可采样的 | v38 已证：字模缓存量 `2×G` 逐屏变、VRAM 跨屏不清零 ⇒ 采样两向失效 |
| 抬水位 / 固定号画布池 | 官方占位有确定上界 | `cap=512` 是**加载字形个数**，被误读成号区间上界 ⇒ 坐标系就错了 |
| 池子 / 段表 / 字符键定号（v33~v36） | 号必须唯一绑定「字符」 | 引擎的号是 `base + 位置`，**同号复用是设计内行为**；把它当「冲突」去消灭，等于逆着架构做 |

**一句话**：我们一直在「**全局字号空间**」里找地方，而引擎的模型是「**每窗口私有画布**」。
找错坐标系以后，无论算法多精细（扫描/账本/闸门/相位），都是在解一个错方程。

## 5. 正确形态（外部案例的共同点 + 本工程已证的结构）

```
每个文本窗口在 InitTextPrinter 时领一块不重叠的画布基址 TILE_BASE（u16，上限 1023）
tile = TILE_BASE + TILE_OFFSET          ← 纯函数，位置决定号，无账本、无扫描、无复用闸门
字模：留 ROM，逐字取 → 写进该号 → UpdateTilemap 提交
```

- **结构性不撞**：两个窗口的 `TILE_BASE` 区间不相交 ⇒ 撞 UI 在结构上不可能（不再是「概率」）。
- **容量可算**：每窗口预算 = `1024 - TILE_BASE`；`15-0b` §11.2 已给出预算表。
- **与外部一致**：这正是美版引擎的网格分支、也正是 Wokann 补丁站的地基。

**本工程已经具备的**：`chs_claim_tile` 里的 `tm == 3` 分支已经在用官方网格公式
（`TB + curX + curTileX + (curY + curTileY) * 30`）——**这条路径从来没出过撞 UI 问题**
（09-21 实测：START 主菜单 8 项全部完整、无残缺、无重叠）。
**出问题的全是 tm0/tm1 走「池子」的那些窗口。**

## 8. 待用户决策

1. **先测 U1/U2**（gdb 采一次同屏窗口普查，零 ROM 风险）——拿到「同屏画布总需求」这个数，
   才知道 1024 够不够、要不要引入 OBJ。
2. 还是**直接执行 15-2 三步**（`tpl[9]` 1→0、`InitTextPrinter` 写 `win[0x16]`、删账本族），
   边跑边收 U1/U2。

**我的建议**：走 1 → 2。理由：U1 是唯一还能推翻整个方案的数（如果同屏画布需求 > 1024，
就必须先决定 OBJ 分担多少）；而它是一次只读采样，代价远小于改错坐标系后再返工。
