# 跨游戏调研：CJK 游戏怎么把「字库 >> 显存」这件事做掉（2026-09-21）

> 触发（用户原话）：「市面上有那么多日版汉化，那么官方中文卡带，你就不能调研这些获取灵感吗？
>   来来回回就是绕回 gdb 测试占用，然后避让占用（建立空闲区/避让带/高水位），你好像脑筋就死在这里了？」
>   「而且为啥限制了宝可梦？」
>
> 方法：**三路外部并行调研**（官方中文卡带 / 日文编码与汉字 / 通用字形缓存）+ 复核本工程四次结论。
> 标注：**[读原]** = 实际读了正文或源码；**[仅搜]** = 只拿到标题/摘要，不作判据。

---

## 〇、一句话结论

**没有任何一个 CJK 游戏（官方或民间）给字符分配「永久的 tile 号」。**

它们全部使用 **`字符 → 运行期槽位`** 的映射：**号是「这一帧的槽位」，不是「字符的身份」**。
本项目一年的「分配器 / 避让带 / 高水位」在业界找不到第二家 ——
它是在**错的坐标系**上解一个**不存在的方程**。

而且它解释了一个我们一直没问对的问题：**撞 UI 的结构性原因是「扩容」，不是「分配不当」。**

## 三、卡点辨析：「账本」被误判了（本轮最关键的一段）

`20260921_真问题定位` §9.3 原文：

> 「官方是 `TB + 2×字形码`（按字形索引）⇒ 同字同号 ⇒ 天然共享、永不覆盖。
>  我们做不到照抄形式：字库按需上传，取字形码要先建 `code → slot` 表 = **账本**（用户明令禁止）。
>  所以只复刻**性质**，而不复刻**形式**。」

**这一步是整个项目卡住的地方。** 两者是完全不同的东西：

| | 账本（用户禁止的） | `code → slot` 表（正解） |
|---|---|---|
| 数据来源 | **读回 tilemap / VRAM**，推断「这格是不是我们写的」 | 我方**私有数组**，自己分配 |
| 依赖对象 | 对**别人行为**的观测 ⇒ 不可靠、随场景变 | 只依赖**自己** |
| 业界先例 | **无** | **全世界都这么做**（= 字形缓存 glyph cache） |
| 官方对应物 | — | 官方的 **`charmap`** 就是 `code → glyphIdx` |

⇒ **`code → slot` 不是账本，是「字形缓存」**：
- SNES：「按需取字 → 生成 tile → 改 tilemap 引用」（事实 3）
- NDS NFTR：`CMAP` = `code → glyphIndex`（事实 4）
- Kanzi / Unity：glyph cache + LRU 淘汰（正文字形缓存）
- **官方日版宝可梦自己**：`tile = TB + 2*glyphIdx` —— `glyphIdx` **就是 slot**

**用户禁止的是「探测外部占用」，不是「管理自己拥有的槽位」。这两件事被混为一谈了。**

## 四、结论：唯一能「加字不涨号」的结构

```
tile = TILE_BASE + 2 * slot(code)          ← 复刻官方形式
slot ∈ [0, S)，S = 槽数（我方私有表管理，非账本）
号需求 = 2 × S                              ← 有上界，与字库总量无关
```

对照表（这才是回答「够不够」的地方）：

| 方案 | 号需求 | 加字 / 加场景 | 同屏多块 |
|---|---|---|---|
| 避让带 / 高水位（已判死） | `∑(每块字数)` **无上界** | 线性增长 ⇒ **迟早不够** | 覆盖 |
| 位置定号（v21 方案 H，现状） | `∑(每块字数)` **无上界** | 线性增长 ⇒ 靠版式不变式侥幸 | 靠块基准错开，仍有重叠风险 |
| **字形槽定号（本方案）** | **`2S ≤ 512` 有上界** | **槽位轮换，号不变** | **同字同号，自动共享** |

⇒ **这就是用户要的「可持续」**：加场景、加文字、加字库，**号需求恒定**。
⇒ **用户担心的「加多了就冲突崩」在这个结构下不成立**（冲突来自「号随字数增长」，而不是来自「字变多」）。

## 五、对本工程的具体含义

1. **「容量不够」是伪命题**。
   同屏不同字形数 `G ≤ 屏格数 / 每字格数 = 600 / 6 = 100`（真问题定位 §四）。
   槽需求 `≤ 2×256 = 512 号`，而 charBase 2 的号空间是 `[0, 1024)`。**余量 2 倍**。

2. **不需要「接管 UI 分配」、不需要「避让带」、不需要「水位」**。
   撞 UI 的根因是**扩容**（事实 6）；本方案**没有新增号**（字形只是轮流占用固定槽），
   因此**结构上不产生新的 UI 冲突**。

3. **与「原地覆盖字库」是同一件事的两种形态**。
   把中文字形放进「运行时槽位」＝ 事实 6 的「原地覆盖」在 VRAM 侧的对应物：
   **不改变装载长度、不改变布局、只换内容**。

4. **旧结论不冲突**：
   `15-0b` 的「位置定号」是对**官方 tm0** 的正确描述；
   `真问题定位` 的「官方 = 字形索引定号」是对**官方 tm1（多数窗口）**的正确描述。
   两者并不矛盾 —— **tm1 才是主路径**（36 个窗口），我们却按 tm0 的模型去实现了。

## 六、待决（实施阶段，不在本轮）

1. **槽数 S 与 TB 越界**：实测 `TILE_BASE` 最大 752 ⇒ `752 + 2S ≤ 1024` ⇒ `S ≤ 136`；或按 `15-0b` 第 2 步在 `InitTextPrinter` 钩子里把 TB 归一。
2. **槽位回收时机**：窗口重画 / 屏幕切换时重置（`InitTextPrinter` 粒度太细 —— 设置页 22 块会被误判为 22 屏）。
3. **与静态 UI 图块区间的关系**：若 UI 也用 `[0,1024)`，需在**设计上**分开（构建期确定），而不是**运行时探测**（后者即避让带）。
