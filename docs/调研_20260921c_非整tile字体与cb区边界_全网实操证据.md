## 0. 一句话总览

| 问题 | 答案 |
|---|---|
| 11×11 这类非整 tile 字形，业界怎么渲染？ | **像素光标 + 移位 + mask/OR 直写 tile**（FE8 官方源码、MOTHER3 都是这么做的）。我们现有算法已是标准形态，**渲染不是问题**。 |
| 有没有办法绕过/扩充 cb 区（1024 tile 墙）？ | **没有。** 逐项核查全部无实操先例或真机不可行。唯一硬件级"扩充"（8bpp 跨块寻址）容量持平、无净收益。 |
| 那全世界怎么显示几千个中文的？ | **字库留 ROM，当屏用到的字形按需写进一小片固定槽区，槽区由文本系统自管、随重画回收**。没有人绕墙，大家都在墙内轮换。 |

## 1. Q1：非整 tile 字体的渲染实操（三个一手源）

### 1.1 金标准：FE8 官方反编译 `fireemblem8u/src/fontgrp.c` [读原]

https://github.com/FireEmblemUniverse/fireemblem8u —— 不是汉化补丁，是**官方引擎本尊**的逐行源码，含完整中文字形所需的全套机制：

- **字体区 = 固定一小片**：`InitTextFont(&gDefaultFont, (void*)(VRAM+0x1000), 0x80, 0)` —— 0x06001000 起、**0x80（128）个槽**、每槽 64 字节（8×16 像素 = 上下两个纵向堆叠的 4bpp tile）。整个游戏全部对话文字只用 **128 槽 = 256 个 tile 号**。
- **跨 tile 字形的标准解法**：`subx = text->x & 7`（像素光标对 8 取余）；字形每行位图升位成 **u64 后左移 `2*subx` 位**，自然溢出到右侧相邻槽（16px 字形最多跨 3 槽）；合并用 `maskLut + colorLut` 做「不透明覆盖、透明保留」的读-改-写（`dst &= mask; dst |= color`）。
- **定号 = 槽位 bump 分配器，与字形身份完全解耦**：`InitText` 时 `chr_position = chr_counter; chr_counter += tileWidth`；槽 i 的 tile 号 = 基号 + 2i（上半）/ 2i+1（下半）。**号属于"文本对象的第 i 个槽"，不属于"哪个汉字"**。
- **防闪烁 = 双缓冲翻页**：`InitTextDb` 分配 2× 槽，每次 `PutText` 后 `db_id ^= 1`。
- **字库本体在 ROM**：IS 全系（FE GBA→DS）对话字形 4bpp 16×16、**每字带独立宽度字节**、按 Shift-JIS 码指针表寻址（FEDS_Font_Tool 佐证 [读原] https://github.com/delvier/FEDS_Font_Tool ）。

### 1.2 MOTHER 3 英化 Text Welding [读原]

https://mother3.fobby.net/blog/?p=552 、https://mother3.fobby.net/or

- 字形 1bpp 从 ROM 取（显示时转 4bpp），另有每字宽度表；焊接 = 纯位运算：前字右移、后字按累计宽度 **bitwise OR** 进同一 tile；溢出列 "shift everything left 3" 写入新 tile。
- **"the main font could only be 11 pixels tall"** —— 11px 高字形的**商业游戏先例**。
- 21 字/行、42 字/屏的限制是 **RAM 分配限制而非 tile 数限制**；修法 = 双槽轮换（"trick the game into using only two slots and constantly swapping"）。
- 主对话字体 16×16，Tomato 原话：没有任何一个文本例程没被动过。

### 1.3 tonc（GBA 开发权威教程）[读原]

https://gbadev.net/tonc/text.html

- 变宽/变尺寸字体在 tile 模式 = "bit-shifting hell"；"things just get horrible if I'd allowed for multi-tile fonts"（跨 tile 字形是最难部分）。
- **"It would be more VRAM efficient to only copy in the glyphs that you are using at that time. This will take some management, though."** —— 官方教程直接点名：省 VRAM 的正道 = 按需拷当前用到的字形，代价是需要管理。

### 1.4 Q1 结论

1. **无一人用「RAM 整行位图缓冲再拷 VRAM」**。主流（FE8、MOTHER3、KaioShin DQ Monsters 范例 [仅搜]）全部逐字形直写 tile，读-改-写合并。
2. **11×11 无公开先例**（中文圈事实标准是 16×16 整盒；12×12 见于 NDS；12×12 紧排 2 字 3 tile 无任何文献记录），但同构问题（跨槽字形）有标准解，且 MOTHER3 有 11px 高先例、FE8 有 16px 跨 3 槽先例——**我们的 `blend_glyph_4bpp`（写砖 + 跨度整段重写 + 尾列清底）就是这个算法族**。
3. 真正的分水岭不在渲染算法，在**槽的生命周期**：FE8 的槽属于文本对象、bump 分配、重画回收——号的需用量 = 屏上字符数，与字库总量无关。

## 2. Q2：绕过/扩充 cb 区的逐项核查

| 技术 | 机制 | 实操证据 | 判定 |
|---|---|---|---|
| **HBlank 切 charBase** | BGxCNT 逐扫描线可写，上/下半屏指向不同块，等效一层 >1024 tile | 机制可行 [读原]（tepples FAQ、GBATEK）；逐行改 BG **滚动/仿射**有商业先例（Sonic Advance 3 BG3 水波 [读原] Copetti）；**切 charBase 本身：零商业先例**，且 VBA 不模拟 waitstate、"disastrous for code designed to run within Hblank" [读原] | 无先例 + 真机时序敏感，对话框场景收益低 |
| **HDMA 字模流送** | 每条 HBlank 272 周期（68 dots / 16.212μs）[读原 GBATEK]；IWRAM→VRAM 32bit 约 4 周期/字 ⇒ 每行实际 **约 60–70 字 ≈ 240–270 字节 ≈ 7–8 个 4bpp tile** | 调色板/滚动/仿射的 HDMA 案例很多 [读原]；**逐行流送 BG tile 的商业游戏：未找到** | 预算 7-8 tile/行 × 160 行，且 tile 8 行对齐约束；无先例 |
| **OBJ（精灵）文字** | OAM 128 项硬上限；每扫描线约 960 精灵像素 [读原 Tonc]；OAM 在 VDraw 锁定、只能 VBlank 更新 [读原] | homebrew 商业级 **Goodboy Galaxy** 源码有 `reserve_obj_multi(int n)` 注释 "(for text)" [仅搜 deepwiki]；商业游戏整段对话框用 OBJ 的逆向记录：未找到 | 只够人名/光标级小量；tepples FAQ 认可 "one sprite per letter" [读原] |
| **8bpp 跨块寻址** | 10bit 索引 × 64B/tile = 64KB，**一层可寻址全部 4 个 char block** [读原 Tonc: "you can actually access a total of four blocks!"] | 硬件特性，真实可用 | 唯一"真扩充"，但每块只 256 tile、容量持平（像素数不变）、调色板 16→256 色结构全变。**无净收益** |
| **借 OBJ 区 / 扩展 charblock** | 传闻 | [读原] 定论："On the emulators I've tested, this does indeed work. **On a real GBA, however, it does not.**"；10bit 索引 = 1024 是硬件死限 | **谣言，真机不可行，勿信** |
| **Mode 3/4/5 位图模式** | 无 tile 限制 | 真实用途仅 GBA Video、CPU 3D（Super Monkey Ball Jr.）、Doom/Wolfenstein 移植 [读原 Copetti/Tonc] | 对现有 tile 游戏等于重写渲染器，不可行 |

### Q2 结论

**cb 区扩充不存在。** 全部候选技术里：两个是谣言/不可行（借 OBJ 区、真机强写），两个无先例且预算/时序不友好（HBlank 切块、HDMA 流送），一个无净收益（8bpp），一个只够小量（OBJ）。

tepples FAQ 把 "dynamically modifying tile sets"（动态改 tile 集）列为写文字的正规方法 [读原]——**这才是所有人实际用的"绕过"：不绕墙，墙内轮换**。

**两条普查级结论**：

1. **没有任何工程把全字库静态塞进 VRAM**——物理上就不可能：GBA VRAM 共 96KB，3000 常用汉字 2bpp 点阵至少 192KB。实际做法一律是字库大图 + 码表驻留 ROM，**渲染时才把用到的字形写进原有文本 tile 槽**。
2. **公开文献里没有任何"中文字模与官方 UI 撞 tile 号"的案例**——不是他们解决了这个问题，而是**复用原引擎动态渲染通道的架构下这个问题不存在**（原来画假名的槽现在画汉字，槽号还是引擎自己的）。

唯一的反面教材是 SFC FE 中文的"强刷显存"：向硬件不允许的 VRAM 地址硬写，老模拟器放行、真机和精确模拟器上乱码——**靠模拟器不精确活着的方案**。

## 4. 对本工程的合成

### 4.1 我们的位置对照

| 维度 | 业界标准（FE8/MOTHER3/NDS） | 本工程现状 | 差距 |
|---|---|---|---|
| 跨槽字形渲染 | u64 移位 + mask/OR 读-改-写直写 tile | `blend_glyph_4bpp` 同族算法 | ✅ 已达标 |
| 11px 级字号 | MOTHER3 11px 高先例；FE8 16px 跨 3 槽 | 11×11 跨 2 槽（更简单） | ✅ 无先例但同构已证 |
| 字库驻留 | 全部在 ROM，按码寻址 | Big/Small/Middle 库在 ROM `0x094~097` | ✅ 已达标 |
| **槽的生命周期** | **槽属文本对象，bump 分配、重画回收、双缓冲防闪**；号需求 = 屏上字符数 | tm0/tm1 走全局池子（v33 段表），号需求随字数增长 | ❌ **唯一结构性缺口** |
| 与 UI 共存 | 复用引擎自己的槽 ⇒ 构造性无冲突 | 自造落址 ⇒ 撞 UI | ❌ 同上，是上一条的后果 |

### 4.2 这次调研真正的新增量

1. **FE8 一手源码**把"槽位管理"的标准形态展示到可照抄的程度：固定 128 槽、`subx = x & 7` 移位、bump 分配器、`InitTextDb` 双缓冲——之前 `调研_20260921b` 的"字形槽定号"结论（槽位数 S 有上界、加字不涨号）现在有了**官方引擎源码级的实证**。
2. **cb 扩充的系统性否定**：HBlank 切块 / HDMA 流送 / OBJ / 8bpp / 借 OBJ 区，逐项给出周期数、先例情况和真机定论——"绕过 1024 tile 墙"这条路**外部实操层面不存在**，以后不必再回头试。
3. **"撞 UI"问题是本工程特有的**：因为我们的 hook 在引擎的号空间之外自造落址；全行业的做法（复用引擎槽位）让这个问题构造性不存在。

### 4.3 与已判死项的对照（重要，防止误翻案）

- 「移植美版 text.c」的死刑**不被本次调研推翻**：死因是日版 4 种 textMode 语义与美版 3 种不对应、Window ABI 全错位（`复盘_20260909` / `移植失败缺陷台账_rh汉语引擎_20260920`）——全量移植确实不可行。
- FE8 证明的是**不需要移植引擎**：只需要借它的**槽位生命周期模式**（分配→用→重画回收），而这可以在我们现有 hook 内实现，不必动 `InitTextPrinter`/`PrintNextChar` 全家。

### 4.4 合成判据（本次调研的最终陈述）

> **渲染我们已经会了；墙也搬不走；业界唯一的路是"槽位轮换"——字库在 ROM，屏上用到的字按需写进引擎自己的文本槽，槽随重画回收。**
> 我们的 tm3（官方网格模式）从未撞 UI，正是因为它就是这个模式；撞 UI 的全是走自造池子的 tm0/tm1 窗口。方向收敛于：把 tm0/tm1 也纳入同一种槽生命周期，而不是继续给池子换区间。
