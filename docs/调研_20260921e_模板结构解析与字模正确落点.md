# 调研_20260921e · 窗口模板结构全解析与字模正确落点
> 方法：**逐指令反汇编原盘 + 静态全枚举**。本轮**零模拟器、零采样、零 gdb**。
> 全部结论可脚本复算（工具见文末）。这份文档推翻的是**号坐标系**本身，不是又一个分配算法。

---

## 0. 一句话结论

**我方字模的正确位置 = 该 BG 层的「块内号 `[514,1024)`」。**

这个号在不同 `charBase` 下自动指向不同物理块（`charBase+1`），**零换算、零探测、号有上界、加字不涨号**。
当前代码的人口划分是对的，**错的是段基址**：p0 用 384/946、p2 用 192/320——全在「本块内」，正好躺在引擎预取区里。p1 的 514 方向正确。

## 1. 窗口模板结构（本轮新判据，100% 交叉验证）

`ctrl` 模板表 `0x081BB3DC..0x081BB8BC`，**53 条，步长 `0x18`**。字段：

| 偏移 | 含义 | 证据 |
|---|---|---|
| `+0x00` | **bgId**（0-3） | `0x08002878` 用它查三张寄存器表 |
| `+0x01` | **charBase** | `0x08002878`: `cnt = tpl[3]\|(tpl[2]<<8)\|(tpl[1]<<2)`，GBA `BGxCNT` bit2-3 = charBase |
| `+0x02` | **screenBase** | 同上，bit8-12 = screenBase |
| `+0x03` | priority | 同上，bit0-1 |
| `+0x08` | font | `InitTextPrinter` → `win[0x0B]`(fontNum) |
| `+0x09` | **textMode** | `InitTextPrinter` → `win[0x0A]` |
| `+0x0C` | tileData | `0x06000000 + charBase*0x4000` |
| `+0x10` | tilemap | `0x06000000 + screenBase*0x800` |

**三张寄存器表**（`0x08002878` 的跳转表，已 dump 验证）：

```
0x081B343C → 04000008 0400000A 0400000C 0400000E   = REG_BG0..3CNT
0x081B344C → 04000010 04000014 04000018 0400001C   = REG_BG0..3HOFS
0x081B345C → 04000012 04000016 0400001A 0400001E   = REG_BG0..3VOFS
```

**交叉验证**：53 条的 `charBase*0x4000+0x06000000` 与 `tileData` 全等；`screenBase*0x800+0x06000000` 与 `tilemap` 全等（仅 4 条例外，全部可解释：key5 = OBJ 模板占位；key11/12/14 = 两窗口共享 tilemap）。

**⇒ 「界面配了哪些 BG 层、每层 charBase 多少」现在是 ROM 里的明文字段，静态可读，不必上机。**

## 2. 三条通路（本轮新判据）

| 函数 | 语义 | 调用点数 |
|---|---|---|
| `0x08004228(key)` | 注册表查表：`key → tpl_ptr`（线性遍历 `0x081BB8D4` 起，项 8 字节 `(tpl@+0, key@+4)`） | 6 |
| `0x08002C28(win, key)` | **建窗口**：填默认值 → 查表 → `win[0]=tpl`，从模板相位复制 `font/textMode/...` | **30** |
| `0x080027DC(key)` | **配一个 BG 层**：查表 → `*0x03000320=tpl` → `0x08002878` 写 `REG_BGxCNT` + HOFS/VOFS 清零 | **80** |

`0x080027DC` 的 80 个调用点的 `key` 全部为**硬编码立即数**，已全部提取（`.tmp/bg_layer_map.py`）。
**⇒ 「哪个界面配了哪几层、每层 charBase 多少」可直接枚举。**

**注册表 53 条 key 的构成**：tm0×15（官方自画）｜**tm1×34**（预取图集）｜tm2×1（OBJ）｜tm3×2（网格）。

## 3. 引擎预取写哪里（决定我方位置的唯一依据）

`0x08002950(tpl, tileBase≡1)` 配置单例 → `0x080029E0()` 分帧推进，`index` 遍历 `[0,256)`、每槽 2 砖：

```
写砖范围 = tpl->tileData + [1,513) * 32
         = [本块号 1..511]  +  [下一块号 0]
```

**⇒ 该层块内号 `1..512` 是引擎的；`513` 起了才是空地。**

**⇒ 我方占块内号 `[514,1024)` ⇒ 物理自动落在 `charBase+1` 块。**

（起 514 而非 513 的原因：槽步进 `CHS_SLOT_STRIDE=2`，槽头必须偶数偏移，`chs_tile_slot()` 会拒奇数。）

## 4. 三个人口的物理落点（互不重叠）

`chs_domain_of()` 已是「按 charBase 分人口」，**只要段基址统一为 514**：

| 人口 | 服务层 charBase | 槽号 = 514+2k | **物理块** |
|---|---|---|---|
| p0 | cb1（队伍/概况） | 514..1023 | **cb2** |
| p1 | cb2（多数界面） | 514..1023 | **cb3** |
| p2 | cb0 | 514..1023 | **cb1** |

**容量**：`k ∈ [0,254]`（514+2*254=1022，+1=1023 封顶）⇒ **255 槽/人口**。
对比现状 54 / 127 / 32 槽 —— **不是「挤出来一点」，是几何本身就允许 255**。

## 5. 当前代码错在哪（这就是「蛋被覆盖」的算式）

```
p0 段基址 384 / 946  →  cb0/cb1 块内号  → 在引擎预取区 [1,512] 内  ⇒ 必被覆盖
p2 段基址 192 / 320  →  cb0 块内号      → 同上                      ⇒ 必被覆盖
p1 段基址 514        →  下一块块内号    → 方向正确 ✓
```

**队伍页的文本层是 key3（`bgId=0, charBase=1, tm1`）**：`tileData=0x06004000`，引擎预取写 `0x06004020..0x06008020`。
而 p0 段 946 → `0x06004000+946*32 = 0x0600B640`，p1 段 514 → `0x0600C040` 附近……

**关键**：946 落在 `[0x06004020, 0x06008020)` 内 ⇒ **被引擎字模缓存重写**。这就是「队伍里的蛋被覆盖」的直接机制。
**它不是「没有地契」，是「站在了引擎自己的写字板上」。**

## 6. 「不撞」的静态判据（可复算）

设文本层 `charBase = C`，我方占 `C+1` 块。同界面另一 BG 层 `charBase = C'`：

| C' | 结果 |
|---|---|
| `C' = C` | 它的号 512..1023 也是 `C+1` 块 ⇒ **撞** |
| `C' = C+1` | 它的号 0..511 就是 `C+1` 块 ⇒ **撞** |
| `C' = C-1` | 只碰 `C` 块（引擎区），不碰我方 |
| `C' = C+2 / C+3` | **安全** |

**⇒ 冲突 ⟺ `C' ∈ {C, C+1}`。**

**实测（`.tmp/bg_layer_map.py`，80 个配层调用点 → 32 个界面）**：**32 个界面全部「下一块干净」，0 真实冲突。**

> 换言之：**引擎自己从不让两个 BG 层用相邻 charBase。** 我方只要站到 `charBase+1`，就天然不与任何一层冲突。
> （工具输出的 4 条 ⚠ 全部来自 `owner` 回溯失败点的错误归组，非真实冲突。）

这也顺带解释了：**tm3 从来撞不着**——它是 `key4/6`（`bgId=0, charBase=2`），下一块 cb3，而同界面只有一层。

## 7. 修复 = 段表三行（不是又一个分配器）

```c
/* 改前 */
chs_p0_seg_b[2] = { 384, 946 };   chs_p0_seg_n[2] = { 32, 22 }
chs_p1_seg_b[1] = { 514 };        chs_p1_seg_n[1] = { 127 }
chs_p2_seg_b[2] = { 192, 320 };   chs_p2_seg_n[2] = { 32, 32 }

/* 改后：三人口同一几何 */
chs_p0_seg_b[1] = { 514 };        chs_p0_seg_n[1] = { 255 }
chs_p1_seg_b[1] = { 514 };        chs_p1_seg_n[1] = { 255 }
chs_p2_seg_b[1] = { 514 };        chs_p2_seg_n[1] = { 255 }
```

**未决的实施细节**（都不是判据问题）：
1. `CHS_SLAB_KEYS_MAX = 224` < 255 ⇒ 需扩 slab 或把槽数定在 224。
2. slab 空间（`0x0203FFD2` 前）能否容下 `3×(255×8+255×4)` ≈ 9.2 KB —— 要复算静态断言。
3. 段表从「多段」退化为「单段」，`chs_tile_slot` 的反查逻辑可保留（单段是它的退化情形）。
4. 冲突判据（§6）应脚本化入仓，作为**构建期**检查（**不是运行时探测**）。

## 8. 为什么这不是「避让带 / 高水位」的 N.0 版

| | 避让带 / 水位 / 池子族 | 本方案 |
|---|---|---|
| 分区依据 | **采样若干屏 VRAM，取被引用砖求补集** | **引擎自己的公式：预取写 `[1,513)`** |
| 号需求 | `∑(每块字数)`，**无上界** | **510 号有上界，与字库总量无关** |
| 加场景/加文字 | 号线性增长 ⇒ 迟早不够 | **号不变**，只换槽内容（≈字形缓存） |
| 依赖 | 对**别人**行为的观测 ⇒ 不可靠 | 只依赖**我方私有**槽表 |

**§6 的冲突判据也是构建期一次性静态检查**（读 ROM 明文模板表），不是「每屏去探测」。
**这正是 tm3 已经在用、且一年来从未撞过的模式。**

## 10. 与既有结论的关系

- **推翻**：「存在一个全局官方占位区，我方要在里面找空档」——那个「占位区」是 `cap=512` 的误读。
- **保留**：「引擎预取是 tm1 唯一字模来源」（P32 停用仍正确）；「预取单例、只写一块」（仍正确，且**正是**本轮分区依据）。
- **保留**：v33「人口 = 窗口所在 BG 层的 charBase」（方向正确）。
- **否定**：p0/p2 现段基址；v8~v21 分配器族；一切「换区间」变体。
