# 窗口九宫格 + 字形缓存区实测定界（2026-09-21 晚）

> 一句话：**「引擎只占层内号 `[1,513)`，所以 514 以后是空的」这个前提是错的。**
> 引擎把**窗口九宫格边框**放在 `512..520`，我们的池子从 514 起，正好整块盖在边框上。
> 正确落点是 **`[521,1024)`**。

## 1. 怎么发现的

玩家截图：**设置页疯狂撞 UI + 领航员/训练家撞文字**。先排掉「测的 ROM 版本不对」，直接看
**原生 VRAM dump**（`.tmp/drive_*_vram.bin`，本来就有一堆，不用开模拟器）。

### 1.1 设置页只有一层 BG，却引用了 ≥512 的号

`drive_optIO.log`：`DISPCNT=0x7140` ⇒ 只开 **BG0**（+OBJ+窗口效果），
`BG0CNT=0x0F08` ⇒ charBase=2、screenBase=15（map @`0x06007800`）、4bpp。

把 BG0 的 32×32 map 逐格读出来（`.tmp/mapgrid.py optIO 0`）：

```
r01  0 0 515 516 [  1   3   5] 516 ... 517 0 0
r02  0 0 515 516 [  2   4   6] 516 ... 517 0 0
r05  0 0 515 516 [1 3 5 7 9 11] 516 ... 517
...
r13  0 0 515 516 [1 3 5 7 9 11] 516 ... 1 503 3 516 517
r00/r04/r19: [512 513×24 514] / [518 519×24 520]
```

* `512,513,514,515,516,517,518,519,520` 被 **358 个格子**引用 —— 少量号被反复引用 = **重复图案**；
* 每行交替 `1,3,5,…` 与 `2,4,6,…` ⇒ **竖直对 `(t, t+1)` = 一个 8×16 字形**，字距 2 号 = 1 列。

把 512..520 这 9 块砖按物理地址（`charBase*0x4000 + t*32`）取出来渲染
（`.tmp/optrender.py`）：

* `r_opt_all.png` = 用真实调色板重建的整层 —— **就是一扇带花纹边框的窗口**；
* `r_opt_hit.png` = 那 9 块砖本身 —— **蓝灰色虚线花边**。

⇒ **`512..520` 是窗口九宫格：`512=TL 513=顶 514=TR 515=左 516=fill 517=右 518=BL 519=底 520=BR`。**

我方池 `[514,1024)` ⇒ 514..520 全被我们写掉 ⇒ **边框碎掉 + 我们的字被边框重画覆盖**。
这就是「设置页疯狂撞 UI」。

### 1.2 原盘对照（排除「是我们写的」）

`drive_o_party` / `drive_o_sum` / `drive_o_sum2`（**原盘**，无我方 hook）的 `BG2(cb2)` map
同样引用 `512..520`，形态一致（r16=512/513…/514、r19=518/519…/520，内部填 516）。
⇒ 这是**引擎自己的美术**，不是我们写的。

### 1.3 全 dump 扫描：≥521 一个都没有

`.tmp/hirefs.py` 遍历 `.tmp/drive_*_vram.bin` 全部层，列出 map 引用号 ≥521 的 —— **空**
（唯一例外：原盘开始菜单 `o_menu BG0(cb2)` 用 `537..539 / 603..611`，但那一层是 **tm3**，
走官方 30 格网、根本不经过本池）。

## 2. 字形缓存区的真实几何（反汇编 + EWRAM 实测）

### 2.1 `0x08002950` 逐指令（`scripts/jp_dis.py 0x08002930 352`）

```asm
08002950: push {lr}
          r3 = r0                                   ; win
          [0x0300032E] = 0                          ; 计数器清零
          [0x03000328] = win[0x00]                  ; 模板指针（单例）
          [0x0300032C] = r1                         ; tileBase（单例）
          win[0x16]    = r1                         ; ★TILE_BASE
          font = 模板[+0x08]
          font > 5 → return 0
          跳转表 @0x080029B0：font1 → +512 ; font4 → +512
                              font2/3/5 → +256 ; font0 → 0
080029CC: movs r0,#128 ; lsls r0,#2  → 512
080029D2: movs r0,#128 ; lsls r0,#1  → 256
```

⇒ `0x08002950` = **配置本窗口字形缓存区**：写下 `TILE_BASE`，并按 font 报告该缓存**需要多少槽**
（`2×槽数` 块砖；fn2/3/5 → 512 砖；fn1/4 → 1024 砖）。

### 2.2 EWRAM 实测（`.tmp/ewwin.py`）

用「`win[0x00]` 必须落在模板表 `[0x081BB3DC,0x081BB8D4)`」做硬过滤，捞出活跃窗口：

```
optIO (设置页) tpl#49 tm=1 fn=3  TILE_BASE=1
o_party(队伍页) tpl#07 tm=1 fn=3  TILE_BASE=1
o_menu (开始菜单) tpl#06 tm=3     TILE_BASE=1
```

槽 k 占砖 `(TILE_BASE+2k, TILE_BASE+2k+1)` ⇒ fn=3 的缓存区 = **`[1,513)`**。
实测设置页 map 用到 `503/504`（= 槽 251）、原盘队伍页用到 `253/254`（= 槽 126）
⇒ **这一段是真的被引擎用到接近满的**，我方塞不进 `[1,513)` 内部。

### 2.3 于是两段之间只剩「边框之上」

```
层内号布局（charBase=2 的文本层，实测）
  [   0,    1)  slot 0 首砖 / 空白
  [   1,  513)  引擎字形缓存区（fn2/3/5：256 槽 × 2 砖）
  [ 512,  521)  窗口九宫格  ← v10/v38 的池从这里第 3 格开始，必撞
  [ 521, 1024)  空 —— 全 dump 扫描零引用 ⇒ 我方池
```

## 3. tm3 网格（顺带钉死，解释「tm3 从不撞」）

原盘开始菜单 `mapgrid.py o_menu 0`：窗口在 22..29 列，边框 = `603..611`；
文字行**成对**出现，下半行的号 = 上半行 **+30**：

```
r02  606 [86 87 88 89] 607 607 608      ← 上半 8 行
r03  606 [116 117 118 119] 607 607 608  ← 下半 8 行 = 86+30 …
r04  606 [147 148 149 150] …            ← 下一行（+31）
```

⇒ glyph = `(t, t+30)`（两行 map = 一个 8×16 字形）、网格宽 **30**、`TILE_BASE=84`（首字 = TB+2 = 86）。
与渲染层 `chs_lower_delta(tm3)=30`、`chs_tm3_grid_tile()` 完全吻合 ⇒ **tm3 一直是「号 = 位置」，
用的是引擎自己的坐标系，所以从来没出过撞 UI**。这也反证：**只要用引擎自己的号，就不会撞。**

## 5. 尚未解决（下一步）

设置页**除了撞边框，还有第二层「撞文字」**：
该屏 map 里**所有文字行都指向同一批槽 `1..12`**（每行 6 个字形都一样 ⇒ 全页文字塌成同一批字形）。
对照 `t_party`（汉化版，只画一次的窗口）：map 里我方池号 `584/585…` **保留完好**。

⇒ 推测：设置页那种**会被反复重画**的窗口，引擎在重画时**用自己的缓存槽号把 map 表项盖掉**；
而 tm1 的字形像素来源是引擎预取 `0x080029E0`。若成立，则 tm1 的正解不是「另领号」，
而是**让引擎自己的槽里装我们的字**（hook 字形写入侧，而非分配侧）。
待核：① 谁在重写这张 map（哪个函数/哪一帧）；② 该屏窗口是否每帧 reprint。
