# GBA 文本渲染原理

> 跨游戏共用的原理层。具体游戏的函数地址、tile 常量、字库布局见各 `docs/{gameId}/`。
> 这些结论决定了「哪些方案一定行不通」，动手前先读完。

---

## 1. 三层结构：谁打字节 / 谁摆格号 / 谁解释

| 层 | 是什么 | 在哪 |
|---|---|---|
| 文本打印器 | 一个窗口结构（习惯叫 `win` / TextPrinter）：模板、状态、字号、颜色、文本指针、光标、tile 基号 | RAM（如 `0x0202xxxx`） |
| 模板 | 指向 `tileData`（写内容的目标）+ `tilemap`（格号数组，NULL = 缓冲直绘）+ 调色板 + 默认色 | ROM/RAM |
| 硬件解释 | BG 控制寄存器给出的 charBase / screenBase / 色深（4bpp） | `0x04000008` 等 |

**核心三要素必须一致**：

1. 写字模的 VRAM 基址（`tileData`）
2. tilemap 里写的 tile 格号
3. 硬件按 charBase 实际解释的地址

只改其中一方 → 花屏 / 字看不见 / 图被改坏。

---

## 2. 原版模型：固定字库 + tilemap 引用（**不是**往 VRAM 画字）

- 原版字形 tile 是 ROM 里的固定数据，一次画好，永不改写。
- 打印时只做两件事：把光标推进，往 tilemap 写一个**已存在的 tile 号**。
- 因此**同一个字全屏共用同一个 tile**：5 行×7 字 = 35 个显示位，实际只有 7 个不同汉字 → 只占 14 个 tile。
- 破折号等重复符号同理（5 格共用 1 个 tile）。

## 3. 汉化模型：字模要现场写进 VRAM

- 汉字字符集远大于原版假名表，不可能预置全部字形。
- `F7 00 hi lo` 指向字库码位 → 打印时把该字形**写进 VRAM**，再让 tilemap 指向它。
- 于是 tile 变成「有内容、会被改写」的资源 → tile 冲突、跨行覆盖、窗间抢占全部由此产生。

**这就是为什么不能照抄原版公式**：原版公式假设 tile 是稳定符号，我们的 tile 是可变数据。

---

## 4. 12px 的真相：每字 2 列 = 4 个 tile

| 事实 | 说明 |
|---|---|
| 字宽 12px + 1~2px 空 → 占 2 个 tile 列 | GBA tile = 8px，12px 必然跨 2 列 |
| 上下两片各 2 tile → 每字 **4 个 tile** | 16px 高字形分两行写 |
| 与字号无关 | 12px「装不下」不是错的，8px 也占 2 列 |

**火红与红宝石同构**：火红实测 12px 墨宽、13px 步进、每字 4 tile、tile 号按**屏幕列**连续递增
（不是按字分配）；红宝石原版公式 `TILE_BASE + TILE_OFFSET + 2*x + y` 是同一个思路。
差别只在：火红把这 4 个 tile 放在自己独占的 char block 里，所以不撞 UI。

## 5. 为什么需要 textMode 分派

同一个游戏里，不同窗口走不同落址路径：

| 典型 textMode | 场景 | 落址方式 |
|---|---|---|
| 0 | 对话框/战斗/菜单项 | `TILE_BASE + TILE_OFFSET` 线性，每字 +2 |
| 1 | 需要分配 tile 的（图鉴列表等） | 网格 `band*62 + 2*col` |
| 2 | 血条等小字窗 | 写 `win[tileData]` 缓冲，字号 8px |
| 3 | 菜单/存档框 | 同网格（沿用原版路径） |

**结论**：汉化层必须按 textMode 分派，不能全局套一种落址；也不能只改 textMode 而保留旧路径的唯一分支。

---

## 6. 由此推出的硬约束（跨游戏通用）

1. **不能换 charBase 给文本私有 char block**：很多 GBA 游戏在解压图形时**硬编码绝对地址**
   （如 `0x06008000`），改 BG 的 charBase 后游戏写的图形落到别处 → 花屏。判定方法：统计 `BGxCNT` 写入点，
   若绝大多数写的是固定值、极少改写，说明硬件解释被写死。
2. **不能只改模板的 `tileData`**：三要素必须同时改且互相对齐。
3. **不能按字符做 glyph 缓存**（同字共用 tile）：与「tile 号 = 屏幕行列的纯函数」互斥；
   且汉字集 × 4 tile 远超一个 char block 容量。
4. **不能用「抬水位/改段宽」解决溢占**：行号是累计值（列表可到 30+ 行），16~18 行 × 31 列装不进几百个 tile。
5. **不能靠缩短译文解决布局**：布局问题在引擎/表结构解决，改译文属改数据迁就渲染。

---

## 7. 判定「字为什么没显示」的顺序

1. 字符有没有被打印器消费（`text_index` 是否推进、返回值是否 =1）。
2. 落址算出的 tile 号是否 `>= 上限`（如 `0x1F0`）。
3. 该 tile 的 VRAM 内容是不是这个字的字模（dump 比对）。
4. tilemap 格号是否指到了这个 tile（谁覆盖了）。
5. 硬件解释的 charBase 是否指向写内容的基址。

按这个顺序查，比"猜字号/猜颜色"快得多。
