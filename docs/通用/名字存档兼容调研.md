# 训练家名 / 宝可梦名：显示汉化且串档不乱

> 目标：中文名在汉化版里正常显示，同时**存档字段保持原版编码**，
> 这样存档串回日版/美版游戏不会变乱码。
> 调研日期 2026-11-23。样本：火红日版汉化 2.2、本工程 red 侧现状、master 的 SLT2（已废弃）。

---

## 1. 问题本质：两件事被混在一起

| 层 | 内容 | 应该存在哪 |
|---|---|---|
| **显示** | 屏上要出现「妙蛙种子」「小智」 | 可随意用中文编码（F7 00 hi lo） |
| **存档** | `struct Pokemon.nickname[10]`、`SaveBlock.playerName[8]` | **必须保持原版编码**，否则串档乱码 |

Gen3 的字段是**定长**的：

- `nickname[10]` — 10 字节。中文 3 字 = 12B（每字 `F7 00 hi lo`）⇒ **塞不下**
- `playerName[8]` / `rivalName[8]` — 8 字节，同理

所以「直接写中文进存档」必然要么截断（残字），要么写坏后续字段。
**这就是用户说的「保存存档时把汉化编码写进去，串回日版变乱码」的根因。**

## 2. 火红汉化 2.2 的做法（实测，2026-11-23）

样本 `roms/translated/宝可梦火红日版汉化2.2.gba`（16 MB，日版 BPRJ 打底）。
对照 `roms/origin/POKEMON_FIRE_BPRJ00.gba` 逐字节 diff：678,922 字节不同，
2,295 个 >64B 的差异块。

### 2.1 中文文本整块搬到新区

汉化在 `0x6D0000` 起新增了大段文本（日版该区全是 `FF` 空白）。
编码与本工程一致：`F7 00 hi lo`。

```
汉化 0x6D0000: f7 00 35 f7 00 36 f0 f7 00 97 ab f7 00 8b f7 00 8b ab fe ...
日版 0x6D0000: ff ff ff ff ff ff ff ff ff ff ...
```

### 2.2 核心手法：**改指针，不改原表**

日版 `0x16F744` 处是一个数据表指针，原值 `0x0816F9FB`（原有日文表）；
汉化版把它改成 **`0x086D0000`**（新增的中文表）：

| 位置 | 日版 | 汉化 2.2 |
|---|---|---|
| `0x16F744` | `0816F9FB` | `086D0000` |

⇒ **原表一个字节没动**，只是把「读哪张表」的指针换了。
这与本工程在 `docs/FIRERED_BPRE00/00-12px与昵称参照.md` 里记录的
「原版日文名表一个字节没动 / 新增 412 项指针表 / 只改 9 处读点」完全吻合。

### 2.3 配套：中文变长字符串的长度函数

火红汉化在 `0x1DB554`、`0x1DB55C`、`0x1DB564` 三处放了标准 Thumb 跳板
（`00 4B 18 47` + 目标地址），指向新增函数 `0x7C0001` / `0x7C0199` / `0x7C01BF`。
日版这三处原是空白，属于**纯新增**。

`0x7C0000` 反汇编（手工解码）：

```
push {r4,r5,lr}
mov  r4,r1          @ 保存 src
mov  r5,r0          @ 保存 dst/计数
movs r0,#0
loop1:
  ldrb r3,[r1]
  cmp  r3,#0xF7     @ 中文前缀？
  beq  f7_path
  sub  r3,#0xA1     @ 日文半角/全角区间判断
  cmp  r3,#9
  bhi  ...          @ 超出 → 走 FF 判断
  adds r1,#1
  adds r0,#10       @ 每个日文字符计 10（=0x0A）
  ...
f7_path:
  adds r1,#3
  adds r0,#12       @ 每个中文字符计 12
  b    loop1
end:
  ldrb r3,[r1]
  cmp  r3,#0xFF     @ 结束符
  beq  done
```

**关键点**：中文字符占 12 字节，日文占 10 字节，长度函数必须分别对待。
火红原版没有中文，所以它的长度函数只认日文；汉化必须换掉。

### 2.4 字体：函数指针表挂载

`0x742148` 在日版是 `FFFFFFFF`，汉化改成 `0x081DB3EF`（12px 绘制函数）。
与本工程文档记录的火红 12px 挂载方式一致（不走 `bl`，走指针表）。

## 3. 本工程 red（AXVJ）现状

### 3.1 宝可梦名 —— 已按火红思路解耦 ✅

| 位置 | 实现 | 存档影响 |
|---|---|---|
| 战斗血条名 | `NickFullName_entry.s`：`GetMonData(mon,11)` 取 species → `0x09EB0AF4 + species*24` | **无**（不碰 nickname） |
| 遭遇「野生的XXX」 | `NickSlot_entry.s`：替换 `0x0811C7AA` 的 `GetMonData(mon,2,sp)` | **无** |
| 摘要页 | `SummaryScreen_PrintNicknameGender_entry.s` | **无** |

⇒ 宝可梦名已经是「显示查表、存档不动」。**队伍界面只是还没接这条路**。

### 3.2 训练家名 —— **未解耦** ❌

现状是从数据侧「扩 stride」：

```
docs/POKEMON_RUBY_AXVJ00/10-文本与数据.md:
  训练家名 11 -> 44（扩 stride）
  训练家个人名（名槽 4..8 存 u32，拷贝 5B -> 21B）
```

这是**改数据表布局**，不是运行时解耦。问题：

- 存档里的 `playerName[8]` 仍是定长字段，写中文必须截断或溢出；
- 溢出就会写坏相邻字段 ⇒ 串档乱码。

### 3.3 SLT2 为什么被放弃（master 时代的旧法）

`f33208f`「彻底删除 F9 80 短语表与 SLT2 运行时查表」：
SLT2 = 短语表 + 运行时递归查表（`F9 80` magic + 5B 短语退路）。
弃用理由（从提交记录可见）：编码不统一、要维护短语码分配、要递归查表、
还要保留 5B 退路 —— 复杂度高而收益不明确。

⇒ **SLT2 不是火红思路**，用户的「不太优化」判断成立。
火红思路是「指针重定向 + 显示层换表」，不需要运行时短语解析。

## 4. 结论：应该怎么做

### 4.1 宝可梦名（已有基建，可直接用）

沿用 `NickFullName` 的模式：**加一处「按 species 查中文名表」的 hook**，
接到队伍界面。存档完全不碰。

### 4.2 训练家名（需要新增解耦层）

推荐（火红式）：

1. **存档仍写原版编码**——`playerName[8]` 写玩家真实输入（日文/拉丁）；
2. **显示时查表**——`名字 hash / 固定玩家名表 → 中文串`；
   剧情里出现的固定 NPC 名（如对手、博士）走「指针重定向到中文表」；
3. 玩家**自定义名字**没有表可查，需保留「用原版编码显示」的兜底
   （即自定义名不做汉化，或做运行时音译表——后者不在本次范围）。

⚠ 关键取舍：**玩家自己输入的名字无法「既中文显示又原版存档」**，
除非引入额外的映射区（那就会写进存档）。火红的实际做法是
固定名查表、自定义名保持原样。
