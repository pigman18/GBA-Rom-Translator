# 队伍字体：火红做法调研（2026-11-23）

## 结论先行

**火红名字 = 9px 墨迹宽 / 10px 步进；我们的 Small = 8px 宽 / 8px 步进。**
**高度完全一样（都是 9px）。**

**「蛋」显示残缺的真正根因不是渲染，是 BDF 源本身就坏了**：
`small.bdf` 里「蛋」的墨迹只有 7px 宽、结构完全失真（实测见下）。

**最终做法：步进保持 8，把 BDF 源从 SimSun 换成 Unifont + 整框 OR 降采样到 8×9。**
（10px 步进在 tilemap 路径下已验证不可行，见 §5；渲染层未改动。）

---

## 一、实测数据（不靠注释，全部自己量）

### 1.1 屏幕上的实际字宽（逐像素扫描）

| 样本 | 墨迹列段 | 单字宽 | 字间距 |
|---|---|---|---|
| 火红「喷火龙」 | x=128..136 / 138..146 / 148..156 | **9 px** | **10 px** |
| ruby「蛇纹熊」 | x=128..151（三字粘连成一整块） | 8 px | 8 px |

火红：`9px 墨迹 + 1px 空隙 = 10px 步进`
ruby：`8px 墨迹 + 0px 空隙 = 8px 步进` ← **字与字直接贴在一起**

### 1.2 字库 bin 里的实际字模（`dump_font_slots.py` 的正确读法）

关键：tile 顺序是 **TL(0) / TR(1) / BL(2) / BR(3)**，`tile = (x>>3)*2 + (y>>3)`。
（我最初按 TL/BL/TR/BR 读，全部读错，浪费了大量时间。）

`蛇` gidx 0x0BBD：
```
Small  墨迹 x=1..8  (宽 8)  y=6..14 (高 9)  ← pad_top=6
Normal 墨迹 x=0..10 (宽 11) y=2..12 (高 11) ← pad_top=2
```

### 1.3 small.bdf 源文件里的字形（问题的根源）

`parse_bdf` 读出的「蛋」：
```
.######.........
.#.####.........
.####...........
#...#...........
.######.........
.######.........
...####.........
######.#........
```
**只有 7px 宽，完全看不出「蛋」的结构**（13 画被压进 7×8）。
「妙」「蛇」同样失真。

### 1.4 SimSun 内嵌点阵只有 12/14/16/17px 档

```
simsun.ttc strike: 6x12, 7x12, 7x14, 8x14, 8x16, 9x17
```
**没有 9px 档。** 所以 `gen_chs_bdfs.py` 里 `small: ink 9x9` 实际是把 12px 点阵
**缩小**到 9px（再被 build 裁到 8px），必然糊。这不是渲染 bug，是源数据质量。

## 二、火红怎么做（全网调研）

来源：百度贴吧《悠然大佬火红字库补丁解析》（作者逐行反汇编标注）

1. **火红字库有两套，各占 0x6D780 字节**
   - 大字库 `0x00000-0x6D780`
   - 小字库 `0x80000-0xED780`
   - 两套之间 0x12890 字节空位

2. **小字库不是 8×8，是 8×16 区域**
   - 字符码表分布：`0x0100-0x01F6`、`0x0200-0x02F6`、…、`0x1E00-0x1E5D`
   - 一级汉字 3775 + 二级 3008 = 6763 字（GB2312 全集）

3. **显示流程**：找码值 → 找 tile 数据 → 交给**原渲染程序**（不自己画）

4. **★ 关键：`0x217619` 处的代码专门控制中文字符的显示宽度**
   - 火红改的就是这个值，把步进从 8 改成 10
   - 这是「同一套 tile 网格，靠改步进常量放大字距」的做法

5. 另有 4 处把战斗画面的字体调大

**与我们做法的对应关系**：
| 火红 | 我们 | 差异 |
|---|---|---|
| `0x217619` 控制中文显示宽度 | `CHS_GLYPH_ADVANCE_SMALL = 8` | 改成 10 即可 |
| 小字库 8×16 区域 | 16×16 槽 / 128B | 我们槽更大，够用 |
| 两套字库（大/小） | Normal 12px + Small 8px | 同构 |

## 三、可行性（已算过）

**窗口容量**：队伍窗口 `width=8` 格 = 64px。
- 9px 墨迹 + 10px 步进：6 个字占 59px ✅ 装得下
- 当前 8px 步进：6 个字占 48px

**引擎改动面**：`grid_phase_adv` / `grid_phase_for` / `grid_draw_chs` 的
`delta = (phase + adv) >> 3` 会自动跟随 `adv`，改常量即可。
但 `adv=10` 时每字跨列数 `ncols = (phase+10+7)>>3` 会在 1/2 列间切换，
需要实测确认 `grid_emit` 的跨列拼接正确。

## 四、最终方案（2026-11-23 定案）

### 4.1 步进保持 8，改字库源

试过 10px 步进三版全失败（详见 §5），结论：**tilemap 整格映射无法表达
「一格内两字共享」**。火红能做到 9px 是因为它按像素直写 VRAM 缓冲。

本工程保持 8px 步进，从**字库质量**解决：

| 项 | 旧 | 新 |
|---|---|---|
| BDF 源 | SimSun 12px 缩到 8px | **Unifont 原生 16×16** |
| 降采样 | 左上角裁切 | **整框 OR**（块内任一像素有墨迹即算） |
| ink | 8×8 | **8×9**（宽度仍限 8，高度用满 9） |
| 主墨宽 | 9px（被裁掉 1 列） | **严格 8px**（完整显示） |

### 4.2 为什么必须换 Unifont

SimSun **没有 9px 点阵档**（实测 `available_sizes` 只有 6x12/7x12/7x14/
8x14/8x16/9x17），把 12px 压到 8px 后复杂字彻底糊掉：

```
蛋（SimSun 8px）:     蛋（Unifont OR 8x9）:
.#######             .#######      ← 上「疋」
.#.####              ..#.#..#
.####                ..#.###.
#...#                .#######
.######              #...#...      ← 下「虫」
.######              ..#####.
...####              ..#####.
######.#             ..#.#.#.
                     .#######
```

### 4.3 为什么用 OR 而不是面积投票

Unifont 笔画只有 1px 宽，15×15 压到 8×9 时落在 2×2 块里只占 25%。
实测 50% 阈值：「土」只剩左竖，字形散架；60% 阈值更糟。
**OR 保证笔画连续**，代价是笔画略粗 —— 8px 下这是可接受的权衡。

### 4.4 关键发现：字库不是从 bin 读的

`configs/<game>/fonts/*.bdf` 是**打包时实时生成**字库的来源
（`engine.py:_resolve_slot_bdf`）。直接替换 `graphic/fonts/*.bin` **无效**
（我一开始踩了这个坑，白跑了好几轮）。

正确改法：
1. `scripts/font/unifont_to_small_bdf.py` 生成新的 `small.bdf`
2. `font.config.json` 里 `Small.ink` 改 `8x9`

### 4.5 逐槽阴影开关（2026-11-24）

全局 `shadow` 已移除，改为 `font_slots[].shadow` 逐槽配置，**默认 false**。

**★ 三套字库都必须 false**，原因不是「装不下」，而是**双重阴影**：

渲染层 `grid_draw_chs` 已经**程序化补**阴影 —— 它把墨迹右下 1px 先铺
E 色（shadow），再把 C 色（主墨）压在上面。这是为了对齐 origin 的三色
预渲染字模（pal9/pal15 实测 1/8/15）。

字库若再自带一层阴影，两层叠加：

```
字库自带阴影 + 渲染层补阴影   →   字形糊成一团
```

实测症状（2026-11-24，Normal 误设 true）：开始菜单「继续游戏」四个字
整片糊掉、笔画全连成块；「玩家」「时间」「徽章」同样糊。改回 false 后
立即恢复正常，阴影只剩右下 1px。

| 槽 | ink | 步进 | shadow | 说明 |
|---|---|---|---|---|
| Normal | 12x12 | 12 | **false** | 渲染层已补，不可重复 |
| Middle | 9x11 | 9 | **false** | 同上 |
| Small | 8x9 | 8 | **false** | 同上 |

配置方式（`font.config.json` 的 `font_slots[]` 每项加 `shadow` 字段）：
```json
{ "label": "Normal", "ink": "12x12", "shadow": false }
{ "label": "Middle", "ink": "9x11",  "shadow": false }
{ "label": "Small",  "ink": "8x9",   "shadow": false }
```

这个开关留给将来「字库直出三色预渲染、渲染层不再补影」的场景。

实现：
- `build_chinese_font.py` 新增 `--shadow-map LABEL=0|1`（优先级高于 `--shadow`），
  `--shadow` 默认值由 true 改为 **false**。
- `engine.py` 逐槽读 `slot["shadow"]` 组 `--shadow-map` 参数；全局
  `fp_cfg["shadow"]` 只作兜底（仅 slot 未写时生效，且只有 `is True` 才传 `--shadow`）。
- 标点 patch 段改为按 bin 名匹配槽，逐槽决定是否传 `--no-shadow`。

产物实测：Small=[15] 无阴影 / Normal=[14,15] 有阴影 / Middle=[15] 无阴影。

## 五、10px 步进三版失败记录（别再重走）

| 版本 | 改动 | 结果 |
|---|---|---|
| v1 | 只改 `CHS_GLYPH_ADVANCE_SMALL` 8→10 | phase 序列对（0,2,4,6），但每字仍 8px |
| v2 | `rel` 改为从累计宽度派生（`width>>3`） | rel/phase 自洽，仍 8px |
| v3 | `WIN_TILE_OFFSET` 让 tile 号跳 2 | tilemap 变 159/163/167，仍 8px |

**根因**：字 0 的 p1（第 9 列，写 col+1 像素 0）会被字 1 的 p0 覆盖，
而 `grid_load` 的挑回只从**当前 tile** 读，读不到字 0 写在 p1 的像素。
tilemap 整格映射无法表达「一格内两字共享」。

诊断数据（`-DGRID_DIAG`，落 `0x0203E000`）：
```
[54] gidx=0x09BD phase=0 rel=0 col=16 t0=159   ← 蛇
[56] gidx=0x0B8C phase=2 rel=1 col=17 t0=161   ← 纹
[58] gidx=0x0C67 phase=4 rel=2 col=18 t0=163   ← 熊
```
phase 完全正确，问题只在 tile 内容互相覆盖。
